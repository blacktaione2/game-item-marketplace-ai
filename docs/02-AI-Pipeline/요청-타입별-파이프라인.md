# 요청 타입별 AI 파이프라인

이 프로젝트의 설계 목표는 **"LLM API를 감싸기만 한 서비스"가 되지 않는 것**이다.
모든 요청을 하나의 LLM 호출로 흘려보내는 대신, 요청 종류를 먼저 판별해서
**종류마다 다른 파이프라인**을 태운다. 레이턴시와 비용을 요청 타입 단위로
통제하기 위해서다.

이 문서는 ADR-0008 ~ 0018에 흩어진 결정을 하나의 흐름으로 묶은 것이다.
개별 결정의 근거는 각 ADR에 있고, 여기서는 **무엇이 어떤 순서로 실행되는가**와
**각 단계가 무엇을 보장하지 않는가**를 다룬다.

## 전체 흐름

```
POST /api/assistant
      │
      ├─(0) 인증 ────────────────── 토큰 없음/무효/만료 → 401
      │      tenant_code가 여기서 나온다 (요청 본문이 아니라 클레임)
      │
      ├─(0) 요청 한도 ───────────── 20회/분 초과 → 429 + Retry-After
      │      키는 tenant + user. **분당은** 캐시 조회보다 앞이라 적중도 센다
      │
      ├─(1) 시맨틱 캐시 조회 ────── 적중 → 즉시 반환 (llm_calls = 0)
      │                              **적중이면 일일 예산을 안 쓴다** (ADR-0044)
      │
      ├─(2) Intent Router
      │      규칙(정규식) → 애매하면 KoELECTRA → 확신도 낮으면 COMPOUND
      │
      ├─(3) 의도별 분기
      │      faq_smalltalk  → 정적 응답            (LLM 0회)
      │      item_search    → 검색 파이프라인       (LLM 2회 — 질의이해 ‖ 도메인판정)
      │      price_forecast → LSTM/Cold Start      (LLM 3회 — 위 둘 + 설명)
      │      anomaly_check  → Autoencoder          (LLM 1회 — 검색을 안 탄다)
      │      compound       → 에이전트 (MCP 도구)   (LLM 1~6회 = 도구 호출 수 + 1)
      │
      └─(4) 정책에 따라 캐시 저장
```

### 두 한도가 서로 다른 것을 막는다 (ADR-0044)

| | 목적 | 캐시 적중 | 세는 시점 |
|---|---|---|---|
| **20회/분** | 부하·남용 차단 | **센다** | 요청 **앞** (의존성) |
| **50회/일** | **LLM 비용** | **안 센다** | 응답 **뒤** (`consume_daily`) |

분당까지 적중을 빼면 캐시되는 질의 하나로 서버를 무한정 두드릴 수 있다.
반대로 일일 한도가 적중을 세면 **비용 0인 요청이 비용 한도를 깎는다** — 그리고
그건 이론이 아니라 실제로 닿던 경로다. 프론트가 배지를 정직하게 유지하려고
`staleTime` 을 안 걸어서(ADR-0037), 아이템 상세에 들어갔다 돌아올 때마다 재요청이
나간다. 서버는 25.9ms 에 캐시로 답하는데 하루치는 깎였다.

대가는 검사와 증가 사이의 동시성 누수인데, 이 계층은 하루 단위에서 고정 윈도우의
2배 누수를 이미 수용하고 있어 같은 크기다.

`‖` 는 `asyncio.gather` 로 동시에 나간다는 뜻이다 — **비용은 2회인데 지연은
느린 쪽 하나치**다(ADR-0039). 그래서 `llm_calls` 로는 분기 안에서 무슨 일이
있었는지 알 수 없다: 0건이든, 결과가 있든, 도메인 밖이든 검색 분기는 전부 2다.
`no_results` / `out_of_domain` 플래그를 봐야 한다.

구현: `app/services/assistant/pipeline.py`

### 진행 상황은 이 단계들을 그대로 흘린다 (ADR-0044)

`POST /api/assistant/stream` 이 위 (1)~(3)을 **일어나는 대로** SSE 로 내보낸다.
흘리는 것은 **토큰이 아니라 단계**다 — 복합 질의의 7~25초는 대부분 도구 호출이라
토큰만 흘리면 마지막 1~2초만 빨라 보인다.

`tool` 이벤트는 도구가 **끝났을 때가 아니라 시작할 때** 나간다. 완료 시점에만
알렸더니 11.1초짜리 도구 실행 내내 *"도구를 고르는 중"* 이라는 틀린 라벨이 떠
있었고, 그 응답 자신의 `agent_tool_ms` 가 그렇다고 말해줬다. **캐시 적중도 같은
스트림으로 온다**(`cache` → `done` 즉시) — 적중일 때만 일반 응답을 주면
클라이언트에 코드 경로가 둘 생기고 아끼는 것은 25.9ms 다.

이벤트 형식은 [API 명세](../03-API-Specs/API-명세.md)에 있다.

### 분기가 스스로 물러선다

시세·이상거래 분기는 **대상 id가 있어야 실행된다.** 그런데 `"이거 얼마?"`처럼
대상을 지칭하지 않는 질의도 규칙에서는 시세 문의로 확정된다.

그래서 각 분기가 **자기가 실행 가능한지 먼저 확인하고, 안 되면 COMPOUND로
올린다.** 라우터를 완벽하게 만드는 대신 분기가 스스로 물러서게 하는 쪽이
현실적이다 — 에이전트는 검색부터 시작할 수 있으니 어차피 답을 낸다.

응답의 `routing.initial_intent`와 `intent`가 다르면 에스컬레이션된 것이다.

## (1) 시맨틱 캐시

`app/services/cache/` · ADR-0012

**기본은 정확 일치이고, 유사도 매칭은 `faq_smalltalk`에만 열려 있다.**

이유는 실측이다. 이 코퍼스의 질의-질의 유사도로는 **"같은 질문"과 "다른 질문"이
분리되지 않는다.**

| 쌍 | 코사인 유사도 |
|---|---|
| 함정 쌍 (`+8 롱소드 시세` vs `+9 롱소드 시세`) | **0.9787** |
| 동의 쌍 (표현만 다른 같은 질문) | 0.845 |

**함정 쌍이 동의 쌍보다 유사도가 높다.** 파인튜닝 모델과 베이스 모델 모두
그랬으므로 파인튜닝 부작용이 아니라 짧은 질의에 대한 문장 임베딩의 성질이다.
그래서 유사도 매칭을 **오탐 대가가 작은 곳에만** 허용한다.

### 의도별 정책

| 의도 | 캐시 | TTL | 유사도 매칭 |
|---|---|---|---|
| `faq_smalltalk` | O | 24시간 | **O** |
| `item_search` | O | 10분 | X |
| `price_forecast` | O | **다음 자정까지** | X |
| `anomaly_check` | **X** | — | X |
| `compound` / `unknown` | O | 5분 | X |

- `price_forecast`가 자정 만료인 이유: 예측이 일별 시세 시리즈 기준이라
  날짜가 바뀌면 근거가 바뀐다. 고정 TTL이면 자정 직전 값이 다음 날까지 산다
- `anomaly_check`를 캐시하지 않는 이유: 단건 판정이라 재사용될 일이 거의 없고,
  유사 질의로 잘못 히트하면 그게 곧 보안 오판이다

### 응답 내용에 따른 예외 — 0건 응답은 저장하지 않는다

ADR-0016. `is_cacheable(intent, response)`가 `no_results` 응답을 거부한다.

- 0건 판정의 근거인 필터 추출이 완전히 안정적이지 않다(약 1.1% 오추출).
  질의 문자열로 캐시하면 여러 추출 중 하나를 TTL 동안 고정하게 된다
- **0건은 가장 낡기 쉬운 답이다.** 매물 하나만 등록돼도 거짓이 되고, 오류의
  방향("없다")이 더 나쁘다

### 도메인 밖 응답도 저장하지 않는다 — 이유 하나만 겹친다

ADR-0039. `is_cacheable`이 `out_of_domain`도 거부하는데, **위 둘 중 첫째만
적용된다.**

| 사유 | 0건 | 도메인 밖 |
|---|---|---|
| 판정 근거가 비결정적 (LLM) | O | **O** |
| 답이 낡는다 | O | **X — `"삼성전자 주식"`은 내일도 밖이다** |

즉 도메인 밖 응답은 낡지 않는데도 저장하지 않는다. 근거는 오직 첫째다 —
게이트가 오거부한 경우 그 판정이 TTL 내내 굳어 멀쩡한 검색을 막는다. 판정이
결정적으로 바뀌면(룰이나 보정된 분류기로 옮기면) 이 금지는 다시 볼 수 있다.

### 캐시 적중 시 `llm_calls`는 0으로 덮어쓴다

캐시된 응답에는 원래 호출 수가 박혀 있다. 그대로 돌려주면 캐시가 아낀 비용이
아니라 원본 비용으로 읽혀서 캐시 효과 측정이 정반대로 나온다.

## (2) Intent Router

`app/services/router/` · ADR-0010

```
규칙(정규식) ──확정──> 의도
     │
   abstain
     ↓
KoELECTRA-small ──확신도 >= 임계값──> 의도
     │
   확신도 낮음
     ↓
  COMPOUND
```

규칙이 먼저인 이유는 대부분의 질의가 규칙으로 끝나고, 그게 **LLM 호출 0회에
수 밀리초**이기 때문이다. 분류기는 lazy 로딩이라 규칙만으로 처리되는 요청은
모델을 아예 안 올린다.

**FAQ 규칙이 우선한다.** `"수수료 얼마인가요"`는 FAQ와 PRICE 패턴에 모두
걸려서 COMPOUND로 잘못 올라갔다. FAQ 우선순위를 명시해 고쳤고, 홀드아웃
정확도는 86.7%로 변하지 않아 규칙 과적합이 아님을 확인했다.

### 확신도는 교정되어 있지 않다 — 임계값이 아니라 데이터로 고쳤다

분류기를 손실 0.013까지 학습시켰더니 **틀린 답의 확신도 중앙값이 0.978,
맞은 답이 0.991**이었다. 어떤 임계값도 둘을 못 가르고, 경계 질의
에스컬레이션이 **0/20**으로 붕괴했다.

임계값을 조정하는 대신 **애매함을 가르쳤다** — LLM으로 생성한 모호한 발화
108건을 `compound`로 라벨링 + label smoothing 0.1. 결과 **15/20**.

`intent_confidence_threshold`는 여전히 잠정값이다.

## (3-a) 검색 파이프라인

`app/services/search/`

```
질의
 ├─ 도메인 판정               ← LLM 1회 (아래와 병렬, gather)
 │    └─ 밖이면 여기서 끝 ────────── 확정 거절 (임베딩·ES·리랭킹 생략)
 └─ Query Rewrite + Text-to-DSL   ← LLM 1회 (동의어 확장 + 구조화 필터를 한 번에)
      ├─ rewritten_query ──┬─ BM25 (nori)      ─┐
      │                    └─ 임베딩 → kNN      ─┤ 한 번의 _msearch
      └─ filters ──────────── 양쪽 filter 절 ───┘
                                                 ↓
                                          앱 레벨 RRF 융합
                                                 ↓
                                    Cross-Encoder 재순위 (ONNX int8, 상위 20)
                                                 ↓
                                            상위 N건 반환
```

> **임베딩과 리랭커는 전용 스레드에서 돈다**(ADR-0028). 둘 다 동기 CPU
> 호출이라 `async` 핸들러에서 그냥 부르면 이벤트 루프 전체가 멈춘다 — 격리
> 측정으로 리랭커 103~189ms, 임베딩 28~40ms다. `app/core/threadpool.py`의
> `run_cpu()`가 유일한 통로이고 풀 크기는 2다.

### 설계 결정

**Rewrite와 Text-to-DSL을 한 LLM 호출로 합쳤다.** 따로 부르면 검색 한 번에
왕복이 2회 붙는다. 하나의 프롬프트에서 JSON으로 둘 다 받는다.

> **그 원칙이 공짜가 아니라는 것은 ADR-0039 에서 처음 측정됐다.** 같은 스키마에
> 도메인 판정 필드를 하나 더 얹었더니 재작성 토큰집합 일치도가 대조군 대비
> **-0.248** 떨어졌고 문구를 고쳐도 그대로였다. 그래서 도메인 판정은 합치지
> 않고 **병렬 별도 호출**로 뒀다 — 순차가 아니므로 왕복이 늘지 않는다. 합칠지
> 나눌지의 기준은 "호출 수"가 아니라 **"두 일이 서로를 망가뜨리는가"**다.

**RRF는 앱에서 계산한다.** ES의 네이티브 RRF는 Platinum 라이선스이고 이
클러스터는 basic이다 (ADR-0005). `_msearch`로 BM25와 kNN을 한 번에 보내고
융합은 파이썬에서 한다.

**리랭커는 다국어 mMARCO 변종이다.** 영어 전용 `ms-marco-MiniLM-L-6-v2`는
한국어를 자모 단위로 쪼개서 **재순위가 없느니만 못했다** (ADR-0006).
ONNX int8 양자화 + 상위 20건 제한은 레이턴시 예산 때문이다.

**한국어 분석은 nori.** `docker/elasticsearch/Dockerfile`에 플러그인을 구워
넣는다 — 안 그러면 컨테이너 재생성마다 사라진다.

### 하드 필터 — 임계값이 없다는 게 요점

카테고리 혼입(`"5만원 이하 검"`에 활이 섞임)을 **점수 임계값이 아니라 스키마로**
막는다. ADR-0014·0015.

| 필드 | 값 |
|---|---|
| `category` | 무기 / 방어구 / 장신구 / 소모품 / 계정 / 재화 |
| `subcategory` | 검 · 둔기 · 창 · 활 · 지팡이 / 갑옷 · 방패 · 신발 · 로브 · 모자 · 각반 / 반지 · 목걸이 · 팔찌 · 귀걸이 / 물약 · 주문서 · 재료 / 계정 / 재화 |
| `element` | 화염 · 냉기 · 번개 · 암흑 · 신성 · **무속성** |

`subcategory == "활"`은 실행마다 흔들리지 않는다. 재색인 비용이 있는 대신
**캘리브레이션이 필요 없다.**

**속성 태깅 규칙** (자명하지 않아 ADR-0015에 못박았다):

- **저항은 속성이 아니다.** `용비늘 방패`(화염 피해 감소)를 `화염`으로 태깅하면
  `"불속성 장비"`에 대화염 방패가 나온다 — 없애려는 오탐과 같은 종류다
- **이름이 아니라 효과로 판정한다.** `바람의 장궁`은 효과가 순수 물리라 `무속성`
- **`무속성`은 값이고 `null`이 아니다.** 필터의 `null`은 "속성 조건 없음"
- **그 구분을 모델이 못 해서 코드가 채운다** (ADR-0040). 프롬프트에 이미
  `무속성/속성 없는 -> "무속성"` 과 `null` 과의 차이가 적혀 있는데도 **50번 중
  42번을 틀렸다.** 그래서 `fill_missing_element()` 가 추출이 `null` 을 냈고 질의에
  글자가 있으면 채운다 — **채우기만 하고 덮어쓰지 않으므로** 잘 되는 다른 속성
  추출에 닿을 수 없다. `무속성` 하나만 다루는 이유는 `"화염 저항 방어구"` 처럼
  **낱말이 있어도 답이 `null` 인 짝**이 다른 속성에는 있기 때문이다

> **모델을 올리며 이 절의 전제가 하나 바뀌었다** (ADR-0045). `gpt-5.4-mini` 는
> `무속성` 을 스스로 맞히므로 후처리의 **채우기 경로가 0건 발동**한다. 대신
> **부정형에 스스로 채우는** 반대 결함이 생겨, 후처리가 `무속성` 일 때만
> **지우기**도 한다. 원소 추출은 111/117 → **117/117**.

**측정된 효과** (질의 10건 × 상위 8건, 라벨 34~70건):

| | 필터 없음 | +subcategory | +element |
|---|---|---|---|
| 부적합 결과 | 50건 | 26건 | **14건** |
| 적합 결과 | 20건 | 20건 | **20건 (손실 0)** |

**빠진 값은 임포트 시점에 터진다.** `HARD_FILTER_FIELDS`에 값이 없는 아이템은
그 필터가 걸린 검색에서 **조용히 사라지므로** `app/corpus/__init__.py`가
막는다.

### 0건 처리

ADR-0016. 결과가 비면 **LLM을 거치지 않고** 확정 응답을 만들고, 무슨 조건으로
찾았는지 같이 준다.

```
검 · 화염 속성 · 30,000원 이하 조건에 맞는 매물이 없습니다.
```

결과가 있으면 항목 자체가 종류·속성을 달고 나와 검증되지만, **0건에는 검증할
대상이 없다** — 그때 유일한 근거가 "무슨 조건으로 찾았는가"다.

`llm_calls`는 **0이 아니라 2**다. `understand_query`는 건너뛸 수 없고(필터를
알아야 0건 판정이 선다) 도메인 판정이 그와 병렬로 한 번 더 나간다.

> **2026-08-09 정정** — 이 줄이 ADR-0016 시절의 `1` 로 남아 있었다. 아래
> "결과가 있어도 설명 LLM 을 부르지 않는다" 절이 *"ADR-0039 이후 **2**"* 라고
> 이미 적고 있었으므로 한 문서 안에서 갈려 있었다. **값이 바뀐 절과 값을 인용한
> 절이 떨어져 있으면, 고칠 때 뒤쪽만 고치게 된다.**

### 결과가 있어도 설명 LLM 을 부르지 않는다 (ADR-0036)

0건 처리를 만들 때는 그게 예외 경로였는데, **결과가 있는 경로도 같아졌다.**

```
검 · 100,000원 이하 조건으로 4건 찾았습니다.
```

계기는 환각이다. `10만원 이하 검` 질의에 22,000~45,000원짜리 검 네 건을
찾아놓고, 설명 LLM 이 *"10만원 이하의 검은 없습니다 … 모두 10만원을 초과하거나
검이 아닌 무기입니다"* 라고 답했다. 두 주장 다 거짓이고, 반증하는 카드 넷이
답변 바로 아래에 떠 있었다.

원인은 프롬프트가 **하드 필터가 이미 끝낸 판정을 다시 시킨 것**이다. "종류가
맞지 않는 항목은 빼고 말하라"고 지시하면서, 페이로드에는 `subcategory`(`검`)를
안 넣고 `category`(`무기`)만 넣었다 — 판단하라면서 판단할 필드를 안 준 셈이다.
그 지시 자체가 ADR-0014·0015 이전의 화석이다.

**결과 목록을 문장으로 옮길 이유가 없다.** 항목이 이름·가격·종류·속성을 달고
나오므로 설명이 더할 정보가 없고, 더할 게 없는 자리에서 LLM 은 지어낸다.

따라서 검색 분기의 `llm_calls` 는 **0건이든 아니든 같다.** 두 경우를 가르려면
`no_results` 를 봐야 한다. LLM 설명은 나머지 세 분기에 그대로 있다.

> 그 값은 ADR-0036 시점에 **1**이었고 ADR-0039 이후 **2**다(도메인 판정이
> 병렬로 하나 더 나간다). **바뀌지 않은 것은 "분기 안에서 무슨 일이 있었든 같은
> 값"이라는 성질**이고, 이 문단이 말하려는 것도 그쪽이다.

### 도메인 밖 질의는 검색 전에 끊는다

ADR-0039. 판정 전용 프롬프트(`domain_gate.judge_in_domain`)를 질의이해와
**동시에** 던진다.

```
질의 ─┬─ understand_query ──┐
      └─ judge_in_domain ───┴─▶ 밖 ─▶ 확정 거절 (임베딩·ES·리랭킹 생략)
                               └─ 안 ─▶ 임베딩 → 하이브리드 → 리랭킹
```

**처음엔 `understand_query` 의 JSON 스키마에 `in_domain` 필드를 더했다** — 호출이
안 는다는 게 장점이었다. 두 번 측정하고 두 번 다 기각됐다: 미검출은 두 번 다
0/38 인데 오거부가 29.9% → 13.4% 로 기준(1%)을 한참 넘었고, **재작성 토큰집합
일치도가 대조군 대비 -0.234 → -0.248 로 문구를 고쳐도 그대로**였다. 문구가 아니라
스키마가 늘어난 것 자체의 대가였고, 재작성 텍스트는 BM25·kNN 양쪽에 들어간다.

떼어내면 추출 프롬프트를 건드리지 않으므로 **회귀가 구조적으로 0**이다. 대가는
호출 1회 증가인데, 둘 다 순수 I/O 대기라 병렬로 던지면 지연은 느린 쪽 하나치다.
그래서 검색을 타는 분기의 `llm_calls` 는 **2**(시세 분기는 설명까지 3)이고,
`timings` 의 `query_understanding_ms` 와 `domain_gate_ms` 를 **더하면 안 된다.**

**kNN 은 어떤 질의에도 k 건을 돌려준다.** 그래서 `"삼성전자 주식 어때?"` 가
시세 분기를 타면 검색이 `게임 머니 1000만 골드` 를 "찾아내고", 예측은 그
아이템의 진짜 값을 계산하며, 설명 LLM 은 **질의의 주어를 골라** "삼성전자
주식의 최근 거래가는 약 26,090원" 이라고 답한다. 숫자만 진짜인 문장이다.

방어는 세 갈래로 나뉘고, 갈래마다 필요한 장치가 다르다.

| 분기 | 도메인 밖 38건 중 | 장치 |
|---|---|---|
| `item_search`·`price_forecast` | 22 (58%) | `in_domain` 게이트 → 확정 거절 |
| `compound` (에이전트) | 7 (18%) | MCP `search_items` 가 **문장으로 된 안내**를 돌려준다 |
| `faq_smalltalk` | 9 (24%) | **이미 안전** — 기본 응답이 취급 범위를 밝히며 거절한다 |

세 번째가 요점이다. FAQ 분기는 손대지 않았는데, `_DEFAULT_FAQ` 가 이미
"아이템 검색·시세 확인·이상거래 점검을 도와드릴 수 있습니다" 라고 답한다 —
LLM 0회에 결정적이다. **아무것도 안 해도 맞는 경로에 게이트를 더하면 그건
장식이다.**

에이전트 쪽에 빈 목록이 아니라 안내 문장을 주는 이유는 `estimate_note` 와
같다 — **원시 신호(빈 배열)는 읽을 수 있는 말이 아니다.** 모델은 빈 목록을
"매물이 없다"로 읽고 아는 대로 답한다.

### 리랭커 점수 하한은 도입하지 않는다

ADR-0018. 두 번 측정했고 두 번 다 기각인데 **사유가 다르다.**

| | 07-30 | 07-31 |
|---|---|---|
| 사유 | 입력 노이즈 > 마진 | **질의 간 점수 눈금 비교 불가** |
| 고칠 수 있나 | 예 (ADR-0017이 고쳤다) | **아니오** |

질의별 적합 최솟값이 **−3.84 ~ +2.90(폭 6.74점)** 으로 움직이는데 전역
부적합 최댓값은 −2.54다. 전역 임계값이 안전하려면 최악 질의보다 낮아야 하고,
그 깊이에서는 자를 게 없다. 분할 126가지를 전수 열거하니 **부등호 유지가
44%**였다.

**크로스인코더 로짓은 한 질의의 후보 집합 안에서만 의미가 있다.**
노이즈가 나아졌다고 다시 시도하지 말 것.

## (3-b) 시세 예측

`app/services/forecast/` · ADR-0008

```
거래 이력 조회
   ├─ 충분(>= 최소 윈도) → PriceLSTM (14일 윈도 → 7일 직접 다단계)
   └─ 부족             → Cold Start: ES kNN으로 유사 아이템 → 추세 가중 상속
```

**아이템별 모델이 아니라 전역 모델 하나다.** 아이템마다 학습하면 신규 아이템은
영원히 모델이 없고, 학습·배포 비용이 아이템 수에 비례한다. 대신 가격 절대값이
아니라 **윈도 마지막 가격 대비 비율**로 정규화해 아이템 간 스케일 차이를 없앴다.

### 판단 기준은 MAPE가 아니라 "기준선을 이겼는가"

**합성 데이터라 MAPE 자체는 아무것도 증명하지 않는다.** `train_forecast`는
항상 naive 기준선을 같이 출력한다.

| | 값 |
|---|---|
| LSTM MAPE | **4.70%** |
| 최고 naive 기준선 (last-value / linear drift) | 4.87% |
| 신호 상관 | 0.304 |

이겼지만 근소하다. 그리고 그 근소함과 "평균 회귀 경향"은 **같은 현상**이다 —
데이터 생성 과정상 예측 가능한 정보량이 원래 적다.

### 알려진 한계

- **정규화 기준점이 단일 시점**(윈도 마지막 가격)이라 실거래 노이즈에 취약하다
- 메인 LSTM에 **조건부 피처(카테고리·희귀도)가 없다**
- 모델 파일은 gitignore 대상이다. 없으면 `/api/forecast`가 **503과 함께 실행할
  명령**을 돌려준다 (`python -m scripts.train_forecast`, CPU 10초)

## (3-c) 이상거래 탐지

`app/services/anomaly/` · ADR-0009

```
거래 → 11개 문맥 상대 피처 → RobustScaler → TradeAutoencoder(11-8-4-8-11)
                                                    ↓
                                          재구성 오차 = 이상 점수
                                                    ↓
                                          피처별 기여도 분해 → LLM 설명
```

Isolation Forest 대신 오토인코더를 쓴 이유는 **재구성 오차를 피처별로 쪼갤 수
있어서**다. "왜 이상인가"를 축 단위로 답할 수 있다.

피처 11개: `log_price_ratio`, `log_amount`, `log_quantity`, `hour_sin`,
`hour_cos`, `log_buyer_age`, `log_seller_age`, `log_buyer_trades_24h`,
`log_seller_trades_24h`, `log_pair_trades_7d`, `is_auction`

### 임계값은 학습셋에서 뽑으면 안 된다

**오토인코더는 자기 학습 데이터를 가장 잘 복원한다.** 그 분위수는 낙관 편향이다.

| 임계값 출처 | 홀드아웃 정상 트래픽 발화율 |
|---|---|
| 학습셋 p99 | **1.32%** (의도 1.00%) |
| 홀드아웃 p99 | 1.00% |

그래서 정상 데이터를 **3분할**한다: 학습 / 임계값 산정 / 평가.

### 오토인코더와 규칙은 다른 질문에 답한다 — 대체가 아니다

재구성 오차는 "**드문가**"가 아니라 "**표현 불가능한가**"를 잰다.

| 시나리오 | AE | `max |z|` 규칙 |
|---|---|---|
| 신규 계정(뮬) 거래 | **놓침** | 100% 탐지 |
| 여러 축에 증거가 흩어진 복합 이상 | **탐지** | 놓침 |

신규 계정은 학습 데이터 꼬리에 이미 있어서 거의 완벽히 복원된다. **규칙을
모델로 대체하지 말 것.** 상호 보완이다.

### 합성 이상치는 정상 분포를 먼저 확인하고 주입한다

처음에 복합 이상 시나리오를 정상 최댓값(1.31배)보다 큰 1.5배 가격으로 만들어
가격 규칙 하나에 63% 잡혔다. 정상 분포의 p80~p95(1.046~1.073배)로 재조정하니
가격 규칙 탐지율이 **0%**가 됐다. 그제야 "여러 축에 흩어진 이상"이 됐다.

같은 이유로 더미 유저 풀에 **의도적인 반복 거래 상대 구조**를 넣었다
(150명 × 3파트너, 35% 반복). 없으면 `pair_trades_7d` 하나로 복합 이상이
분리돼 상호작용 테스트가 통째로 무의미해진다.

## (3-d) 에이전트 (복합 질의)

`app/services/agent/` · `app/services/mcp/` · ADR-0011

순차 도구 호출 루프, 최대 5단계. **도구 실패는 예외가 아니라 결과로 돌아간다** —
에이전트가 스스로 고쳐 부를 기회를 준다.

`llm_calls` 는 `len(tool_calls) + 1` 이므로 범위는 **1~6**이다. 하한이 2가 아니라
1인 이유는 **도구를 하나도 안 부르고 끝나는 실행이 실제로 있기 때문**이다 —
도메인 밖 질의에서 에이전트가 자기 시스템 프롬프트만으로 거절한 사례가
`llm_calls=1` 로 관측됐다(ADR-0039). *그때 MCP 쪽 방어는 한 번도 실행되지
않았고, 그 사실을 알려준 것이 이 숫자였다.*

### MCP는 진짜 프로토콜이되 전송만 인프로세스다

에이전트가 같은 FastAPI 앱 안에 있어서 self-HTTP 호출은 알려진 이벤트 루프
블로킹과 맞물려 교착 위험이 있다. 그래서 **인메모리 전송**을 쓴다. 프로토콜은
실제 MCP이고, `python -m app.services.mcp`로 같은 서버를 stdio로 노출한다.

> 그 "알려진 블로킹"은 ADR-0028에서 대부분 해소됐다(임베딩·리랭커·분류기가
> 전용 스레드로 나갔다). **결정은 그대로 유지한다** — 자기 자신에게 HTTP를
> 거는 것은 블로킹이 없어도 왕복·직렬화·타임아웃을 공짜로 얻는 선택이 아니다.

### 도구

| 도구 | 필수 인자 | 감싸는 것 |
|---|---|---|
| `search_items` | `tenant_code`, `query` | 검색 파이프라인 |
| `forecast_item_price` | `tenant_code`, `item_id` | 시세 예측 |
| `detect_trade_anomaly` | `tenant_code`, `trade_id` | 이상거래 탐지 |

### 도구 출력의 필드명은 프롬프트 엔지니어링이다

에이전트가 매물 등록가(`price`)와 최근 체결가(`anchor_price`)를 직접 비교해
**"저평가됐으니 지금 사라"**는 잘못된 결론을 냈다. 이름을 바꿔 고쳤다.

| 이전 | 이후 |
|---|---|
| `price` | `listing_price` |
| `anchor_price` | `baseline_price` + `baseline_source` |

`baseline_source`는 `"최근 체결가"` / `"관측된 거래 N건의 평균"` /
`"등록가(거래 이력 없음)"` 중 하나다. **새 필드를 추가할 때도 이름만 보고
뜻이 서게 지을 것.**

`subcategory`·`element`도 같은 이유로 노출한다 — 이름만 보고 모델이 활을
검이라 단정한 전례가 있다.

## 파이프라인 전반의 결정성

ADR-0017. **`temperature`는 0이고 `chat()`이 항상 명시적으로 보낸다.**

생략하면 OpenAI가 **1.0**을 쓴다. 이 프로젝트는 그 상태로 6개 Phase를 돌았고,
그때 생긴 변동을 "LLM의 근본 특성"으로 오진했다.

| | temp 1.0 | temp 0.0 |
|---|---|---|
| 재작성 토큰집합 모드 일치율 | 0.840 | **0.990** |
| 불안정 질의 | 5/10 | **1/10** |

**예외는 하드네거티브 생성 하나**다(`scripts/generate_hard_negatives.py`).
거기서는 다양성이 곧 데이터 품질이라 자기 클라이언트를 1.0으로 만든다.
"일관성" 명목으로 0으로 되돌리지 말 것.

## 프로바이더 계층 — 장애 시 무엇이 일어나는가

ADR-0041 · 0042. **이 계층이 붙기 전에는 분기마다 다른 일이 일어났다.**

| 분기 | 폴백 도입 전 |
|---|---|
| 검색 · FAQ | **살았다** (`understand_query` 는 원본 질의로 폴백, 게이트는 fail-open, FAQ 는 LLM 0회) |
| 시세 · 이상거래 · 에이전트 | **500** |

검색이 산 것은 **설계가 아니라 fail-open 두 개가 우연히 겹친 결과**다.

### 두 겹이 순서대로 선다

```
OpenAI 실패 → Claude 폴백 → (둘 다 실패) → 결정적 문장 → (그것도 아니면) 500
```

**1. 폴백 (ADR-0042).** 연속 3회 실패면 60초 동안 1차를 건너뛴다. 서킷을 둔 이유는
정합성이 아니라 **지연**이다 — 예외만 잡아 넘기면 장애 동안 모든 요청이 1차
타임아웃을 먼저 문다(ADR-0030 에서 AMQP 기본 60초로 "구매는 성공하는데 1분"을
겪은 그 축이다). 둘 다 죽으면 **1차 예외**를 올린다. 2차 예외로 바꿔치면 진단이
엉뚱한 프로바이더를 가리킨다.

> **폴백 구현의 대부분은 형식 번역이다.** `LLMClient` 는 중립인데 에이전트 루프가
> OpenAI 메시지 형식을 그대로 쓴다(`{"role": "tool", "tool_call_id"}`). 인터페이스만
> 맞추고 형식을 안 맞추면 `complete()` 는 되고 **에이전트만 조용히 깨진다** —
> 폴백이 가장 필요한 순간에. 특히 **연속된 도구 결과를 한 메시지로 합쳐야** 하고,
> 안 합치면 도구 하나일 땐 되고 **둘일 때 400** 이다.

**2. 내려앉기 (ADR-0041).** 설명 LLM 이 죽어도 그 시점에는 예측·판정이 **이미
계산돼 있다.** 없는 것은 산문뿐이라 `_search_answer` 와 같은 방식으로 결정적
문장을 만든다. 폴백을 **콜러블로** 받아 성공 경로에서는 만들지 않는다.

> 그 문장은 **프롬프트가 조건부로 붙이던 고지를 그대로 붙인다** — 콜드스타트
> 추정이라는 것, 이상거래 판정이 합성 코퍼스라는 것. 빠지면 **모델이 살아 있을
> 때만 정직한** 응답이 된다.

**에이전트 분기는 손대지 않았다.** 거기서는 **LLM 이 곧 분기**라 내려앉을 자리가
없고, 정직한 500 이 맞다.

### 관측

| 신호 | 무엇을 말하나 |
|---|---|
| `outcome="degraded"` | **둘 다** 죽어 결정적 문장으로 답했다 |
| `ai_llm_provider_calls_total{provider,outcome}` | 어느 프로바이더가 몇 번 성공/실패했나 |
| `/health` 의 `llm_fallback` | 폴백이 **구성됐는가** (키 자체는 안 싣는다) |

> 1차만 죽어 폴백이 답한 경우는 `degraded` 로 안 잡힌다 — **사용자는 정상 응답을
> 받기 때문이다.** 그건 프로바이더 카운터로 본다. 그리고 그 카운터는
> `ai_llm_calls_total`(응답의 **상수**)과 짝지어 읽는다 — **어긋나면 그 상수가
> 틀린 것**이다.

## 임베딩 파인튜닝

`app/services/training/` · ADR-0007

sentence-transformers + `MultipleNegativesRankingLoss` + **하드 네거티브 마이닝**.

**규칙 + LLM 하이브리드다.** 구조화 필드로 유도 가능한 쌍(강화 형제, 같은
카테고리 내 텍스트 중첩)은 결정적으로 마이닝하고, LLM은 규칙이 못 만드는 것만
공급한다 — 현실적인 사용자 표현, 의미적 near-miss(속성·직업 스왑).

### 평가 방법론

**RAGAS 단독으로 판단하지 않는다.** LLM 심판은 실행마다 흔들려서 작은 평가셋
위의 단일 델타는 근거가 안 된다. 항상 결정론적 IR 지표와 함께 본다.

| 지표 | 파인튜닝 전 | 후 |
|---|---|---|
| Recall@1 | 0.148 | **0.389** |
| MRR | 0.301 | **0.510** |
| RAGAS context_precision | 0.294 | **0.513** |

**`TRAIN_ITEMS`(24)와 `EVAL_ITEMS`(18)는 엄격히 분리**되고 임포트 시점에
검증된다. 평가셋 오염은 조용히 일어나 수치만 부풀린다.

**CI 게이트도 같은 원칙을 따른다** (ADR-0043, `ai-quality.yml`). 코퍼스·트리플·
학습 코드가 바뀌면 임베딩을 재학습해 **IR 지표로 판정**하고, **RAGAS 는
`workflow_dispatch` 리포트**다 — 심판 변동폭을 특성화하지 않은 지표에 문턱을 걸지
않는다는 위 원칙의 CI 판이다. 문턱(recall@1 0.35 / recall@5 0.48 / MRR 0.47)은
재학습 변동을 학습 7회로 측정해 잡았고, **잡는 것은 큰 회귀**(코퍼스 훼손, 베이스
모델 오지정, 트리플 깨짐)지 미세한 품질 저하가 아니다.

## 이 파이프라인이 보장하지 않는 것

문서를 읽고 과신하지 않도록 한자리에 모은다.

| 항목 | 상태 |
|---|---|
| 시세 예측 정확도 | 합성 데이터 기준. 기준선 대비 근소 우위(4.70% vs 4.87%) |
| 이상거래 재현율 | 합성 주입 기준. 규칙 기준선이 이기는 시나리오가 있다 |
| 라우터 확신도 | **교정 안 됨.** 임계값은 잠정 |
| 캐시 유사도 매칭 | FAQ 외에는 **불가**로 실측됨 |
| ~~`"무속성"` 필터~~ | **해결됨 (ADR-0040 → 0045).** 추출이 8/50 이었는데 **프롬프트가 아니라 코드로** 고쳤고(62~86% → 93%), 모델 교체 후 원소 추출 전체가 **117/117** 이다 |
| ~~`"어둠 속성"` 표기~~ | **모델 교체로 닫혔다 (ADR-0045).** `gpt-4o-mini` 에서 `"어둠 속성 로브"` 가 6/6 `null` 이었는데 `gpt-5.4-mini` 는 맞힌다. *"열려 있다"가 **"이 모델에서 열려 있다"** 였다* |
| `전설 등급` 같은 등급 축 | 필드가 없어 텍스트 신호로만 동작 |
| `"단검만"` 같은 세분 질의 | `subcategory=검`이라 롱소드·대검이 같이 나온다 |
| 리랭커 하한 | **도입 안 함**(위) |
| 요청 한도의 정밀도 | AI 쪽은 고정 윈도우라 **경계에서 최대 2배 통과**한다(ADR-0024). 비용 폭주 차단이 목적이지 정확한 분당 N이 아니다 |
| Redis 장애 시 한도 | **통과시킨다**(fail-open). 리미터는 비용 방어이지 정합성 장치가 아니다 — 구매 경로의 분산 락은 반대다 |

## 이 문서가 다루지 않는 것 — 체결 후 비동기 경로

거래 **체결**은 AI 파이프라인이 아니라 백엔드가 처리한다(Redis 락 + DB 트랜잭션).
체결 후에는 RabbitMQ 로 이벤트가 나가고 알림이 만들어진다 — ADR-0030.

**AI 서버는 그 경로에 관여하지 않는다.** 기획서에는 "체결 후 시세 갱신"도 있지만,
시세 예측이 Postgres 가 아니라 합성 코퍼스(`app/corpus/trade_history.py`)를 읽으므로
**반영할 대상이 없다.** id 공간 (C) 완전 통합에 묶인 항목이다 — 그게 풀리면
시세 갱신 소비자가 이 파이프라인과 처음으로 만난다.
