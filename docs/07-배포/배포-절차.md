# 배포 절차 (Oracle Cloud ARM)

> **이 문서는 "해봤다"가 아니라 "이 순서로 하면 되고 각 단계에서 무엇을 확인하는가"다.**
> 로컬에서 arm64 이미지 빌드와 QEMU 기동까지 확인했고, 실제 인스턴스에 올리는 것은
> 클라우드 접근이 있는 쪽에서 한다.

## 0. 전제

| | |
|---|---|
| 대상 | Oracle Cloud ARM, 4 OCPU / 24GB — **다른 프로젝트와 공유** |
| 여유 | `free -h` 기준 available **20Gi** (다른 프로젝트가 2.3Gi) |
| 이 스택의 실측 | **약 3.1GB** (ai 1.25 · ES 1.10 · backend 0.48 · MQ 0.14 · PG 0.07 · Redis 0.02 · nginx 0.01) |
| **먼저 해둘 것** | **OpenAI 대시보드 월 사용량 상한** — 코드 3계층이 다 뚫려도 마지막에 막는 유일한 장치 |

메모리는 여유가 크다. **제약은 CPU다** — 4 OCPU에서 ES(JVM) + 백엔드(JVM) + torch
추론이 경쟁한다.

### 디스크를 먼저 재고 시작한다

메모리는 쟀는데(`free -h`) **디스크는 안 쟀다.** 1단계가 대상에서 빌드하는 것이므로
빌드 공간이 거기 있어야 한다.

```bash
df -h /var/lib/docker /   # 20GB 이상 여유를 권한다
```

| 무엇이 | 얼마나 |
|---|---|
| 이미지 4종 (ai 2.9 · ES-nori 1.9 · backend 0.6 · web 0.07) | **약 5.5 GB** |
| `ai_models` 볼륨 | 0.65 GB |
| **빌드 캐시** | **10 GB 이상까지 자란다** |

> **빌드 캐시가 실제 사고를 냈다.** 개발기에서 이게 19.35 GB 까지 자라 호스트를
> 채웠고, 그 결과 컨테이너 안에서 `read-only file system` → containerd 크래시 →
> **`docker` 명령 전체 무응답**이 됐다. 증상 어디에도 "디스크"라는 단어가 없다.
> 빌드 후 `docker builder prune -af` 를 습관으로 두고, 진단은
> `docs/05-Troubleshooting/도커-디스크-고갈-vhdx-압축.md` 를 본다.
>
> 대상은 리눅스라 vhdx 압축 단계는 없다 — **`prune` 이 곧 회수**다. vhdx 문제는
> Windows 개발기에만 있다.

## 1. 이미지 — 대상에서 빌드하는 편이 낫다

```bash
git clone <repo> && cd game-item-marketplace-ai
docker compose --profile app build
```

교차 빌드(`buildx --platform linux/arm64`)로 **4종 모두 빌드되는 것을 확인했다** —
web·backend, 그리고 AI 이미지(pip 계층 **1041.5s**, exit 0). 의존성도 전부 aarch64
휠로 해결된다(`torch-2.13.0+cpu`, `onnxruntime-1.28.0`, numpy·scipy·tokenizers…).

그래도 **대상에서 빌드하는 쪽이 낫다** — 에뮬레이션이 17분 걸린 계층이 네이티브에선
훨씬 짧고, 아키텍처 불일치 가능성도 없앤다. 교차 빌드는 "된다"를 미리 확인한
것이지 배포 산출물을 만드는 용도가 아니다(ADR-0032).

> **리랭커 양자화는 avx2 그대로다**(ADR-0032). 이름이 x86을 가리키지만 산출물은
> 이식 가능한 ONNX이고, **aarch64에서 로드·추론되는 것을 확인했다.** arm64 전용
> 설정은 top-5 순위를 0/5로 바꿔서 기각했다 — 기록된 품질 수치가 전부 avx2 기준이다.

## 2. 시크릿 — 기본값이면 뜨지 않는다

`prod` 프로파일에서 `SecretGuard`가 저장소 기본값을 거부한다. **경고가 아니라 기동 거부다.**

```bash
cat > .env <<'EOF'
POSTGRES_PASSWORD=<생성>
REDIS_PASSWORD=<생성>
RABBITMQ_PASSWORD=<생성>
JWT_SECRET=<32바이트 이상>
DEMO_PASSWORD=<데모 계정용>
ADMIN_PASSWORD=<GM 전용, 데모와 달라야 함>
EOF
chmod 600 .env
```

`ai/.env`에도 **`JWT_SECRET`을 같은 값으로** 넣고 `OPENAI_API_KEY`를 채운다.
다르면 **발급은 되는데 AI 서버만 401**이라 증상이 헷갈린다.

| 값 | 안 넣으면 |
|---|---|
| 인프라 3종 비밀번호·`JWT_SECRET` | **기동 거부**(SecretGuard) |
| `DEMO_PASSWORD` / `ADMIN_PASSWORD` | 기동 거부. 비어 있으면 아무도 로그인 못 한다 |
| 둘이 **같으면** | 기동 거부 — 역할 분리가 무효가 된다 |

## 3. 기동 — 두 단계다

```bash
docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app up -d
# ai-init 이 모델 5종을 만들고 ES를 색인한다 (수 분, LLM 호출 없음)
# db-seed 가 데모 데이터를 넣는다

docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app \
    restart backend web
```

**재시작이 필요한 이유가 두 가지 겹친다** (ADR-0031):

1. **비밀번호가 시드에 덮인다.** `DemoAccountInitializer`는 백엔드 기동 시 돌지만
   `db-seed`는 백엔드가 healthy가 된 **뒤에** 실행된다(테이블을 Hibernate가 만들어서
   그 순서를 피할 수 없다)
2. **nginx가 옛 IP를 물고 있다.** `proxy_pass`에 호스트명을 literal로 쓰면 nginx가
   기동 시 한 번 DNS를 풀고 캐시한다 → 백엔드 재생성 후 502

**잊으면 아래 검증이 401 또는 502로 지목한다.**

## 4. 검증 — 세 스크립트

```bash
./load/verify-deploy.sh                       # 포트 미노출 + prod + 실제 로그인
DEMO_PASSWORD=… ADMIN_PASSWORD=… ./load/verify-auth.sh   # 로그인·비밀번호 분리
./load/verify-container.sh                    # 4분기 응답 · SPA 폴백 · CORS 0
```

`verify-auth.sh`의 **판정 6(XFF 위조)은 배포에서 건너뛴다** — 백엔드 포트가 닫혀
있어 스푸핑 대상 자체가 없다. 스크립트가 그 사실을 `[FAIL]`로 알리는데, **배포
구성에서는 그게 정상**이다(포트 미노출이 1차 방어선이고 XFF 신뢰 목록이 2차다).

## 5. 공개 — HTTPS

여기부터는 실제 호스트에서만 가능하다.

```bash
# 방화벽: 80/443 만
sudo ufw allow 80,443/tcp && sudo ufw enable
# Oracle Cloud 는 보안 목록(Security List)도 따로 열어야 한다

# 인증서
sudo certbot --nginx -d <도메인>
```

nginx는 컨테이너 안이므로 **호스트에 별도 nginx/caddy를 두어 TLS 종단**을 하고
`localhost:80`으로 넘기는 쪽이 단순하다. 컨테이너 안 nginx 설정을 건드리면
`frontend/nginx.conf`의 경로 규칙과 `vite.config.ts`가 어긋날 위험이 생긴다.

**TLS를 붙였으면 `TRUSTED_PROXIES`를 채운다** — 그러지 않으면 모든 요청의 IP가
프록시 하나로 합쳐져 로그인 한도가 배포 전체 합계가 된다.

```bash
docker inspect gimp-web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# 이 값을 .env 의 TRUSTED_PROXIES 에 넣고 backend 재시작
```

> 컴포즈 네트워크의 IP는 고정이 아니다. 재생성하면 바뀌므로 **재시작 시마다 확인**한다.
> 비워두면 헤더를 안 읽을 뿐이라 조용히 뚫리지는 않는다.

## 6. 배포 후 — 재측정할 것

배포해야만 잴 수 있는 것들이다.

| 항목 | 왜 |
|---|---|
| **스레드풀 크기** | ADR-0028의 워커 표는 **12코어** 기준. 4 OCPU면 초과 구독이 더 심하다. `cpu_pool_workers` 를 1·2·4로 바꿔가며 재고 최적값을 고른다 |
| 부하 기준선 | ADR-0020의 수치는 개발기 것이다. **세션 간 비교 금지** 규칙이 그대로 적용되므로 대상에서 새로 잰다 |
| ES 힙 | 기본 512m. 4 OCPU 공유에서 충분한지 |

## 7. 롤백

```bash
docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app down
git checkout <이전 태그> && docker compose --profile app build
```

**볼륨은 지우지 않는다** — `ai_models`(650MB)를 다시 만들면 수 분이 더 걸린다.
데이터를 초기화해야 할 때만 `down -v`.

## 알려진 한계

| | |
|---|---|
| **회원가입 없음** | 계정은 시드 고정. 의도적 제외(ADR-0031) |

| 부하테스트 미실행 | 배포 대상에서 돌리지 않는다. 포트가 닫혀 있어 SSH 터널이 필요하다 |
| nginx DNS 캐시 | 컨테이너 재생성마다 `restart web`. 잦아지면 `resolver` + 변수로 바꿀 것 |
