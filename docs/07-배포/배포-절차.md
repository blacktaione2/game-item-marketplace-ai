## ⚠️ 0-A. 호스트를 공유하는가 — 먼저 물을 것

```bash
uname -m                                  # aarch64 확인
df -h /                                   # 20GB 이상 여유
docker compose version                    # **2.24 이상** (!override 지원)
sudo ss -tlnp | grep -E ':80|:443'        # 80/443 이 비었는가
docker ps                                 # 기존 컨테이너
```

**`docker compose version` 이 2.24 미만이면 `ports: !override []` 가 조용히
무시된다** — 포트가 안 닫히는데 에러가 없다. `snap` 이나 `apt install docker.io`
말고 **Docker 공식 저장소**를 쓸 것.

**80/443 이 이미 쓰이고 있으면** 4·5절의 구성이 달라진다. 아래 ⚠️ 절 참고.

> 실제 대상은 여유 14G 뿐이었다. 필요량은 20G(이미지 5.5 + 모델 0.65 + **빌드 캐시
> 10G+**)라 콘솔에서 부트 볼륨을 **49G → 97G** 로 온라인 확장했다(Always Free 200GB
> 한도 안이라 무료). 빠듯하게 가지 않은 이유: **실패하면 같은 파일시스템의 남의
> 서비스가 같이 죽는다.**

| **먼저 해둘 것** | **OpenAI 대시보드 월 사용량 상한** — 코드 3계층이 다 뚫려도 마지막에 막는 유일한 장치 |

메모리는 여유가 크다. **제약은 CPU다** — 4 OCPU에서 ES(JVM) + 백엔드(JVM) + torch
추론이 경쟁한다.

### 디스크를 먼저 재고 시작한다

메모리는 쟀는데(`free -h`) **디스크는 안 쟀다.** 1단계가 대상에서 빌드하는 것이므로
빌드 공간이 거기 있어야 한다.

```bash
df -h /var/lib/docker /   # 20GB 이상 여유를 권한다
```

| 무엇이 | 얼마나 |
|---|---|
| 이미지 4종 (ai 2.9 · ES-nori 1.9 · backend 0.6 · web 0.07) | **약 5.5 GB** |
| `ai_models` 볼륨 | 0.65 GB |
| **빌드 캐시** | **10 GB 이상까지 자란다** |

> **빌드 캐시가 실제 사고를 냈다.** 개발기에서 이게 19.35 GB 까지 자라 호스트를
> 채웠고, 그 결과 컨테이너 안에서 `read-only file system` → containerd 크래시 →
> **`docker` 명령 전체 무응답**이 됐다. 증상 어디에도 "디스크"라는 단어가 없다.
> 빌드 후 `docker builder prune -af` 를 습관으로 두고, 진단은
> `docs/05-Troubleshooting/도커-디스크-고갈-vhdx-압축.md` 를 본다.
>
> 대상은 리눅스라 vhdx 압축 단계는 없다 — **`prune` 이 곧 회수**다. vhdx 문제는
> Windows 개발기에만 있다.

## 1. 이미지 — 대상에서 빌드하는 편이 낫다

```bash
git clone <repo> && cd game-item-marketplace-ai
docker compose --profile app build
```

교차 빌드(`buildx --platform linux/arm64`)로 **4종 모두 빌드되는 것을 확인했다** —
web·backend, 그리고 AI 이미지(pip 계층 **1041.5s**, exit 0). 의존성도 전부 aarch64
휠로 해결된다(`torch-2.13.0+cpu`, `onnxruntime-1.28.0`, numpy·scipy·tokenizers…).

그래도 **대상에서 빌드하는 쪽이 낫다** — 에뮬레이션이 17분 걸린 계층이 네이티브에선
훨씬 짧고, 아키텍처 불일치 가능성도 없앤다. 교차 빌드는 "된다"를 미리 확인한
것이지 배포 산출물을 만드는 용도가 아니다(ADR-0032).

> **리랭커 양자화는 avx2 그대로다**(ADR-0032). 이름이 x86을 가리키지만 산출물은
> 이식 가능한 ONNX이고, **aarch64에서 로드·추론되는 것을 확인했다.** arm64 전용
> 설정은 top-5 순위를 0/5로 바꿔서 기각했다 — 기록된 품질 수치가 전부 avx2 기준이다.

## 2. 시크릿 — 기본값이면 뜨지 않는다

`prod` 프로파일에서 `SecretGuard`가 저장소 기본값을 거부한다. **경고가 아니라 기동 거부다.**

```bash
cat > .env <<'EOF'
POSTGRES_PASSWORD=<생성>
REDIS_PASSWORD=<생성>
RABBITMQ_PASSWORD=<생성>
JWT_SECRET=<32바이트 이상>
DEMO_PASSWORD=<데모 계정용>
ADMIN_PASSWORD=<GM 전용, 데모와 달라야 함>
EOF
chmod 600 .env
```

`ai/.env`에도 **`JWT_SECRET`을 같은 값으로** 넣고 `OPENAI_API_KEY`와
`ANTHROPIC_API_KEY`를 채운다. `JWT_SECRET`이 다르면 **발급은 되는데 AI 서버만
401**이라 증상이 헷갈린다.

> **LLM 키는 루트 `.env`가 아니라 `ai/.env`다.** 루트는 docker-compose용이고,
> `ai`·`ai-init` 서비스가 `env_file: ./ai/.env`를 쓰므로 **이 한 곳이 로컬과
> 컨테이너를 둘 다 덮는다.** 실제로 `ANTHROPIC_API_KEY`를 루트에만 넣어
> **아무 일도 일어나지 않은** 적이 있다(ADR-0042).

| 값 | 안 넣으면 |
|---|---|
| 인프라 3종 비밀번호·`JWT_SECRET` | **기동 거부**(SecretGuard) |
| `DEMO_PASSWORD` / `ADMIN_PASSWORD` | 기동 거부. 비어 있으면 아무도 로그인 못 한다 |
| 둘이 **같으면** | 기동 거부 — 역할 분리가 무효가 된다 |
| `OPENAI_API_KEY` | 기동은 되고 **LLM 분기가 호출 시점에** 실패한다 |
| `ANTHROPIC_API_KEY` | 기동은 되고 **폴백이 없다**. 조용하지 않다 — 기동 로그에 `LLM 폴백 없음` 경고가 뜨고 `/health`의 `llm_fallback`이 `false`다 (ADR-0042) |

## 3. 기동 — 두 단계다

```bash
docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app up -d
# ai-init 이 모델 5종을 만들고 ES를 색인한다 (수 분, LLM 호출 없음)
# db-seed 가 데모 데이터를 넣는다

docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app \
    restart backend web

# **healthy 가 될 때까지 기다린다.** restart 는 즉시 돌아오지만 백엔드는
# start_period 40s 라 그 사이 검증을 돌리면 nginx 가 502 를 낸다 — 실제로 겪었고,
# 검사 실패를 배포 실패로 오해하기 딱 좋다.
until [ "$(docker inspect -f '{{.State.Health.Status}}' gimp-backend)" = "healthy" ]; do
  sleep 5; done; echo "백엔드 healthy"
```

**재시작이 필요한 이유가 두 가지 겹친다** (ADR-0031):

1. **비밀번호가 시드에 덮인다.** `DemoAccountInitializer`는 백엔드 기동 시 돌지만
   `db-seed`는 백엔드가 healthy가 된 **뒤에** 실행된다(테이블을 Hibernate가 만들어서
   그 순서를 피할 수 없다)
2. **nginx가 옛 IP를 물고 있다.** `proxy_pass`에 호스트명을 literal로 쓰면 nginx가
   기동 시 한 번 DNS를 풀고 캐시한다 → 백엔드 재생성 후 502

**잊으면 아래 검증이 401 또는 502로 지목한다.**

### 3-b. 코드만 갱신할 때 (일상 재배포)

**무엇이 바뀌었는지에 따라 다시 빌드할 이미지가 다르다.** `restart` 는 **옛
이미지로 재시작**할 뿐이므로, 코드가 바뀐 서비스는 반드시 `--build` 로 다시
올려야 한다.

| 바뀐 것 | 다시 빌드할 것 |
|---|---|
| `ai/**` | `ai` |
| `frontend/src/**`, `frontend/nginx.conf` | **`web`** |
| `backend/**` | `backend` (+ 아래 3-a 의 비밀번호 재시작 주의) |

```bash
cd ~/gimp && git pull
DC="docker compose -f docker-compose.yml -f docker-compose.deploy.yml --profile app"
# 바뀐 서비스만 적는다. 둘 다 바뀌었으면 둘 다.
$DC up -d --build ai web && $DC restart web

# **여기서도 healthy 를 기다린다.** 컨테이너는 시작 즉시 `running` 이지만
# uvicorn 은 아직 포트를 안 열었다 — 바로 물으면 `Connection refused` 가 나고,
# 그 오류는 "아직 안 떴다 / 죽었다 / 바인딩 오류" 를 구분해주지 않는다.
until [ "$(docker inspect -f '{{.State.Health.Status}}' gimp-ai)" = "healthy" ]; do
  sleep 3; done; echo "ai healthy"

docker exec gimp-ai python -c "import urllib.request,json;print(json.load(urllib.request.urlopen('http://localhost:8000/health')))"
```

**세 가지를 순서대로 본다.**

| 확인 | 정상 | 아니면 |
|---|---|---|
| `git pull` 출력 | `Updating <old>..<new>` | `Already up to date.` 면 **푸시가 안 된 것**이다. 서버가 아니라 개발기를 볼 것 |
| 빌드 로그 | 바뀐 쪽의 `COPY` 부터 **`CACHED` 가 아님** — `ai` 는 `COPY app app`, `web` 은 `COPY . .` / `RUN npm run build` | 전부 `CACHED` 면 **코드가 안 갔다.** `git pull` 을 안 했거나 바뀐 서비스를 빌드 목록에 안 넣은 것이다 |
| `/health` | `llm_fallback: true` | `false` 면 `ai/.env` 에 `ANTHROPIC_API_KEY` 가 없다 |

> **응답 내용이 바뀌는 변경이면 `cache_version` 을 올렸는지 확인한다.** 시맨틱
> 캐시는 배포 전 응답을 그대로 재생하고, 그건 **"배포가 안 됐다" 와 똑같이
> 보인다.** 화면 관측 패널의 `캐시 적중` + `LLM 호출 0회` 배지가 그 신호다
> (ADR-0040 에서 실제로 겪었다 — 모양이 아니라 **내용**이 바뀌어도 올려야 한다).

## 4. 검증 — 세 스크립트

```bash
export DEMO_PASSWORD=$(grep '^DEMO_PASSWORD=' .env | cut -d= -f2)
export ADMIN_PASSWORD=$(grep '^ADMIN_PASSWORD=' .env | cut -d= -f2)
W=http://localhost:8081      # 80 에 올렸으면 http://localhost

WEB=$W ./load/verify-deploy.sh          # 게시 포트 + prod + 실제 로그인
WEB=$W ./load/verify-auth.sh            # 로그인·비밀번호 분리·XFF·AI 인증
./load/verify-container.sh "$W"         # 4분기 응답 · SPA 폴백 · CORS 0
WEB=$W ./load/verify-sse.sh             # SSE 가 실제로 흐르는가 (ADR-0044)
```

⚠️ **`verify-sse.sh` 는 코드로 알 수 없는 것을 잰다.** `X-Accel-Buffering` 헤더가
있는지는 소스로 보면 되지만, **헤더가 있다는 것과 이벤트가 나눠서 도착한다는
것은 다른 명제**다 — 프록시가 하나 더 끼거나 gzip 이 켜지거나
`proxy_http_version` 이 1.0 이면 헤더가 멀쩡해도 전부 끝난 뒤 한꺼번에 온다.
판정은 **첫 이벤트 시각 / 마지막 이벤트 시각 비율**(< 0.5)이다.

`/api/assistant` 를 1회 더 쓰므로(위 셋이 이미 9회) 하루 50회 중 10회가 된다.

⚠️ **`verify-auth` 직후 `verify-container` 를 바로 돌리면 429 가 난다.** 앞엣것의
판정 6이 위조 XFF 로 로그인을 40회 시도해 IP 한도(30회/분)를 소진한다. **1분
기다렸다 돌린다** — 스크립트가 그 원인을 정확히 지목하므로 메시지를 믿으면 된다.

⚠️ **`python3` 이 있어야 한다.** 검증 스크립트가 JSON 파싱에 쓴다. 예전 판본은
`python` 을 불렀는데 **우분투에는 그 이름이 없어 배포 대상에서 아예 못 돌았다** —
증상이 "로그인 실패 (HTTP 200)" 이라 원인이 안 보였다.

**넷 다 전부 통과해야 한다.** 예전에는 `verify-auth.sh`의 판정 6이 배포에서
`[FAIL]`인 것이 정상이라고 적혀 있었는데, **그 검사가 배포되지 않는 경로(백엔드
직결 포트)를 재고 있었기 때문**이다. ADR-0033에서 프록시 경유로 옮겼으므로 이제
**통과해야 하고**, 실패하면 nginx의 `X-Forwarded-For` 설정이 빠진 것이다.

`verify-container.sh`에 `ADMIN_PASSWORD`가 필요한 이유는 GM 전용 분기까지 확인하기
때문이다. 두 스크립트 모두 예전에는 `demo-token`으로 토큰을 받았고, 그게 사라진
뒤로 **줄곧 깨져 있었다** — 그래서 이 절차가 지시하던 명령이 실행되지 않았다.

## ⚠️ 4-A. 80/443 이 이미 쓰이고 있다면 (실제 겪은 구성)

이전 프로젝트가 호스트 nginx 로 80·443 을 쓰고 있었다. 그래서:

**① 컨테이너 nginx 를 다른 포트에, 그리고 localhost 에만 묶는다**

```bash
sed -i 's|^WEB_PORT=.*|WEB_PORT=127.0.0.1:8081|' .env
$DC up -d web
docker port gimp-web        # 80/tcp -> 127.0.0.1:8081
```

`0.0.0.0` 이면 클라우드 방화벽만 열려도 **TLS 없이 직접 접근**된다.
`127.0.0.1` 로 묶으면 외부에서 닿는 문이 **호스트 nginx 의 443 하나**가 된다.

**② 호스트 nginx 에 별도 파일로 추가** — 기존 파일은 certbot 이 관리 중이라 안 건드린다

```nginx
# /etc/nginx/sites-available/item-exchange
server {
    listen 80;
    listen [::]:80;
    server_name item-exchange.duckdns.org;

    location / {
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}
```

```bash
sudo ln -sf /etc/nginx/sites-available/item-exchange /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d item-exchange.duckdns.org   # 리다이렉트는 2 선택
```

⚠️ **`nginx -t` 가 실패하면 reload 하지 말 것.** 같은 nginx 를 쓰는 **남의 사이트가
같이 죽는다.** reload 뒤에는 기존 도메인도 200 인지 반드시 확인한다.

⚠️ **`proxy_read_timeout 120s` 가 앞단에도 있어야 한다.** AI 에이전트 분기가
7~25초라 기본 60초로는 **앞단에서 504** 가 난다. 컨테이너 nginx 만 120s 여도 소용없다.

### 프록시가 두 겹이 되면 XFF 가 무의미해진다

```
클라이언트 → 호스트 nginx → 컨테이너 nginx → 백엔드
```

백엔드는 XFF 의 **마지막 값**을 클라이언트로 쓰는데(ADR-0033), 두 겹이면 그게
**호스트 nginx 의 IP** 다. 즉 `TRUSTED_PROXIES` 를 채워도 의도한 효과가 안 난다.

**비워두는 것이 맞다.** 헤더를 아예 안 읽으므로 로그인 한도가 배포 전체 합계(30회/분)가
되지만, ADR-0031 이 *"데모 배포에서 그 공유는 실사용에 지장이 없다"* 고 이미 판단했다.
**2단 프록시 대응은 별도 라운드로 등록돼 있다.**

## 5. 공개 — HTTPS

여기부터는 실제 호스트에서만 가능하다.

```bash
# 방화벽: 80/443 만
sudo ufw allow 80,443/tcp && sudo ufw enable
# Oracle Cloud 는 보안 목록(Security List)도 따로 열어야 한다

# 인증서
sudo certbot --nginx -d <도메인>
```

nginx는 컨테이너 안이므로 **호스트에 별도 nginx/caddy를 두어 TLS 종단**을 하고
`localhost:80`으로 넘기는 쪽이 단순하다. 컨테이너 안 nginx 설정을 건드리면
`frontend/nginx.conf`의 경로 규칙과 `vite.config.ts`가 어긋날 위험이 생긴다.

**TLS를 붙였으면 `TRUSTED_PROXIES`를 채운다** — 그러지 않으면 모든 요청의 IP가
프록시 하나로 합쳐져 로그인 한도가 배포 전체 합계가 된다.

> **이 지시는 한동안 위험했다.** nginx가 `X-Forwarded-For`를 붙이지 않는데 백엔드는
> 그 헤더를 읽었으므로, 채우는 순간 **클라이언트가 위조한 값이 그대로 신뢰**됐다
> (실측: 위조 40회 전부 통과 / 헤더 없으면 31번째 429). ADR-0033에서 nginx에
> `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`를 넣어 해소했다.
> **호스트에 별도 nginx/caddy를 두어 TLS를 종단한다면 그쪽에도 같은 헤더 설정이
> 필요하다** — 안 하면 같은 구멍이 한 겹 앞에서 다시 생긴다.

```bash
docker inspect gimp-web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# 이 값을 .env 의 TRUSTED_PROXIES 에 넣고 backend 재시작
```

> 컴포즈 네트워크의 IP는 고정이 아니다. 재생성하면 바뀌므로 **재시작 시마다 확인**한다.
> 비워두면 헤더를 안 읽을 뿐이라 조용히 뚫리지는 않는다.

## 6. 배포 후 — 재측정할 것

배포해야만 잴 수 있는 것들이다.

| 항목 | 왜 |
|---|---|
| **스레드풀 크기** | ADR-0028의 워커 표는 **12코어** 기준. 4 OCPU면 초과 구독이 더 심하다. `cpu_pool_workers` 를 1·2·4로 바꿔가며 재고 최적값을 고른다 |
| 부하 기준선 | ADR-0020의 수치는 개발기 것이다. **세션 간 비교 금지** 규칙이 그대로 적용되므로 대상에서 새로 잰다 |
| ES 힙 | 기본 512m. 4 OCPU 공유에서 충분한지 |
