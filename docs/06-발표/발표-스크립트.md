# 게임 아이템 통합 거래 플랫폼 — 발표·면접 통합 스크립트

> 슬라이드([발표자료.html](발표자료.html))가 10분용 요약이라면, 이 문서는
> **"무엇을 만들었나 → 어떤 기술을 왜 골랐나 → 그 선택이 맞았다는 근거는
> 무엇인가"** 를 끝까지 따라갈 수 있는 긴 판본이다. 시간 배분과 슬라이드별
> 멘트는 [발표-노트](발표-노트.md)에 따로 있다.
>
> 이 문서는 **파생 문서**다. 결정의 근거는 각 [ADR](../01-Decisions/)에 있고
> 여기서는 그것들을 하나의 이야기로 잇는다. 수치가 어긋나면 ADR이 옳다.

## 0. 프로젝트 한 줄 소개

**여러 게임사(테넌트)의 아이템·계정·게임머니를 한 플랫폼에서 거래하는
멀티테넌트 거래소이고, 설계 목표는 "LLM API를 감싸기만 한 서비스"가 되지 않는
것입니다.**

모든 요청을 하나의 LLM 호출로 흘려보내는 대신, **요청 종류를 먼저 판별해
종류마다 다른 파이프라인**을 태웁니다. 지연시간과 비용을 요청 타입 단위로
통제하기 위해서입니다.

라이브 데모는 `https://item-exchange.duckdns.org` 이고 Oracle Cloud ARM
(aarch64, 4 OCPU / 24GB)에서 돕니다.

규모 감각을 먼저 드리면:

| | |
|---|---|
| 결정 기록(ADR) | **45건** |
| 테스트 | AI **301건** + 백엔드 **57건** (CI가 커밋마다 돌린다) |
| 트러블슈팅 사례집 | **27건** — 그중 상당수가 *"검사 자체가 틀렸던"* 사례다 |
| 부하테스트 | 동시 구매 **26,600여 건**, 오버셀 **0건** |

**발표에서 제일 하고 싶은 말은 이겁니다.** 기능을 다 보여드리기엔 시간이
짧아서, 기능보다 **주장에 근거가 붙어 있는지**를 중심으로 가져왔습니다. 그래서
개선한 것뿐 아니라 **해보고 접은 것**도 같이 있습니다.

## 1. 전체 아키텍처 결정

### 1-1. 왜 Spring Boot와 FastAPI를 분리했는가

```
사용자 (브라우저)
    │
    └─ nginx :80  (단일 오리진 — 배포)
       또는 Vite dev proxy :5173 (개발)
         │
         ├─ /api/backend/*  ──► Spring Boot :8080   (거래·인증·알림)
         └─ /api/ai/*       ──► FastAPI    :8000   (AI 파이프라인)
                                    │
              ┌─────────────────────┼──────────────────┐
              │                     │                  │
        PostgreSQL           Elasticsearch         OpenAI / Claude
        (거래 원장)           (검색 · kNN)          (LLM)
              │                     │
            Redis                RabbitMQ
       (분산 락 · 캐시)         (체결 후 알림)
```

두 서버를 나눈 이유는 **각 생태계의 강점을 그대로 쓰기 위해서**입니다.

Spring Boot는 트랜잭션·JPA·Spring Security가 성숙해 있고, FastAPI는
PyTorch·sentence-transformers·ONNX Runtime을 그대로 쓸 수 있으며 async
네이티브입니다.

**고려한 대안 둘:**

- **Spring Boot 단일 서버 + Python을 자식 프로세스로** — 프로세스 관리가
  복잡해지고, 무엇보다 임베딩 모델을 요청마다 올리거나 상주시켜야 해서
  4 OCPU 환경에 맞지 않습니다.
- **FastAPI 단일 서버** — 거래 트랜잭션·비관적 락·Spring Security를 파이썬으로
  다시 짜야 합니다. 이 프로젝트의 동시성 검증(오버셀 0)이 그 계층에 있습니다.

### 1-2. API 게이트웨이를 두지 않은 이유 (ADR-0023)

두 서버가 **각자 JWT를 검증**합니다. 게이트웨이를 안 둔 근거가 셋입니다.

1. **4 OCPU를 다른 프로젝트와 공유**합니다. 상시 프로세스를 하나 더 띄우는
   비용이 이득보다 큽니다.
2. 게이트웨이의 주된 이점인 **단일 오리진은 이미 확보**돼 있습니다 — 개발은
   Vite dev proxy, 배포는 nginx가 같은 경로 규칙으로 제공합니다. 그래서
   **양쪽 서버 모두 CORS 설정이 없습니다.**
3. **AI 서버는 어차피 자기가 검증해야 합니다.** 비용(LLM)이 발생하는 쪽이
   여기고, 게이트웨이를 둬도 그 앞을 우회하는 경로가 남으면 의미가 없습니다.

대가는 **검증 로직이 Java/Python 두 벌**이라는 것입니다. 완화책으로 클레임
집합을 ADR과 API 명세 한 곳에 고정하고, **발급은 백엔드만** 합니다(파이썬은
검증 전용).

> 이 "우회 경로" 걱정은 추상적인 게 아니었습니다. 나중에 실제로
> `POST /api/llm/test` 라는 라우터에 **인증 의존성이 빠져 있는 것**을
> 발견했습니다 — 토큰 없이 임의 프롬프트를 OpenAI로 보낼 수 있는, 비용 방어
> 3계층을 통째로 우회하는 구멍이었습니다. 라우터를 지우고,
> `tests/test_route_auth_coverage.py` 가 **인증 없는 경로가 존재하지 않음**을
> 고정하게 했습니다. *라우터별 `Depends` 는 빠뜨려도 조용합니다.*

### 1-3. 멀티테넌시 — 인덱스 per 테넌트

Elasticsearch 격리는 **물리적 클러스터 분리가 아니라 인덱스 per 테넌트**입니다.
테넌트별로 샤드·레플리카를 독립 구성할 수 있고, 업계 표준 스택에 가깝습니다.
완전 격리보다 운영 단순성을 택한 **의도적 트레이드오프**입니다.

**테넌트는 요청이 아니라 서명된 클레임에서 옵니다.** 원래는 `X-Tenant-Id`
헤더였는데, 그건 그냥 문자열이라 **누구나 아무 테넌트나 주장할 수 있었습니다.**
멀티테넌시가 이 프로젝트의 간판인데 가장 큰 구멍이 거기 있었던 셈입니다.

## 2. 핵심 기술 스택 선택

### 2-1. PostgreSQL — Oracle이 아니라

라이선스·운영 단순성이 첫째고, 직전 프로젝트가 Oracle이라 **경험을 분산**하려는
의도가 둘째입니다. **검색·벡터 저장소로는 쓰지 않습니다** — 그 역할은
Elasticsearch가 합니다. 포트폴리오 관점에서 "이론적으로 더 화려한 것"보다
**설명 가능한 표준 선택**을 택한 지점입니다.

### 2-2. Elasticsearch — nori를 이미지에 굽는다

한국어 형태소 분석기 **nori** 플러그인을 `docker/elasticsearch/Dockerfile`에
구워 넣습니다. 이미지를 직접 빌드하는 이유는 단순합니다 — **플러그인을 런타임에
설치하면 컨테이너를 재생성할 때마다 사라집니다.**

nori가 실제로 일한 사례가 있습니다. 검색에 카테고리 혼입(`"5만원 이하 검"`에
활이 섞임)이 있어서 처음엔 BM25를 의심했는데, **BM25는 정상이었습니다** —
nori가 `단궁`을 한 토큰으로 유지해서 `검`에 매칭되지 않았습니다. 활은
**kNN 2위**로, 파인튜닝한 임베딩이 올린 것이었습니다. *의심할 대상을 먼저
측정하지 않았으면 엉뚱한 데를 고쳤을 겁니다.*

### 2-3. Redis — 분산 락과 시맨틱 캐시, 그리고 정반대의 장애 정책

같은 Redis를 세 가지로 씁니다: **분산 락**(구매·입찰), **시맨틱 캐시**,
**요청 한도**.

여기서 설명하고 싶은 설계 포인트는 **장애 정책을 일부러 반대로 걸었다**는
것입니다.

| 용도 | Redis 장애 시 | 왜 |
|---|---|---|
| 구매 락 | **거절한다** | 정합성 장치다. 락 없이 통과시키면 오버셀이 난다 |
| 요청 한도 | **통과시킨다**(fail-open) | 비용 방어 장치다. 정합성과 무관하고, 막으면 서비스가 죽는다 |

**같은 인프라를 쓴다고 같은 정책일 필요는 없습니다.** 그 컴포넌트가 무엇을
보호하는지가 정책을 결정합니다.

> 다만 fail-open에는 함정이 있었습니다. 시맨틱 캐시의 `lookup`/`store`가
> `except: pass` 였고 리미터도 fail-open이라, `REDIS_PASSWORD` 선언이 빠져
> 인증이 실패했을 때 **증상이 "적중률 0%" 하나뿐**이었습니다. 그런데 이
> 저장소는 이미 "임계값 0.98이라 잘 안 맞는 게 정상"이라고 적어둔 상태였습니다
> — **컴포넌트가 무력해 보일 이유를 이미 갖고 있으면, 진짜 고장이 그 뒤에
> 숨습니다.** 지금은 두 지점 모두 경고를 남깁니다.

`redisson-spring-boot-starter`는 **Boot 4와 호환되지 않습니다**(재배치된
`RedisProperties`를 참조해 컨텍스트 기동이 실패). 순수 `org.redisson:redisson`에
`RedissonClient` 빈을 직접 정의해 씁니다.

### 2-4. RabbitMQ — 큐가 나르는 것을 바꿨다

기획서의 원안은 `락 → 큐 발행 → 컨슈머가 DB 작업`이었습니다. **채택하지
않았습니다.** 그러면 구매가 `202 Accepted`가 되고, 이 프로젝트가 부하테스트로
검증한 **`재고 감소분 == 성공 응답 수`** 라는 단언이 응답 시점에 성립하지
않습니다.

그래서 **체결은 동기로 두고, 큐는 체결 *이후*(알림)만** 나릅니다. 26,600건에서
검증한 보장을 지키는 쪽을 택했습니다.

세 가지 설계 결정이 붙습니다.

- **발행은 `@TransactionalEventListener(AFTER_COMMIT)`** — 트랜잭션 안에서
  발행하면 롤백된 거래의 알림이 나갑니다.
- **발행 실패는 거래를 실패시키지 않습니다**(fail-open). 다만 fail-open에는
  *지연* 축도 있습니다 — AMQP 기본 연결 타임아웃이 60초라, 그대로 두면 브로커가
  죽었을 때 **"구매는 성공하는데 1분 걸림"** 이 됩니다. `connection-timeout: 2s`.
- **멱등 키는 `(recipient_id, trade_id)` 유니크**이고, 잡는 예외는
  `DuplicateKeyException` 이어야 합니다. 부모 타입인
  `DataIntegrityViolationException` 은 FK 위반도 삼켜서, 없는 유저를 가리키는
  메시지가 **DLQ로 가는 대신 "이미 처리됨"으로 사라집니다.**

> 이 라운드에서 배운 일반 규칙: **새 인프라 의존성은 장애 정책을 세 곳에
> 걸어야 합니다** — 호출부, `depends_on`, 그리고 **헬스체크**. 마지막을
> 놓쳤더니 Spring이 자동 등록한 `rabbit` 헬스 인디케이터 때문에 브로커가 죽자
> **거래·검색까지 포함해 인스턴스 전체가 `unhealthy`** 가 됐습니다. 코드는
> 정성껏 fail-open이었는데 말입니다.

### 2-5. LLM 프로바이더 — OpenAI 주, Claude는 용도가 정해진 보조

Gemini·DeepSeek은 **의도적으로 쓰지 않습니다.** 직전 프로젝트에서 4개
프로바이더를 썼기 때문에, 이번엔 **구체적인 용도가 있을 때만** 추가한다는
원칙을 세웠습니다. Claude는 두 가지 용도로만 들어옵니다 — **서킷 브레이커 뒤의
실제 폴백 대상**과 LLM-Judge 비교 모델.

**모델 ID 선택이 결정 사항이 됐습니다** (ADR-0045). 채택한 것은
`gpt-5.4-mini-2026-03-17` / `claude-sonnet-4-6` 인데, **최신 모델이 아니라
`temperature=0`을 아직 받는 가장 최신 모델**입니다. 그 위 세대는 전부 거부합니다:

```
Unsupported value: 'temperature' does not support 0 with this model
`temperature` is deprecated for this model
```

`temperature=0`을 포기하면 이 저장소가 ADR-0017에서 세운 결정성이 통째로
무너집니다. **"왜 낡은 모델이냐"의 답이 취향이 아니라 재현 가능한 한 줄짜리
검사로 남아 있는** 셈입니다.

날짜를 고정한 것도 결정입니다. 이전 `gpt-4o-mini`는 **부동 별칭**이었고, 그게
"모델이 드리프트한 것"과 "우리가 바꾼 것"을 구분하지 못하게 만들었습니다.

## 3. AI 파이프라인 — 이 프로젝트의 본체

### 3-0. 전체 흐름

```
POST /api/assistant
   │
   ├─(0) 인증 ─────────── 토큰 없음/무효/만료 → 401
   ├─(0) 요청 한도 ────── 20회/분 초과 → 429 + Retry-After
   │
   ├─(1) 시맨틱 캐시 ──── 적중 → 즉시 반환 (LLM 0회, p95 25.9ms)
   │
   ├─(2) Intent Router ── 규칙 → 애매하면 KoELECTRA → 확신도 낮으면 COMPOUND
   │
   ├─(3) 의도별 분기
   │      faq_smalltalk  → 확정 응답        (LLM 0회)
   │      item_search    → 검색 파이프라인   (LLM 2회 — 질의이해 ‖ 도메인판정)
   │      price_forecast → LSTM/Cold Start  (LLM 3회 — 위 둘 + 설명)
   │      anomaly_check  → Autoencoder      (LLM 1회)
   │      compound       → 에이전트(MCP)     (LLM 1~6회 = 도구 수 + 1)
   │
   └─(4) 정책에 따라 캐시 저장
```

**설계 목표가 `llm_calls` 라는 한 숫자로 드러납니다.** "LLM을 안 쓴다"가 아니라
**"유형마다 다르게 쓴다"** 입니다.

캐시가 라우터보다 **앞**에 있는 이유를 자주 물어보시는데 — 어떤 분기로 갈
것이든, 같은 질문이면 **일을 아예 안 하는 게 가장 쌉니다.**

### 3-1. Intent Router — 2단 구조 (ADR-0010)

```
규칙(정규식) ──확정──► 의도
     │
   abstain(확신 없음)
     ▼
KoELECTRA-small ──확신도 ≥ 임계값──► 의도
     │
   확신도 낮음
     ▼
   COMPOUND (에이전트가 알아서 한다)
```

규칙이 먼저인 이유는 **대부분의 질의가 규칙으로 끝나고 그게 LLM 0회에 수
밀리초**이기 때문입니다. 분류기는 lazy 로딩이라 규칙만으로 처리되는 요청은
모델을 아예 안 올립니다 — 4 OCPU 제약에서 나온 설계입니다.

**여기서 제일 배운 게 있습니다.** 분류기를 손실 0.013까지 학습시켰더니
경계 질의 에스컬레이션이 **0/20** 으로 붕괴했습니다. 확신도를 보니:

| | 확신도 중앙값 |
|---|---|
| **틀린** 답 | 0.978 |
| **맞은** 답 | 0.991 |

**어떤 임계값도 둘을 못 가릅니다.** 확신도가 교정(calibrate)돼 있지 않은
겁니다. 임계값을 조정하는 대신 **애매함을 가르쳤습니다** — LLM으로 생성한 모호한
발화 108건을 `compound`로 라벨링하고 label smoothing 0.1을 넣었더니 **15/20**.

> 일반화하면: **모델이 확신하는 것과 맞는 것은 다른 이야기입니다.** 임계값을
> 돌리기 전에 분포를 먼저 그려봐야 합니다.

### 3-2. 시맨틱 캐시 — 유사도 매칭을 대부분 막았다 (ADR-0012)

이름이 시맨틱 캐시인데 **기본은 정확 일치**이고, 유사도 매칭은
`faq_smalltalk`에만 열려 있습니다. 이유는 실측입니다.

| 쌍 | 코사인 유사도 |
|---|---|
| **함정 쌍** (`+8 롱소드 시세` vs `+9 롱소드 시세`) | **0.9787** |
| 동의 쌍 (표현만 다른 같은 질문) | 0.845 |

**함정 쌍이 동의 쌍보다 유사합니다.** 파인튜닝 모델과 베이스 모델 **둘 다**
그랬으므로 파인튜닝 부작용이 아니라 **짧은 질의에 대한 문장 임베딩의 성질**
입니다. 그래서 유사도 매칭은 **오탐 대가가 작은 곳에만** 허용합니다.

"정확 일치"의 범위는 딱 한 번 넓혔습니다 — `normalize_query()`로 **문장 끝
문장부호와 중복 공백**만 제거합니다. `"…알려줘!"`가 `"…알려줘"`를 못 맞히는 건
아무도 원하지 않으니까요. 조사·띄어쓰기까지 손대면 `"100렙 이상"`/`"100렙이상"`은
되지만 **멈출 원칙이 없어집니다.** 가드는
`test_trap_pairs_still_get_different_keys`이고, 이 테스트는 공허하지 않습니다 —
욕심 많은 정규화(숫자·공백 제거)는 함정 쌍 16개 중 **4개를 충돌**시킵니다.

의도별 정책:

| 의도 | 캐시 | TTL | 유사도 |
|---|---|---|---|
| `faq_smalltalk` | O | 24시간 | **O** |
| `item_search` | O | 10분 | X |
| `price_forecast` | O | **다음 자정까지** | X |
| `anomaly_check` | **X** | — | X |
| `compound` | O | 5분 | X |

`price_forecast`가 자정 만료인 이유 — 예측 근거가 **일별** 시세 시리즈라 날짜가
바뀌면 근거가 바뀝니다. 고정 TTL이면 자정 직전 값이 다음 날까지 삽니다.

### 3-3. 검색 파이프라인

```
질의
 ├─ 도메인 판정           ◄─ LLM 1회 (아래와 병렬 gather)
 │    └─ 밖이면 종료 ──────── 확정 거절 (임베딩·ES·리랭킹 생략)
 └─ Query Rewrite + Text-to-DSL  ◄─ LLM 1회 (동의어 확장 + 필터 추출을 한 번에)
      ├─ rewritten_query ──┬─ BM25 (nori)   ─┐
      │                    └─ 임베딩 → kNN  ─┤ 한 번의 _msearch
      └─ filters ──────────── 양쪽 filter 절 ┘
                                             ▼
                                      앱 레벨 RRF 융합
                                             ▼
                             Cross-Encoder 재순위 (ONNX int8, 상위 20)
                                             ▼
                                        상위 N건
```

**(a) Rewrite와 Text-to-DSL을 한 호출로 합쳤습니다.** 따로 부르면 검색 한 번에
왕복이 2회 붙습니다.

**(b) RRF를 앱에서 계산합니다** (ADR-0005). ES의 네이티브 RRF는 **Platinum
라이선스**이고 이 클러스터는 basic입니다. `_msearch`로 BM25와 kNN을 한 번에
보내고 융합만 파이썬에서 합니다.

**(c) 리랭커는 다국어 mMARCO 변종입니다** (ADR-0006). 원래 계획은 영어
`ms-marco-MiniLM-L-6-v2` 였는데, **영어 토크나이저가 한국어를 자모 단위로
쪼개서 재순위가 없느니만 못했습니다.** 이건 "성능이 조금 나쁘다"가 아니라
**부호가 뒤집힌** 결과라서, 안 재봤으면 리랭킹을 넣고 품질이 떨어진 채로
갔을 겁니다. ONNX 변환 + int8 양자화 + 상위 20건 제한은 레이턴시 예산입니다.

**(d) 임베딩을 직접 파인튜닝합니다** (ADR-0007). sentence-transformers +
`MultipleNegativesRankingLoss` + **하드 네거티브 마이닝**.

여기서 설계 얘기를 하나 하고 싶습니다. 기획서에는 하드 네거티브 쌍을 LLM으로
생성한다고 적었는데, 실제로는 **규칙 + LLM 하이브리드**입니다.

| 방식 | 담당 |
|---|---|
| **규칙(결정적)** | 구조화 필드로 유도 가능한 쌍 — 강화 수치 형제(+8 vs +9), 같은 카테고리 내 텍스트 중첩 |
| **LLM** | 규칙이 못 만드는 것 — 현실적인 사용자 표현, 의미적 near-miss(속성·직업 스왑) |

**LLM으로 만들 수 있다고 LLM으로 만들 이유는 없습니다.** 결정적으로 만들 수
있는 쪽은 결정적으로 만드는 게 재현 가능하고 공짜입니다.

측정 결과(홀드아웃):

| 지표 | 파인튜닝 전 | 후 |
|---|---|---|
| Recall@1 | 0.148 | **0.389** |
| MRR | 0.301 | **0.510** |
| RAGAS context_precision | 0.294 | **0.513** |

`TRAIN_ITEMS`(24)와 `EVAL_ITEMS`(18)는 **엄격히 분리**되고 임포트 시점에
검증됩니다. 평가셋 오염은 조용히 일어나 수치만 부풀립니다.

### 3-4. 하드 필터 — 임계값이 없다는 게 요점 (ADR-0014 · 0015)

카테고리 혼입을 **점수 임계값이 아니라 스키마로** 막습니다.

| 필드 | 값 |
|---|---|
| `category` | 무기 / 방어구 / 장신구 / 소모품 / 계정 / 재화 |
| `subcategory` | 검 · 둔기 · 창 · 활 · 지팡이 / 갑옷 · 방패 · … |
| `element` | 화염 · 냉기 · 번개 · 암흑 · 신성 · **무속성** |

측정(질의 10건 × 상위 8건):

| | 필터 없음 | +subcategory | +element |
|---|---|---|---|
| **부적합** 결과 | 50건 | 26건 | **14건** |
| **적합** 결과 | 20건 | 20건 | **20건 (손실 0)** |

`subcategory == "활"` 은 **실행마다 흔들리지 않습니다.** 재색인 비용이 있는
대신 **캘리브레이션이 필요 없습니다.**

속성 태깅 규칙 중 자명하지 않은 것들 — 발표에서 한 번 짚을 만합니다:

- **저항은 속성이 아닙니다.** `용비늘 방패`(화염 피해 감소)를 `화염`으로 태깅하면
  `"불속성 장비"` 검색에 **대화염 방패**가 나옵니다. 없애려던 오탐과 같은 종류죠.
- **이름이 아니라 효과로 판정합니다.** `바람의 장궁`은 효과가 순수 물리라 `무속성`.
- **`무속성`은 값이고 `null`이 아닙니다.** 필터의 `null`은 "속성 조건 없음".

**빠진 값은 임포트 시점에 터집니다.** 값이 없는 아이템은 그 필터가 걸린 검색에서
**조용히 사라지므로**, `app/corpus/__init__.py`가 막습니다.

### 3-5. 시세 예측 — 전역 모델 하나 (ADR-0008)

```
거래 이력 조회
   ├─ 충분 → PriceLSTM (14일 윈도 → 7일 직접 다단계)
   └─ 부족 → Cold Start: ES kNN으로 유사 아이템 → 추세 가중 상속
```

**아이템별 모델이 아니라 전역 모델 하나입니다.** 아이템마다 학습하면 신규
아이템은 영원히 모델이 없고, 학습·배포 비용이 아이템 수에 비례합니다. 대신 가격
절대값이 아니라 **윈도 마지막 가격 대비 비율**로 정규화해 스케일 차이를
없앴습니다.

**판단 기준이 MAPE가 아닙니다.** 합성 데이터라 MAPE 자체는 아무것도 증명하지
않습니다. 그래서 `train_forecast`는 **항상 naive 기준선을 같이 출력**합니다.

| | 값 |
|---|---|
| LSTM MAPE | **4.70%** |
| 최고 naive (last-value / linear drift) | 4.87% |
| 신호 상관 | 0.304 |

**이겼지만 근소합니다.** 그리고 그 근소함과 "평균 회귀 경향"은 같은 현상입니다 —
데이터 생성 과정상 예측 가능한 정보량이 원래 적습니다. 이 문장을 그대로
적어두는 게 이 프로젝트의 방식입니다.

### 3-6. 이상거래 탐지 — 오토인코더를 고른 이유는 정확도가 아니다 (ADR-0009)

```
거래 → 11개 문맥 상대 피처 → RobustScaler → TradeAutoencoder(11-8-4-8-11)
                                                  ▼
                                    재구성 오차 = 이상 점수
                                                  ▼
                                    피처별 기여도 분해 → LLM 설명
```

Isolation Forest 대신 오토인코더를 쓴 이유는 **재구성 오차를 피처별로 쪼갤 수
있어서**입니다. GM에게 *"왜 이상인가"*를 축 단위로 답할 수 있어야 합니다.
화면에 뜨는 기여도 막대가 그겁니다.

**임계값을 학습셋에서 뽑으면 안 됩니다.** 오토인코더는 자기 학습 데이터를 가장
잘 복원하므로 그 분위수는 낙관 편향입니다.

| 임계값 출처 | 홀드아웃 정상 트래픽 발화율 |
|---|---|
| 학습셋 p99 | **1.32%** (의도한 값 1.00%) |
| 홀드아웃 p99 | 1.00% |

그래서 정상 데이터를 **3분할**합니다: 학습 / 임계값 산정 / 평가.

**그리고 이 모델은 규칙 기준선에 지는 영역이 있고, 진 대로 적었습니다.**

| 시나리오 | 오토인코더 | `max \|z\|` 규칙 |
|---|---|---|
| 신규 계정(뮬) 거래 | **놓침** | **100% 탐지** |
| 여러 축에 증거가 흩어진 복합 이상 | **탐지** | 놓침 |

재구성 오차는 "**드문가**"가 아니라 "**표현 불가능한가**"를 잽니다. 신규 계정은
학습 데이터 꼬리에 이미 있어서 거의 완벽히 복원됩니다. **규칙을 모델로 대체하지
말 것** — 상호 보완입니다.

> 합성 이상치 주입에서도 배운 게 있습니다. 처음에 복합 이상을 정상
> 최댓값(1.31배)보다 큰 **1.5배** 가격으로 만들었더니 가격 규칙 하나에 63%가
> 잡혔습니다. "복합"이 아니라 그냥 비싼 거래였던 겁니다. 정상 분포의
> p80~p95(1.046~1.073배)로 재조정하니 가격 규칙 탐지율이 **0%**가 됐고, 그제야
> "여러 축에 흩어진 이상"이 됐습니다. **합성 데이터로 평가할 땐 정상 분포를
> 먼저 확인하고 주입해야 합니다.**

### 3-7. 에이전트 + 내부 MCP (ADR-0011)

복합 질의는 **순차 도구 호출 루프**(최대 5단계)로 처리합니다. 도구는 **내부 MCP
서버**로 노출된 셋입니다.

| 도구 | 감싸는 것 |
|---|---|
| `search_items` | 검색 파이프라인 |
| `forecast_item_price` | 시세 예측 |
| `detect_trade_anomaly` | 이상거래 탐지 |

**MCP는 진짜 프로토콜이되 전송만 인프로세스입니다.** 에이전트가 같은 FastAPI
앱 안에 있어서 self-HTTP 호출은 왕복·직렬화·타임아웃을 공짜로 얻는 선택이
아니고, 당시 알려진 이벤트 루프 블로킹과 맞물려 교착 위험도 있었습니다.
`python -m app.services.mcp`로 **같은 서버를 stdio로도 노출**하므로 외부 MCP
클라이언트가 붙을 수 있습니다.

**MCP를 쓴 범위를 의도적으로 좁혔습니다.** 외부 커넥터(Steam API, Discord, 위키)는
**제외**입니다 — 서드파티 인증·파싱·에러 처리 비용을 지지 않고 MCP 서버
설계/구현만 보여주는 게 목표였습니다.

**도구 출력의 필드명이 프롬프트 엔지니어링입니다.** 이게 이 프로젝트에서
가장 재미있는 버그였습니다. 에이전트가 매물 등록가(`price`)와 최근
체결가(`anchor_price`)를 직접 비교해 **"저평가됐으니 지금 사라"**는 잘못된 투자
조언을 냈습니다. 고친 방법은 로직이 아니라 **이름**입니다.

| 이전 | 이후 |
|---|---|
| `price` | `listing_price` |
| `anchor_price` | `baseline_price` + `baseline_source` |

`baseline_source`는 `"최근 체결가"` / `"관측된 거래 N건의 평균"` /
`"등록가(거래 이력 없음)"` 중 하나입니다. **새 필드는 이름만 보고 뜻이 서게
지어야 합니다.**

## 4. 환각 방어 — 이 프로젝트가 가장 오래 붙잡은 주제

LLM을 쓰는 서비스에서 제일 무서운 건 **틀린 답이 아니라 그럴듯하게 틀린 답**
입니다. 여기서 실제로 겪은 세 가지와 대응을 보여드리겠습니다.

### 4-1. 설명 LLM이 자기 검색 결과를 부정했다 (ADR-0036)

`10만원 이하 검` 질의에 22,000~45,000원짜리 검 **네 건**을 찾아놓고, 설명 LLM이
이렇게 답했습니다.

> *"10만원 이하의 검은 없습니다 … 모두 10만원을 초과하거나 검이 아닌 무기입니다."*

**두 주장 다 거짓이고, 반증하는 카드 넷이 답변 바로 아래에 떠 있었습니다.**

원인은 프롬프트가 **하드 필터가 이미 끝낸 판정을 다시 시킨 것**이었습니다.
"종류가 맞지 않는 항목은 빼고 말하라"고 지시하면서, 페이로드에는
`subcategory`(`검`)를 안 넣고 `category`(`무기`)만 넣었습니다 — **판단하라면서
판단할 필드를 안 준 셈**입니다. 그 지시 자체가 하드 필터 도입 이전의 화석이었죠.

**해결은 프롬프트 수정이 아니라 호출 제거였습니다.** 결과 목록을 문장으로 옮길
이유가 없습니다 — 항목이 이름·가격·종류·속성을 달고 나오므로 설명이 더할 정보가
없고, **더할 게 없는 자리에서 LLM은 지어냅니다.**

```
검 · 100,000원 이하 조건으로 4건 찾았습니다.
```

> **일반 규칙으로 남긴 것:** 결정적 단계가 이미 보장한 성질을 LLM에게 다시
> 확인시키지 말 것. 근거를 지어냅니다.

### 4-2. 도메인 밖 질의에 다른 아이템의 진짜 숫자로 답했다 (ADR-0039)

`"삼성전자 주식 어때?"` 에 이렇게 답했습니다.

> *"삼성전자 주식의 최근 거래가는 약 26,090원"*

**모든 숫자가 진짜였습니다** — `게임 머니 1000만 골드`의 실제 예측값이었죠.
**거짓인 것은 주어 하나뿐**입니다. kNN은 어떤 질의에도 k건을 돌려주므로 검색이
뭔가를 "찾아내고", 예측은 그 아이템의 진짜 값을 계산하고, 설명 LLM이
**질의에서 주어를 골라** 왔습니다.

대응이 셋인데, 각각 다른 성격입니다.

| 분기 | 도메인 밖 38건 중 | 장치 |
|---|---|---|
| `item_search`·`price_forecast` | 22 (58%) | **도메인 판정 게이트** → 확정 거절 |
| `compound`(에이전트) | 7 (18%) | MCP가 빈 배열이 아니라 **문장으로 된 안내**를 반환 |
| `faq_smalltalk` | 9 (24%) | **이미 안전** — 기본 응답이 취급 범위를 밝히며 거절 |

**세 번째가 요점입니다.** FAQ 분기는 손대지 않았습니다. 이미 맞게 동작하고 LLM
0회로 결정적이니까요. **아무것도 안 해도 맞는 경로에 게이트를 더하면 그건
장식이고, 장식은 잘못된 확신을 팝니다.**

설계에서 가장 신경 쓴 두 가지:

- **판정을 질의이해 프롬프트의 JSON 스키마에 얹지 않았습니다.** 얹으면 호출이
  안 느는 게 장점인데, **두 번 측정하고 두 번 기각**했습니다 — 재작성 토큰집합
  일치도가 대조군 대비 **-0.234 → -0.248** 로, **문구를 고쳐도 안 움직였습니다.**
  즉 문구가 아니라 **스키마가 늘어난 것 자체의 대가**였고, 재작성 텍스트는
  BM25·kNN 양쪽에 들어갑니다. 별도 호출로 떼어내니 회귀가 **구조적으로 0**이고,
  둘 다 순수 I/O 대기라 **병렬로 던지면 지연은 느린 쪽 하나치**입니다.
- **거절 문구가 질의를 되풀이하지 않습니다.** `"삼성전자 주식은 다루지
  않습니다"` 처럼 대상을 받아 적으면, 게이트가 틀렸을 때(도메인 안을 거절했을
  때) 그 문장이 오히려 설득력을 갖습니다. `_out_of_domain()` 은 아예
  **질의를 인자로 받지 않습니다** — 지시가 아니라 **함수 시그니처로** 막았습니다.

### 4-3. 결과가 0건일 때 (ADR-0016)

결과가 비면 **LLM을 거치지 않고** 확정 응답을 만들고, **무슨 조건으로 찾았는지**
같이 줍니다.

```
검 · 화염 속성 · 30,000원 이하 조건에 맞는 매물이 없습니다.
```

같은 입력 5회의 답변이 **5가지 → 1가지**가 됐습니다. 결과가 있으면 항목 자체가
종류·속성을 달고 나와 검증되지만, **0건에는 검증할 대상이 없습니다** — 그때
유일한 근거가 "무슨 조건으로 찾았는가"입니다.

**0건 응답은 캐시에 저장하지 않습니다.** 판정 근거인 필터 추출이 완전히 안정적이지
않아 질의 문자열로 캐시하면 여러 추출 중 하나를 TTL 동안 고정하게 되고,
**"없다"는 가장 낡기 쉬운 답**이기 때문입니다(매물 하나만 등록돼도 거짓).

### 4-4. 결정적 후처리가 프롬프트를 이겼다 (ADR-0040)

`"무속성 검 찾아줘"` 가 `element="무속성"` 을 **50번 중 8번**만 맞혔습니다.
모델이 "무속성"을 *"속성 언급 없음"* 으로 읽는 겁니다. 코퍼스 42개 중 **35개가
무속성**이라 필터를 잃으면 검색이 사실상 무필터가 됩니다.

**프롬프트에는 이미 정확히 그 말이 적혀 있었습니다** — `무속성/속성 없는 →
"무속성"`, 그리고 `null`과의 차이까지. **맞는 말로 지시했는데 42/50을
틀렸습니다.**

그래서 `fill_missing_element()` 라는 **결정적 후처리**가 추출이 `null`을 냈고
질의에 글자가 있으면 채웁니다. 안전선이 셋입니다.

- **채우기만 하고 덮어쓰지 않습니다** → 잘 되는 다른 속성 추출(97.5%)에 닿을 수 없음
- **`무속성` 하나만** 다룹니다 → `"화염 저항 방어구"` 처럼 **낱말이 있어도 답이
  `null` 인 짝**이 다른 속성에는 있습니다(저항은 속성이 아니니까요)
- **부정형은 채우지 않습니다** → 정반대로 필터링하는 것이 안 하는 것보다 나쁩니다

**더 큰 소득은 정확도가 아니라 결정성이었습니다.** 원 추출은 두 실행에서
62% ↔ 86% 로 흔들렸는데 **후처리한 결과는 두 번 다 93%에 같은 잔차**였습니다.

> 그리고 이 판단이 모델 교체에서 검증됐습니다(ADR-0045). `gpt-5.4-mini`는
> 무속성을 스스로 맞혀 **채우기 경로가 0건 발동**합니다. 대신 **부정형에 스스로
> 채우는** 반대 결함이 생겨서, 후처리가 이제 **지우기**도 합니다. *결정적 단계를
> 확률적 단계 앞에 두는 판단은 옳았고, 그것이 막던 것이 **그 모델의 성질**
> 이었을 뿐입니다.* 원소 추출은 111/117 → **117/117**.

### 4-5. 프롬프트를 눈으로 고치면 안 된다

이 주제에서 가장 인상적인 실측입니다. `불속성`과 `무속성`을 혼동하지 말라는
**한 줄 설명**을 프롬프트에 추가했더니:

> 정답률 **97.5% → 22%**

**혼동 가능한 값을 이름으로 부르는 것 자체가 모델을 그쪽으로 프라이밍**했습니다.
되돌렸습니다. **그 줄은 명백히 옳아 보였고 코드 리뷰를 통과했을 겁니다.**

그래서 프롬프트를 건드리는 하네스를 세 개 만들었습니다:
`evaluate_rewrite_determinism.py`(추출),
`evaluate_explanation_prompts.py`(설명 프롬프트),
`evaluate_domain_gate.py`(도메인 게이트).

여기서 정착된 규칙 넷:

1. **대조군 없는 before/after는 근거가 아니다.** temperature 0에서도 10건 중 1건은
   다르게 재작성되므로, 신구 일치도 0.89는 **구-구 일치도를 모르면 아무 말도 못
   합니다.** 옛 프롬프트를 두 번 돌린 게 *"문구 문제"* 를 *"스키마 문제"* 로
   바꿨습니다.
2. **한 번에 하나만 바꾼다.** 문구 4개를 같이 넣었다가 게이트가 나빠졌는데
   (4.13% → 5.30%), 어느 둘 때문인지는 **측정이 아니라 샘플을 읽어서** 추정했습니다.
3. **수집과 채점을 분리한다.** 첫 하네스는 인라인 채점 후 답변을 버려서, 지표가
   틀린 걸 알았을 때 재검증에 LLM 99회가 또 들었습니다. 답변을 저장하니
   다섯 번째 지표를 추가해 재채점하는 데 **0회**가 들었습니다(`--score-only`).
4. **비긴다는 건 지표가 차이를 못 본다는 뜻일 수 있다.** 두 후보가 계획한 네
   지표에서 0-0-0-0 이었는데, **샘플을 읽어보니** 한쪽이 가격 질문에
   *"거래를 진행하는 것이 좋습니다"* 라는 **요청하지 않은 투자 조언**을 33건 중
   6건 하고 있었습니다. 다섯 번째 지표를 만들어 기각했습니다. **지표는 내가
   생각해낸 것만 잽니다.**

## 5. 동시성 — 오버셀 0건

### 5-1. 설계

```
구매 요청 → Redis 분산 락 획득 (Redisson)
             │ 실패 → 409
             ▼
        재고 확인 → 차감 → 거래 생성  (한 트랜잭션)
             ▼
        커밋 후(AFTER_COMMIT) RabbitMQ 발행 → 알림
```

낙관적 락(`@Version`)과 분산 락을 **병행**합니다(ADR-0001). 분산 락이 1차
직렬화이고, 낙관적 락이 최후 방어선입니다.

### 5-2. 검증 — 주장에서 사실로

여기가 이 프로젝트에서 **주장이 사실로 바뀐 지점**입니다. ADR-0001을 쓸 때는
"오버셀이 안 난다"가 설계상의 주장이었고, 부하테스트가 그걸 처음 검증했습니다.

| | 결과 |
|---|---|
| **오버셀** | **0건** — 동시 구매 26,600여 건에서 `재고 감소분 == 성공 응답 수` |
| 처리량 상한(단일 아이템 경합) | **107 req/s**, knee ≈ 4 VU |
| 병목 — 경합 시 | 락 **대기** 0.178s vs **보유** 0.007s → 큐잉 |
| 병목 — 20개로 분산 시 | **429 req/s** (4배). 대기 ~0, 대신 **보유가 5배** → DB가 제약 |

**`load/run.sh`가 매 실행마다 `재고 감소분 == 201 응답 수 + 워밍업 1` 을
단언합니다.** 하네스를 건드릴 일이 있어도 이 단언은 남겨야 합니다.

> **병목은 하나가 아니라 부하 형태에 따라 옮겨갑니다.** 경합 프로파일만 쟀으면
> "락이 병목"에서 끝났을 겁니다. 대조군(분산 프로파일)이 그걸 뒤집었습니다.

시드 데이터가 **전제 조건이지 최적화가 아닙니다** — 데모 아이템은 `stock=10`
이라 실부하는 10요청이면 소진되고, 그러면 **락 경합이 아니라 거절률을 재게
됩니다.**

## 6. 관측성 — 그리고 여기서 배운 게 제일 많다

### 6-1. 계측 지점은 하나 (ADR-0019)

파이프라인이 이미 단계별 `timings` dict를 재고 있으므로, 단계마다 계측 코드를
흩뿌리는 대신 **응답을 만들 때 한 번** 히스토그램으로 옮깁니다
(`record_response()`). 새 단계가 생기면 `_STAGE_BY_KEY`에 **한 줄**입니다.

**라벨은 `tenant`/`intent`/`stage`/`outcome`에서 멈춥니다.** `item_id`,
`trade_id`, `user_id`, 질의 문자열은 **절대 라벨로 쓰지 않습니다** — 무한히
늘어나는 값이라 시계열이 폭발합니다. *"어떤 아이템이 느렸나"* 는 메트릭이 아니라
**로그로 답할 문제**입니다.

**Prometheus/Grafana는 `--profile observability` opt-in**입니다. 4 OCPU 공유
박스에서 부하테스트 중 스크레이핑하면 **측정 대상의 CPU를 뺏습니다.** 부하테스트
집계는 히스토그램이 누적값이라는 성질을 이용해 **`/metrics`를 전후로 받아
차분**해서 읽습니다.

### 6-2. 부하 중 벽시계 시간은 그 단계의 작업량이 아니다 (ADR-0025 → 0026)

이게 발표에서 깊게 파는 지점 중 하나입니다.

캐시 적중 경로를 분해했더니 `cache_encode` 27% / `cache_lookup` 73% 였습니다.
**"임베딩은 27%뿐이니 손댈 가치가 없다"** 고 판단하고 접었습니다.

**그런데 격리해서 재보니 정반대였습니다.**

| | 10 VU 부하 중 (벽시계) | 격리 측정 |
|---|---|---|
| `cache_lookup` | **73%** | **1.05ms** |
| `cache_encode` | 27% | **15.77ms** |

`encode_one`은 `async` 핸들러 안의 **동기 CPU 호출**이라 **이벤트 루프 전체를
막습니다**(10ms 티커가 평균 17.28ms 늦게 깨어났습니다). **73%는 다른 요청들이
그 27%를 기다린 시간**이었습니다.

적중 시 임베딩을 지연화한 결과:

| | 이전 | 이후 |
|---|---|---|
| p95 | 279ms | **25.9ms** |
| 처리량 | 48 req/s | **316 req/s** |

**기록을 지우지 않고 정정만 붙였습니다.** ADR-0025의 반박이 틀렸고 ADR-0020의
원래 지목이 옳았다는 것까지 그대로 남아 있습니다.

> **확인 비용이 쌉니다.** 10ms `asyncio.sleep` 티커를 옆에서 돌리고 얼마나 늦게
> 깨는지 보면 됩니다. 어떤 단계가 격리 측정으로 예측되는 것보다 훨씬 커 보이면
> 이걸 먼저 의심하세요.

### 6-3. 나머지도 스레드로 뺐다 — 그런데 `asyncio.to_thread`가 아니다 (ADR-0028)

전용 `ThreadPoolExecutor(max_workers=2)` 를 `run_cpu()` 뒤에 뒀습니다.
`asyncio.to_thread`의 기본 실행기(대상 박스 8, 개발 박스 16)는 **측정에서 더
나빴습니다** — torch가 4워커에서 **+85% 느립니다**. 이미 내부적으로 intra-op
스레드를 쓰기 때문입니다.

**임계도 뒀습니다: 격리 중앙값 5ms 아래는 인라인으로 둡니다.** 스레드 홉이
0.211ms라서, 오토인코더(0.31ms)와 LSTM(0.45ms)은 옮기면 손해입니다.

**이 라운드의 사전 조사가 세 가지를 뒤집었습니다:**

1. 지배적 블로커는 임베딩이 아니라 **리랭커**(103~189ms, `encode_one`의 4~5배)
2. 오토인코더는 **애초에 대상이 아니었다**
3. `/api/anomaly/*` 는 **한 번도 루프를 막은 적이 없다** — 핸들러가 `async def`가
   아니라 `def` 라서 FastAPI가 이미 오프로드하고 있었습니다. 같은
   `detect_trade`가 `/api/assistant`를 통해서는 **막았습니다**(2.3~3.4초)

**얻은 것은 루프 응답성뿐이고, 처음부터 그것만 예측했습니다.** 티커 p99가
29.33 → 10.65ms, 20ms 초과가 49 → 0~1건. **처리량은 안 움직였습니다**
(436.56 → 436.93 req/s). *일을 스레드로 옮긴다고 그 일이 빨라지지는 않습니다.*

### 6-4. 그리고 ARM에서 다시 쟀더니 메커니즘이 안 옮겨갔다

대상 박스(4 OCPU ARM)에서 재측정하니 `encode_one`이 **4워커에서 오히려
빨라졌습니다**(277 → 241 → 205ms). 12코어 박스에서 4워커가 +85%였던 것과
**정반대**입니다. 오버서브스크립션 논리는 코어 수에 비례하니 안 옮겨간 거죠.

**그래도 워커는 2로 뒀습니다.** 이유가 달라졌을 뿐입니다 — 이득이 검색당
약 12ms 인데 실 LLM p95가 4.45초라 **0.3%** 고, 4워커는 **다른 라이브
프로젝트와 공유하는 박스의 코어 넷을 다 채웁니다.** 유휴 박스 벤치마크가 볼 수
없는 비용입니다.

부수적으로 **유휴 티커 바닥이 Linux 0.11ms vs Windows 5.54ms** 였습니다 —
아래 6-5의 실패한 판정선은 **Windows 타이머 아티팩트**였고 대상 환경에는 아예
존재하지 않는 문제였습니다.

### 6-5. 사전 등록한 판정선이 틀렸고, 고쳐서 통과시키지 않았다

ADR-0028에서 측정 **전에** 판정선을 걸었습니다: `이벤트 루프 지연 max < 20ms`.

**같은 코드가 32.75ms(실패)와 17.89ms(통과)를 냈습니다.**

원인: 부하를 전혀 안 건 **유휴 서버가 이미 max 16.34ms** 였습니다(OS 타이머
분해능). 판정선은 잡음 바닥 위에 **3.66ms**만 남겨두고 있었고, 하필 3,600표본 중
**하나**로 결정되는 `max`에 걸려 있었습니다.

**판정선을 고쳐서 통과시키지 않았습니다.** 결과를 보고 기준을 바꾸면 그건
사전 등록이 아니라 사후 합리화입니다. **실패로 기록**하고, 두 실행이 일치한
`p99`(29.33 → 10.65ms)와 초과 건수(49 → 0~1)로 채택을 판단했습니다.

> 일반 규칙 둘:
> - **유도 과정에 잡음 바닥이 안 나오는 판정선은 유도가 없는 것이다.**
> - **`max`에 판정선을 걸지 말 것.** 한 표본이 결정합니다.
> - 그리고 이 규칙엔 **이산(discrete) 판본**이 있습니다 — `2/16 → ≤1/16` 같은
>   사전 등록은 **동전 한 번 던지기와 구별되지 않습니다**(정확 95% 구간이
>   [1.6%, 38.3%] vs [0.2%, 30.2%]). *사전에 걸었다고 측정 가능해지는 건
>   아닙니다.* 작은 표본의 비율 옆에는 구간을 같이 찍어야 합니다.

## 7. 보안

### 7-1. JWT — 신원은 헤더가 아니라 서명된 클레임에서 온다 (ADR-0023)

| 클레임 | 값 | 쓰임 |
|---|---|---|
| `sub` | userId | 행위자 |
| `tenant_id` | `1` (Long) | 백엔드 조회 격리 |
| `tenant_code` | `"nexon"` (str) | AI 서버의 ES 인덱스 선택 |
| `role` | `USER` / `ADMIN` | GM 검토 큐 접근 |

**`tenant_id`와 `tenant_code`를 둘 다 싣습니다.** 두 서버가 표기를 다르게 쓰는
건 그대로 두되 **출처를 하나(토큰)로** 만들었습니다. 예전에는 프론트의
`demo.ts`가 그 차이를 흡수했는데, 이제 그 값들은 서버로 나가지 않습니다.

**AI 요청 본문에서 `tenant_code`를 뺀 게 실제 구멍을 하나 닫았습니다** — 시맨틱
캐시 키가 테넌트별로 갈리므로, 본문으로 받던 동안에는 **남의 테넌트 캐시를
조회하도록 요청할 수 있었습니다.**

**측정한 비용: 요청당 0.7ms** — 312ms 요청의 **0.22%** 입니다
(`spring_security_filterchains_seconds` 실측). 처리량이 떨어져 보였을 때 가설
둘(인증 오버헤드, 테이블 누적)을 세워 **둘 다 측정으로 기각**했고, 귀속시킬
근거가 없어 **귀속시키지 않았습니다.**

### 7-2. 로그인이 테넌시 모델과 어긋나 있었다 (ADR-0034)

**자격증명이 두 부분이 아니라 세 부분입니다**: `{tenantCode, username, password}`.

`users`가 `(tenant_id, username)` 유니크라 **아이디 하나로는 행이 특정되지
않습니다.** 그런데 조회는 username만으로 하고 있었고, 리포지토리 주석에는
*"데모 테넌트가 하나뿐이라 아이디는 전역 유일하다"* 고 적혀 있었습니다 —
**스키마가 한 적 없는 주장**입니다.

같은 아이디로 두 번째 테넌트를 만드니 `NonUniqueResultException`이 났고, 그게
**401로 표면화**됐습니다. 즉 **그 계정은 영구히 로그인 불가가 됐는데 증상은
"비밀번호가 틀렸다"** 였습니다.

**그리고 그 401 위장에는 공범이 있었습니다.** `/error`가 `PUBLIC_PATHS`에
없었습니다. Spring Security 6+ 는 ERROR 디스패치도 필터링하므로, Boot의 에러
포워드가 `anyRequest().authenticated()`에 다시 걸려 **인증 없는 경로의 모든
400·500이 401로 나왔습니다.** 그 한 줄이 실제 결함 **둘**을 "비밀번호가
틀렸다"로 위장했습니다(위 중복 아이디 건과, 256비트 미만 `JWT_SECRET` 건).

응답 코드 설계:

| 상황 | 응답 | 왜 |
|---|---|---|
| 비밀번호 불일치 | **401** | |
| 없는 사용자 | **401** | 404로 갈리면 **사용자 열거**가 된다. 메시지도 같다 |
| 없는 테넌트 | **401** | 갈리면 **테넌트 목록**이 샌다 |
| `tenantCode` 누락 | **400** | 자격증명이 틀린 게 아니라 요청이 불완전하다 |

**비밀번호는 저장소에 없습니다.** `seed-demo.sql`의 해시는 29자 자리표시자라 어떤
비밀번호와도 매칭되지 않고, 실제 값은 기동 시 환경변수에서 주입됩니다. 안 넣으면
**아무도 로그인 못 하는 쪽**으로 실패합니다. **GM 비밀번호는 별도**입니다 —
하나면 데모 비밀번호를 아는 사람이 곧 GM이 되어 역할 인가가 무의미해집니다.

### 7-3. 요청 한도 — 세 계층, 그리고 "무엇을 세는가"

| 경로 | 한도 | 키 |
|---|---|---|
| `POST /api/assistant`(+`/stream`) | 20회 / 분 | tenant + user |
| 구매 / 입찰 | 10회 / 초 | user |
| `POST /api/auth/login` | 30회 / 분 | **IP** |
| `POST /api/assistant`(+`/stream`) | **50회 / 일** | tenant + user |

**새 의존성을 안 넣었습니다** — 백엔드는 이미 쓰던 Redisson의 `RRateLimiter`를,
AI 서버는 시맨틱 캐시가 이미 여는 `redis.asyncio` 를 재사용합니다.

**두 한도가 다른 것을 세고, 캐시 적중 취급이 다릅니다** (ADR-0044).

| | 목적 | 캐시 적중 | 세는 시점 |
|---|---|---|---|
| **20회/분** | 부하·남용 차단 | **센다** | 요청 **앞** |
| **50회/일** | **LLM 비용** | **안 센다** | 응답 **뒤** |

분당까지 적중을 빼면 **캐시되는 질의 하나로 서버를 무한정 두드릴 수** 있습니다.
반대로 일일 한도가 적중을 세면 **비용 0인 요청이 비용 예산을 깎습니다** — 그리고
이건 이론이 아니라 실제로 닿던 경로였습니다. 프론트가 배지를 정직하게 유지하려고
`staleTime`을 안 걸어서, **아이템 상세에 들어갔다 돌아올 때마다 하루치가 하나씩
깎이고 있었습니다.**

**일일 키의 TTL이 86,400이 아니라 "자정까지 남은 초"입니다.** 그 TTL을
`Retry-After`로 내보내는데, 24시간으로 두면 01시에 처음 물어보고 23시에 한도에
닿은 사용자에게 **"22시간 뒤에 오세요"** 라고 말합니다. 정답은 1시간이죠.
*내부 값이라고 치부한 값이 관측 가능한 출력으로 새는지 확인해야 합니다.*

### 7-4. 요청 *크기* 는 따로 막아야 한다 (ADR-0035)

**세 계층이 전부 요청 *수* 를 셉니다.** 그런데 `query`에 `max_length`가 없고
자르는 코드도 없었습니다. **19,800자 질의가 200으로 통과하고 16.4초** 걸렸습니다
(정상은 ~50자 / 4.5초). 한도를 다 지키면서 하루 예산을 **배수로** 늘릴 수 있는
셈입니다.

500자 상한의 근거는 추측이 아닙니다 — 임베딩은 **128토큰**, 리랭커는 **256토큰**
에서 자르므로 그 너머는 LLM 요금만 늘리고, 데이터셋 질의 547건의 **최댓값이
33자**입니다.

> 발견 단서가 좋았습니다: **같은 DTO 안에서 `size`는 `ge=1, le=50`으로 묶여
> 있는데 `query`는 안 묶여 있었습니다.** *한 필드가 묶여 있고 이웃이 안 묶여
> 있으면, 안 묶인 쪽은 결정이 아니라 누락입니다.*

### 7-5. 헤더를 신뢰하는 것과 쓰는 것은 별개다 (ADR-0033)

로그인 IP 한도가 프록시 뒤에서는 **키 하나로 붕괴**하는 문제를 `X-Forwarded-For`
신뢰로 풀었습니다. 신뢰 목록(`rate-limit.trusted-proxies`)의 **기본값은 비어**
있어서, 설정 안 한 배포는 예전처럼 헤더를 무시합니다 — **잊은 배포가 더 안전한
쪽으로 실패**합니다.

**그런데 이 저장소는 그 두 일 중 첫째만 하고 있었습니다.** `nginx.conf`에
`X-Forwarded-For` 를 쓰는 줄이 아예 없었고, **nginx는 자기가 안 만드는 헤더를
지우지도 않습니다.** 그래서 런북의 *"nginx IP를 `TRUSTED_PROXIES`에 넣어라"* 를
따르면 **로그인 한도가 통째로 사라졌습니다** — 실측으로 위조 XFF 40개가 전부
통과했고, 헤더 없는 대조군은 31번째에 429였습니다.

> 부수 교훈: 그때 `verify-auth.sh`의 XFF 검사는 **백엔드 포트를 직접** 때리면서
> *"어차피 nginx가 헤더를 덮어쓴다"* 는 주석을 달고 있었습니다. **바로 그 틀린
> config에 대한 검증 안 된 주장**이었죠. **배포하지 않는 경로를 겨눈 검사는
> 배포하는 경로에 대해 아무것도 말해주지 않습니다.**

## 8. 장애 대응 — 두 겹이 순서대로 선다

```
OpenAI 실패 → Claude 폴백 → (둘 다 실패) → 결정적 문장 → (그것도 아니면) 500
```

### 8-1. 폴백 (ADR-0042)

**서킷 브레이커를 둔 이유가 정합성이 아니라 지연입니다.** 예외만 잡아 넘기면
장애 동안 **모든 요청이 1차 타임아웃을 먼저 뭅니다** — RabbitMQ에서 "구매는
성공하는데 1분"을 겪은 그 축입니다. 연속 3회 실패면 60초 동안 1차를 건너뜁니다.
**새 의존성 없이** 카운터와 타임스탬프로 만들었습니다.

**구현의 대부분이 형식 번역이고, 거기가 위험합니다.** `LLMClient`는 중립인데
에이전트 루프가 OpenAI 메시지 형식을 그대로 씁니다(`{"role": "tool",
"tool_call_id"}`). 인터페이스만 맞추고 형식을 안 맞추면 `complete()`는 되고
**에이전트만 조용히 깨집니다 — 폴백이 가장 필요한 순간에.** 특히 **연속된 도구
결과를 한 메시지로 합쳐야** 하고, 안 합치면 **도구 하나일 땐 되고 둘일 때
400**입니다.

**둘 다 죽으면 1차 예외를 올립니다.** 2차 예외로 바꿔치면 진단이 엉뚱한
프로바이더를 가리킵니다.

### 8-2. 내려앉기 (ADR-0041)

설명 LLM이 죽으면 500이었습니다. 그런데 **그 시점에는 예측·판정이 이미 계산돼
있습니다.** 없는 것은 **산문뿐**입니다.

지금은 `_search_answer()`와 같은 방식으로 결정적 문장을 만들고
`outcome="degraded"`를 답니다. `llm_calls`도 줄어드는데, **그 호출이 성사되지
않았기 때문**입니다 — 안 줄이면 **안 나간 돈을 세게** 됩니다.

두 가지 디테일:

- 폴백 문장을 **콜러블로** 넘겨서 성공 경로에서는 만들지 않습니다.
- 그 문장이 **프롬프트가 조건부로 붙이던 고지를 그대로** 붙입니다(콜드스타트
  추정이라는 것, 합성 코퍼스라는 것). 빠뜨리면 **모델이 살아 있을 때만 정직한**
  응답이 됩니다.

**에이전트 분기는 손대지 않았습니다** — 거기서는 **LLM이 곧 분기**라 내려앉을
자리가 없고 정직한 500이 맞습니다.

`degraded`가 별도 outcome인 이유는 **500이 안 나므로 다른 데서는 안 보이기**
때문입니다. 사용자는 답을 받았으니 실패가 아니지만 `ok`도 아닙니다.

### 8-3. 500 본문에서 예외 문자열을 뺐다

업스트림 메시지에는 **ES 인덱스명·쿼리 DSL·내부 호스트**가 섞여 나옵니다.
백엔드는 `server.error.include-stacktrace: never`로 처음부터 같은 자세였고
**AI 서버 다섯 라우터만 안 맞춰져 있었습니다.**

> **한쪽이 선언한 설정을 이웃이 안 했다면 그건 결정이 아니라 누락입니다.**
> 그래서 하나만 고치고 멈추지 않고 다섯을 한 번에 바꿨습니다. 각각
> `logger.exception`을 남깁니다 — **누출을 막으면서 진단 수단까지 없애면 안
> 됩니다.**

## 9. 배포

### 9-1. 컨테이너화 — 단일 오리진을 재현한다 (ADR-0029)

`--profile app`을 붙이면 nginx가 SPA와 두 API를 `http://localhost` 하나로
서빙합니다. **개발의 Vite dev proxy와 같은 경로 규칙**이라, 이게 **양쪽 서버에
CORS가 계속 없는 이유**입니다. `load/verify-container.sh`가 그걸 **행동으로**
단언합니다 — `Origin` 헤더를 붙여 보내고 `access-control-*`가 안 나오는지 봅니다.

> 그 검사의 **첫 판본이 틀렸습니다.** 일부러 CORS를 켜고 돌렸더니 **통과**했는데,
> 겨눈 경로가 404였기 때문입니다(AI 헬스는 `/api/health`가 아니라 `/health`).
> **404에는 미들웨어가 안 붙습니다.** *검사가 대상에 닿았는지를 확인하지 않으면
> 아무것도 확인하지 않는 겁니다.*

**모델 650MB는 이미지가 아니라 명명된 볼륨에 삽니다.** 그중 466MB가 XLM-R 임베딩
행렬(25만 vocab × 384차원)인데 이건 낭비가 아닙니다.

### 9-2. ARM 대응 — 아키텍처로 분기하는 코드가 없다 (ADR-0032)

네 이미지 전부 `linux/arm64`로 크로스빌드되고 모든 의존성이 aarch64 휠로
풀립니다(`torch-2.13.0+cpu`, `onnxruntime-1.28.0` 등).

**리랭커의 int8 설정은 ARM에서도 `avx2`로 둡니다.** 이름은 x86인데 산출물은
이식 가능한 ONNX이고 에뮬레이트된 aarch64에서 로딩·추론이 확인됐습니다.
`AutoQuantizationConfig.arm64`로 바꾸는 것은 **측정하고 기각**했습니다 —
top-1은 5/5 일치인데 **top-5 순서가 0/5 일치**였습니다. 이 저장소의 품질 수치가
전부 avx2 기반이라, **측정된 품질을 측정 안 된 속도 추측과 바꾸는** 거래입니다.

**크로스빌드는 확신용이지 산출물용이 아닙니다** — 빌드는 네이티브인 대상에서
합니다. `--output type=cacheonly`를 씁니다. 3GB짜리 에뮬레이트 이미지를 개발
박스에 남기는 건 순수 비용이고, **그 빌드 캐시가 디스크를 채워 데몬을
죽였습니다.**

### 9-3. 공개 배포 (ADR-0031)

`docker-compose.deploy.yml`을 얹으면 **nginx의 80만 공개**되고
`SPRING_PROFILES_ACTIVE=prod`가 `SecretGuard`를 무장시킵니다 — **저장소 기본
비밀값으로는 기동을 거부**합니다.

여기 함정 셋이 있는데, **전부 실제로 돌려보기 전엔 안 보입니다.**

- **`ports: []`는 포트를 없애지 않습니다** — Compose는 시퀀스를 *덧붙입니다*.
  `!override []`가 필요합니다.
- **`environment:`는 셸을 상속하지 않습니다** — 세 변수를 차례로 잊었고, 증상은
  전부 **애플리케이션**을 가리켰습니다("password authentication failed"), compose가
  아니라.
- **닫힌 포트와 죽은 컨테이너는 밖에서 똑같아 보입니다.** `verify-deploy.sh`의 첫
  실행이 *"8080 닫힘"* 으로 통과했는데 백엔드는 실제로 **기동을 거부**한
  상태였습니다. 지금은 스택이 돌고 있는지를 **먼저** 단언하고, **프록시 경로로
  실제 로그인**까지 합니다.

### 9-4. SSE가 배포에서만 안 흐른 이유 (ADR-0044)

`X-Accel-Buffering: no` 를 넣었는데 배포에서 **8개 이벤트가 13.98초 중 마지막
0.27초에 몰려서** 왔습니다.

원인이 둘 겹쳐 있었습니다. **nginx는 그 헤더를 존중하면서 동시에 숨깁니다** —
`Date`, `Server`, `X-Pad`, `X-Accel-*` 이 기본 hidden 목록입니다. 그리고 공개
URL이 `https`인데 우리 nginx는 평문 80을 서빙하므로, **앞에 TLS를 끊는 호스트
nginx가 하나 더** 있었습니다. 우리 nginx가 헤더를 먹고, 앞의 프록시는 그걸 보지
못해 버퍼링한 겁니다.

`proxy_pass_header X-Accel-Buffering;` 로 고쳤습니다 — **존중하는 것과 전달하는
것은 별개**입니다.

> 그리고 이 진단에서 **검사 하나가 원리적으로 불가능**하다는 걸 알았습니다.
> 헤더의 *존재*를 단언하는 검사는 **프록시 뒤에서 만족 불가능**합니다. 체인의 두
> 지점에서 재보니 우리 nginx 직결은 헤더가 **있고**(비율 0.01), 공개 URL은
> **없습니다**(비율 0.02) — 그리고 **그 부재가 앞 프록시가 먹었다는 증거**입니다.
> *프록시가 먹는 헤더는 응답에서 확인할 수 없고, 사라지는 위치로 추적해야
> 합니다.* 그 검사는 정보용으로 내리고 **판정은 비율이** 집니다.

## 10. CI/CD와 품질 게이트

워크플로 넷을 **일부러 파일로 쪼갰습니다**(`ai`/`backend`/`frontend`/`ai-quality`).
각자 `paths` 필터를 들 수 있어서 **문서만 고친 커밋은 아무것도 돌리지 않습니다.**

### 10-1. 기획서엔 "RAGAS 품질 게이트"였는데, 이름 그대로 만들지 않았다 (ADR-0043)

**pass/fail은 결정론적 IR 지표(Recall@k · MRR)가 집니다.** RAGAS는
`workflow_dispatch` **리포트**로 내렸습니다.

이유가 둘입니다.

1. **심판 변동폭을 특성화한 적이 없습니다.** 안 잰 잡음 위에 문턱을 거는 건 이
   저장소가 이미 두 번 한 실수입니다(6-5의 티커 판정선, 무속성 사전 등록 기준).
2. **실측으로 매 실행 약 648회 호출 / 119분**이 듭니다. 커밋마다 과금할 수 없습니다.

> ADR-0021이 이 작업의 착수 조건으로 적어둔 *"모델 아티팩트 배포 전략이
> 먼저"* 는 **독립인 문제 둘을 한 줄로 묶은 것**이었습니다 — 재학습은 20스텝이라
> **배포할 게 없고**, 과금 문제는 RAGAS를 내리니 **사라졌습니다.**
> *한 줄로 묶인 보류 사유는 실제보다 커 보입니다. 항목별로 쪼개세요.*

### 10-2. 문턱은 재학습 변동을 먼저 재서 잡았다

그리고 그 측정에 **세 갈래**가 필요했습니다. 시드가 42로 고정돼 있어서 그냥 두
번 돌리면 **비트 단위로 동일한 가중치**가 나옵니다 — 변동 0인데 그건 **측정이
아니라 구조**고, 안정적인 프로세스와 구별되지 않습니다.

| 갈래 | 결과 |
|---|---|
| 같은 시드 ×2 (대조군) | **비트 단위 동일** |
| 시드 ×3 | recall@1 0.0185 · recall@5 0.0370 · MRR 0.0127 ← **유일한 실제 변동원** |
| 스레드 1 vs 2 | **가중치는 다른데 지표는 넷째 자리까지 동일** |

하한 = 관측 최솟값 − 2×변동폭 → **0.35 / 0.48 / 0.47**.

> **반복 실행 옆에는 아티팩트 해시를 같이 찍어야 합니다.** 없으면 *"수치가
> 같았다"* 와 *"같은 파일이었다"* 를 구별할 수 없습니다.

**잡는 회귀의 크기를 과장하지 않습니다** — 코퍼스 훼손·베이스 모델 오지정·트리플
깨짐 같은 **큰** 회귀는 잡고, 미세한 품질 저하는 못 잡습니다.

**수집과 채점은 분리했습니다**: `evaluate_training_variance`가 문턱을 유도하고
(학습 7회, LLM 0회), `check_ir_gate`가 그걸 적용합니다. 그래서 **문턱을 바꾸는 데
재학습 비용이 0**입니다.

### 10-3. 부하테스트는 일부러 CI에 안 넣었다

무거워서가 아닙니다. **GH 러너는 세 번째 환경**이라 그 수치가 ADR-0020과도, 배포
대상과도 비교되지 않고, 아직 **단언할 SLO가 없으며**(ADR-0020이 일부러 안 걸었죠),
`live-llm`은 커밋마다 OpenAI에 과금합니다. 4 OCPU 걱정은 **러너를 self-host 하지
않는 것**으로 답합니다.

### 10-4. 초록 배지가 말해주지 않는 것

**백엔드 잡은 GHA 서비스 컨테이너 대신 `docker-compose.yml`을 올립니다.** 서비스
컨테이너는 `command`를 못 정해서 Redis를 `--requirepass`로 못 띄우는데,
`RedissonConfig`는 무조건 AUTH를 보냅니다. compose를 쓰면 CI가 로컬과 동일해지는
이점도 있습니다.

**RabbitMQ는 안 올립니다.** 백엔드가 AMQP 의존성을 갖게 됐지만
`NotificationFlowTest`는 **브로커 없이** 발행 *단계*와 컨슈머 멱등성을 검증하도록
쓰였습니다(스파이가 호출을 기록하고, 실제 전송은 실패해 fail-open이 삼킵니다).
**그래서 초록 CI는 브로커 경로에 대해 아무 말도 하지 않습니다** — 큐 배수·DLQ·
브로커 다운 지연은 `load/verify-mq.sh`가 덮습니다.

## 12. 기각한 것들 — 이 발표의 전환점

**여기가 이 프로젝트에서 제일 오래 붙잡은 부분입니다.**

| 항목 | 결론 |
|---|---|
| **리랭커 점수 하한** | **2회 측정, 2회 기각. 사유가 달랐다.** 처음엔 노이즈가 마진보다 커서, 두 번째는 **질의 간 점수 눈금이 비교 불가**라서 |
| **시맨틱 캐시 유사도 매칭** | 함정 쌍 0.9787 vs 동의 쌍 0.845. **함정이 더 유사하다.** FAQ에만 허용 |
| **프롬프트로 혼동 방지** | 한 줄 추가가 정답률을 **97.5% → 22%** 로 떨어뜨렸다. 되돌림 |
| **캐시 임베딩 지연화** | **기각했다가 당일 뒤집혔다.** "27%뿐"이라 접었는데 **그 27%가 나머지 73%를 만들고 있었다** |

| **`asyncio.to_thread`** | 로드맵에 그 이름으로 등록했는데 **측정이 기각**했다. 기본 실행기에서 torch가 **+85%** 느려진다 |
| **arm64 재양자화** | top-1은 5/5 일치인데 **top-5 순서가 0/5**. 측정된 품질을 측정 안 된 속도와 바꾸는 거래 |
| **판정선 `티커 max < 20ms`** | **같은 코드가 32.75ms와 17.89ms.** 고쳐서 통과시키지 않고 **실패로 남겼다** |

| **RAGAS를 CI 게이트로** | 심판 변동폭 미측정 + **커밋마다 648회 / 119분** |

### 12-1. 특히 깊게 파고 싶은 하나 — 리랭커 하한 (ADR-0018)

처음 기각 사유는 *"질의 재작성 노이즈(최대 1.31점)가 적합/부적합 마진
(0.3~0.6점)을 삼킨다"* 였습니다. 그런데 ADR-0017이 `temperature`를 고쳐서
**노이즈를 실제로 없앴습니다** — 편차가 0.319로 떨어지고 마진은 0.60,
10개 컬렉션이 일치하고 순위 역전이 사라졌습니다. **절대 하한 `T = −4.34`가
채택 가능해 보였습니다.**

**그다음이 이 프로젝트에서 제일 마음에 드는 측정입니다.** 같은 데이터의
tune/holdout 분할 **126가지를 전수 열거**했더니:

- 문턱을 안전하게 만드는 **부등식이 44%의 분할에서만 성립**
- 실제로 쓰던 분할은 하필 **83퍼센타일**
- **안전하면서 동시에 쓸모 있는 마진이 없다** — 마진 ≥ 4.0이면 모든 분할이
  안전한데 **아무것도 안 잘립니다**

근본 원인은 구조적입니다. **질의별 적합 최솟값이 −3.84 ~ +2.90(폭 6.74점)**
으로 움직이는데 **전역 부적합 최댓값은 −2.54**입니다. 전역 안전 컷은 **자를
가치가 있는 모든 것 아래**에 놓입니다. 크로스인코더 로짓은 **한 질의의 후보
집합 안에서만** 의미가 있습니다.

> **핵심 문장:** *같은 분할을 반복 실행하면 노이즈를 재는 것이지 일반화를 재는
> 게 아닙니다.* 그리고 이미 수집한 데이터로 분할을 전수 열거하는 건 **추가 API
> 호출이 0**입니다. 분할 위에서 보정한 문턱을 채택하기 전에 반드시 하세요.
>
> **노이즈가 나아졌다고 다시 시도하지 말 것** — 노이즈는 더 이상 막는 게
> 아닙니다. 질의를 가로질러 비교 가능한 **질의별 점수 정규화**가 필요합니다.

### 12-2. 검사 자체가 틀린 27건

측정 하네스를 만들다 보면 **시스템이 아니라 검사가 틀립니다.**
`docs/05-Troubleshooting/검사-자체가-틀린-사례들.md`에 **27건**이 있고, 방향이
넷입니다.

| 방향 | 증상 | 발견 난이도 |
|---|---|---|
| **오보** | 정상 시스템에 실패 보고 | 쉽다 — 확인하다 드러난다 |
| **침묵** | 90% 거절된 실행을 **조용히 통과**시켰다 | **어렵다 — 아무 일도 안 일어난다** |
| **동전 던지기** | 같은 코드에서 통과와 실패가 갈린다 | **어렵다 — 한 번만 돌리면 안 보인다** |
| **구분 실패** | 실패 *원인*을 못 갈라 엉뚱한 데를 지목했다 | **어렵다 — 보고서가 그럴듯하다** |

**마지막 것이 최근에 제일 많습니다.** 예를 들어 `/api/assistant`에 429가
떴을 때 응답에 `out_of_domain`도 `results`도 없는데, **그게 정확히 "게이트가
거절했다"의 서명과 같습니다.** 그래서 검사가 *"게이트가 정상 검색을 막고
있다"* 고 보고했는데 진실은 **일일 한도 소진**이었습니다. *본문을 파싱하기 전에
상태 코드를 읽어야 합니다.*

여기서 나온 체크리스트:

- **판정에 쓴 모든 값을 실패 메시지에 넣어라.** 그게 위 캐시 검사를 반쯤
  공허하다고 드러냈습니다 — `hit=False, llm_calls=0` 을 찍었는데 **둘 다 참일
  수 없었습니다.** 통과/실패 한 줄만 찍었으면 그대로 나갔을 겁니다.
- **일부러 실패하는 케이스로도 돌려봐라.** 통과만 본 검사는 **항상 통과하는
  검사와 구별되지 않습니다.**
- **판정을 지는 명령에 표시용 필터를 걸지 마라.** `cmd | tail` 뒤의 `$?`는
  **`tail`의 종료 코드**(항상 0)라, 올바르게 실패하던 가드 둘이 성공을
  보고했습니다. cp949로 깨진 한글을 정리하려고 붙인 파이프였습니다.

| 등급(`전설`) 축 | 필드가 없어 텍스트 신호로만 동작. **코퍼스에 등급 taxonomy를 만들어야** 열린다 |
| 리랭커 하한 | **도입 안 함** — 질의 간 점수 정규화가 선행 조건 |
| 도메인 게이트 오거부 | 현재 모델에서 **2.55%**. 프롬프트가 이전 모델에 맞춰져 있고 **재조정은 홀드아웃 셋을 다시 쓴다** |
| 게임 메커니즘 질문 | `강화 확률 올리는 방법` 처럼 **아이템 어휘를 단 규칙 질문**은 게이트를 통과한다. 다만 방어층 덕에 결과는 **틀린 답이 아니라 무관한 답**이다 |
| 요청 한도 정밀도 | 고정 윈도우라 경계에서 **최대 2배 통과.** 비용 폭주 차단이 목적이지 정확한 분당 N이 아니다 |
| 회원가입 | **없다 — 결정이다.** 열면 이메일 인증·비밀번호 재설정·스팸 계정 방어가 딸려온다 |
| 4 OCPU 실서비스 | **안 된다.** 그래서 상시 기동을 피하고 지연 로딩·프로파일 opt-in을 넣었다. 부하 수치도 **생성기가 같은 박스에 있어 보수적**이다 |

---

## 14. 이 프로젝트가 남긴 습관 세 가지

**1. 주장 옆에 측정을 붙인다 — 그리고 지면 진 대로 적는다.**
모든 모델을 단순 기준선과 비교했고, **넷 중 둘은 졌습니다**(신규 계정 탐지는
규칙이, 시세 예측은 근소하게 이겼을 뿐). 그걸 지우지 않는 게 나머지 수치의
신뢰를 만듭니다.

**2. 판정 기준을 결과보다 먼저 정하고, 틀렸으면 틀린 대로 남긴다.**
사전 등록한 판정선이 두 번 실패했고 두 번 다 **고쳐서 통과시키지 않았습니다.**
결과를 보고 기준을 바꾸면 그건 사전 등록이 아니라 사후 합리화입니다.

**3. 검사도 틀린다고 가정한다.**
27건이 그 목록입니다. 새 검사를 만들면 **일부러 실패하는 케이스로도** 돌려보고,
**판정에 쓴 값을 전부 출력**합니다. 통과만 본 검사는 항상 통과하는 검사와
구별되지 않습니다.

## 15. 면접 예상 질문과 답

**Q. LLM을 쓰는 서비스가 많은데, 이 프로젝트의 차별점은?**

파이프라인을 유형별로 가른 것이 첫째고, 그 결과가 `llm_calls` 라는 한 숫자로
관측 가능하다는 게 둘째입니다. FAQ는 0회, 검색은 2회, 캐시 적중은 0회입니다.
그리고 **환각을 프롬프트가 아니라 구조로** 막았습니다 — 검색 설명 LLM은 아예
없앴고(결과 카드가 스스로 말하니까), 거절 함수는 **질의를 인자로 받지 않아서**
주어를 되풀이하는 게 시그니처상 불가능합니다.

**Q. 왜 Isolation Forest가 아니라 오토인코더인가?**

정확도 때문이 아니라 **설명 가능성** 때문입니다. 재구성 오차를 피처별로 쪼개면
GM에게 "왜 이상인가"를 축 단위로 보여줄 수 있고, 그게 화면의 기여도 막대입니다.
대신 **신규 계정(뮬) 거래는 `max|z|` 규칙이 100%, 오토인코더는 놓칩니다.**
상호 보완이지 대체가 아니라고 적어뒀습니다.

**Q. 합성 데이터인데 수치에 의미가 있나?**

**단독으로는 없다고 봅니다.** 그래서 `train_forecast`가 항상 naive 기준선을 같이
출력하고, 판단 기준을 MAPE가 아니라 **"기준선을 이겼는가"** 로 뒀습니다. 4.70%
vs 4.87%면 **이겼지만 근소하고**, 그 근소함 자체가 데이터 생성 과정의 성질이라고
같이 적었습니다.

**Q. 테스트가 적지 않나?**

AI 301건 + 백엔드 57건인데 **범위가 좁습니다.** AI는 **네트워크 없이 도는
결정론적 단위**에만 한정했습니다 — 모델 품질은 홀드아웃 리포트가, 검색 품질은
CI의 IR 게이트가 판단합니다. 백엔드는 도메인 규칙·인증·격리·알림 흐름까지
있지만 **Redis 락과 거래 흐름은 여전히 수동 검증**이고, 동시성은 단위 테스트가
아니라 **부하테스트가 오버셀 0건으로** 단언합니다. 로드맵에 남겨뒀습니다.

**Q. 4 OCPU에서 실서비스가 되나?**

**안 됩니다.** 그래서 상시 기동을 피하고 모델은 지연 로딩, Prometheus/Grafana는
프로파일 opt-in입니다. 부하 수치도 **생성기가 측정 대상과 같은 박스에 있어
보수적**이라고 적었습니다.

**Q. AI 코딩 도구를 썼나?**

썼습니다. 다만 진행 방식이 **판정 기준을 먼저 정하고 측정으로 검증**하는
쪽이었습니다. 이 저장소에 프롬프트 한 줄이 정답률을 97.5%에서 22%로 떨어뜨린
기록이 남아 있는데, **그 줄은 명백히 옳아 보였고 리뷰를 통과했을 겁니다.**
그래서 프롬프트를 건드리는 하네스를 셋 만들었고, 그게 이 프로젝트의 작업
방식입니다.

**Q. 다시 만든다면 뭘 다르게 하겠나?**

두 가지입니다. 첫째, **평가셋을 더 일찍 만들었을 겁니다.** 무속성 추출 문제는
라벨 붙은 평가셋이 생기고 나서야 진단됐고, 그 전엔 "가끔 이상하다"였습니다.
둘째, **`temperature`를 처음부터 확인했을 겁니다.** 6개 Phase 동안 OpenAI 기본값
1.0으로 돌면서 그 변동을 "LLM의 근본 특성"으로 오진했습니다. *LLM이
비결정적으로 굴면 모델을 논하기 전에 요청 파라미터를 먼저 보세요.*
