"LLM API를 감싸기만 한 서비스"가 되지 않는 것

모든 요청을 하나의 LLM 호출로 흘려보내면 구현은 간단하다. 대신 FAQ 한 줄에도 검색 한 번과 똑같은 비용과 지연이 붙는다.

사례 1 — 임계값

같은 데이터를 두 번 재고, 두 번 기각했다

  1. 1차 — 보류. 적합/부적합 마진이 0.3~0.6인데 LLM 질의 재작성의 흔들림이 1.31점이었다. 재려는 신호보다 노이즈가 크다
  2. 노이즈를 없앴다. 원인은 temperature가 API에 아예 안 넘어가고 있던 것(기본 1.0). 0으로 두니 산포 0.319, 10회 실행이 전부 같은 판정. 임계값이 채택 가능해 보였다
  3. 2차 — 기각. 같은 데이터를 질의 단위로 재분할해 126가지 전수 열거했더니 임계값을 안전하게 만드는 부등호가 44%의 분할에서만 성립했다. 쓰고 있던 분할은 83백분위였다 — 운이 좋았던 것
뿌리는 구조적이다. 질의별 적합 최솟값이 −3.84~+2.90(폭 6.74)로 움직이는데 전역 부적합 최댓값은 −2.54다. 크로스인코더 로짓은 질의를 가로질러 비교 가능한 눈금이 아니다. temperature를 더 만져도 이 결론은 안 바뀐다.

교훈 — 같은 분할을 반복 실행하면 노이즈를 재는 것이지 일반화를 재는 게 아니다. 전수 열거는 추가 API 호출 없이 공짜였고, 채택 직전의 임계값을 뒤집었다.

사례 3 — 검사 자체가 틀린다

측정 하네스에서 틀린 건 시스템이 아니라 검사였다 — 4건

방향증상발견 난이도
오보 ×2정상 시스템에 실패 보고쉽다 — 확인하다 드러난다
침묵 ×190% 거절된 실행을 조용히 통과시켰다어렵다 — 아무 일도 안 일어난다
동전 던지기 ×1같은 코드에서 통과와 실패가 갈린다어렵다 — 한 번만 돌리면 안 보인다

가장 최근 건 — 동기 호출을 스레드로 빼면서 판정 기준을 측정 전에 걸었다: 이벤트 루프 지연 max < 20ms. 그런데 같은 코드가 32.75ms(실패)와 17.89ms(통과)를 냈다.

부하를 전혀 안 건 유휴 서버가 이미 max 16.34ms였다(OS 타이머 분해능). 판정선은 잡음 바닥 위에 3.66ms만 남겨두고 있었고, 하필 3,600표본 중 하나로 결정되는 max에 걸려 있었다.

판정선을 고쳐서 통과시키지 않았다. 결과를 보고 기준을 바꾸면 그건 사전 등록이 아니라 사후 합리화다. 실패로 기록하고, 두 실행이 일치한 p99(29.33 → 10.65ms)와 초과 건수(49 → 0~1)로 채택을 판단했다.

AI 검색 지연 중 LLM 몫
  • ADR-0001의 주장을 처음 검증했다. "Redis 분산 락 + 낙관적 락이 오버셀을 막는다"는 실동시성에서 확인된 적이 없었다. 이제 매 실행마다 재고 감소분 == 성공 응답 수를 단언한다
  • 병목은 하나가 아니라 부하 형태에 따라 옮겨간다. 단일 경합에서는 락 대기 0.178s vs 보유 0.007s(큐잉)인데, 분산하면 처리량이 4배가 되는 대신 보유 시간이 5배로 올라 DB가 제약이 된다. 대조군 없이 쟀으면 "락이 병목"에서 끝났을 것이다
  • 캐시 적중과 실 LLM을 반드시 분리한다. 안 나눴으면 "우리 검색이 p95 4.45초"라고 결론냈을 것이다 — 우리 코드(ES+리랭커+임베딩)는 합쳐서 82ms다

부하 생성기가 측정 대상과 같은 박스(4 OCPU 공유)에 있어 보수적인 수치다.

이 프로젝트가 남긴 습관 세 가지

  1. 기준선 없이 숫자를 말하지 않는다. 모든 모델을 단순 기준선(naive 예측, max|z| 규칙)과 비교했고 진 것은 진 대로 적었다. 오토인코더는 신규 계정 시나리오에서 규칙에 완패했고, 그 사실이 문서에 그대로 남아 있다
  2. 판정 기준을 측정 전에 박고, 틀리면 틀린 채로 남긴다. 마지막 라운드에서 내가 건 판정선이 계측기의 잡음 안에 있었다. 고쳐서 통과시키는 대신 실패로 기록하고, 왜 틀렸는지를 체크리스트로 만들었다
  3. 집계는 원인을 지목하지 않는다. "27%뿐"이라 접었던 항목이 알고 보니 나머지 73%의 원인이었다. 합계를 재고 그 안의 원인을 코드를 읽어 지목하는 건 측정이 아니다
문서는 결과가 아니라 과정이다. 마지막 Phase에서 가장 값어치 있었던 산출물은 기능이 아니라 세 번의 정정이었다. 매끈하게 다시 쓰는 대신 정정 블록으로 남겼다 — 그래야 그 문서만 읽는 사람이 틀린 결론을 진실로 받아들이지 않는다.
