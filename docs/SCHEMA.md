# SCHEMA — 이 저장소(vault)의 문서 운영 규칙

이 문서는 **LLM(과 사람)이 이 vault에 노트를 어떻게 쓰고 고칠지**를 정한다.
내용을 담지 않고 **규칙만** 담는다. 새 문서를 만들기 전에 여기를 먼저 읽는다.

> 이 문서가 LLM Wiki 3층 구조의 **Schema 층**이다. 나머지 둘은
> [INDEX](INDEX.md)가 안내한다.

---

## 1. 3층 구조 — 무엇이 어디에 속하나

| 층 | 이 저장소에서 | 다루는 법 |
|---|---|---|
| **Raw Sources**<br>(원천 자료) | **소스 코드 전체**(`ai/`, `backend/`, `frontend/`, `load/`), 그리고 [최종 기획서](00-Architecture/게임아이템_통합거래플랫폼_최종기획.md) | **읽기 전용으로 참조한다.** 기획서는 착수 시점의 스냅샷이라 이미 여러 항목이 뒤집혔고, **고치지 않는다** — 무엇이 왜 바뀌었는지 대조할 기준선이기 때문이다 |
| **Wiki**<br>(정리본) | `01-Decisions`(ADR) · `02-AI-Pipeline` · `03-API-Specs` · `04-DevLog` · `05-Troubleshooting` · `06-발표` · `07-배포` · `00-Architecture`의 로드맵·회고 | 아래 2~5절의 규칙으로 쓴다 |
| **Schema**<br>(운영 규칙) | **이 문서** | 규칙이 바뀌면 여기를 먼저 고치고, 그다음 문서를 고친다 |

**코드가 원천 자료라는 말의 실무적 의미**: 이 vault의 문서는 **코드에서 읽을 수
없는 것**만 담는다. *무엇을 했는가*는 코드와 git 히스토리가 말하고, 문서는
**왜 그렇게 했는가 · 무엇을 재봤는가 · 무엇을 기각했는가**를 담는다.

## 2. 문서 종류와 각각의 계약

| 폴더 | 종류 | 시점 | 고쳐 쓰나 |
|---|---|---|---|
| `01-Decisions` | **ADR** — 결정 하나 | **작성 시점에 고정** | ✗ 원문을 고치지 않는다. 뒤집히면 **정정 블록을 덧붙이고** 새 ADR을 판다 |
| `04-DevLog` | 작업 일지 | 그날 고정 | ✗ 추가만 |
| `05-Troubleshooting` | 재발 가능한 함정 | 누적 | △ 같은 계열 사례는 **기존 문서에 추가** |
| `02-AI-Pipeline`<br>`03-API-Specs` | **파생 문서** | **항상 현행** | ✓ **바뀌면 같은 커밋에서 고친다** |
| `06-발표` · `07-배포` | 파생 문서 | 항상 현행 | ✓ |
| `00-Architecture` | 로드맵·회고 | 로드맵은 현행, 회고는 고정 | △ |

### 2-1. 왜 ADR은 고쳐 쓰지 않는가

**틀렸던 판단이 이 저장소에서 가장 값어치 있는 기록**이기 때문이다. 예를 들어
[ADR-0025](01-Decisions/0025-관측성-2단계-착수-보류와-분해-측정.md)는 캐시
임베딩 지연화를 **기각**했다가 당일 뒤집혔는데, 원문을 지우지 않고 정정만
붙였다. 결과만 남기면 *"왜 그 오판이 그럴듯했는가"* 가 사라진다.

정정 블록의 형태:

```markdown
> **[정정] 2026-08-07** — 이 절의 X 는 틀렸다. 실측으로 Y 였다.
> 원인은 Z 다. 원문을 지우지 않는 이유는 그 오판이 그럴듯했던 근거가
> 같이 사라지기 때문이다.
```

### 2-2. 파생 문서는 드리프트가 곧 결함이다

`02-AI-Pipeline`과 `03-API-Specs`는 **"지금 무엇이 참인가"** 를 말하는 문서다.
ADR이 *왜*를 기록하고 이 둘이 *지금*을 기록한다. **파이프라인 단계나
엔드포인트가 바뀌면 같은 패스에서 같이 고친다.**

> 실제로 이걸 어겨서 2026-08-09 점검에 **자기모순 4건**이 나왔다 — 같은 문서
> 안에서 `llm_calls` 를 표는 2, 예시는 1로 적고 있었고, 제거된
> `demo-token` 이 permitAll 목록에 남아 있었다. **값이 바뀐 절과 값을 인용한
> 절이 떨어져 있으면 뒤쪽만 고치게 된다.** 파생 문서를 고칠 땐 같은 숫자를
> 문서 전체에서 grep 한다.

## 3. 프론트매터

모든 `.md`는 YAML 프론트매터로 시작한다.

```yaml
---
status: 채택됨          # 아래 표. DevLog 는 생략 가능
created: 2026-08-09     # 필수, 절대 날짜
updated: 2026-08-09     # 파생 문서만 필수 (내용을 고칠 때 같이 올린다)
tags: [search, llm]     # 권장
---
```

| `status` | 뜻 | 쓰는 곳 |
|---|---|---|
| `채택됨` / `기각됨` / `대체됨` | 결정의 귀결 | ADR |
| `현행` | 지금 참인 내용 | 파생 문서 |
| `진행중` / `완료` | 작업 상태 | 로드맵·회고·누적 사례집 |
| `원천자료` | **고치지 않는다** | 기획서 |

**날짜는 항상 절대 표기다.** "지난주", "최근"은 쓰지 않는다 — 6개월 뒤에 읽는
사람에게 상대 날짜는 정보가 아니다.

## 4. 링크 규칙

### 4-1. 최소 2개, 그리고 양방향

**새 문서는 관련 문서를 최소 2개 링크한다.** 그리고 **링크는 한쪽만 걸지
않는다** — 새 문서에서 기존 문서를 가리켰으면, 기존 문서에도 새 문서로 오는
줄을 추가한다. 링크가 한 방향뿐이면 **나중에 기존 문서 쪽에서 출발한 사람은 그
연결을 영영 못 찾는다.**

### 4-2. 두 표기법과 각각의 용도

| 표기 | 쓰는 곳 | 왜 |
|---|---|---|
| `[[문서-이름]]` | **vault 안**의 개념 참조 | Obsidian 그래프에 뜨고 백링크가 자동으로 잡힌다 |
| 표준 마크다운 링크 (`[제목]` + 괄호 안 상대경로) | **GitHub에서도 눌러야 하는** 링크 | README·발표자료처럼 웹에서 읽히는 문서 |

**둘 다 유효하다.** 다만 `05-Troubleshooting` 사례집처럼 **여러 문서가 반복해
가리키는 허브**는 `[[…]]` 를 쓴다 — 백링크 목록 자체가 *"이 함정이 어디서
재발했나"* 의 답이 된다.

### 4-3. ADR은 번호로 부른다

본문에서는 `ADR-0039` 처럼 **번호로** 부르고, 문서 끝의 "관련 문서" 절에서
경로를 준다. 본문마다 긴 경로를 넣으면 읽기가 끊긴다.

## 5. 내용 규칙 — 이 저장소가 반복해서 지키는 것

### 5-1. 출처를 명시한다

**모든 수치에는 그것을 만든 것이 붙어야 한다.**

- 어떤 스크립트/하네스가 냈는가 (`scripts/evaluate_hard_filters.py`)
- 표본이 몇 개인가
- **어떤 모델·환경에서 쟀는가** — 이건 특히 중요하다. 이 저장소의 품질 수치
  다수가 **특정 LLM 모델에 딸려 있고**, 모델을 바꾸면 주장이 *"지금 쓰지 않는
  모델에 대한 주장"* 이 된다([[LLM-동작을-측정-없이-단정하기]])

### 5-2. 기각한 것을 남긴다

**해보고 접은 것은 지우지 않는다.** 접은 이유가 없으면 다음 사람(과 6개월 뒤의
나)이 같은 걸 다시 시도한다. 특히 **다시 시도해도 되는 조건**을 같이 적는다:

> 리랭커 하한은 노이즈가 나아졌다고 다시 시도할 게 아니다. 필요한 것은
> **질의 간 비교 가능한 점수 정규화**다.

### 5-3. 진 것은 진 대로 적는다

모든 모델은 단순 기준선과 비교하고, **기준선에 졌으면 졌다고 적는다.** 그게
나머지 수치의 신뢰를 만든다.

### 5-4. 사전 등록한 판정선은 사후에 고치지 않는다

측정 **전에** 건 기준이 실패하면 **실패로 남긴다.** 결과를 보고 기준을 바꾸면
그건 사전 등록이 아니라 사후 합리화다. 채택하려면 **다른 근거**를 대야 한다.

### 5-5. 일반 규칙은 일반 위치에도 남긴다

사례 문서에서 나온 교훈이 **이 프로젝트 밖에서도 참인 규칙**이면,
`05-Troubleshooting` 사례에만 두지 말고 **`CLAUDE.md`의 Gotchas** 에도 한 줄
남긴다. 사례는 검색해야 나오고 Gotchas는 매번 읽힌다.

### 5-6. 안내문은 저장소를 먼저 읽고 쓴다

사용자가 직접 실행할 명령(배포·검증)은 **즉석에서 지어내지 않는다.**
`07-배포/배포-절차.md` 와 `load/verify-*.sh` 에 **같은 일을 하는 기존 절차**가
있으면 그걸 인용한다.

> **안내문은 검사보다 덜 검증된다.** 검사와 달리 돌려볼 대상이 없어서, 틀려도
> 사용자가 실행할 때까지 안 드러난다. 실제로 한 라운드에서 배포 명령이 **여섯
> 번 틀렸고 그중 넷은 답이 이미 이 저장소 안에 있었다.**

## 6. 문서를 만들/고칠 때의 체크리스트

**새 문서**

- [ ] 프론트매터 4키(`status`·`created`·`updated`?·`tags`)
- [ ] **관련 문서 2개 이상** 링크
- [ ] 그 문서들에도 **역방향 링크** 추가
- [ ] [INDEX](INDEX.md)에 한 줄 추가 (허브 문서인 경우)
- [ ] 수치마다 출처(스크립트·표본 수·모델)
- [ ] 기각한 대안과 **다시 볼 조건**

**기존 문서 수정**

- [ ] ADR·DevLog인가? → **원문 대신 정정 블록**
- [ ] 파생 문서인가? → 고치고 `updated` 갱신
- [ ] 같은 수치를 **다른 문서가 인용하고 있지 않은가** → `grep` 해서 같이 고친다
- [ ] 링크가 깨지지 않았는가

**라운드를 닫을 때**

- [ ] 관련 ADR / DevLog / 로드맵 / `CLAUDE.md` / `README.md` 갱신
- [ ] 재발 가능한 진단 패턴이 있으면 `05-Troubleshooting`
- [ ] 개수 표기(ADR·테스트·사례) 일관성
- [ ] **컨테이너로 한 번 돌려본 뒤에** 닫는다 — 로컬 프로세스로는 안 보이는
      결함 계열이 따로 있다([[로컬-프로세스로는-볼-수-없는-결함]])
