# ADR-0019: 관측성 1단계 — 계측은 부하테스트가 물을 질문에서 역산한다

## 상태

채택됨. (2단계 — ELK·분산 트레이싱 — 는 부하테스트 결과가 지목할 때 착수)

## 배경

Phase 8의 다음 항목이 부하테스트인데, **관측성 없이 부하를 걸면 `p95 = 3초`만
얻고 그 3초가 어디서 왔는지 말할 수 없다.** 그래서 목적을 "대시보드를 갖춘다"가
아니라 **"부하테스트가 병목을 읽을 수 있게 한다"**로 잡고, 답해야 할 질문에서
역산해 범위를 정했다.

착수 전 사실 확인에서 **원래 계획의 전제가 두 군데 틀렸다.**

## 정정 1 — 통합 진입점이 단계 분해를 버리고 있었다

계획은 "이미 있는 `timings`를 메트릭으로 승격"이었다. `timings`는 실제로 있었다.
문제는 **`/api/assistant`에서 그게 사라진다**는 것이었다.

`_execute()`가 반환하는 payload에 `run_search`의 `timings`가 실리지 않아,
통합 진입점 — 부하테스트가 때릴 바로 그 엔드포인트 — 은 `execution_ms` 하나만
노출했다. 분해는 `/api/search`에만 있었다.

거기에 더해 **설명 생성 LLM 호출이 아예 계측되지 않았다.** 검색 분기는 LLM을
2회 부르는데 재작성만 분해돼 있었다.

→ 그래서 이번 작업의 첫 순서는 메트릭이 아니라 **분해 복원**이다.

### 복원의 효과가 즉시 나타났다

복원 직후 첫 요청:

| 단계 | 1회차 | 2회차 |
|---|---|---|
| `embedding_ms` | **35,327ms** | 19.4ms |
| `rerank_ms` | 1,951ms | — |
| `query_understanding_ms` (LLM) | 3,306ms | 1,690ms |
| `explain_ms` (LLM) | 2,111ms | — |
| **`execution_ms`** | **42,920ms** | 1,743ms |

**첫 요청의 82%가 LLM이 아니라 임베딩 모델 지연 로딩이었다.** 복원 전이라면
`execution_ms = 42920` 하나만 보고 "LLM이 느리다"고 결론냈을 것이다.

부하테스트에 직결되는 결론: **워밍업 없이 시작하면 초기 수십 초가 모델 로딩으로
오염된다.** 이건 다음 라운드의 설계 입력이다.

## 정정 2 — 진짜 공백은 백엔드였다

`grep`으로 확인하니 백엔드에 `Timer`·`micrometer`·`actuator`·`nanoTime` 어느
것도 없었다. 그런데 **부하테스트의 간판 시나리오가 고경합 구매/입찰**이다.

반대로 AI 쪽은 k6가 응답 본문의 `timings`를 읽으면 서버 변경 없이도 분해가
된다. 즉 무게중심이 계획과 반대였다.

## 결정

### 1. 백엔드 — 락은 대기와 보유를 갈라 잰다

`TradeService.withItemLock()`이 고경합의 유일한 시임이라 계측을 그 자리에 모았다.

| 메트릭 | 구간 |
|---|---|
| `trade_lock_wait_seconds{outcome}` | `tryLock()` 호출~반환 |
| `trade_lock_hold_seconds` | 트랜잭션 실행 구간 |

**둘을 합쳐 재면 구분이 안 된다** — 대기가 길면 경합이, 보유가 길면 트랜잭션
자체가 문제다. 실측:

```
trade_lock_wait_seconds_sum  4.863   max 0.766   (8회 획득)
trade_lock_hold_seconds_sum  0.692   max 0.487
```

대기가 보유를 압도한다 = 요청들이 서로 뒤에서 줄 섰다.

### 2. 409의 원인을 사유별로 센다

구매/입찰 거절은 셋 다 409라 상태 코드만으로는 구분되지 않는다.
`GlobalExceptionHandler`에 `trade_rejection_total{reason}`을 뒀다.

**이 지표가 곧바로 오해를 하나 막았다.** 동시 구매 8건 중 2건이 409였는데
`reason=invalid_request`(재고 소진)였고 **락 타임아웃이 아니었다** — 락은 8건
전부 획득했다. 카운터가 없었으면 "락 경합"으로 오독할 상황이었다.

`optimistic_conflict`가 0이 아니면 분산 락이 새고 있다는 뜻이라 그 자체로 신호다.

### 3. AI — 계측 지점은 `record_response` 하나

`timings` dict가 이미 표준 형태이므로 응답을 만들 때 한 번 히스토그램으로
옮긴다. 단계마다 계측 코드를 흩뿌리지 않는다 — 새 단계가 생기면
`_STAGE_BY_KEY`에 한 줄만 추가한다.

`outcome`은 성공/실패가 아니라 **무엇이 일어났는지**를 센다(`ok` /
`no_results` / `tool_failure`). 뒤 둘은 에러가 아니지만 부하테스트에서 구분해서
봐야 한다.

에이전트의 `elapsed_ms`도 `agent_llm_ms` / `agent_tool_ms`로 쪼갰다 — 복합
질의의 병목 질문이 정확히 "LLM인가 도구인가"다.

### 4. 라벨은 테넌트까지, 카디널리티 상한을 명시

이 프로젝트는 이미 전부 테넌트 스코프다(ES 인덱스, 캐시 네임스페이스, 이상탐지
임계값). 메트릭만 예외로 둘 이유가 없다.

카디널리티 = `tenant` × `intent`(6) × `stage`(13). 테넌트가 O(10)까지 안전하다.

> **절대 라벨로 쓰지 않는다**: `item_id` · `trade_id` · `user_id` · 질의 문자열.
> "어떤 아이템이 경합했나"는 메트릭이 아니라 로그로 답할 문제다.

### 5. Prometheus + Grafana는 선택 프로파일

`docker compose --profile observability up` 일 때만 뜬다. **자원 절약만이
이유가 아니다** — 배포 대상이 다른 프로젝트와 공유하는 4 OCPU라, 부하테스트 중
같은 박스에서 스크래핑하면 **측정 대상과 부하 생성기에서 CPU를 뺏는다.**

부하테스트는 **스냅샷 차분**으로 읽는다. 히스토그램은 누적값이라 전후로
`/metrics`를 받아 빼면 실행 구간의 정확한 집계가 나온다. 스크래핑 불필요.

대시보드는 코드로 둔다(`docker/grafana/`). UI에서 만들면 재현이 안 된다.
패널 폼은 데이터의 역할로 정했다 — **단계별 지연은 "여러 범주의 크기 비교"라
13계열 시계열이 아니라 정렬된 바 게이지**이고, 막대마다 이름이 붙으므로 색이
정보를 나르지 않아 단일 색조를 쓴다. 다계열 패널의 색은 검증된 팔레트에서
가져와 6개 검사를 통과시켰다(다크, 최악 인접쌍 CVD ΔE 8.4).

## 고려한 대안

1. **Prometheus를 기본 기동** — 부하테스트 중 CPU 경합. 위 5번.
2. **로그 기반 집계만** — 인프라가 0이지만 두 서비스를 가로지르는 집계가
   수작업이 되고, 대시보드 스크린샷이라는 포트폴리오 자산을 잃는다.
3. **AI 쪽에 균등한 비중** — 계획의 원안. 사실 확인 후 기각(정정 2).
4. **요청 id 전파(백엔드 → AI)** — **넣지 않았다.** 백엔드가 AI를 부르는 곳은
   `HealthController` 한 곳뿐이라 이을 호출 사슬이 없다. 프론트가 두 서버를
   각각 호출하는 구조다. 트레이싱은 호출 사슬이 생길 때 재검토한다.

## 알려진 한계

- **워밍업이 없다.** 위 35초 모델 로딩은 첫 요청이 흡수한다. 부하테스트는
  워밍업 요청을 먼저 보내야 하고, 그걸 안 하면 초반 수치가 오염된다
- **`http.server.requests`의 URI 라벨은 백엔드만**이다. FastAPI 쪽은 경로별
  히스토그램을 안 붙였다 — 단계별 분해가 더 유용해서 미뤘다
- **부하 상황의 수치가 아직 없다.** 위 락 실측은 동시 요청 8건짜리 스모크다.
  실제 분포는 다음 라운드가 낸다
- 이상탐지·예측 파이프라인의 모델 로딩도 지연 로딩이라 같은 첫 요청 비용이
  있는데, 이번엔 검색 경로만 실측했다
