# ADR-0035: 한도가 요청 수만 세고 있었다 — 요청 크기 상한과 세션 만료 처리

## 상태

채택됨. **배포 전 점검 3회차**다. 1회차(ADR-0033)는 보안 구멍, 2회차(ADR-0034)는
진단 불가능, 이번은 **비용과 견고성**이다. 보안 구멍은 나오지 않았다.

## 배경

3회차는 앞의 두 회차가 건드리지 않은 영역을 겨냥했다 — 아이템 CRUD 인가(IDOR),
입력 크기, 관측성, 프론트 세션. 인가·격리·시크릿은 이번에도 깨끗했다.

`ItemService` 는 `getItem(tenantId, itemId)` 로 테넌트를 좁히고 `requireSeller` 로
소유자를 확인한다. 메트릭 라벨은 `tenant`/`intent`/`stage`/`outcome` 뿐이고,
로그에 비밀번호·토큰이 찍히는 곳은 백엔드·AI 모두 0건이다.

**나온 것은 크기에 관한 것이었다.**

## 결정 1: 질의 길이에 상한을 둔다 (500자)

한도 3계층(토큰 요구 · 20회/분 · 50회/일, ADR-0031)은 **전부 요청 수를 센다.**
요청 하나의 길이에 상한이 없으면 **한도를 지키면서 하루 예산을 배수로 늘릴 수 있다.**

```
19,800자 질의 → 200 OK, 16.4초
응답이 질의 전체를 그대로 되돌려준다 (≈20KB)
```

정상 질의는 ~50자 / 4.5초다.

### 발견 단서는 같은 파일 안에 있었다

```python
query: str                                  # 상한 없음
size: int = Field(default=10, ge=1, le=50)  # 상한 있음  ← 대조군
```

**같은 DTO 에서 크기는 묶고 길이는 빠뜨렸다.** `size=999` 는 실제로 422 로 막힌다.
"이 저자는 상한을 둘 줄 안다"는 것이 바로 옆 줄에 있었기 때문에, 없는 쪽이 의도가
아니라 누락임이 분명했다.

### 500자의 근거

숫자를 감으로 정하지 않았다. 둘로 뒷받침된다.

**1. 파이프라인이 그 너머를 보지도 않는다.**

| 단계 | 절단 |
|---|---|
| 임베딩(캐시·kNN) | **128토큰** (`max_seq_length`) |
| 리랭커 | **256토큰** (`max_length`) |
| 의도 분류기 | 고정 `MAX_LENGTH` |
| **LLM** | **자르지 않는다** |

즉 256토큰을 넘는 텍스트는 캐시·검색·리랭킹 어디에도 영향을 주지 않고 **LLM 요금만
늘린다.** 상한을 그 위에 두면 동작은 그대로고 비용만 막힌다.

**2. 실제 질의가 그 근처에도 안 간다.**

데이터셋 질의 **547건**을 재보니 최소 5 · 중앙 18 · p99 31 · **최대 33자**다.
500자는 관측 최댓값의 **15배**다.

`min_length=1` 도 같이 걸었다 — 빈 질의로 LLM 을 부를 이유가 없는데 예전에는 그대로
파이프라인에 들어갔다.

## 결정 2: DB 제약을 DTO 에 반영한다

`Item.name` 컬럼은 `varchar(200)` 인데 `ItemCreateRequest.name` 에는 `@NotBlank` 만
있고 `@Size` 가 없었다.

| 입력 | 결과 |
|---|---|
| name 300자 | **500** |
| name 200자 | 201 |

**잘못된 입력은 400 이어야 한다.** 500 은 "서버가 고장났다"는 뜻이라 클라이언트가
재시도하고 로그가 오염된다.

`description` 은 컬럼이 `TEXT` 라 DB 상한이 없다. 그래도 5,000자로 묶었다 —
공개 배포에서 상한 없는 문자열은 저장소를 채우는 경로다.

**수정 요청에도 같은 상한을 걸었다.** 등록만 막으면 같은 결함이 경로 하나로 남는다.

## 결정 3: 토큰 만료 시 세션을 접는다

ADR-0023 설계안에는 *"만료 시 재발급 후 1회 재시도"* 가 있었다. **로그인이 진짜
비밀번호가 되면서(ADR-0031) 조용한 재발급이 불가능해졌는데** — 비밀번호를 들고 있지
않으니 다시 받을 수가 없다 — **그 자리를 대체할 처리가 들어가지 않았다.**

TTL 이 1시간이라 데모 탭을 열어두면 반드시 만나는 상태다. 예전에는 만료 후 모든
동작이 에러를 내고 사용자가 직접 로그아웃을 눌러야 했다.

할 수 있는 건 세션을 접고 로그인 화면으로 되돌리는 것뿐이고, 그게 맞다.

> **로그인 실패의 401 과 세션 만료의 401 을 갈라야 한다.** 안 가르면 비밀번호를 틀릴
> 때마다 "세션 만료"가 뜬다. `accessToken` 이 설정돼 있었는지가 그 구분이다 —
> 토큰을 들고 갔는데 401 이면 세션이 죽은 것이고, 토큰 없이 401 이면 로그인 실패다.

## 영향

| | |
|---|---|
| AI 테스트 | 125 → **137** (경계값 12건) |
| 백엔드 테스트 | 46 → **49** (길이 경계 3건) |
| 동작 변화 | 500자 초과 질의는 **422**, 200자 초과 이름은 **400** |
| 동작 변화 | 만료된 세션은 자동으로 로그인 화면으로 돌아간다 |

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| 질의를 자르고 계속 진행 | 사용자가 자기 질의가 잘린 걸 모른다. 거부가 정직하다 |
| 토큰 수로 한도를 재계산 | 계층이 하나 늘고 토크나이저 의존이 생긴다. 길이 상한이 같은 효과를 훨씬 싸게 낸다 |
| `description` 을 그대로 무제한 | 컬럼이 TEXT 라 DB 는 안 막는다. 공개 배포에서 상한 없는 문자열은 저장소 채우기 경로다 |
| 만료 시 자동 재로그인 | **비밀번호를 들고 있지 않다.** 들고 있으려면 메모리에 평문 비밀번호를 두게 된다 |
| nginx `client_max_body_size` 로만 막기 | 1MB 는 여전히 정상 질의의 2만 배다. 상한은 의미 있는 층에 있어야 한다 |

## 배운 것

**한도의 단위가 방어하려는 대상과 같은지 물어야 한다.** 이 프로젝트는 "LLM 비용"을
막으려고 3계층을 쌓았는데 세 계층 모두 **요청 수**를 셌다. 비용은 요청 수 × 요청
크기인데 뒤쪽이 자유였다.

> **막으려는 양과 세는 양이 다르면, 아무리 여러 겹을 쌓아도 한 축이 열려 있다.**

그리고 발견 방법에 관해:

> **같은 파일 안의 비대칭이 가장 싼 단서다.** `size` 에는 상한이 있고 `query` 에는
> 없다는 것 — 저자가 상한을 둘 줄 안다는 증거가 바로 옆에 있으므로, 없는 쪽은
> 의도가 아니라 누락이다. 코드를 읽을 때 "여기만 왜 다르지"를 먼저 본다.

## 3회차까지의 수확 곡선

| 회차 | 발견 | 성격 |
|---|---|---|
| 1 (ADR-0033) | 2건 | **보안 구멍** — 무인증 LLM 경로, XFF 우회 |
| 2 (ADR-0034) | 3건 | 진단 불가능 — 401 마스킹, 테넌시 불일치, 짧은 시크릿 |
| 3 (ADR-0035) | 3건 | **비용·견고성** — 전부 fail-safe 쪽 |

**보안 구멍은 1회차에서 끝났다.** 4회차는 하지 않는다 — 남은 것은 실환경에서만
드러나는 종류(실사용 부하, ARM 지연, 실제 트래픽 패턴)다.
