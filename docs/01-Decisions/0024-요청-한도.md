# ADR-0024: 요청 한도 — 비용이 나가는 곳부터, 새 의존성 없이

## 상태

채택됨. Phase 8 보안 항목의 후반부(5b)로, 인증(ADR-0023) 뒤에 온다.

## 배경

인증이 먼저 들어간 덕에 요청마다 **검증된 신원(tenant + user)**이 있다.
IP가 아니라 실제 신원으로 셀 수 있는 상태이고, 이게 5b를 5a 뒤에 둔 이유다.

## 결정 1: 전 API에 걸지 않는다 — 막을 것이 두 종류다

| 대상 | 키 | 막는 이유 |
|---|---|---|
| `POST /api/assistant` | tenant + user | **실제로 돈이 나간다.** LLM 2회가 실측 지연의 97%(ADR-0020) |
| `POST /api/auth/demo-token` | **IP** | 인증 없이 열린 유일한 경로 |
| 구매·입찰 | user | 남용 방지 |
| 조회 계열 | — | 싸다. 걸 근거가 없다 |

**`demo-token`은 설계 중에 추가됐다.** 인증 뒤의 경로는 전부 토큰이 필요한데
이 경로만 아니다. 여기가 무제한이면 나머지 한도는 "토큰을 새로 받아서 우회"가
성립한다. 다만 **신원이 없으므로 키를 IP로 잡아야 하고, 이번 범위에서 유일한
예외다.**

> **IP 키의 한계**: NAT·회사망·모바일 캐리어 뒤에서는 **여러 사용자가 한 IP를
> 공유**하므로 정상 사용자가 남의 요청 때문에 막힐 수 있다. 신원이 없는 경로라
> 대안이 없고, 한도(분당 30)를 정상 사용(전환당 1~2회)보다 크게 잡아 완화했다.
> 실사용 환경에서는 이 값이 재조정 대상이다.

**`X-Forwarded-For`는 읽지 않는다.** 신뢰할 프록시가 없는 상태에서 그 헤더를
보면 누구나 값을 바꿔가며 새 버킷을 받는다 — 한도를 거는 코드가 스스로 우회로를
만드는 셈이다. 리버스 프록시를 두면 그때 `ForwardedHeaderFilter`로 신뢰 경계를
세우고 나서 읽어야 한다. 순서가 반대면 안 된다.

## 결정 2: 각자 이미 가진 것을 쓴다 (새 의존성 0개)

| | 방식 | 근거 |
|---|---|---|
| 백엔드 | Redisson `RRateLimiter` (토큰 버킷) | 분산 락 때문에 이미 있다 |
| AI 서버 | `redis.asyncio` 고정 윈도우 (`INCR`+`EXPIRE`) | 시맨틱 캐시가 쓰는 클라이언트 |

두 서버가 다른 알고리즘인 것은 설계 의도가 아니라 **각자 가진 것을 쓴 결과**다.
그 차이가 만드는 실제 효과는 하나뿐이다:

> **고정 윈도우는 경계에서 최대 2배까지 통과한다.** 창이 끝나기 직전과 다음 창
> 시작 직후에 몰리면 짧은 구간에 2배가 나간다. 슬라이딩 윈도우는 Lua가 필요한데,
> 목적이 **비용 폭주 차단**이지 "정확한 분당 N"이 아니라서 그 정밀도를 사지 않았다.

구현에서 조용한 함정이 둘 있어 각각 대응했다.

- **`EXPIRE`를 창의 첫 요청에만 건다.** 매번 갱신하면 창이 계속 밀려
  **한도가 사실상 사라지는데**, 정상 응답만 나오므로 눈치채기 어렵다.
  `tests/test_rate_limit.py`가 `expire` 호출 횟수를 고정한다
- **설정값을 키에 넣는다.** `RRateLimiter`는 rate를 Redis에 저장하고
  `trySetRate`는 이미 설정돼 있으면 아무것도 하지 않는다. 키가 그대로면 한도를
  바꿔도 옛 값이 계속 산다 — 부하테스트용으로 올렸다 되돌렸을 때 **조용히 안
  돌아오는** 종류의 함정이다

## 결정 3: Redis가 죽으면 통과시킨다

리미터는 **비용 방어이지 정합성 장치가 아니다.** Redis 장애로 서비스 전체가
멈추는 쪽이 더 나쁘다. 대신 조용하지 않도록 경고 로그를 남긴다.

구매 경로의 분산 락은 **반대**다. 거긴 정합성(오버셀 방지, ADR-0001)이라
실패하면 거절한다. 같은 Redis를 쓰지만 실패 정책이 반대인 것은 의도적이다.

## 결정 4: 한도는 실측에서 역산하되, 측정값과 판단을 구분해 적는다

이 프로젝트는 임계값을 감으로 정했다 뒤집힌 전례가 셋이다(오토인코더 학습셋
편향, 시맨틱 캐시 유사도, 리랭커 하한). 그래서 근거를 **두 층으로 나눠** 적는다 —
어디까지가 측정이고 어디부터가 판단인지 섞이면 나중에 재검토가 불가능하다.

### `/api/assistant` — 분당 20회 / 사용자

| 층 | 값 | 출처 |
|---|---|---|
| **물리적 상한** | **0.81 req/s ≈ 48.6회/분** | ADR-0020 `live-llm` 실측. 한 사용자가 이보다 더 낼 수 없다 |
| **적용 한도** | **20회/분** | 위 상한의 **약 41% 지점**. 측정값이 아니라 **마진을 적용한 판단** |
| 정상 사용 추정 | 분당 1회 미만 | 사람이 질문을 읽고 다음을 치는 속도. **추정이지 측정이 아니다** |

> **초안에서 이 서술이 틀렸었다.** "0.81 req/s 실측 → 20회/분, 정상 사용의
> 20배"라고 썼는데, 0.81 req/s를 분당으로 환산하면 48.6회이므로 20회는 **상한의
> 41%**이지 20배가 아니다. "20배"는 *추정 정상 빈도*를 기준으로 한 수치인데
> *물리적 상한*과 한 문장에 섞여 근거가 흐려졌다. 숫자(20)는 유지하되 서술을
> 갈랐다.

### 구매·입찰 — 초당 10회 / 사용자

전체 처리량 상한이 **107 req/s**(ADR-0020, knee ≈ 4 VU)인데 그건 시스템 전체
값이고, 한 사용자가 그중 10%를 초과해 점유할 이유가 없다.

### `demo-token` — 분당 30회 / IP

정상 사용은 사용자 전환당 1~2회다(개발 모드 React StrictMode의 이중 호출 포함).
30회면 정상 사용을 한참 넘는다.

**의도는 정밀 튜닝이 아니다.** 정상 사용자가 절대 닿지 않는 곳에 두되 폭주는
막는다.

## 결정 5: 부하테스트 충돌 — 구성으로 가르고, 감사 가능하게

`cache-warm`이 단일 사용자로 **27 req/s**를 낸다(ADR-0020). 운영 한도를 그대로
두면 부하테스트가 **리미터를 측정**한다 — ADR-0020에서 "락 경합인 줄 알았더니
재고 고갈을 재고 있던" 것과 같은 종류의 오염이고, 429가 조용히 섞이는 만큼 더
안 보인다.

### 시나리오마다 대응이 다른 기준

**그 부하 시나리오가 "단일 사용자 행위"를 시뮬레이션하는가, "다중 사용자
행위"를 시뮬레이션하는가**로 갈린다.

| 시나리오 | 성격 | 대응 |
|---|---|---|
| `cache-warm` (27 req/s) | **단일 사용자가 캐시를 데우는 것이 시나리오의 전제**다. VU마다 토큰을 나누면 테스트 목적 자체가 깨진다 | 구성 완화만 |
| `purchase` | **여러 사용자의 동시 구매**가 실제 상황에 더 가깝고 이미 구매자가 3명뿐이다 | 구성 완화 + 사용자 수 확대 |

### 완화는 파일에 남지 않게 한다

| | 방법 |
|---|---|
| 백엔드 | `application-loadtest.yml` + `SPRING_PROFILES_ACTIVE=loadtest` |
| AI 서버 | 기동 시 환경변수 `RATE_LIMIT_ASSISTANT_PER_MIN=…` |

`application.yml`의 숫자를 손으로 고쳤다 되돌리는 방식은 **되돌리는 걸 잊을 수
있어서** 쓰지 않는다. 완화한 값이 어디에도 저장되지 않으면 그 실수가 불가능하고,
어떤 구성으로 돌았는지가 **실행 명령에 드러난다.** 우회 헤더
(`X-Bypass-RateLimit` 류)를 기각한 것과 같은 기준이다 — **감사 가능해야 한다.**

방식이 서로 다른 것은 Spring에는 프로파일이 있고 pydantic-settings는 `.env`
하나를 읽기 때문이다. 보장하려는 성질("완화값이 파일에 남지 않는다")은 같다.

### 끄지 않고 올린다

`enabled: false`가 아니라 큰 값을 쓴다. 리미터 경로가 그대로 돌아야 그 오버헤드가
측정에 포함되고, **`run.sh`가 실행 후 한도 초과 카운터로 오염 여부를 단언**할 수
있다. 아예 끄면 그 확인이 불가능해진다.

## 관측 — 429가 보여야 한다

ADR-0019의 규칙(계측 지점 하나, 라벨은 유한한 값만)을 지키되 **예외를 명시한다.**

| 메트릭 | 라벨 |
|---|---|
| `ai_rate_limited_total` | `tenant`, `path`(경로 패턴) |
| `rate_limited_total` (백엔드) | `scope` (`demo_token` / `trade`) |

- **AI**: 한도 거절은 파이프라인 진입 전에 끝나므로 `record_response()`를 지나지
  않는다. 계측 지점이 하나라는 원칙의 예외이고, 이유를 `metrics.py`에 적어뒀다
- **백엔드**: 기존 `trade.rejection{reason}`에 합치지 **않았다** — 토큰 발급은
  거래가 아니라서 이름이 거짓이 된다. 계측 *지점*은 `GlobalExceptionHandler`
  하나로 유지하되 이름은 정직하게 뒀다

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| **전 API 일괄 적용** | 조회는 싸고 걸 근거가 없다. 근거 없는 한도는 나중에 원인 모를 429를 만든다 |
| **우회 헤더로 부하테스트 통과** | 인증 구멍이다. 감사도 불가능하다 |
| **부하 시 `application.yml` 직접 수정** | 되돌리는 걸 잊으면 운영 한도가 사라진 채로 남는다 |
| **부하 시 리미터 끄기(`enabled: false`)** | 오버헤드가 측정에서 빠지고, 오염 여부를 확인할 카운터도 안 생긴다 |
| **AI도 토큰 버킷(Lua)** | 목적이 비용 차단이라 경계 2배를 수용할 수 있다. 새 Lua 스크립트를 들일 값어치가 없다 |
| **Redis 실패 시 거절(fail-closed)** | 비용 방어 때문에 서비스 전체가 멈춘다. 정합성 장치가 아니다 |
| **`X-Forwarded-For`로 IP 판별** | 신뢰할 프록시가 없으면 헤더 하나로 우회된다 |

## 검증 (실측)

| 확인 | 결과 |
|---|---|
| `demo-token` 30회/분 | 30회 통과, **31회차부터 429**, `Retry-After: 60` |
| `/api/assistant` 20회/분 | 20회 통과, **21회차부터 429**, `Retry-After: 29`(잔여 TTL) |
| **사용자 격리** | user3이 막힌 상태에서 **user4는 200** |
| 구매 10회/초 | 순차 15건은 전부 통과(1초를 넘겨 리필됨), **동시 25건은 17/8** |
| 메트릭 | `ai_rate_limited_total{path,tenant}`, `rate_limited_total{scope}` 둘 다 노출 |
| `loadtest` 프로파일 | `profile is active: "loadtest"`, 동시 25건 **25/25 통과** |
| 부하테스트(완화 구성) | 체크 **100%**, 오염 경고 없음, **오버셀 0건 유지**(834 == 834) |

### 안전망이 자기 자신에게 걸렸다

오염 경고를 처음 붙였을 때 **작동하지 않았다.** 부하 실행에서 3,361건 중 300건만
통과했는데(나머지가 429) 경고가 조용했다.

원인은 리미터가 아니라 **경고의 입력**이었다. `snapshot_metrics.py`는 카운터를
증가분 절댓값 **상위 25개만** 출력하는데, 그 순위에 바이트 카운터(억 단위)가
섞여 있고 Spring Security가 3,362짜리 필터체인 계열을 9개 추가하면서
`rate_limited_total`의 증가분 3,057이 **표시에서 밀려났다.**

**잘린 화면을 안전망의 입력으로 삼은 것이 잘못이다.** 스냅샷 원본에서 직접
세도록 고쳤고, 고친 뒤 같은 조건에서 10,178건을 잡았다.

> **`diff.txt`의 카운터 목록은 상위 25개라는 것을 읽는 사람이 알아야 한다.**
> 표시 자체의 개선(단위가 다른 계열을 한 순위에 섞지 않기)은 이번 범위 밖으로
> 두고 로드맵에 등록했다.

이 하네스에서 **검사 자체가 틀린 것은 이번이 세 번째**다(앞의 둘은 ADR-0020).
앞의 둘은 정상 시스템에 실패를 보고한 **오보**였고 이번은 결함을 놓친
**침묵**이라 방향이 반대다. 세 건과 재발 조건 체크리스트는
[[검사-자체가-틀린-사례들]]에 모았다.

## 영향

- 새 의존성 **0개**
- 테스트 AI **108 → 116건**(한도 8건). 백엔드는 10건 유지
- `run.sh`가 실행 후 **한도 초과 카운터를 확인해 오염을 경고**한다.
  ADR-0020의 정합성 단언과 같은 자리, 같은 목적이다
- 부하테스트 실행 절차가 바뀐다(`load/README.md`) — 두 서버 모두 완화 구성으로
  띄워야 한다
- **IP 키는 NAT 뒤에서 오탐 가능**하다(위). 지금은 데모라 실害가 없지만 실사용
  전에 재조정해야 한다
