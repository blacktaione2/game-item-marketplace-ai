# ADR-0031: 공개 준비 — 로그인, LLM 비용, 신뢰 프록시

## 상태

채택됨. **9b(ARM·실배포)보다 앞선다** — 이게 안 되면 배포가 곧 사고다.

## 배경

배포 서버를 **공개**하기로 하면서 네 가지가 즉시 문제가 됐다.

| | 상태 |
|---|---|
| 토큰 발급 | `POST /api/auth/demo-token {userId}` — **비밀번호 없음** |
| LLM 비용 | 익명으로 무한 호출 가능. 요청당 LLM 2회, **카드로 결제** |
| IP 한도 | nginx 뒤에서 **전 사용자가 한 키를 공유** |
| 시크릿 | `gimp_local_pw` 등이 **소스에 그대로** |

세 번째는 ADR-0029가 걸어둔 트리거가 **정확히 지금 걸린 것**이다 —
*"신뢰할 수 있는 리버스 프록시가 전제되지 않으면"* 이라던 조건이 충족됐다.

## 결정 1: 로그인은 최소 — 시드 계정만, 회원가입 없음

`demo-token` 제거, `POST /api/auth/login {username, password}` 신설.
**계정은 시드로 고정이고 가입 경로가 없다.**

가입을 열면 이메일 인증·비밀번호 재설정·계정 복구가 따라오고, 공개 배포에서는
**스팸 계정 방어**라는 다른 문제가 열린다. 이 프로젝트의 서사(AI 파이프라인·
멀티테넌시·동시성)와 무관한 범용 웹 기능이다 — C1(거래를 큐로)을 기각한 것과
같은 기준이다.

### 비밀번호를 소스에 두지 않는다

시드 SQL은 `export_demo_sql.py`가 만드는 **자동 생성 파일이고 커밋된다.**
해시를 박으면 비밀번호가 저장소에 남는다. 그래서 `DemoAccountInitializer`가
기동 시 환경변수로 주입한다.

### 비밀번호가 둘인 이유

`DEMO_PASSWORD`(일반 4계정) / `ADMIN_PASSWORD`(GM). 하나면 **데모 비밀번호를 아는
사람이 곧바로 GM이 되고**, 이상거래 큐가 GM 전용인 것(ADR-0023)이 무의미해진다.

> 시드의 자리표시자는 **29자로 BCrypt 형식이 아니다**(정상 60자). 어떤 비밀번호와도
> 매칭되지 않으므로, 주입을 빠뜨린 배포는 **아무도 로그인 못 하는 쪽**으로 실패한다.

## 결정 2: LLM 비용 — 3계층, 각각 다른 것을 막는다

| 계층 | 막는 것 | 담당 |
|---|---|---|
| **OpenAI 월 사용량 상한** | **최악의 금액** | 사람(대시보드). 코드가 뭘 하든 최후 안전망 |
| 로그인 게이트 | 익명 대량 호출 | 결정 1 |
| **사용자별 일일 한도 50회** | 로그인한 사람의 폭주 | 이번 라운드 |

**50의 도출**: 분당 20회면 물리 상한이 하루 28,800회다. 데모에 필요한 건 한 번
둘러보는 정도(검색 몇 번 + 시세 + 이상거래 + 에이전트 = 20~30회)라 그 2배로 잡았다.
계정 5개를 다 소진해도 250회, 요청당 LLM 2회이므로 최악 500호출이다.

### 리셋은 한국시간 자정 — 키에 날짜를 넣는다

```
ratelimit:assistant_daily:50/1d:2026-08-03:nexon:3
```

Redis 만료에 맡기면 창이 **그 사용자의 첫 호출** 기준이라 사람마다 리셋 시각이
다르고 예측이 안 된다. 날짜가 키에 있으면 "한국시간 자정"이라고 설명할 수 있다.

**고정 윈도우의 2배 한계를 하루 단위에서도 그대로 받는다** — 자정 전후로 몰리면
짧은 시간에 100회가 가능하다(ADR-0024가 분 단위에서 기록한 그 현상). 수용하는
이유는 실제 비용 상한이 OpenAI 월 한도이고 이 계층은 **평범한 남용**을 막는 것이기
때문이다. 정확히 막으려면 슬라이딩 로그가 필요한데 100 vs 50 차이에 새 구조를
들일 값어치가 없다.

> **분당에 막힌 요청은 일일 카운터를 올리지 않는다.** 먼저 올리고 나중에 검사하면
> 잠깐 몰아친 대가로 하루치를 잃는다.

## 결정 3: XFF — 신뢰하는 프록시에서 온 것만

```java
if (!trustedProxies.contains(remoteAddr)) return remoteAddr;  // 헤더 무시
return lastValueOf(header("X-Forwarded-For"));                // 맨 뒤 = 우리 프록시가 붙인 값
```

**기본값은 빈 목록**이다. 설정을 안 하면 예전과 똑같이 XFF를 무시하므로, 잊은
배포가 **더 안전한 쪽**으로 실패한다.

맨 마지막 값을 쓰는 이유: XFF는 `클라이언트, 프록시1, 프록시2` 순으로 쌓이는데
앞쪽은 클라이언트가 위조해 넣을 수 있고 **맨 뒤가 우리 프록시가 붙인 값**이다.

## 결정 4: 기본 시크릿으로는 `prod`가 뜨지 않는다

`SecretGuard`가 `JWT_SECRET`·DB·Redis·RabbitMQ 비밀번호를 검사하고, 데모 비밀번호가
비었거나 **둘이 같으면** 기동을 거부한다. 경고 로그는 기동 로그에 묻힌다 —
`loadtest` 프로파일을 별도 파일로 뺀 것과 같은 발상으로 **구조적으로 잊을 수 없게**
만든다.

> `prod`로 띄우지 않으면 아무 일도 하지 않는다. 배포 절차가 그 프로파일을 명시해야
> 실질 방어가 된다 — 그래서 배포 오버레이가 프로파일을 박아둔다.

## 결정 5: 배포에서는 nginx의 80만 노출한다

ADR-0029는 부하 하네스 때문에 8080·8000을 열어뒀다. 로컬에서는 맞지만 **공개
배포에서는 nginx를 우회하는 경로**가 된다.

**포트 미노출이 1차 방어선이고 XFF 신뢰 목록이 2차다.** 둘은 서로를 대체하지 않는다 —
디버깅하려고 포트를 잠깐 열거나, 앞에 로드밸런서를 두거나, 컨테이너 네트워크에
접근이 생기면 1차가 무너진다. 그때 2차가 남아 있어야 한다.

검증도 그래서 갈린다:

| 판정 | 어디서 | 왜 |
|---|---|---|
| 6 (XFF 위조 무시) | **로컬**(포트 열림) | 배포 구성에서는 **연결이 안 돼 "통과"** 한다 — 아무것도 확인 안 하고 |
| 9 (포트 미노출) | **배포 오버레이**(로컬에 띄워서) | 배포에서만 검증 가능한 검사를 만들지 않는다 |

## 판정선과 결과 — 10개 전부 통과

| # | 기준 | 결과 |
|---|---|---|
| 1 | `demo-token`이 **유효 토큰을 들고도** 404 | 통과 |
| 2 | 틀린 비밀번호 401 / 없는 사용자도 401 | 통과 |
| 3 | 비밀번호 분리 **양방향** | 통과 |
| 4 | 토큰 없이 `/api/assistant` → 401 | 통과 |
| 5 | 일일 한도 초과 → 429 | 단위 테스트로 고정(과금 회피) |
| 6 | 위조 XFF로 한도 우회 불가 ※ | 통과 |
| 7 | `prod` + 기본 시크릿 → 기동 거부 ※ | 통과 |
| 8 | 회귀: 백엔드 42건, AI 121건, 프론트 빌드 | 통과 |
| 9 | 배포 구성에서 8080·8000·15672·9200 닫힘 ※ | 통과 |
| 10 | **프록시 경유 로그인 200** ※ | 통과 |

※ = 실패 케이스를 만들어 확인한 항목.

**판정 3을 양방향으로 넓힌 것이 핵심이다.** "일반 비밀번호로 GM 로그인 실패"만
보면 **초기화가 반대로 잘못된 경우**(ADMIN 비밀번호가 일반 계정에도 걸리는)를
못 잡는다. 역방향은 일반 계정 **4개 전부**를 돈다 — 한 계정에만 잘못 적용되는 것이
실제 실수 형태다.

**판정 6은 실제로 실패시켜 봤다.** 호스트를 신뢰 목록에 넣자 위조 XFF 40개가 한도를
우회했고 검사가 실패로 보고했다.

> ### 정정 (2026-08-04, ADR-0033) — 판정 6은 **엉뚱한 대상을 재고 있었다**
>
> 위 문단은 사실이다. 다만 **그 검사가 검증한 경로는 배포되지 않는 경로였다.**
> 판정 6은 백엔드 포트에 직접 쏘면서 이렇게 적어뒀는데:
>
> > `nginx 를 거치면 nginx 가 헤더를 자기 값으로 덮으므로 스푸핑 시나리오 자체가
> > 재현되지 않는다`
>
> **그 주장이 틀렸다.** `frontend/nginx.conf` 에는 `X-Forwarded-For` 를 설정하는
> 줄이 **아예 없었고**, nginx 는 설정하지 않은 헤더를 지우지 않고 그대로 넘긴다.
> 즉 클라이언트가 보낸 위조 XFF 가 백엔드에 도달했다.
>
> 배포 전 점검에서 프록시 경유로 다시 재자 **위조 40회가 전부 통과**했다
> (대조군: 헤더 없이는 31번째 429 — 리미터 자체는 정상). 아래 결정 3이
> "잊은 배포가 안전한 쪽으로 실패한다"고 적은 것은 맞지만, **런북대로
> `TRUSTED_PROXIES` 를 채운 배포는 오히려 한도가 사라지는** 상태였다. 안전한
> 설정과 올바른 설정이 양립하지 않았다.
>
> 이 라운드의 잘못은 **"신뢰 목록"만 만들고 그 값을 붙이는 쪽을 안 고친 것**이다.
> 헤더를 *읽는* 쪽에 조건을 걸면서, 그 헤더를 *쓰는* 주체가 없다는 것을 확인하지
> 않았다. 수정은 nginx 한 줄이고 검사는 프록시 경유로 옮겼다 — ADR-0033.

## 작업 중 잡은 것 — 여섯 건

### 1. `BadCredentialsException`이 500으로 나갔다

Spring Security의 예외 변환은 **필터 체인에서 던져진 것만** 다루는데 이건 서비스
안쪽에서 나온다. 핸들러가 없으면 자격증명 오류가 **서버 오류**로 보고되고,
클라이언트는 재시도하고 로그는 오염된다. 401로 매핑했다.

### 2. 테스트가 429에 걸렸다

양방향 검증이 계정 전부를 도는데 로그인 한도가 IP당 30회/분이다. **리미터는 정상
동작**이고 테스트가 비밀번호 로직을 재는 것이라 그 테스트에서만 껐다.

### 3. 판정 1의 검사가 약했다

`demo-token`이 404가 아니라 **401**을 냈다 — 경로가 `PUBLIC_PATHS`에서 빠져 보안
계층이 먼저 막기 때문이다. 숫자만 401로 바꾸면 **약한 검사**가 된다: 누군가 이
엔드포인트를 인증 뒤에 되살려도 똑같이 401이다. **유효한 토큰을 들고 가도록** 고쳐서
404가 "핸들러가 없다"의 직접 증거가 되게 했다.

### 4. compose 환경변수 누락 — 세 번째

`DEMO_PASSWORD`·`ADMIN_PASSWORD`를 셸에서 넘겼는데 컨테이너에 안 들어갔다.
`docker-compose.yml`의 `environment`에 선언이 없었기 때문이다. `RABBITMQ_HOST`
(ADR-0030)에 이은 두 번째였고, 이어서 **`DB_PASSWORD`도 같은 이유로 빠져 있었다** —
Postgres는 새 비밀번호로 초기화되는데 앱은 `application.yml` 기본값을 썼다.

> **compose의 `environment`는 셸 환경을 자동 상속하지 않는다.** 증상이 각각
> "설정이 안 먹는다", "password authentication failed"라 원인이 애플리케이션
> 쪽으로 보인다.

### 5. `ports: []`는 포트를 지우지 않는다

Compose는 시퀀스를 **이어 붙인다.** 빈 목록을 더해봐야 기본 파일의 포트가 남는다.
`!override []`로 교체를 명시해야 한다.

**이걸 놓칠 뻔한 경위가 더 중요하다** — 처음 실행에서 8080이 닫힌 것처럼 보였는데,
사실은 `SecretGuard`가 기동을 거부해 **컨테이너가 안 뜬 것**이었다. 그래서
`verify-deploy.sh`에 "스택이 실제로 떠 있는가"를 **먼저** 넣었다.

### 6. 비밀번호 주입이 시드에 덮인다

`DemoAccountInitializer`는 백엔드 기동 시 돌고, `db-seed`는 백엔드가 **healthy가 된
뒤에** 실행된다(테이블을 Hibernate가 만들어서 그 순서를 피할 수 없다). 그래서
시드의 자리표시자가 초기화기 결과를 지운다.

거기에 **nginx가 옛 IP를 물고 있는 문제**가 겹친다 — `proxy_pass`에 호스트명을
literal로 쓰면 nginx가 기동 시 한 번 DNS를 풀고 캐시하므로, 백엔드 재생성 후 502다.

둘 다 **기동 후 `restart backend web`** 으로 해결되고, 그 단계를 잊으면
**판정 10이 401 또는 502로 지목한다.** 검사 하나가 두 실수를 다 잡는다.

|---|---|
| HTTPS·도메인 | **실제 호스트에서만** 가능 — 배포 단계 |
| nginx DNS 재해석(`resolver` + 변수) | 컨테이너 재생성이 잦아질 때. 지금은 재시작으로 충분하다 |
| 회원가입·비밀번호 재설정 | 결정 1에서 의도적으로 제외 |
| 응답 시간 기반 사용자 열거 | 계정이 5개 고정이라 열거의 값어치가 없다 |

## 공개 데모의 딜레마 — 숨기지 않고 적는다

비밀번호를 README에 적으면 로그인 게이트의 의미가 반감된다. 그래도 적어야 접속이 된다.

**로그인 게이트의 목적은 접근 제한이 아니라 익명 대량 호출 차단이다.** 비밀번호가
공개돼도 (a) 봇이 자동으로 넘지 못하고 (b) 사용자별 일일 한도가 걸린다. 진짜
방어선은 **OpenAI 월 상한**이고 이건 그 앞의 두 겹이다.

**GM 비밀번호는 공개하지 않는다** — 그게 비밀번호를 둘로 나눈 이유다.
