# ADR-0020: 부하테스트 — 오버셀 0건 검증과 병목 판정

## 상태

채택됨. 도구는 k6, 성공 기준은 SLO가 아니라 **이진 정합성 단언**.

## 배경

Phase 8 순서 2번. 앞 라운드(ADR-0019)가 계측을 깔면서 입력 두 개를 남겼다 —
워밍업 필수, 락 대기/보유 분리 준비됨.

**이번 라운드의 가장 큰 산출물은 처리량이 아니다.** ADR-0001이 "Redis 분산 락 +
낙관적 락이 오버셀을 막는다"고 주장하는데, **실동시성에서 검증된 적이 없었다.**
지금까지 curl 수동 확인이 전부였다.

## 착수 전 발견 — 지금 데이터로는 락을 못 잰다

관측성 라운드의 스모크(동시 구매 8건)에서 **2건이 재고 소진으로 거절**됐다.
그 테스트는 락 경합이 아니라 **재고 고갈을 측정하고 있었다.**

시드가 `stock=10`(고정가)이라 부하를 걸면 10요청 만에 바닥나고 그 뒤로는 전부
`invalid_request`다. 락 대기는 0에 수렴한다. 입찰도 대안이 못 된다 —
`bidPrice > minimumAcceptableBid()` 때문에 동시 입찰의 절반이 정상 실패한다.

→ **`seed-loadtest.sql`을 선행 조건으로 만들었다.** 아이템 9001~9021, 재고
1천만. 데모 시드와 분리한다.

"계측이 있다"와 "시나리오가 그걸 쓴다"는 다른 문제라는 게 여기서 드러났다.

## 결정

### 도구: k6

기획서·로드맵의 원안이고, 응답 본문의 `timings`를 Trend로 기록하는 것과
스테이지 기반 램프를 선언적으로 쓸 수 있다. `winget install GrafanaLabs.k6`.

### 성공 기준: 지연시간 목표를 걸지 않는다

이 프로젝트는 임계값을 감으로 정했다 뒤집힌 전례가 둘 있고(오토인코더 학습셋
편향, 시맨틱 캐시 유사도), **첫 측정에는 비교 기준이 없다.** 곡선을 먼저 그리고
SLO는 다음 라운드에서 정한다.

대신 **자의적이지 않은 이진 기준**을 건다: 오버셀 0건, 5xx 0건,
`optimistic_conflict` 0건, 거절 사유가 예상과 일치.

### 판독 규칙을 측정 전에 등록했다

사후에 그럴듯한 해석을 붙이는 걸 막으려고 `load/README.md`에 먼저 적었다.

| 관측 | 결론 |
|---|---|
| 대기↑, 보유 평평 | 병목은 큐잉. 상한 ≈ `1/보유시간` |
| 대기↑, 보유도 ↑ | 병목은 트랜잭션(DB) |
| `spread`에서도 대기 | Redisson/Redis 자체 |

## 결과 1 — 오버셀 0건 (ADR-0001 최초 검증)

`run.sh`가 매 실행마다 `재고 감소분 == 201 응답 수 + 워밍업 1건`을 확인한다.

| 프로파일 | 구매 | 재고 감소 | 판정 |
|---|---|---|---|
| contended 20VU/30s | 3,200 | 3,201 | **일치** |
| spread 20VU/30s | 12,925 | 12,926 | **일치** |
| step (0→80VU/100s) | 10,480 | 10,481 | **일치** |

**총 26,600여 건의 동시 구매에서 오버셀 0건.** `optimistic_conflict`도 0이라
분산 락이 새지 않았고 낙관적 락이 발동할 일도 없었다.

## 결과 2 — 병목이 어디로 옮겨가는지 보인다

20 VU, 30초, 같은 조건에서 프로파일만 바꿨다.

| | contended (1개 아이템) | spread (20개) |
|---|---|---|
| 처리량 | 105.9/s | **429.6/s** |
| 락 **대기** 평균 | **0.1782s** | 0.0064s |
| 락 **보유** 평균 | 0.0068s | **0.0335s** |

- **contended**: 대기가 보유의 26배. 판독 규칙 → **큐잉이 병목**.
  상한 ≈ 1/0.0068 ≈ 147/s, 실측 106/s (73%. 나머지는 락 획득/해제 왕복)
- **spread**: 대기가 27배 줄어 사실상 사라졌다. **대조군이 성립했다** — 대기는
  고정 오버헤드가 아니라 진짜 경합이었다. 대신 보유가 5배 늘었다(0.0068 →
  0.0335). 판독 규칙 → 429/s에서는 **DB가 제약**

**병목이 하나가 아니라 부하 형태에 따라 옮겨간다.** 대조군 없이 contended만
쟀으면 "락이 병목"에서 끝났을 것이다.

## 결과 3 — 처리량은 4 VU에서 포화된다

계단식(0→5→10→20→40→80 VU, 각 20초):

| VU | 2 | 4 | 9 | 19 | 39 | 79 |
|---|---|---|---|---|---|---|
| 처리량/s | 86.2 | **106.3** | 100.7 | 107.8 | 106.6 | **106.5** |

**knee ≈ 4 VU, 상한 ≈ 107 req/s.** VU를 20배(4→79) 늘려도 처리량은 평평하고
대기만 길어진다(p95 651ms) — 단일 아이템 락이 모든 구매를 직렬화하는 전형적인
서명이다.

## 결과 4 — AI: LLM이 지연의 97%

두 모드로 나눈 이유는 그대로 부하를 걸면 **우리가 튜닝할 수 없는 OpenAI의
rate limiter를 측정**하게 되기 때문이다.

| | cache-warm (10VU) | live-llm (3VU) |
|---|---|---|
| 처리량 | **27.1/s** | 0.81/s |
| p95 | **283ms** | **4.45s** |
| `llm_calls` | **0** | 62 (2/req) |

`live-llm`의 단계 분해:

| 단계 | 평균 |
|---|---|
| `query_understanding` (LLM ①) | 1.47s |
| `explain` (LLM ②) | 1.52s |
| `retrieval` (ES) | 30.6ms |
| `rerank` (ONNX) | 33.4ms |
| `embedding` | 18.1ms |

**LLM 2회가 `execution`(3.07s)의 97%.** 우리 코드가 하는 일은 합쳐서 82ms다.
두 모드로 안 나눴으면 "우리 검색이 p95 4.45초"라고 결론냈을 것이다.

## 결과 5 — 캐시 적중 경로에서 낭비를 발견했다

`cache-warm`은 `llm_calls=0`인데도 p95가 283ms고, **그중 캐시 조회 단계만
107.9ms**였다.

원인은 `assistant/pipeline.py`의 순서다.

```python
embedding = get_embedding_service().encode_one(query)   # ~108ms
hit = await cache.lookup(tenant_code, query, embedding)
```

`lookup()`은 **정확 일치를 먼저** 시도하고, 정확 일치는 질의 문자열 해시 키만
쓴다 — 임베딩이 필요 없다. 그런데 임베딩이 호출자에서 미리 계산되므로
**모든 정확 일치 적중이 쓰지도 않을 인코딩 비용을 지불한다.**

정확 일치는 FAQ를 제외한 **전 의도의 기본 경로**다(ADR-0012). 즉 캐시가 아끼는
LLM 호출 옆에서 100ms를 그냥 버리고 있다.

**이번 범위 밖이라 고치지 않고 로드맵에 등록했다.** 지연 계산으로 바꾸면
캐시 적중 경로가 절반 가까이 빨라질 것으로 보이지만, 그건 측정으로 확인할
일이다.

## 고려한 대안

1. **LLM을 스텁으로 교체** — 프로덕션 코드에 테스트용 분기가 생긴다. 이미 있는
   캐시 경로로 같은 효과를 얻었다(`cache-warm`).
2. **에이전트(복합 질의) 포함** — LLM 최대 6회라 비용·시간이 크고, 얻는 정보가
   결과 4의 합성이다. 제외.
3. **SLO를 먼저 정하고 pass/fail** — 근거 없는 숫자가 되고, LLM이 끼면 OpenAI
   지연이 기준을 좌우한다.
4. **Prometheus를 켜고 스크래핑** — 측정 대상과 CPU를 경합한다(ADR-0019).
   스냅샷 차분으로 대체.

## 알려진 한계

- **부하 생성기가 측정 대상과 같은 박스에 있다.** 4 OCPU 공유 환경이라 이
  수치는 **보수적**이다. 전용 생성기라면 더 나온다
- **단일 인스턴스 측정이다.** 수평 확장 시 락이 어떻게 되는지는 안 봤다
- `live-llm`은 3 VU / 31요청이라 표본이 작다. OpenAI 지연 자체의 분산이 커서
  p95를 정밀하게 읽을 크기가 아니다
- **PostgreSQL·Redis가 컨테이너 기본 설정**이다. 튜닝하면 spread의 DB 제약이
  달라진다
- 검증 하네스가 두 번 틀렸다(아래) — 지금 통과하는 단언도 하네스가 맞다는
  전제 위에 있다

## 부수 기록 — 정합성 단언이 자기 하네스를 두 번 잡았다

1. **워밍업 구매가 안 세어졌다.** k6는 `setup()`에서 커스텀 메트릭을 집계하지
   않는데, 워밍업은 실제 구매 1건을 낸다. 1건 차이로 "결함"이 보고됐다
2. **`spread`에서 재고를 9001만 봤다.** 실제로는 9002~9021로 흩어져 사는데
   9001만 조회해 13,293건 불일치가 보고됐다

둘 다 시스템이 아니라 검사 쪽 결함이었다. **정상 시스템에 실패를 보고하는
검사는 없느니만 못하므로** 고쳤고, 기대식을 코드에 명시했다
(`재고 감소분 == 201 + 워밍업 1건`, 재고는 9001~9021 **합계**).

역으로 보면 이 단언이 그만큼 민감했다는 뜻이기도 하다.
