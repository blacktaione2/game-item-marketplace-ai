# ADR-0021: CI/CD 1단계 — 범위를 build+test로 자르고 부하테스트를 뺐다

## 상태

채택됨. GitHub Actions 워크플로 3종(`ai` / `backend` / `frontend`).
RAGAS 품질 게이트와 Docker 이미지 푸시는 **선행 결정이 있어** 미뤘다.

## 배경

Phase 8 순서 3번. 기획서의 원안은 `build → test → RAGAS 품질 게이트 →
Docker 이미지 푸시`인데, 그중 뒤의 둘은 지금 실행 불가능하다(아래).

착수 전에 정한 것은 **경계** 하나다 — 직전 라운드(ADR-0020)가 만든 부하 하네스를
CI에 넣을 것인가.

## 결정 1: 부하테스트는 CI에 넣지 않는다

무겁다는 이유보다 앞서는 이유가 셋이다.

| 이유 | 내용 |
|---|---|
| **환경이 달라 수치가 비교 불가** | ADR-0020의 수치에는 "부하 생성기 동거, 4 OCPU 공유"라는 조건이 붙어 있다. GH 러너(2 vCPU)에서 재면 **세 번째 환경**이 생기고 ADR 수치와도 실서버와도 비교가 안 된다 |
| **걸 임계값이 없다** | ADR-0020이 SLO를 **의도적으로 걸지 않았다**(첫 측정에는 비교 기준이 없다). 임계값 없는 부하테스트는 CI에서 아무것도 단언하지 않는다 |
| **전제 조건이 CI에 없다** | `seed-loadtest.sql` + 컨테이너 + 워밍업이 필요하고, `live-llm` 모드는 **OpenAI 키를 쓴다** — 매 커밋마다 실제 과금이다 |

"4 OCPU 경합이 재발하지 않느냐"는 우려는 **셀프호스트 러너를 쓰지 않는 것**으로
해소된다. GH 호스팅 러너는 다른 박스다. 오라클 박스에 러너를 붙이는 선택지는
바로 이 이유로 배제했다.

**재검토 조건을 명시해둔다.** ADR-0020이 미룬 SLO가 정해지면, `run.sh`의 이진
단언(오버셀 0 · 5xx 0 · `optimistic_conflict` 0)만 떼어 `workflow_dispatch`
(수동 버튼)로 올릴 값어치가 생긴다. **스케줄이 아니라 수동 트리거다.**

## 결정 2: 워크플로를 셋으로 나눈다

단일 워크플로에서는 job 단위 경로 필터를 걸 수 없다. **이 저장소는 문서 커밋
비중이 크므로**(ADR만 고친 커밋이 흔하다) 파일을 나눠 각자 `paths`를 건다.

| 워크플로 | 경로 | 하는 일 | 실측 |
|---|---|---|---|
| `ai.yml` | `ai/**` | pytest 78건 | 설치 67s + 테스트 3s |
| `backend.yml` | `backend/**` | `./gradlew build` | 컨테이너 16s + 빌드 65s |
| `frontend.yml` | `frontend/**` | `npm ci && npm run build` | — |

AI 설치 시간(torch CPU 21s + 나머지 46s)은 **분할할 만큼 크지 않다.**
`requirements-ci.txt`로 무거운 것을 빼는 안은 기각했다 — 전체 설치가 의존성 핀을
검증하는 유일한 수단이기 때문이다(아래).

## 결정 3: 백엔드는 compose 파일을 그대로 쓴다

`contextLoads()`는 살아있는 Postgres·Redis를 요구한다. GHA service containers
대신 저장소의 `docker-compose.yml`로 두 서비스만 띄웠다.

이유는 편의가 아니다 — **service containers는 `command`를 지정할 수 없어서**
Redis를 `--requirepass`로 띄울 수 없고, 그러면 `RedissonConfig`가 보내는 AUTH가
거절된다. compose를 쓰면 로컬과 동일한 구성이 되고 compose 파일 자체도 검증된다.
ES·RabbitMQ는 백엔드가 붙지 않으므로 뺐다.

**이 테스트가 보증하는 범위를 과장하지 않는다.** `contextLoads()`는 Initializr
기본값 한 건이고 행동을 단언하지 않는다. 그래도 돌리는 이유는 컨텍스트 기동
실패가 이 프로젝트에서 **실제로 터진** 회귀 유형이기 때문이다
(`redisson-spring-boot-starter`가 Boot 4에서 `RedisProperties` 재배치로 기동
실패 → plain redisson + 수동 `@Bean`). 워크플로 헤더와 README에 같은 단서를 달았다.

## 결정 4: CI가 자연히 못 잡는 것 둘을 명시적으로 검사한다

- **`requirements.txt` ASCII 검사** — pip이 시스템 로케일 코덱으로 읽어서 한글
  주석이 cp949 환경의 설치를 깨뜨린다. **리눅스 러너는 UTF-8이라 그냥 통과한다.**
  명시적으로 확인해야 의미가 있다
- **`import ragas`** — `langchain-community<0.4` 핀을 풀면 ragas 0.4.x가 제거된
  `langchain_community.chat_models.vertexai`를 무조건 import해서 깨진다.
  **설치는 성공하고 import에서만 드러난다**

## 첫 실행이 곧바로 진짜 결함을 잡았다

`ai` 워크플로 첫 실행이 빨간불이었다. 원인은 CI 설정이 아니라 저장소다 —
**`mcp`가 `requirements.txt`에 없었다.** Phase 6에서 손으로 설치했고, 그 venv가
그대로 살아 있어서 이후 작업이 전부 선언 없이 돌아갔다. 새 클론에서는
`from mcp import Client`가 `ModuleNotFoundError`로 죽고 테스트 모듈 2개가 수집
단계에서 실패한다.

**오래 산 개발 환경은 빠진 선언을 감춘다.** 로컬에서 78건이 통과한다는 사실은
이 결함에 대해 아무 정보도 주지 않았다.

진단 과정에서 하나 더 나왔다. `redis`도 빠져 있는데 **이건 CI가 못 잡는다** —
`app/services/cache/dependencies.py`가 함수 안에서 지연 임포트하므로 수집이
통과한다. 하지만 시맨틱 캐시는 전 의도의 기본 경로(ADR-0012)라 새 클론의 첫
요청에서 죽는다. 같은 결함이므로 같이 선언했다.

> 진단은 CI 로그 없이 했다. 공개 저장소여도 Actions 로그 API는 admin 권한을
> 요구하고 `gh`가 설치돼 있지 않았다. 대신 **추적된 파일만 있는 새 클론을
> `python:3.11-slim` 컨테이너에 올려** 같은 조건을 재현했다 — 윈도우 로컬에서는
> 재현되지 않았으므로(`models/`·`.env` 없는 클론에서도 78건 통과) 리눅스 환경이
> 필요했다.

두 건 모두 트러블슈팅 문서로 남겼다. 종류가 다르므로 파일을 나눴다 —
**저장소 위생** 쪽은 [[의존성-선언-누락-오래된-venv]](지연 임포트 목록 포함),
**진단 방법론** 쪽은 [[ci-로그-접근-불가-컨테이너-재현]]이다. 후자는 의존성과
무관한 결함(경로 구분자·로케일·대소문자 등 "윈도우에서만 통과하는" 부류)에도
그대로 쓴다.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| **부하테스트를 스케줄(nightly)로** | 환경이 달라 수치가 비교 불가하고 걸 임계값이 없다. `live-llm`은 과금 |
| **셀프호스트 러너(오라클 박스)** | 측정 대상과 CPU를 공유한다. ADR-0019가 관측 스택을 선택 프로파일로 뺀 것과 같은 이유 |
| **`requirements-ci.txt`로 무거운 의존성 제외** | 전체 설치가 `langchain-community` 핀을 검증하는 유일한 수단이다. 실측 67초라 아낄 이유도 없다 |
| **GHA service containers** | `command`를 못 줘서 Redis에 `--requirepass`를 걸 수 없다 → 로컬과 다른 구성 |
| **`./gradlew build -x test`** | "build+test"라는 이름이 거짓이 된다. 컨테이너 16초면 충분히 싸다 |
| **k6 스크립트 문법 검사(`k6 inspect`)** | k6 설치가 붙는 것에 비해 얻는 게 적다 |

## 미룬 것 — "안 함"이 아니라 "선행 결정이 있다"

| 항목 | 선행 결정 |
|---|---|
| **RAGAS 품질 게이트** | 파인튜닝 임베딩·리랭커 ONNX가 gitignore라 새 클론에 없다. CI 재생성은 수 분 + LLM 호출(과금). **모델 아티팩트 배포 전략**이 먼저다 |
| **Docker 이미지 푸시** | 같은 문제 — 모델 없는 AI 이미지는 기동 즉시 실패한다. 레지스트리 선택도 미정 |

## 영향

- 커밋마다 **AI 78건 + 백엔드 빌드 + 프론트 빌드**가 자동 검증된다
- `backend/gradlew`에 실행 비트를 세웠다(`100644` → `100755`). 리눅스 클론에서
  `./gradlew`가 Permission denied로 죽던 상태였다 — CI가 아니었으면 계속 몰랐다
- 새 의존성을 추가할 때 `requirements.txt`에 선언하지 않으면 **이제 CI가 막는다**
- 부하테스트는 수동으로 남는다. 재검토 조건은 위에 적었다
