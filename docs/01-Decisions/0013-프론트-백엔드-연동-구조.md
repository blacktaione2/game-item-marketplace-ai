# ADR-0013: 프론트엔드는 dev proxy로 단일 오리진을 보고, 인증은 Phase 8까지 유보한다

## 상태

채택됨

## 배경

Phase 7에서 React SPA를 붙이면서 정할 것이 네 가지였다.

1. 백엔드가 **둘**이다 — Spring Boot(8080, 거래 트랜잭션)와 FastAPI(8000,
   AI 파이프라인). 프론트가 이 둘을 어떻게 나눠 부를 것인가
2. 인증을 지금 만들 것인가
3. 화면 범위
4. 에이전트 응답(7~25초)을 스트리밍할 것인가

착수 전 조사에서 전제를 두 개 정정해야 했다.

- **세션 기반 로그인은 존재하지 않는다.** `spring-boot-starter-security`
  의존성 자체가 없고, `X-Tenant-Id`/`X-User-Id` 헤더가 전부다. 컨트롤러에
  "인증(JWT) 도입 전까지의 임시 방편"으로 명시돼 있다. 따라서 "쿠키 유지 vs
  토큰 전환"이 아니라 "인증을 만들 것인가"가 실제 질문이었다.
- **PostgreSQL이 비어 있어 시연 시나리오가 끊겨 있었다.** 별도 문서로 정리했다
  (`docs/05-Troubleshooting/저장소-분리로-인한-id-공간-균열.md`).

## 결정

**1. Vite dev proxy로 단일 오리진을 만든다.**

```
/api/backend/*  →  http://localhost:8080
/api/ai/*       →  http://localhost:8000
```

브라우저는 오리진 하나만 보므로 **양쪽 서버에 CORS 설정을 추가하지 않는다.**
기존 서버 코드를 건드리지 않는다는 점이 결정적이었다. 배포 시에는 리버스
프록시가 같은 역할을 하며, 그건 Phase 8 배포 작업이다.

**2. 인증은 만들지 않는다.** 상단에 데모 사용자 드롭다운을 두고 선택한 id를
`X-User-Id`로 보낸다. 보안(per-tenant JWT claims, API Gateway, rate limiting)은
CLAUDE.md에 이미 **Phase 8 항목**으로 있으므로 거기서 한 번에 다룬다. Phase 7을
지금 인증에 쓰면 화면이라는 본 목적이 밀린다.

**3. 테넌트 식별자 이중화를 프론트가 흡수한다.** 백엔드는 `X-Tenant-Id: 1`
(Long), AI 서버는 `tenant_code: "nexon"`(str)을 쓴다. 프론트에 상수 하나를 두고
호출 대상에 따라 맞는 필드를 보낸다. **두 서버 중 어느 쪽도 고치지 않는다** —
근본 통일은 Phase 8 정리 대상이다.

> **후속 (2026-08-01, ADR-0023): 결정 2와 3은 대체됐다.**
> 인증이 들어오면서 `X-User-Id`/`X-Tenant-Id` 헤더는 **제거됐고**, 신원·테넌트는
> 서명된 JWT 클레임에서 온다. 드롭다운은 남았지만 이제 **서버가 그 사용자의
> 토큰을 발급**하고 이후 요청은 토큰으로 나간다.
>
> 결정 3의 "이중화를 프론트가 흡수한다"도 대체됐다 — 토큰이 `tenant_id`(Long)와
> `tenant_code`(str)를 **둘 다** 싣고 다니므로 출처가 하나가 됐고, `demo.ts`의
> 상수는 화면 표기용으로만 남았다. 결정 1(Vite proxy)과 4(TanStack Query)는
> 그대로 유효하다.

**4. 상태 관리는 TanStack Query만.** 전역 스토어(Redux/Zustand)를 두지 않는다.
이 앱의 상태는 거의 전부 서버 상태이고 클라이언트 상태는 데모 사용자 선택
하나라 `useState`로 충분하다.

**5. 스트리밍하지 않는다.** `/api/assistant`는 POST 단일 JSON이고, EventSource는
GET 전용이라 그대로 못 쓴다. `fetch` + `ReadableStream`으로 우회할 수는 있지만
FastAPI를 `StreamingResponse`로 바꾸고 에이전트 루프가 단계별 이벤트를
`yield`하도록 고쳐야 한다 — Phase 6 코드 수정이 붙는다. Phase 7은 진행 표시로
대신하고 스트리밍은 스트레치로 남긴다.

**6. 화면 3개.** `/`(어시스턴트+검색), `/items/:id`(상세+시세+거래),
`/anomalies`(GM 검토 큐). 관리자 CRUD 화면은 만들지 않는다 — 비용 대비 보여줄
게 적고 이 프로젝트의 차별점은 AI 파이프라인이다.

## 고려한 대안

1. **두 오리진 그대로 노출 + 양쪽에 CORS 설정** — 서버 두 곳을 고쳐야 하고,
   프리플라이트와 헤더 허용 목록을 양쪽에서 관리하게 된다. dev proxy가 같은
   결과를 코드 수정 0으로 낸다.
2. **Spring Boot가 FastAPI를 전부 프록시** — 진입점이 하나로 깔끔해지지만 AI
   응답이 JVM을 한 번 더 통과하고, `AiServerClient`의 타임아웃(2s/3s)이 에이전트
   응답(최대 25초)과 맞지 않아 그것부터 고쳐야 한다.
3. **지금 JWT 도입** — 실제 인증 흐름을 시연할 수 있지만 Phase 7이 백엔드
   작업으로 번진다. Phase 8에 이미 예정돼 있다.
4. **스트리밍(fetch + ReadableStream)** — UX는 낫지만 Phase 6 서버 코드 수정이
   전제다. 스트레치.

## 결과

- `frontend/` — Vite + React + TypeScript + React Router + TanStack Query +
  Recharts. 타입체크·빌드 통과.
- **끊겨 있던 시연 경로가 연결됐다.** 프록시를 통한 실측:

  ```
  GET  /api/backend/items/2      → 200  (+8 강화 롱소드, 재고 10)
  POST /api/ai/forecast          → 200  (history 30pts + forecast 7pts)
  POST /api/backend/items/2/purchase → 201, 재고 10 → 9
  POST /api/backend/items/24/bids    → 201
  GET  /api/ai/anomaly/alerts    → 200  (26,702건 중 알림 284건)
  ```

- **파이프라인 내부 동작을 화면에 배지로 노출했다** — 의도, 판정 근거,
  확신도, 에스컬레이션 여부, 캐시 적중/방식, LLM 호출 수, 도구 호출 트레이스.
  이게 Phase 6 작업이 눈에 보이는 유일한 지점이다.
- 캐시 배지는 **회귀 감지 장치**를 겸한다. Phase 6에서 고친 `llm_calls`
  오표시가 재발하면 화면에서 바로 드러난다(캐시 적중이면 반드시 0). 실측
  1회차 2 → 2회차 0으로 정상.
- 차트 색은 dataviz 스킬의 검증된 슬롯 1·2이고 `validate_palette.js`로
  라이트/다크 두 모드 전 항목 통과(인접 CVD ΔE 24.7 / 26.8, 기준 8).
