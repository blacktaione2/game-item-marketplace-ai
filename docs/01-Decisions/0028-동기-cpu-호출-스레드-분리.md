# ADR-0028: 동기 CPU 호출을 루프 밖으로 — 크기 2의 전용 풀

## 상태

채택됨. ADR-0026이 "적중 경로만 고쳤다"고 남겨둔 나머지를 처리한다.

## 배경

ADR-0026에서 캐시 적중 경로의 `encode_one`을 지연시켜 p95를 279 → 25.9ms로
낮췄다. 그때 명시적으로 적어둔 한계가 있다 — **`encode_one`·리랭커·KoELECTRA·
오토인코더가 전부 여전히 동기이고, 적중 경로에서만 하나를 뺐을 뿐**이라는 것.
로드맵에 `asyncio.to_thread`로 등록해뒀다.

## 착수 전 실측이 등록 내용을 세 군데 뒤집었다

먼저 각 호출을 **격리 측정**했다. 이 기계는 조용하지 않아서 두 번 돌린 값의
범위로 적는다.

| 호출 | 격리 median | 진입점 |
|---|---:|---|
| `rerank` (후보 20) | **103 ~ 189 ms** | async |
| `encode_one` | 28 ~ 40 ms | async |
| `classifier.predict` (KoELECTRA) | 17 ~ 35 ms | async |
| `build_timeline()` (최초 1회) | **2,343 ~ 3,372 ms** | 아래 |
| `detector.score` (26,702행 전체) | 9 ~ 12 ms | **sync def** |
| `detector.score` (1행) | **0.31 ms** | — |
| `predict_ratios` (LSTM) | **0.45 ms** | — |
| `run_in_executor` 왕복 | 0.211 ms (p95 0.35) | — |

**정정 1 — 대상 목록이 틀렸다.** 로드맵은 "임베딩·리랭커·KoELECTRA·오토인코더"를
동급으로 적었다. 오토인코더 점수 계산은 **0.31ms**, LSTM 추론은 **0.45ms**로
스레드 왕복 비용(0.211ms)과 같은 자리수다. **옮길 대상이 아니다.**

**정정 2 — 주범이 임베딩이 아니었다.** 등록할 때 든 근거는 `encode_one`
15.77ms인데, 같은 검색 요청 안의 `rerank`가 **그 4~5배**다. 가장 큰 블로커를
지목하지 않은 채 등록돼 있었다.

**정정 3 — `/api/anomaly/*`는 이미 루프를 막지 않는다.** 두 엔드포인트가
`async def`가 아니라 **`def`** 라서 FastAPI가 자체 스레드풀로 넘긴다. 반면
`detect_trade`는 `/api/assistant`(async)에서도 불리고, **그쪽에서만**
`build_timeline()`의 2.3~3.4초가 루프를 통째로 멈춘다. 같은 함수가 진입점에
따라 다르게 동작하고 있었다.

## 결정 1: `asyncio.to_thread`를 쓰지 않는다 — 전용 풀, 크기 2

등록된 항목의 이름 자체가 `asyncio.to_thread`인데 측정이 그걸 기각했다.
`to_thread`는 기본 실행기(`min(32, cpu+4)`)를 쓰고 그 값은 개발기 16 / 배포
대상 8이다. 같은 작업 8건을 워커 수만 바꿔 돌린 결과(12코어):

| 워커 | `encode_one` (torch) | `rerank` (ONNX RT) | `detector.score` (numpy) |
|---:|---:|---:|---:|
| 1 | 510 ms | 1,019 ms | 72.8 ms |
| 2 | 572 ms **(+12%)** | 823 ms **(−19%)** | 35.6 ms (−51%) |
| 4 | 943 ms **(+85%)** | 705 ms (−31%) | 27.3 ms (−62%) |

**torch는 스레드를 늘릴수록 느려진다.** 이미 내부적으로 코어 수만큼 intra-op
스레드를 쓰기 때문에 바깥 스레드를 늘리면 초과 구독이 된다. 검색 1건은
`encode` 1회 + `rerank` 1회이므로 절대시간으로 합산하면:

- 워커 2: `+62ms`(encode) `−196ms`(rerank) → **−134 ms 이득**
- 워커 4: `+433ms` `−314ms` → **+119 ms 손해**

기본 실행기 크기(8·16)는 **둘 다 손해 구간**이다. 그래서 크기를 우리가 정한다.
`app/core/threadpool.py` 한 곳이 유일한 이음매다(`record_response()`와 같은
원칙).

## 결정 2: 옮기는 기준선은 격리 median **5ms**

취향이 아니라 검증 도구의 분해능에서 나온다. 계측기는 10ms 티커이고, 한 틱의
절반보다 짧은 블로킹은 정상 지터와 구분할 수 없다 — 고쳐도 고쳤다는 걸 보일
방법이 없다. 게다가 왕복 비용이 0.211ms라 0.31ms짜리를 옮기면 순비용이 68%다.

## 결정 3: 동기 함수는 동기로 둔다

`encode_one`을 `async`로 바꾸면 `scripts/*`, `indexer.py`(대량 인덱싱), 학습
코드, MCP stdio 서버까지 따라 바뀐다. 그쪽엔 막을 루프가 없다. **async
파이프라인 안의 호출 지점만** 감쌌다.

부수적으로 `semantic_cache.lookup()`의 임베딩 콜러블이 async가 됐다. ADR-0026이
넣은 성질(**정확 일치면 호출 자체가 일어나지 않는다**)은 그대로다.

> **테스트는 콜러블을 일부러 동기로 유지했다.** `async def`로 쓰면 호출만으로는
> 코루틴이 생길 뿐이고 `await` 해야 터지므로, `embed()`를 부르고 기다리지 않는
> 구현을 통과시킨다. 동기 함수는 **호출되는 순간** 터져서 가드가 더 강하다.

## 판정선과 결과 — 하나는 실패했다

측정 전에 세 개를 등록했다.

### 판정선 1 (실패, 그리고 **판정선 쪽이 틀렸다**)

> `live-llm` 3VU 중 티커 **최대 지연 < 20 ms**

| | 유휴(부하 0) | 변경 전 | 변경 후 #1 | 변경 후 #2 |
|---|---:|---:|---:|---:|
| mean | 5.53 | 2.97 | 2.00 | 1.38 |
| p99 | 6.68 | 29.33 | **11.88** | **10.65** |
| **max** | **16.34** | 224.01 | **32.75** ✗ | **17.89** ✓ |
| 20ms 초과 | 0 | 49 / 3,700 | 1 / 3,688 | 0 / 3,612 |

**같은 코드에서 한 번은 실패, 한 번은 통과했다.** 원인은 판정선에 있다 —
20ms의 근거로 "틱 주기의 2배"를 댔는데 그건 계측기의 *설정값*이지 *분해능*이
아니다. 나중에 잰 유휴 대조군이 **부하 0에서 이미 16.34ms**다(Windows 타이머
분해능). 판정선은 잡음 바닥 위에 3.66ms만 남겨두고 있었고, 하필 3,600표본 중
하나로 결정되는 `max`에 걸려 있었다.

**판정선을 고쳐 통과시키지 않았다.** 결과를 보고 기준을 바꾸면 사전 등록의
의미가 없다. 실패로 기록하고, 판정선 설계 규칙을 새로 남겼다 —
[[검사-자체가-틀린-사례들]] 사례 4.

**그래서 채택 근거는 무엇인가.** 같은 표에서 흔들리지 않은 두 값이다:
**p99 29.33 → 11.88 / 10.65**, **20ms 초과 49건 → 1건 / 0건**. 두 실행 모두
같은 방향이고 크기도 비슷하다. 변경 후 p99(10.65~11.88ms)는 유휴 max(16.34ms)
보다도 낮다.

### 판정선 2 (통과)

> 풀을 거친 호출이 직접 호출 대비 **+20% 이내**

**같은 프로세스 안에서 A-B-A-B로 교대**했다(4라운드 × 12회 = 각 48표본). 격리
측정값을 기준으로 쓰지 않은 이유는 이 기계의 세션 간 편차가 크기 때문이다 —
같은 항목이 103ms와 189ms로 나왔다. `load/README.md`의 "세션 간 절대 비교 금지"와
같은 규칙이다.

| | 직접 median | 풀 경유 median | 차이 |
|---|---:|---:|---:|
| `encode_one` | 75.48 ms | 73.24 ms | **−3.0%** |
| `rerank(20)` | 109.79 ms | 108.64 ms | **−1.0%** |

페널티가 없다. (두 값 모두 격리 측정보다 큰데, 이 스크립트가 네 종류를 연달아
돌려 기계가 부하 상태이기 때문이다. 두 팔이 같은 조건이라 비교는 성립한다.)

### 판정선 3 (통과)

> `cache-warm` 불변, 테스트 118건 통과, 적중 시 `cache_encode` 부재

적중 경로는 이 변경을 지나지 않아야 한다. **같은 세션에서 코드를 되돌려가며**
쟀다(stash → 측정 → 복원 → 측정, 양쪽 다 k6로 워밍업 후).

| | 변경 전 | 변경 후 |
|---|---:|---:|
| 처리량 | 436.56 /s | **436.93 /s** |
| p95 | 26.23 ms | **24.92 ms** |
| `stage_cache_ms` median | 5.0 ms | 5.0 ms |

`ai_stage_duration_seconds_count{stage="cache_encode"}`는 적중 **4,578건 동안
4.0 → 4.0** 으로 증가가 없었다 — ADR-0026의 회귀 신호가 유지된다.
테스트는 118건 통과.

## 얻은 것과 얻지 못한 것

**처리량은 약속하지 않았고 늘지도 않았다.** 스레드로 옮긴다고 CPU 작업이
빨라지지 않으며, torch는 동시 실행에서 오히려 느려진다. 얻은 것은 **루프
응답성 하나**이고 판정선도 거기에 걸었다.

부수 효과 하나가 실제로 의미 있다: `settings.agent_tool_timeout_seconds`
주석이 "로딩이 동기라 이벤트 루프를 막는 동안은 타임아웃이 발동조차 못 한다"고
적어둔 상태였다. 임베딩·리랭커가 루프 밖으로 나가면서 **그 경로에 한해 타임아웃이
실제로 발동할 수 있게 됐다.**

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| `asyncio.to_thread` 그대로 | 기본 실행기 크기(8·16)가 측정상 손해 구간 |
| 풀 크기 1 | 리랭커의 −19%를 버린다. 페널티가 없다고 측정됐으므로 2를 유지 |
| 풀 크기 4 이상 | torch +85%. 4 OCPU 대상에서는 더 나쁘다 |
| 모든 동기 호출을 옮긴다 | 0.31ms·0.45ms짜리는 왕복 비용이 순손실 |
| `torch.set_num_threads()` 축소 | **단일 요청 지연을 바꾸는 별개 변경**이다. 별도 측정이 필요해 등록만 했다 |
| 전 함수를 async로 승격 | `scripts/*`·학습·MCP stdio가 전부 따라온다. 막을 루프가 없는 곳들이다 |

## 영향

- 검색 요청의 동기 블로킹(encode + rerank)이 루프에서 빠졌다. p99 티커 지연
  29.33 → 10.65~11.88ms
- `/api/assistant`의 첫 이상거래 질의가 더 이상 루프를 2.3~3.4초 멈추지 않는다
- **처리량 수치는 이 변경으로 갱신되지 않는다.** ADR-0026의 316 req/s는 적중
  경로 수치이고 이 변경은 적중 경로를 지나지 않는다(위 표에서 확인)
- 새 동기 CPU 호출을 추가할 때는 `run_cpu`로 감싸되, **격리 median 5ms 미만이면
  감싸지 않는다**

## 남은 위험 — 트리거를 명시한다

**FastAPI 자체 스레드풀(anyio, 기본 40)과 이 전용 풀이 동시에 CPU를 쓰면 초과
구독이 된다.** `/api/anomaly/*`가 anyio 쪽으로 가기 때문이다. 지금은 두 경로가
겹칠 일이 없어 두고 본다.

> **재착수 트리거**: `/api/anomaly/*`가 데모 조회를 벗어날 때 — 구체적으로
> **k6에 검색과 이상거래를 섞는 프로파일이 생기거나**, 두 경로의 동시 요청이
> 실측될 때. 그때 **첫 조치는 전용 풀 확대가 아니라 anyio 상한을 내리는 것**
> (`anyio.to_thread.current_default_thread_limiter().total_tokens`) — 총 스레드
> 수가 문제지 이 풀이 작아서 생긴 문제가 아니다.

`build_timeline()`의 `lru_cache`는 원자적이지 않아 두 스레드가 동시에 진입하면
2.3초를 두 번 쓴다. 결과는 같으므로 두고 본다.

## 설계안에 있었는데 하지 않은 것

`app/main.py`에 lifespan을 추가해 풀을 `shutdown` 하기로 했었다. **하지 않았다** —
`ThreadPoolExecutor`가 인터프리터 종료 시 워커를 join하는 atexit 훅을 이미
등록하므로, 그 lifespan은 동작을 바꾸지 않는 코드다.
