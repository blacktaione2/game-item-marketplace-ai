# ADR-0010: Intent Router는 룰 우선 2단 구조로 하고, 애매하면 에이전트로 보낸다

## 상태

채택됨

## 배경

Phase 0~5로 검색·시세예측·이상탐지가 완성됐지만 각각 별도 엔드포인트로만
존재했다. 사용자가 어느 엔드포인트를 부를지 알아야 했고, 여러 기능이 필요한
질문은 답할 수 없었다.

기획서는 "룰 기반 우선 분기 → 애매한 요청만 KoELECTRA"를 명시하고 있다.
구현에 들어가면서 정할 것은 세 가지였다: 진입점 구조, 경계 케이스 처리,
그리고 **KoELECTRA가 실제로 값을 하는지 어떻게 확인할 것인가**.

## 결정

**1. 기존 엔드포인트를 대체하지 않고 앞에 선다.** 새 진입점
`POST /api/assistant`를 추가하고 `/api/search`·`/api/forecast`·
`/api/anomaly/*`는 그대로 뒀다. 기존 엔드포인트는 디버깅용으로 계속 유효하고,
무엇보다 **MCP 도구가 감쌀 대상**이다(ADR-0011). 없애면 도구 레이어가 감쌀 게
사라진다.

**2. 의도 6종.** 기획서 분기와 1:1이다 — `faq_smalltalk`, `item_search`,
`price_forecast`, `anomaly_check`, `compound`, `unknown`.

**3. 애매하면 `compound`로 보낸다.** "이 아이템 적정가야?"가 검색인지
시세예측인지 억지로 가리지 않는다. 애매하다는 것 자체가 "도구 하나로는
부족"이라는 신호이므로 에이전트가 도구를 스스로 고르게 한다. 오분류(엉뚱한
답)의 비용이 에이전트 경로 비용(느리고 비쌈)보다 크다.

**4. 학습은 LLM 생성, 평가는 수작업.** Phase 4 방법론(ADR-0007)을 그대로
적용했다. 평가셋 60건과 경계 발화 20건을 전부 손으로 썼고, LLM이 잘 만들지
않는 형태를 일부러 넣었다(초성 `ㅎㅇ`/`ㄱㅅ`, 조사 생략 `사용법좀`, 은어
`먹튀`, 축약 `~임?`).

**5. 룰 단독이 기준선이다.** Phase 5의 나이브 기준선, Phase 5-2의 `max |z|`
규칙과 같은 역할. **평가셋 오답을 보고 룰을 고치지 않았다** — 고치면 기준선이
부풀고 비교가 오염된다.

## 고려한 대안

1. **KoELECTRA 단독 라우팅** — 아래 결과대로 룰(80%)에 크게 못 미친다(58%).
   룰이 잡는 명시적 표현을 굳이 모델에 맡길 이유가 없다.
2. **LLM으로 의도 분류** — 정확도는 높겠지만 모든 요청에 LLM 왕복이 붙는다.
   "요청 유형별로 비용을 통제한다"는 계획서의 핵심 목표와 정반대다.
3. **애매한 질의를 되묻기** — 대화 턴이 늘고, 에이전트가 어차피 검색부터
   시작할 수 있으므로 대부분 되물을 필요가 없다.
4. **koelectra-base(110M)** — small(14M)이 룰을 못 이기는 것이 모델 용량
   문제가 아니라 학습 데이터의 스타일 편향 때문으로 보여(아래) 키울 근거가
   약하다. 실사용 로그 확보 후 재검토.

## 결과

수작업 홀드아웃 60건 기준.

| 방법 | 정확도 |
|---|---|
| 룰 단독 (기준선) | 80.0% |
| **분류기 단독** | **58.3%** |
| 2단 라우터 (배포) | **86.7%** |

경계 발화 20건 중 **15건이 `compound`로 에스컬레이션**됐다.

### KoELECTRA는 룰을 못 이긴다 — 그리고 그 이유가 중요하다

분류기 단독 58.3%는 룰 80%에 한참 못 미친다. 그런데 **LLM 생성 데이터에서
떼어낸 검증 조각에서는 94.5%가 나왔다.** 같은 모델이 LLM 말투에서는 94.5%,
사람이 쓴 말투에서는 58.3%다.

이 36%p 격차가 Phase 4에서 "스타일 적응분"이라고 불렀던 것의 정체다. 그때는
개선폭 차이(+0.209 vs +0.146)로 간접 추정했는데, 여기서는 같은 모델의 정확도가
평가셋 출처에 따라 반토막 나는 형태로 직접 드러났다. **평가셋을 손으로 써야
하는 이유의 가장 선명한 증거다.**

그럼에도 2단 라우터가 86.7%로 기준선을 4건 앞선다. 룰이 확신하는 구간은 룰이
처리하고, 룰이 기권한 10건에서만 분류기가 개입하기 때문이다. 분류기의 가치는
정확도가 아니라 **커버리지 보완**에 있다.

### 남은 오답은 안전한 방향으로 치우쳐 있다

2단 라우터의 오답 8건 중 6건이 `compound`로 빠진 것이다. 에이전트가 여전히
정답을 낼 수 있으므로 느리고 비쌀 뿐 틀린 답은 아니다. 초기 버전에서
`"이 거래 사기 아니야?"`가 FAQ로 분류돼 정적 문구를 뱉던 것과 비교하면
실패의 성격이 다르다.

## 알려진 한계

### 1. 확신도는 교정되어 있지 않다

첫 학습(스무딩 없이 손실 0.013까지)에서 **오답의 확신도 중앙값이 0.978로
정답(0.991)과 사실상 구분되지 않았다.** 경계 발화 20건 전부를 0.99 확신도로
특정 클래스에 배정해 에스컬레이션이 0/20이 됐다.

임계값 조정으로는 못 고친다 — 분리 자체가 없기 때문이다. 그래서 두 가지를
했다.

- **모호한 발화를 `compound`로 직접 학습**시켰다(LLM 생성 108건). 애매함을
  확신도에서 유도하지 않고 클래스로 가르친 것이다. `compound`는 언어 형태가
  아니라 "취할 행동"으로 정의되므로 의미상 모순이 없다.
- **레이블 스무딩 0.1** 적용.

에스컬레이션이 0/20 → 15/20으로 회복됐지만, **근본적으로 softmax 확신도를
신뢰할 수 없다는 사실은 그대로다.** 임계값 0.70은 그 상태에서의 잠정치다.

### 2. 룰이 확신해서 틀리는 4건

경계 발화 중 4건(`"이거 얼마?"`, `"가격 어때"` 등)은 룰이 확신해 분류기를
거치지 않는다. 다만 실행 단계에서 **분기가 스스로 물러선다** — 시세 분기는
대상을 특정할 수 없으면 `compound`로 올린다. 라우터를 완벽하게 만드는 대신
분기가 실행 가능성을 스스로 확인하게 한 것이고, 실제로 그렇게 동작한다.

### 3. 측정 범위

- 홀드아웃 60건은 작다. 86.7%는 52/60이고 한 건이 1.7%p다.
- 실사용 로그가 없다. 수작업 평가셋도 결국 내가 상상한 사용자 말투다.
- 단일 실행이며 시드 분산을 재지 않았다.
