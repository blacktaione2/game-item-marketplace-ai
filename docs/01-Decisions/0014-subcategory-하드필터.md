# ADR-0014: 카테고리 혼입은 `subcategory` 하드 필터로 막는다 (리랭커 점수 하한은 측정 결과 기각)

## 상태

채택됨.

> **2026-07-31: 이 문서의 리랭커 하한 기각은 ADR-0018로 대체됐다.**
> 기각 사유(입력 노이즈 > 마진)의 원인이 `temperature` 미설정이었고
> (ADR-0017), 고친 뒤 재측정하니 산포가 1.3 → 0.319로 내려가 10회 수집이
> 전부 같은 결론을 냈다. **쓸 수 있는 쪽은 아래에서 의심했던 절대 하한이었고,
> 대안으로 여겼던 상대 낙폭이 오히려 실패했다.** `subcategory` 하드 필터
> 채택(이 문서의 본 결정)은 그대로 유효하다.

## 배경

Phase 7에서 화면을 붙이자 문제가 눈에 보였다.

> `"5만원 이하 검 찾아줘"` → +9/+8/+7 강화 롱소드, 미스릴 단검,
> **+8 강화 스틸 해머**, **초심자용 단궁(활)**

`category` 필드가 `무기`까지밖에 없어서 검/활/지팡이를 구분할 수단이 없었다.
두 후보가 있었다.

| 후보 | 성격 | 비용 |
|---|---|---|
| A. 리랭커 점수 하한 | 필터링 로직 | 코드 몇 줄, 재색인 불필요 |
| B. `subcategory` 하드 필터 | 데이터 스키마 | 매핑 변경 + 42건 재색인 |

처음에는 **A를 먼저** 하기로 했다. 근거는 "리랭커가 이미 `초심자용 단궁`을
최하위(−4.15)로 판정하고 있으니 자르는 기준만 두면 된다"였고, 변경 범위가
작다는 점도 컸다.

## A를 측정해서 기각했다

수작업 질의 10건(튜닝 5 / 홀드아웃 5) × 상위 8건 = 70건에 적합/부적합을
라벨링해 측정했다(`scripts/evaluate_rerank_floor.py`,
`app/corpus/rerank_floor_queries.py`).

**같은 스크립트를 두 번 돌렸는데 홀드아웃 판정이 뒤집혔다.**

| 실행 | 튜닝 적합 최솟값 | T | 홀드아웃 적합 잘림 |
|---|---|---|---|
| A | −3.59 | −4.09 | **1건 (실패)** |
| B | −3.71 | −4.21 | 0건 (통과) |

원인은 **LLM 질의 재작성의 비결정성**이었다. `"5만원 이하 검"`이 실행마다
`"검 소드 대검"` 또는 `"검 소드 대검 단검"`으로 재작성되고, 토큰 하나 차이로
`미스릴 단검` 점수가 **1.31점** 이동했다(−3.66 ↔ −2.35). 리랭커 자체는
결정론적이다(같은 재작성 질의로 3회 반복 시 소수점까지 동일).

재려던 적합/부적합 마진이 **0.3~0.6**인데 입력 노이즈가 **0.5~1.3**이다.
신호보다 노이즈가 크면 어떤 임계값도 "이번 실행에서는 맞았다" 이상이 못 된다.
상대 낙폭(1위 대비)도 홀드아웃에서 적합 3건을 잘라 더 나빴다.
→ `docs/05-Troubleshooting/비결정적-입력-위의-임계값.md`

> **2026-07-31 원인 정정 (ADR-0017).** 이 비결정성을 여기서 LLM의 특성처럼
> 서술했는데, 실제 원인은 **`temperature`를 API에 한 번도 안 넘긴 것**이었다.
> 생략하면 OpenAI 기본값 1.0이 적용된다. 0으로 두니 토큰집합 모드 일치율이
> 0.840 → 0.990으로 올랐다. **이 ADR의 결정(하드 필터 채택)은 유지된다** —
> 임계값이 필요 없다는 장점은 그대로고, 재작성이 안정된 지금도 완전 재현은
> 아니다(1/10). 다만 **리랭커 하한은 이제 재측정 대상**이다(로드맵 5번).

**이전 진단도 함께 정정한다.** "리랭커는 이미 올바르게 판정하고 있다"는 n=1
관찰이었다. 질의를 늘려 보니 `"단검 보여줘"`에서 `전설 등급 대검`(−3.11)·
`+8 롱소드`(−3.35)·`+9 롱소드`(−3.40)가 정답인 `미스릴 단검`(−3.64)보다
**위에 있었다.** 순위 자체가 뒤집힌 경우에는 하한이 원리적으로 무력하다.

## 결정

**B를 채택한다 — `subcategory` keyword 필드 + 하드 필터.**

`subcategory`의 결정적 장점은 **임계값이 없다**는 것이다.
`subcategory == "활"`은 실행마다 흔들리지 않는다. 재색인 비용이 있는 대신
캘리브레이션이 필요 없다.

**"작은 변경"이 "안전한 변경"은 아니었다.** A는 코드 몇 줄이지만 그 변경을
안전하게 하려면 임계값을 정할 수 있어야 하고, 그게 안 되면 변경 크기는
의미가 없다.

### 분류 체계

사용자가 실제로 필터하는 층위로 잡았다.

| category | subcategory |
|---|---|
| 무기 | 검(7) · 지팡이(4) · 활(4) · 둔기(3) · 창(1) |
| 방어구 | 갑옷(6) · 방패 · 신발 · 로브 · 모자 · 각반 |
| 장신구 | 반지 · 목걸이 · 팔찌 · 귀걸이 |
| 소모품 | 물약(2) · 주문서(2) · 재료 |
| 계정 / 재화 | 계정(2) / 재화 |

**단검·대검은 `검`에 넣었다.** 그보다 잘게 쪼개면 `"검 찾아줘"`가 단검을
놓친다. 대신 `"단검만"` 같은 더 세밀한 질의는 여전히 텍스트 신호에 의존한다
(아래 한계 참고).

### 구현

- `app/corpus/{train,eval}_items.py` — 42건 전부에 `subcategory` 부여
- `search/mapping.py` — `keyword` 필드 추가
- `search/filters.py` — `SearchFilters.subcategory` → `term` 절
- `search/query_understanding.py` — 스키마·표기 대응·예시 추가.
  **종류를 특정할 수 없는 질의는 `null`로 두라**고 명시했다 — 억지로 채우면
  맞는 결과까지 걸러진다
- `corpus/__init__.py` — 임포트 시점 가드. `subcategory`가 빠진 아이템은
  종류 필터가 걸린 검색에서 **조용히 사라지므로** 그 자리에서 터뜨린다
  (실제로 발동하는지 충돌을 주입해 확인했다)
- MCP 도구 출력과 프론트 결과 카드에도 노출 — 이름만 보고 모델이 활을 검이라
  단정한 전례가 있어, 종류를 주면 스스로 검증할 수 있다

## 결과

같은 평가셋 재측정:

| | 이전 | 이후 |
|---|---|---|
| 부적합 결과 | 50건 | **26건** (−48%) |
| 적합 결과 | 20건 | **20건** (손실 0) |

질의별로:

| 질의 | 결과 |
|---|---|
| `"5만원 이하 검 찾아줘"` | **검 4건만.** 단궁·해머 제거 |
| `"100렙 이상 활 찾아줘"` | **바람의 장궁 1건만.** 대검·지팡이·암살검 제거 |
| `"마법사가 쓸 지팡이 추천"` | 지팡이 4건 전부 |
| `"싼 아이템 추천"` | `subcategory=null` 정상 — 억지로 채우지 않았다 |

부수 효과로 `"단검 보여줘"`에서 `미스릴 단검`이 1위(−0.31)로 올라왔다.
다만 **이건 필터 효과인지 재작성 변동인지 분리되지 않았다** — 위 비결정성
때문에 단정할 수 없다.

## 고려한 대안

1. **리랭커 점수 하한** — 위와 같이 측정해서 기각. 질의 재작성이 결정론적으로
   바뀌면 다시 후보가 된다(로드맵에 착수 조건으로 등록).
2. **더 잘게 쪼갠 분류(단검/대검/롱소드 분리)** — `"검 찾아줘"`가 단검을
   놓친다. 사용자가 필터하는 층위가 아니다.
3. **프롬프트로 LLM에게 걸러내게 하기** — 이미 시도했고 **불안정하다.**
   같은 프롬프트가 `"3만원 이하 불속성 검"`에서는 스스로 짚었지만
   `"5만원 이하 검"`에서는 단궁을 검 목록에 넣었다. 완화책이지 해법이 아니다.

## 알려진 한계

### 1. 속성(불속성/얼음속성) 조건은 여전히 텍스트 신호다

`"3만원 이하 불속성 검"`은 이제 **검류만** 돌려주지만 그중 불속성은 **한 건도
없다.** 코퍼스의 불속성 아이템(불꽃의 마법봉 33,000원 / 불꽃의 대검
143,000원)이 전부 3만원을 넘어 조건을 만족하는 것이 애초에 없기 때문이다.

같은 메커니즘(`element` keyword 필드 + 하드 필터)으로 풀 수 있고 재색인도
한 번이면 되지만, 이번 범위에 넣지 않았다. 로드맵에 등록.

### 2. "조건 만족 결과 없음"을 여전히 말하지 않는다

하드 필터가 걸리면 ES가 0건을 반환할 수 있게 되어 **탐지 가능해졌지만**,
위 예시처럼 필터를 통과하는 항목이 있으면 여전히 근사치가 나간다. 속성 필터
(한계 1)가 들어가면 이 질의는 0건이 되고, 그때 "없다"고 말하는 처리가 필요하다.

### 3. 더 세밀한 종류 질의

`"단검만 보여줘"`는 `subcategory=검`으로 필터되어 롱소드·대검이 같이 나온다.
분류 층위를 사용자 필터 기준으로 잡은 대가다.

### 4. 측정 범위

평가셋이 질의 10건 / 라벨 46~70건으로 작다. 그리고 **질의 재작성 비결정성이
해결되지 않아** 이 수치들도 시행 간 분산을 갖는다 — 부적합 50→26 같은 큰 변화는
분명하지만 소수점을 신뢰할 크기는 아니다.
