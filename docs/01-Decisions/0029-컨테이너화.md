# ADR-0029: 컨테이너화 (9a) — nginx가 단일 오리진을 재현하고, 모델은 볼륨에 둔다

## 상태

채택됨. **9a(로컬 x86에서 완결)까지다.** ARM 이미지와 실배포는 9b로 나눴다.

## 배경

Phase 8까지 끝났는데 **앱 Dockerfile이 하나도 없었다.** `docker-compose.yml`은
인프라 4종(Postgres · ES · Redis · RabbitMQ)만 띄우고, Spring · FastAPI · React는
전부 로컬 프로세스로만 돌았다. 배포 대상(Oracle Cloud ARM 4 OCPU)에 올린 적이
없다.

착수 전 실측:

| 항목 | 현재 |
|---|---|
| 앱 Dockerfile | **0개** |
| 모델 총량 | **650 MB** (임베딩 466 · 리랭커 130 · 라우터 55) |
| 단일 오리진 | **Vite dev proxy에만 존재** |
| 프론트 절대 URL | 0건 (상대 경로만) — 프록시가 그대로 먹는다 |

**임베딩 466MB는 낭비가 아니다.** `paraphrase-multilingual-MiniLM-L12-v2`는
XLM-R 토크나이저(25만 어휘)를 써서 임베딩 행렬만 `250,002 × 384 = 9,600만`
파라미터다 — 트랜스포머 본체(2,100만)의 4배다. 줄이려면 어휘를 잘라야 하고
그건 모델 동작을 바꾸므로 측정이 필요하다. 범위 밖으로 등록만 했다.

## 결정 1: nginx가 SPA를 서빙하고 두 서버를 프록시한다

CORS를 넣지 않은 근거가 그동안 "dev proxy가 단일 오리진을 만든다"였는데,
배포하면 그 근거가 사라진다.

| 안 | 대가 |
|---|---|
| **nginx 리버스 프록시** | 컨테이너 하나 추가. **두 서버 코드 무변경** |
| 두 서버에 CORS 추가 | 여섯 단계 동안 안 건드린 서버 코드를 배포 때문에 건드린다. 프리플라이트·인증 헤더 허용까지 따라온다 |

경로 규칙은 `vite.config.ts`와 **같아야 한다** — 어긋나면 개발에서는 되고
배포에서만 깨진다.

**덤으로 배포하면 바로 터질 문제 하나가 같이 해결됐다**: `try_files $uri
/index.html`이 없으면 `/items/3`을 새로고침할 때 404다. dev 서버가 가려주고
있어서 안 보이던 결함이다.

## 결정 2: 모델 650MB를 이미지에 넣지 않는다

| 안 | 대가 |
|---|---|
| **볼륨 + `ai-init` 컨테이너** | 첫 기동 전 준비 1회. **README가 이미 그렇게 안내한다** |
| 이미지에 포함 | torch까지 합쳐 2GB 이상. ARM 크로스빌드·전송이 그만큼 느려지고, 모델을 바꿀 때마다 이미지를 다시 만든다 |

`ai-init`은 커밋된 학습 데이터(`ai/data/`)로 모델 5종을 만들고 ES를 색인한다.
**LLM을 부르지 않는다.** 이미 있으면 건너뛴다 — 아니면 `up` 할 때마다 재학습한다.

## 결정 3: 기본 프로파일을 바꾸지 않는다

앱은 `--profile app`에 둔다. **자원 절약이 아니라 의미 보존이다.**
`docker compose up -d`는 지금까지 "인프라만"이었고 README · CLAUDE.md ·
CI backend 워크플로가 전부 그 전제 위에 있다. 여기에 앱을 끼우면 그 명령의
뜻이 조용히 바뀐다.

**로컬 프로세스 개발이 여전히 1급 경로다.** 컨테이너는 "배포하면 뜨는가"를
확인하는 경로이지 개발 루프가 아니다(HMR을 잃는다).

## 결정 4: 기동 순서 — `service_healthy`로는 절반만 된다

준비 상태가 세 층인데 healthcheck는 첫 층만 답한다.

| 층 | 무엇이 답하나 | 없으면 |
|---|---|---|
| 프로세스가 연결을 받는가 | healthcheck (인프라 4종에 이미 있었다) | backend 부팅 실패 |
| 스키마가 있는가 | backend가 부팅하며 생성 | — |
| **데이터가 있는가** | **아무도 자동으로 안 한다** → `ai-init` / `db-seed` | 기동은 되는데 검색 0건, 상세 빈 값 |

세 번째가 빠지면 **실패가 아니라 "조용히 이상함"** 으로 나타나 더 나쁘다.

순서가 두 갈래다:

```
인프라 healthy ─┬─► ai-init (모델 5종 → ES 색인) ─► ai ─┐
                └─► backend (스키마 생성) ─► db-seed ───┴─► web
```

**`seed-demo.sql`은 `ai-init`에 합칠 수 없다** — 테이블을 backend가 만들기
때문에(`ddl-auto: update`) backend가 healthy가 된 뒤에만 가능하다.

> **의존성으로 못 막는 것이 하나 있다.** AI 서버의 Redis 연결은 지연 연결이라
> Redis가 죽어 있어도 기동은 성공하고 첫 요청에서 드러난다. `depends_on`을
> 걸되 그게 보호막이라고 믿으면 안 된다 — 그 경로를 지키는 것은 리미터의
> fail-open과 캐시의 try/except다(ADR-0024).

## 판정선 — 새로 만들지 않고 기존 이진 기준을 재사용했다

컨테이너화는 성능 작업이 아니다. p95를 걸면 도커 오버헤드를 잰다.

| # | 기준 | 결과 |
|---|---|---|
| 1 | `/api/assistant` 4분기(FAQ·검색·시세·이상거래) 전부 응답 | **통과** |
| 2 | `load/run.sh purchase contended`의 오버셀 0 단언 | **통과** — 재고 감소 5,295 = 성공 5,294 + 워밍업 1 |
| 3 | `/items/3` 새로고침이 404가 아님 | **통과** (200) |
| 4 | 두 서버가 CORS 헤더를 내지 않음 | **통과** — 단, 검사를 먼저 고쳐야 했다(아래) |

판정 1이 의미 있는 이유는 **네 분기가 서로 다른 자원을 쓰기 때문**이다 —
정적 응답 / ES+임베딩+리랭커+LLM / LSTM / 오토인코더+26,702건 코퍼스.
하나라도 볼륨에서 빠졌으면 그 분기만 실패한다.

> **처리량은 비교하지 않는다.** 컨테이너에서 172.66 req/s가 나왔지만
> ADR-0020의 105.9 req/s와 **세션도 환경도 다르다.** `load/README.md`의
> "세션 간 절대 비교 금지"가 여기에도 적용된다.

## 이 라운드의 진짜 산출물 — 신선한 환경이 드러낸 결함 4건

컨테이너가 뜬 것보다 **뜨기까지 드러난 것**이 값어치 있었다.

| # | 결함 | CI가 잡을 수 있었나 |
|---|---|---|
| 1 | `finetune_embedding`이 **자기 출력물을 베이스로** 사용 → 새 환경에서 401 | **아니오** |
| 2 | `evaluate_embedding`·`compare_eval_sets`가 **모델을 자기 자신과 비교** | **아니오** |
| 3 | `accelerate` 선언 누락 (세 번째 사례) | **아니오** |
| 4 | 판정 4의 검사가 **404 경로를 보고 있어 CORS를 켜도 통과** | — (내가 만든 검사) |

1·2는 [[출력-경로를-입력으로-쓴-설정값]], 3은 [[의존성-선언-누락-오래된-venv]],
4는 [[검사-자체가-틀린-사례들]]에 각각 남겼다.

**2번이 가장 위험하다.** 죽지 않고 "개선폭 0"이라는 그럴듯한 숫자를 낸다.
Phase 4 수치(Recall@1 0.148 → 0.389)가 틀렸다는 뜻은 아니다 — 당시엔
`EMBEDDING_MODEL` 환경변수로 스톡 모델을 가리켜 쟀을 것이다. 틀린 건
**커밋된 상태의 재현성**이다.

**4번은 실패 케이스를 안 돌렸으면 "CORS 검증 통과"라고 적고 넘어갔을 것이다.**
일부러 CORS를 켜고 돌렸더니 통과했고, 그제서야 `/api/ai/health`가 404라는 걸
알았다(AI 서버의 헬스는 `/health`다). 고친 검사는 **404면 실패로 보고**한다 —
대상에 닿았는지를 확인하지 않는 검사는 아무것도 확인하지 않는다.

부수적으로 `load/run.sh`도 고쳤다. 스위트 이름을 검증하지 않아서
`backend contended`(존재하지 않는 이름)가 조용히 **AI 부하**로 돌았다 —
실수가 OpenAI 과금으로 이어지는 구조였다. 이제 거절한다.

## 알려진 동작 변화 — IP 키 한도가 하나로 합쳐진다

`/api/auth/demo-token`은 IP 단위 30회/분인데, 프록시를 거치면 백엔드가 보는
`remote_addr`이 **전부 nginx**라서 30회/분이 배포 전체의 합계가 된다.

**ADR-0024가 `X-Forwarded-For`를 안 읽기로 한 근거는 "신뢰할 수 있는 리버스
프록시가 전제되지 않으면 스푸핑으로 우회할 수 있다"였는데, 이번 배포로 그
전제가 생겼다.** 즉 조건이 바뀌었다.

그럼에도 이번 범위에서 고치지 않았다 — XFF를 읽으려면 "프록시 IP에서 온
요청일 때만 신뢰"가 같이 필요하고 그건 보안 경로 변경이라 별도 측정과 실패
케이스가 붙어야 한다. 데모 배포에서 30회/분 공유는 실사용(사용자 전환당
1~2회)에 지장이 없다.

> **트리거**: 여러 사용자가 동시에 쓰는 배포가 생기거나, `rate.limited{scope=demo-token}`이
> 실제로 관측될 때. 그때 nginx에 XFF를 추가하고 백엔드가 **프록시 IP에서 온
> 것만** 신뢰하도록 같이 바꾼다. 지금 nginx는 **일부러 XFF를 만들지 않는다** —
> 헤더가 있으면 누군가 그걸 읽는 순간 구멍이 열린다.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| 두 서버에 CORS 추가 | 배포 때문에 서버 코드를 건드린다. nginx면 무변경이다 |
| 모델을 이미지에 포함 | 2GB+, ARM 전송이 느려지고 모델 변경마다 재빌드 |
| 앱을 기본 프로파일에 | `docker compose up -d`의 의미가 바뀐다. CI·문서가 그 전제 위에 있다 |
| 컨테이너로 개발 | HMR을 잃는다. 컨테이너는 검증 경로이지 개발 루프가 아니다 |
| p95 목표를 판정선에 | 도커 오버헤드를 재게 된다. 컨테이너화는 성능 작업이 아니다 |

## 영향

- 이미지 3종: backend 599MB · ai 613MB · web 74.5MB
- `docker compose --profile app up -d` 하나로 전체가 뜬다
- **부하 하네스가 계속 동작한다** — backend 8080, ai 8000을 프록시 뒤에서도
  직접 노출했다. 막으면 `snapshot_metrics.py`가 빈 차분을 내지 에러를 내지 않는다
- 완화 프로파일도 기동 인자로 넘어간다(`SPRING_PROFILES_ACTIVE=loadtest`) —
  파일에 남지 않는다는 ADR-0024의 원칙 유지
