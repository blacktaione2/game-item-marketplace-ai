# ADR-0033: 배포 전 점검 — 무인증 LLM 경로와 붙이지 않은 XFF

## 상태

채택됨. **공개 배포 직전 전체 점검에서 나온 차단 결함 2건 + 죽은 검사 4건**을
고친 라운드다. 새 기능은 없다.

## 배경

"배포 전 마지막 전체 점검"으로 시작했다. 테스트는 초록이었고(AI 121 · 백엔드 42),
시크릿도 깨끗했고, JWT 검증·`SecurityConfig`·예외 처리·actuator 노출은 모두
견고했다. **그럼에도 공개하면 안 되는 상태였다.**

두 결함 다 **개별 라운드의 판정선을 전부 통과한 코드**에서 나왔다. 그게 이 ADR의
핵심이다 — 판정선은 그 라운드가 바꾼 것을 검사하지, 라운드 사이에 벌어진 틈을
검사하지 않는다.

## 결정 1: `/api/llm/test` 를 **제거한다**

Phase 2의 OpenAI 왕복 확인용 엔드포인트에 **인증 의존성이 없었다.**

nginx는 `/api/ai/*` 를 그대로 넘긴다. 즉 공개 포트에서 바로 닿는다.

| 경로 | 토큰 없이 |
|---|---|
| `POST /api/ai/assistant` | 401 |
| `POST /api/ai/search` | 401 |
| `POST /api/ai/forecast` | 401 |
| `POST /api/ai/anomaly/detect` | 401 |
| `GET /api/ai/anomaly/alerts` | 401 |
| **`POST /api/ai/llm/test`** | **200** |

```
$ curl -X POST http://localhost/api/ai/llm/test -d '{"prompt":"Reply with the single word OPEN"}'
{"provider":"openai","response":"OPEN"}
```

**익명 요청이 임의 프롬프트를 OpenAI로 보냈고 과금은 이쪽에 붙는다.** ADR-0031이
세운 비용 방어 3계층(토큰 요구 · 20회/분 · 50회/일)을 **전부 우회한다** — 그
계층들이 전부 `/api/assistant` 에 걸려 있기 때문이다.

인증을 붙이는 대신 **지운다.** 운영 경로가 아니고, 연동 확인은 `/health` 와
`/api/assistant` 가 대신한다. 참조하는 코드·테스트·프론트가 하나도 없었다.

### 라우터를 지우는 것으로는 부족하다

**결함의 원인은 그 파일이 아니라 방식이다.** 인증을 경로마다 `Depends` 로 붙이면
**빠뜨려도 아무 신호가 없다.** 다음에 라우터를 추가하면서 잊는 것도 똑같이
조용하다. 그래서 개별 경로가 아니라 성질을 고정한다:

`ai/tests/test_route_auth_coverage.py` — **인증 의존성이 없는 경로가 존재하지
않는다.** 면제는 `/health`·`/metrics` 둘뿐이고 각각 사유가 붙어 있다.

> **이 검사도 한 번 틀렸다.** 처음 작성본은 `app.routes` 를 한 겹만 훑었는데, 이
> FastAPI 버전(0.140)은 `include_router` 한 라우터를 `_IncludedRouter` 로 감싸
> 평탄화하지 않는다. **경로를 0개로 세고 통과**했다 — 함께 넣은
> `test_there_is_something_to_check` 가 아니었으면 **항상 통과하는 검사**를 그대로
> 넣을 뻔했다. 사례집(`검사-자체가-틀린-사례들`)의 "침묵" 분류 그대로다.

뮤테이션으로도 확인했다. 무인증 라우트를 인메모리로 주입하니 가드가
`['POST'] /api/llm/test` 1건을 잡았고, 복원 후 0건으로 돌아왔다.

## 결정 2: nginx가 `X-Forwarded-For` 를 **붙인다**

ADR-0031은 백엔드에 "신뢰 목록에 있는 출처의 XFF만 읽는다"를 넣었다. **그런데 그
헤더를 붙이는 쪽을 안 고쳤다.**

```nginx
proxy_set_header X-Real-IP $remote_addr;   # 있었다
                                            # X-Forwarded-For 는 없었다
```

**nginx는 자기가 설정하지 않은 헤더를 지우지 않는다.** 그래서 클라이언트가 보낸
XFF가 백엔드에 그대로 도달했고, 백엔드는 신뢰 목록에 있는 출처(=nginx)에서 온
요청이므로 그 값을 클라이언트 IP로 채택했다.

| 프록시 경유 로그인 40회 | 결과 |
|---|---|
| **위조 XFF (매번 다른 값)** | **40회 전부 통과 — 한도 없음** |
| 대조군 (XFF 없음) | **31번째 429** (한도 30/분) |

차이는 헤더 하나다. **리미터는 정상이었고, 위조가 매번 새 버킷을 만들었다.**

결과적으로 **런북대로 `TRUSTED_PROXIES` 를 채우면 한도가 사라지고**, 안 채우면
안전한 대신 한도가 배포 전체의 합계가 됐다. **안전한 설정과 올바른 설정이
양립하지 않았다.**

수정은 한 줄이고, 백엔드 코드는 손대지 않는다:

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

`$proxy_add_x_forwarded_for` 는 `들어온 XFF + ", " + $remote_addr` 이라 **마지막
원소가 nginx가 실제로 본 주소**다. `RateLimitInterceptor.clientIp()` 가 이미
`parts[parts.length - 1]` 을 쓰고 있었다 — **코드는 없는 설정을 전제로 쓰여
있었다.**

### 왜 검사가 6단계 동안 못 잡았나

`verify-auth.sh` 판정 6은 **백엔드 포트에 직접** 쏘면서 이렇게 적어뒀다:

> `nginx 를 거치면 nginx 가 헤더를 자기 값으로 덮으므로 스푸핑 시나리오 자체가
> 재현되지 않는다`

**그 문장이 사실이 아니었다.** 덮는 설정이 없었다. 검사는 **배포되지 않는 경로를
검증하면서, 검증하지 않는 경로에 대한 미확인 주장을 근거로 달고 있었다.** 게다가
배포 구성에서는 8080이 닫혀 이 판정이 `[FAIL]` 로 나왔고, 런북에 **"그게
정상"** 이라고 적혀 있었다 — 실패가 정상으로 문서화된 검사는 아무것도 못 막는다.

판정 6을 **프록시 경유로 옮겼다.** 이제 배포에서 통과해야 하며, 실패하면 nginx
설정이 빠진 것이다.

## 결정 3: `demo-token` 을 쓰던 검사 4종을 되살린다

ADR-0031이 `demo-token` 을 제거했는데 **호출하는 쪽을 안 고쳤다.**

| 파일 | 상태 |
|---|---|
| `load/verify-container.sh` | 첫 줄에서 `[FAIL]` 후 `exit 1` |
| `load/verify-mq.sh` | 404 본문을 JSON 파싱하다 traceback |
| `load/k6/purchase-contention.js` | `setup()` 에서 throw |
| `load/k6/ai-search.js` | `setup()` 에서 throw |

**부하 하네스 전체와 검증 스크립트 3종 중 2종이 죽어 있었다.** 그리고
`docs/07-배포/배포-절차.md` 4단계가 `verify-container.sh` 실행을 지시하고 있었다.

가장 아픈 것은 **오버셀 0건 단언을 다시 돌릴 방법이 없었다**는 점이다 — 이
프로젝트에서 동시성을 보증하는 유일한 장치다.

전부 `POST /api/auth/login {username, password}` 로 전환했다. `run.sh` 는
`DEMO_PASSWORD` 가 없으면 **먼저 막는다** — 없이 돌리면 k6의 `setup()` 예외로
나타나 원인이 부하 스크립트처럼 보인다. k6에는 `-e` 로 **명시해서** 넘긴다.
시스템 환경변수 상속 기본값에 기대지 않는 이유는, 이 저장소가 "환경변수는 자동
상속될 것"이라는 가정으로 이미 세 번 틀렸기 때문이다(compose의 `RABBITMQ_HOST` ·
`DEMO_PASSWORD` · `DB_PASSWORD`).

## 결정 4: `.env.example` 에 필수 3종을 넣는다

`DEMO_PASSWORD` · `ADMIN_PASSWORD` · `TRUSTED_PROXIES` 가 빠져 있었다. compose와
배포 절차 문서에는 있지만, **운영자가 실제로 복사하는 파일은 이것 하나**다.

빠지면 설계대로 **아무도 로그인 못 하는 쪽**으로 실패한다 — 안전하지만, 파일에
단서가 없으면 원인을 찾는 데 시간이 든다.

### 결정 2 — **네 측정이 있어야 "맞는 이유로 통과"가 된다**

앞의 둘만 보면 **"XFF를 아예 안 읽게 됐다"도 똑같은 결과**를 낸다(사례 10의 '약함').
그래서 신뢰 경로가 살아 있는지를 따로 쟀다 — 신뢰 프록시(nginx 컨테이너) **안에서**
백엔드로 직접 쏴서, 요청 출처가 신뢰 목록에 들어가게 만들었다.

| 측정 | 결과 | 무엇을 말하는가 |
|---|---|---|
| 프록시 경유 · 위조 XFF 40회 | **31번째 429** | 위조로 새 버킷을 못 만든다 |
| 프록시 경유 · XFF 없음 | 31번째 429 | 대조군과 동일해졌다 |
| **신뢰 프록시 · 마지막 값 변경** | **40회 통과** | **XFF를 실제로 읽고 있다** |
| **신뢰 프록시 · 앞쪽만 변경** | 31번째 429 | 클라이언트가 위조하는 자리는 무시된다 |

수정 전 시험군은 **40회 전부 통과**(한도 없음)였다.

### 결정 3 — 되살아난 검사

| 검사 | 결과 |
|---|---|
| `verify-auth.sh` | **10/10** (판정 6 프록시 경유 + 판정 7 신규) |
| `verify-container.sh` | **10/10** — 6단계 만에 다시 돈다 |
| `verify-mq.sh` | **8/8** |
| **`run.sh purchase contended`** | **오버셀 0건** — 재고 감소 2,696 = 성공 2,695 + 워밍업 1 |

**오버셀 0건 단언을 다시 돌릴 수 있게 된 것이 이 라운드에서 가장 큰 회복이다.**

### 회귀

AI **125** · 백엔드 **42** · 프론트 빌드 통과.

> **`./gradlew test` 는 `--rerun-tasks` 로 돌렸다.** 그냥 돌리면
> `Task :test UP-TO-DATE` + `BUILD SUCCESSFUL` 이 나오는데 **테스트가 0건 실행된다.**
> 점검을 그 초록으로 시작했으면 그게 첫 번째 잘못된 검사였을 것이다.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| `llm/test` 에 `require_actor` 만 추가 | 운영 경로가 아닌데 공격면만 남는다. 연동 확인은 `/health` 로 된다 |
| 백엔드가 `X-Real-IP` 를 읽게 | nginx가 이미 보내므로 더 짧아 보이지만, **다중 프록시에서 무너진다**(중간 프록시가 덮어쓴다). XFF + 신뢰 목록이 표준이고 백엔드 코드는 이미 그렇게 쓰여 있었다 |
| 삭제된 경로 하나만 테스트로 고정 | **다음 누락을 못 잡는다.** 원인은 파일이 아니라 "개별 `Depends` 는 빠뜨려도 조용하다"는 방식이다 |
| k6가 비밀키로 직접 서명 | 발급 로직의 세 번째 사본이 생긴다. 검증기가 두 벌인 것만으로도 갈라질 위험이 있다 |

## 배운 것

**라운드의 판정선은 그 라운드가 바꾼 것만 검사한다.** 두 결함 다 각 라운드의
기준을 전부 통과했다. `llm/test` 는 Phase 2 유물이라 이후 어느 라운드도 쳐다보지
않았고, XFF는 **읽는 쪽만 바꾸고 쓰는 쪽을 안 봤다.**

일반화하면 이렇다.

> **어떤 값을 "신뢰한다"고 정할 때는 그 값을 *쓰는 주체*가 존재하는지 같이
> 확인해야 한다.** 읽는 쪽에 조건만 걸면, 조건은 만족되는데 값은 아무나 넣는
> 상태가 된다 — 그리고 그건 신뢰하기 *전*보다 나쁘다.

그리고 검사에 대해 하나 더:

> **배포되지 않는 경로를 검증하는 검사는, 통과해도 아무것도 보증하지 않는다.**
> 판정 6은 "포트가 열린 구성에서만 성립한다"는 단서까지 달고 있었는데, 그
> 단서가 곧 "배포에서는 아무것도 안 잰다"는 뜻이었다. 단서를 붙이는 것과 대상을
> 옮기는 것은 다르다.
