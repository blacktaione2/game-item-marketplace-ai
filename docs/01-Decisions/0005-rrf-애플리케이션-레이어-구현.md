# ADR-0005: RRF를 Elasticsearch 네이티브 기능이 아닌 애플리케이션 레이어에서 계산한다

## 상태

채택됨

## 배경

계획서상 검색은 BM25(키워드)와 kNN(dense_vector 의미 검색) 결과를
RRF(Reciprocal Rank Fusion)로 융합하는 하이브리드 방식이다. Elasticsearch
8.x는 RRF를 내장 기능으로 제공하므로 처음에는 그걸 쓰려고 했다.

그런데 실제로 던져보니 두 가지 벽에 부딪혔다.

1. 8.14부터 도입된 `retriever` 문법은 우리가 쓰는 **8.13.4에 아예 없다**:

   ```
   parsing_exception: Unknown key for a START_OBJECT in [retriever].
   ```

2. 8.13에 있는 구문법(`rank.rrf`)은 **라이선스가 막는다**. 우리 클러스터는
   basic 라이선스다:

   ```
   security_exception: current license is non-compliant for
   [Reciprocal Rank Fusion (RRF)]
   ```

즉 ES의 네이티브 RRF는 Platinum/Enterprise 전용 기능이고, 포트폴리오
프로젝트에서 유료 라이선스를 살 이유는 없다.

## 결정

RRF를 애플리케이션(FastAPI) 레이어에서 직접 계산한다.

- BM25 질의와 kNN 질의를 `_msearch`로 **한 번의 왕복**에 같이 던진다
  (검색 두 번을 순차로 호출해 레이턴시를 두 배로 만들지 않기 위해).
- 두 결과의 **순위**만 가지고 표준 RRF 공식을 적용한다:

  ```
  score(d) = Σ over retrievers  1 / (k + rank_r(d)),   k = 60
  ```

- 각 문서에 `bm25_rank` / `knn_rank`를 같이 실어 응답한다. 어느 검색기가
  그 문서를 올렸는지 보이면 튜닝할 때 판단 근거가 된다.

## 고려한 대안

1. **ES 네이티브 RRF (`rank.rrf`)** — 라이선스가 막아서 불가.
2. **ES 8.14+로 업그레이드해서 `retriever` 문법 사용** — 8.14의
   `retriever` 문법 자체는 basic에서도 파싱되지만 `rrf` retriever는 여전히
   라이선스 대상이라 문제가 해결되지 않는다. 버전만 올리고 같은 벽에
   부딪힐 일이다.
3. **점수 선형 결합(`query` + `knn`을 한 요청에 넣고 score를 그냥 합산)** —
   ES 8.13에서 `rank` 없이 둘을 같이 주면 점수가 더해진다. 하지만 BM25
   점수(상한 없음, 코퍼스 통계 의존)와 코사인 유사도(0~1)는 스케일이 완전히
   달라서, 정규화 없이 더하면 사실상 BM25가 결과를 지배한다. 정규화를
   직접 하려면 결국 애플리케이션 로직이 필요하고, 그럴 바에는 스케일
   자체를 안 쓰는 RRF가 낫다.
4. **애플리케이션 레이어 RRF (채택)** — 순위만 쓰기 때문에 점수 정규화가
   아예 필요 없다는 RRF의 장점을 그대로 살리면서, 라이선스에 묶이지 않는다.
   구현도 20줄 수준이다.

## 결과

- `ai/app/services/search/hybrid.py`의 `reciprocal_rank_fusion()`이 융합을
  담당한다. 순수 함수라 단위 테스트가 쉽다 — 대칭 입력이 정확히 동점이
  되는지, 두 리스트에 모두 등장한 문서가 한쪽에서만 1위인 문서를 이기는지를
  `ai/tests/test_hybrid.py`에서 검증한다 (`python -m pytest`).

  > **2026-07-29 정정**: 원래 이 문단은 "검증했다"고만 적혀 있었는데, 당시
  > 검증은 임시 스크립트로 돌리고 리포지토리에 남기지 않았다. 문서만 보면
  > 회귀 테스트가 있는 것처럼 읽혀서 실제 테스트 파일로 복원했다. 이때
  > **직관이 틀렸던 케이스**도 회귀 테스트로 함께 박아뒀다 — "2등+2등이
  > 1등+3등보다 낫다"고 단정했지만 1/x의 볼록성 때문에
  > `1/(k+1) + 1/(k+3) > 2/(k+2)` 로 반대였다. 구현이 아니라 기대가 틀렸다.
- `k=60`은 RRF 원논문의 관례값이다. 이 값이 커질수록 상위권 순위 차이가
  덜 중요해진다 — 나중에 튜닝 대상이 될 수 있어 상수로 빼뒀다.
- 부수 효과로 융합 로직이 우리 코드 안에 있으므로, Phase 4에서 RAGAS로
  검색 품질을 평가할 때 가중치를 바꿔가며 실험하기 쉬워졌다. ES 네이티브
  기능이었다면 불가능했을 자유도다.
- 만약 나중에 Elastic Cloud 등 라이선스가 있는 환경으로 옮긴다면 네이티브
  RRF로 되돌리는 것도 선택지지만, 위의 실험 자유도를 잃는다는 점을 감안해
  판단할 것.
