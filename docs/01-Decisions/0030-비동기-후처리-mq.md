# ADR-0030: 비동기 후처리 — 큐로 넘긴 것은 체결이 아니라 그 뒤다

## 상태

채택됨.

## 배경 — 기획서에는 있는데 로드맵에 없었다

Phase 9a에서 배포 프로파일을 짜다가 **RabbitMQ가 코드 어디에도 없다**는 걸 확인했다.

```
backend/src/main, ai/app  →  amqp|rabbit  0건
backend/build.gradle       →  0건
```

기획서의 트래픽 처리 설계에는 MQ가 핵심으로 들어 있고, `TradeService` javadoc에도
*"RabbitMQ 비동기 처리는 이후 단계에서 붙인다"* 고 적혀 있었다. 그런데
**로드맵에는 Phase 0의 "docker-compose에 RabbitMQ 포함"이 전부**였다.

즉 "나중에 한다"가 아니라 **일정에 올라간 적이 없다.** 기획서에서 로드맵으로
내려오지 않은 항목이고, 인프라만 떠 있고 아무도 쓰지 않는 상태로 아홉 단계를
지나왔다.

## 결정 1: 거래 처리 자체는 큐로 보내지 않는다

기획서의 흐름은 `락 → MQ 발행 → 컨슈머가 DB 트랜잭션`이다. 그대로 하면
**구매가 비동기가 된다.**

| | 기획서 그대로 (C1) | 채택 (C2) |
|---|---|---|
| API 계약 | `201 Created` → **`202 Accepted`** | **무변경** |
| 프론트 | 폴링 또는 대기 상태 필요 | 무변경 |
| **오버셀 단언** | `재고 감소분 == 성공 응답 수`가 **응답 시점에 성립하지 않는다** | **그대로 유지** |
| k6 하네스 | 따라 바뀜 | 무변경 |
| 큐가 맡는 것 | 체결 | **체결 후 알림** (기획서 4단계) |

**ADR-0001이 주장하고 ADR-0020이 실동시성 26,600건에서 검증한 보장을 지키는
쪽을 택했다.** C1이 얻는 것은 "기획서 문구와 일치" 하나뿐인데, 그 대가로 이
저장소에서 가장 강한 단언을 다시 설계해야 한다.

> 실무에서도 재고 차감은 동기로 두고 후처리를 비동기로 미는 쪽이 흔하다.

## 결정 2: `AFTER_COMMIT` 발행 — 이 라운드의 핵심

트랜잭션 **안에서** 발행하면 두 가지가 깨진다.

- **롤백돼도 메시지는 나간다** — 존재하지 않는 거래의 알림
- **컨슈머가 커밋 전 상태를 본다** — 소비가 커밋보다 빠르면 거래를 못 찾는다

`@TransactionalEventListener(phase = AFTER_COMMIT)` 은 커밋이 성공한 뒤에만
불린다. 롤백되면 아예 호출되지 않는다.

두 번째 위험은 **메시지를 자족적으로 만들어** 한 번 더 막았다 —
`TradeCompletedEvent` 가 필요한 값을 전부 실어서 컨슈머가 조회하지 않는다.

## 결정 3: 발행 실패는 거래를 실패시키지 않는다 (fail-open)

알림은 부가 기능이다. 브로커가 죽었다고 구매가 실패하면 안 된다.
이 저장소의 기존 정책과 같은 결이다 — **AI 리미터는 fail-open(비용 방어),
구매 락은 fail-closed(정확성)**.

**그런데 fail-open 에는 지연이라는 두 번째 축이 있다.** 발행은 커밋 직후
같은 스레드에서, 즉 **응답 전에** 일어난다. RabbitMQ 클라이언트의 기본 연결
타임아웃은 60초라 그대로 두면 *"구매가 성공은 하는데 1분 걸린다"* 가 된다 —
fail-open 의 정신에 어긋나면서 "성공했다"는 판정은 통과하는 상태다.

```yaml
spring.rabbitmq.connection-timeout: 2s
spring.rabbitmq.template.retry.enabled: false   # 재시도는 지연을 배로 만든다
```

**판정선도 그 설정값에서 도출했다**(아래). 내가 정한 숫자라 근거가 있다.

대가는 **유실**이다. 브로커가 죽은 동안의 알림은 사라진다. 진짜 해결은 outbox
패턴인데 범위가 커서 트리거와 함께 등록만 했다.

## 결정 4: 멱등성 — 그리고 예외를 **좁게** 잡는다

RabbitMQ 는 at-least-once 다. 커밋은 됐는데 ack 가 실패하면 같은 메시지가 다시 온다.
`(recipient_id, trade_id)` 에 unique 를 건다 — 거래 하나가 구매자·판매자 **둘**에게
알림을 만들므로 `trade_id` 단독은 쓸 수 없다.

**여기서 두 번 틀리기 쉽다.**

1. **중복을 예외로 흘려보내면 모든 재전달이 DLQ 로 간다.** 멱등성 장치가 오히려
   실패를 만든다 → 잡아서 정상 종료한다
2. **그렇다고 `DataIntegrityViolationException` 을 잡으면 안 된다.** 그건 상위
   타입이라 **FK 위반까지 삼킨다** — 존재하지 않는 유저를 가리키는 메시지가
   "이미 처리됨"으로 조용히 사라진다 → `DuplicateKeyException`(SQLState 23505)만 잡는다

2번은 **판정 6(DLQ)을 어떻게 만들지 고민하다 발견했다.** 검증 방법을 설계하는
과정이 설계 결함을 드러낸 사례다.

## 결정 5: 순서는 보장하지 않는다

기획서는 "컨슈머가 순서대로 처리"라고 적지만 **알림에는 순서가 무의미하다** —
거래마다 독립이고 서로를 덮어쓰지 않는다. 순서가 필요해지는 것은 같은 아이템의
시세를 순차 갱신할 때인데, **그 소비자는 아직 만들 수 없다**(아래).

## 컨슈머가 할 수 있는 일은 하나뿐이었다

기획서의 4단계는 "알림 + 시세 갱신"인데, 착수 전 확인 결과:

| 작업 | 가능 여부 |
|---|---|
| **알림 생성** | 가능 — 단 `notifications` 엔티티가 없어 새로 만들어야 했다 |
| ~~시세 갱신~~ | **막혀 있다.** 시세 예측이 `app/corpus/trade_history.py`(합성)를 읽는다. Postgres 거래가 생겨도 반영할 대상이 없다 — id 공간 (C) 완전 통합에 묶인 항목 |
| ~~이상거래 탐지 트리거~~ | 같은 이유로 막혀 있다(`detect_trade` 가 합성 코퍼스 전용) |

## 판정선과 결과 — 8개 전부 통과, 4개는 실패를 만들어 확인

| # | 기준 | 결과 |
|---|---|---|
| 1 | **오버셀 0 단언이 그대로 성립** | **통과** — 재고 감소 2,752 = 성공 응답 수 |
| 2 | 큐 배수 후 **구매 수 == 알림 수** | **통과** — 5건 → 5건 |
| 3 | **롤백되면 발행되지 않는다** ※ | **통과** (+ 대조군 "커밋되면 발행된다") |
| 4 | 같은 메시지 2회 소비 → 알림 **1건** ※ | **통과** |
| 5 | **브로커 정지 시 구매 성공 + 지연 상한 이내** ※ | **통과** — 201, 지연 증가 **7ms** ≤ 2,000ms |
| 6 | 컨슈머 3회 실패 → **DLQ 1건** ※ | **통과** — 원본 큐 0, DLQ 1 |
| 7 | 재전달이 **DLQ 를 채우지 않는다** | **통과** — DLQ 0 |
| 8 | `seed-demo.sql` **재적용이 FK 위반 없이 성공** | **통과** |

※ = 실패 케이스를 인위로 만들어야 확인되는 항목.

**판정 2의 타이밍**: 소비가 비동기라 부하 직후 바로 세면 컨슈머가 큐를 다 못
비운 상태일 수 있다 — 정상인데 "알림이 부족하다"는 거짓 실패가 난다. 그래서
`messages_ready` 와 **`messages_unacknowledged` 를 둘 다** 0으로 기다린 뒤 센다.
`ready` 만 보면 컨슈머가 물고 있는 것을 놓친다. **시간 초과는 통과가 아니라
실패**로 처리한다.

**판정 5의 7ms 를 오해하면 안 된다.** 컨테이너를 멈추면 TCP 연결이 **거부**되어
즉시 실패한다 — 연결 타임아웃은 그 경우가 아니라 **호스트 도달 불가**(패킷 유실)일
때 걸린다. 즉 2초는 **설정으로 보장한 최악 상한**이고 7ms 는 흔한 경우의 실측이다.
네트워크 분단을 로컬에서 재현하지 못해 상한 쪽은 측정이 아니라 구성으로 담보한다.

## 마이그레이션 도구가 없다

```
build.gradle    →  flyway·liquibase 0건
application.yml →  ddl-auto: update
```

새 테이블은 제약과 함께 생성되므로 `notifications` 는 문제없다. **다만
`ddl-auto: update` 는 기존 테이블에 제약을 추가하는 것을 신뢰할 수 없다** —
다음에 기존 테이블을 건드릴 때 이 한계가 걸린다.

`seed-demo.sql` 의 삭제 순서에 `notifications` 를 **맨 앞**에 넣었다. `tenant_id`·
`recipient_id` 로 `tenants`·`users` 를 참조하므로, 안 지우면 `users` 삭제에서 FK
위반이 난다. 생성기(`export_demo_sql.py`)를 고치고 재생성했다.

> `trade_id` 는 **일부러 FK 가 아니라 값**이다. 알림은 거래의 수명주기에 묶이지
> 않는다 — 거래가 지워져도 "무엇이 일어났는지"의 기록은 남는 편이 맞고, FK 로
> 묶으면 시드의 거래 삭제까지 알림에 걸린다.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| C1 — 거래 처리를 큐로 | 오버셀 0 검증을 다시 설계해야 한다. 얻는 게 기획서 문구 일치뿐 |
| 배포에서 RabbitMQ 제외 | 9a에서 잠깐 제안했다가 철회했다. **문제는 배포가 아니라 미구현**이었다 |
| outbox 패턴 | 유실을 진짜로 막지만 범위가 크다. 트리거와 함께 등록 |
| `DataIntegrityViolationException` 포괄 catch | FK 위반까지 삼켜 진짜 오류가 사라진다 |
| 컨슈머 동시성 1 (순서 보장) | 알림에 순서가 무의미하다. 필요해지는 소비자는 아직 못 만든다 |

## 영향

- 백엔드 테스트 **29 → 36건**
- 체결 응답에 발행 1회가 붙는다. 정상 상태 실측 **29ms**, 브로커 정지 시 **36ms**
- **"MQ 를 넣어서 빨라졌다"고 말할 수 없다.** 지금 체결 경로에는 후처리가 없어
  줄어들 게 없다. 이 라운드가 만든 것은 **후처리를 붙일 자리**다 — ADR-0020이
  분산 프로파일에서 DB 가 제약임을 보였는데, 후처리를 동기로 붙이면 락 보유가
  그만큼 늘어난다. 그걸 미리 막는 구조다
- `Jackson2JsonMessageConverter` 대신 `JacksonJsonMessageConverter` — Spring AMQP 4
  에서 앞의 것은 제거 예정이다

## 남긴 것 (트리거 있음)

| 항목 | 트리거 |
|---|---|
| **outbox 패턴** | 알림 유실이 실제로 문제가 될 때 (지금 fail-open 은 의도된 선택) |
| **시세 갱신 소비자** | 시세 예측이 Postgres 거래를 읽게 될 때 (id 공간 (C)) |
| **이상거래 탐지 트리거** | 같은 조건 |
| **DLQ 감시** | DLQ 가 0이 아닌 상태가 관측될 때. 지금은 사람이 보는 신호이지 알림이 가지 않는다 |
