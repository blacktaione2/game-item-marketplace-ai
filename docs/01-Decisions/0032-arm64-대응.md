# ADR-0032: ARM 대응 — 계획했던 재양자화를 측정하고 기각했다

## 상태

채택됨. 9b의 앞쪽(이미지·검증)이고, 실배포는 클라우드 접근이 있는 쪽에서 한다.

## 배경

배포 대상이 Oracle Cloud **ARM**이다. `reranker.py`에 이런 주석이 여섯 단계 동안
남아 있었다:

```python
# avx2 설정은 x86 개발 환경 기준 — 배포 대상인 Oracle Cloud ARM에
# 올릴 때는 AutoQuantizationConfig.arm64로 다시 생성하는 편이 좋다.
qconfig = AutoQuantizationConfig.avx2(is_static=False, per_channel=False)
```

**"~하는 편이 좋다"는 측정이 아니다.** 그래서 쟀다.

## 결정 1: arm64 양자화 설정을 **기각한다**

같은 모델을 두 설정으로 양자화해 평가 질의 5건 × 후보 20건을 비교했다.

| | 결과 |
|---|---|
| arm64 모델이 x86에서 실행되는가 | **된다** — 비교 자체가 가능했다 |
| **top-1 일치** | **5/5** |
| **top-5 순위 일치** | **0/5** |
| 점수차(top1) | 0.064 ~ 0.268 |
| 파일 크기 | 둘 다 112.8 MB |

**사전 등록한 판정선("top-5 순위 일치")이 실패했다.** 1위는 안 흔들리는데 2~5위가
매번 재배열된다.

### 왜 기각인가 — 무엇을 무효화하는지가 결정적이다

**기록된 품질 수치는 전부 avx2로 측정한 것이다.** 하드 필터 부적합 50 → 26 → 14
(ADR-0014·0015), 임베딩 Recall@1 0.148 → 0.389, 리랭커 하한 기각 근거(ADR-0018).
양자화를 바꾸면 그 수치가 **배포된 시스템을 더 이상 설명하지 않는다.**

바꿀 이유는 "ARM에서 더 빠를 수 있다"인데 **그건 측정한 적이 없다.**

> **재보지 않은 성능 이득을 위해 재본 품질 수치를 버리는 거래다.** 그래서 안 한다.
> `embedding_base_model` 때(ADR-0029)와 같은 결이다 — 커밋된 상태가 문서의 수치를
> 재현할 수 있어야 한다.

### 그래서 검증 대상이 바뀌었다

avx2를 유지한다는 것은 **"이름은 x86이지만 ARM에서도 실행된다"** 는 전제에 기댄다.
그건 주장이지 측정이 아니므로, 에뮬레이션한 aarch64에서 직접 확인했다.

```
machine = aarch64
onnxruntime = 1.28.0
inputs = ['input_ids', 'attention_mask']
output shape = (4, 1)   finite = True
```

**로드·추론되고 결과가 유한하다.** 이게 avx2 유지 결정의 실제 근거다.

> 최소 구성(onnxruntime + numpy)으로 쟀다. optimum·transformers를 에뮬레이션에서
> 설치하면 훨씬 오래 걸리는데, 여기서 의심스러운 것은 **ONNX Runtime의 실행 경로**
> 하나였다.

### 되살릴 조건

**ARM에서 리랭킹이 실제로 병목으로 지목될 때.** 그때는 `evaluate_hard_filters`를
다시 돌려 품질 수치를 갱신하는 것이 전환의 일부다 — 숫자를 새로 만들지 않고
설정만 바꾸는 것은 허용하지 않는다.

## 결정 2: 대상에서 빌드한다 (교차 빌드는 검증용)

베이스 이미지 9종이 **전부 arm64를 제공한다**(ES 포함) — 착수 전에 확인했다.
`buildx --platform linux/arm64`로 **web(22MB)·backend** 빌드를 확인했다.

**AI 이미지는 처음엔 완주하지 못했다 — 디스크가 찼다**(C: 여유 2.56GB까지 떨어져
중단). 에뮬레이션에서 torch 설치가 크고 빌드 캐시가 그 몇 배다. 그래서 아래
"남긴 것"에 **"디스크 여유가 확보될 때"** 라는 트리거로 등록했었다.

### 추가 측정 (2026-08-04, 디스크 정리 후) — **완주했다**

```
#8 DONE 1041.5s      pip 계층 (약 17분, 에뮬레이션)
#12 DONE 0.5s        마지막 계층까지 통과, exit 0
```

**이미지는 만들지 않았다** — `--output type=cacheonly`. 알고 싶은 것은 "빌드가
되는가"뿐이고, 3GB 이미지를 x86 디스크에 남길 이유가 없다.

**진짜 위험은 "빌드가 되는가"가 아니라 "의존성에 aarch64 휠이 있는가"였다.**
그래서 빌드 전에 가장 의심스러운 하나를 따로 봤다 — `Dockerfile`이 torch 를
`--index-url https://download.pytorch.org/whl/cpu` 에서 받는데, **그 인덱스가
aarch64를 제공하는지**는 확인된 적이 없었다.

| 확인 | 결과 |
|---|---|
| `whl/cpu` 인덱스의 aarch64 휠 | **있다** — `cp311 manylinux_2_28_aarch64` 가 **2.7.0부터** |
| 대조 (파일 개수) | x86_64 476 · aarch64 204 |
| 실제 해석 결과 | **`torch-2.13.0+cpu`** |
| 나머지 컴파일 의존성 | 전부 aarch64 휠 — `numpy` `scipy` `onnxruntime-1.28.0` `tokenizers` `pyarrow` `cryptography` `pandas` `uvloop` … |

`onnxruntime 1.28.0` 이 aarch64에서 설치되는 것은 **결정 1의 전제와 같은
사실**이다 — 위에서 에뮬레이션으로 추론까지 확인한 그 런타임이다.

그래도 **배포는 대상에서 빌드하는 쪽이 낫다.** 네이티브라 빠르고 아키텍처 불일치
가능성이 없다. 이 교차 빌드가 바꾼 것은 *배포 방법*이 아니라 **확신의 근거**다 —
"베이스가 arm64를 제공하니 되겠지"에서 "된다"로 옮겼다.

> 이 라운드가 남긴 부작용 하나: **이 빌드의 캐시가 디스크를 채워 Docker 데몬을
> 죽였다.** 증상이 "read-only file system"이라 원인을 가리키지 않는다 —
> `docs/05-Troubleshooting/도커-디스크-고갈-vhdx-압축.md`. 재실행할 때는
> **`docker builder prune -af` 를 먼저**, 끝나고 또 한 번.

## 결정 3: 배포 절차를 문서로 남긴다

`docs/07-배포/배포-절차.md`. **"해봤다"가 아니라 "이 순서로 하면 되고 각 단계에서
무엇을 확인하는가"** 형태다 — 실제 인스턴스 접근이 없으므로 그 이상을 주장하지 않는다.

이번 세션에서 실측한 함정이 전부 들어간다:

- 기동 후 **`restart backend web`** 이 필요한 두 가지 이유(ADR-0031)
- `TRUSTED_PROXIES`를 안 채우면 한도가 배포 전체 합계가 된다
- `verify-auth.sh`의 **판정 6은 배포에서 `[FAIL]`이 정상**이다(포트가 닫혀 있어
  스푸핑 대상 자체가 없다)
- 배포 후에만 잴 수 있는 것 — 스레드풀 크기, 부하 기준선

## 영향

- `reranker.py`가 `_quantization_config()`로 설정을 한 곳에 모았다. 아키텍처를
  읽지 않지만 **왜 안 읽는지가 그 함수에 적혀 있다**
- 여섯 단계 묵은 "~하는 편이 좋다" 주석이 **측정과 결론**으로 바뀌었다
- 배포 절차 문서 신설 (`docs/07-배포/`)

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| arm64 설정으로 전환 | top-5 순위 0/5. 품질 수치를 다시 재야 하는데 성능 이득은 미측정 |
| 아키텍처 자동 분기 | 위 문제를 **자동으로** 일으킨다. 한 번 짰다가 되돌렸다 |
| 설정값으로 빼서 opt-in | 아무도 안 쓸 스위치다. 되살릴 조건이 명확하므로 그때 바꾸면 된다 |
| 교차 빌드로 배포 이미지 생산 | 느리고, 대상에서 빌드하면 불일치 가능성이 사라진다 |
