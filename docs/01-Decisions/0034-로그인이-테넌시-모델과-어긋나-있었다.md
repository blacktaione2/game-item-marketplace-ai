# ADR-0034: 로그인이 테넌시 모델과 어긋나 있었고, 오류가 401로 가려지고 있었다

## 상태

채택됨. **배포 전 점검 2회차**에서 나온 3건이다. ADR-0033이 1회차였고, 그때는
"보안 구멍"이었다면 이번엔 전부 **fail-closed 인데 진단이 불가능해지는** 종류다.

## 배경

1회차(ADR-0033)를 고친 뒤 같은 절차를 한 바퀴 더 돌렸다. 이번에는 **1회차에서 얕게
본 영역**에 무게를 뒀다 — 특히 **테넌트 격리**는 이 프로젝트의 간판인데 검증한 적이
없었다.

거래 흐름의 테넌트 스코프는 깨끗했다(`getItem`·`getUser` 모두
`findByIdAndTenantId`). AI 서버도 `tenant_code`를 토큰에서만 읽고 캐시 키를
네임스페이스로 나눈다. **그런데 로그인이 어긋나 있었다.**

## 결정 1: `/error`를 `PUBLIC_PATHS`에 넣는다 — **이게 나머지를 가리고 있었다**

Spring Security 6+는 **ERROR 디스패치도 필터링한다.** 예외가 나면 Boot가 `/error`로
포워드하는데, 그 경로가 허용 목록에 없으면 `anyRequest().authenticated()`에 걸려
**401**이 된다.

실측한 증상 셋이 전부 같은 원인이었다.

| 입력 | 나와야 할 값 | 수정 전 |
|---|---|---|
| 깨진 JSON으로 로그인 | 400 | **401** |
| 두 테넌트에 같은 아이디 | 500 | **401** |
| `JWT_SECRET`이 256비트 미만 | 500 | **401** |
| *(대조)* 유효 토큰으로 없는 경로 | 404 | 404 ✔ |

대조군이 결정적이다 — **인증된 요청은 정상적으로 404가 나온다.** 즉 마스킹은
비인증 경로에서만 일어난다.

> **결함 둘이 "비밀번호가 틀렸다"로 보였다.** 공개 배포에서 로그인이 안 될 때
> 401만 보고 비밀번호를 의심하게 되는데, 실제 원인은 서버 오류일 수 있다.
> **한 줄의 부재가 다른 결함들의 발견을 막고 있었다.**

본문이 새지는 않는다 — `server.error.include-stacktrace` 기본값이 `never`라
`{timestamp, status, error, path}`만 나간다.

## 결정 2: 로그인이 `tenantCode`를 받는다

`users`의 유니크 제약은 처음부터 **`(tenant_id, username)`** 이었다. 그런데 조회는
`findByUsername` 하나였고, 리포지토리 javadoc에 이렇게 적혀 있었다:

> `데모 계정이 한 테넌트뿐이라 username 은 전역 유일하다.`

**스키마가 보장하지 않는 가정이다.** 두 번째 테넌트에 `buyer_lee`를 실제로 넣어봤다.

```
NonUniqueResultException: Query did not return a unique result: 2 results were returned
→ 클라이언트에는 401
```

**해당 계정은 영구히 로그인 불가가 되고, 원인은 어디에도 보이지 않는다.**

### (a) 전역 유니크가 아니라 (b) 테넌트 명시를 택한 이유

| | |
|---|---|
| **스키마가 이미 (b)를 선택했다** | (a)는 **설계를 버그에 맞추는 것**이다. 코드가 `findByUsername` 하나라서 제약을 내리는 셈 |
| **간판과 어긋난다** | 인덱스를 테넌트별로 나누고 모든 테이블에 `tenant_id`를 넣어놓고 신원의 키만 전역이면, 그 자체가 질문거리다 |
| **모델상 틀리다** | 게임사 A와 B가 각각 `buyer_lee`를 못 갖는 건 B2B 멀티테넌시에서 성립하지 않는다 |
| **나중 비용이 비대칭** | (a)를 택하면 테넌트가 둘이 되는 순간 **(b)를 그때 하게 되고**, 운영 중 DB의 제약 마이그레이션이 얹힌다 |

ADR-0033의 XFF와 같은 모양이다 — **읽는 쪽만 만들고 쓰는 쪽을 안 만든** 상태였고,
그때도 "백엔드가 `X-Real-IP`를 읽게 하자"(설계 축소)가 아니라 "nginx가 XFF를 붙이게
하자"(설계 완성)를 택했다.

### 원칙과 충돌하지 않는다

"요청이 신원을 주장하지 않는다"(ADR-0022·0023)를 어기는 게 아니다. **로그인은
자격증명을 제시하는 자리 자체이고**, 자격증명이 `테넌트 + 아이디 + 비밀번호` 셋이 될
뿐이다. 발급 이후에는 전부 토큰에서 온다 — 요청 본문의 `tenant_code`는 여전히 없다.

없는 테넌트도 **401**이다. 400이나 404로 갈리면 테넌트 목록이 새어 나간다 —
사용자 열거를 막은 것과 같은 이유다.

## 결정 3: `JWT_SECRET` 길이를 기동 시점에 검사한다

`SecurityConfig` 생성자에 이런 주석이 있었다:

> `HS256은 키가 256비트 이상이어야 한다. 짧으면 여기서 즉시 실패하는 게 맞다`

**사실이 아니었다.** `SecretKeySpec`은 길이를 검증하지 않는다(빈 배열만 거부). Nimbus의
`KeyLengthException`은 **첫 로그인 시점**에야 난다.

5바이트 시크릿으로 실측한 결과가 나쁘다.

| | |
|---|---|
| 컨테이너 | **healthy** |
| 헬스체크 | 통과 |
| 로그인 | **401** (가려진 `KeyLengthException`) |

즉 **모든 게 초록인데 아무도 로그인 못 하는 배포**가 되고, 어디에도 시크릿을 가리키는
신호가 없다.

`SecretGuard`가 아니라 `SecurityConfig` 생성자에 넣었다 — **`SecretGuard`는 `prod`
전용이고 "저장소 기본값인가"만 본다.** 짧은 키는 **모든 프로파일에서** 고장이므로 검사도
모든 프로파일에 있어야 한다. 저장소 기본값은 35바이트라 기존 구성은 그대로 뜬다.

## 결정 1이 곧바로 드러낸 것 — 검사 둘이 틀린 이유로 통과하고 있었다

`/error` 를 열자 **멀쩡하던 `verify-auth.sh` 판정 2의 두 건이 즉시 실패했다.**

```bash
login_code buyer_lee "틀린값"     # 한글 인자
login_code 없는계정 "$DEMO_PW"    # 한글 인자
```

Windows 셸에서 한글 인자가 cp949로 재인코딩돼 **깨진 JSON**이 나갔고, 서버는 정직하게
**400**을 냈는데 마스킹이 그걸 **401로 바꿔놨다.** 검사는 401을 기대하므로 통과했다.

| | 실제 | 검사 |
|---|---|---|
| 수정 전 | 400 → **401로 표시** | **통과** |
| 수정 후 | **400** | 실패 |
| ASCII로 고친 뒤 | **401** | 통과 |

**이 두 검사는 비밀번호 검증을 한 번도 재본 적이 없다.** 뮤테이션으로도, 실패 케이스를
돌려도 안 잡혔을 것이다 — 비밀번호 로직을 망가뜨리면 검사가 정직하게 실패하고, 실제로
401이 나오니 실패 케이스도 통과한다. **다른 결함을 고치자 저절로 드러났다**(사례 14).

> 검사의 입력값은 ASCII로 둔다. 이 저장소의 cp949 함정이 **검사 안에서** 발현한
> 첫 사례다.

## 영향

| | |
|---|---|
| 백엔드 테스트 | 42 → **46** (테넌트별 로그인 3건 + 400/401 구분 1건) |
| 호출부 변경 | 프론트 2 · k6 2 · verify 4 — **로그인하는 모든 곳** |
| 동작 변화 | 비인증 경로의 400·500이 더 이상 401로 가려지지 않는다 |
| 동작 변화 | `tenantCode` 없는 로그인 요청은 **400** |

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| username을 전역 유니크로 | 설계를 버그에 맞춘다. 위 표 참고 |
| `tenantCode`를 **선택**으로 두고 단일 테넌트면 생략 허용 | 동작이 데이터에 따라 달라진다. "speculative flexibility 금지"와 맞물려 설명이 길어진다 |
| 서브도메인에서 테넌트 추론 | 테넌트별 DNS가 필요한데 데모에 없다. 생기면 그때가 낫다 |
| 길이 검사를 `SecretGuard`에 | 그건 `prod` 전용이다. 짧은 키는 모든 프로파일에서 고장난다 |
| `/error` 대신 예외 핸들러 총망라 | 미래의 모든 예외를 열거해야 한다. 원인은 예외 종류가 아니라 **에러 디스패치가 보안 체인에 걸리는 것**이다 |

## 배운 것

**1회차에서 "깨끗하다"고 판단한 영역이 검증된 적 없는 영역이었다.** 테넌트 격리는
이 프로젝트가 여섯 단계 동안 자랑해온 성질인데, 실제로 두 테넌트를 만들어 확인한 적은
한 번도 없었다. 만들자마자 결함이 나왔다.

> **테스트가 없는 성질은 "동작한다"가 아니라 "확인한 적 없다"이다.** 특히 데이터가
> 그 성질을 발현시키지 않는 경우(테넌트가 하나뿐인 시드) 코드를 아무리 읽어도
> 안 보인다 — **데이터를 만들어야 보인다.**

그리고 진단에 관해:

> **오류를 뭉개는 계층이 하나 있으면 그 아래의 모든 결함이 같은 얼굴을 한다.**
> 401 마스킹 하나 때문에 서로 무관한 세 결함이 전부 "비밀번호가 틀렸다"로 보였다.
> 결함을 찾기 전에 **결함이 자기 이름으로 보고되는지**를 먼저 봐야 한다.
