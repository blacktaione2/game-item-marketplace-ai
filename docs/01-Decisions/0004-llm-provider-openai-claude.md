# ADR-0004: LLM 프로바이더는 OpenAI(메인) + Claude(보조, 용도 한정)만 쓴다

## 상태

채택됨

## 배경

이전 프로젝트에서는 LLM 프로바이더를 4개(예: OpenAI, Gemini, DeepSeek 등)
붙여서 썼다. 이번 프로젝트에서 AI 파이프라인(Query Rewrite, 설명 생성,
Agentic Tool-Calling 등)에 쓸 LLM 프로바이더를 다시 정하면서, "여러 개를
쓴다" 자체를 목표로 삼지 않기로 했다. 프로바이더가 늘어날수록 프롬프트
호환성 검증, 응답 포맷 차이 흡수, 요금제/레이트리밋 관리, 장애 대응
포인트가 그만큼 늘어나는데, 이전 프로젝트에서 4개를 쓴 것도 "다양하게
써봤다"는 것 이상의 명확한 근거가 각 프로바이더마다 있었던 건 아니었다.

## 결정

- **메인 프로바이더: OpenAI API** — 검색 Query Rewrite + Text-to-DSL,
  가격/이상거래 설명 생성, Agentic Tool-Calling의 최종 응답 생성 등
  전체 파이프라인의 기본 LLM 호출은 전부 OpenAI로 처리한다.
- **보조 프로바이더: Claude API** — 스트레치 단계에서, 아래 두 가지
  용도가 있을 때만 사용한다. 이 두 용도 외의 일반적인 "가끔 다른 모델도
  써보고 싶어서" 같은 이유로는 확장하지 않는다.
  1. **Resilience4j 서킷 브레이커의 실제 폴백 대상.** OpenAI 호출이
     서킷 브레이커 임계치를 넘겨 open 상태가 됐을 때, 정적 안내
     메시지로 끝내는 대신 실제로 Claude API로 전환해서 요청을 계속
     처리한다. 이래야 "회복탄력성"이라는 이름에 걸맞은 데모가 된다 —
     프로바이더가 하나뿐이면 서킷 브레이커의 폴백 경로가 사실상
     "그냥 실패 응답"과 다를 게 없다.
  2. **LLM Judge 평가 하네스에서 비교 평가용.** RAGAS 등으로 파이프라인
     품질을 정량 평가할 때, 평가 모델과 생성 모델이 같으면
     self-preference bias(모델이 자기 출력 스타일을 더 후하게 평가하는
     경향)가 낀다. Claude를 채점자로 써서 OpenAI가 생성한 응답을
     평가하면 이 편향을 줄일 수 있다.
- **Gemini/DeepSeek은 쓰지 않는다.** 이전 프로젝트의 4-프로바이더
  구성과 달리, 이번에는 "프로바이더를 추가하려면 그걸 정당화하는
  구체적인 용도가 먼저 있어야 한다"는 원칙을 지킨다. 지금 시점에 이
  두 프로바이더를 정당화할 구체적 용도가 없으므로 추가하지 않는다.

## 고려한 대안

1. **OpenAI 단일 프로바이더** — 가장 단순하지만, Resilience4j 서킷
   브레이커를 "붙이는 시늉"만 하게 된다. 폴백 대상이 없으면 브레이커가
   open 되든 안 되든 사용자에게 보이는 결과는 실패 응답으로 동일해서,
   회복탄력성 설계를 포트폴리오에서 보여주려는 목적과 어긋난다.
2. **이전 프로젝트처럼 4개 프로바이더(OpenAI/Claude/Gemini/DeepSeek)** —
   각 프로바이더를 어디에 왜 쓰는지 설명하기 어려웠던 이전 경험을
   반복하게 된다. 프로바이더 수 자체가 기술력을 증명하지 않는다는
   판단.
3. **OpenAI(메인) + Claude(보조, 용도 한정) (채택)** — 두 번째
   프로바이더를 추가하되, "서킷 브레이커 폴백"과 "LLM Judge 비교 평가"
   라는 구체적이고 서로 다른 두 가지 근거가 있어야만 추가한다는 원칙을
   명시적으로 남겨서, 이후 세 번째 프로바이더를 추가하고 싶어질 때도
   같은 기준을 적용하게 한다.

## 결과

- Phase 2(AI 서버 최소 골격)에서는 OpenAI 연동만 실제로 구현한다.
  `ai/app/services/llm/`에 `LLMClient` 추상 인터페이스를 두고
  `OpenAIClient`만 구현체로 붙인다 — Claude 클라이언트는 이 인터페이스
  위에 나중에 얹을 자리만 비워둔다(서킷 브레이커/Claude 클라이언트
  실제 구현은 Phase 6 이후 스트레치 단계).
- 향후 세 번째 프로바이더 도입을 검토할 때는, 이 ADR의 "구체적인 용도가
  먼저 있어야 한다" 원칙을 기본값으로 삼는다.
