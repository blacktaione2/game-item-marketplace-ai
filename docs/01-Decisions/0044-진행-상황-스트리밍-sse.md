# ADR-0044: 진행 상황 스트리밍 — 토큰이 아니라 단계를 흘린다

## 상태

채택됨. `POST /api/ai/assistant/stream` 신설(SSE). **기존 `POST /api/assistant`
는 그대로 둔다.** 테스트 AI **270 → 292**.

## 배경

복합 질의는 7~25초가 걸린다. 그동안 화면은 *"의도를 분류하고 필요한 도구를 부르는
중입니다"* 라는 **고정 문구 하나**를 띄웠다 — 20초 내내 같은 글자다. 진행이
멈춘 것과 진행 중인 것이 구분되지 않는다.

## 결정 1: 흘리는 것은 토큰이 아니라 단계다

기본형은 LLM 토큰 스트리밍이지만 여기서는 **단계 이벤트**를 흘린다.

| | 토큰 스트리밍 | 단계 스트리밍 |
|---|---|---|
| 덮는 구간 | 마지막 답변 생성 | **전체** |
| 복합 질의에서 | 정체 구간이 그대로 침묵 | 도구 호출마다 갱신 |
| 구현 범위 | `LLMClient.chat()` 을 스트리밍 API 로 교체 → OpenAI/Anthropic 양쪽 번역 재작성(ADR-0042) | 이미 있는 계측점에 콜백 한 줄 |

**실측이 이 판단을 뒷받침한다.** 워밍된 복합 질의 5.24초의 내역:

```
0.24s  routing            의도 판별
0.24s  thinking step 1    도구를 고르는 중
1.01s  tool search_items  검색 실행
2.36s  thinking step 2
3.21s  tool forecast_item_price
3.23s  thinking step 3
5.24s  done               답변 완성
```

토큰을 흘렸다면 3.23초까지는 여전히 침묵이고 마지막 2초만 빨라 보인다.
**정체는 답변 생성이 아니라 그 앞에 있다.**

## 결정 2: 캐시 적중도 스트림으로 감싼다

"적중이면 스트림을 안 열고 그냥 반환"이 더 빨라 보이지만 채택하지 않았다.
그러면 **프론트가 스트리밍 경로와 일반 응답 경로를 둘 다 갖는다.** 두 경로는 그
자체로 새 버그 표면이고, 적중은 p95 25.9ms(ADR-0026)라 아낄 것도 없다.
적중이면 `cache` 이벤트와 `done` 이 곧바로 나간다 — **응답 모양이 하나다.**

## 결정 3: 기존 엔드포인트를 갈아치우지 않는다

`load/k6/ai-search.js` 와 `verify-container.sh` 가 `POST /api/assistant` 에 걸려
있다. 갈아치우면 이번 변경에 **부하 하네스와 배포 검증이 통째로 딸려온다.**
스트리밍은 덧붙이는 경로이고, `ask()` 의 `on_progress` 기본값이 no-op 이라
기존 호출자는 한 글자도 안 바뀐다.

## 결정 4: `EventSource` 를 쓰지 않는다

`EventSource` 는 **GET 전용이고 `Authorization` 헤더를 못 붙인다.** 토큰을 쿼리
파라미터로 옮기면 되긴 하는데, **그러면 nginx 접근 로그에 토큰이 남는다.**
그래서 `fetch` + `ReadableStream` 으로 직접 읽는다. 대가는 파싱을 손으로 하는
것이고, 그 대가로 붙은 두 줄이 실제로 필요하다:

- `decoder.decode(value, { stream: true })` — 없으면 **한글이 청크 경계에서
  깨진다**(UTF-8 3바이트).
- `buffer = chunks.pop()` — 마지막 조각은 불완전할 수 있다. 안 남기면 청크가
  쪼개진 순간 JSON 파싱이 터진다.

## 실측이 뒤집은 것 둘

설계대로 짜고 나서 **실제로 재보니 둘이 틀렸다.** 둘 다 코드를 읽어서는 안
보였다.

### 1. 가장 긴 대기가 진행 표시에 안 잡혔다

처음엔 도구 호출이 **끝날 때만** 알렸다. 재보니:

```
0.27s  branch
6.86s  tool search_items    <- 6.6초 무음
```

그 6.6초가 LLM 이 어떤 도구를 부를지 정하는 시간이고, **진행 표시를 넣은 이유가
정확히 그 구간**이었다. `thinking` 이벤트를 LLM 호출 **앞에** 넣어 덮었다.
*끝난 것만 알리면 가장 긴 대기가 그대로 침묵으로 남는다.*

### 2. 라벨이 11초 동안 틀린 말을 하고 있었다

`thinking` 을 넣고 다시 재니 이번엔 `thinking → tool` 사이가 11.12초였다.
그런데 응답의 `timings` 가 **`agent_tool_ms: 11150.4`** 라고 말한다 — 그 구간은
생각이 아니라 **도구 실행**(콜드 상태의 임베딩·리랭커 로딩)이었다. 화면에는
11초 내내 "도구를 정하는 중" 이 떠 있었다.

이벤트를 **끝난 것이 아니라 시작하는 것**으로 바꿨다. 화면이 마지막 줄을 "지금
하는 일"로 그리므로 의미가 그래야 맞다. 실패만 한 번 더 알린다 — 성공은 다음
줄이 뜨는 것으로 드러나지만 **실패는 말하지 않으면 안 보인다.**

> **교훈 두 개가 같은 뿌리다.** 진행 표시의 의미는 "무엇이 끝났나"가 아니라
> "지금 무엇을 하고 있나"다. 그리고 **그 답은 재봐야 안다** — 여기서는
> `timings` 가 이미 답을 갖고 있었는데(`agent_llm_ms` / `agent_tool_ms` 를 따로
> 재는 이유가 바로 그것이었다) 이벤트를 붙일 때 그걸 안 읽었다.

### 덤: 귀속은 워밍 여부로 뒤집힌다

| | routing | 지배 구간 | 전체 |
|---|---|---|---|
| 콜드 | 0.98s | **도구 11.1s** (모델 로딩) | 16.4s |
| 워밍 | 0.24s | **LLM 3.6s** | 5.2s |

한쪽만 보고 "에이전트는 도구가 병목" 이라고 적었으면 틀렸을 것이다.
ADR-0020 의 *"병목은 부하 모양에 따라 옮겨간다"* 와 같은 형태다.

## 배포에서만 드러나는 것 — 그리고 그걸 검사하는 법

SSE 는 **로컬 개발 루프가 원리적으로 못 보는 결함**이 셋 있다
(`docs/05-Troubleshooting/로컬-프로세스로는-볼-수-없는-결함.md` 계열).

| 결함 | 로컬에서 왜 안 보이나 | 대응 |
|---|---|---|
| nginx 버퍼링 | Vite dev proxy 는 버퍼링을 안 한다 | 응답에 `X-Accel-Buffering: no` |
| `proxy_http_version` 기본값 1.0 | 프록시 자체가 없다 | nginx 에 1.1 + `Connection ""` |
| 스트림 경로에 한도 누락 | 로컬에서는 한도에 안 닿는다 | `test_assistant_stream.py` 가 두 경로 모두 `limit_assistant` 를 타는지 확인 |

**`proxy_buffering off` 를 nginx 에 적지 않고 헤더를 쓴 이유가 둘이다.**
응답 단위라 같은 `location` 을 지나는 다른 경로(검색·시세)의 버퍼링을 안
건드리고, 설정이 아니라 코드에 붙어 있어 배포 구성이 바뀌어도 같이 따라간다.

`load/verify-sse.sh` 가 **실제로 흐르는지**를 잰다 — 코드로는 알 수 없는 유일한
항목이다. **헤더가 있다는 것과 이벤트가 나눠서 도착한다는 것은 다른 명제**이기
때문이다. 판정은 절대 시간이 아니라 **첫 이벤트 시각 / 마지막 이벤트 시각 비율**
이다(< 0.5). 절대값은 질의·서버 속도로 달라지지만 "첫 이벤트가 끝과 거의 동시"
라는 성질은 안 달라진다. 두 가지를 더 조심했다:

- **복합 질의로 잰다.** FAQ 로 재면 서버가 즉답해서 버퍼링돼 있어도 "빨리 왔다"로
  보인다 — 그건 검사가 아니라 우연이다.
- **`curl -N` 을 쓴다.** 없으면 curl 자신이 버퍼링해서, 서버가 흘려도 한꺼번에
  온 것처럼 보인다(검사가 자기 자신 때문에 틀리는 형태다).

`verify-container.sh` 에 넣지 않은 이유는 비용이다 — 그건 이미 하루 50회 중
9회를 쓴다.

## 결정 5: 일일 한도는 캐시 적중을 세지 않는다

스트리밍 경로가 같은 한도를 타는지 확인하다가 **원래 있던 어긋남**을 찾았다.

`limit_assistant` 은 FastAPI 의존성이라 핸들러보다, 따라서 **캐시 조회보다**
먼저 돈다. 그래서 두 한도가 모두 캐시 적중을 셌다. 두 경로가 서로 다르지는
않았으므로 스트리밍이 만든 문제는 아니고, 문서에도 한 줄 적혀 있었다 —
*"캐시 조회보다 앞이라 적중도 카운트된다"*. 그런데 그건 **`Depends` 순서의
결과를 서술한 것이지 결정이 아니다.** ADR-0024·0031 어디에도 근거가 없다.

두 한도의 목적이 다르다.

| | 목적 | 캐시 적중 | 세는 시점 |
|---|---|---|---|
| **20회/분** | 부하·남용 차단 | **센다** | 요청 **앞** (의존성) |
| **50회/일** | **LLM 비용** | **안 센다** | 응답 **뒤** (`consume_daily`) |

분당까지 적중을 빼면 캐시되는 질의 하나로 서버를 무한정 두드릴 수 있다.
반대로 일일 한도는 README 가 *"진짜 상한은 OpenAI 월 사용량 한도"* 라고 적은
**비용 계층**인데, 비용 0인 요청이 그 예산을 깎고 있었다.

**이론이 아니라 실제로 닿던 경로다.** ADR-0037 이 배지를 정직하게 유지하려고
`staleTime` 을 일부러 안 걸었고(`refetchOnMount` 는 기본 `true`), 그래서
**아이템 상세에 들어갔다 돌아올 때마다 재요청**이 나간다. 서버는 캐시 적중으로
25.9ms 에 답하는데 하루 50회는 그렇게 소진된다.

### 대가

- **검사와 증가 사이에 동시 요청이 끼면 하루 경계에서 몇 건 샌다.** 이 계층은
  이미 고정 윈도우의 2배 누수를 하루 단위에서 수용하고 있으므로 같은 크기다.
- **리미터가 순수 의존성이 아니게 됐다.** 두 라우트가 응답을 보고 정산해야 하고,
  그래서 `_ask_metered()` 하나만 부르게 묶었다 — 규칙이 갈라지면 **스트리밍
  경로가 곧 상한 우회로**다. `test_assistant_stream.py` 가 두 핸들러 모두
  `ask()` 를 직접 부르지 않는지 소스로 확인한다.
- **실패한 요청은 소비한다.** 거기까지 갔으면 LLM 호출이 이미 나갔을 수 있고,
  실패를 공짜로 만들면 그 자체가 우회로가 된다.

### 조용히 사라질 수 있는 자리 둘

- **검사와 증가가 다른 키를 쓰면 한도가 없어진다** — 검사는 영원히 0을 읽고
  증가는 아무도 안 보는 카운터를 올린다. 정상 응답만 나오므로 아무도 모른다.
  `_daily_key()` 하나를 양쪽이 쓰게 하고 테스트로 박았다.
- **`_peek` 는 올리기 전에 보므로 `_hit` 과 부등호가 하나 다르다**
  (`<` vs `<=`). 그대로 옮겨 적으면 한도가 1 늘어난다.

### 실측 (로컬 Redis, FAQ 질의라 LLM 0회)

| | `cache.hit` | 일일 카운터 |
|---|---|---|
| **미적중 x2 (대조군)** | False | 0 → **1 → 2** |
| **적중 x3** | True | **2 → 2 → 2** |

**대조군이 요점이다.** 적중만 재면 "적중이 안 센다"와 "증가가 통째로 고장"이
구분되지 않는다 — 처음 잰 결과가 정확히 그 상태(전부 적중, 카운터 0)였고,
그대로 통과시킬 뻔했다.

## 배포에서 실제로 막힌 것 — 프록시가 **둘**이었다

`load/verify-sse.sh` 가 첫 실행에서 **버퍼링을 잡았다.** 이벤트 8건이 전부 마지막
0.27초에 몰려 왔다(전체 13.98초, 비율 0.98). 검사를 만든 이유가 정확히 이것이다.

두 가지가 겹쳤고 둘 다 이 ADR 이 놓친 것이다.

### 1. nginx 는 그 헤더를 존중하면서 **동시에 지운다**

`Date` · `Server` · `X-Pad` · `X-Accel-*` 는 nginx 가 업스트림 응답에서
클라이언트로 넘기지 않는 **기본 숨김 목록**이다. 우리 nginx 하나만 있으면 문제가
없다 — 존중하면 끝이다.

그런데 이 배포는 **`https://` 다.** `gimp-web` 은 평문 80 을 내므로 **TLS 를
끝내는 프록시가 앞에 하나 더 있다**(공유 박스의 호스트 nginx). 우리 nginx 가
헤더를 소비하고 지우니, **앞단은 아무 지시도 못 받고 자기 차례에 버퍼링한다.**

`proxy_pass_header X-Accel-Buffering;` 로 그 헤더만 기본 숨김에서 빼냈다. 존중과
전달은 별개라, 우리 nginx 는 계속 버퍼링을 끄면서 **앞단도 같은 지시를 받는다.**

> **"프록시 한 겹"을 가정하고 설계했다.** 결정 4 의 표가 *"nginx 버퍼링"* 을 한
> 줄로 적은 것이 그 가정이다. 실제 배치는 공유 박스라 TLS 프록시가 하나 더 있고,
> 그건 저장소 밖에 있다 — **저장소 안의 설정만으로 닫히지 않는 항목이 있다는
> 것 자체를 적어두지 않은 것이 빠진 부분이다.**

### 2. 내 검사의 판정 하나가 참이 될 수 없었다

첫 판본은 **응답에 `X-Accel-Buffering` 이 있는지를 FAIL 로 걸었다.** 위 기본 숨김
때문에 **프록시를 거치면 그 헤더는 없는 게 정상**이고, 그 검사는 통과할 방법이
없었다. 게다가 헤더가 없다는 사실은 "앞단이 지웠다"와 "앱이 안 붙였다"를
구분해주지도 않는다.

앱이 붙이는지는 `test_assistant_stream.py` 가 소스로 고정하므로, 배포 검사가
판정할 것은 **실제로 나눠서 도착하는가** 하나다. 헤더 줄은 참고로 내린다.

> **프록시가 소비하는 헤더는 응답에서 확인할 수 없다.** 확인하려면 그 프록시의
> *행동*을 봐야 한다 — 이 검사가 비율을 보는 이유가 그것인데, 정작 같은 검사
> 안에서 헤더 존재를 판정으로 걸어 스스로 모순이었다.

### 고친 뒤 — 사슬의 두 지점에서 재서 층을 짚었다

같은 검사를 두 주소로 돌렸다.

| | 비율 | `X-Accel-Buffering` | 전체 |
|---|---|---|---|
| **A** `http://localhost:8081` (우리 nginx 만) | **0.01** | **있음** | 12.70s |
| **B** `https://item-exchange.duckdns.org` (+ 앞단) | **0.02** | **없음** | 4.39s |

**둘 다 흐른다. 그리고 B 에서 헤더가 사라진 것이 실패가 아니라 증거다** —
앞단이 그 헤더를 받아 소비했고(그래서 없어졌고) 버퍼링을 껐다(그래서 0.02 다).
A 에 남아 있는 것은 `proxy_pass_header` 가 기본 숨김에서 빼냈다는 확인이다.

수신 순서(B, 워밍):

```
0.08s  routing → branch → thinking
0.82s  tool search_items
1.95s  thinking
2.71s  tool forecast_item_price
4.39s  done
```

> **같은 검사를 사슬의 두 지점에서 돌리면 층을 짚을 수 있다.** 한 지점만 재면
> "버퍼링된다"까지가 끝이고 어느 프록시인지는 추측이 된다. 헤더 유무가 A 와 B 에서
> 갈리는 것 자체가 어느 층이 그걸 소비했는지 알려준다 — **소비되는 헤더는
> 사라지는 위치로 추적한다.**

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| LLM 토큰 스트리밍 | 정체 구간을 못 덮는다. 게다가 `chat()` 을 통째로 바꿔야 하고 그러면 OpenAI/Anthropic 번역을 다시 짜야 한다(ADR-0042) |
| WebSocket | 단방향인데 양방향 프로토콜을 쓴다. nginx·인증·재접속이 전부 새로 붙는다 |
| 캐시 적중은 스트림 없이 반환 | 프론트에 코드 경로가 둘 생긴다. 아끼는 것은 25.9ms |
| 기존 엔드포인트를 스트리밍으로 교체 | 부하 하네스와 배포 검증이 딸려온다 |
| nginx `proxy_buffering off` | `location` 전체에 걸린다. 응답 단위 헤더가 더 좁다 |
| 폴링(`GET /status`) | 상태를 서버에 저장해야 한다. 지금은 요청 하나가 상태를 다 들고 있다 |

## 영향

- **`app/core/progress.py` 신설.** `assistant/` 가 아니라 `core/` 인 이유는
  `agent` 도 쓰기 때문이다 — `assistant/` 에 두면 `pipeline → agent → assistant`
  로 순환 임포트가 된다.
- **`ask()` 와 `run_agent()` 에 `on_progress` 추가, 기본값 no-op.** 기존 호출자
  무변경.
- **콜백 실패는 파이프라인을 안 죽인다**(`safe_emit`). 클라이언트가 끊겼다고
  요청이 실패하면 안 된다. 다만 **조용히 삼키지 않고 경고를 남긴다** — 이
  저장소는 `except: pass` 하나 때문에 캐시가 죽은 걸 아무도 몰랐던 전례가 있다.
- **클라이언트가 끊으면 작업을 취소한다.** 안 그러면 아무도 안 읽는 답변에 LLM
  요금이 계속 나간다.
- **스트림이 열린 뒤의 오류는 상태 코드가 아니라 페이로드다.** 헤더가 이미
  나갔으므로 404/503/500 을 낼 방법이 없다. `{"type":"error"}` 로 보내되
  **예외 문자열은 안 싣는다**(ADR-0041 과 같은 자세).
- **프론트 번들 +0.64KB gzip** (js +0.59, css +0.05). 실측이다 — 변경 전후로
  각각 빌드해서 뺐다.
- 테스트 **270 → 292**. 절반은 SSE, 절반은 일일 한도(결정 5)다.

## 한계

- **배포에서 밟았고 통과했다** — 위 「고친 뒤」 참조(A 0.01 / B 0.02, 각 3/3).
  다만 그건 **프록시 두 겹까지**이고, 앞단 설정은 저장소 밖이다. 그쪽이 바뀌면
  이 항목은 다시 열린다 — `verify-sse.sh` 가 그때 잡아줄 유일한 수단이다.
- **재접속·재시도가 없다.** SSE 의 `Last-Event-ID` 재개는 서버가 진행 상태를
  들고 있어야 성립하는데, 지금은 요청 하나가 상태를 다 들고 있다. 연결이 끊기면
  사용자가 다시 묻는다 — 20초짜리 요청에 대해 그건 충분히 나쁘지만, 재개를
  지원하려면 상태 저장소가 먼저다.
- **`/api/assistant` 와 두 벌이 됐다.** 두 경로가 같은 `ask()` 를 부르므로 로직은
  하나지만, 라우터가 둘이라 응답 형태를 바꿀 때 양쪽을 봐야 한다.
- **콜드 상태의 캐시 저장 구간(약 10초)은 여전히 무음이다.** 임베딩 모델 지연
  로딩이고 두 번째 요청부터는 사라진다. 실제 상황이 아닌 것에 UI 문구를 붙이지
  않았다.
