# ADR-0026: 적중 경로에서 임베딩을 계산하지 않는다 — 막는 것은 자기 요청만이 아니었다

## 상태

채택됨. **ADR-0025의 결정 2를 정정한다**(그 문서에도 정정 블록을 넣었다).

## 배경 — 표적을 두 번 잘못 잡았다

| | 지목한 것 | 실제 |
|---|---|---|
| ADR-0020 | "임베딩 낭비" (코드 읽기) | 방향은 맞았으나 비중은 안 쟀다 |
| ADR-0025 | "조회가 73%니 임베딩은 아니다" (부하 중 wall-time) | **73%를 만든 원인이 그 27%였다** |
| **ADR-0026** | **격리 측정** | 임베딩이 이벤트 루프를 막는다 |

이번 라운드는 원래 "조회 최적화"로 설계했다. **예측값의 근거를 대려다 전제가
무너졌다** — 검토자가 "48.1 → 20ms의 20은 어디서 나왔나"를 물었고, 답하려면
단일 GET 왕복 비용을 알아야 했는데 모르고 있었다.

## 측정 — 격리하니 다른 그림이 나왔다

부하 없이 단일 요청으로 쟀다(스크래치패드 벤치, 50회 평균).

| | 격리 | 부하 중(10 VU) |
|---|---|---|
| Redis `GET` (단일 키) | 0.46ms | — |
| `SMEMBERS` + `MGET`(2키) + 파싱 | 1.00ms | — |
| **`lookup()` 정확 일치 전체** | **1.05ms** | **48.1ms** |
| **`encode_one`** | **15.77ms** | 18.0ms |

**Redis 작업은 1ms다.** 48ms 중 47ms는 Redis가 아니다.

### 이벤트 루프가 실제로 막힌다

`encode_one`을 반복 호출하면서 10ms 타이머를 함께 돌렸다.

```
10ms 타이머의 평균 지연   17.28ms
10ms 타이머의 최대 지연   36.02ms
```

`encode_one`은 `async def` 핸들러 안의 **동기 CPU 호출**이라 그 시간만큼
**이벤트 루프 전체가 멈춘다.** 동시 부하에서는 **다른 요청의 `await`가 그만큼
밀리고**, 그 대기가 그 요청의 `cache_lookup` 구간에 잡힌다.

> **동시성 하에서 측정한 단계별 wall-time은 작업량이 아니다.** 그 단계가
> 루프를 막는 동기 호출을 포함하면, 다른 요청의 대기를 자기 시간으로 흡수한다.
> 일반화한 교훈은 [[합계만-재고-원인을-지목했다]] 사례 2.

## 결정: 임베딩을 값이 아니라 콜러블로 넘긴다

```python
# 전
embedding = get_embedding_service().encode_one(query)   # 무조건 계산
hit = await cache.lookup(tenant_code, query, embedding)

# 후
def embed() -> list[float]:      # 결과를 기억한다
    nonlocal embedding
    if embedding is None:
        embedding = get_embedding_service().encode_one(query)
    return embedding

hit = await cache.lookup(tenant_code, query, embed)      # 정확 일치면 안 부른다
```

`lookup()`은 정확 일치 루프에서 반환하므로 **`embed()`를 부르지 않는다.**
유사도 경로와 저장 경로는 그대로 필요하고, 기억해두므로 두 번 계산하지 않는다.

콜러블로 받는 이유는 **캐시 모듈이 임베딩 서비스를 알게 되는 결합을 피하려는
것**이다. 값으로 받으면 호출자가 미리 계산할 수밖에 없고, 그게 문제의 원인이었다.

### 단일 GET 최적화는 채택하지 않았다

원래 설계는 정확 일치를 단일 `GET`으로 끝내는 것이었다. 실측상 아끼는 것이
**0.6ms**(1.05 → 0.46)라 값어치가 없다. `_load_entries`가 하는 만료 엔트리
지연 정리도 그대로 유지된다.

## 예측과 결과

**예측을 격리 측정에서 도출했다** — 안전 마진이 아니다.

> 적중 경로의 작업은 `lookup()` 하나만 남는다(격리 1.05ms). `cache-warm`은
> 전량 적중이라 루프를 막는 요청이 사라지므로 대기도 사라진다.
> → `cache_ms` **10ms 이하**. 빗나가면 원인 모델이 틀린 것이므로 되돌리고 재분해.

| | 수정 전 | 수정 후 | |
|---|---|---|---|
| `cache_ms` 평균 | 66.0ms | **5.3ms** | 예측(≤10ms) 적중 |
| `cache_lookup` 평균 | 48.1ms | **5.3ms** | |
| `cache_encode` 호출 수 | 19,568회급 | **2회** | setup의 저장 2건뿐 |
| **전체 p95** | 279ms | **25.9ms** | **10.8배** |
| 처리량 | ~48 req/s | **316 req/s** | **6.6배** |
| 40초간 요청 | 1,909 | **19,570** | |
| `llm_calls` | 0 | 0 | 무변화 |
| checks | 100% | 100% | 무변화 |

`cache_encode` 호출 수 **2회**가 구조적 증거다 — 19,568번의 적중에서 임베딩이
한 번도 계산되지 않았다.

## 검증

- **단위 테스트(1순위)**: 정확 일치에 **부르면 터지는 콜러블**을 넘겨도 예외가
  나지 않는지. 적중률·`llm_calls`가 같은 것만으로는 확인되지 않는다 — 결과가
  같아도 내부에서 여전히 즉시 계산하고 있을 수 있다
- 유사도 경로에서는 **정확히 1회** 호출되는지(안 부르면 그것대로 결함)
- 런타임: 적중 응답에 `cache_encode_ms` 키가 **생기지 않는다**
- 부하: 같은 세션에서 전후 비교(위), loadtest 구성은 ADR-0024 것을 그대로

테스트 116 → **118건**.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| **단일 GET으로 정확 일치** | 실측 이득 0.6ms. 원래 설계였지만 표적이 틀렸다 |
| `asyncio.to_thread`로 임베딩을 빼기 | **더 근본적이지만 이번 범위 밖.** 미적중 경로까지 포함해 전 요청의 동작을 바꾸므로 별도 결정이다. 측정값을 붙여 등록했다 |
| `lookup`이 임베딩 서비스를 직접 부르기 | 캐시 모듈이 임베딩에 결합된다. 콜러블이면 안 생긴다 |
| 미적중 경로도 이번에 최적화 | 유사도 게이팅이 **저장된 엔트리의 의도** 기준이라(ADR-0012) 조회 시점엔 후보를 몰라 전체 로드를 피할 수 없다 |

## 영향

- **적중 경로에만 효과가 난다.** 미적중 위주 부하에서는 이득이 없고, 임베딩은
  여전히 루프를 막는다 — 근본 해결(`to_thread`)은 로드맵에 등록했다
- ADR-0020의 원래 직감("적중 경로에서 임베딩을 빼라")이 옳았다. 다만 그 근거로
  적혀 있던 이유(단순 낭비)보다 **효과가 훨씬 컸다** — 낭비가 자기 요청에서
  끝나지 않았기 때문이다
- **README의 "측정된 결과"에 처음으로 큰 폭의 개선 수치가 들어간다**(p95 10.8배)
- 이번 발견의 패턴이 **다른 단계 결론에도 적용될 수 있다.** 지금 뒤지지는 않되
  "비슷한 이상치가 나오면 이 패턴부터 의심하라"는 표식을 로드맵에 남겼다
