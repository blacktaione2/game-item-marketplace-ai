# ADR-0015: `element` 속성 하드 필터 — 속성은 "효과" 기준이고 저항은 속성이 아니다

## 상태

채택됨

## 배경

ADR-0014가 `subcategory`로 종류 혼입을 막았지만 **속성은 텍스트 신호로 남아
있었다.** 그 결과가 두 가지로 나타났다.

| 질의 | 이전 상태 |
|---|---|
| `"불속성 검 찾아줘"` | 검류 **7건 전부** 반환 — 그중 불속성은 1건 |
| `"3만원 이하 불속성 검"` | 조건 만족 아이템이 코퍼스에 없는데 **근사치 3건** 반환 |

두 번째가 더 중요하다. `"조건에 맞는 매물이 없다"`고 답하는 처리(로드맵 다음
항목)는 **ES가 0건을 반환하는 경로가 실제로 존재해야** 만들 수 있다. 속성이
필터가 아닌 동안에는 이 질의가 항상 검류를 채워 돌려줘서 그 경로를 밟을 수
없었다.

메커니즘은 판단할 게 없다 — `subcategory`와 **완전히 같다**(keyword 필드 +
term 절). 임계값이 없다는 장점도 같다. 그래서 이 ADR이 기록하는 것은
메커니즘이 아니라 **"무엇을 속성으로 볼 것인가"라는 분류 규칙**이다. 그쪽은
자명하지 않았다.

## 결정

`element` keyword 필드 + `SearchFilters.element` → `term` 절. 정본 어휘는
**`화염` / `냉기` / `번개` / `암흑` / `신성` / `무속성`** 6종.

### 규칙 1: 정본 어휘는 코퍼스 설명문의 단어를 쓴다

사용자는 `"불속성"`이라고 하지만 아이템 설명문은 `"화염 계열 마법 위력 25%
증가"`라고 쓴다. 정본을 **설명문 쪽**으로 잡았다 — BM25 텍스트와 필터 값이
같은 단어를 쓰게 된다. 사용자 표기는 프롬프트 대응표가 흡수한다
(`불`/`불속성`/`화염`/`파이어` → `화염`, `전기`/`뇌전` → `번개` 등).

### 규칙 2: 저항은 속성이 아니다

**효과의 방향이 반대인 것을 같은 값으로 묶으면 안 된다.**

| 아이템 | 설명문 | 태깅 |
|---|---|---|
| 용비늘 방패 | 화염 피해 40% **감소** | `무속성` |
| 암흑 로브 | 암흑 속성 **저항** 25% | `무속성` |
| +9 강화 미스릴 갑옷 | 모든 속성 **저항** 10% | `무속성` |

용비늘 방패를 `화염`으로 태깅하면 `"불속성 장비 찾아줘"`가 **대(對)화염
방패**를 돌려준다. 그건 지금 없애려는 오탐과 정확히 같은 종류다. `element`는
"그 아이템이 내는 속성"이고 저항은 별개 축이다. 프롬프트에도
`"화염 저항 방어구"` 같은 질의는 `element`를 `null`로 두라고 명시했다.

### 규칙 3: 이름이 아니라 효과로 판정한다

| 아이템 | 이름 | 효과 | 태깅 |
|---|---|---|---|
| 바람의 장궁 | 속성어 있음 | 공격력 +140, 사거리 증가 (순수 물리) | `무속성` |
| 그림자 암살검 | 속성어 있음 | 치명타 +45%, 은신 중 공격력 | `무속성` |
| 성기사의 워메이스 | 없음 | **신성 피해** 추가 | `신성` |
| 폭풍의 창 | 없음 | **번개 속성 피해** 추가 | `번개` |

이름은 게임의 작명 관습이고 속성은 기능이다. 둘이 어긋나는 케이스가 양방향으로
있어서(이름만 속성어 / 이름엔 없는데 속성 있음) 기준을 하나로 못박아야 했다.

### 규칙 4: `무속성`은 값이고 `null`이 아니다

- 데이터의 `"무속성"` = **이 아이템은 속성이 없다**
- 필터의 `None` = **속성 조건을 걸지 않는다**

섞으면 `"검 찾아줘"`에 `element="무속성"`이 들어가 불꽃의 대검이 사라진다.
42건 전부가 값을 갖고, 없으면 임포트 시점에 터진다.

### 분포

| 속성 | 건수 | 아이템 |
|---|---|---|
| `화염` | 3 | 불꽃의 마법봉 · 불꽃의 대검 · 용의 숨결 지팡이 |
| `냉기` | 1 | 얼음 서리 지팡이 |
| `번개` | 1 | 폭풍의 창 |
| `신성` | 1 | 성기사의 워메이스 |
| `암흑` | 1 | 심연의 귀걸이 |
| `무속성` | 35 | 나머지 |

### 구현

- `app/corpus/{train,eval}_items.py` — 42건 전부에 `element` 부여
- `search/mapping.py` — `keyword` 필드, `search/filters.py` — `term` 절
- `search/query_understanding.py` — 스키마·표기 대응표·저항 예외·예시 3건.
  **속성이 언급되지 않으면 `null`**을 명시
- `corpus/__init__.py` — 가드를 `HARD_FILTER_FIELDS = ("subcategory",
  "element")` 로 일반화. 값이 빠진 아이템은 그 필터가 걸린 검색에서
  **조용히 사라지므로** 임포트 시점에 터뜨린다. 3가지 충돌(줄 삭제 / 빈
  문자열 / subcategory 삭제)을 주입해 전부 발동함을 확인했다
- MCP 도구 출력·프론트 결과 카드에 노출. 카드에서 `무속성`은 안 띄운다
  (42건 중 35건이라 노이즈다 — `+0` 강화나 `0`렙을 안 띄우는 것과 같은 규칙)
- `scripts/evaluate_hard_filters.py` 신설 — 아래 측정용

## 결과

`scripts/evaluate_hard_filters.py`. 질의 10건 × 상위 8건, 라벨 34~46건.

**이전/이후를 같은 실행 안에서 쟀다.** 지난 실행의 집계와 비교하면 그 사이
질의 재작성이 달라진 효과가 섞인다 — 리랭커 하한이 기각된 것과 같은 함정
(ADR-0014)이라, `element` 절만 빼는 패스를 연달아 돌려 A/B로 잡았다.

| 질의 | 적합 이전→이후 | 부적합 이전→이후 |
|---|---|---|
| `"불속성 검 찾아줘"` | 1 → 1 | **6 → 0** |
| `"얼음속성 지팡이"` | 1 → 1 | **3 → 0** |
| `"3만원 이하 불속성 검"` | 0 → 0 | **3 → 0** |
| 나머지 7건 (속성 조건 없음) | 변화 없음 | 변화 없음 |
| **합계** | **20 → 20** | **26 → 14 (−46%)** |

**적합 손실 0건.** 부적합 12건 감소가 전부 속성 질의 3건에서 나왔고, 속성
조건이 없는 질의 7건은 한 건도 변하지 않았다 — 효과의 귀속이 깨끗하다.
이전 상태의 부적합 26건은 ADR-0014가 기록한 수치와 정확히 일치한다.

### 핵심: 0건이 재현된다

```
3만원 이하 불속성 검 찾아줘
  필터  {'category': '무기', 'subcategory': '검', 'element': '화염', 'price_max': 30000.0}
  결과 0건
  5회 반복 → 결과 건수 분포 {0: 5}   0건 5/5회
```

**한 번 0건인 것은 증거가 아니다** — 질의 재작성이 비결정적이라 필터 추출이
실행마다 흔들릴 수 있다. 5회 반복해서 필터 조합까지 동일하게 재현되는 것을
확인했다. 이제 "결과 없음" 처리가 밟을 수 있는 테스트 케이스가 존재한다.

참고로 지금도 답 자체는 맞게 나온다 — 어시스턴트가
`"검색 결과가 없습니다. 해당 가격대의 불속성 검 아이템이 존재하지 않거나…"`
라고 답했다. 하지만 그건 **결과 0건을 LLM에게 넘겨서 LLM이 알아서 맞춘
것**이고, 필요 없는 LLM 호출을 쓰며 LLM이 항목을 지어내지 않는다는 보장도
없다. 구조적 처리는 여전히 다음 항목이다.

## 고려한 대안

1. **저항까지 `element`에 묶기** — 위 규칙 2. 오탐 방향이 반대라 기각.
   저항 검색이 필요해지면 별도 축(`resist_element`)이어야 한다.
2. **속성을 다중값(배열)로** — 현재 코퍼스에 속성이 둘인 아이템이 없다.
   단일 `keyword`로 충분하고, 배열은 필요해질 때 넣어도 매핑 호환된다.
3. **이름 기준 태깅** — 규칙 3. 양방향으로 어긋나서 기각.
4. **프롬프트로 걸러내게 하기** — ADR-0014에서 이미 불안정함이 확인됐다.

## 알려진 한계

### 1. 세 번째 축이 남았다 — 다만 "공짜"가 아니다

측정 중 발견했다. `"2만원 이하 전설 등급 무기"`도 정답이 0건인 질의인데
**부적합 3건을 계속 돌려주고, 5회 전부 0건이 안 됐다**(결과 건수 분포
`{3: 5}`). `전설 등급`이 아직 텍스트 신호이기 때문이다 — `element` 이전의
속성과 정확히 같은 상태다.

**그런데 이건 `subcategory`/`element`와 같은 작업이 아니다.** 그 둘은 설명문에
이미 근거가 있어서 태깅이 *판독*이었다. 등급은 코퍼스에 개념 자체가 없어서
**새로 발명**해야 한다 — `미스릴 단검`이 몇 등급인지는 데이터가 답해주지
않는다. 착수하려면 등급 체계를 먼저 정의해야 하고, 그건 별도 판단이다.

즉 **"결과 없음" 처리를 넣어도 이 질의는 여전히 근사치를 돌려준다.** 다음
작업의 범위를 잡을 때 이걸 계산에 넣어야 한다.

### 2. 라벨이 이름 기반이라 비순환이지만 대가가 있다

`is_fit()`은 `element` 필드를 **보지 않는다.** 필드로 라벨하면 "element 필터가
element 조건을 만족시켰는가"가 되어 순환논증이다. 대가로, 이름에 속성어가
없는 속성 아이템(`성기사의 워메이스`·`폭풍의 창`·`용의 숨결 지팡이`)은 속성
질의에서 필터가 남겨도 라벨이 부적합으로 센다. 현재 질의셋에서는 이 셋이
필터를 통과할 수 없어 실제로 발생하지 않지만, 질의를 늘릴 때 확인해야 한다.

### 3. 표본이 작고 편중돼 있다

42건 중 속성 보유가 7건, 속성 질의가 3건뿐이다. 부적합 −46%는 그 3건에서만
나온 수치이므로 **"속성 질의에서는 확실히 듣는다"까지가 근거이고, 검색 품질
전반의 개선률로 읽으면 안 된다.** `무속성`이 35/42라 필터 선택성도 낮다.

### 4. `subcategory`의 한계는 그대로다

`"단검 보여줘"`는 여전히 부적합 6건(롱소드·대검이 같은 `검`). ADR-0014 한계 3.
