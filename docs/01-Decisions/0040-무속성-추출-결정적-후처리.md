# ADR-0040: `무속성` 은 프롬프트가 아니라 코드로 채운다

## 상태

채택 (2026-08-08). 로드맵에 "평가셋 구축이 선행" 으로 묶여 있던 항목이다.

## 배경

`"무속성 검 찾아줘"` 가 `element="무속성"` 을 **50번 중 8번만** 낸다. 나머지는
`null` 이다 — 모델이 "무속성" 을 **"속성 언급 없음"** 으로 읽는다.

대가가 크다. 코퍼스 42건 중 **35건이 무속성**이라, 이 필터가 빠지면 검색이 사실상
무필터가 된다. 무속성 검을 요청해도 불꽃의 대검이 섞여 나온다.

### 왜 지금까지 못 쟀나 — 재는 도구가 아니라 **잴 입력**이 없었다

| 하네스 | 무엇을 재나 | 왜 이 결함을 못 보나 |
|---|---|---|
| `evaluate_rewrite_determinism` | **안정성** (같은 질의 두 번) | 두 번 다 틀려도 만점 |
| `evaluate_hard_filters` | 필터가 걸린 뒤 부적합 결과 수 | 필터가 **아예 안 걸리면** 지표에 안 나타남 |

그리고 결정적으로 **`data/` 의 질의 547건 중 `무속성` 을 언급하는 것이 0건이다.**

## 결정 — 프롬프트를 건드리지 않는다

프롬프트에는 **이미** 이렇게 적혀 있다.

```
- 무속성/속성 없는 -> "무속성"
- null("속성 조건 없음")과 "무속성"("속성이 없는 아이템만")은 다릅니다.
```

**정확히 옳은 말로 이미 지시받았는데 42/50 을 틀린다.** 프롬프트가 부족한 게
아니다. 그리고 이 자리는 이 저장소가 프롬프트 한 줄로 **97.5% → 22%** 를 겪은 바로
그 자리다 — 혼동 대상(`불속성`)을 이름으로 부르자 모델이 그쪽으로 쏠렸다. 직전
라운드(ADR-0039 「정정」)에서도 프롬프트 변형 셋이 연달아 기각됐다.

> **결정 단계가 보장할 수 있는 것을 LLM 에게 다시 묻지 않는다.** ADR-0036 이 검색
> 설명 LLM 을 없애고 ADR-0039 가 `_out_of_domain()` 에서 인자를 없앤 것과 같은
> 처방이다. **질의에 그 글자가 있는지는 코드가 확실히 안다.**

`fill_missing_element(query, element)` — 추출이 `null` 을 냈고 질의에 `무속성`
또는 `속성 없…` 이 글자 그대로 있으면 채운다.

### 채우기만 하고 덮어쓰지 않는다

`element` 가 이미 있으면 손대지 않는다. 그래서 이 함수는

- 지금 잘 되는 다른 속성 추출에 **닿을 수 없고**
- `"불속성"` 이 `무속성` 으로 나오는 별개 결함(약 1%)도 안 건드린다 — 그건
  `null` 이 아니라 **잘못된 값**이라 조건을 통과하지 못한다

실패 방향도 한쪽이다. 질의에 표현이 없으면 아무 일도 안 일어나므로,
`"검 찾아줘"` 에 무속성이 끼는 사고는 **구조적으로 불가능**하다.

### `무속성` 하나만 다룬다 — 넓히면 지금 되는 것이 깨진다

다른 속성으로 넓히고 싶어진다. 안 된다.

> `"화염 저항 방어구"` 는 `화염` 을 담고 있지만 정답은 `null` 이다. element 는
> 아이템이 **내는** 속성이고 저항은 별개 축이다. 지금 프롬프트가 이걸 맞게 처리한다
> (평가셋 저항 무리 12/12). **낱말로 밀면 이 무리가 통째로 깨진다.**

`무속성` 에는 그런 짝이 없다(`무속성 저항` 은 말이 안 된다). 그래서 이 하나만
안전하다.

### 부정형은 **알려진 한계**다

`"무속성 아닌 검"` 의 옳은 답은 "무속성을 제외한 전부" 인데 `SearchFilters.element`
는 동등 비교 하나뿐이라 표현할 수 없다. 그래서 **필터를 안 건다** — 맞는 답이라서가
아니라 표현 가능한 최선이라서다.

여기서 지키는 것은 "부정형을 알아듣는 것" 이 아니라 **"무속성을 잘못 채우지 않는
것"** 이다. 채우면 사용자가 원한 것의 **정반대**를 준다.

## 평가셋 — 네 무리로 나눈 이유

`app/corpus/element_queries.py`, 39건 전부 수작업 + 정답 라벨.

| 무리 | 정답 | 없으면 |
|---|---|---|
| `무속성` (14) | `"무속성"` | 고치려는 결함이 안 보인다 |
| `타속성` (8) | 해당 속성 | 무속성 고치다 다른 속성을 덮어써도 모른다 |
| **`미언급` (10)** | `None` | **"전부 무속성" 이 만점을 받는다** |
| `저항` (4) | `None` | `"화염 저항 방어구"` 가 화염으로 걸린다 |
| `부정형` (3) | `None` (한계) | 정반대를 주는 것을 못 잡는다 |

`미언급` 에 `"속성 좋은 무기"` 를 일부러 넣었다 — `속성` 이라는 낱말은 있는데 답은
`None` 이다. 낱말로 미는 구현은 여기서 걸린다.

`무속성` 에는 **일부러 미수록 표현**(`"속성 안 붙은 신발"`)을 하나 넣었다. 전부 맞는
평가셋은 한계를 못 보여준다.

## 측정 — A/B 에 추가 호출이 들지 않는다

후처리는 **질의와 추출 결과만으로 결정되는 함수**다. 원본 추출을 한 번 수집해두면
"후처리 적용" 은 채점 시점에 계산할 수 있다. 그래서 전후를 몇 번이든 다시 봐도
API 호출이 0이다(`--score-only`).

39건 × 3회 × 2실행 = **LLM 234회**.

| 무리 | 1차 전 → 후 | 2차 전 → 후 | 무속성 오채움 |
|---|---|---|---|
| 무속성 | 62% → **93%** | 86% → **93%** | 0 → 0 |
| 타속성 | 88% → 88% | 88% → 88% | 0 → 0 |
| 미언급 | 100% → 100% | 100% → 100% | **0 → 0** |
| 저항 | 100% → 100% | 100% → 100% | **0 → 0** |
| 부정형 | 100% → 100% | 100% → 100% | **0 → 0** |

### 정확도보다 **결정성**이 더 큰 소득이다

**기준선이 62% ↔ 86% 로 흔들리는데 후처리 뒤는 두 번 다 93%, 잔여 오답까지 같은
두 질의다.** ADR-0017 이래 이 저장소가 붙들고 있던 "같은 질의가 실행마다 다른 답을
낸다" 가 이 축에서는 사라졌다. 결정적 단계가 확률적 단계를 덮으면 그렇게 된다.

## 사전 등록 기준 둘이 실패했고, **고쳐 쓰지 않는다**

```
FAIL  무속성 정확도 >= 95%       (93%)
FAIL  타속성 정확도 >= 95% (회귀) (88%)
PASS  미언급에 무속성 오채움 = 0
PASS  저항에 무속성 오채움 = 0
PASS  부정형에 무속성 오채움 = 0
```

둘 다 **내가 기준을 잘못 쓴 것**이지 변경이 나쁜 게 아니다. 그렇다고 결과를 보고
숫자를 고치면 사전 등록의 의미가 없어지므로, ADR-0028 이 한 대로 **실패한 채로
남기고 채택 근거를 다른 데 둔다.**

- **타속성 88%** — 후처리 **전후가 같다**(21/24 → 21/24, 두 실행 모두). 내 변경이
  닿지 않는 기존 결함이다. 의도는 *"후처리 때문에 나빠지면 안 된다"* 라는 **상대**
  기준이었는데 **절대** 문턱으로 썼다. **두 라운드 전에 held-out 기준을 전부
  대조군 상대값으로 쓴 이유가 정확히 이건데, 여기서 그걸 안 했다.**
- **무속성 93%** — 부족분 3건이 **전부 `"속성 안 붙은 신발"`**, 즉 한계를 드러내려고
  일부러 넣은 미수록 표현이다. 14건 중 1건 = 7.1% > 5% 이므로 **이 기준은 처음부터
  만족 불가능**했다. 그걸 알면서 95% 를 등록한 것이 잘못이다.

### 채택 근거

1. **안전 기준 셋(오채움 = 0)이 사전 등록됐고 두 실행 모두 통과** — 이게 "전부
   무속성으로 채우기" 를 막는 자리다
2. **후처리가 손댄 판정은 두 실행 합쳐 16건, 전부 정답으로 바뀌었다.** 틀린 방향으로
   바꾼 건 0건
3. **회귀 0** — 타속성·미언급·저항·부정형이 두 실행 모두 전후 동일
4. **두 실행이 일치**한다

## 이 라운드가 덤으로 찾은 것

`"어둠 속성 로브"` 가 `element=null` 을 낸다 — **6/6, 두 실행 모두.** 프롬프트에
`어둠/어둠속성/암흑/다크 -> "암흑"` 이 있는데도 그렇다. `무속성` 과 같은 가족이다.

**후처리로 넓히지 않는다.** `암흑` 을 낱말로 채우면 평가셋의 `"암흑 저항 목걸이"`
가 깨진다 — 위 「넓히면 지금 되는 것이 깨진다」 그대로다. 별도 항목으로 등록한다.

## 고려한 대안

| 대안 | 왜 안 했나 |
|---|---|
| 프롬프트 수정 | 이미 옳은 말로 지시돼 있고 42/50 을 틀린다. 같은 자리에서 97.5% → 22% 전례 |
| `element` 를 목록형으로 바꿔 부정 표현 | 매핑·필터·프롬프트·화면이 다 바뀐다. 부정형은 평가셋 39건 중 3건이다 |
| 모든 속성으로 후처리 확대 | `"화염 저항 방어구"` 가 깨진다. 지금 되는 것을 깨는 변경이다 |
| LLM 재질의(속성만 다시 묻기) | 호출이 늘고, 같은 모델에게 같은 것을 다시 묻는 것이다 |

## 영향

- `understand_query()` 가 성공·폴백 **양쪽에서** 후처리를 적용한다. 규칙이 하나여야
  어디서 걸리는지 헷갈리지 않는다. 폴백은 "필터 없는 검색" 이지만 여기서 채우는
  값은 모델의 추측이 아니라 **질의 원문에 있는 글자**라 취지와 어긋나지 않는다
- 테스트 **26건 추가** (AI 177 → 203). 전부 LLM 없이 돈다 — 후처리가 결정적 함수라
  가능하다. 추출 정확도 자체는 스크립트가 잰다
- **검색 결과가 바뀐다.** `"무속성 검"` 이 이제 실제로 6건으로 좁혀진다.
  `cache_version` 을 올릴 필요는 없다 — 응답 **모양**은 그대로다
- 새 스크립트 `evaluate_element_extraction.py`, 새 코퍼스 `element_queries.py`
