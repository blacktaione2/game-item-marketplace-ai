# ADR-0016: 검색 0건은 LLM을 거치지 않고 확정 응답으로 처리하고, 캐시에 저장하지 않는다

## 상태

채택됨

## 배경

`element` 필터(ADR-0015)로 `"3만원 이하 불속성 검"`이 **0건을 반환**하게 되면서,
비로소 "조건에 맞는 게 없다"고 말하는 경로를 만들 수 있게 됐다.

그런데 그때까지의 동작은 **빈 결과 리스트를 그대로 LLM에 넘기는 것**이었고,
LLM이 알아서 "검색 결과가 없습니다"라고 답했다. 답은 맞았다. 문제는 그게
**구조적 보장이 아니라는 것**이다. 같은 입력으로 5회 돌려 측정했다.

| | 답변 종류 | LLM 호출 |
|---|---|---|
| 이전 (빈 결과 → LLM) | **5회 / 5가지** | 2회 |
| 이후 (확정 응답) | **5회 / 1가지** | 1회 |

이전 5건은 전부 답이 맞았다 — **지어내기는 관측되지 않았다.** 측정된 것은
변동성이다. 그리고 문구가 매번 달랐다는 것 외에 공통 결함이 하나 더 있었다:
**어떤 조건으로 찾았는지 다섯 개 모두 말하지 않았다.**

> 사용자의 요청에 맞는 3만원 이하의 불속성 검 제품이 검색 결과에 없습니다.
> 따라서 해당 제품은 찾을 수 없습니다.

결과가 없다는 사실은 전했지만, 시스템이 질의를 **어떻게 해석했는지**는 전하지
않는다. 질의 재작성이 아직 비결정적인 상태(로드맵)에서 이건 실질적인 문제다 —
`"불속성"`을 `냉기`로 잘못 뽑아 0건이 된 경우와 진짜로 없는 경우가 사용자에게
똑같이 보인다.

## 결정

### 1. 0건이면 LLM 호출 없이 확정 응답을 만든다

`_no_results()`가 추출된 필터에서 문구를 조립한다.

```
검 · 화염 속성 · 30,000원 이하 조건에 맞는 매물이 없습니다.
조건을 완화하면 결과가 나올 수 있습니다.
```

5회 실행 전부 문자열까지 동일했다. 필터가 하나도 안 걸린 채 0건이면 완화할
조건이 없으므로 다른 문구로 갈라진다(`"다른 표현으로 다시 검색해 보세요"`).

### 2. `llm_calls`는 0이 아니다

> **[2026-08-07] 이 절의 "1"은 그때의 값이다.** ADR-0036 이 설명 호출을 없애
> 검색 분기 전체가 1이 됐고, ADR-0039 가 도메인 판정을 병렬로 추가해 **지금은
> 2**다(시세는 3). **바뀌지 않은 것은 "0이 아니다"와 그 이유**뿐이다.

**이 수치를 0으로 적고 싶은 유혹이 있는데 틀린 값이다.** `run_search` 안의
`understand_query`가 이미 한 번 호출됐고 **그건 건너뛸 수 없다** — 어떤 필터가
걸렸는지 알아야 0건 판정이 성립하기 때문이다. 없어지는 건 설명 생성 호출
하나다(2 → 1). `llm_calls == 0`은 캐시 적중 경로뿐이고, 그 구분이 흐려지면
캐시 효과 측정이 망가진다(ADR-0012에서 같은 함정을 지적했다).

> **[2026-08-07 정정] 마지막 문장의 역이 틀렸다.** `llm_calls == 0`이 캐시 적중
> 경로"뿐"은 아니다 — `faq_smalltalk`은 LLM 없이 확정 응답을 만들므로
> **미적중에서도 0**이다. 이 문단이 다루는 검색 분기 안에서는 맞는 말이지만,
> 일반 명제로 읽히게 써서 실제로 오독을 낳았다: 컨테이너 검증에 캐시 검사를
> 넣으면서 FAQ 질의로 `llm_calls == 0`을 단언했고, 그 단언은 **캐시가 죽어
> 있어도 항상 참**이었다(실배포 실측 `hit=false, llm_calls=0`). 적중 여부는
> `cache.hit`으로 읽는다.

프론트 배지도 그 기준으로 만들었다 — `no_results`인데 `llm_calls > 1`이면
회귀로 표시된다.

### 3. 걸린 조건을 응답에 노출한다

`applied_filters`(구조화)와 `conditions`(표시용 문구)를 **0건일 때만** 준다.

**비대칭이 의도된 것이다.** 결과가 있으면 항목 자체가 종류·속성을 달고
나오므로(ADR-0014·0015) 사용자가 그걸 보고 판정을 검증할 수 있다. **0건에는
검증할 대상이 없다** — 그때 유일한 근거가 "무슨 조건으로 찾았는가"다. 필드를
항상 붙이는 것보다 이 경계가 이유를 더 잘 설명한다.

### 4. **0건 응답은 캐시에 저장하지 않는다**

이번 작업에서 가장 중요한 결정이다. `is_cacheable(intent, response)`에
응답 기반 예외를 하나 뒀다.

- **0건 판정의 근거인 필터 추출이 비결정적이다.** 0건 응답을 질의 문자열로
  캐시하면 여러 추출 결과 중 하나를 임의로 골라 TTL(10분) 동안 고정하는 셈이
  된다. 판정은 매 요청의 실제 필터 결과로 다시 해야 한다.

  > **2026-07-31 정정 (ADR-0017).** 이 이유는 **측정이 아니라 추론이었다.**
  > 실측하니 `temperature=1.0`에서도 필터 추출은 10질의 × 10회 전부 동일했다
  > (모드 일치율 1.000). 당시 관측한 건 재작성 *텍스트*의 변동이었고 거기서
  > 필터도 흔들릴 것이라고 일반화했다. 완전히 안정적이진 않아서 90회 중 1회
  > 오추출은 있지만(약 1.1%), "비결정적이라 캐시 못 한다"의 근거로 쓰기엔
  > 약하다. **아래 이유 2가 독립적으로 서 있어 결정 자체는 유지된다.**
- **0건은 가장 낡기 쉬운 답이다.** 매물이 하나 등록되면 즉시 거짓이 되고,
  오류의 방향("없다")이 사용자에게 더 나쁘다.

검증: 같은 0건 질의를 두 번 연속 호출해도 2회차가 `cache.hit = False`,
`llm_calls = 1`이고 필터를 새로 뽑는다. 대조군(정상 검색)은 2회차가
`cache.hit = True`, `llm_calls = 0`으로 기존 동작이 유지된다.

## 고려한 대안

1. **프롬프트를 강화해 LLM이 0건을 더 잘 다루게 하기** — ADR-0014에서 프롬프트
   레벨 완화가 질의에 따라 되기도 하고 안 되기도 함을 이미 확인했다. 그리고
   결과가 없다는 걸 이미 아는 상태에서 호출을 쓰는 게 애초에 낭비다.
2. **어떤 조건을 완화하면 결과가 나오는지 제안하기** — 필터를 하나씩 빼며
   ES를 다시 질의해야 한다. 0건 한 번에 추가 질의 N번이고, 이번 범위를 넘는다.
   나중에 필요해지면 별도 항목으로.
3. **0건 응답을 짧은 TTL로 캐시하기** — TTL을 줄여도 결정 4의 첫 번째 이유
   (비결정적 판정을 굳힌다)는 그대로 남는다. 저장 자체를 안 하는 게 맞다.
4. **`results == []`로 판정하기** (별도 플래그 없이) — FAQ 응답은 `results`
   키 자체가 없어서 "검색해서 0건"과 "검색이 아님"이 구분되지 않는다.
   `no_results` 플래그를 명시적으로 둔다.

## 알려진 한계

### 1. 필터 추출이 0건을 만드는 질의에만 적용된다

`"2만원 이하 전설 등급 무기"`도 정답이 0건인 질의지만 **이번 작업으로 고쳐지지
않는다.** `전설 등급`이 아직 텍스트 신호라서(ADR-0015 한계 1) ES가 0건을
반환하지 않고 근사치 3건을 돌려주며, 그러면 이 경로를 아예 밟지 않는다.

이 처리는 **"0건을 만드는 능력"을 만들지 않는다** — 이미 0건이 된 것을 제대로
말하는 것뿐이다. 0건을 만드는 쪽은 하드 필터의 몫이고, `rarity` 축은 등급 체계
정의가 선행돼야 하는 별도 항목이다.

### 2. 캐시가 비대칭이다

0건 응답은 캐시에서 **나오지 않지만**, 직전의 비어있지 않은 결과가 TTL(10분)
동안 살아 있으면 그게 먼저 적중해서 0건 경로를 가린다. `ITEM_SEARCH`를
캐시한다는 기존 결정(ADR-0012)의 결과이고 이번 작업으로 바뀌지 않았다.
방향상 덜 나쁜 쪽이다 — "있다"고 했다가 없는 것이, "없다"고 했다가 있는 것보다
사용자가 확인할 여지가 있다.

### 3. 시세 분기의 0건은 여전히 에이전트로 올라간다

`_forecast_branch`는 아이템을 못 찾으면 에이전트로 에스컬레이션한다. 의도된
기존 동작이다 — 거기서 0건은 "조건에 맞는 매물이 없다"가 아니라 "어느
아이템인지 특정 못 했다"이고, 에이전트는 검색부터 다시 시작할 수 있다.
이번 처리는 `ITEM_SEARCH` 분기에만 넣었다.
