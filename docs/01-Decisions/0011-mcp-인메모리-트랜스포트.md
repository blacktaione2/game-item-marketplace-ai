# ADR-0011: 내부 도구 MCP 서버를 인메모리 트랜스포트로 붙이고, stdio 진입점을 따로 둔다

## 상태

채택됨

## 배경

계획서는 Phase 3~5의 기능(검색·시세예측·이상탐지)을 **내부 MCP 서버로 감싸서**
에이전트가 MCP로 호출하게 한다고 정하고 있다. 외부 서비스 연동(Steam API,
Discord 등)은 스코프 밖이고, 내부 역량을 MCP로 감싸는 것만 대상이다.

> 참고: 최초 기획서 8절은 "MCP — 스코프 크리프 방지"로 제외에 넣었다가,
> 내부 도구 한정으로 범위를 좁혀 재도입한 것이다. 기획서 쪽 문구도 정정했다.

트랜스포트를 정해야 했는데, 이 프로젝트에는 두 가지 제약이 겹쳐 있다.

1. **에이전트가 MCP 클라이언트인 동시에 서버와 같은 FastAPI 앱 안에 있다.**
2. **임베딩 인코딩이 async 함수 안에서 동기로 실행돼 이벤트 루프를 막는다**
   (로드맵 기술 부채). 첫 호출에서 13.5초 블로킹을 실측했다.

## 결정

**MCP SDK의 인메모리 스트림 페어로 클라이언트-서버를 연결한다.**
`Client(server)`에 서버 객체를 직접 넘기면 SDK가 인메모리 트랜스포트를 잡는다.
JSON-RPC 핸드셰이크, `tools/list`, `tools/call`이 모두 실제 프로토콜대로
오간다. 다른 점은 바이트가 소켓이 아니라 메모리 스트림을 지난다는 것뿐이다.

**별도로 `python -m app.services.mcp` stdio 진입점을 둔다.** 같은 서버 정의를
외부 MCP 클라이언트(Claude Desktop 등)에 붙일 수 있다. 이게 있어야 이 서버가
프로세스 안에서만 쓰이는 함수 묶음이 아니라 진짜 MCP 서버임이 드러난다.

**도구는 3종, 새 기능은 없다.** `search_items`, `forecast_item_price`,
`detect_trade_anomaly`가 각각 기존 파이프라인을 호출하는 얇은 래퍼다.

**도구 출력은 API 응답이 아니라 LLM 컨텍스트 페이로드로 취급해 추린다.**
파이프라인 반환값에는 임베딩 순위·타이밍·문서 본문이 다 들어 있는데, 그대로
넘기면 컨텍스트와 비용만 먹는다.

## 고려한 대안

1. **FastAPI에 streamable-HTTP MCP 마운트** — 표준 원격 트랜스포트지만
   에이전트가 자기 자신에게 HTTP를 호출하게 된다. 위 제약 2번(이벤트 루프
   블로킹)과 겹치면 교착이나 타임아웃 위험이 있다. 블로킹 이슈를 먼저
   해결하면 선택지가 된다.
2. **별도 프로세스(stdio 서브프로세스)** — 격리는 가장 확실하고 배포 형태도
   현실적이다. 다만 서버 프로세스가 torch·임베딩 모델·예측 모델·이상탐지
   모델을 또 로드해서 24GB 공유 인프라에 메모리를 두 배로 쓴다. 데모용
   진입점으로는 남겨뒀다.
3. **MCP 없이 in-process 함수 호출** — 가장 단순하지만 계획서의 "MCP 서버
   설계/구현을 보여준다"는 목적 자체를 없앤다.

## 결과

- `ai/app/services/mcp/{server,session,__main__}.py`.
- 도구 스키마는 **타입 힌트에서 자동 생성**되고, 그걸 그대로 OpenAI의 `tools`
  파라미터로 변환한다(`openai_tool_schemas`). 도구 정의를 두 벌 관리하지
  않는 것이 이 구조의 실질적 이득이다.
- 에이전트 루프는 순차 최대 5스텝. 실제 복합 질의에서
  `search_items` → `forecast_item_price` 체인이 동작하는 것을 확인했다.
- `LLMClient`에 `chat(messages, tools)`를 추상 메서드로 추가하고 기존
  `complete(prompt)`를 그 위의 기본 구현으로 내렸다. **호출부는 한 곳도
  수정하지 않았다.**

### 도구 실패는 예외가 아니라 결과로 돌려준다

MCP는 도구 내부 예외를 `is_error=True`로 감싸서 돌려준다. 여기에 타임아웃과
트랜스포트 오류도 같은 형태로 맞춰, 에이전트가 실패를 **결과로 읽고** 다른
도구로 우회하거나 부분 결과로 답하게 했다. 시스템 프롬프트에 "실패한 것은
숨기지 말고 밝혀라"를 넣었다.

이 레이어는 **Resilience4j 서킷 브레이커와 무관하다.** 서킷 브레이커는 LLM
프로바이더 장애(OpenAI → Claude 폴백) 대상이고 Spring 쪽 라이브러리이며,
도구 호출은 같은 파이썬 프로세스 안이라 걸 대상 자체가 아니다.

### 도구 출력 라벨링이 답의 정확성을 바꿨다

첫 검증에서 에이전트가 **등록가 143,000원과 예측 기준가 156,490원을 직접
비교해 "지금 사면 오른다"는 잘못된 결론**을 냈다. 두 값은 기준이 다른데
도구가 둘 다 `price`/`anchor_price`로만 줘서 모델이 구분할 방법이 없었다.

`listing_price`, `baseline_price` + `baseline_source`("최근 체결가" /
"관측된 거래 N건의 평균" / "등록가(거래 이력 없음)")로 바꾸자 답이 정확해졌다.
**도구 출력의 필드명은 모델에게는 프롬프트다.**

## 알려진 한계

- **타임아웃이 보장이 아니다.** 클라이언트의 `read_timeout_seconds`는 async
  대기로 구현돼 있어서, 도구가 동기 CPU 작업으로 이벤트 루프를 막는 동안에는
  발동하지 못한다. 임베딩 인코딩이 정확히 그 경우다. 기술 부채 항목을 해결하기
  전까지 도구 타임아웃은 최선 노력이다.
- **병렬 도구 호출을 지원하지 않는다.** 같은 블로킹 이슈 때문에 병렬로 띄워도
  실제 이득이 안 난다. 순차만 지원한다.
- **조건부 Reflection은 미구현.** "확신도가 낮다"를 무엇으로 판정할지가 그
  자체로 설계·검증 대상이라, 에이전트가 실제로 도는 걸 본 뒤에 정하기로 하고
  로드맵 스트레치로 옮겼다.
