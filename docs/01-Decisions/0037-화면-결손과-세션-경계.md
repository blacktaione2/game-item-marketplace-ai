# ADR-0037: 브라우저 점검이 드러낸 화면 결손과 세션 경계

## 상태

채택 (2026-08-07). ADR-0036 에 이어 같은 점검에서 나온 네 건이다.

## 배경

배포된 서비스를 실제로 써보며 나온 것들이다. **전부 자동 검사가 통과한 상태에서
나왔고**, 그럴 수밖에 없다 — 검사는 엔드포인트가 답하는지를 보지 화면에서 갈 수
있는지를 보지 않는다.

| 증상 | 실체 |
|---|---|
| 로그아웃 후 재로그인하면 직전 화면 | 라우팅을 안 한다 — **그리고 쿼리 캐시가 안 비워진다** |
| 알림 배지가 안 눌린다 | `<span>` 이다. `api.notifications()` 는 있는데 **아무도 안 부른다** |
| 거래 내역을 볼 데가 없다 | 백엔드에 **조회 엔드포인트가 없다** |
| "← 검색으로" 가 빈 검색 화면으로 | `<Link to="/">`. 그리고 뒤로가기로 바꿔도 **결과는 사라진다** |

## 결정

### 1. 로그아웃이 쿼리 캐시를 비운다

이게 이 ADR 에서 유일하게 격리 문제다. 나머지 셋은 기능 결손이다.

```tsx
function logout() {
  setAccessToken(null);
  sessionStorage.removeItem(SESSION_KEY);
  queryClient.clear();     // ← 이것
  navigate("/");
  setSession(null);
}
```

**쿼리 키에 사용자가 없다.** `["notifications","unread"]`, `["trades"]`,
`["alerts"]` 전부 그렇다. 토큰만 지우면 이전 계정의 응답이 캐시에 남아, 다음
사용자 화면에 **재요청이 도착하기 전까지** 그대로 보인다. 알림 개수는 5초마다
갱신되므로 최대 5초, 거래 내역은 그 화면에 들어가는 순간이다.

#### 왜 키에 사용자 id 를 넣지 않았나

그쪽이 더 정밀하다. 하지만 **새 쿼리를 추가할 때마다 잊을 수 있고**, 잊었을 때
증상이 조용하다 — 화면에 남의 데이터가 잠깐 보이는 건 버그로 안 보인다. 이
저장소는 같은 형태(빠뜨리면 조용히 잘못된다)로 이미 여러 번 당했다.

"세션이 끝나면 서버 상태는 전부 무효"는 빠뜨릴 데가 없다. 대가는 재로그인 후
첫 화면이 캐시 없이 시작한다는 것이고, 그건 맞는 동작이다.

### 2. 검색 질의를 URL 에 둔다 (`/?q=...`)

`useState` + `useMutation` → `useSearchParams` + `useQuery`.

**"← 검색으로" 만 뒤로가기로 바꾸면 해결되지 않는다.** 어느 쪽이든 `Assistant`
가 재마운트되고, 지역 상태는 언마운트와 함께 사라지며 mutation 결과는 캐시에
남지 않는다. 돌아가 봐야 빈 검색 화면이다.

URL 에 있으면 셋이 한꺼번에 따라온다.

- 뒤로가기가 **질의를 되살린다**
- `useQuery` 가 그 질의를 키로 **캐시된 응답을 즉시** 내준다 (AI 응답은 비싸다)
- 검색 링크를 **공유·북마크**할 수 있다

> **함정 하나.** TanStack Query v5 에서 `enabled: false` 인 쿼리는 status 가
> 계속 `pending` 이다. `isPending` 으로 로딩을 그리면 **질의를 넣기도 전에**
> 버튼이 "처리 중…" 으로 잠긴다. 실제로 도는지는 `isFetching` 만 안다.

### 3. `GET /api/trades` — 내 거래 내역

구매자·판매자 **양쪽**을 한 목록에. 거래소 사용자는 둘 다 하고, 나누면 "오늘
무슨 일이 있었나"를 보려고 두 탭을 오간다. 대신 `side`(`BUY`/`SELL`)로 방향을
표시한다.

`TradeResponse` 를 재사용하지 않고 `TradeHistoryResponse` 를 따로 뒀다.
**보는 사람이 정해져 있기 때문**이다 — "내가 산 것인가"와 "상대가 누구인가"는
거래 자체의 필드가 아니라 조회자에 따라 달라진다. `buyerId: 3` 은 화면에서 아무
뜻이 없어서 이름을 담는다.

`join fetch` 셋으로 N+1 을 막는다(50건이면 쿼리 151회). 전부 `ManyToOne` 이라
`Pageable` 이 SQL 로 내려간다.

### 4. `PATCH /api/notifications/read` — 모두 읽음

**대상을 요청이 고르지 않는다.** id 목록을 받으면 남의 알림 id 를 넣을 수 있고,
그걸 막으려면 소유권 검사를 따로 붙여야 한다. 수신자를 토큰에서 받아 조건에
넣으면 그 검사가 **필요 없어진다** — 남의 행은 애초에 조건에 안 걸린다.

개별 읽음은 두지 않았다. 화면에 그 동작이 없고, 없는 동작을 위해 API 를 만들지
않는다.

벌크 update 를 쓴다. 목록 상한은 20건인데 **안 읽은 알림에는 상한이 없어서**
엔티티로 불러오면 몇 건이 올지 알 수 없다. `clearAutomatically` 로 영속성
컨텍스트를 비운다 — 벌크 update 는 DB 를 직접 치므로 이미 올라온 엔티티가 옛
상태로 남는다.

## 테스트

`MyDataScopeTest` 6건 (백엔드 49 → **55**). 공통 주제는 **"내 것만 나오는가"** 다.

**다른 사용자를 반드시 같이 만든다.** 혼자만 있는 DB 에서는 "내 것만 나온다"와
"전부 나온다"가 같은 결과라, 격리를 하나도 안 해도 통과한다.

일부러 틀린 구현으로 돌려서 단언에 힘이 있는지 확인했다.

| 변조 | 결과 |
|---|---|
| `n.recipient.id <> :recipientId` | `모두_읽음은_내_알림만_바꾼다` 실패 |
| `... or t.id > 0` (사실상 전체) | `내가_관여한_거래만_나온다` · `side_로_갈린다` 실패 |

6건 중 3건이 잡혔고, 원복 후 `git diff` 로 변조 흔적이 남지 않은 것을 확인했다.

## 영향

- 프론트 화면이 3개 → **5개** (`/trades`, `/notifications` 추가)
- 백엔드 컨트롤러 5개 → **6개** (`TradeHistoryController`)
- 이력서 비교에서 누락으로 잡혔던 **"거래 내역 조회"가 이 라운드에서 닫힌다**
- 구매 성공 시 `["trades"]`·`["notifications"]` 도 무효화한다. 알림은 큐를
  거치므로 즉시 없을 수 있지만(ADR-0030), 무효화해두면 도착 후 다음 조회가 집는다
