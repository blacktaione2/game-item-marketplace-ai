# ADR-0037: 브라우저 점검이 드러낸 화면 결손과 세션 경계

## 상태

채택 (2026-08-07). ADR-0036 에 이어 같은 점검에서 나온 네 건이다.

## 배경

배포된 서비스를 실제로 써보며 나온 것들이다. **전부 자동 검사가 통과한 상태에서
나왔고**, 그럴 수밖에 없다 — 검사는 엔드포인트가 답하는지를 보지 화면에서 갈 수
있는지를 보지 않는다.

| 증상 | 실체 |
|---|---|
| 로그아웃 후 재로그인하면 직전 화면 | 라우팅을 안 한다 — **그리고 쿼리 캐시가 안 비워진다** |
| 알림 배지가 안 눌린다 | `<span>` 이다. `api.notifications()` 는 있는데 **아무도 안 부른다** |
| 거래 내역을 볼 데가 없다 | 백엔드에 **조회 엔드포인트가 없다** |
| "← 검색으로" 가 빈 검색 화면으로 | `<Link to="/">`. 그리고 뒤로가기로 바꿔도 **결과는 사라진다** |

## 결정

### 1. 로그아웃이 쿼리 캐시를 비운다

이게 이 ADR 에서 유일하게 격리 문제다. 나머지 셋은 기능 결손이다.

```tsx
function logout() {
  setAccessToken(null);
  sessionStorage.removeItem(SESSION_KEY);
  queryClient.clear();     // ← 이것
  navigate("/");
  setSession(null);
}
```

**쿼리 키에 사용자가 없다.** `["notifications","unread"]`, `["trades"]`,
`["alerts"]` 전부 그렇다. 토큰만 지우면 이전 계정의 응답이 캐시에 남아, 다음
사용자 화면에 **재요청이 도착하기 전까지** 그대로 보인다. 알림 개수는 5초마다
갱신되므로 최대 5초, 거래 내역은 그 화면에 들어가는 순간이다.

#### 왜 키에 사용자 id 를 넣지 않았나

그쪽이 더 정밀하다. 하지만 **새 쿼리를 추가할 때마다 잊을 수 있고**, 잊었을 때
증상이 조용하다 — 화면에 남의 데이터가 잠깐 보이는 건 버그로 안 보인다. 이
저장소는 같은 형태(빠뜨리면 조용히 잘못된다)로 이미 여러 번 당했다.

"세션이 끝나면 서버 상태는 전부 무효"는 빠뜨릴 데가 없다. 대가는 재로그인 후
첫 화면이 캐시 없이 시작한다는 것이고, 그건 맞는 동작이다.

### 2. 검색 질의를 URL 에 둔다 (`/?q=...`)

`useState` + `useMutation` → `useSearchParams` + `useQuery`.

**"← 검색으로" 만 뒤로가기로 바꾸면 해결되지 않는다.** 어느 쪽이든 `Assistant`
가 재마운트되고, 지역 상태는 언마운트와 함께 사라지며 mutation 결과는 캐시에
남지 않는다. 돌아가 봐야 빈 검색 화면이다.

URL 에 있으면 셋이 한꺼번에 따라온다.

- 뒤로가기가 **질의를 되살린다**
- `useQuery` 가 그 질의를 키로 **캐시된 응답을 즉시** 내준다 (AI 응답은 비싸다)
- 검색 링크를 **공유·북마크**할 수 있다

> **함정 하나.** TanStack Query v5 에서 `enabled: false` 인 쿼리는 status 가
> 계속 `pending` 이다. `isPending` 으로 로딩을 그리면 **질의를 넣기도 전에**
> 버튼이 "처리 중…" 으로 잠긴다. 실제로 도는지는 `isFetching` 만 안다.

> **[정정] `staleTime: 5분` 을 같이 넣었다가 뺐다.** "AI 응답은 비싸니 돌아왔을
> 때 다시 부르지 말자"는 생각이었는데, **배지를 거짓말하게 만들었다.** 같은
> 질의를 다시 물으면 서버를 안 부르고 첫 응답을 다시 그리는데 거기엔
> `cache: {hit:false}` 가 박혀 있어 **영원히 미적중으로 보인다.** 사용자가
> "재질문했는데 캐시 적중이 안 된다"고 보고해서 드러났다.
>
> 이 화면의 배지 줄은 서버 파이프라인을 눈에 보이게 하는 **계측 장치**다. 그
> 값을 클라이언트가 얼려두면 계측이 아니라 잔상이 된다. 비용 걱정은 서버 캐시가
> 이미 답한다 — 적중 경로는 LLM 0회에 p95 25.9ms(ADR-0026)다. 그리고 기본값
> (`staleTime: 0`)이어도 **캐시된 데이터는 즉시 그려지고 뒤에서 다시 받으므로**,
> 뒤로가기로 결과가 살아 돌아오는 동작은 그대로다.
>
> 일반 규칙: **관측값을 나르는 응답은 클라이언트에서 캐시하지 않는다.** 값이
> 맞느냐가 아니라 *언제 찍힌 값이냐*가 의미의 일부이기 때문이다.

### 3. `GET /api/trades` — 내 거래 내역

구매자·판매자 **양쪽**을 한 목록에. 거래소 사용자는 둘 다 하고, 나누면 "오늘
무슨 일이 있었나"를 보려고 두 탭을 오간다. 대신 `side`(`BUY`/`SELL`)로 방향을
표시한다.

`TradeResponse` 를 재사용하지 않고 `TradeHistoryResponse` 를 따로 뒀다.
**보는 사람이 정해져 있기 때문**이다 — "내가 산 것인가"와 "상대가 누구인가"는
거래 자체의 필드가 아니라 조회자에 따라 달라진다. `buyerId: 3` 은 화면에서 아무
뜻이 없어서 이름을 담는다.

`join fetch` 셋으로 N+1 을 막는다(50건이면 쿼리 151회). 전부 `ManyToOne` 이라
`Pageable` 이 SQL 로 내려간다.

### 4. `PATCH /api/notifications/read` — 모두 읽음

**대상을 요청이 고르지 않는다.** id 목록을 받으면 남의 알림 id 를 넣을 수 있고,
그걸 막으려면 소유권 검사를 따로 붙여야 한다. 수신자를 토큰에서 받아 조건에
넣으면 그 검사가 **필요 없어진다** — 남의 행은 애초에 조건에 안 걸린다.

개별 읽음은 두지 않았다. 화면에 그 동작이 없고, 없는 동작을 위해 API 를 만들지
않는다.

벌크 update 를 쓴다. 목록 상한은 20건인데 **안 읽은 알림에는 상한이 없어서**
엔티티로 불러오면 몇 건이 올지 알 수 없다. `clearAutomatically` 로 영속성
컨텍스트를 비운다 — 벌크 update 는 DB 를 직접 치므로 이미 올라온 엔티티가 옛
상태로 남는다.

### 5. 같은 질의를 다시 물으면 다시 부른다 — 그리고 캐시 키를 정규화한다

배포 후 재점검에서 두 건이 더 나왔다. **하나는 4번을 고치며 내가 만든 결함이다.**

#### 버튼이 아무 반응도 안 했다

`setSearchParams({ q })` 는 값이 같으면 URL 을 안 바꾸고, 그러면 아무 일도 일어나지
않는다. 처음엔 *"캐시된 결과가 이미 떠 있으니 맞는 동작"* 이라고 주석에
**합리화해뒀는데 틀렸다** — 버튼을 눌렀는데 반응이 없으면 사용자에게는 고장이다.
같은 질의면 `refetch()` 한다.

> 합리화가 코드 주석에 들어가면 검토를 통과한다. "이게 맞다"고 적혀 있으면 다음
> 사람은 그게 판단인지 변명인지 구분할 수 없다.

#### `"...알려줘!"` 가 미적중이었다

캐시 키가 `sha1(query.strip())` 이라 종결 기호 하나로 다른 키였다. 그래서
`normalize_query()` 로 **문장 끝 부호와 중복 공백**을 없애고 해싱한다.

**유사도를 연 게 아니다.** 여전히 정확 일치이고 "같은 글자"의 범위만 넓혔다.
ADR-0012 가 막은 건 `+8`/`+9`, `이상`/`이하` 처럼 한 글자가 답을 뒤집는 경우인데
종결 기호는 그 축에 없다.

범위를 좁게 잡은 이유가 있다. 조사·어미까지 건드리면 `"100렙 이상"` /
`"100렙이상"` 은 되지만 **그 다음이 어디서 멈출지 근거가 없어진다.** 지금은
반례를 만들 수 없는 것만 넣었다.

### 6. 랜딩에 매물 목록을 둔다

가장 큰 결손이 마지막에 나왔다. **거래소인데 매물을 볼 수가 없었다** — 랜딩이 빈
검색창 하나라, 링크를 처음 여는 사람은 무엇을 파는지도, 무엇을 물어야 하는지도
모른다.

`GET /api/items` 는 **페이징까지 되는 채로 이미 있었다.** 프론트가 부르지 않았을
뿐이다. 백엔드 작업 0.

#### 별도 라우트를 만들지 않았다

검색의 **빈 상태**를 목록으로 채운다(`?q=` 가 없으면 목록). 둘은 같은 질문의 두
형태이고, `/items` 를 따로 두면 "검색"과 "목록" 중 어디로 가야 하는지를 사용자가
정해야 한다.

#### 열이 여섯 개뿐인 이유 — 기록된 결정을 지켰다

종류·속성·강화·요구레벨은 **Postgres `items` 에 없다.** ES 매핑에만 있고,
`export_demo_sql.py` 가 이렇게 정해뒀다.

> 화면을 위해 백엔드 스키마를 늘리지 않는다 — 거래 상태는 Postgres 가, 검색용
> 속성은 ES 가 갖는 현재 분담을 유지한다.

화면 사정으로 뒤집지 않았다. 뒤집는 비용도 작지 않다 — `seed-demo.sql` 은
`DELETE FROM trades` / `notifications` 로 시작하므로 **재시딩이 실거래 기록을
지운다.**

> **남은 불일치로 등록한다.** 검색 결과 카드는 `검 · +9 · 60렙` 을 보여주는데
> 그걸 클릭해 들어간 상세 화면에는 그 정보가 없다. 같은 아이템이 화면마다 다르게
> 보인다. 해결하려면 (a) Postgres 스키마를 늘리거나 (b) 상세가 ES 를 함께 읽어야
> 하고, 둘 다 별도 결정이다.

#### TanStack Table 을 쓰지 않았다

정렬·페이징을 **서버가 한다**(Spring `Pageable`). 그러면 그 라이브러리가 파는
것(클라이언트 정렬·필터·가상화)이 전부 남고, 열 6개짜리 표에 헤드리스 추상화만
얹힌다. 실측으로도 이 화면 전체가 번들을 **2.9KB** 늘렸을 뿐이다 — 라이브러리를
넣었다면 그 몇 배가 기능 없이 들어갔을 것이다.

`shadcn/ui` + Tailwind 도 같은 이유로 안 넣었다. 지금 `styles.css` 는 4KB 변수
기반이고, Tailwind 를 깔면 **다섯 화면을 전부 다시 써야 하는데 기능은 그대로다.**

#### `Page<T>` 직렬화 형태를 테스트로 고정했다

프론트가 `content` / `totalElements` / `number` / `size` 이름에 직접 의존한다.
그 이름들은 Spring 의 `PageImpl` 이 정하는 것이라 **판올림에서 바뀔 수 있고,
바뀌면 화면이 조용히 빈 표가 된다.** Boot 4 로 옮기며 이미 여러 번 겪은 부류라
백엔드 테스트로 박아뒀다.

정렬 검사는 **가격**으로 한다. 첫 판본이 `sort=name,asc` 였다가 틀렸는데 이유가
둘이다 — `남`(ㅏ) 이 `내`(ㅐ) 보다 앞이라는 걸 잘못 알았고, 애초에 **한글 정렬
순서는 DB 로케일이 정한다.** 판정 근거를 환경에 맡기면 여기서 통과하고 배포에서
갈릴 수 있다.

### 7. 계측 배지를 **지우지 않고 분리한다**

"의도·캐시·LLM 호출·도구 호출이 브라우저에 노출되는 게 포트폴리오 관점에서
감점 아닌가"는 질문이 나왔다. 타당한 감각이다 — 실제 거래소라면 사용자에게
`intent` 를 보여주지 않는다.

**그래도 지우지 않는다.** 이 프로젝트의 주장은 *"LLM API 를 감싸기만 한 서비스가
되지 않는 것"* 이고, 라우팅·캐시·MCP 도구 체인이 **화면에서 확인되는 유일한
지점**이 이 배지들이다. 지우면 링크를 여는 사람에게는 챗봇 하나로 보이고,
"코드를 열어 보세요"는 잘 통하지 않는다.

문제는 존재가 아니라 **배치**였다. 배지가 답변 **위에** 있어서 내부 계측이
제품보다 먼저 읽혔다. 셋을 바꿨다.

| | 전 | 후 |
|---|---|---|
| 순서 | 배지 → 답변 | **답변 → 근거(카드·기여도) → 파이프라인** |
| 경계 | 없음 (제품 UI 와 같은 표면) | `<details>` 패널, **점선 테두리에 표면 없음** |
| 라벨 | 없음 | "파이프라인 — 데모용 관측 패널입니다. 실제 서비스에서는 노출하지 않습니다." |

> **같은 정보가 위치와 이름에 따라 "실수로 새어나온 내부"도 되고 "의도적인
> 관측 패널"도 된다.** 읽는 사람이 그것을 판단할 근거를 화면이 줘야 한다.

`<details>` 를 쓴 이유는 열림 상태를 리액트가 들 이유가 없고 키보드·스크린리더
동작이 공짜로 따라오기 때문이다. `open` 으로 둔 것은 의도적이다 — 접힌 채로
두면 이 프로젝트의 차별점을 아무도 안 열어본다.

## 테스트

`MyDataScopeTest` 6건 (백엔드 49 → **55**). 공통 주제는 **"내 것만 나오는가"** 다.

**다른 사용자를 반드시 같이 만든다.** 혼자만 있는 DB 에서는 "내 것만 나온다"와
"전부 나온다"가 같은 결과라, 격리를 하나도 안 해도 통과한다.

일부러 틀린 구현으로 돌려서 단언에 힘이 있는지 확인했다.

| 변조 | 결과 |
|---|---|
| `n.recipient.id <> :recipientId` | `모두_읽음은_내_알림만_바꾼다` 실패 |
| `... or t.id > 0` (사실상 전체) | `내가_관여한_거래만_나온다` · `side_로_갈린다` 실패 |

6건 중 3건이 잡혔고, 원복 후 `git diff` 로 변조 흔적이 남지 않은 것을 확인했다.

### 캐시 키 정규화 (AI 141 → **144**)

여기서도 **양방향**을 쟀다. 붙어야 할 것이 붙는지만 보면, 전부 붙여버리는
정규화도 통과한다.

| 확인 | 결과 |
|---|---|
| 정규화 **없을 때** 부호 변형 3개가 기준과 일치 | **0 / 3** — 새 테스트는 수정 전이면 실패한다 |
| 정규화 **있을 때** | 3 / 3 |
| 함정 쌍 16쌍이 현재 정규화로 충돌 | **0** |
| 같은 쌍이 **과잉** 정규화(공백·숫자 제거)로 충돌 | **4** |

마지막 줄이 함정 쌍 테스트가 헛돌지 않는다는 증거다 — 과하게 하면 실제로 걸린다.
`"???"` 와 `"!!!"` 이 같은 키가 되지 않는 것도 같이 고정했다(정규화 결과가 비면
원본을 쓴다).

## 영향

- 프론트 화면이 3개 → **5개** (`/trades`, `/notifications` 추가)
- 백엔드 컨트롤러 5개 → **6개** (`TradeHistoryController`)
- 이력서 비교에서 누락으로 잡혔던 **"거래 내역 조회"가 이 라운드에서 닫힌다**
- 구매 성공 시 `["trades"]`·`["notifications"]` 도 무효화한다. 알림은 큐를
  거치므로 즉시 없을 수 있지만(ADR-0030), 무효화해두면 도착 후 다음 조회가 집는다
