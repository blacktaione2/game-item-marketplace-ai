# ADR-0003: Item 삭제는 물리 삭제 대신 CLOSED 상태 전환(소프트 삭제)으로 처리한다

## 상태

채택됨

## 배경

`DELETE /api/items/{itemId}`가 호출됐을 때 `items` 행을 실제로 지울지,
상태만 바꿀지를 정해야 했다. `Trade`가 `item_id`를 `nullable = false`
FK로 물고 있어서, 한 번이라도 거래(구매/입찰)가 발생한 아이템을 물리
삭제하면 그 거래 이력이 고아 참조가 되거나(FK 제약 위반으로 삭제 자체가
막히거나), FK를 nullable로 풀어야 하는 문제가 있었다.

## 결정

`ItemService.delete()`는 행을 지우지 않고 `Item.status`를 `CLOSED`로
전환한다(`Item.close()`). 목록/조회 API는 `status`로 필터링하지 않고
있으므로 CLOSED 아이템도 기본적으로 조회는 되며, 구매/입찰 시점에
`item.isOnSale()` 체크로 거래만 막힌다.

## 고려한 대안

1. **물리 삭제(`DELETE FROM items ...`) + `Trade.item_id`를
   nullable로 변경** — 거래 이력 조회 시 "이미 삭제된 아이템"이라는
   정보를 잃고, 매번 null 체크가 필요해진다. 정산/분쟁 대응처럼 거래
   이력의 무결성이 중요한 마켓플레이스 도메인 특성상 적합하지 않다고
   판단했다.
2. **소프트 삭제 (채택)** — 거래 이력이 항상 유효한 `Item` 참조를
   유지한다. 다만 지금은 목록 조회 API가 CLOSED 아이템을 걸러내지
   않으므로, 프론트엔드에서 표시 여부를 판단하거나 이후 단계에서
   `findAllByTenantIdAndStatus` 같은 조회 메서드를 추가해야 한다는
   부채가 남는다.

## 결과

- `ItemStatus.CLOSED`가 논리 삭제를 의미한다 (`SOLD_OUT`과는 구분되는
  별도 상태).
- 삭제된 아이템은 DB에서 사라지지 않으므로, GDPR류 "완전 삭제" 요구가
  생기면(이 프로젝트 범위 밖) 별도의 하드 삭제/익명화 배치가 필요하다.
- Phase 3(검색 파이프라인)에서 Elasticsearch 인덱싱을 붙일 때, CLOSED
  아이템을 검색 결과에서 제외하는 필터를 반드시 넣어야 한다 — 이 ADR을
  참고해서 놓치지 않을 것.
