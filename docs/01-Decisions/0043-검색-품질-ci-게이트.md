# ADR-0043: 검색 품질 CI 게이트 — RAGAS는 게이트에서 내리고, 문턱은 재학습 변동을 재고 정했다

## 상태

채택됨. 워크플로 `ai-quality.yml` 신설(네 번째). 매 커밋(해당 경로 변경 시)
임베딩을 재학습해 **결정론적 IR 지표**로 판정하고, **RAGAS는 수동 실행 리포트**로
내린다. 테스트 AI **257 → 267**.

## 배경

기획서의 CI 원안은 `build → test → RAGAS 품질 게이트 → Docker 이미지 푸시`였고,
ADR-0021은 뒤의 둘을 미루면서 착수 조건을 이렇게 적었다:

> **모델 아티팩트 배포 전략**이 먼저다. 파인튜닝 임베딩·리랭커 ONNX가
> gitignore라 새 클론에 없고, CI 재생성은 수 분 + LLM 호출(과금)이다.

**그 조건의 두 절반이 각각 다른 이유로 무너진다.**

| 당시 기록 | 지금 |
|---|---|
| "새 클론에 모델이 없다 → 아티팩트 배포 전략이 필요" | **트리플 162건 x 2에폭 = 약 20스텝.** 재학습이 로컬 2.1분이라 배포할 게 아니라 **다시 만들면 된다** |
| "LLM 호출(과금)" | RAGAS를 **게이트에서 내리면** 사라진다. IR 지표는 LLM을 안 쓴다 |

즉 막고 있던 건 "아티팩트 배포 전략"이라는 **하나의 선행 결정이 아니라**, 서로
독립인 문제 둘이었다. 하나로 묶어 적어둔 탓에 "그 전략이 서기 전엔 아무것도 못
한다"로 읽혔다. **묶어놓은 착수 조건은 실제보다 커 보인다.**

## 결정 1: 게이트는 결정론적 IR 지표가 지고, RAGAS는 리포트다

| | 역할 | 근거 |
|---|---|---|
| **Recall@k · MRR** | **pass/fail 게이트**, 매 커밋 | 결정론적, LLM 0회, 무료 |
| **RAGAS** | **리포트**, `workflow_dispatch` + 체크박스 | 심판 변동폭 미특성화 + 매 커밋 과금 |

기획서가 "RAGAS 품질 게이트"라고 쓴 것을 그대로 구현하지 않는다. 이유 둘:

1. **LLM 심판의 변동폭을 재지 않았다.** 이 저장소는 잡음을 재지 않고 문턱을
   정했다가 사전 등록 기준이 실패한 전례가 둘 있다(ADR-0028의 틱 max,
   ADR-0040의 타속성 95%). RAGAS 변동을 특성화하려면 같은 데이터를 여러 번
   채점해야 하고 **그 측정 자체가 수백 회짜리 호출**이다. 재기 전에는 걸지 않는다.
2. **매 커밋 과금.** 약 **648회**, 40분 이상(실측). 부하 테스트를 CI에 넣지 않은
   것(ADR-0021)과 같은 판단이다.

> **[정정] 이 숫자를 처음에 216이라고 적었고 3배 틀렸다.**
> *"질의 54건 x 지표 2종 x 모델 2개"* 로 곱해 **지표당 1회**를 가정했는데, ragas의
> `ContextPrecisionWithReference` 는 소스에서 **검색된 컨텍스트마다 1회씩 순차
> 호출**한다(`for context in retrieved_contexts: ... await`). `--top-k 5` 이므로
> precision 만 54×5×2 = **540**, recall 이 54×1×2 = **108** 이다.
> 첫 수동 실행이 **42분 이상** 걸리는 것을 보고 되짚었다 — 216회면 7분쯤이다.
> **입력 개수로 곱해 만든 비용 추정은, 라이브러리가 호출당 무엇을 하는지
> 확인하기 전에는 추측이다.** 결론(게이트에서 내린다)은 오히려 강해졌다.

**"게이트"라는 단어를 지키려고 심판이 흔들리는 지표에 문턱을 거는 게 더 나쁘다.**
ADR-0007이 세운 방법론(RAGAS는 항상 IR 지표와 짝지어 읽는다)의 CI판이기도 하다.

## 결정 2: 문턱은 재학습 변동을 재고 정한다 — 그리고 재는 법이 함정이었다

`scripts/evaluate_training_variance.py`, 학습 7회, LLM 0회.

**그냥 두 번 돌려 비교하면 안 된다.** `finetune_embedding`은 시드가 42로 고정돼
있어(HuggingFace 기본값), 같은 박스에서 반복하면 **변동 0이 나오는데 그건 측정
결과가 아니라 구조다.** 그래서 세 갈래로 나눴고, 셋 다 **가중치 파일 해시**를
같이 냈다.

| 팔 | 가중치 해시 | recall@1 | recall@5 | mrr |
|---|---|---|---|---|
| 같은 시드 x2 | **동일** | 0.3889 | 0.6111 | 0.5099 |
| 시드 x3 (1/2/3) | 셋 다 상이 | 0.3889~0.4074 | 0.5556~0.5926 | 0.4999~0.5126 |
| 스레드 1 vs 2 | **상이** | 0.3889 | 0.6111 | 0.5099 |

세 가지가 나왔고 하나는 예상 밖이다.

- **같은 시드는 비트 단위로 같은 모델을 낸다.** 대조군이 없었으면 "변동 0"을
  안정성으로 읽었을 것이다.
- **스레드 수를 바꾸면 가중치는 달라지는데 지표는 넷째 자리까지 같다.**
  `mean_rank`(7.24)까지 같으니 순위 순열이 통째로 안 바뀌었다 — 부동소수점
  리덕션 순서 차이가 마지막 비트 수준이라는 뜻이다. **머신이 달라지는 축은
  시드 축보다 훨씬 작다**는 실측 근거다(CI 러너는 다른 하드웨어다).
- 따라서 실제 변동원은 시드뿐: **recall@1 0.0185 · recall@5 0.0370 · MRR 0.0127**.

부수 소득 하나. 이 표는 **"지표가 같다"와 "모델이 같다"가 다른 명제**임을
보여준다. 게이트의 공허함 방지 검사는 지표 동일성만 보므로 그 방향으로는
불완전하고, 반대 방향(모델이 같으면 지표도 같다)은 참이라 그 용도로는 유효하다.
이런 건 해시를 같이 찍지 않으면 알 수 없다.

### 문턱

```
하한 = 관측 최솟값 - 2 x 변동폭

recall@1  0.3889 - 2(0.0185) = 0.3519 -> 0.35
recall@5  0.5556 - 2(0.0370) = 0.4816 -> 0.48
mrr       0.4999 - 2(0.0127) = 0.4745 -> 0.47
```

**2배는 유도가 아니라 판단이다.** 시드 3개의 max-min은 분포가 아니라 표본 3개의
범위이고, 범위는 표본이 적을수록 참값을 **과소추정**한다. 게다가 CI 러너는
여기서 못 잰 하드웨어다(스레드 팔이 0을 냈으니 작을 것으로 보지만, 작다와 0은
다르다). 반올림은 전부 **내림** — 하한에서 안전한 쪽이다.

**개선폭 > 0**도 같이 단언한다. 이쪽은 같은 실행에서 두 모델을 같은 코드로 재기
때문에 **머신 차이가 상쇄**되고, ADR-0007이 실제로 하는 주장이기도 하다.
반대로 "기록값 0.3889 대비 무회귀"는 걸지 않는다 — 그 값은 학습 **1회**의
결과라 재학습 변동을 회귀로 오인한다.

### 이 게이트가 잡는 회귀의 크기 (과장하지 않는다)

여유가 이만큼이면 잡히는 것은 **큰 회귀**다: 코퍼스 훼손, 베이스 모델 오지정,
트리플 생성 깨짐, 학습이 사실상 안 된 경우. 미세한 품질 저하는 못 잡는다.
그건 홀드아웃 리포트를 사람이 읽는 일이고, **CI가 대신해준다고 적어두면 거짓
안심이 된다.**

### 이름: "IR 게이트"라고 줄이지 않는다

처음에 잡 이름을 `ir-gate`, 스텝을 "IR 게이트"로 줄여 썼다가 바로 오해를 샀다 —
**런타임에 검색을 수행할지 말지 결정하는 장치**로 읽힌 것이다. 그렇게 읽힐 만하다:

- `IR` 은 Information Retrieval(정보검색) **학문 분야**의 약어다. 이 저장소에서
  "IR 지표"는 Recall@k / MRR 을 뜻하고 `evaluation.py` 가 이미 그렇게 쓴다
- 하지만 "게이트"와 붙으면 **요청 시점의 장치**처럼 들리고, 실제로 이 프로젝트에
  그런 것이 셋이나 있다 — **시맨틱 캐시**(일을 할지 말지), **도메인 게이트**
  (범위 밖이면 검색 안 함, ADR-0039), **Intent Router**(어느 분기로)

셋 다 요청마다 돌고 이건 **커밋마다** 돈다. 겹치는 게 없다. 그래서 CI에 보이는
이름을 `search-quality-gate` / "검색 품질 측정" / "검색 품질 게이트 판정"으로
바꿨다. **스크립트 파일명(`check_ir_gate.py`)은 그대로 뒀다** — 코드 안에서는
"IR 지표"가 이미 정의된 어휘이고 맥락이 붙어 있다. 맥락이 없는 곳(CI 화면)만
고치는 게 표면 대비 효과가 크다.

*저자가 헷갈리게 줄인 이름은 읽는 사람도 헷갈린다.* 포트폴리오라 더 그렇다.

## 결정 3: 워크플로를 또 나눈다 — 무게가 아니라 `paths` 때문에

`ai.yml`에 붙이지 않고 `ai-quality.yml`을 새로 만들었다. 이 저장소는 이미 워크플로를
파일별로 쪼개 각자 `paths` 필터를 갖게 하는 규칙을 쓴다(ADR-0021). 게이트는 학습이
필요해 느린데, 라우터 한 줄을 고쳤다고 그 비용을 낼 이유가 없다. 그래서 **임베딩
품질에 실제로 영향을 주는 경로만** 건다 — `app/corpus/**`,
`app/services/training/**`, `app/core/config.py`, 트리플·평가질의, 관련 스크립트 셋.

GitHub Actions는 **YAML 앵커를 지원하지 않는다.** `push`/`pull_request`의 목록을
`&`/`*`로 묶으려다 워크플로가 통째로 파싱 단계에서 깨질 뻔했다. 중복을 손으로
유지한다.

## 결정 4: 모델을 캐시하지 않는다 (베이스 모델은 캐시한다)

학습이 20스텝이라 아낄 게 없는데, 캐시는 **"낡은 모델이 조용히 재사용된다"**는
실패 모드를 새로 만든다. 이 저장소는 캐시가 옛 결과를 재생해서 "배포가 안 먹은
것처럼" 보인 사건을 두 번 겪었다(ADR-0040의 `cache_version`).

반면 **베이스 모델(470MB)은 캐시한다** — 키를 `config.py` 해시로 잡아서 베이스
모델을 바꾸면 무효화되게 했다. 상수 키로 두면 모델을 바꿔도 옛 모델을 계속 쓴다.

## 고려한 대안

| 대안 | 기각 이유 |
|---|---|
| RAGAS에 pass/fail | 심판 변동폭 미측정 + 매 커밋 과금. 위 결정 1 |
| 여유 있는 문턱으로 바로 진행 | 변동 측정이 **무료**였다(LLM 0회, 학습 7회 15분). 안 잴 이유가 없다 |
| 기록값(0.3889) 대비 무회귀 | 1회 학습의 결과를 문턱으로 쓰면 재학습 변동이 회귀로 보인다 |
| 모델을 아티팩트로 배포 | 20스텝짜리 학습에 배포 파이프라인을 붙이는 건 과하다. ADR-0021의 전제가 여기서 무너진다 |
| `ai.yml`에 스텝 추가 | `paths` 필터가 워크플로 단위라, 라우터 수정에도 5분을 낸다 |
| RAGAS를 별도 잡으로 | 셋업·학습을 두 번 하고, 게이트가 판정한 모델과 RAGAS가 채점한 모델이 **다른 실행**이 된다 |

## 영향

- **새 워크플로 1개** — `ai-quality.yml`. 기존 셋은 그대로.
- **`ai.yml`의 머리말을 고쳤다.** *"모델 품질은 학습 스크립트의 홀드아웃 리포트가
  판단한다 — CI가 아니다"*가 이제 절반만 참이다. 드리프트를 그 자리에서 막았다.
- **신규 스크립트 2개** — `evaluate_training_variance.py`(문턱의 유도),
  `check_ir_gate.py`(판정). `evaluate_embedding.py`에 `--json` 추가.
- **수집과 채점을 분리했다.** 문턱을 고칠 때 재학습·재평가가 필요 없다 — 이
  저장소가 프롬프트 평가에서 이미 쓰는 규칙(`--score-only`)과 같다.
- **`evaluate_embedding`이 모델 없을 때 exit 1로 바뀌었다.** 전에는 안내 메시지를
  내고 0으로 끝났는데, CI가 그걸 통과로 읽으면 게이트가 통째로 공허해진다 —
  사례집 5·11("안 뜬 것을 닫힌 것으로 읽었다")과 같은 형태다.
- **`data/training_variance.json`은 추적한다.** 실행 산출물이 아니라 문턱의
  **유도 근거**라서, 없으면 그 숫자를 검증할 방법이 사라진다. 반대로
  `ir_metrics.json`은 gitignore(실행마다 생성, CI에서는 아티팩트).
- **테스트 257 → 267.** `tests/test_ir_gate.py`는 통과 케이스마다 **떨어지는
  케이스를 같이** 넣는다 — 게이트가 CI에서만 도는 탓에, 잘못 만들면 초록만 보다가
  회귀를 놓친다.

## 첫 러너 실행 (2026-08-08)

`ai-quality` 가 첫 푸시에서 **통과**했다. 잡 2.1분(로컬 추정과 일치), RAGAS 스텝은
push 라서 `skipped`, 아티팩트 업로드 성공.

**여유폭을 읽으려다 막혔고, 그래서 하나 더 고쳤다.** 아티팩트는 공개 저장소여도
다운로드에 토큰이 필요하다(이 저장소가 이미 겪은 제약 —
`ci-로그-접근-불가-컨테이너-재현.md`). 그래서 통과했을 때 "얼마나 통과했는지"가
사실상 안 보이는데, **문턱을 다시 유도할 때 필요한 게 정확히 그 여유폭이다.**
`check_ir_gate.py` 가 `$GITHUB_STEP_SUMMARY` 에 표를 직접 쓰게 했다.

| 지표 | 베이스 | 튜닝 | 개선 | 하한 | 여유 |
|---|---|---|---|---|---|
| recall@1 | 0.1481 | **0.3889** | +0.2408 | 0.35 | **+0.0389** |
| recall@5 | 0.4444 | **0.6111** | +0.1667 | 0.48 | +0.1311 |
| mrr | 0.3005 | **0.5099** | +0.2094 | 0.47 | **+0.0399** |

recall@1 과 MRR의 여유가 각각 **시드 변동폭의 약 2배**다(설계상 그렇게 잡았으니
당연하다). 다른 시드가 최악으로 나와도 0.3704 라 하한 위다.

> **파이프로 붙이지 않았다.** `check_ir_gate | tee -a $GITHUB_STEP_SUMMARY` 로
> 쓰면 스텝의 종료 코드가 `tee` 의 것이 되어 **게이트 실패가 묻힌다.** 방금 사례
> 26으로 적어둔 실수에 그대로 걸릴 뻔했고, 파이썬 안에서 쓰면 그 문제가 아예
> 없다. 실패 경로도 확인했다 — 요약에 실패 사유가 찍히고 exit 1 이다.

## 한계

- **문턱은 3개 시드의 범위에서 유도했다.** 분포가 아니다. 2배 여유가 그 대가다.
- **러너에서의 재학습 변동은 여전히 1회 표본이다.** 첫 실행이 0.3889 로 로컬과
  같은 값을 냈다는 것은 스레드 팔의 결론(머신 축은 작다)과 일치하지만, 표본
  하나로 축이 0 이라고 말할 수는 없다. 여유폭이 줄어드는 게 보이면 재유도할 것.
- **RAGAS 스텝은 이제 밟혔다** — 아래 「RAGAS 경로 검증」 참조. 남은 미검증은
  게이트가 **실제로 빨간불을 내는 것**을 러너에서 본 적이 없다는 점이다. 판정
  로직은 `test_ir_gate.py` 가 양방향으로 고정하지만, 워크플로가 실패를 실패로
  보고하는지는 실패하는 커밋이 하나 나와야 확인된다.

## RAGAS 경로 검증 (2026-08-08, 수동 실행)

시크릿 등록 + `workflow_dispatch` 로 실제로 돌렸고 **성공**했다. 배선이 확인됐다.
동시에 이 결정의 근거가 되는 수치가 **두 번 더 틀린 것**으로 드러났다.

| | 처음 적은 값 | 1차 정정 | **실측** |
|---|---|---|---|
| 호출 수 | 216 | 648 | 약 648 |
| 소요 | (추정 안 함) | 40분 이상 | **7,160초 = 119분** |

게이트 부분(파인튜닝 35초 + 측정 10초 + 판정 0초)은 **45초**이고, 나머지 119분이
전부 RAGAS다. 호출당 약 11초 × 순차. **"매 커밋 RAGAS 게이트"는 커밋마다 2시간
짜리 잡을 돌린다는 뜻**이었고, 결정은 오히려 훨씬 강해졌다.

### 리포트가 안 읽히면 리포트가 아니다

RAGAS 점수가 **로그에만 찍히고 아무 데도 저장되지 않았다.** 그런데 Actions 로그는
공개 저장소여도 토큰이 있어야 읽힌다 — 즉 두 시간과 요금을 쓰고 얻은 수치를
사실상 아무도 못 본다. 게이트 여유폭에서 방금 고친 것과 **같은 결함**이 리포트
쪽에 그대로 있었다.

- `run_ragas()` 가 점수를 **반환**하고, `--json` 산출물에 `ragas` 키로 들어간다
- `$GITHUB_STEP_SUMMARY` 에 표를 붙인다. **"판정에 쓰지 않는다"는 문장을 표
  안에 넣는다** — 표만 보면 게이트처럼 읽히고, 그러면 이 ADR의 결론이 사라진다
- **RAGAS 를 JSON 저장보다 먼저 돌린다.** 순서가 반대면 두 시간짜리 결과가
  파일에 안 들어간다
- **채점 실패율이 10%를 넘으면 점수를 신뢰하지 않는다고 명시한다.** 기존 코드는
  실패를 세서 출력만 하고 성공분 평균을 그대로 냈다 — 표본 절반이 사라진 채
  그럴듯한 숫자가 남는 사례집 19의 형태다

렌더러는 `test_ir_gate.py::TestRagasSummary` 가 고정한다. **한 번 돌리는 데 두
시간이 걸리므로**, 실제 실행으로만 확인하려 들면 결함이 다음 실행까지 안 보인다.

### `concurrency` 가 유료 실행을 죽일 뻔했다

`group: ai-quality-${{ github.ref }}` 에 `cancel-in-progress: true` 였는데,
`workflow_dispatch` 도 ref 가 `refs/heads/main` 이라 **push 와 같은 그룹**이다.
이 파일을 고치는 커밋을 하나 밀면 — 그리고 이 파일은 자기 자신의 `paths` 에 있다 —
**돌고 있던 2시간짜리 RAGAS 실행이 취소된다.** 실제로 그럴 뻔했고, 그룹 키에
`github.event_name` 을 넣어 갈랐다.

일반화: **취소 정책은 "같은 일의 새 버전"에만 걸어야 하는데, 그룹 키가 거친
만큼 서로 다른 일이 한 그룹에 묶인다.** 수동 실행은 비싸고 반복하기 어려우니
자동 실행과 같은 취소 그룹에 두지 않는다.
- **리랭커·하이브리드 파이프라인 전체는 게이트 밖이다.** `evaluate_embedding`은
  의도적으로 dense 검색만 잰다(BM25와 리랭커가 신호를 희석시켜서 — ADR-0007).
  하드필터 회귀는 `evaluate_hard_filters.py`가 보지만 그건 LLM을 쓰므로 CI에
  없다.
- **RAGAS 변동폭은 여전히 미측정이다.** 그걸 재는 것이 RAGAS에 문턱을 걸기 위한
  착수 조건이고, 지금은 그럴 이유가 없다(IR 지표가 게이트를 지고 있다).
