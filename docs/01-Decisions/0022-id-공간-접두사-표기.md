# ADR-0022: id 공간 접두사 표기 — 경계에서만, 그리고 기본 인자 제거

## 상태

채택됨. 로드맵의 "(B) 네임스페이스 분리"를 **표현 계층으로 축소**해서 적용했다.
축소 판단의 근거는 착수 전 실측이다(아래).

## 배경

합성 코퍼스(유저 1~206, 거래 1~26,702)와 PostgreSQL(유저 1~5, 거래 1~N)이
**범위가 겹치는데 다른 대상**을 가리킨다. `3`은 양쪽에서 유효하다.

Phase 7에서 안전장치(A)만 넣었다 — `app/core/ids.py`의 `require_supported()`가
호출자에게 공간을 명시하게 하고, 미지원 공간은 501로 거부한다.

## 착수 전에 세 가지를 셌다

설계를 확정하기 전에 코드에서 실제로 확인했다. 결과가 계획을 바꿨다.

### 1. 가드 호출 지점은 **한 곳**뿐이다

`require_supported()`는 `anomaly/pipeline.py`의 `detect_trade()`에서만 불린다.
공간을 선언하는 곳은 셋이고 전부 `SYNTHETIC`이다 — 라우터의 `DetectRequest`,
`assistant/pipeline.py`, `mcp/server.py`.

### 2. 합성 id는 **배열 위치**이지 특징 값이 아니다

생성이 두 곳 다 위치 기반 재부여다 — `corpus/trades.py`의 `user_id = index + 1`,
`anomaly/dataset.py`의 `trade["trade_id"] = index + 1`(주입 이상치를 병합한 뒤
다시 매긴다).

그리고 **`features.py`는 id를 값으로 쓰지 않는다.** 전부 묶음 키다 —
`buyer_window[buyer_id]`, `pair_window[(buyer_id, seller_id)]`,
`users_by_id[user_id]`. 11개 축은 맥락 상대 수치이고, **모델은 id를 본 적이
없다.**

### 3. 프론트는 이미 접두사를 붙이고 있다

`AnomalyQueue.tsx`가 `id_space === "synthetic"`이면 `합성#3`으로 렌더링한다.
사람이 이 번호를 읽는 유일한 지점에서 이미 구분되고 있었다.

## 결정 1: 표현 계층만 — 결론은 유지하되 **근거는 교체됐다**

원래 "표현 계층만"을 제안한 근거는 *"이상탐지 특징이 id를 값으로 쓸 수 있으니
전면 문자열화는 학습을 건드린다"* 였다. **이 근거는 확인 2에 의해 폐기됐다** —
쓰지 않는다. 전면 문자열화가 학습을 깨뜨린다는 걱정에는 근거가 없었다.

실제 근거는 다르다.

- **위치 인덱스에 접두사를 붙여도 정체성이 되지 않는다.** `index + 1`은
  `build_timeline()`마다 다시 매겨지고, `_index_by_trade_id()`가 그걸 도로
  위치로 되돌린다. 장식일 뿐이다
- **내부는 공간이 하나뿐이다.** 충돌은 외부 id가 들어오는 **경계에서만**
  가능하다. `pair_window[(buyer, seller)]` 같은 hot path의 dict 키를 문자열로
  바꾸는 것은 순수 비용이다
- **표현 절반은 이미 돼 있다**(확인 3)

그래서 `parse_ref("syn:3") -> (SYNTHETIC, 3)` / `format_ref()`를 `core/ids.py`에
두고, 변환은 **API 경계에서만** 한다.

> 결론이 같아도 근거가 틀렸으면 틀린 것이다. 이 프로젝트는 같은 실수를 한 적이
> 있다 — ADR-0016의 "필터 추출이 불안정하다"는 근거는 측정 없이 추론한 것이었고
> ADR-0017에서 정정됐다.

## 결정 2: `detect_trade`의 기본 인자를 제거한다 — 이번 라운드의 실질적 수정

확인 1에서 나온 것이다.

```python
# 전
def detect_trade(tenant_code: str, trade_id: int, id_space: IdSpace = IdSpace.SYNTHETIC)
# 후
def detect_trade(tenant_code: str, trade_id: int, id_space: IdSpace)
```

라우터는 처음부터 기본값을 두지 않았고 주석으로 그 이유까지 적어뒀는데,
**정작 함수는 기본값을 두고 있었다.** 지금 두 호출자가 우연히 명시하고 있어서
버그로 드러나지 않았을 뿐, 인자를 빠뜨린 새 호출자는 조용히 합성 데이터로
답을 받는다 — 이 모듈이 막으려는 바로 그 실패 방식이다.

**접두사 파싱을 붙여도 이 구멍은 안 닫힌다.** 원안대로 코퍼스부터 문자열화해도
마찬가지다. 그래서 이게 이번 라운드의 실질적 수정 대상이다.

`tests/test_id_space.py`가 `inspect.signature`로 시그니처를 고정한다 — 이
결함은 다시 생겨도 조용할 것이기 때문이다(`test_llm_temperature.py`와 같은
이유).

## 결정 3: 400과 501을 가른다

`parse_ref()`는 **지원 여부를 보지 않는다.** `"pg:3"`은 정상적으로 파싱되고,
그다음 `require_supported()`가 501로 막는다.

| 입력 | 응답 | 뜻 |
|---|---|---|
| `"syn:3"` | 200 | |
| `"pg:3"` | **501** | 요청은 맞다. 서버가 아직 그 평면을 못 읽는다 |
| `"3"` | **400** | 어느 평면인지 알 수 없다. **추측하지 않는다** |
| `"foo:3"` `"syn:abc"` `"syn:0"` | 400 | |

요청 형식도 바꿨다: `trade_id: int` + `id_space` **두 필드 → `trade_ref` 한 값**.
두 필드는 **서로 어긋나게 올 수 있고 어긋난 것을 검출할 방법이 없다.**
한 값으로 합치면 그 조합 자체가 사라진다.

## 기록해둘 사실: `/api/anomaly/alerts`는 가드를 지나지 않는다

문서가 "id를 받는 모든 진입점이 가드를 통과한다"고 서술해왔는데 **사실이
아니다.** GM 검토 큐(`list_alerts`)는 외부에서 id를 받지 않고 합성 코퍼스만
훑으므로 검사할 대상 자체가 없고, `_summarize()`가 `id_space`를
`"synthetic"`으로 **하드코딩**한다.

**지금은 안전하다.** 위험해지는 조건이 분명하다 — **이 목록에 백엔드 거래가
섞이는 순간** 거래마다 공간이 달라지므로 하드코딩이 곧바로 거짓이 되고, 화면은
합성 유저 번호(1~206)를 실제 번호처럼 보여준다. 사용자는 그 번호를 자기 거래
조회에 넣을 것이다.

여기에 **가짜 가드를 넣지 않았다.** `require_supported(SYNTHETIC, ...)`를
불러봐야 하드코딩된 값이라 항상 통과한다 — 통과가 보장된 검사는 검사가 아니라
장식이고, "가드가 있다"는 잘못된 안심만 준다. 대신 함수 docstring과 API 명세에
**전제와 그것이 깨지는 조건**을 적었다.

## 범위 밖 — 파싱이 된다고 처리가 되는 것은 아니다

`"pg:3"`을 파싱할 수 있게 된 것과 **백엔드 거래를 이상탐지할 수 있게 된 것은
다르다.** 후자는 Postgres 거래를 11개 특징 축으로 변환하는 코드가 필요하고,
그 특징은 `pair_trades_7d`처럼 **이력 기반**이라 5건짜리 데모 데이터로는
의미가 없다.

`app/core/ids.py`에는 "`SUPPORTED_SPACES`에 `BACKEND`를 추가하면 모든 가드가
한 번에 열린다"고 적혀 있는데, **그게 정확히 위험한 이유이기도 하다** — 열기만
하고 처리가 없으면 501 대신 엉뚱한 답이 나간다. 그 한 줄은 연동 코드가 생긴
뒤에 고친다.

## 고려한 대안

| 대안 | 기각 사유 |
|---|---|
| **(B) 원안 — 코퍼스 생성부터 문자열 id** | 확인 2로 *가능*하다는 건 밝혀졌지만, 위치 인덱스를 문자열화하는 값어치가 불분명하고 dict 키 hot path에 비용이 붙는다. 내부는 공간이 하나뿐이다 |
| **(C) 완전 통합 — 26,702건을 Postgres로** | 이번 라운드 범위를 훨씬 넘는다. 학습·평가 파이프라인 전체가 데이터 소스를 바꾸게 된다 |
| **접두사 없는 정수에 기본값(synthetic) 부여** | 추측이 애초의 결함이다. 400이 맞다 |
| **`/alerts`에 형식적 가드 추가** | 하드코딩 값이라 항상 통과한다. 잘못된 안심만 준다 |
| **응답에도 `trade_ref` 추가** | `trade_id` + `id_space`가 이미 있고 화면이 그걸 조합해 쓴다. 같은 사실의 출처가 둘이 된다 |

## 영향

- `POST /api/anomaly/detect`의 **요청 형식이 바뀐다**(`trade_ref`). 실코드
  소비자는 없었다 — 프론트는 `/alerts`만 부르고, 검색한 결과 이 엔드포인트를
  호출하는 코드는 저장소에 없었다. 문서만 갱신하면 된다
- 테스트 78건 → **93건**. 접두사 파싱, 400/501 구분, 시그니처 고정
- 프론트 변경 **없음.** "프론트가 접두사를 보낸다"는 항목은 대상이 없었다 —
  `/detect`를 호출하지 않는다
- `_extract_trade_id()`(자연어에서 번호를 뽑는 어시스턴트 경로)는 그대로다.
  사람이 `"거래 3번"`이라고 말하면 접두사가 있을 수 없으므로 여전히 합성으로
  해석하고 **답변에 그 사실을 밝힌다**
