# 설정값 하나가 입력과 출력을 겸했다 — 파인튜닝이 자기 출력물을 베이스로 썼다

> 컨테이너화를 하다가 `ai-init` 이 죽었다. 원인은 도커 설정이 아니라 **코드**였고,
> 같은 결함이 평가 스크립트 두 곳에 더 있었다. 그쪽이 더 나쁘다 — **죽지 않고
> 틀린 답을 낸다.**

## 문제

새로 만든 컨테이너에서 모델 생성 단계가 401 로 죽었다.

```
huggingface_hub.errors.RepositoryNotFoundError: 401 Client Error.
Repository Not Found for url:
  https://huggingface.co/models/embedding-finetuned/resolve/main/modules.json
```

`models/embedding-finetuned` 를 HuggingFace **저장소 id** 로 해석하고 있다.

## 발생 원인

```python
# ai/scripts/finetune_embedding.py
parser.add_argument("--out", default="models/embedding-finetuned")   # 출력
...
model = SentenceTransformer(settings.embedding_model)                # 입력(베이스)
#                           └── 기본값이 "models/embedding-finetuned" = 위의 출력
```

**`settings.embedding_model` 이 두 가지를 동시에 뜻하고 있었다.**

- 런타임에는 "검색이 쓸 모델" → 파인튜닝된 것을 가리켜야 맞다
- 학습 스크립트에는 "파인튜닝의 출발점" → 스톡 모델을 가리켜야 맞다

기존 개발 환경에서는 `models/embedding-finetuned` 디렉터리가 **이미 있어서**
로컬 경로로 로딩됐고, 아무 일도 안 일어난 것처럼 보였다(자기 자신을 한 번 더
파인튜닝했을 뿐이다). 디렉터리가 없는 환경에서만 401 로 드러난다.

### 더 나쁜 쪽 — 평가가 자기 자신과 비교하고 있었다

```python
# ai/scripts/evaluate_embedding.py
base  = SentenceTransformer(settings.embedding_model)   # models/embedding-finetuned
tuned = SentenceTransformer(args.finetuned)             # 기본값도 models/embedding-finetuned
```

`--base` 인자는 없다. 즉 **before 와 after 가 같은 모델**이고, 지금 돌리면
개선폭이 0 으로 나온다. `compare_eval_sets.py` 도 같다.

> **Phase 4 수치(Recall@1 0.148 → 0.389)가 틀렸다는 뜻은 아니다.** 당시에는
> `EMBEDDING_MODEL` 환경변수로 스톡 모델을 가리켜 측정했을 것이다 — README 에
> 그 폴백 방법이 적혀 있다. 틀린 것은 **커밋된 상태의 재현성**이다. 새로 클론한
> 사람은 그 숫자를 다시 만들 수 없고, 더 나쁘게는 "개선 없음" 이라는 잘못된
> 결론을 얻는다.

## 해결 방법

베이스를 **1급 설정값**으로 올리고, 세 곳이 그걸 쓰게 했다.

```python
# ai/app/core/config.py
embedding_model: str = "models/embedding-finetuned"          # 런타임이 쓸 것
embedding_base_model: str = (                                 # 파인튜닝의 출발점
    "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"
)
```

| 파일 | 전 | 후 |
|---|---|---|
| `scripts/finetune_embedding.py` | `settings.embedding_model` | `settings.embedding_base_model` |
| `scripts/evaluate_embedding.py` | 〃 | 〃 |
| `scripts/compare_eval_sets.py` | 〃 | 〃 |

값이 두 개가 되면 다시 헷갈릴 자리이므로, **왜 `embedding_model` 이면 안 되는지**를
설정값과 세 호출 지점 모두에 주석으로 남겼다.

## 배운 점

### 하나의 이름이 두 역할을 겸하면 한쪽에서만 틀린다

이 버그가 오래 살아남은 이유는 **런타임 쪽에서는 완벽하게 맞았기** 때문이다.
검색은 파인튜닝 모델을 써야 하고 실제로 그걸 썼다. 틀린 건 학습·평가 경로뿐인데,
그쪽은 자주 돌지 않는다.

→ 설정값 이름이 "무엇을 쓸 것인가"만 말하고 **"누가 쓸 것인가"를 말하지 않으면**
이런 겸직이 생긴다. 입력과 출력이 같은 이름을 가리키는지 의심할 것.

### 죽는 결함보다 조용한 결함이 오래 산다

같은 뿌리에서 두 종류가 나왔다.

| | 증상 | 발견 |
|---|---|---|
| 학습 스크립트 | **401 로 죽는다** | 신선한 환경에서 즉시 |
| 평가 스크립트 | **개선폭 0 을 보고한다** | 아무도 눈치 못 챔 |

두 번째는 "파인튜닝이 효과 없었다" 는 그럴듯한 결론으로 읽힌다. 숫자가 나오므로
측정한 것처럼 보이고, 그게 가장 위험한 형태다.

### 신선한 환경만이 전제가 완전한지 증명한다

ADR-0021 이 `mcp` 누락으로 배운 것과 같다 — 그때는 CI 가 잡았고 이번엔 컨테이너가
잡았다. **오래 산 개발 환경은 결함을 감춘다.** 이번 건은 CI 도 못 잡는다:
CI 는 pytest 만 돌리고 어떤 테스트도 학습 스크립트를 지나지 않는다.

→ 재현성 주장(README 의 수치)은 **주기적으로 신선한 환경에서 실제로 재현해봐야**
한다. "스크립트가 저장소에 있다"는 재현 가능성의 증거가 아니다.
