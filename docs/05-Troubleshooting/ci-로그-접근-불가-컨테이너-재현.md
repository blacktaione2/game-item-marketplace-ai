# CI가 실패했는데 로그를 읽을 수 없을 때

> GitHub Actions가 빨간불인데 **로그를 받을 수 없고**, 로컬(윈도우)에서는
> 재현되지 않는 상황이 실제로 나왔다(ADR-0021). 이때 쓸 수 있는 방법이 있다 —
> 추적된 파일만 있는 새 클론을 리눅스 컨테이너에 올려 CI와 같은 조건을 만든다.
>
> 이 방법으로 잡은 결함은 [[의존성-선언-누락-오래된-venv]]에 있다. 이 문서는
> **진단 방법** 쪽이다.

## 문제

`ai` 워크플로가 실패했는데 어느 테스트가 왜 실패했는지 알 수 없었다.

**로그를 못 받는다.** 공개 저장소인데도 Actions 로그 API는 admin 권한을
요구한다.

```
$ curl -sL ".../actions/runs/{id}/logs"
{ "message": "Must have admin rights to Repository." }
```

`gh` CLI는 설치돼 있지 않았고, 브라우저 없이 익명으로 받을 수 있는 경로도
없었다(웹 UI의 로그 링크는 인증된 요청으로 blob 스토리지에서 받아온다).

**로컬에서 재현이 안 된다.** 파일 조건을 맞춰도 마찬가지였다 — `models/`도
`.env`도 없는 새 클론에서 78건이 전부 통과했다. 즉 **윈도우/리눅스 차이이거나
패키지 버전 차이**인데, 그 이상은 알 수 없었다.

## 알아낼 수 있는 것과 없는 것

로그 없이도 **jobs API는 인증 없이 읽힌다.** 여기서 두 가지가 나온다.

```bash
curl -s ".../actions/runs/{run_id}/jobs"
```

- **어느 스텝에서 죽었는지** — 설치가 아니라 테스트에서 죽었다는 걸 여기서 알았다.
  덕분에 의존성 설치·핀 문제는 후보에서 빠졌다(나중에 보면 이 판단은 절반만
  맞았다 — 설치가 성공했는데도 원인은 의존성이었다)
- **스텝별 소요 시간** — `started_at`/`completed_at` 차이. 성능 판단에 그대로 쓸 수 있다

없는 것은 **stdout 한 줄도 없다**는 점이다. 그래서 재현이 필요하다.

## 해결 방법 — 새 클론 + 컨테이너

CI 환경의 핵심 조건은 둘이다: **추적된 파일만 있다**, **리눅스다.**

```bash
# 1. 추적된 파일만 있는 클론 (원격이 아니라 로컬 저장소에서 떠도 된다)
git clone -q /path/to/repo /scratch/cicheck

# 2. CI와 같은 리눅스 + 같은 파이썬으로 전체 설치 후 실행
docker run --rm -v "C:\...\cicheck:/repo" -w /repo/ai python:3.11-slim bash -c "
  pip install -q --retries 5 --no-cache-dir torch --index-url https://download.pytorch.org/whl/cpu &&
  pip install -q --retries 5 --no-cache-dir -r requirements.txt &&
  python -m pytest -q 2>&1 | tail -40"
```

한 번에 원인이 그대로 찍혔다.

주의할 점:

- **로컬 저장소에서 클론하면 원격 왕복이 없다.** 커밋만 돼 있으면 된다
- **`--retries`를 준다.** 첫 시도에서 pip이 해시 불일치로 죽었는데(전송 오류)
  재시도로 해결됐다. 컨테이너 네트워크는 CI보다 불안정하다
- 윈도우 경로를 볼륨으로 넘길 때는 **PowerShell 쪽에서 실행**한다. Git Bash는
  경로를 MSYS 규칙으로 변환해버린다
- 이 방법은 **다른 종류의 결함에도 그대로 쓴다** — 경로 구분자, 파일명
  대소문자, 로케일, 줄바꿈 등 "윈도우에서만 통과하는" 결함이 전부 같은 부류다

### 시간이 아깝다면

전체 설치가 매번 1분 이상이면 이미지를 한 번 만들어두고 소스만 갈아끼우는 게
낫다. 이번엔 두 번 돌리는 걸로 끝나서 하지 않았다.

## 대안과 그 한계

| 방법 | 한계 |
|---|---|
| `gh run view --log` | 설치 + 인증이 필요하다. 있으면 이게 제일 빠르다 |
| 워크플로에서 `::error::`로 출력을 애노테이션에 실어보내기 | 실패를 관측하려고 CI 설정을 고치는 것이라, 고칠 때마다 커밋 한 번씩 들어간다 |
| 워크플로에 아티팩트 업로드 추가 | 다운로드에 역시 인증이 필요하다 |
| 실패할 때까지 커밋으로 찔러보기 | 커밋 히스토리가 더러워지고 사이클이 느리다(한 번에 1~2분) |

## 배운 점

**"CI 로그를 못 읽는다"는 진단 불가가 아니다.** CI 환경은 재현 가능한
조건 몇 개로 정의된다 — 이번 경우엔 "추적된 파일만" + "리눅스" 둘이었다.
그걸 로컬에서 구성하는 쪽이 원격 로그를 얻으려고 애쓰는 것보다 빨랐고, 게다가
**수정을 검증하는 수단으로 그대로 재사용**됐다(수정 후 같은 컨테이너에서 78건
통과를 먼저 확인하고 나서 푸시했다).

역으로, 재현 환경 없이 커밋으로 찔러봤다면 원인(선언 누락)을 알아내는 데
여러 번의 왕복이 필요했을 것이다.
