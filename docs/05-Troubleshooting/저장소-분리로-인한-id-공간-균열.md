# 두 저장소가 같은 id 공간을 쓴다고 가정했지만 실제로는 갈라져 있었다

> **엔티티별 상태** (2026-07-30 재점검)
>
> | 엔티티 | 상태 |
> |---|---|
> | tenants | 해결됨 — 양쪽 id 1 = `nexon` |
> | items | **해결됨** — 시딩으로 ES와 같은 id (1~24, 101~118) |
> | users | **미해결** — 합성 1~206 vs 백엔드 1~5, 겹치는데 다른 사람 |
> | trades | **미해결** — 합성 1~26,702 vs 백엔드 1~, 겹치는데 다른 거래 |
>
> users·trades는 (A) 안전장치만 적용했다. 근본 해결(네임스페이스 분리 또는
> 완전 통합)은 Phase 8로 이관.

## 문제

Phase 7에서 프론트엔드를 붙이려고 시연 시나리오를 점검하다 발견했다.

> `검색 → 아이템 상세 → 시세 예측 → 구매/입찰`

검색과 시세는 되는데 **상세와 구매가 원리적으로 불가능했다.** 검색이
`item_id=24`를 돌려주지만 백엔드 DB에 그 아이템이 없다.

```
Elasticsearch : 아이템 42건 (id 1~24, 101~118)
Python 더미   : 유저 150명, 거래 26,489건 (인메모리)
PostgreSQL    : items 0 / users 0 / tenants 0 / trades 0
```

Phase 1에서 curl로 CRUD·구매·입찰을 검증했을 때는 그때 만든 행이 있었지만,
이후 그 데이터는 남지 않았다. **Phase 2~6 내내 아무도 눈치채지 못했다.**

## 발생 원인

AI 서버와 백엔드가 **서로 다른 저장소를 소스 오브 트루스로 쓴다.**

| 컴포넌트 | 저장소 | 아이템 정의 출처 |
|---|---|---|
| 검색·시세예측·이상탐지 | Elasticsearch + 인메모리 더미 | `ai/app/corpus` |
| 아이템 CRUD·거래 | PostgreSQL | 없음(수동 INSERT) |

두 쪽이 `item_id`라는 **같은 이름의 식별자**를 쓰기 때문에 같은 공간이라고
암묵적으로 가정했는데, 실제로는 서로를 전혀 모른다. ES 색인 스크립트
(`seed_items`)는 Postgres에 아무것도 쓰지 않는다.

이게 늦게 발견된 이유가 중요하다. **각 컴포넌트는 자기 저장소 안에서 완결적으로
정상이었다.**

- 검색 API 테스트 → ES만 본다 → 통과
- 시세·이상탐지 → ES + 인메모리 더미만 본다 → 통과
- 백엔드 CRUD 수동 검증 → 그때 만든 행으로 → 통과
- 단위 테스트 36건 → 순수 함수·키 규칙만 → 통과

**저장소를 가로지르는 경로를 아무도 밟지 않았다.** 화면을 붙여 실제 사용자
동선을 따라가기 전까지는 드러날 수 없는 종류의 결함이다.

## 해결 방법

**코퍼스를 단일 진실 공급원으로 삼고 거기서 SQL을 생성**한다.

`ai/scripts/export_demo_sql.py` → `backend/src/main/resources/db/seed-demo.sql`

- `ALL_ITEMS` 42건을 **ES와 같은 item_id로** INSERT
- 테넌트 1건, 데모 유저 5명(판매자를 여러 명에 분산)
- 재실행 가능하게 DELETE를 먼저 두고, 명시적 id를 넣었으므로 **시퀀스를
  `setval`로 최대값 뒤로 민다**(안 하면 다음 INSERT가 id=1을 다시 써서 죽는다)

SQL을 손으로 쓰지 않는 것이 핵심이다. 손으로 쓰면 아이템을 추가할 때마다
두 곳을 고쳐야 하고, 언젠가 반드시 어긋난다.

### 스키마가 완전히 같지는 않다

Postgres `items`에는 `enhancement_level`/`required_level`이 없다(ES 매핑에만
있다). **백엔드 스키마를 늘리지 않았다** — 거래 상태는 Postgres가, 검색용
속성은 ES가 갖는 현재 분담을 유지하는 편이 낫다고 판단했다. 대신 상세 화면이
어느 필드를 어디서 가져오는지 명시했다.

### 확인

```
POST /items/2/purchase → HTTP 201, 거래 #1, 재고 10 → 9
POST /items/24/bids    → HTTP 201, 거래 #2
```

## 2차 발견 — 아이템만 고쳤을 뿐이었다

위 시딩을 마치고 "해결"로 보고했는데, **users와 trades에 같은 균열이 그대로
남아 있었다.** 실측:

| 엔티티 | 합성 코퍼스 | PostgreSQL |
|---|---|---|
| users | 1 ~ 206 (206명) | 1 ~ 5 (5명) |
| trades | 1 ~ 26,702 | 1 ~ (증가) |

그리고 이쪽이 **더 나쁜 종류**다. 아이템은 "한쪽이 비어 있음"이라 404로
시끄럽게 실패했지만, 유저·거래는 **양쪽 다 채워져 있고 범위까지 겹친다.**
`trade_id=3`은 양쪽 모두에서 유효한데 전혀 다른 거래다 — 조용히 틀린 답이
나간다.

실제로 노출되던 문제:

- GM 큐가 `구매자 #52 / 판매자 #41`을 그대로 보여줬다. 백엔드에는 1~5뿐이라
  존재하지 않는 번호다.
- `POST /api/anomaly/detect {trade_id}`에 사용자가 자기 거래 번호를 넣으면
  **무관한 합성 거래의 이상 판정이 에러 없이 돌아왔다.**

### 적용한 완화 (A)

**범위 검사로는 못 막는다** — 두 공간이 겹치기 때문이다. 그래서 호출자가
공간을 명시하게 했다.

`app/core/ids.py`에 `IdSpace` / `SUPPORTED_SPACES` / `require_supported()`를
두고, id를 받는 진입점이 전부 그걸 통과하게 했다.

```
id_space 누락        → HTTP 422  Field required
id_space="backend"  → HTTP 501  '...아직 지원하지 않습니다. 현재 지원: synthetic.
                                 두 데이터는 id 범위가 겹쳐서 서로를 대신할 수 없습니다.'
id_space="synthetic"→ HTTP 200
```

정책을 한 파일에 모은 이유는 Phase 8에서 백엔드 거래를 연동할 때
`SUPPORTED_SPACES`에 한 줄 추가하면 **모든 진입점의 가드가 동시에 풀리게**
하기 위해서다. 이 유틸은 (B) 네임스페이스 분리로 갈 때도 그대로 재사용된다.

화면 쪽은 합성 id에 `합성#` 접두사를 붙이고 경고 문구를 띄운다 — 라벨만으로는
사용자가 그 번호를 다른 화면에 입력하는 것까지 막지 못하므로, API 가드와
**둘 다** 필요하다.

## 3차 — "모든 진입점이 통과한다"도 사실이 아니었다 (2026-08-01)

Phase 8에서 이 완화를 마무리하며(ADR-0022) 호출 지점을 실제로 세어보니 **위
문단이 틀렸다.** `require_supported()`를 부르는 곳은 **한 곳**뿐이고,
GM 큐(`GET /api/anomaly/alerts`)는 **가드를 지나지 않는다** — 외부에서 id를
받지 않고 합성 코퍼스만 훑기 때문에 검사할 대상 자체가 없다. 대신
`_summarize()`가 `id_space`를 `"synthetic"`으로 하드코딩한다.

지금은 안전하지만 **이 목록에 백엔드 거래가 섞이는 순간** 그 하드코딩이 거짓이
되고, 위 "GM 큐가 `구매자 #52`를 보여줬다"와 **똑같은 증상이 재발한다.**

그리고 더 나쁜 게 하나 더 있었다 — `detect_trade()`에 **기본 인자가 남아
있었다**(`id_space: IdSpace = IdSpace.SYNTHETIC`). 라우터는 기본값을 안 두고
주석으로 이유까지 적어뒀는데 함수는 두고 있었다. 두 호출자가 우연히 명시하고
있어서 드러나지 않았을 뿐, 인자를 빠뜨린 새 호출자는 **조용히 합성 데이터로
답을 받는다** — 이 완화가 막으려던 바로 그 실패 방식이다.

**교훈: "전부 통과하게 했다"는 서술은 세어보기 전까지 가설이다.** 이 문서의
2차 발견("아이템만 고쳤을 뿐이었다")과 정확히 같은 형태의 실수가, 완화를 적용한
쪽에서 한 번 더 반복됐다.

### 현재 API (2026-08-01 기준)

```
POST /api/anomaly/detect  {"tenant_code": "nexon", "trade_ref": "syn:3"}

"syn:3"   → 200
"pg:3"    → 501   (요청은 맞다. 서버가 아직 그 평면을 못 읽는다)
"3"       → 400   (어느 평면인지 알 수 없다 — 추측하지 않는다)
```

`trade_id` + `id_space` **두 필드는 서로 어긋나게 올 수 있었으므로** 한 값으로
합쳤다. 자세한 내용은 ADR-0022.

## 배운 점

**컴포넌트마다 저장소가 다르면 식별자 공간이 조용히 갈라지고, 그 균열은
컴포넌트 단위 검증으로는 절대 안 잡힌다.** 각자는 자기 저장소 안에서 완벽하게
정상이기 때문이다.

그리고 이 프로젝트에서 이게 6개 Phase 동안 숨어 있었던 이유는 **검증이 늘
컴포넌트 단위였기 때문**이다. 기준선 비교, 홀드아웃, 오탐 측정 — 방법론은
엄격했지만 전부 한 컴포넌트 안에서였다. 저장소를 가로지르는 경로는 화면을
붙이기 전까지 아무도 밟지 않았다.

### 체크리스트를 만든 것과 실행한 것은 다르다

이 문서를 쓰면서 아래 체크리스트를 만들었고, 그 첫 항목이 정확히 users·trades
문제를 잡아냈어야 했다 — "새 컴포넌트가 기존 컴포넌트와 같은 이름의 식별자를
쓰는가? 쓴다면 그 값이 실제로 같은 대상을 가리키는지 확인했는가?"

**만들어놓고 items에만 돌렸다.** 눈앞의 증상(구매 실패)이 아이템에서 났으니
아이템을 고치고 해결로 판단했고, 같은 검사를 나머지 엔티티에 돌려볼 생각을
안 했다. 문서에 체크리스트가 존재하는 것과 그것이 실행되는 것은 별개다.

그래서 체크리스트에 **"전체 엔티티에 대해 실제로 실행했는가"** 항목을 넣었다.
목록을 만든 순간 만족해버리는 것이 이 종류 문서의 고유한 실패 모드다.

### 재발 조건과 체크리스트

자기 저장소를 갖는 컴포넌트를 추가할 때마다 해당된다. 이 프로젝트에는 이미
PostgreSQL / Elasticsearch / Redis / 인메모리 더미가 있다.

- [ ] 새 컴포넌트가 기존 컴포넌트와 **같은 이름의 식별자**를 쓰는가?
      쓴다면 그 값이 실제로 같은 대상을 가리키는지 확인했는가?
- [ ] **위 항목을 한 엔티티가 아니라 전체 엔티티에 대해 실제로 돌렸는가?**
      (items만 보고 users·trades를 놓친 전례가 있다 — 위 절 참고)
- [ ] 두 공간의 id 범위가 **겹치는가?** 겹치면 범위 검사로는 못 가른다.
      호출자가 공간을 명시하게 하고, 명시 안 하면 거부한다
- [ ] 두 저장소를 채우는 경로가 **하나의 소스에서** 나오는가? 각각 따로
      채운다면 언젠가 어긋난다
- [ ] **저장소를 가로지르는 사용자 동선**을 한 번이라도 끝까지 밟아봤는가?
      컴포넌트별 테스트가 전부 통과해도 이건 안 잡힌다
- [ ] 명시적 id로 시드를 넣었다면 **시퀀스를 `setval`로 밀었는가?**
- [ ] 두 저장소의 스키마가 다른 필드는 무엇이고, 화면이 어느 쪽을 소스 오브
      트루스로 쓰는지 정해뒀는가?
- [ ] **가드를 넣었다면 호출 지점을 세어봤는가?** "전부 통과하게 했다"는
      세기 전까지 가설이다. 가드를 우회하는 경로(외부 id를 안 받는 목록
      조회 등)가 있다면, 그게 왜 지금은 안전하고 **무엇이 바뀌면 위험해지는지**
      까지 적는다 (3차 발견 참고)
- [ ] **가드가 걸린 함수에 기본 인자가 남아 있지 않은가?** 기본값이 있으면
      인자를 빠뜨린 호출자가 조용히 통과한다. 시그니처를 테스트로 고정한다
- [ ] 값과 그 값의 **해석 방식(공간·단위·타임존)을 두 필드로 나눠 받고 있다면**,
      둘이 어긋나게 올 수 있고 어긋난 것을 검출할 방법이 없다. 한 값으로
      합칠 수 있는지 본다 (`trade_id` + `id_space` → `trade_ref: "syn:3"`)
