# 도구 출력 필드명이 모호하면 LLM이 없는 인과관계를 만들어낸다

## 문제

Phase 6 에이전트를 실제 복합 질의로 검증하다가 나온 답이다.

> 질의: `"불꽃의 대검 지금 사도 괜찮은 가격이야? 앞으로 오를까?"`
>
> 답변: 현재 "불꽃의 대검"의 가격은 **143,000원**입니다. (…) 향후 7일 내에
> 조금 상승할 것으로 보입니다. 2026년 7월 29일: **156,490원** (…)
> **결론적으로, 현재 143,000원에 구매하는 것이 적절해 보이며, 앞으로 가격이
> 오를 가능성이 있음을 확인했습니다.**

도구 호출은 둘 다 성공했고 반환값도 정확했다. 그런데 **결론이 틀렸다.**

143,000원은 판매자가 올린 **등록가**이고, 156,490원은 **최근 체결가
155,380원**을 기준으로 한 7일 뒤 예측값이다. 기준이 다른 두 숫자다. 모델은
이걸 "지금 143,000 → 곧 156,490"으로 읽어서 **13,490원(9.4%) 상승**이라는,
어느 도구도 말한 적 없는 결론을 만들어냈다. 실제 예측 변동률은 **+0.78%**였다.

도구도 파이프라인도 정상이었다. 이 결함은 **조합 지점에만** 존재했다.

## 발생 원인

두 MCP 도구가 의미가 다른 값을 **구분 불가능한 이름**으로 내보냈다.

| 도구 | 필드 | 실제 의미 |
|---|---|---|
| `search_items` | `price` | 판매자 등록가 |
| `forecast_item_price` | `anchor_price` | 최근 체결가(또는 관측 거래 평균, 또는 등록가) |

`price`와 `anchor_price`는 사람이 코드를 읽으면 다르다는 걸 알지만, **모델에게
주어진 건 이름과 숫자뿐이다.** 둘 다 "이 아이템의 가격"으로 읽히므로 시간순
비교가 자연스러워 보인다.

`anchor_price`는 더 나빴다. 같은 필드가 **경로에 따라 세 가지 다른 것**을 담는다.

- 이력 충분 → 최근 체결가
- Cold Start + 관측 거래 있음 → 그 평균
- Cold Start + 거래 없음 → 등록가

세 번째 경우엔 `search_items`의 `price`와 **같은 값**이 나온다. 이름만으로는
언제 같고 언제 다른지 알 방법이 없다.

## 해결 방법

**기준을 이름에 박고, 파생값에는 출처를 같이 실었다.**

| 이전 | 이후 |
|---|---|
| `price` | `listing_price` |
| `anchor_price` | `baseline_price` + `baseline_source` |

`baseline_source`는 문자열로 `"최근 체결가"` / `"관측된 거래 3건의 평균"` /
`"등록가(거래 이력 없음)"` 중 하나를 넣는다.

도구 설명(description)에도 명시했다.

- `search_items`: "반환되는 listing_price는 **판매자가 올린 등록가**이지
  시세가 아니다"
- `forecast_item_price`: "가격 전망 질문에는 반드시 이 도구를 쓴다 —
  search_items가 주는 등록가는 시세가 아니다"

시스템 프롬프트에도 한 줄 넣었다: "등록가와 예측 기준가는 기준이 다릅니다.
두 값을 직접 빼서 등락을 말하지 마세요. 등락은 expected_change_pct를 쓰세요."

### 수정 후

> 현재 "불꽃의 대검"의 **등록가는 143,000원**입니다. **최근 체결가를 기준으로
> 한 예측 기준가는 155,380원**이므로 (…) 예상 변화율이 **0.78%**로 (…)

이제 두 값을 구분해서 말하고, 등락은 도구가 준 변화율을 쓴다.

## 배운 점

**Agentic 파이프라인에서 도구 출력의 필드명은 데이터 스키마가 아니라
프롬프트다.** 사람이 읽는 API 응답에서는 필드명이 모호해도 문서를 보거나
코드를 따라가면 되지만, 모델에게는 이름과 값이 전부다. 이름이 모호하면 모델은
**모른다고 말하는 대신 그럴듯한 관계를 만들어낸다.**

이 실패 모드가 특히 위험한 이유는 세 가지다.

1. **도구는 전부 성공한다.** 에러도 예외도 없고 로그에도 안 남는다.
2. **답이 그럴듯하다.** 숫자가 실제 데이터에서 나왔으므로 검증하기 전엔
   틀린 걸 알 수 없다.
3. **단일 도구 테스트로는 안 잡힌다.** 각 도구를 따로 부르면 값이 다 맞다.
   결함은 **체이닝 지점에만** 생긴다.

그래서 도구를 하나씩 검증하는 것으로는 부족하고, **여러 도구를 엮는 실제
질의로 답변의 결론까지 읽어야** 한다.

### 재발 조건과 체크리스트

MCP 도구를 추가하거나 기존 도구의 반환값을 바꿀 때마다 확인한다.

- [ ] 다른 도구에 **같은 개념의 다른 값**을 내보내는 필드가 있는가?
      있다면 이름만으로 구분되는가? (`price` vs `listing_price` vs
      `baseline_price`)
- [ ] 한 필드가 **경로에 따라 다른 것**을 담는가? 담는다면 무엇을 담았는지
      알려주는 동반 필드가 있는가? (`baseline_source`)
- [ ] 모델이 두 도구의 숫자를 **빼거나 나누면** 의미 있는 값이 나오는가?
      안 나온다면 그걸 하지 말라고 명시했는가?
- [ ] 도구 description에 "이 값이 무엇이 **아닌지**"를 적었는가?
      (`"등록가이지 시세가 아니다"`)
- [ ] **여러 도구를 엮는 질의**로 검증했는가? 도구별 단위 검증만으로는
      이 결함이 안 잡힌다.
- [ ] 답변의 **결론**까지 읽었는가? 인용된 숫자가 맞아도 그 숫자들로 만든
      결론이 틀릴 수 있다.
