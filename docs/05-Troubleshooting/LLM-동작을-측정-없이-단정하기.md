# LLM의 동작을 측정 없이 단정했다 — 한 라운드에서 나온 세 건

> 2026-07-31 재작성 결정성 작업에서 세 가지가 걸렸는데, 증상은 다르지만 원인이
> 하나다: **LLM이 왜 그렇게 동작하는지를 재보지 않고 결론지었다.** 셋 다
> 그럴듯했고, 셋 다 틀렸거나 과장이었다. 이 프로젝트는 LLM 위에 파이프라인을
> 얹고 있어서 재발 조건이 상시 존재한다.

## 사례 1: 미설정 파라미터를 "모델의 근본 특성"으로 진단했다

### 문제

같은 질의가 실행마다 다르게 재작성되는 현상을 여러 라운드에 걸쳐
**"LLM 질의 재작성의 비결정성"** 으로 서술했다. ADR-0014는 그걸 근거로
리랭커 하한을 기각했고, ADR-0016은 0건 응답 캐시 금지의 근거로 삼았다.

### 발생 원인

`temperature`를 API에 **한 번도 안 넘겼다.**

```python
kwargs = {"model": self._model, "messages": messages}   # temperature 없음
```

생략하면 OpenAI Chat Completions는 **기본값 1.0**을 쓴다. 최대 샘플링 온도로
6개 Phase를 돌렸다.

**아무도 이걸 못 본 이유**: 코드가 정상으로 보였고 에러도 없었다.
**없는 파라미터는 눈에 띄지 않는다.** 있는 코드는 읽히지만 없는 코드는 안
읽힌다. "LLM은 원래 그렇다"는 설명이 그럴듯해서 더 안 봤다.

### 해결

`temperature=0`을 **명시적으로** 실어 보낸다. 토큰집합 모드 일치율
0.840 → 0.990, 불안정 질의 5/10 → 1/10. 검색 품질은 무변화.

`tests/test_llm_temperature.py`가 "값이 kwargs에 들어가는가"를 고정한다 —
이 결함은 다시 생겨도 조용할 것이기 때문이다.

## 사례 2: 관측하지 않은 것을 관측한 것에서 일반화했다

### 문제

ADR-0016이 0건 응답을 캐시하지 않는 이유 1로 **"판정 근거인 필터 추출이
비결정적이다"** 를 들었다.

### 발생 원인

**그건 측정이 아니라 추론이었다.** 실제로 관측한 건 재작성 *텍스트*의 변동
(`"검 소드 대검"` vs `"검 소드 대검 단검"`)이고, 거기서 "필터도 흔들릴
것"이라고 넘겨짚었다. 둘 다 같은 LLM 호출의 출력이니 자연스러운 추론처럼
보였다.

실측하니 **temperature 1.0에서도 필터는 10질의 × 10회 전부 동일**했다
(모드 일치율 1.000). 텍스트는 흔들리는데 필터는 안 흔들렸다 — 자유 서술
필드와 열거형 필드의 안정성이 다르다.

### 해결

이유 1의 강도를 낮추고 그 사실을 ADR-0016·0017 양쪽에 남겼다. **결정 자체는
유지**된다 — 이유 2(0건은 매물 하나만 등록돼도 거짓이 되는 가장 낡기 쉬운
답)가 독립적으로 서 있기 때문이다.

결정이 살아남은 건 **근거를 두 개 세워놨기 때문**이지 추론이 맞아서가 아니다.

## 사례 3: 타당해 보이는 프롬프트 한 줄이 정답률을 4배 낮췄다

### 문제

남은 오추출이 `불속성` ↔ `무속성` 혼동(한 글자 차이, 정반대 뜻)이라
프롬프트에 혼동 방지 문구를 넣었다.

> **`불속성`과 `무속성`을 혼동하지 마세요.** `불속성`은 불(화염) 속성이라
> "화염"이고, `무속성`은 속성이 아예 없다는 뜻이라 "무속성"입니다.

### 발생 원인

| | `"3만원 이하 불속성 검"` → `화염` |
|---|---|
| 추가 전 | **39/40 (97.5%)** |
| 추가 후 | **11/50 (22%)** |
| 되돌린 후 | **50/50** |

`무속성`을 눈에 띄게 언급한 것 자체가 모델을 그쪽으로 유도했다.
**"혼동하지 마라"고 말하는 행위가 혼동을 만들었다.**

### 해결

되돌렸다. 프롬프트 수정은 눈으로 판단하지 않고
`scripts/evaluate_rewrite_determinism.py`로 잰다.

### 이 사례가 특히 위험한 이유

문구 자체가 **누가 봐도 타당하다.** 코드 리뷰로 안 걸리고, 스모크 테스트로도
안 걸린다(가끔 틀리는 게 아니라 78%가 틀리는데도 "어쩌다 틀렸네"로 보인다).
측정 없이 넣었으면 0건 경로의 핵심 질의를 4배 악화시킨 채 배포했을 것이다.

## 공통 원인과 판별법

세 사례 모두 **"LLM이 왜 그렇게 동작하는지에 대한 주장을 재보지 않고
했다"** 이다. 그런데 형태가 다르다.

| 사례 | 주장의 형태 | 실제 |
|---|---|---|
| 1 | 원인을 모델 탓으로 | 우리 쪽 설정 누락 |
| 2 | 관측한 것에서 일반화 | 일반화가 성립 안 함 |
| 3 | 개입이 도움이 될 것 | 4배 악화 |

### 판별 순서

LLM이 이상하게 동작할 때 **이 순서로** 확인한다.

1. **요청 파라미터를 먼저 본다.** `temperature`, `top_p`, `max_tokens`, `seed`,
   `response_format` — 안 넘긴 게 있으면 그 API의 기본값이 무엇인지 확인한다.
   "안 넘겼다 = 무난한 값"이 아니다.
2. **"모델 특성"이라는 결론은 1번을 확인한 뒤에만 낸다.**
3. **관측한 축과 주장하는 축이 같은지 본다.** 텍스트가 흔들린 걸 봤다면
   텍스트에 대해서만 말한다. 필터도 흔들린다고 하려면 필터를 재야 한다.
4. **프롬프트 수정은 전후를 잰다.** n은 최소 30 — 5~10회로는 20%대 실패율도
   "어쩌다"로 보인다.

### 체크리스트

- [ ] 이 LLM 호출이 넘기지 **않는** 파라미터는 무엇이고, 그 기본값은?
- [ ] "모델이 원래 그렇다"고 쓰기 전에 설정을 확인했는가?
- [ ] 내가 잰 것과 내가 주장하는 것이 같은 대상인가?
- [ ] 프롬프트를 고쳤다면 전후를 n≥30으로 쟀는가?
- [ ] 결론이 뒤집혔을 때 **결정까지 무너지는가**, 아니면 다른 근거가 있는가?
      (사례 2는 근거가 둘이라 살아남았다)
