# 검사 자체가 틀린 사례들 — 오보, 침묵, 그리고 동전 던지기

> 측정 하네스에 자동 검사나 판정선을 붙일 때마다 **검사가 틀렸다.** 시스템이
> 아니라 검사가. 아홉 건이 쌓였고 방향이 셋으로 갈린다 — 정상 시스템에 실패를
> 보고한 게 넷, **결함이 있는데 조용했던 게 넷**, **정상 시스템에 실패를 보고한 게 넷**, **같은 코드에서 통과와
> 실패가 갈린 게 하나**다.
>
> 침묵이 가장 나쁘다. 오보는 사람이 확인하다 발견하지만, 침묵은 **검사가 있다는
> 안심만 주고 아무것도 안 한다.**
>
> **제목에 건수를 넣지 않는다.** 원래 "세 건"이었는데 네 번째가 생겼다. 내용이
> 늘 때마다 제목과 6곳의 링크가 같이 틀리는 건 이 문서가 경고하는 드리프트
> 그 자체다.

## 사례 1: 워밍업 1건이 집계에서 빠져 "오버셀 1건" 오보 (ADR-0020)

### 문제

`재고 감소분 == 성공 응답 수` 단언이 매번 1건 어긋났다. 오버셀이 일어난 것처럼
보였다.

### 발생 원인

k6는 **`setup()`에서 발생한 커스텀 메트릭을 집계하지 않는다.** 그런데 워밍업이
실제 구매 1건을 낸다. 재고는 줄었는데 `created_201`에는 안 잡힌다.

### 해결

기대식에 워밍업을 명시했다. 워밍업을 GET으로 바꾸지 않은 이유는 **락 경로 자체를
데우는 것이 목적**이기 때문이다.

```bash
WARMUP_PURCHASES=1
EXPECTED=$(( ${CREATED:-0} + WARMUP_PURCHASES ))
```

## 사례 2: 분산 프로파일인데 아이템 하나만 조회 (ADR-0020)

### 문제

같은 단언이 `spread` 프로파일에서 13,293건 불일치를 보고했다.

### 발생 원인

`spread`는 9002~9021로 흩어져 사는데 재고를 **9001에서만** 읽었다.

### 해결

부하 아이템 전체의 재고 **합**을 본다. 두 프로파일이 한 식으로 성립한다.

```sql
SELECT COALESCE(SUM(stock),0) FROM items WHERE id BETWEEN 9001 AND 9021;
```

## 사례 3: 경고가 잘린 화면을 읽고 있었다 (ADR-0024) — 방향이 반대다

### 문제

요청 한도를 도입하면서 "부하테스트가 리미터에 걸렸는가"를 검사하는 경고를
붙였다. 그런데 **3,361건 중 300건만 통과한 실행에서 경고가 조용했다.**

앞의 둘과 달리 **아무 일도 일어나지 않았다.** 사람이 k6 요약의 체크 실패율
(8.93%)을 보고 나서야 이상하다는 걸 알았다.

### 발생 원인

경고가 `load/out/*.diff.txt`를 grep했는데, `snapshot_metrics.py`는 카운터를
**증가분 절댓값 상위 25개만** 출력한다. 그리고 그 순위에 **단위가 다른 계열이
섞여 있다.**

```
process_cpu_time_ns_total                  16312500000.0   ← 나노초
jvm_gc_memory_allocated_bytes_total          450887680.0   ← 바이트
...
spring_security_filterchains_*_total              3362.0   ← 9개 계열이 자리를 먹는다
                                                            (인증 도입으로 새로 생김)
rate_limited_total{scope="trade"}                 3057.0   ← 25위 밖으로 밀려남
```

카운터 값은 스냅샷 원본에 **정상적으로 있었다**(8 → 3065). 표시가 자른 것이다.

### 해결

검사가 **원본에서 직접 센다.** 렌더링된 출력을 읽지 않는다.

```bash
# 전: diff.txt를 grep  →  0건으로 읽힘
# 후: before/after 스냅샷에서 직접 합산  →  10,178건 검출
LIMITED="$("$PY" -c "...re.match(r'^(ai_)?rate_limited_total\{...')..." \
  "$OUT/$TAG.before.txt" "$OUT/$TAG.after.txt")"
```

### 아직 같은 형태로 남아 있는 것

**`run.sh:95`의 오버셀 단언은 여전히 k6의 렌더링된 텍스트 요약을 grep한다.**

```bash
CREATED="$(grep -oE 'created_201[^0-9]*([0-9]+)' "$OUT/$TAG.k6.txt" ...)"
```

지금은 안전하다 — k6 요약은 커스텀 메트릭을 **항상 전부** 출력하고 잘라내지
않는다. 즉 "요약을 읽어서" 위험한 게 아니라 **"잘라내는 요약을 읽어서"** 위험한
것이다. 그 성질이 바뀌면(k6 옵션 변경, 메트릭 수 급증) 같은 침묵이 재발한다.
`--summary-export`로 JSON을 받는 쪽이 근본적이지만 이번 범위 밖으로 뒀다.

## 사례 4: 판정선이 계측기의 잡음 바닥 안에 있었다 (ADR-0028) — 방향이 또 다르다

### 문제

동기 CPU 호출을 스레드로 내보내면서 **사전 등록 판정선**을 걸었다:
"`live-llm` 3VU 중 10ms 티커의 **최대 지연 < 20ms**".

같은 코드로 두 번 쟀더니 **한 번은 32.75ms(실패), 한 번은 17.89ms(통과)** 였다.
판정선이 판정을 못 했다.

### 발생 원인

**판정선을 계측기의 잡음 바닥을 재기 전에 정했다.** 20ms의 근거는 "틱 주기
10ms의 2배"였는데, 그건 계측기의 *설정값*이지 *분해능*이 아니다.

나중에 **부하를 전혀 걸지 않은 유휴 대조군**을 재고서야 드러났다:

| | 유휴(부하 0) | 변경 전 | 변경 후 #1 | 변경 후 #2 |
|---|---:|---:|---:|---:|
| mean | 5.53 | 2.97 | 2.00 | 1.38 |
| p99 | 6.68 | 29.33 | 11.88 | 10.65 |
| **max** | **16.34** | 224.01 | **32.75** | **17.89** |
| 20ms 초과 | 0 | 49 | 1 | 0 |

**아무 일도 안 하는 서버가 이미 16.34ms를 찍는다.** Windows 타이머 분해능이라
`asyncio.sleep(0.010)`이 정확히 10ms에 깨어날 수 없다. 즉 판정선은 바닥 위에
**3.66ms**만 남겨두고 있었다. 게다가 하필 **`max`** 를 골랐다 — 3,600개 표본
중 단 하나로 결정되는, 가장 불안정한 통계량이다.

같은 표에서 **`p99`와 "20ms 초과 개수"는 두 실행 모두 명확하다.** 29.33 →
11.88 / 10.65, 49건 → 1건 / 0건. 볼 수 있는 신호가 있는데 안 보이는 걸 골랐던
것이다.

### 해결

판정선 자체를 되돌려 고치지 않았다 — **틀린 채로 남기고 실패로 보고했다.**
결과를 본 뒤에 기준을 바꾸면 그건 판정선이 아니라 사후 합리화다.

대신 규칙을 하나 추가했다:

> **판정선을 정하기 전에 계측기의 유휴 바닥값을 먼저 잰다.** 그리고 단일 표본
> 통계량(`max`)이 아니라 분위수나 초과 건수로 건다.

### 왜 이 방향이 따로 있어야 하는가

오보와 침묵은 **결과가 일정하다** — 늘 틀리게 울리거나 늘 조용하다. 그래서
한 번 알아채면 끝난다. 이건 다르다. **실행마다 답이 바뀌므로**, 운이 좋으면
"통과했다"고 적고 넘어가고 운이 나쁘면 멀쩡한 변경을 기각한다. 두 번 돌리지
않았다면 이 결함 자체를 못 봤다.

## 사례 5: 대기 조건이 "대상 없음"을 "조건 충족"으로 읽었다 (ADR-0029) — 두 번

컨테이너화 라운드에서 **같은 형태의 대기 조건을 두 번** 잘못 만들었다.

```bash
# (a) CI 완료 대기 — head_sha 쿼리가 빈 배열을 돌려줬다
sum(1 for r in runs if r['status'] != 'completed')   # 빈 배열 -> 0 -> "전부 완료"

# (b) ai-init 종료 대기 — 새 실행은 시작도 안 했는데 통과했다
docker ps -a --filter name=gimp-ai-init | grep "Exited"   # 이전 실행의 Exited 를 봤다
```

둘 다 **"대상이 없는 상태"와 "대상이 조건을 만족한 상태"를 구분하지 않았다.**
(a) 는 아무 실행도 못 찾았을 때, (b) 는 낡은 실행이 남아 있을 때 통과한다.

고친 방식은 **낡은 값으로는 만족할 수 없는 조건**을 쓰는 것이다.

```bash
# 이미지 ID가 "바뀐다"를 본다 — 이전 값으로는 성립하지 않는다
OLD=5900d775f8e1
until [ "$(docker images --format '{{.ID}}' gimp-ai:local)" != "$OLD" ]; do sleep 20; done
```

## 사례 6: 빌드가 "성공"했는데 내용이 구버전이었다 (ADR-0029)

`requirements.txt` 에 `accelerate` 를 추가하고 재빌드했는데 **같은 ImportError 가
계속 났다.** 세 번째로 같은 오류를 보고서야 이미지 안을 열어봤다.

```
$ docker run --rm --entrypoint sh gimp-ai:local -c "sed -n '18,26p' requirements.txt"
langchain-community<0.4          <- 디스크에는 24행에 accelerate 가 있다
```

`docker compose build` 는 `Built` 를 출력했고 이미지 타임스탬프도 갱신됐는데,
`COPY requirements.txt .` 레이어가 **파일 변경에도 캐시를 탔다**(Docker Desktop
/ WSL2 파일 공유에서 알려진 현상). `--no-cache` 로 다시 빌드하니 해결됐다.

**성공 메시지만 믿었으면 원인을 계속 코드에서 찾고 있었을 것이다.** 실제로 두
번의 재빌드를 코드 문제로 오해하며 낭비했다.

## 사례 7: 테스트가 검증 지점에 도달조차 못 했다 (ADR-0030)

체결 후 알림을 큐로 넘기면서 **가장 중요한 성질**에 테스트를 걸었다 —
*"롤백된 거래는 이벤트를 발행하지 않는다"*. `@TransactionalEventListener(AFTER_COMMIT)`
이 그걸 보장한다.

```java
@Test
void 롤백된_거래는_이벤트를_내보내지_않는다() {
    try { tradeService.purchase(tenantId, itemId, buyerId, 99); }  // 재고 3
    catch (InvalidTradeRequestException expected) {}
    verify(publisher, never()).publish(any());
}
```

통과했다. 그래서 **일부러 깨봤다** — `AFTER_COMMIT` 을 트랜잭션 내부 발행으로 바꿨다.
**그래도 통과했다.**

### 발생 원인

`quantity=99` 는 **재고 확인**에서 거절되는데, 그 확인이 **발행 지점보다 앞**이다.

```
doPurchase()
  ├─ 재고 확인  → 여기서 예외      ← 테스트가 태운 경로
  ├─ ...
  ├─ save()
  └─ publishCompleted()            ← 도달조차 안 함
```

즉 이 테스트는 *"롤백됐는데 발행 안 됨"* 이 아니라 *"발행 지점에 도달조차 안 함"* 을
재고 있었다. 리스너의 단계(phase)와 **아무 상관이 없다.**

### 해결

거래 서비스를 거치지 않고 **이벤트 등록과 롤백만** 재현한다.

```java
template.execute(status -> {
    springEventPublisher.publishEvent(event);
    status.setRollbackOnly();
    return null;
});
verify(publisher, never()).publish(any());
```

그리고 **대조군**을 같이 넣었다 — 같은 경로가 커밋되면 발행된다. 이게 없으면
"항상 통과하는 테스트"와 구분되지 않는다.

고친 뒤 다시 뮤테이션을 넣으니 **정확히 그 한 건만** 실패했다.

### 앞의 사례들과 다른 점

사례 3·5는 검사의 **입력**이 틀렸고(잘린 화면, 빈 목록), 사례 6은 **대상**이
틀렸다(구버전 이미지). 이건 **경로**가 틀렸다 — 검사는 진짜 코드를 진짜로 실행했는데,
그 실행이 검증하려는 지점을 지나지 않았다.

> **통과하는 테스트를 뮤테이션으로 검사하는 습관이 아니었으면 못 봤다.**
> 이 저장소에서 그 습관이 결함을 잡은 게 이번이 세 번째다.

## 사례 8: 상한이 있는 목록의 길이를 총계로 셌다 (ADR-0030)

`verify-mq.sh` 가 "구매 5건 -> 알림 5건"을 단언하는데, 어느 순간부터
**"구매 5건인데 알림 0건"** 이 계속 나왔다.

```bash
notif_count() { curl -s "$BACKEND/api/notifications" ... | python -c "print(len(...))"; }
```

`/api/notifications` 는 **최근 20건 상한**이다. 20건이 쌓인 뒤로는 몇 건을 더
만들어도 길이가 `20 -> 20` 이라 증가분이 0 이 된다.

### 시스템을 먼저 의심했다

두 번 연속 실패를 보고 "브로커 재연결이 안 되나" 로 갔다. 계측을 열어보고서야
방향이 바뀌었다.

```
trade_event_published_total{outcome="ok"}      99      ← 발행은 잘 된다
trade_event_published_total{outcome="failed"}  12      ← 브로커 정지 구간의 것
큐: ready 0, unacked 0, consumers 1                    ← 컨슈머도 붙어 있다
```

**세 지표가 전부 정상이었다.** 시스템은 멀쩡했고 검사가 틀렸다.

### 해결

상한이 없는 집계를 쓴다.

```bash
notif_count() { curl -s "$BACKEND/api/notifications/unread-count" ... ; }
```

### 왜 이게 새로운 방향인가

사례 3은 **잘린 화면**을 읽었고, 이건 **잘린 API 응답**을 읽었다. 형태는 같지만
차이가 있다 — 화면은 사람용이라 "표시가 자를 수 있다"는 의심이 자연스러운데,
**API 응답은 데이터처럼 보인다.** 페이지네이션·상한이 걸린 엔드포인트를
집계 용도로 쓰면 **어느 임계값을 넘는 순간부터** 조용히 틀리기 시작한다.

> 그 전까지는 통과한다. 20건 전에는 이 검사가 정상 동작했다.

## 사례 9: 검사가 다음 실행을 망가뜨리는 상태를 남겼다 (ADR-0030)

같은 스크립트를 **연달아 두 번** 돌리면 두 번째가 실패했다. 판정 5가 브로커를
정지시켰다 살리는데, 백엔드의 캐시된 연결은 곧바로 복구되지 않는다. 그 상태로
다음 실행의 판정 2가 돌면 발행이 실패한다.

즉 **검사가 자기 뒤처리를 안 해서 다음 실행의 전제를 깨뜨렸다.**

해결은 끝에 복구 확인을 붙이는 것이고, 덤으로 **"브로커가 돌아오면 발행이
재개된다"** 는 진짜 성질을 단언하게 됐다(판정 9).

> **검사를 두 번 연달아 돌려보면 이 부류가 드러난다.** 한 번만 돌리면
> "처음엔 통과했는데 왜 지금은 안 되지"로 나타나고, 원인을 시스템에서 찾게 된다.

## 배운 점

### 성공 신호가 확인 대상과 어긋나는 계열이 따로 있다

이 저장소에서 세 번 반복된 형태다.

| 겉보기 신호 | 실제 |
|---|---|
| "포트가 응답한다" | 내가 띄운 프로세스가 아니라 **살아남은 옛 JVM**이 응답 |
| "검사가 통과했다" | 검사가 **아무것도 확인하지 않고** 통과 (사례 3·5) |
| "빌드가 성공했다" | **구버전 내용**이 담긴 이미지가 만들어짐 (사례 6) |

공통 처방은 하나다 — **신호가 아니라 결과물을 확인한다.** 포트가 아니라 기동
로그를, 통과 여부가 아니라 무엇을 셌는지를, `Built` 가 아니라 이미지 안의 파일을.

### 검사는 세 방향으로 틀린다

| 방향 | 증상 | 발견 난이도 |
|---|---|---|
| **오보** | 정상 시스템에 실패 보고 | 쉽다 — 확인하다 드러난다 |
| **침묵** | 결함이 있는데 통과 | **어렵다 — 아무 일도 안 일어난다** |
| **동전 던지기** | 같은 코드에서 통과/실패가 갈린다 | **어렵다 — 한 번만 돌리면 안 보인다** |

정상 시스템에 실패를 보고하는 검사는 없느니만 못하지만, **결함을 놓치는 검사는
그보다 더 나쁘다.** 있다는 사실만으로 안심을 주기 때문이다.

### 검사를 붙였으면 실패시켜 봐야 한다

사례 3은 **일부러 오염된 조건(운영 한도 그대로)으로 돌려봤기 때문에** 발견됐다.
완화 구성으로만 돌렸으면 경고가 안 울리는 게 정상으로 보였을 것이고, 그 상태로
"오염 검사가 있다"고 문서에 적었을 것이다.

→ **음성 사례와 양성 사례를 둘 다 돌린다.** 초록만 보고 검사가 동작한다고
결론짓지 않는다. (CI 첫 도입 때도 같은 방식이 결함을 잡았다 —
[[의존성-선언-누락-오래된-venv]])

### 요약된 출력 위에 검사를 세우지 않는다

표시용 출력은 **읽는 사람을 위해 자르고 정렬한다.** 그 판단 기준(상위 N, 절댓값
순)은 검사가 필요로 하는 것과 다르다. 원본이 있으면 원본에서 센다.

특히 **단위가 다른 값이 한 순위에 섞이면** 순위는 의미를 잃는다 — 바이트는
언제나 요청 수를 이긴다. 이 표시 결함 자체는 로드맵에 등록해뒀다.

### 재발 조건 체크리스트

- [ ] 이 검사의 **입력이 원본인가, 사람이 읽으라고 가공된 출력인가?**
      후자면 가공 규칙(자르기·정렬·반올림)이 검사를 조용히 무력화할 수 있다
- [ ] **일부러 실패하는 조건으로 돌려봤는가?** 통과만 확인한 검사는
      "항상 통과하는 검사"와 구분되지 않는다
- [ ] 검사가 세는 대상의 **범위가 시나리오와 일치하는가?**
      (사례 2 — 프로파일은 20개인데 검사는 1개를 봤다)
- [ ] 측정 구간 **밖에서 발생하는 부수 효과**가 있는가?
      (사례 1 — `setup()`의 요청이 상태를 바꾼다)
- [ ] 새 구성요소가 들어오면서 **기존 검사의 전제가 바뀌지 않았는가?**
      (사례 3 — 인증 도입으로 필터체인 계열 9개가 순위를 잠식했다)
- [ ] **판정선이 계측기의 잡음 바닥보다 충분히 위에 있는가?**
      바닥을 재본 적이 없다면 그 판정선의 근거는 없는 것이다 (사례 4)
- [ ] 판정선이 **단일 표본 통계량(`max`, `min`)** 에 걸려 있지 않은가?
      표본 하나가 판정을 뒤집으면 그건 시스템이 아니라 운을 재는 것이다 (사례 4)
- [ ] **같은 조건에서 두 번 돌려 같은 답이 나오는가?**
      한 번만 돌린 판정은 통과든 실패든 근거가 약하다 (사례 4)
- [ ] 대기·완료 조건이 **"대상이 없는 상태"에서도 통과하지 않는가?**
      빈 목록, 이전 실행의 잔해가 조건을 만족시킬 수 있다 (사례 5).
      낡은 값으로는 성립할 수 없는 조건으로 바꿀 것
- [ ] 도구가 준 **성공 메시지가 아니라 결과물**을 봤는가?
      `Built` / `200 OK` / `통과`는 확인 대상이 아니라 신호일 뿐이다 (사례 6)
- [ ] 테스트가 **검증하려는 지점을 실제로 지나는가?**
      앞선 검증에서 걸러지면 뒤의 코드는 실행조차 안 된다 (사례 7).
      확인법: 그 지점을 **일부러 깨고** 테스트가 실패하는지 본다
- [ ] "안 일어난다"를 단언하는 테스트에 **대조군**이 있는가?
      `never()` 계열은 아무것도 안 해도 통과한다 (사례 7)
- [ ] 세는 값에 **상한·페이지네이션**이 걸려 있지 않은가?
      API 응답은 데이터처럼 보이지만 잘려 있을 수 있고, **임계값을 넘는 순간부터**
      조용히 틀린다 (사례 8). 총계가 필요하면 총계를 주는 엔드포인트를 쓴다
- [ ] 검사를 **연달아 두 번** 돌려도 같은 결과인가?
      자기가 바꾼 상태를 되돌리지 않으면 다음 실행의 전제를 깨뜨린다 (사례 9)
