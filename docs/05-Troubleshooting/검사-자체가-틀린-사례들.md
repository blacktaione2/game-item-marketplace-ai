# 검사 자체가 틀린 사례들 — 오보, 침묵, 그리고 동전 던지기

> 측정 하네스에 자동 검사나 판정선을 붙일 때마다 **검사가 틀렸다.** 시스템이
> 아니라 검사가. **방향이 다섯으로 갈린다** — 오보(정상 시스템에
> 실패 보고), **침묵(결함이 있는데 통과)**, 동전 던지기(같은 코드에서 결과가
> 갈림), 약함(결과는 맞는데 근거가 다름), 그리고 **엉뚱한 대상(대상 안에서는
> 정확한데 잰 대상이 틀림)**이다.
>
> 사례 14가 붙은 방식이 특히 볼 만하다 — **다른 결함을 고치자 저절로
> 드러났다.** 뮤테이션으로도, 실패 케이스로도 안 잡히던 것이다.
>
> 사례 15는 한 발 더 나갔다: **결함을 잡으려고 방금 추가한 검사가 그 자리에서
> 틀렸다.** 그것도 잡을 대상은 제대로 잡으면서 단언의 절반이 헛돌았다.
>
> **사례 16~18 은 하루에 나왔다.** 배포된 서비스를 직접 써보며 결함을 고치는
> 동안, 그 결함을 재려고 만든 지표와 검사가 **네 번 틀렸다.** 새 판정 도구를
> 만드는 라운드일수록 이 목록이 길어진다 — 도구가 늘면 틀릴 자리도 는다.
>
> 침묵이 가장 나쁘다. 오보는 사람이 확인하다 발견하지만, 침묵은 **검사가 있다는
> 안심만 주고 아무것도 안 한다.**
>
> **제목에 건수를 넣지 않는다.** 원래 "세 건"이었는데 네 번째가 생겼다. 내용이
> 늘 때마다 제목과 6곳의 링크가 같이 틀리는 건 이 문서가 경고하는 드리프트
> 그 자체다.

## 사례 1: 워밍업 1건이 집계에서 빠져 "오버셀 1건" 오보 (ADR-0020)

### 문제

`재고 감소분 == 성공 응답 수` 단언이 매번 1건 어긋났다. 오버셀이 일어난 것처럼
보였다.

### 발생 원인

k6는 **`setup()`에서 발생한 커스텀 메트릭을 집계하지 않는다.** 그런데 워밍업이
실제 구매 1건을 낸다. 재고는 줄었는데 `created_201`에는 안 잡힌다.

### 해결

기대식에 워밍업을 명시했다. 워밍업을 GET으로 바꾸지 않은 이유는 **락 경로 자체를
데우는 것이 목적**이기 때문이다.

```bash
WARMUP_PURCHASES=1
EXPECTED=$(( ${CREATED:-0} + WARMUP_PURCHASES ))
```

## 사례 2: 분산 프로파일인데 아이템 하나만 조회 (ADR-0020)

### 문제

같은 단언이 `spread` 프로파일에서 13,293건 불일치를 보고했다.

### 발생 원인

`spread`는 9002~9021로 흩어져 사는데 재고를 **9001에서만** 읽었다.

### 해결

부하 아이템 전체의 재고 **합**을 본다. 두 프로파일이 한 식으로 성립한다.

```sql
SELECT COALESCE(SUM(stock),0) FROM items WHERE id BETWEEN 9001 AND 9021;
```

## 사례 3: 경고가 잘린 화면을 읽고 있었다 (ADR-0024) — 방향이 반대다

### 문제

요청 한도를 도입하면서 "부하테스트가 리미터에 걸렸는가"를 검사하는 경고를
붙였다. 그런데 **3,361건 중 300건만 통과한 실행에서 경고가 조용했다.**

앞의 둘과 달리 **아무 일도 일어나지 않았다.** 사람이 k6 요약의 체크 실패율
(8.93%)을 보고 나서야 이상하다는 걸 알았다.

### 발생 원인

경고가 `load/out/*.diff.txt`를 grep했는데, `snapshot_metrics.py`는 카운터를
**증가분 절댓값 상위 25개만** 출력한다. 그리고 그 순위에 **단위가 다른 계열이
섞여 있다.**

```
process_cpu_time_ns_total                  16312500000.0   ← 나노초
jvm_gc_memory_allocated_bytes_total          450887680.0   ← 바이트
...
spring_security_filterchains_*_total              3362.0   ← 9개 계열이 자리를 먹는다
                                                            (인증 도입으로 새로 생김)
rate_limited_total{scope="trade"}                 3057.0   ← 25위 밖으로 밀려남
```

카운터 값은 스냅샷 원본에 **정상적으로 있었다**(8 → 3065). 표시가 자른 것이다.

### 해결

검사가 **원본에서 직접 센다.** 렌더링된 출력을 읽지 않는다.

```bash
# 전: diff.txt를 grep  →  0건으로 읽힘
# 후: before/after 스냅샷에서 직접 합산  →  10,178건 검출
LIMITED="$("$PY" -c "...re.match(r'^(ai_)?rate_limited_total\{...')..." \
  "$OUT/$TAG.before.txt" "$OUT/$TAG.after.txt")"
```

### 아직 같은 형태로 남아 있는 것

**`run.sh:95`의 오버셀 단언은 여전히 k6의 렌더링된 텍스트 요약을 grep한다.**

```bash
CREATED="$(grep -oE 'created_201[^0-9]*([0-9]+)' "$OUT/$TAG.k6.txt" ...)"
```

지금은 안전하다 — k6 요약은 커스텀 메트릭을 **항상 전부** 출력하고 잘라내지
않는다. 즉 "요약을 읽어서" 위험한 게 아니라 **"잘라내는 요약을 읽어서"** 위험한
것이다. 그 성질이 바뀌면(k6 옵션 변경, 메트릭 수 급증) 같은 침묵이 재발한다.
`--summary-export`로 JSON을 받는 쪽이 근본적이지만 이번 범위 밖으로 뒀다.

## 사례 4: 판정선이 계측기의 잡음 바닥 안에 있었다 (ADR-0028) — 방향이 또 다르다

### 문제

동기 CPU 호출을 스레드로 내보내면서 **사전 등록 판정선**을 걸었다:
"`live-llm` 3VU 중 10ms 티커의 **최대 지연 < 20ms**".

같은 코드로 두 번 쟀더니 **한 번은 32.75ms(실패), 한 번은 17.89ms(통과)** 였다.
판정선이 판정을 못 했다.

### 발생 원인

**판정선을 계측기의 잡음 바닥을 재기 전에 정했다.** 20ms의 근거는 "틱 주기
10ms의 2배"였는데, 그건 계측기의 *설정값*이지 *분해능*이 아니다.

나중에 **부하를 전혀 걸지 않은 유휴 대조군**을 재고서야 드러났다:

| | 유휴(부하 0) | 변경 전 | 변경 후 #1 | 변경 후 #2 |
|---|---:|---:|---:|---:|
| mean | 5.53 | 2.97 | 2.00 | 1.38 |
| p99 | 6.68 | 29.33 | 11.88 | 10.65 |
| **max** | **16.34** | 224.01 | **32.75** | **17.89** |
| 20ms 초과 | 0 | 49 | 1 | 0 |

**아무 일도 안 하는 서버가 이미 16.34ms를 찍는다.** Windows 타이머 분해능이라
`asyncio.sleep(0.010)`이 정확히 10ms에 깨어날 수 없다. 즉 판정선은 바닥 위에
**3.66ms**만 남겨두고 있었다. 게다가 하필 **`max`** 를 골랐다 — 3,600개 표본
중 단 하나로 결정되는, 가장 불안정한 통계량이다.

같은 표에서 **`p99`와 "20ms 초과 개수"는 두 실행 모두 명확하다.** 29.33 →
11.88 / 10.65, 49건 → 1건 / 0건. 볼 수 있는 신호가 있는데 안 보이는 걸 골랐던
것이다.

### 해결

판정선 자체를 되돌려 고치지 않았다 — **틀린 채로 남기고 실패로 보고했다.**
결과를 본 뒤에 기준을 바꾸면 그건 판정선이 아니라 사후 합리화다.

대신 규칙을 하나 추가했다:

> **판정선을 정하기 전에 계측기의 유휴 바닥값을 먼저 잰다.** 그리고 단일 표본
> 통계량(`max`)이 아니라 분위수나 초과 건수로 건다.

### 왜 이 방향이 따로 있어야 하는가

오보와 침묵은 **결과가 일정하다** — 늘 틀리게 울리거나 늘 조용하다. 그래서
한 번 알아채면 끝난다. 이건 다르다. **실행마다 답이 바뀌므로**, 운이 좋으면
"통과했다"고 적고 넘어가고 운이 나쁘면 멀쩡한 변경을 기각한다. 두 번 돌리지
않았다면 이 결함 자체를 못 봤다.

## 사례 5: 대기 조건이 "대상 없음"을 "조건 충족"으로 읽었다 (ADR-0029) — 두 번

컨테이너화 라운드에서 **같은 형태의 대기 조건을 두 번** 잘못 만들었다.

```bash
# (a) CI 완료 대기 — head_sha 쿼리가 빈 배열을 돌려줬다
sum(1 for r in runs if r['status'] != 'completed')   # 빈 배열 -> 0 -> "전부 완료"

# (b) ai-init 종료 대기 — 새 실행은 시작도 안 했는데 통과했다
docker ps -a --filter name=gimp-ai-init | grep "Exited"   # 이전 실행의 Exited 를 봤다
```

둘 다 **"대상이 없는 상태"와 "대상이 조건을 만족한 상태"를 구분하지 않았다.**
(a) 는 아무 실행도 못 찾았을 때, (b) 는 낡은 실행이 남아 있을 때 통과한다.

고친 방식은 **낡은 값으로는 만족할 수 없는 조건**을 쓰는 것이다.

```bash
# 이미지 ID가 "바뀐다"를 본다 — 이전 값으로는 성립하지 않는다
OLD=5900d775f8e1
until [ "$(docker images --format '{{.ID}}' gimp-ai:local)" != "$OLD" ]; do sleep 20; done
```

## 사례 6: 빌드가 "성공"했는데 내용이 구버전이었다 (ADR-0029)

`requirements.txt` 에 `accelerate` 를 추가하고 재빌드했는데 **같은 ImportError 가
계속 났다.** 세 번째로 같은 오류를 보고서야 이미지 안을 열어봤다.

```
$ docker run --rm --entrypoint sh gimp-ai:local -c "sed -n '18,26p' requirements.txt"
langchain-community<0.4          <- 디스크에는 24행에 accelerate 가 있다
```

`docker compose build` 는 `Built` 를 출력했고 이미지 타임스탬프도 갱신됐는데,
`COPY requirements.txt .` 레이어가 **파일 변경에도 캐시를 탔다**(Docker Desktop
/ WSL2 파일 공유에서 알려진 현상). `--no-cache` 로 다시 빌드하니 해결됐다.

**성공 메시지만 믿었으면 원인을 계속 코드에서 찾고 있었을 것이다.** 실제로 두
번의 재빌드를 코드 문제로 오해하며 낭비했다.

## 사례 7: 테스트가 검증 지점에 도달조차 못 했다 (ADR-0030)

체결 후 알림을 큐로 넘기면서 **가장 중요한 성질**에 테스트를 걸었다 —
*"롤백된 거래는 이벤트를 발행하지 않는다"*. `@TransactionalEventListener(AFTER_COMMIT)`
이 그걸 보장한다.

```java
@Test
void 롤백된_거래는_이벤트를_내보내지_않는다() {
    try { tradeService.purchase(tenantId, itemId, buyerId, 99); }  // 재고 3
    catch (InvalidTradeRequestException expected) {}
    verify(publisher, never()).publish(any());
}
```

통과했다. 그래서 **일부러 깨봤다** — `AFTER_COMMIT` 을 트랜잭션 내부 발행으로 바꿨다.
**그래도 통과했다.**

### 발생 원인

`quantity=99` 는 **재고 확인**에서 거절되는데, 그 확인이 **발행 지점보다 앞**이다.

```
doPurchase()
  ├─ 재고 확인  → 여기서 예외      ← 테스트가 태운 경로
  ├─ ...
  ├─ save()
  └─ publishCompleted()            ← 도달조차 안 함
```

즉 이 테스트는 *"롤백됐는데 발행 안 됨"* 이 아니라 *"발행 지점에 도달조차 안 함"* 을
재고 있었다. 리스너의 단계(phase)와 **아무 상관이 없다.**

### 해결

거래 서비스를 거치지 않고 **이벤트 등록과 롤백만** 재현한다.

```java
template.execute(status -> {
    springEventPublisher.publishEvent(event);
    status.setRollbackOnly();
    return null;
});
verify(publisher, never()).publish(any());
```

그리고 **대조군**을 같이 넣었다 — 같은 경로가 커밋되면 발행된다. 이게 없으면
"항상 통과하는 테스트"와 구분되지 않는다.

고친 뒤 다시 뮤테이션을 넣으니 **정확히 그 한 건만** 실패했다.

### 앞의 사례들과 다른 점

사례 3·5는 검사의 **입력**이 틀렸고(잘린 화면, 빈 목록), 사례 6은 **대상**이
틀렸다(구버전 이미지). 이건 **경로**가 틀렸다 — 검사는 진짜 코드를 진짜로 실행했는데,
그 실행이 검증하려는 지점을 지나지 않았다.

> **통과하는 테스트를 뮤테이션으로 검사하는 습관이 아니었으면 못 봤다.**
> 이 저장소에서 그 습관이 결함을 잡은 게 이번이 세 번째다.

## 사례 8: 상한이 있는 목록의 길이를 총계로 셌다 (ADR-0030)

`verify-mq.sh` 가 "구매 5건 -> 알림 5건"을 단언하는데, 어느 순간부터
**"구매 5건인데 알림 0건"** 이 계속 나왔다.

```bash
notif_count() { curl -s "$BACKEND/api/notifications" ... | python -c "print(len(...))"; }
```

`/api/notifications` 는 **최근 20건 상한**이다. 20건이 쌓인 뒤로는 몇 건을 더
만들어도 길이가 `20 -> 20` 이라 증가분이 0 이 된다.

### 시스템을 먼저 의심했다

두 번 연속 실패를 보고 "브로커 재연결이 안 되나" 로 갔다. 계측을 열어보고서야
방향이 바뀌었다.

```
trade_event_published_total{outcome="ok"}      99      ← 발행은 잘 된다
trade_event_published_total{outcome="failed"}  12      ← 브로커 정지 구간의 것
큐: ready 0, unacked 0, consumers 1                    ← 컨슈머도 붙어 있다
```

**세 지표가 전부 정상이었다.** 시스템은 멀쩡했고 검사가 틀렸다.

### 해결

상한이 없는 집계를 쓴다.

```bash
notif_count() { curl -s "$BACKEND/api/notifications/unread-count" ... ; }
```

### 왜 이게 새로운 방향인가

사례 3은 **잘린 화면**을 읽었고, 이건 **잘린 API 응답**을 읽었다. 형태는 같지만
차이가 있다 — 화면은 사람용이라 "표시가 자를 수 있다"는 의심이 자연스러운데,
**API 응답은 데이터처럼 보인다.** 페이지네이션·상한이 걸린 엔드포인트를
집계 용도로 쓰면 **어느 임계값을 넘는 순간부터** 조용히 틀리기 시작한다.

> 그 전까지는 통과한다. 20건 전에는 이 검사가 정상 동작했다.

## 사례 9: 검사가 다음 실행을 망가뜨리는 상태를 남겼다 (ADR-0030)

같은 스크립트를 **연달아 두 번** 돌리면 두 번째가 실패했다. 판정 5가 브로커를
정지시켰다 살리는데, 백엔드의 캐시된 연결은 곧바로 복구되지 않는다. 그 상태로
다음 실행의 판정 2가 돌면 발행이 실패한다.

즉 **검사가 자기 뒤처리를 안 해서 다음 실행의 전제를 깨뜨렸다.**

해결은 끝에 복구 확인을 붙이는 것이고, 덤으로 **"브로커가 돌아오면 발행이
재개된다"** 는 진짜 성질을 단언하게 됐다(판정 9).

> **검사를 두 번 연달아 돌려보면 이 부류가 드러난다.** 한 번만 돌리면
> "처음엔 통과했는데 왜 지금은 안 되지"로 나타나고, 원인을 시스템에서 찾게 된다.

## 사례 10: 검사가 틀리지 않았는데 **약했다** (ADR-0031) — 새 하위분류

`demo-token` 을 제거하고 "경로가 사라졌다"를 판정으로 걸었다.

```java
mockMvc.perform(post("/api/auth/demo-token") ...)
       .andExpect(status().isNotFound());     // 404 를 기대
```

실제로는 **401** 이 나왔다. 경로가 `PUBLIC_PATHS` 에서 빠져 **보안 계층이 먼저
막기** 때문이다.

### 여기서 갈린다

숫자를 401 로 바꾸면 통과한다. 그리고 **틀린 검사는 아니다** — 401 이든 404 든
토큰은 안 나간다. 앞선 아홉 사례처럼 "거짓 실패"도 "조용한 통과"도 아니다.

**그런데 약하다.** 누군가 이 엔드포인트를 **인증 뒤에 되살려도** 똑같이 401 이
나온다. 즉 그 검사는 "핸들러가 없다"를 확인하지 못한다.

### 해결 — 검사가 확인하려는 계층까지 도달시킨다

```java
mockMvc.perform(post("/api/auth/demo-token")
        .header("Authorization", "Bearer " + validToken())   // 보안을 통과시킨다
        ...)
       .andExpect(status().isNotFound());   // 이제 404 는 핸들러 부재의 직접 증거다
```

### 왜 별도 분류인가

앞의 아홉은 **결과가 틀렸다**(오보/침묵/동전던지기). 이건 **결과는 맞는데 근거가
약하다.** 통과가 뜻하는 바가 의도보다 좁다.

| | 증상 | 발견 |
|---|---|---|
| 오보·침묵·동전던지기 | 결과가 틀리다 | 실행하면 드러난다 |
| **약함** | **결과는 맞는데 다른 이유로 맞는다** | **왜 통과했는지 물어야 드러난다** |

> 이건 뮤테이션으로도 잘 안 잡힌다 — 엔드포인트를 지우면 401 이든 404 든 실패하므로
> "잡았다"고 착각하게 된다. **"이 검사가 통과하는 다른 경로가 있는가"** 를 따로
> 물어야 한다.

## 사례 11: 검사가 "안 뜬 것"을 "닫힌 것"으로 읽었다 (ADR-0031)

배포 오버레이가 포트를 닫는지 확인하는 검사에서 **8080 이 닫혔다고 통과**했다.
실제로는 `SecretGuard` 가 기본 시크릿을 거부해 **백엔드 컨테이너가 아예 안 떴다.**

포트가 닫힌 것과 프로세스가 죽은 것은 **밖에서 보면 똑같다.** 사례 5(대기 조건이
"대상 없음"을 "충족"으로 읽음)와 같은 뿌리이고, 이번엔 그게 **보안 검사**에서 났다.

### 해결

**스택이 살아 있는지 먼저 단언한다.**

```bash
for c in gimp-backend gimp-ai gimp-web; do
  [ "$(docker inspect "$c" --format '{{.State.Status}}')" = "running" ] || bad "..."
done
[ "$ALIVE" = "1" ] || { echo "포트 검사를 건너뛴다"; exit 1; }
```

그리고 **"실제로 쓸 수 있는가"** 를 끝에 뒀다 — 프록시 경유 로그인 200. 포트가
닫혔다는 것만으로는 배포가 성립했다고 말할 수 없다. 이 검사 하나가 두 가지 실수를
같이 잡는다(비밀번호가 시드에 덮인 401, nginx 가 옛 IP 를 문 502).

## 사례 12: 검사가 **배포되지 않는 경로**를 쟀다 (ADR-0033) — 또 새 분류

위조 `X-Forwarded-For` 로 로그인 한도를 우회할 수 있는지 보는 검사였다. 통과하고
있었다. **그런데 배포되는 경로를 재고 있지 않았다.**

```bash
# 판정 6 — 백엔드 포트(8080)에 직접
curl -X POST "$BACKEND_DIRECT/api/auth/login" -H "X-Forwarded-For: 10.0.0.$i" ...
```

주석에 근거까지 적혀 있었다:

> `nginx 를 거치면 nginx 가 헤더를 자기 값으로 덮으므로 스푸핑 시나리오 자체가
> 재현되지 않는다`

**그 주장이 사실이 아니었다.** `nginx.conf` 에 `X-Forwarded-For` 를 설정하는 줄이
아예 없었고, nginx 는 **설정하지 않은 헤더를 지우지 않는다.** 배포 전 점검에서
프록시 경유로 다시 재자:

| 프록시 경유 로그인 40회 | 결과 |
|---|---|
| 위조 XFF (매번 다른 값) | **40회 전부 통과 — 한도 없음** |
| 대조군 (XFF 없음) | 31번째 429 |

게다가 배포 구성에서는 8080이 닫혀 이 판정이 `[FAIL]` 로 나왔고, 런북에
**"그게 정상"** 이라고 적혀 있었다. **실패가 정상으로 문서화된 검사**는 아무것도
못 막는다.

### 왜 이게 또 다른 방향인가

앞의 넷과 다르다. 오보도 침묵도 아니고(대상 안에서는 정확히 동작했다),
동전 던지기도 약함도 아니다 — **결과가 맞고 근거도 맞는데, 잰 대상이 틀렸다.**

약함(사례 10)과 헷갈리기 쉬운데 구분이 있다. 약함은 *같은 대상*을 약한 근거로
통과시킨 것이고, 이건 **대상 자체가 다르다.** 뮤테이션으로도 안 잡힌다 — 백엔드
로직을 망가뜨리면 검사가 정직하게 실패하기 때문이다. **망가진 적 없는 nginx 쪽을
건드려야 드러난다.**

### 해결

검사를 **프록시 경유로 옮겼다.** 그리고 일반 규칙:

> **"이 검사는 X 인 구성에서만 성립한다"는 단서가 붙으면, 배포가 X 인지 물어라.**
> 아니면 그 단서는 "배포에서는 아무것도 안 잰다"는 뜻이다. 단서를 붙이는 것과
> 대상을 옮기는 것은 다르다.

## 사례 13: 새로 만든 가드가 대상을 **0개로 세고** 통과했다 (ADR-0033)

사례 12를 고치면서 "인증 의존성이 없는 경로가 존재하지 않는다"는 가드를 새로
넣었다. **첫 작성본이 통과했는데, 검사한 경로가 0개였다.**

```python
assert len(_api_routes()) >= 5
# AssertionError: assert 0 >= 5
```

이 FastAPI 버전(0.140)은 `include_router` 한 라우터를 `_IncludedRouter` 로 감싸
`app.routes` 에 **평탄화하지 않는다.** 한 겹만 훑으면 아무것도 안 보인다.

침묵(사례 3·5와 같은 방향)이지만 기록하는 이유는 **잡아낸 방법** 때문이다.
본 검사와 **함께 넣은** 자기검사가 즉시 실패했다:

```python
def test_there_is_something_to_check(self):
    """경로가 0개면 아래 검사는 공짜로 통과한다 — 그걸 먼저 막는다."""
    paths = {r.path for r in _guarded_routes()}
    assert len(paths) >= 5
    assert "/api/assistant" in paths      # 개수만 세면 엉뚱한 걸 세도 통과한다
```

**개수만 세지 않고 아는 이름이 잡히는지도 본다.** 개수 하한만 두면 다른 무언가를
5개 세고 통과할 수 있다.

→ **집합을 훑어 판정하는 검사에는 "집합이 비지 않았다"를 같이 넣는다.** 비용이
한 줄이고, 없으면 그 검사는 리팩터링 한 번에 조용히 장식이 된다.

## 사례 14: 오류를 뭉개는 계층이 **검사 둘을 틀린 이유로 통과시키고 있었다** (ADR-0034)

`/error` 를 `PUBLIC_PATHS` 에 넣자(비인증 경로의 400·500이 401 로 가려지던 것을
고친 수정) **멀쩡하던 검사 둘이 즉시 실패했다.**

```
[FAIL] 틀린 비밀번호가 401 이 아니다
[FAIL] 없는 사용자가 401 이 아니다
```

원인은 인증이 아니라 **인코딩**이었다.

```bash
login_code buyer_lee "틀린값"     # 한글 인자
login_code 없는계정 "$DEMO_PW"    # 한글 인자
```

Windows 셸에서 한글 인자가 cp949 로 재인코딩돼 **깨진 JSON** 이 나갔다. 서버는
정직하게 **400** 을 냈는데, `/error` 마스킹이 그걸 **401 로 바꿔놨다.** 검사는
401 을 기대하고 있었으므로 통과했다.

| | 실제 응답 | 검사 결과 |
|---|---|---|
| 수정 전 (마스킹 있음) | 400 → **401 로 표시** | **통과** |
| 수정 후 (마스킹 없음) | **400** | 실패 |
| ASCII 로 고친 뒤 | **401** | 통과 |

**즉 이 두 검사는 비밀번호 검증을 한 번도 재본 적이 없다.** "틀린 비밀번호는 거부되는가"를
묻는다고 적혀 있었지만 실제로 확인한 것은 "깨진 요청은 거부되는가"였다.

### 왜 이 사례를 따로 남기는가

분류는 **약함**(사례 10)이다. 새로운 건 **발견 경로**다.

- 뮤테이션으로는 안 잡힌다 — 비밀번호 로직을 망가뜨리면 검사가 정직하게 실패한다
- 실패 케이스를 돌려봐도 안 잡힌다 — 실제로 401 이 나오니까
- **다른 결함을 고치자 저절로 드러났다**

> **오류를 뭉개는 계층이 하나 있으면, 그 아래의 검사들이 조용히 의미를 잃는다.**
> 400 과 401 이 구분되지 않는 동안에는 "401 을 기대하는 검사"가 무엇을 재는지 아무도
> 알 수 없다. 그래서 **응답 코드가 서로 구분되는지부터** 확인해야 한다 — 그게
> 그 코드 위에 세운 모든 검사의 전제다.

곁들여: 이 저장소의 cp949 함정(`CLAUDE.md` Gotchas)이 **검사 안에서** 발현한 첫 사례다.
한글은 화면 표시용으로만 쓰고, **검사의 입력값은 ASCII 로 둔다.**

## 사례 15: 새 검사의 단언 **절반이 항상 참**이었다 (2026-08-07) — 약함, 두 번째

배포에서 시맨틱 캐시가 한 번도 적중하지 않는 결함을 잡고, 재발 방지로
`verify-container.sh` 에 판정을 하나 넣었다.

```bash
write_query "$TMP/c.json" "수수료 얼마인가요" true    # FAQ 질의
...
if [ "$C_HIT" = "True" ] && [ "$C_LLM" = "0" ]; then    # 적중 + LLM 0회
```

### 그 검사는 결함을 **실제로 잡았다**

배포에서 FAIL 했고, 고친 뒤 PASS 했다. 여기서 멈추면 정상적인 성공 사례다.

### 그런데 실패 출력이 이상했다

```
[FAIL] 캐시 미적중 (hit=False, llm_calls=0)
```

**미적중인데 `llm_calls` 가 0이다.** `faq_smalltalk` 분기는 LLM 을 아예 안
부르기 때문이다.

```python
if intent is Intent.FAQ_SMALLTALK:
    return {"answer": _faq_answer(query), "llm_calls": 0}, intent
```

즉 `llm_calls == 0` 단언은 **캐시가 죽어 있어도 참**이었다. 실제로 일한 단언은
`hit == True` 하나뿐이고, 나머지 절반은 장식이었다.

### 두 번 나쁘다

1. **약하다** — 사례 10과 같은 부류. 통과가 뜻하는 바가 의도보다 좁다.
2. **오독을 유도한다** — 이건 사례 10에 없던 축이다. `llm_calls=0` 은 이
   저장소에서 **캐시 적중의 표지로 문서화돼 있었다.** 실패 메시지가 그 값을
   보여주니, 읽는 사람이 "적중인데 왜 실패?"로 정반대 결론에 이를 수 있다.

### 해결 — 미적중 비용이 0이 아닌 의도로 찌른다

```bash
write_query "$TMP/c.json" "5만원 이하 검 찾아줘" true    # 검색: 미적중 2회
```

실측으로 확인했다.

| | 1회차 | 2회차 | 두 단언 |
|---|---|---|---|
| FAQ (전) | — | `hit=False, llm_calls=0` | **하나만 일함** |
| 검색 (후), 고치기 전 | `False 2` | `hit=False, llm_calls=2` | 둘 다 일함 (FAIL) |
| 검색 (후), 고친 뒤 | `False 2` | `적중, llm_calls=0` | 둘 다 일함 (PASS) |

`2 → 0` 이 캐시가 실제로 LLM 을 아꼈다는 직접 증거다.

### 딸려 나온 것 — 문서 세 곳이 오독을 부추기고 있었다

*"`llm_calls == 0` 은 캐시 적중을 뜻한다"* 가 `CLAUDE.md`·`API-명세.md`·
ADR-0016 에 **일반 명제로** 적혀 있었다. 원래 문맥(검색 분기의 0건 처리)에서는
맞는 말인데, 그 문맥이 지워진 채 규칙으로 읽혔고 **내가 그 규칙을 그대로
믿고 검사를 짰다.**

> **문맥 안에서만 참인 명제를 규칙처럼 적으면, 나중에 그 규칙을 근거로 틀린
> 것이 만들어진다.** 조건을 같이 적거나, 조건을 적을 수 없으면 규칙으로 쓰지
> 않는다.

### 이번엔 뮤테이션 없이 잡혔다

사례 10은 *"이 검사가 통과하는 다른 경로가 있는가"* 를 따로 물어야 드러났다.
이번엔 **실패 출력이 스스로 모순을 드러냈다** — 미적중과 `llm_calls=0` 이 한
줄에 같이 찍혔기 때문이다.

> 그래서 얻는 규칙 하나: **실패 메시지에 판정에 쓴 값을 전부 싣는다.** 통과
> 여부만 찍었으면 못 봤다. 이 검사는 `hit` 과 `llm_calls` 를 둘 다 찍었고,
> 그 둘이 서로 안 맞는다는 게 검사의 결함을 가리켰다.

## 사례 16: 지표가 **한국어의 구분을 못 봤다** (2026-08-07, ADR-0038) — 두 번

프롬프트 A/B/C 를 재는 하네스에서 **같은 형태의 오탐이 두 번** 났다.

### (a) 부정문 — 세 안이 나란히 9를 냈다

```
  안         누출  미완결  면책누락  모순
  A(현재)     12    17      0      9
  B(명시)      0     0      0      9
  C(미언급)    0     0      0      9
```

**서로 다른 세 프롬프트가 정확히 같은 값을 냈다.** 그게 신호였다 — 프롬프트가
아니라 **검출기를 재고 있었다.**

```python
says_anomaly = re.search(r"이상\s*거래", answer)   # 첫 판본
```

정상 거래 답변은 `이상 거래로 판별되지 **않았습니다**` 라고 쓴다. 정규식은
`이상 거래` 만 보고 "이상이라 말했다"로 읽었다. 부정어를 읽게 고치니 0 이 됐다.

### (b) 유보 — 권유가 아닌 것을 권유로 셌다

```python
r"(구매|거래|매수|매도|판매)를? ?(진행|고려|추천|...)"   # 첫 판본
```

*"거래를 **고려하실 때** 이 점을 **참고하시기 바랍니다**"* 가 걸렸다. 그건 사라
말라가 아니라 **판단을 사용자에게 넘기는 문장**이고 오히려 바람직하다.

이 오탐이 채택 판정을 흔들 뻔했다 — B 안이 3건으로 나와 "A 보다 나빠졌다"로
읽힐 상태였다. 서술어 기준(`~하는 것이 좋습니다`)으로 좁히니 B 3 → 0.

### 공통 원인 — 구분이 **어미**에 있는데 **명사**로 짰다

한국어에서 긍정/부정도, 권유/유보도 문장 끝에서 갈린다. 그런데 정규식은
**명사가 잡기 쉽다.** 쉬운 쪽으로 짜면 의미가 반대인 문장이 같은 덩어리로 묶인다.

| | 잡으려던 것 | 같이 잡힌 것 |
|---|---|---|
| 모순 | `이상 거래입니다` | `이상 거래로 판별되지 **않았습니다**` |
| 권유 | `거래하는 것이 **좋습니다**` | `거래를 고려하실 때 **참고하시기 바랍니다**` |

> **한국어를 정규식으로 판정할 때는 어미를 봐야 한다.** 그리고 두 사례 다
> **걸린 표본을 눈으로 읽어서** 드러났다 — 숫자만 봤으면 (a)는 "차이 없음",
> (b)는 "B 가 약간 나쁨"으로 결론 났을 것이다.

## 사례 17: 판정 근거를 **환경에 맡겼다** (2026-08-07, ADR-0037)

목록 정렬이 실제로 적용되는지 보는 백엔드 테스트를 이름순으로 짰다.

```java
.andExpect(jsonPath("$.content[0].name").value("내가 파는 검"))   // 실패
```

두 가지가 틀렸다. **`남`(ㅏ) 이 `내`(ㅐ) 보다 앞**이라는 걸 잘못 알았고 —
그건 고치면 그만이다 — 더 중요한 건 **한글 정렬 순서를 DB 로케일이 정한다**는
것이다.

즉 이 검사는 **내 기계에서 통과하고 배포에서 갈릴 수 있었다.** 통과해도 무엇을
확인했는지 알 수 없다. 가격(숫자)으로 바꿨다.

> **판정 근거가 환경 설정에 의존하면 그 검사는 환경을 재는 것이다.** 콜레이션,
> 타임존, 로케일, 부동소수 표기가 이 부류다.

## 사례 18: **계측을 클라이언트가 캐시해 잔상이 됐다** (2026-08-07, ADR-0037)

검색 결과가 뒤로가기에서 살아남게 하려고 `staleTime: 5분` 을 걸었다.

같은 질의를 다시 물으면 화면이 **서버를 안 부르고 첫 응답을 다시 그린다.**
그 응답에는 `cache: {hit:false}` 가 박혀 있어서 **캐시가 살아 있어도 영원히
"미적중"으로 보였다.** 사용자가 "재질문했는데 캐시 적중이 안 된다"고 보고했다.

시스템은 멀쩡했고 **계측이 낡은 값을 보여주고 있었다.** 이 화면의 배지 줄은
서버 파이프라인을 눈에 보이게 하는 장치인데, 그 값을 클라이언트가 얼려두면
계측이 아니라 잔상이 된다.

> **관측값을 나르는 응답은 캐시하지 않는다.** 값이 맞느냐가 아니라 *언제 찍힌
> 값이냐*가 의미의 일부이기 때문이다. 이건 앞 사례들과 방향이 또 다르다 —
> 검사가 틀린 게 아니라 **검사가 보는 창이 정지해 있었다.**

## 사례 19: **실패를 결측이 아니라 "한쪽 답"으로 셌다** (2026-08-07, ADR-0039)

도메인 게이트의 오거부율·미검출률을 재는 스크립트를 새로 썼다. LLM 845회 중
**443회가 429(TPM 한도 초과)로 죽었는데, 스크립트는 그대로 판정을 냈다.**

호출이 실패하면 `in_domain: None` 을 돌려주게 해뒀다. 그런데 두 지표가 그 값을
정반대로 읽었다.

```python
missed   = [r for r in ood        if r["in_domain"] is not False]  # None → 미검출로 집계
rejected = [r for r in in_domain  if r["in_domain"] is False]      # None → 집계 안 됨
```

| 지표 | 나온 값 | 실제 |
|---|---|---|
| 미검출 | **63.2%** — "게이트가 도메인 밖을 다 통과시킨다" | 429 를 센 것 |
| 오거부 | **11.59%** — 실제보다 **낮게** | 실패한 것이 분모에만 남았다 |

> **하나의 결함이 오보와 침묵을 동시에 냈다.** 같은 `None` 이 한 지표는 나쁘게,
> 다른 지표는 좋게 만들었다. 앞의 열여덟 사례는 한 방향으로만 틀렸는데 이건
> 두 방향이 동시다 — 그래서 "숫자가 이상하니 어딘가 틀렸겠지" 로도 방향을
> 좁힐 수 없다.

원인은 **결측값을 도메인 값으로 인코딩한 것**이다. `None` 은 "in_domain 이
아니다"가 아니라 "모른다"인데, 부울 비교에 넣는 순간 한쪽으로 붙는다.

### 어떻게 알아챘나

수집 단계가 세트별 실패 수를 **출력하고 있었다** — `도메인 안 (신) 509건 실패 218`.
판정만 냈으면 63.2% 를 믿고 프롬프트를 고치러 갔을 것이다. 이전 라운드에서
얻은 규칙(**판정에 쓴 값을 전부 출력에 넣는다**)이 그대로 배당을 냈다.

### 고친 방식

```python
# 1. 실패는 분모에서 뺀다 — 답이 아니라 결측이다
def answered(rows): return [r for r in rows if r["error"] is None]

# 2. 실패율이 기준을 넘으면 **채점 자체를 거부한다**
if error_rate > MAX_ERROR_RATE:
    raise SystemExit("실패가 너무 많아 채점하지 않습니다")
```

두 번째가 요점이다. 실패를 분모에서 빼기만 하면 **표본 절반이 사라진 채로
그럴듯한 숫자가 나온다** — 그건 조용한 실패다. 재수집 사유를 명시적으로 낸다.

원인 자체(TPM 200,000 / 호출당 1,400 토큰)는 동시성 3 + 429 지수 백오프로
해결했다. **동시성만 낮추는 것으로는 부족하다** — 제약이 동시 연결이 아니라
분당 토큰이라, 느리게 던져도 총량이 넘으면 결국 걸린다.

## 사례 20: **모델이 내 방어선에 닿기 전에 스스로 거절했다** (2026-08-07, ADR-0039)

배포 전 확인으로 진짜 ES + 진짜 LLM 에 다섯 케이스를 태웠다. 문제의 질의도
넣었다.

```
[도메인 밖] "삼성전자 주식 어때?"
  intent=compound  llm_calls=1
  답변: 죄송하지만, 저는 게임 아이템 거래소의 상담 도우미로 주식에 대한
        정보는 제공할 수 없습니다.
```

**답이 완벽하다.** 여기서 멈췄으면 "복합 분기 방어도 동작한다"고 적었을 것이다.

그런데 `llm_calls=1` 은 `len(tool_calls) + 1` 이므로 **도구 호출이 0회**라는
뜻이다. 이 라운드에 넣은 방어는 MCP `search_items` 가 도메인 밖일 때 돌려주는
안내 문장인데, **도구를 안 불렀으니 그 코드는 실행조차 안 됐다.** 에이전트가
자기 시스템 프롬프트(*"당신은 게임 아이템 거래소의 상담 도우미입니다"*)만으로
거절한 것이다.

즉 **맞는 답이 방어선이 동작한다는 증거가 아니었다.** 도구를 직접 불러 따로
확인했다.

```
[도메인 밖] "삼성전자 주식 시세"  →  {"note": "이 질의는 … 범위 밖입니다"}
[대조군]    "5만원 이하 검"       →  {"item_id": 5, "name": "미스릴 단검", …}
```

> **LLM 에이전트에서는 "약함"(사례 10)이 특히 잡기 어렵다.** 모델이 내 코드
> 경로를 **건너뛰고도 옳은 답**을 낼 수 있기 때문이다. 결정적 코드라면 경로를
> 안 밟으면 대개 답이 틀리는데, 여기서는 안 밟고도 맞았다.
>
> 처방: **방어선마다 그 층이 실행됐다는 흔적을 본다.** 여기서는 `llm_calls`
> 하나가 그 역할을 했다 — 답변만 봤다면 아무 신호도 없었다.

## 사례 21: 검사 **14/14 통과, 배포 정상, 화면만 옛것** (2026-08-07, ADR-0039)

`verify-container.sh` 가 14/14 로 통과했다. 판정 1-c 는 서버가
`out_of_domain: true` 를 준다고 확인했고, 이미지 안 번들에도 새 코드가 있었다.

```
docker exec gimp-web sh -c 'grep -rl "도메인 밖" /usr/share/nginx/html/assets/'
/usr/share/nginx/html/assets/index-BqsMhC-J.js
```

그런데 브라우저에는 그 배지가 안 떴다. **서버도 맞고 이미지도 맞는데 사용자가
보는 것만 틀린** 상태다.

### 원인 — 지시를 안 적은 것이 "캐시 안 함"이 아니다

```nginx
location / { try_files $uri $uri/ /index.html; }   # 캐시 지시 없음
location /assets/ { expires 1y; add_header Cache-Control "public, immutable"; }
```

해시 자산을 영구 캐시하는 건 맞다. 그런데 **그 해시 이름을 알려주는 건
`index.html` 하나뿐**이고, 거기엔 아무 지시가 없었다. 지시가 없으면 브라우저는
`Last-Modified` 기준 **휴리스틱 캐싱**을 적용한다 — "캐시하지 마라"가 아니라
"알아서 정해라"다. 그래서 브라우저가 `index.html` 과 옛 JS 를 **둘 다 로컬에서**
꺼내 쓰고 서버를 아예 부르지 않았다.

> **모든 검사가 서버 쪽만 보고 있었다.** 판정 1~4 는 전부 `curl` 로 서버에
> 직접 묻는다. 브라우저가 서버에 안 물어보는 상황은 그 어떤 검사도 재현하지
> 않는다 — **검사와 사용자가 다른 경로를 밟고 있었다**(사례 12의 변종인데,
> 이번엔 "배포되지 않는 경로"가 아니라 **"검사가 도달할 수 없는 상태"** 다).

### 고친 방식

`location /` 에 `add_header Cache-Control "no-cache";`. 저장 금지가 아니라
**쓰기 전에 확인하라**는 뜻이라 대개 304 로 끝난다.

검사(판정 3-b)는 **둘을 같이 본다.** index.html 만 보면 "전부 no-cache" 로
되돌려도 통과하는데, 그러면 자산까지 매번 다시 받는다. 그리고 자산 경로를
index.html 에서 **직접 뽑아** 확인하므로, 못 찾으면 그것도 실패로 보고한다 —
검사가 대상에 닿았는지를 먼저 확인하는 것이다(사례 3의 교훈).

일부러 틀린 값 셋(`max-age=3600`, 헤더 없음, 올바른 값)으로 돌려 세 경우가
각각 실패·실패·통과로 갈리는 것을 확인했다.

### 그런데 그 새 검사가 첫 실행에서 **오보를 냈다**

배포하고 돌리니 `15 · 실패 1`.

```
[PASS] index.html — Cache-Control: no-cache
[FAIL] 해시 자산이 길게 캐시되지 않는다 — Cache-Control: max-age=31536000
```

설정은 멀쩡했다. `expires 1y;` 와 `add_header Cache-Control "public, immutable";`
는 **서로 모르고 각자 한 줄씩** 내보내므로 응답에 `Cache-Control` 이 **두 줄**이다.

```
cache-control: max-age=31536000        <- expires 가 만든 것
cache-control: public, immutable       <- add_header 가 만든 것
```

검사가 `grep ... | head -1` 로 **첫 줄만** 보고 `immutable` 을 놓쳤다. RFC 상
같은 이름의 헤더 여럿은 쉼표로 이은 하나와 같으므로 브라우저는 정상 동작한다 —
**틀린 건 검사뿐**이다.

> **헤더는 한 줄이라는 가정이 검사 안에 숨어 있었다.** `head -1` 은 "여러 줄이면
> 첫 줄" 이라는 정책을 말없이 정한 것이고, 그 정책에 근거가 없었다. 이제 전부
> 이어붙여 판정하고, 실패 메시지에 **이어붙인 전체 값**을 찍는다 — 다음에 이
> 검사가 실패하면 그 줄이 원인을 바로 말해준다.

같은 라운드에 만든 검사가 **하루도 못 가 자기 오보를 냈다.** 앞의 스무 사례가
말하는 것과 정확히 같다: 새 검사는 통과만이 아니라 **틀린 값 여러 형태**로
돌려봐야 한다. 이번엔 "값이 틀린 경우"만 돌려보고 **"헤더가 여러 개인 경우"** 는
생각하지 못했다.

### 그리고 고친 뒤에도 같은 실패가 또 나왔다 — 이번엔 **옛 판본이 돌았다**

고쳐서 푸시하고 다시 돌렸는데 출력이 **글자 하나까지 같았다.** `git pull` 이
빠져 있었다.

이건 출력만으로 확정할 수 있었다. 고친 판본은 `immutable` **또는** 긴 `max-age`
를 받으므로 `max-age=31536000` 에서 **통과했어야 한다.** 실패가 났다는 것 자체가
"옛 판본이 돌았다"는 증거다.

> **검사 결과를 읽기 전에 "무엇을 실행했는가"가 보여야 한다.** 이 저장소는
> ADR-0031 이 `demo-token` 을 지웠는데 `verify-container.sh` 를 안 고쳐서 그
> 검사가 **여섯 라운드 동안 첫 줄에서 죽어 있던** 전례가 있다. 그때는 검사가
> 낡았고 이번엔 실행본이 낡았는데, **증상은 똑같이 "설명이 안 되는 실패"** 다.

세 검사 스크립트 전부 첫 줄에 판본을 찍게 했다 — 커밋과 **미커밋 변경 여부**를
같이 낸다(로컬에서 고치고 커밋 안 한 상태도 흔하다).

```
검사 판본: ba42178 fix: 캐시 검사가 헤더를 한 줄로 가정해 오보를 냈다
```

**셋 다 고친 이유**는 한 곳만 고치면 다음엔 나머지 둘에서 같은 일이 나기
때문이다 — 이 저장소가 `X-Forwarded-For` 에서 이미 겪은 형태다(한쪽만 손대서
구멍이 남았다).

### 네 번째 — 이번엔 **원인을 정반대로 지목했다**

판본을 맞춰 돌리니 3-b 는 통과했고(`max-age=31536000,public, immutable` — 헤더가
두 줄이라는 가설이 확정됐다) 대신 **1-c 대조군**이 깨졌다.

```
[FAIL] 대조군 실패 — 도메인 안 질의가 막혔다. out_of_domain=False 결과 0건.
       게이트가 전부 거절하고 있다면 미검출 0% 는 아무 의미가 없다
```

그런데 같은 질의(`"5만원 이하 검 찾아줘"`)가 **같은 실행의 판정 1 에서 방금
성공**했다(답변 29자). 게이트가 막았다면 `out_of_domain=True` 여야 하는데
`False` 다. 즉 **게이트 판정이 아예 없었다** — 본문이 응답 JSON 이 아니었던
것이다(429 가 유력).

`verdict()` 가 **HTTP 코드를 안 봤다.** 429 본문에는 `out_of_domain` 이 없으니
`False`, `results` 도 없으니 `0` 이 되고, 그 조합이 "게이트가 막았다"의 신호와
**정확히 같다.**

> 이 파일의 **로그인 검사에 같은 교훈이 이미 주석으로 달려 있었다** — 처음엔
> "비밀번호 확인"만 찍었는데 실제 원인이 429 였고, *"원인을 잘못 지목하는 검사는
> 없느니만 못하다 — 사람이 엉뚱한 곳을 파게 만든다"* 고 적어뒀다. **새 검사를
> 붙이면서 그 교훈을 옮기지 않았다.**

고침: `verdict()` 가 `HTTP코드 out_of_domain intent llm_calls 결과수` 를 내고,
200 이 아니면 **"판정 불가"** 로 사유(429 한도 소진 / 401 인증 / 5xx 서버)를
그대로 말한다. 거절 쪽 두 검사에도 같이 걸었다 — 429 가 거기서 나면
`out_of_domain=False` 라 **"거절 안 됨"** 으로 잘못 보고했을 것이다.

### 다섯 번째 — **고친 그 검사만 고쳤다**

한도가 실제로 소진된 상태에서 다시 돌리니 1-c 는 정직하게 `판정 불가 — 한도
소진(429)` 을 냈다. 그런데 **같은 실행의 판정 1 과 1-b 는 여전히 거짓말을 했다.**

```
[FAIL] FAQ — intent=<없음> (기대 faq_smalltalk), 답변 0자
[FAIL] 캐시 미적중 … Redis 연결을 의심하라: docker exec gimp-ai …
```

전부 같은 429 다. 캐시 검사는 **"Redis 를 의심하라"** 며 엉뚱한 진단 명령까지
띄웠다 — 캐시는 멀쩡했고 요청이 파이프라인에 들어가지도 못했다.

> **바로 앞 절에서 "다른 검사가 이미 배운 것을 옮겼는가"를 체크리스트에
> 적어놓고, 그 라운드 안에서 같은 실수를 했다.** 고칠 때 1-c 만 보고 이웃을
> 안 봤다.

`transport_fault()` / `assistant_call()` 을 파일 맨 위 공용으로 올리고 **세 검사
전부**가 쓰게 했다. 다섯 조합(정상 적중 / 2회차 429 / 1회차만 429 / 진짜 미적중 /
0건)으로 분기가 갈리는 것을 확인했다.

### 곁가지 — 진단 명령 자체도 틀렸다

한도를 확인하라고 준 명령이 `AUTH failed: WRONGPASS` 로 죽었다.

```bash
docker exec gimp-redis sh -c '... -a "$REDIS_PASSWORD" ...'   # 컨테이너 안에서 전개
```

`docker-compose.yml` 의 redis 서비스에는 **`environment:` 블록이 없다.**
`command:` 의 `${REDIS_PASSWORD}` 는 **호스트에서 compose 가 치환**하므로
컨테이너 안에 그 변수는 존재하지 않는다. 빈 값으로 인증을 시도한 것이다.
호스트에서 `.env` 를 읽어 넘겨야 한다.

같이 알게 된 운영 사실: **이 스크립트는 한 실행에 `/api/assistant` 를 9회
부른다.** 사용자당 일일 한도가 50회라 하루 5번쯤 돌리면 소진된다. 스크립트
주석에 남겼다.

## 사례 22: **사전 등록한 기준이 잡음과 구분되지 않았다** (2026-08-07, ADR-0039)

### 문제

도메인 게이트의 오거부를 고치는 라운드에서, 경계 세트 거절을 `현재 2/16 → 목표
1/16 이하` 로 **사전 등록**했다. 형식은 이 저장소 방식 그대로다 — 결과를 보기
전에 정하고 나중에 고쳐 쓰지 않는다.

**형식은 맞았는데 기준 자체가 무의미했다.**

### 발생 원인

표본이 16건이면 **한 건이 최소 측정 단위**다. Clopper-Pearson 정확 구간을
붙여보니 이렇다.

| | 비율 | 95% 구간 |
|---|---|---|
| 2/16 | 12.5% | [1.6%, 38.3%] |
| 1/16 | 6.3% | [0.2%, 30.2%] |

**거의 완전히 포개진다.** 효과가 없어도 우연히 1/16 이 나오고, 실제 개선이
있어도 우연히 2/16 이 나온다. 즉 이 기준은 **동전 한 번 던지기와 구분되지
않는다** — 그런데 출력은 `PASS` / `FAIL` 이라는 단호한 두 글자다.

실제로 그 뒤 실행에서 변형 A 가 `5/32 → 4/32` 를 냈다. 구간이 [5.3%, 32.8%] 와
[3.5%, 29.0%] 로 포개져 잡음이었고, **기준만 봤다면 개선으로 읽었을 것이다.**

### 해결 방법

- **경계 세트를 16 → 32 로 늘렸다.** 늘리면 예전 수치와 분모가 끊기므로
  원래 16건을 `BOUNDARY_V1` 로 이름 고정해 **두 분모로 같이 보고**한다
- **모든 실행에 95% 구간을 같이 찍는다.** 스크립트가 `구간이 겹치면 '개선' 이라고
  부르지 않는다` 고 직접 말한다
- **기준의 성격을 낮춰 적었다.** 통과/실패는 tripwire 고, 실제 판정은 두 실행
  일치 + **걸린 표본을 부류별로 읽기**다. 이 저장소에서 방향을 잡아준 것은
  언제나 후자였다

### 배운 점

- **사전 등록이라는 형식은 기준의 타당성을 보장하지 않는다.** 결과를 보고
  고치지 않는 것과, 애초에 잴 수 있는 기준인 것은 별개다
- **표본이 작을수록 이진 판정은 위험하다.** `PASS`/`FAIL` 은 구간을 숨기고,
  숨겨진 구간은 잡음을 성과로 바꾼다
- **문턱을 정할 때 잡음 바닥을 먼저 재라는 규칙(ADR-0028)의 이산 버전이다.**
  거기서는 유휴 타이머 해상도였고 여기서는 이항 분산이다. 둘 다
  **"이 계측기가 구분할 수 있는 최소 차이" 를 안 물어본 것**이다
- 이건 내가 스스로 잡은 게 아니라 **설계 검토에서 지적받아** 잡았다. 표본 크기는
  코드 리뷰가 아니라 **측정 설계 리뷰**에서만 걸린다

## 사례 23: `str.replace` 가 못 찾으면 **조용히 원본을 돌려준다** (2026-08-07, ADR-0039)

### 문제

프롬프트 변형 A 를 원본에서 파생시켰다.

```python
_PROMPT_A = _PROMPT.replace("다른 말은 쓰지 마세요.
", "...한 줄 추가...", 1)
```

대상 문구가 한 글자라도 다르면 `replace` 는 **예외 없이 원본을 그대로 돌려준다.**
그러면 `A` 와 `control` 이 글자까지 같은 프롬프트가 되고, 비교표에 **두 열이
나란히 같은 숫자**를 낸다.

그 출력은 *"변형이 효과가 없다"* 로 읽힌다. 실제로는 **변형을 재지 않은 것**이다.
그리고 이 라운드는 LLM 을 1,746회 태운다 — 다 쓰고 나서야 알게 된다.

### 해결 방법

import 시점에 단언한다. 변형이 원본과 같으면 거기서 멈춘다.

```python
if _PROMPT_A == _PROMPT:
    raise SystemExit("변형 A 가 원본과 같습니다 - replace 대상 문구를 확인하세요")
```

같은 자리에 하나 더 붙였다. **B 는 A 의 한 줄을 포함해야 ablation 이 성립**하므로
그것도 단언한다 — 안 그러면 "A 만으로 고쳐지는가" 라는 질문 자체가 성립하지 않는다.

그리고 **프롬프트의 예시가 held-out 세트에 있으면 안 된다**는 것도 같이 고정했다.
한 문장 겹치면 그 질의는 다음 측정에서 자동으로 맞고, **일반화가 아니라 암기**를
재게 된다.

### 배운 점

- **파생으로 만든 실험 조건은 "실제로 달라졌는가" 를 단언해야 한다.** 이 저장소가
  임베딩 before/after 에서 겪은 것과 같은 종류다 — 두 피연산자가 사실 같은
  모델이었고, 개선 0 이 실패 없이 보고됐다
- **조용히 원본을 돌려주는 API 는 전부 이 위험을 갖는다** (`str.replace`,
  `dict.get`, `re.sub`). 값이 안 바뀐 것과 바꿀 필요가 없던 것이 구분되지 않는다
- **비용이 큰 측정일수록 사전 단언이 싸다.** 1,746회를 태우기 전에 문자열 비교
  한 줄이면 된다

## 사례 24: **내가 준 확인 절차가 캐시 적중을 구분하지 못했다** (2026-08-08, ADR-0040)

### 문제

`무속성` 추출을 고치고 배포 안내를 이렇게 줬다.

> 확인은 `"무속성 검 찾아줘"` 한 번이면 됩니다 — 불꽃의 대검이 안 섞여 나와야 합니다.

배포 후 그대로 해봤더니 **불꽃의 대검이 그대로 나왔다.** 코드가 틀렸거나 배포가
안 된 것처럼 보였는데 **둘 다 아니었다.** 시맨틱 캐시가 **배포 전에 저장된 응답을
재생**하고 있었다.

### 발생 원인

두 겹이다.

**하나, `cache_version` 을 안 올렸다.** ADR-0040 은 *"응답 모양은 그대로라 올릴
필요 없다"* 고 명시적으로 판단했는데, 설정 주석은 **모양과 내용 둘 다** 올릴
이유라고 말하고 있었다. 필터가 하나 더 걸리면 **같은 질의가 다른 결과 집합**을
내놓는다 — 그게 내용 변경이다. 주석의 절반만 읽었다.

**둘, 내가 준 확인 절차가 그 실패를 구분하지 못했다.** *"불꽃의 대검이 안 나와야
한다"* 는 참/거짓 하나뿐이라, 거짓일 때

- 후처리가 안 걸렸다
- 배포가 안 됐다
- **캐시가 옛 응답을 재생한다**

셋을 구분해주지 못한다. 이 저장소가 반복해 적은 *"판정에 쓴 값을 전부 출력에
넣어라"* 를 **내가 준 절차에는 적용하지 않았다.**

### 해결 방법

- `cache_version` **v2 → v3**
- 확인 절차를 **두 신호로** 바꿨다
  - 화면 관측 패널의 `캐시 적중` / `LLM 호출` 배지 — **적중이면 그 응답은 배포 전
    것이다.** 코드를 의심하기 전에 이걸 본다
  - 답변 **문구** — 고쳐졌으면 `검 · 무속성 조건으로 N건` 이고, 안 고쳐졌으면
    `검 조건으로 N건` 이다. 결과 목록보다 이쪽이 먼저 갈린다
- 그 문구를 테스트로 고정했다(`TestTheUserVisibleSignal`) — 진단에 쓰는 문자열이
  말없이 바뀌면 다음 사람이 같은 데서 헤맨다

### 배운 점

- **"고쳐졌는지" 를 결과물 하나로만 확인하는 절차는 실패 원인을 지목하지
  못한다.** 원인 후보가 셋인데 신호가 하나면, 사람은 대개 가장 무거운 것(코드)을
  먼저 의심한다
- **관측 패널이 이미 답을 들고 있었다.** `캐시 적중 (exact)` + `LLM 호출 0회` 는
  "이 응답은 지금 계산된 게 아니다" 라는 뜻이다. 화면에 있는데 **확인 절차가
  가리키지 않아서** 안 봤다
- **캐시 무효화는 "모양이 바뀌었나" 가 아니라 "같은 질의가 다른 답을 내나" 로
  판단한다.** 전자는 후자의 부분집합이다

## 사례 25: **`running` 을 `준비됨` 으로 읽었다** (2026-08-08, ADR-0042)

### 문제

배포 안내에 이렇게 적었다.

```
$DC up -d --build ai
docker exec gimp-ai python -c "...urlopen('http://localhost:8000/health')..."
```

`Connection refused` 가 났다. 코드가 깨졌거나 기동에 실패한 것처럼 보였는데
**앱이 아직 안 뜬 것뿐**이었다.

### 발생 원인

**컨테이너는 시작하자마자 `running` 이고, 그 시점의 uvicorn 은 아직 포트를 안
열었다.** 그리고 `Connection refused` 는

- 아직 기동 중
- 기동에 실패해 죽음
- 포트를 다른 주소에 바인딩

셋을 **구분해주지 않는다.**

**compose 자신은 이걸 알고 있었다.** `ai` 서비스 헬스체크가 같은 URL 을 쓰면서
`start_period: 20s`, `retries: 12` 를 단다. 즉 "기동에 시간이 걸린다" 가 이미
설정에 적혀 있는데, **내가 준 명령만 그걸 몰랐다.**

그리고 `load/verify-deploy.sh` 도 같은 사각을 갖고 있었다 — 사전 확인이
`.State.Status == running` 만 봤다. 그건 **기동 직후에도 참**이라, 뒤따르는
포트·프록시 검사가 순전히 타이밍 때문에 실패할 수 있었다.

### 해결 방법

- 안내 명령에 **healthy 대기**를 넣었다
- `verify-deploy.sh` 의 사전 확인을 `running` → **`healthy`(있으면)** 로 바꿨다.
  헬스체크가 없는 컨테이너만 `running` 으로 본다
- 실패 시 **status 와 health 를 둘 다 찍는다** — "실패" 한 줄만 내면 안 떴는지
  아직인지 죽었는지를 사람이 다시 조사해야 한다
- `unhealthy` 는 **기다리지 않고 즉시 실패**한다. 기다려도 안 낫는다

### 배운 점

- **`running` 은 준비 상태가 아니다.** 오케스트레이터가 헬스체크를 두는 이유가
  그것이고, **그 신호를 이미 정의해뒀으면 검사도 그걸 봐야 한다** — 따로
  `sleep` 을 넣는 것보다 정확하고 빠르다
- **연결 거부는 진단이 아니다.** 이 파일이 사례 11 에 적어둔 *"포트가 닫혔다와
  프로세스가 죽었다는 밖에서 똑같이 보인다"* 의 반대 방향이다 — 이번엔 아직
  안 연 것이었다

## 사례 26: **파이프 뒤의 `$?` 는 마지막 단계의 종료 코드다** (2026-08-08, ADR-0043)

### 문제

IR 게이트가 실패 경로에서 제대로 떨어지는지 확인하려고 이렇게 쟀다.

```bash
python -m scripts.evaluate_embedding --finetuned models/does-not-exist ... | tail -4
echo "exit=$?"      # -> exit=0

python -m scripts.check_ir_gate ../nope.json | tail -3
echo "exit=$?"      # -> exit=0
```

**둘 다 0 이 나왔다.** 방금 `raise SystemExit(1)` 을 손으로 넣은 코드였다.

두 갈래로 잘못 읽을 수 있었고 **양쪽 다 나쁘다**:

- "가드가 안 걸렸구나" → 멀쩡한 코드를 고치러 간다
- 반대로 통과 경로만 봤다면 "게이트가 잘 돈다" → **실패를 못 잡는 게이트를 배포**

### 발생 원인

`$?` 는 **파이프라인 마지막 명령의 종료 코드**다. `tail` 은 항상 0 으로 끝나므로
앞 단계가 무엇으로 죽든 0 이 보인다. 파이썬의 종료 코드는 `tail` 에 먹혔다.

**표시를 다듬으려고 끼운 필터가 판정을 바꿨다.** 한글 출력이 콘솔 코드페이지 탓에
깨져서 `| grep -v tokenizer | tail` 로 정리한 것이 원인이었다 — 읽기 좋게 만든
행동이 측정을 무효화했다.

이건 이 파일의 사례 21 과 **같은 과**다. 거기서는 `grep … | head -1` 이 헤더
두 줄 중 하나만 읽어 근거 없는 정책을 지어냈다. 이번엔 `| tail` 이 종료 코드를
지어냈다. **표시용 필터는 판정 경로에 있으면 안 된다.**

### 해결 방법

파이프를 걷어내고 다시 쟀다.

```bash
python -m scripts.evaluate_embedding --finetuned models/does-not-exist ... >/dev/null 2>&1
echo "A) exit=$?"   # -> 1
python -m scripts.check_ir_gate ../nope.json >/dev/null 2>&1
echo "B) exit=$?"   # -> 1
```

종료 코드가 필요한데 출력도 보고 싶으면 셋 중 하나다 — 출력을 파일로 보내고
따로 읽기, `${PIPESTATUS[0]}`, `set -o pipefail`.

CI 워크플로 쪽은 이 실수가 **원리적으로 안 난다.** `run:` 스텝은 파이프 없이
명령을 그대로 실행하고 GitHub Actions 가 종료 코드를 읽기 때문이다. 즉 **손으로
확인할 때만 생기는 결함**이라, 손 확인이 CI 보다 약한 경우가 있다는 뜻이기도 하다.

### 배운 점

- **판정에 쓰는 명령에는 파이프를 붙이지 않는다.** 붙이는 순간 `$?` 는 다른
  명령의 것이 된다
- **읽기 좋게 만드는 행동이 측정을 무효화할 수 있다.** 이 저장소에서 두 번째다
  (사례 21 의 `head -1`). 둘 다 "출력을 정리하려다" 나왔다
- **의도적으로 실패하는 입력을 넣어보는 것만으로는 부족하고, 그 결과를 읽는
  방법도 맞아야 한다.** 이번엔 실패 케이스를 제대로 만들어놓고 **읽기에서**
  틀렸다
- 이 검사를 검증하려고 만든 **시뮬레이션이 그 자리에서 또 틀렸다.** 가짜
  `docker` 가 `$3`(`--format`)을 컨테이너 이름으로 봐서 모든 경우가 "실패" 로
  나왔고, 하마터면 멀쩡한 로직을 고칠 뻔했다. `$2` 로 고치니 5경우가 전부
  의도대로 갈렸다 — **검사를 검사할 때도 실패 케이스와 통과 케이스를 둘 다
  넣어야 한다**(전부 실패면 harness 를 의심할 것)

## 배운 점

### 성공 신호가 확인 대상과 어긋나는 계열이 따로 있다

이 저장소에서 세 번 반복된 형태다.

| 겉보기 신호 | 실제 |
|---|---|
| "포트가 응답한다" | 내가 띄운 프로세스가 아니라 **살아남은 옛 JVM**이 응답 |
| "검사가 통과했다" | 검사가 **아무것도 확인하지 않고** 통과 (사례 3·5) |
| "빌드가 성공했다" | **구버전 내용**이 담긴 이미지가 만들어짐 (사례 6) |

공통 처방은 하나다 — **신호가 아니라 결과물을 확인한다.** 포트가 아니라 기동
로그를, 통과 여부가 아니라 무엇을 셌는지를, `Built` 가 아니라 이미지 안의 파일을.

### 검사는 다섯 방향으로 틀린다

| 방향 | 증상 | 발견 난이도 |
|---|---|---|
| **오보** | 정상 시스템에 실패 보고 | 쉽다 — 확인하다 드러난다 |
| **침묵** | 결함이 있는데 통과 | **어렵다 — 아무 일도 안 일어난다** |
| **동전 던지기** | 같은 코드에서 통과/실패가 갈린다 | **어렵다 — 한 번만 돌리면 안 보인다** |
| **약함** | 결과는 맞는데 **다른 이유로** 맞는다 | **아주 어렵다 — "왜 통과했나"를 물어야 한다** |
| **엉뚱한 대상** | 대상 안에서는 정확한데 **잰 대상이 배포되는 것이 아니다** | **가장 어렵다 — 뮤테이션으로도 안 잡힌다** |
| **결측의 인코딩** | 한 결함이 **오보와 침묵을 동시에** 낸다 | 어렵다 — 숫자가 이상해도 방향을 못 좁힌다 (사례 19) |

마지막 방향이 특히 고약한 이유: 검사 대상을 망가뜨리면 검사가 **정직하게
실패한다.** 그래서 "실패시켜 봤다"까지 해도 통과한다 — 망가뜨려야 할 곳은
검사가 쳐다보지도 않는 쪽이기 때문이다(사례 12의 nginx).

정상 시스템에 실패를 보고하는 검사는 없느니만 못하지만, **결함을 놓치는 검사는
그보다 더 나쁘다.** 있다는 사실만으로 안심을 주기 때문이다.

### 검사를 붙였으면 실패시켜 봐야 한다

사례 3은 **일부러 오염된 조건(운영 한도 그대로)으로 돌려봤기 때문에** 발견됐다.
완화 구성으로만 돌렸으면 경고가 안 울리는 게 정상으로 보였을 것이고, 그 상태로
"오염 검사가 있다"고 문서에 적었을 것이다.

→ **음성 사례와 양성 사례를 둘 다 돌린다.** 초록만 보고 검사가 동작한다고
결론짓지 않는다. (CI 첫 도입 때도 같은 방식이 결함을 잡았다 —
[[의존성-선언-누락-오래된-venv]])

### 요약된 출력 위에 검사를 세우지 않는다

표시용 출력은 **읽는 사람을 위해 자르고 정렬한다.** 그 판단 기준(상위 N, 절댓값
순)은 검사가 필요로 하는 것과 다르다. 원본이 있으면 원본에서 센다.

특히 **단위가 다른 값이 한 순위에 섞이면** 순위는 의미를 잃는다 — 바이트는
언제나 요청 수를 이긴다. 이 표시 결함 자체는 로드맵에 등록해뒀다.

### 재발 조건 체크리스트

- [ ] 이 검사의 **입력이 원본인가, 사람이 읽으라고 가공된 출력인가?**
      후자면 가공 규칙(자르기·정렬·반올림)이 검사를 조용히 무력화할 수 있다
- [ ] **일부러 실패하는 조건으로 돌려봤는가?** 통과만 확인한 검사는
      "항상 통과하는 검사"와 구분되지 않는다
- [ ] 검사가 세는 대상의 **범위가 시나리오와 일치하는가?**
      (사례 2 — 프로파일은 20개인데 검사는 1개를 봤다)
- [ ] 측정 구간 **밖에서 발생하는 부수 효과**가 있는가?
      (사례 1 — `setup()`의 요청이 상태를 바꾼다)
- [ ] 새 구성요소가 들어오면서 **기존 검사의 전제가 바뀌지 않았는가?**
      (사례 3 — 인증 도입으로 필터체인 계열 9개가 순위를 잠식했다)
- [ ] **판정선이 계측기의 잡음 바닥보다 충분히 위에 있는가?**
      바닥을 재본 적이 없다면 그 판정선의 근거는 없는 것이다 (사례 4)
- [ ] 판정선이 **단일 표본 통계량(`max`, `min`)** 에 걸려 있지 않은가?
      표본 하나가 판정을 뒤집으면 그건 시스템이 아니라 운을 재는 것이다 (사례 4)
- [ ] **같은 조건에서 두 번 돌려 같은 답이 나오는가?**
      한 번만 돌린 판정은 통과든 실패든 근거가 약하다 (사례 4)
- [ ] 대기·완료 조건이 **"대상이 없는 상태"에서도 통과하지 않는가?**
      빈 목록, 이전 실행의 잔해가 조건을 만족시킬 수 있다 (사례 5).
      낡은 값으로는 성립할 수 없는 조건으로 바꿀 것
- [ ] 도구가 준 **성공 메시지가 아니라 결과물**을 봤는가?
      `Built` / `200 OK` / `통과`는 확인 대상이 아니라 신호일 뿐이다 (사례 6)
- [ ] 테스트가 **검증하려는 지점을 실제로 지나는가?**
      앞선 검증에서 걸러지면 뒤의 코드는 실행조차 안 된다 (사례 7).
      확인법: 그 지점을 **일부러 깨고** 테스트가 실패하는지 본다
- [ ] "안 일어난다"를 단언하는 테스트에 **대조군**이 있는가?
      `never()` 계열은 아무것도 안 해도 통과한다 (사례 7)
- [ ] 세는 값에 **상한·페이지네이션**이 걸려 있지 않은가?
      API 응답은 데이터처럼 보이지만 잘려 있을 수 있고, **임계값을 넘는 순간부터**
      조용히 틀린다 (사례 8). 총계가 필요하면 총계를 주는 엔드포인트를 쓴다
- [ ] 검사를 **연달아 두 번** 돌려도 같은 결과인가?
      자기가 바꾼 상태를 되돌리지 않으면 다음 실행의 전제를 깨뜨린다 (사례 9)
- [ ] **이 검사가 통과하는 다른 경로가 있는가?**
      결과가 맞아도 의도한 이유로 맞는 게 아닐 수 있다 (사례 10).
      뮤테이션으로는 잘 안 잡히므로 **"왜 통과했나"를 따로 물어야 한다**
- [ ] 검사 대상이 **살아 있는지 먼저 확인**했는가?
      "포트가 닫혔다"와 "프로세스가 죽었다"는 밖에서 똑같이 보인다 (사례 11)
- [ ] **실패·결측이 어느 쪽 답으로 집계되고 있지 않은가?**
      `None`을 부울 비교에 넣으면 한쪽으로 붙는다. 분모에서 빼고,
      실패율이 기준을 넘으면 **채점 자체를 거부한다** (사례 19)
- [ ] **실행한 검사가 최신 판본인가?** 결과를 읽기 전에 판본이 출력에
      찍혀야 한다. 설명이 안 되는 실패의 첫 번째 후보다 (사례 21)
- [ ] 본문을 파싱하기 전에 **HTTP 코드를 봤는가?**
      오류 본문에는 찾는 필드가 없고, "필드 없음"은 대개 **의미 있는 값 하나와
      똑같이 보인다** — 429가 "게이트가 막았다"로 읽혔다 (사례 21)
- [ ] 이 파일의 **다른 검사가 이미 배운 것**을 새 검사에 옮겼는가?
      같은 파일 안에서 같은 실수가 반복됐다 (429 구분)
- [ ] 검사가 읽는 값이 **하나뿐이라고 가정하고 있지 않은가?**
      HTTP 헤더는 같은 이름이 여러 줄일 수 있다. `head -1` 은 근거 없는 정책을
      말없이 정하는 것이다 (사례 21)
- [ ] **`running` 을 `준비됨` 으로 읽고 있지 않은가?**
      컨테이너는 시작 즉시 running 이고 앱은 아직 포트를 안 열었다. 헬스체크가
      정의돼 있으면 그 신호를 본다 — sleep 보다 정확하고 빠르다 (사례 25)
- [ ] **"고쳐졌는지" 를 결과물 하나로만 보고 있지 않은가?**
      원인 후보가 여럿인데 신호가 하나면 사람은 가장 무거운 것부터 의심한다.
      캐시 적중 배지가 화면에 있었는데 절차가 안 가리켰다 (사례 24)
- [ ] 검사가 **사용자와 같은 경로**를 밟는가?
      `curl` 은 언제나 서버에 묻지만 브라우저는 캐시에서 꺼내 쓸 수 있다.
      서버가 맞고 이미지가 맞아도 화면이 틀릴 수 있다 (사례 21)
- [ ] 방어선을 확인할 때 **그 층이 실제로 실행됐다는 흔적**을 봤는가?
      LLM 에이전트는 내 코드를 건너뛰고도 옳은 답을 낸다 (사례 20)
- [ ] 지표에 **양방향이 다 있는가?**
      거절률만 재면 "전부 거절"이 만점을 받고, 통과율만 재면 "전부 통과"가
      만점을 받는다. 한 방향만 재는 지표는 반대쪽 극단을 최적해로 만든다
- [ ] 프롬프트를 고쳤다면 **회귀 대조군을 뒀는가?**
      LLM은 같은 입력에도 흔들리므로(ADR-0017), 신·구 일치율만으로는
      프롬프트 탓인지 계측기 바닥인지 알 수 없다. 구프롬프트를 두 번 태운다
- [ ] **이 표본 크기에서 그 차이를 구분할 수 있는가?**
      사전 등록했다는 형식이 기준의 타당성을 보장하지 않는다. n=16 에서
      `2 → 1` 은 95% 구간이 거의 포개진다 — 구간을 같이 찍는다 (사례 22)
- [ ] **비교 대상이 실제로 서로 다른가?**
      파생으로 만든 조건은 `str.replace` 가 조용히 원본을 돌려주는 순간
      대조군과 같아진다. "차이 없음"과 "안 쟀음"이 똑같이 보인다 (사례 23)
- [ ] 종료 코드를 보는데 **파이프를 붙이지 않았는가?**
      `cmd | tail` 뒤의 `$?` 는 `tail` 의 것이라 언제나 0 이다. 출력을 읽기 좋게
      만들려고 끼운 필터가 판정을 바꾼다 (사례 26, 사례 21 의 `head -1`과 같은 과)
- [ ] 재현 조건을 **고정하는 값**(시드 등)이 있는데 반복만으로 변동을 재고
      있지 않은가? 시드가 고정돼 있으면 "변동 0"은 측정이 아니라 **구조**다.
      같은 시드 반복을 대조군으로 두고, 산출물 해시를 같이 찍는다 (ADR-0043)
