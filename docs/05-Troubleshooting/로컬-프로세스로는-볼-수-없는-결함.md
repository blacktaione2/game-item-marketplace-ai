# 로컬 프로세스로는 볼 수 없는 결함 두 건

> ADR-0030(알림 큐)을 로컬 프로세스로 완성하고 판정선 8개를 전부 통과시킨 뒤,
> **같은 코드를 컨테이너로 띄우자 백엔드가 unhealthy 로 죽었다.** 원인은 둘이고,
> **둘 다 로컬 실행에서는 원리적으로 관측할 수 없다.**
>
> 문서를 하나로 묶은 이유: 두 결함의 재발 조건은 다르지만 **발견 방법이 같다** —
> 로컬 개발 루프가 볼 수 없는 지점이라는 것. 사례 1은 단독으로는 너무 얕고(환경변수
> 하나), 사례 2는 그 자체로 값어치가 있어 별도 절과 CLAUDE.md 규칙으로 뺐다.

## 사례 1: 컨테이너 안에서 `localhost` 는 자기 자신이다

### 문제

컨테이너 백엔드가 기동은 하는데 `/actuator/health` 가 **503**, 컨테이너는
`unhealthy`. `depends_on: backend: service_healthy` 가 걸린 `web` 이 아예 안 떴다.

```
AbstractConnectionFactory.connectAddresses ... localhost:5672
```

### 발생 원인

`application.yml` 에 기본값을 `localhost` 로 두고 환경변수로 덮게 설계했는데,
**compose 의 backend 서비스에 `RABBITMQ_HOST` 를 넣는 것을 빠뜨렸다.**

```yaml
# application.yml — 설계 자체는 맞다
spring.rabbitmq.host: ${RABBITMQ_HOST:localhost}

# docker-compose.yml — 여기가 비어 있었다
backend:
  environment:
    DB_HOST: postgres      # 있음
    REDIS_HOST: redis      # 있음
    # RABBITMQ_HOST 없음   ← 컨테이너 안에서 localhost = 자기 자신
```

**로컬 프로세스에서는 `localhost` 가 맞는 값이다.** 그래서 개발 내내, 판정선
8개를 통과시키는 동안에도 정상으로 보였다. 값이 틀린 게 아니라 **환경마다
정답이 다른 값**이었다.

`DB_HOST`·`REDIS_HOST` 는 ADR-0029(컨테이너화) 때 같이 넣었는데, RabbitMQ 는
그 다음 라운드(ADR-0030)에서 생긴 의존성이라 **컨테이너 설정만 뒤처졌다.**

### 해결

```yaml
RABBITMQ_HOST: rabbitmq
RABBITMQ_USER: ${RABBITMQ_USER:-gimp}
RABBITMQ_PASSWORD: ${RABBITMQ_PASSWORD:-gimp_local_pw}
```

`depends_on: rabbitmq: service_healthy` 도 같이 걸었다 — **기동 순서일 뿐 보호막은
아니다**(브로커가 나중에 죽어도 거래는 계속돼야 한다).

## 사례 2: 코드는 fail-open 인데 헬스체크가 fail-closed 였다

**이쪽이 훨씬 중요하다.**

### 문제

ADR-0030 은 *"브로커가 죽어도 구매는 성공한다"* 를 설계 결정으로 삼고 판정선까지
걸어 확인했다 — 브로커를 실제로 정지시키고 구매 201, 지연 증가 7ms.

그런데 컨테이너에서는 브로커가 안 붙자 **인스턴스 전체가 unhealthy** 가 됐다.

```
브로커 다운
  → 스프링이 자동 등록한 rabbit 헬스 인디케이터 DOWN
  → /actuator/health 503
  → 컨테이너 unhealthy
  → depends_on 걸린 web 이 안 뜬다 / 로드밸런서라면 인스턴스를 뺀다
```

즉 **알림 하나 때문에 거래·검색까지 멈춘다.** 코드에서 그토록 조심스럽게 지킨
fail-open 이, 한 계층 위에서 정반대로 뒤집혔다.

### 발생 원인

Spring Boot 는 `spring-boot-starter-amqp` 가 들어오면 **rabbit 헬스 인디케이터를
자동 등록**한다. 그리고 `/actuator/health` 는 등록된 인디케이터를 **AND 로 집계**한다 —
하나라도 DOWN 이면 전체가 DOWN 이다.

그 기본 동작은 "이 의존성이 없으면 서비스가 성립하지 않는다"를 전제한다.
DB 라면 맞다. **알림 브로커에는 틀리다.**

**로컬 프로세스 실행에는 헬스체크라는 개념이 아예 없다.** 그래서 판정 5를 로컬로
확인했을 때 이 계층이 존재하지도 않았다 — 판정선이 맞았는데 **측정 환경이 배포
환경과 달랐다.**

### 해결

```yaml
management:
  health:
    rabbit:
      enabled: false
```

**끄는 것이 정보를 버리는 게 아니다.** 발행 실패는
`trade_event_published_total{outcome="failed"}` 로, 적체는 DLQ 깊이로 본다 —
그건 **건강 여부가 아니라 관측 대상**이다. 헬스체크는 "이 인스턴스가 요청을
처리할 수 있는가"를 답해야 하고, 브로커 없이도 답은 **예**다.

## 배운 점

### 실패 정책은 계층마다 따로 정해지고, 어긋나면 낮은 쪽이 진다

이 저장소는 실패 정책을 의식적으로 갈라 왔다.

| 대상 | 정책 | 이유 |
|---|---|---|
| 구매 락 (Redis) | **fail-closed** | 정확성 — 오버셀이 나면 안 된다 |
| AI 요청 한도 (Redis) | **fail-open** | 비용 방어일 뿐, 막혔다고 서비스가 멈추면 안 된다 |
| 알림 발행 (RabbitMQ) | **fail-open** | 부가 기능 |

그런데 **헬스체크는 그 표에 없었다.** 프레임워크가 자동으로 정해버렸고, 그 기본값이
"모든 의존성은 필수"였다. 코드에서 세 줄 주석까지 달아가며 지킨 정책이 설정 한 줄에
뒤집힌 셈이다.

> **의존성을 하나 추가하면 그 의존성의 실패 정책을 세 곳에서 정해야 한다** —
> 호출 지점(예외를 삼킬 것인가), 기동 순서(`depends_on`), **헬스체크**.
> 마지막 것을 잊으면 앞의 둘이 무의미해진다.

### 로컬 개발 루프가 볼 수 없는 것의 목록

이번 두 건은 우연이 아니다. 로컬 프로세스 실행에는 **없는 계층**이 있다.

| 계층 | 로컬에 있나 | 그래서 못 보는 것 |
|---|---|---|
| 컨테이너 네트워크 | 없음 | `localhost` 가 다른 것을 가리킨다 (사례 1) |
| 헬스체크 | 없음 | 준비 상태 판정이 코드 정책과 어긋난다 (사례 2) |
| 리버스 프록시 | 없음(dev proxy 는 다름) | 클라이언트 IP 가 프록시로 합쳐진다 (ADR-0029) |
| 이미지 빌드 | 없음 | 선언되지 않은 의존성 (ADR-0021·0029) |
| 컨테이너 DNS | 없음 | **연결 실패의 방식이 다르다** (아래) |

### 덤 — 같은 실패도 환경에 따라 다르게 실패한다

수정 후 브로커를 정지시켜 다시 쟀더니 구매 지연이 **2.03초**였다. 로컬에서는
**7ms** 였던 그 측정이다.

| 환경 | 지연 | 이유 |
|---|---:|---|
| 로컬 프로세스 | 7 ms | 포트 **거부**(ECONNREFUSED) — 즉시 실패 |
| 컨테이너 | 2,032 ms | 컴포즈 네트워크에 호스트명이 남아 **연결 타임아웃까지 대기** |

ADR-0030 은 *"2초는 최악 상한, 7ms 는 흔한 경우"* 라고 적었는데 **배포 형태에서는
뒤집힌다.** 판정선은 상한에서 도출했으므로 여전히 성립하지만, **상한을 실제로
쓰게 된다**는 사실이 달라진다.

→ **"실패했을 때 얼마나 걸리는가"는 실패하는 방식에 달렸고, 그 방식이 환경마다
다르다.** 타임아웃 값을 근거로 판정선을 세웠다면 그 타임아웃이 실제로 소진되는
환경에서 한 번 재봐야 한다.

→ **기능이 완성됐다고 판정선을 닫지 말고, 컨테이너로 한 번 띄운 뒤에 닫는다.**
ADR-0029 가 `load/verify-container.sh` 를 남긴 이유가 이것이고, 이번엔 그걸
돌리기 전에 판정선을 닫아서 놓쳤다.

### 목록이 또 늘었다 (2026-08-03, ADR-0031)

공개 준비 라운드에서 **같은 부류가 세 건 더** 나왔다. 전부 로컬 프로세스로는 안 보인다.

| 결함 | 로컬에선 왜 안 보이나 |
|---|---|
| compose 에 `DEMO_PASSWORD`·`DB_PASSWORD` 선언 누락 | 로컬은 셸 환경이나 기본값이 그대로 먹는다. **compose 의 `environment` 는 자동 상속이 아니다** |
| `ports: []` 가 포트를 안 지운다 | 로컬에는 오버레이 자체가 없다. Compose 는 시퀀스를 **이어 붙인다** — `!override` 가 필요하다 |
| nginx 가 옛 컨테이너 IP 를 캐시 | 로컬에는 nginx 가 없다. `proxy_pass` 에 호스트명을 literal 로 쓰면 **기동 시 한 번** DNS 를 푼다 |

그리고 **순서 문제**가 하나 더 있었다 — `DemoAccountInitializer` 가 백엔드 기동 시
비밀번호를 넣는데, `db-seed` 는 백엔드가 healthy 가 된 **뒤에** 실행되어 자리표시자
해시로 덮어쓴다. 이건 컨테이너 구성에서만 생기는 순서다(로컬에서는 사람이 시드를
먼저 넣고 앱을 켠다).

> 셋 다 **기동 후 `restart backend web`** 으로 해결되고, 그 단계를 잊으면
> `verify-deploy.sh` 의 로그인 검사가 401 또는 502 로 지목한다.

### 재발 조건 체크리스트

- [ ] 새 인프라 의존성을 추가할 때 **컨테이너 호스트명 환경변수**를 같이 넣었는가?
      로컬에서 `localhost` 가 맞는 값이면 그 결함은 로컬에서 안 보인다
- [ ] 그 의존성의 **실패 정책을 세 곳 모두** 정했는가? (호출 지점 / `depends_on` /
      **헬스체크**)
- [ ] 프레임워크가 **자동 등록한 헬스 인디케이터**가 있는가? 그게 내 실패 정책과
      같은 방향인가?
- [ ] 판정선을 **배포 형태와 같은 환경**에서 확인했는가? 로컬 프로세스에만 있는
      조건 위의 통과는 배포에서 재현되지 않을 수 있다
- [ ] compose 의 `environment` 에 **새 설정값을 선언**했는가?
      셸에서 넘겨도 선언이 없으면 컨테이너에 안 들어간다 (세 번 겪었다)
- [ ] 오버레이로 **리스트 값을 지우려면** `!override` 를 썼는가?
      `[]` 는 병합되어 아무것도 안 지운다
- [ ] 컨테이너를 재생성한 뒤 **nginx 를 재시작**했는가?
      `proxy_pass` 의 호스트명은 기동 시점에 한 번만 해석된다
