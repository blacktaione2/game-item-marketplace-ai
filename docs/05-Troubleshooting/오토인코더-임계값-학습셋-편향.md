# 오토인코더 임계값을 학습셋 재구성 오차로 잡으면 낙관적으로 편향된다

## 문제

Phase 5-2 이상거래 탐지에서 알림 임계값을 **학습셋 재구성 오차의 99
백분위수**로 잡았다. 의도는 "정상 트래픽의 1%만 검토 큐에 올린다"였다.

그런데 학습에 쓰지 않은 정상 데이터에 그 임계값을 적용해보니 알림률이
의도한 값과 어긋났다.

```
임계값 산정 (p99.0)
  학습셋 기준     7.9779
  홀드아웃 기준   8.4069
  학습셋 임계값을 홀드아웃에 적용하면 정상의 1.32%가 알림 (의도한 1.00%)
```

**의도한 1.00% 대비 1.32배.** 운영에 그대로 올렸다면 GM 검토 큐에 예상보다
32% 많은 알림이 쌓였을 것이고, 원인을 모른 채 임계값을 감으로 올리는 대응을
했을 것이다.

## 발생 원인

오토인코더는 **자기가 학습한 데이터를 가장 잘 재구성한다.** 학습이란 곧
학습셋의 재구성 오차를 최소화하는 과정이므로, 학습셋의 오차 분포는 구조적으로
가장 낙관적인 분포다.

운영에서 마주치는 정상 거래는 학습셋에 없던 조합이라 재구성 오차가 전반적으로
더 높게 나온다. 같은 백분위수라도 홀드아웃 쪽 절대값이 크다(7.98 → 8.41).
낮은 쪽 값을 임계값으로 쓰면 정상 거래가 그 선을 더 자주 넘는다.

이 편향은 모델이 과적합이든 아니든 **항상 같은 방향으로** 생긴다. 정도만
다를 뿐 방향이 뒤집히지 않는다는 점이 중요하다.

## 해결 방법

정상 데이터를 **셋으로 나눈다.**

| 분할 | 용도 |
|---|---|
| `train` | 모델 학습에만 |
| `threshold` | 학습에 안 씀. **임계값은 여기서 잡는다** |
| `eval` | 위 둘과 별개. 정상 + 주입 이상치로 성능 측정 |

분할은 시간순이다 — 24시간·7일 롤링 피처가 있어 무작위 분할은 그 자체로 누수다.
구현은 `ai/app/services/anomaly/dataset.py`의 `build_splits()`.

그리고 학습 스크립트가 **두 임계값을 매번 같이 출력**하게 했다. 편향이 얼마나
되는지 눈에 보이지 않으면 다음 사람이 같은 실수를 반복한다.

```
학습셋 기준     7.9779  <- 쓰면 안 되는 값
홀드아웃 기준   8.4069  <- 채택
```

## 배운 점

**모델이 학습에 사용한 데이터로는 그 모델의 운영 기준선을 정할 수 없다.**
Phase 5-1에서 시세 예측에 시간순 홀드아웃을 둔 것과 정확히 같은 이유이고,
Phase 4에서 임베딩 평가에 홀드아웃 코퍼스를 쓴 것과도 같은 원칙이다.
이 프로젝트에서 세 번째로 같은 원칙을 적용한 사례다.

특히 놓치기 쉬운 이유가 있다. 홀드아웃은 보통 **성능 측정**을 위한 장치로
인식되는데, 여기서 홀드아웃이 필요한 이유는 성능 측정이 아니라 **임계값이라는
운영 파라미터의 보정**이다. "평가는 홀드아웃에서 했으니 됐다"고 생각하면
임계값이 학습셋에서 나온 것을 그냥 지나치게 된다. 분할을 둘이 아니라 셋으로
나눠야 하는 이유가 여기에 있다.

### 재발 조건과 체크리스트

모델을 재학습하거나 다른 이상탐지 모델을 추가할 때 같은 실수를 반복하기 쉽다.
**임계값·컷오프 성격의 값을 정할 때마다** 아래를 확인한다.

- [ ] 이 값을 산출한 데이터가 모델 학습에 쓰였는가? 쓰였다면 잘못된 것이다.
- [ ] 백분위수로 정한 값이라면, 학습에 안 쓴 정상 데이터에서 실제 발동률을
      재봤는가? 의도한 값과 일치하는가?
- [ ] 성능 측정용 평가셋과 임계값 산정용 데이터가 분리돼 있는가? 같은 데이터로
      둘 다 하면 평가가 임계값에 유리하게 기울어진다.
- [ ] 시계열/행동 롤링 피처가 있다면 분할이 시간순인가?

이 원칙은 이상탐지에 국한되지 않는다. 분류 임계값, 신뢰도 컷오프, 캐시 히트
판정 유사도 임계값(Phase 6 Semantic Cache) 등 **운영 파라미터 전반**에 적용된다.
