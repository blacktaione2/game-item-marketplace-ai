# 2026-07-29

## Phase 4: 임베딩 파인튜닝 — Hard Negative 자동 생성

### 설계 판단: 규칙 + LLM 하이브리드

계획서(`CLAUDE.md`)에는 "hard negative 페어를 LLM으로 자동 생성"이라고 적혀 있지만,
실제 데이터를 보고 역할을 나눴다.

먼저 데이터를 확인해보니 `enhancement_level` 필드로 결정론적으로 뽑을 수 있는 쌍이
있었다 — `+7/+8/+9 강화 롱소드`. **이건 LLM에 맡길 이유가 없다.** 공짜이고,
재현 가능하고, 100% 정확하다.

반대로 LLM이 아니면 못 만드는 것도 명확했다:
- 사용자가 실제로 칠 법한 검색어(anchor). 아이템명을 그대로 치는 사용자는 없다
- `"얼음 서리 지팡이"` vs `"불꽃 서리 지팡이"`처럼 **속성/직업/티어만 뒤바뀐**
  의미적 near-miss. 구조화 필드에 속성 정보가 없으므로 규칙으로는 못 만든다

그래서:

| 담당 | 생성물 | negative 유형 |
|---|---|---|
| 규칙 | 강화 수치만 다른 형제 아이템 | `structural` |
| 규칙 | 같은 카테고리 내 텍스트 최대 중첩 아이템 | `corpus` |
| LLM | anchor 질의 + 의미적 near-miss | `synthetic` |
| 규칙 | 다른 카테고리 무작위 (대조군) | `easy` |

Hard negative는 **가능하면 코퍼스에 실재하는 아이템**을 쓴다. 모델이 실제 카탈로그
안에서 헷갈리는 쌍을 구분하도록 학습시키는 게 목적이라서다. 구조적 형제가 없는
아이템만 LLM 합성으로 채운다.

데이터 현황상 강화 형제를 가진 아이템은 24건 중 3건(롱소드 3종)뿐이라, LLM 없이는
커버리지가 안 나온다는 것도 확인됐다 — 계획서의 LLM 활용 방침이 맞았다.

### 결과물

`ai/data/train_triplets.jsonl` — sentence-transformers가 바로 먹는 JSONL
(anchor / positive / negative). LLM 호출 24회(아이템당 1회, 질의와 negative를
한 번에 받음).

- 트리플 **162건**, 고유 anchor **72개**, 아이템 커버리지 **24/24**
- 생성된 anchor 예시: `"8강 활"`, `"사거리가 긴 궁수 무기"`, `"130레벨 방어구 있나요"`,
  `"55레벨 이상 불 속성 지팡이"`, `"초보자 방어구"` — 아이템명 복붙이 아닌
  실제 사용자 말투가 나왔다
- 가장 어려운 쌍 예시: `"얼음 서리 지팡이"` vs `"불꽃 서리 지팡이"`(속성 교체),
  `"불꽃의 마법봉"` vs `"불꽃의 마법검"`(무기 종류 교체),
  `"+9 강화 롱소드"` vs `"+6 강화 롱소드"`(강화 수치 교체)

### 검수 장치 — false negative 방지

LLM에게 "아주 조금만 다르게 만들라"고 시키면 **자기 자신을 negative로 뱉는 사고**가
날 수 있다. 그대로 학습에 넣으면 정답을 오답으로 가르치는 셈이라 치명적이다.
`sanitize_synthetic()`으로 두 가지를 처리한다:

1. 합성 negative가 positive 아이템 이름과 같으면 **폐기** (공백 정규화 후 비교)
2. 합성 negative가 실재 코퍼스 아이템과 이름이 같으면 **폐기하지 않고 `corpus`로 승격** —
   전체 텍스트와 `item_id`를 붙여 근거 있는 negative로 만든다

단위 테스트로 확인: 자기 자신 2건(공백 변형 포함) 폐기, 실재 아이템 1건 승격,
진짜 합성 2건 유지. 실제 전체 실행에서도 승격 1건이 잡혔다.

### 품질 지표 — 척도를 두 개 낸 이유

"hard negative가 정말 어려운가"를 표면 유사도(문자 bigram Jaccard)로 검증하는데,
**처음엔 척도 하나만 썼다가 잘못된 결론이 나올 뻔했다.**

처음 측정에서 `synthetic`이 0.1248로 `structural`(0.2651)보다 낮게 나왔다. 원인은
positive는 "이름 + 설명"인데 synthetic negative는 **이름만** 있어서, 길이 차 때문에
Jaccard가 부당하게 낮게 나온 것이었다. 반대로 이름끼리만 비교하니 이번엔 `corpus`가
불리해졌다 — corpus negative는 설명문 어휘가 겹쳐서 어려운 것이지 이름이 비슷한 게
아니기 때문이다.

그래서 **두 척도를 모두 리포트**하고, 유형별로 공정한 쪽을 기준으로 판정한다.

| negative 유형 | 건수 | 이름 유사도 | 전체 유사도 | 판정 기준 | vs easy |
|---|---|---|---|---|---|
| `structural` | 6 | 0.5000 | 0.2651 | 전체 | 7.0배 |
| `synthetic` | 72 | 0.3211 | 0.1273 | 이름 | 17.2배 |
| `corpus` | 60 | 0.0656 | 0.1321 | 전체 | 3.5배 |
| `easy` (대조군) | 24 | 0.0187 | 0.0380 | — | — |

전 유형이 자기에게 공정한 척도에서 easy를 유의미하게 상회 → hard negative가 실제로
"어렵다"는 게 수치로 확인됨. 스크립트가 이 판정을 자동으로 출력하고, 뒤집히면 경고한다.

### 사용법

```bash
python -m scripts.generate_hard_negatives              # 전체 24건, LLM 사용
python -m scripts.generate_hard_negatives --dry-run    # 규칙만, LLM 호출 없음(로직 점검용)
python -m scripts.generate_hard_negatives --limit 3    # 앞 3건만(프롬프트 비용 확인용)
```

`--dry-run`을 먼저 돌려 규칙 기반 마이닝을 검증한 뒤 LLM을 태우는 순서를 권장.
실제로 이번에도 `--dry-run` → `--limit 3` → 전체 순으로 진행해서 프롬프트 문제를
싸게 걸러냈다.

## Phase 4: train/eval 분리 → 파인튜닝 → RAGAS 비교

### 코퍼스 분리 (평가 오염 방지)

아이템 정의를 `scripts/seed_items.py`에서 `app/corpus/`로 옮기고 둘로 쪼갰다.

- `train_items.py` 24건 — 트리플 생성 + 파인튜닝 전용
- `eval_items.py` 18건 — **평가 전용, 학습에 일절 안 씀** (신규 작성, item_id 101~)
- `__init__.py`가 임포트 시점에 item_id/이름 중복을 검사해 겹치면 즉시 `ValueError`

가드가 실제로 동작하는지도 확인했다(이름 충돌·id 충돌 각각 주입해서 예외 발생 검증).
안 터지는 가드는 없느니만 못하다.

홀드아웃 보호를 **양방향**으로 걸었다: 합성 negative가 평가 아이템 이름과 겹치면
폐기한다. 평가 아이템 이름이 학습에 negative로 들어가면 모델이 그 이름을 오답으로
밀어내도록 학습해서 평가가 부당하게 **불리해지기** 때문이다. 부풀려지는 방향만
막으면 된다고 생각하기 쉬운데 아니다.

검색 코퍼스는 train + eval 42건 전체로 두고, 정답만 eval 아이템으로 잡았다.
학습에 쓴 아이템이 방해 문서로 섞여 있어야 현실적인 난이도가 된다.

### 파인튜닝

`MultipleNegativesRankingLoss`, 트리플 138건(easy negative 24건은 제외 — MNRL은
배치 내 다른 positive를 자동으로 negative로 쓰므로 명시적 슬롯에는 hard한 것만
넣는 게 신호가 강하다), 2 epoch, batch 16. loss 3.46 → 2.60, 학습 69초(CPU).

### 결과 — 첫 정량 증명

평가 질의 54건(홀드아웃 18아이템 × 3), **처음 보는 아이템 기준**:

| IR 지표 | 전 | 후 | 변화 |
|---|---|---|---|
| recall@1 | 0.1481 | 0.3889 | **+0.2408** |
| recall@3 | 0.3148 | 0.5370 | +0.2222 |
| recall@5 | 0.4444 | 0.6111 | +0.1667 |
| recall@10 | 0.6111 | 0.7778 | +0.1667 |
| MRR | 0.3005 | 0.5099 | **+0.2094** |
| mean_rank | 10.72 | 7.24 | -3.48 |

| RAGAS 지표 | 전 | 후 | 변화 |
|---|---|---|---|
| context_precision | 0.2935 | 0.5133 | **+0.2198** |
| context_recall | 0.4630 | 0.6111 | +0.1481 |

**결정론적 IR 지표와 LLM 심판 RAGAS가 같은 방향·비슷한 크기로 움직였다.**
서로 독립적인 두 측정이 일치했다는 게 단일 지표보다 훨씬 강한 근거다.
RAGAS만 돌렸으면 "LLM 심판이 흔들린 거 아니냐"는 반박에 답할 수 없었다.

### 자기검증 — 붕괴한 모델이 아닌가

MNRL은 임베딩 공간을 압축시키는 경향이 있어서, 극단적으로는 모든 벡터가 한 점에
모여도 랭킹 지표가 우연히 좋아 보일 수 있다. 그래서 코퍼스 임베딩 분포를 확인했다.

- 평균 쌍별 유사도 0.3901 → 0.5129 (압축은 실제로 일어남)
- 표준편차 0.1651 → 0.1581 (거의 유지)
- 최대 비대각 유사도 0.9541 (1.0 아님)

→ 압축은 있었지만 **붕괴는 아니고**, 아이템들이 여전히 구별된다. 개선은 진짜다.

### 교차 검증 — 질의 스타일 오염이었나

위 결과의 가장 큰 약점은 "학습 anchor와 평가 질의를 둘 다 LLM이 비슷한 프롬프트로
만들었으니 스타일 적응 아니냐"였다. 그래서 **LLM이 절대 만들지 않는 형식**으로
질의 15건을 손으로 써서 같은 홀드아웃 코퍼스에 돌렸다
(키워드 나열 / 오타 / 초성 / 붙여쓰기).

| 질의셋 | n | MRR 전 | MRR 후 | 변화 |
|---|---|---|---|---|
| LLM 생성 | 54 | 0.3005 | 0.5099 | +0.2094 |
| 수동 작성 | 15 | 0.4965 | 0.6427 | **+0.1462** |

**두 셋 모두 개선, 수동셋이 LLM셋의 약 70% 수준.** 스타일 적응만으로는 설명되지
않는다는 뜻이다. 다만 LLM셋 개선폭이 더 큰 건 스타일 적응분이 실제로 존재함을
시사한다.

스타일별:

| 스타일 | n | MRR 전 | MRR 후 | 변화 |
|---|---|---|---|---|
| typo | 4 | 0.2923 | 0.7656 | **+0.4733** |
| keyword | 5 | 0.3991 | 0.4833 | +0.0842 |
| nospace | 4 | 1.0000 | 1.0000 | 0.0000 |
| chosung | 2 | 0.1417 | 0.0810 | -0.0607 |

- **오타 질의가 가장 크게 좋아졌다** — 이게 핵심 증거다. 오타는 어휘 일치를
  깨뜨리므로 표면 매칭으로 풀 수 없다. `용의 숨결 지팡히` 12위→1위,
  `마도사 후두` 17위→1위, `수호자 팔지` 37위→16위. 의미로 찾고 있다는 뜻
- **붙여쓰기는 전/후 모두 1위** — 서브워드 토크나이저가 원래 잘 하는 영역이라
  천장 효과. 개선 여지가 없었을 뿐 나빠진 건 아니다
- **초성은 나빠졌다** — 아래 한계 참고

해석 주의: 두 셋은 스타일 말고 "아이템명과의 어휘 중첩"도 다르다(수동 키워드형은
이름 조각을 포함, LLM 질의는 이름 복사 금지). 그래서 **셋 간 절대 수치 비교는
무의미**하고 각 셋 내부의 전/후 변화량만 비교해야 한다.

### 한계 (수치와 같이 밝혀야 하는 것들)

- **초성 검색은 dense 임베딩으로 원리적으로 안 된다.** `ㅍㅇㅊ` 5위→8위,
  `ㄱㅊ ㄱㅂ` 12위→27위. 다만 n=2이고 42건 중 무작위 기대 순위가 ~21위라
  **전/후 모두 사실상 노이즈**다. 파인튜닝 전 5위는 실력이 아니라 우연이다.
  결론은 "파인튜닝이 초성을 망쳤다"가 아니라 **"초성은 이 구조로 못 푸니 자모
  분해 색인 같은 별도 메커니즘이 필요하다"**. 한국어 서비스에서 흔한 입력이라
  로드맵에 남김
- **질의 스타일 적응이 일부 섞여 있다.** 위 교차 검증으로 "그것만은 아니다"까지는
  확인했지만 완전히 배제되진 않았다. 실사용자 질의 로그가 생기면 다시 재야 한다
- **평가셋이 작다.** 54건이라 recall@1의 0.148→0.389는 8건→21건. 방향은 분명하지만
  소수점까지 믿을 크기는 아니다
- **단일 실행.** 시드 여러 개로 분산을 재지 않았다
- **dense 전용 수치다.** 파인튜닝이 바꾸는 게 임베딩뿐이라 의도적으로 임베딩
  코사인 랭킹만 쟀다. 전체 하이브리드 파이프라인(BM25/리랭커는 그대로)의 개선폭은
  이보다 작을 것이다

방법론 전반은 ADR-0007에 정리.

## 파인튜닝 모델을 실제 파이프라인에 반영

Phase 5로 넘어가기 전에 파인튜닝 결과를 서빙에 붙였다.

- `settings.embedding_model` → `models/embedding-finetuned` (베이스와 동일한
  384차원이라 인덱스 매핑은 그대로. 교체 전에 차원부터 확인했다 — 안 맞으면
  재색인이 조용히 깨진다)
- 전체 42건 재색인 (`--recreate`). 저장된 벡터는 모델에 종속적이라 모델을 바꾸면
  반드시 재색인해야 한다
- 검색 API 스모크 체크 4건 통과:
  - `"불속성 검"` → 불꽃의 대검 1위(rerank 1.99, 유일한 양수), 불꽃의 마법봉 2위
  - `"100렙 이상 활"` → 바람의 장궁 1위(`level_min=100` 필터 정상)
  - `"3만원 이하 강화된 갑옷"` → 전부 방어구 3만원 이하
  - `"마법사가 쓸 만한 지팡이"` → 상위 4건이 전부 마법사용(얼음 서리 지팡이,
    용의 숨결 지팡이, 불꽃의 마법봉, 수정 마법구)
- 웜 레이턴시는 이전과 동일 수준(embed 29~43ms, retrieve 41~78ms). 첫 호출만
  지연 로딩으로 느리다

**해석 주의**: 이 스모크 체크는 "정상 동작 확인"이지 A/B 비교가 아니다. Phase 3
관찰 시점과 비교하면 코퍼스도 24건 → 42건으로 늘어서 두 변수가 같이 바뀌었다.
개선의 근거는 어디까지나 위의 홀드아웃 평가 수치다.

**주의사항 하나**: `models/`는 gitignore 대상이라 새로 clone한 환경에는 파인튜닝
모델이 없고, 그 상태로 AI 서버를 띄우면 임베딩 시점에 실패한다. 재생성 절차를
`CLAUDE.md` Gotchas에 적어뒀다.

부수적으로, 이번에 Docker Desktop이 내려가 있어서 컨테이너부터 다시 올렸다.
ES 볼륨은 유지되고 있었다.

## Phase 5 (1) 시세 예측 + Cold Start 백오프

- `ai/app/services/forecast/` 신설 — dataset(윈도우/비율 정규화), model
  (`PriceLSTM`), predictor(지연 로딩), cold_start(ES 도너 검색 + 가중 트렌드
  상속), evaluation(MAPE·나이브 기준선·신호 상관), pipeline(분기)
- `POST /api/forecast`, `python -m scripts.train_forecast` 추가
- 새 의존성 없음 — torch/numpy는 sentence-transformers가 이미 끌고 와 있었다
- 더미 거래 이력 `app/corpus/trade_history.py` — 시드 고정 생성기로 이력 보유
  19건 × 120일(하락/상승/횡보/이벤트 급등) + Cold Start 4건(관측 0·2·3·5건).
  노이즈는 AR(1) 평균회귀 — iid는 비현실적이고 순수 랜덤워크는 120일이면 발산

### 설계 핵심

가격을 윈도우 마지막 값 기준 **비율**로 정규화했다. 3천원 물약과 85만원 계정을
전역 모델 하나로 다룰 수 있게 되고, 동시에 이게 Cold Start 상속의 근거가 된다 —
물려받는 건 절대 가격이 아니라 "며칠 새 몇 배가 되는가"의 모양이고, 수준(앵커)은
아이템 자신의 것을 쓴다. 상세는 ADR-0008.

### 결과

검증셋(아이템별 **시간순** 분할, 380 윈도우 — 무작위 분할은 미래 누수):

| 방식 | MAPE |
|---|---|
| LSTM | **4.70%** |
| 나이브(직전값 유지) | 4.87% |
| 나이브(선형 외삽) | 7.18% |

Cold Start 도너 선택:

| 대상 | 상속받은 아이템 |
|---|---|
| +9 강화 은빛 사슬갑 | +9 강화 미스릴 갑옷(.34) / +9 강화 사슬 갑옷(.33) / 암흑 로브(.33) |
| 그림자 암살검 | 전설 등급 대검 / +8 강화 롱소드 / 불꽃의 대검 |
| 레벨 150 궁수 계정 | 만렙 전사 계정 (계정 카테고리 유일 도너, weight 1.0) |

에러 경로 4건 확인: 없는 아이템 404, 없는 테넌트 404, horizon 초과 400,
미학습 모델 503(재생성 명령 포함).

### 해석 — 개선폭이 작은 것과 평균회귀는 같은 원인이다

두 가지를 발견했고, 별개 현상이 아니다.

1. 나이브 대비 개선폭이 3.4%로 작다. "모델이 그냥 1.0을 뱉는 것 아닌가"를
   따로 검사했더니 예측 편차와 실제 편차의 상관이 **0.304**(예측 std 0.011,
   실제 0.064)였다. 붕괴가 아니라, 저신호 구간에서 MSE 최적해가 평균 쪽으로
   수축하는 정상 동작이다.
2. 모델이 학습한 것은 장기 추세 외삽이 아니라 **평균회귀**다. 상승 아이템인
   용비늘 방패가 −1.3%를, 하락 아이템인 +9 강화 롱소드가 +1.37%를 예측한다.
   최근 14일이 마지막 값보다 낮으면 반등, 높으면 조정을 예측한다.

**두 관찰은 하나의 원인에서 나온다.** 더미 데이터의 추세는 0.3%/일인데 AR(1)
노이즈는 std 3.5%다. 14일 창 안에서 추세 성분은 노이즈에 완전히 묻히고, 남는
학습 가능한 구조는 평균회귀뿐이다. 즉 모델은 데이터 생성 과정에 실제로 존재하는
신호를 정확히 찾아냈고, 개선폭이 작은 것은 **모델의 성능 부족이 아니라 이 데이터에
예측 가능한 정보량 자체가 원래 적기 때문**이다. 신호의 상한이 낮으면 어떤 모델을
써도 나이브를 크게 이길 수 없다.

따라서 (a) 모델 용량을 키우는 방향의 튜닝은 여기서 얻을 게 없고, (b) "추세를
예측한다"고 설명하면 틀린 설명이 된다. 개선은 실거래 데이터가 쌓여 신호 상한이
올라간 뒤에 판단할 문제다.

기타 한계: 합성 데이터라 MAPE 단독으로는 아무것도 증명하지 않아 기준선 비교를
학습 스크립트 상시 출력에 고정했다. 이벤트 급등 구간은 시간순 분할상 학습
구간에 들어가 **스파이크 예측력은 아직 측정되지 않았다.** 정규화 앵커가 단일
지점이라는 점, 메인 모델에 카테고리 등 조건부 피처가 없다는 점은 ADR-0008의
"알려진 한계"에 정리했다.

무관한 기존 이슈: 임베딩 인코딩이 async 함수 안 동기 호출이라 이벤트 루프를
막는다(Phase 3 `search/pipeline.py`부터 있던 패턴이라 그대로 맞췄다).

## Phase 5 (2) Autoencoder 이상거래 탐지

- `ai/app/services/anomaly/` 신설 — features(맥락 대비 11축 + RobustScaler),
  dataset(정상 3분할), scenarios(행동 기반 이상치 주입), model
  (`TradeAutoencoder` 11-8-4-8-11), detector(점수 + 피처 기여도),
  evaluation(PR-AUC + 규칙 기준선), pipeline
- `POST /api/anomaly/detect`, `GET /api/anomaly/alerts`,
  `python -m scripts.train_anomaly` 추가
- `app/corpus/trades.py` — 일별 집계를 개별 체결 26,489건으로 풀고, 유저
  150명 풀에 **의도적 단골 구조**(인당 단골 3명, 정상 거래의 35%)를 넣었다.
  정상에 반복 거래가 없으면 `pair_trades_7d` 하나로 이상치가 분리돼 상호작용
  검증이 무의미해진다

### 설계 핵심 — 순환논증 회피

이상치를 피처 값으로 심지 않고 **행동으로** 주입했다. 작업장이면
`seller_trades_24h = 50`을 세팅하는 게 아니라 같은 판매자의 거래 50건을
24시간 안에 실제로 만들고, 피처는 그걸 보고 파생시킨다. 규칙으로 만든 걸
규칙으로 되찾으면 아무것도 증명하지 못한다. 상세는 ADR-0009.

### 결과

정상 3분할: 학습 18,673 / 임계값 홀드아웃 3,874 / 평가 4,155.
평가셋 이상거래 137건(기저율 3.30%).

| 방법 | PR-AUC | 정밀도(R-precision) |
|---|---|---|
| 오토인코더 | 0.679 | 0.591 |
| 규칙: 전 피처 max \|z\| | 0.669 | 0.599 |
| 규칙: 가격 \|z\| | 0.335 | 0.292 |

| 유형 | 오토인코더 | 가격 \|z\| | max \|z\| |
|---|---|---|---|
| 자전거래 | 100% | 100% | 100% |
| 계정 도용 투매 | 100% | 100% | 100% |
| 작업장 대량 유통 | **81%** | 0% | 40% |
| 대포 계정 고액거래 | 12% | 0% | **100%** |
| 복합 미세 이상 | **13%** | 0% | 0% |

### 해석 — 오토인코더는 규칙보다 낫지 않다. 다른 것을 잰다

전체 PR-AUC는 max |z|와 사실상 동률이다. 대포 계정에서 12%로 크게 진 것이
버그인지 확인했더니 메커니즘이었다 — `log_buyer_age` 입력 −3.77(정상 평균
−0.07)을 오토인코더가 −3.97로 재구성한다. **이상값을 105% 따라간다.**
정상 데이터에도 신규 계정 꼬리가 실재하므로 그 영역을 학습해버린 것이다.

> 재구성 오차는 "희귀함"이 아니라 "재현 불가능함"을 잰다. `max |z|`는
> 희귀함을 잰다. 둘은 다른 질문이다.

증거가 여러 축에 흩어지면 오토인코더가 이기고(작업장 81% vs 40%, 복합 미세
13% vs 0%), 한 축만 극단인데 그 값이 학습 분포에 표현돼 있으면 규칙이
이긴다(대포 계정). 따라서 **대체가 아니라 병행**이 정직한 결론이다.
계획서가 오토인코더를 고른 이유(설명가능성)는 그대로 유효하다.

### 이번에 스스로 고친 것 두 가지

1. **평가 예산 상한** — 첫 실행에서 알림 예산 42건에 이상거래가 223건이라
   재현율 상한이 19%로 눌렸다. 유형 비교가 성립하지 않았다. 주입량을 줄이고
   예산을 이상거래 수와 같게(R-precision) 바꿨다.
2. **복합 미세 보정** — 가격을 1.5배로 심었더니 가격 규칙 단독으로 63%가
   잡혔다. 정상 데이터의 가격 배율 **최대가 1.31배**라 1.5배는 미세한 이상이
   아니라 극단치였다. 각 축을 정상 p80~p95로 내렸다.
   → `docs/05-Troubleshooting/합성-이상치-주입-정상분포-확인.md`

### 설명가능성 (오토인코더를 고른 유일한 근거)

```
#23659  score=2055.41  가격배율=0.05  [계정 도용 투매]
    시세 대비 체결가 91% / 거래 금액 3% / 구매자 계정 나이 3%
#5000   score=3.50     가격배율=1.02  [정상]
    판매자 24시간 거래 건수 42% / 체결 시각 15% / 경매 여부 10%
```

에러 경로 3건 확인(없는 거래 404, 없는 테넌트 404 + 학습된 테넌트 안내,
미학습 모델 503). LLM 자연어 설명은 Phase 6 Intent Router에 연결한다.

### 한계

- **알림 큐가 가격 이상치로 도배된다.** 상위 8건이 전부 계정 도용 투매
  (점수 1,200~2,000 vs 작업장 11). 유형별 쿼터나 로그 스케일 점수 필요
- **병목 4차원은 튜닝하지 않았다.** 평가셋으로 고르면 테스트셋 쇼핑이고,
  홀드아웃 재구성 오차로 고르면 병목이 클수록 항상 유리해 기준이 못 된다
- 기저율 3.30%는 실제(1% 미만)보다 높아 PR-AUC가 낙관적이다. 유형별 재현율을
  주 지표로 봤다

### Intent Router — KoELECTRA는 룰을 못 이겼다

수작업 홀드아웃 60건:

| 방법 | 정확도 |
|---|---|
| 룰 단독 (기준선) | 80.0% |
| 분류기 단독 | **58.3%** |
| 2단 라우터 (배포) | **86.7%** |

**같은 모델이 LLM 생성 검증셋에서는 94.5%, 사람이 쓴 평가셋에서는 58.3%다.**
Phase 4에서 "스타일 적응분"으로 간접 추정했던 것이, 여기서는 평가셋 출처에
따라 정확도가 반토막 나는 형태로 직접 드러났다. 평가셋을 손으로 써야 하는
이유의 가장 선명한 증거다.

그럼에도 2단 라우터가 기준선을 4건 앞선다. 분류기의 가치는 정확도가 아니라
룰이 기권한 구간의 **커버리지 보완**에 있다. 상세는 ADR-0010.

### 확신도가 교정되어 있지 않았다

첫 학습(스무딩 없이 손실 0.013)에서 **오답 확신도 중앙값 0.978, 정답 0.991** —
사실상 구분이 없었다. 경계 발화 20건 전부를 0.99로 확신해 에스컬레이션이
**0/20**이 됐다. "애매하면 에이전트로"라는 설계 목표가 통째로 깨진 것이다.

임계값으로는 못 고친다(분리 자체가 없다). 대신 **모호한 발화를 `compound`로
직접 학습**시키고(LLM 생성 108건) 레이블 스무딩 0.1을 넣었다.
→ 에스컬레이션 0/20 → **15/20** 회복.

### 시맨틱 캐시 — 계획 대비 범위를 줄였다

동의 쌍 16 / 함정 쌍 16으로 임계값을 측정했더니:

| | 동의 쌍 | 함정 쌍 |
|---|---|---|
| 평균 유사도 | 0.8453 | 0.8439 |
| 최대 | — | **0.9787** |

**함정 쌍이 동의 쌍보다 유사도가 높거나 같다.** 오탐 0%인 임계값 0.98에서
홀드아웃 적중률은 **0%** — 정확 일치 캐시와 동일하다.

파인튜닝 임베딩 탓인지 베이스 모델과 비교했더니 베이스가 **더 나빴다**
(격차 −0.1455 vs +0.0014). 파인튜닝 문제가 아니라 짧은 질의에서 어휘 중첩이
지배적인 문장 임베딩의 성질이다.

그래서 **기본을 정확 일치로 두고, 유사도 매칭은 `faq_smalltalk`에만** 허용했다.
조회 시점엔 라우팅 전이라 의도를 모르므로 **저장된 엔트리의 의도로 게이팅**한다.
`"안녕"` → `"안녕하세요"` 캐시 유사도 히트를 확인했다. 상세는 ADR-0012.

### 엔드투엔드에서 잡은 결함 4건

1. **에이전트가 등록가와 예측 기준가를 직접 비교**해 "지금 사면 오른다"는
   잘못된 결론을 냈다. 도구가 둘 다 `price`/`anchor_price`로만 줘서 구분할
   방법이 없었다 → `listing_price` / `baseline_price` + `baseline_source`로 변경
2. `"그림자 암살검 시세"`에 예측 도구를 안 부르고 등록가를 시세로 답함 →
   도구 설명에 "등록가는 시세가 아니다" 명시
3. `"수수료 얼마인가요"`가 FAQ+시세 동시 매칭으로 복합 질의에 빠져 에이전트가
   "수수료 도구가 없다"고 답함 → FAQ 신호 우선 규칙 추가
4. 캐시 히트인데 `llm_calls`가 원본 값(2회)으로 표시 → 캐시 효과 측정이
   정반대로 읽힘 → 히트 시 0으로 덮어씀

3번 수정 후 홀드아웃 수치는 그대로(86.7%)였다. 평가셋 FAQ 항목에 "얼마"가
없어서 영향이 없었던 것이고, **평가셋 오답을 보고 고친 게 아니므로 오염 우려도
없다.**

### 카테고리 혼입이 실제로 발생했다 — Phase 3 스트레치 착수 조건 충족

`"3만원 이하 불속성 검"`에 **초심자용 단궁(활)과 +6 스틸 해머**가 섞였고,
초기엔 에이전트가 "모두 불속성 검"이라고 단정했다. 프롬프트를 보강해 지금은
"미스릴 단검과 초심자용 단궁은 불속성 검이 아니다"라고 스스로 짚지만,
**검색 레이어의 혼입 자체는 그대로다.**

로드맵 Phase 3 스트레치 `subcategory` 하드 필터의 착수 조건이 발동했다.

다만 **착수는 Phase 7 이후로 미뤘다.** 조건 충족이 곧 최적 타이밍은 아니고,
프론트엔드 없이는 혼입이 사용자에게 얼마나 거슬리는지 확인할 수단이 없어
재색인 범위를 근거 있게 정할 수 없기 때문이다. 조건 개정 내역은 로드맵에
남겼다.
