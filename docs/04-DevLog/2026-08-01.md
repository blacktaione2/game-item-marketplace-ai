# Phase 8-4: id 공간 통일 (B-축소) (ADR-0022)

## 착수 전에 세 가지를 셌고, 그게 계획을 바꿨다

설계를 확정하기 전에 코드에서 확인했다.

| 확인 | 결과 |
|---|---|
| 가드 호출 지점 | **한 곳**뿐 (`detect_trade`). 공간 선언은 셋, 전부 `SYNTHETIC` |
| 합성 id의 성격 | `index + 1`, **배열 위치**. `features.py`는 id를 **묶음 키로만** 쓴다 — 모델은 id를 본 적이 없다 |
| 프론트 | **이미 `합성#3`으로 접두사를 붙이고 있었다** |

## 결론은 유지, 근거는 폐기

"표현 계층만"을 제안할 때 든 근거는 *"특징이 id를 값으로 쓸 수 있으니 전면
문자열화는 학습을 건드린다"* 였다. **확인 2가 이 근거를 폐기했다** — 안 쓴다.

실제 근거는 다르다: 위치 인덱스에 접두사를 붙여도 정체성이 되지 않고, 내부는
공간이 하나뿐이며(충돌은 경계에서만 가능), 표현 절반은 이미 돼 있었다.

**결론이 같아도 근거가 틀렸으면 틀린 것이다.** ADR-0016 → 0017에서 같은 정정을
한 적이 있다.

## 실질적 수정은 접두사가 아니라 기본 인자였다

```python
- def detect_trade(tenant_code, trade_id, id_space: IdSpace = IdSpace.SYNTHETIC)
+ def detect_trade(tenant_code, trade_id, id_space: IdSpace)
```

라우터는 처음부터 기본값을 안 뒀고 주석으로 이유까지 적어뒀는데 **함수는 두고
있었다.** 두 호출자가 우연히 명시하고 있어서 안 드러났을 뿐이다.

**접두사 파싱을 붙여도 이 구멍은 안 닫힌다.** `inspect.signature`로 고정했다.

## 400과 501을 갈랐다

`parse_ref()`는 지원 여부를 보지 않는다. 실측 확인:

```
syn:3   -> 200  trade_id=3 id_space=synthetic score=3.65
pg:3    -> 501  (요청은 맞다. 서버가 아직 그 평면을 못 읽는다)
3       -> 400  (어느 평면인지 알 수 없다 — 추측하지 않는다)
syn:abc -> 400    foo:3 -> 400    syn:0 -> 400
```

요청 형식도 두 필드(`trade_id` + `id_space`)에서 한 값(`trade_ref`)으로 합쳤다.
두 필드는 **서로 어긋나게 올 수 있고 어긋난 걸 검출할 방법이 없다.**

## `/alerts`가 가드를 안 지난다는 걸 기록했다

문서가 "id를 받는 모든 진입점이 가드를 통과한다"고 서술해왔는데 사실이 아니다.
GM 큐는 외부 id를 안 받고 합성 코퍼스만 훑으므로 검사 대상 자체가 없다.

**지금은 안전하고, 위험해지는 조건이 분명하다** — 이 목록에 백엔드 거래가
섞이면 `id_space` 하드코딩이 곧바로 거짓이 된다.

**가짜 가드는 넣지 않았다.** 하드코딩 값에 `require_supported()`를 불러봐야
항상 통과한다 — 통과가 보장된 검사는 잘못된 안심만 준다. docstring과 API
명세에 전제와 그 전제가 깨지는 조건을 적는 쪽을 택했다.

## 하지 않은 것

- **프론트 변경 없음.** `/detect`를 호출하지 않는다(`/alerts`만 쓴다).
  설계안의 "프론트가 접두사 전송" 항목은 대상이 없었다
- **`SUPPORTED_SPACES`에 `BACKEND`를 넣지 않았다.** 파싱이 된다고 처리가 되는
  건 아니다 — 백엔드 거래를 11개 특징 축으로 바꾸는 코드가 따로 필요하고,
  `pair_trades_7d` 같은 이력 기반 특징은 5건짜리 데모 데이터로는 무의미하다

## 검증

- 테스트 78 → **93건** 통과
- 엔드포인트 6종 입력으로 200/501/400 갈림 실측(위)
- `/alerts` 무변경 확인 (284건, `id_space=synthetic`)

# Phase 8-5a: JWT 인증 (ADR-0023)

rate limiting은 5b로 분리했다. JWT만으로도 변경면이 넓고, rate limit 키가 토큰
신원이라 순서 의존도 있다.

## 게이트웨이를 두지 않았다

4 OCPU 공유도 이유지만 더 결정적인 건 **AI 서버가 어차피 직접 노출돼 있다**는
점이다 — 8000이 열려 있고 비용(LLM)이 나가는 쪽이 여기다. 게이트웨이를 세워도
그 앞을 우회하면 의미가 없다. 단일 오리진은 Vite dev proxy가 이미 준다.

대가는 검증기가 두 벌인 것이다. 클레임 이름을 양쪽 한 곳씩에 모아 서로를
가리키게 하고, **발급은 백엔드만** 하게 했다.

## 발급은 데모, 검증은 진짜

`POST /api/auth/demo-token {userId}` — 비밀번호 없음. **경로 이름이 곧
경고다.** 대신 서명·만료·발급자·필수 클레임은 전부 실제로 검증한다.
클레임 값은 요청이 아니라 **DB에서** 읽는다.

## 테넌트를 클레임으로 옮긴 게 핵심이었다

`X-Tenant-Id: 1`은 그냥 문자열이라 누구나 아무 테넌트나 주장할 수 있었다.
멀티테넌시가 간판인 프로젝트에서 격리가 성립하지 않던 상태다.

AI 서버 요청 본문·쿼리에서도 `tenant_code`를 뺐다 — **ADR-0022에서
`trade_id`+`id_space`를 한 값으로 합친 것과 같은 논리**다. 부수 효과로 실제
구멍 하나가 닫혔다: 시맨틱 캐시 키가 테넌트별로 갈리는데, 본문으로 받던 동안엔
**남의 테넌트 캐시를 조회하도록 요청할 수 있었다.**

## 실측 검증

```
토큰 없이 구매                    401
쓰레기 토큰                       401
정상 토큰                         200
정상 토큰 + X-Tenant-Id: 2 덧붙임  200  ← 헤더가 실제로 죽었다
alerts: 없음 / USER / ADMIN       401 / 403 / 200
actuator/prometheus 인증 없이     200
부하 하네스 오버셀 단언            0건 유지 (1946 == 1946)
```

테스트 AI **93 → 108**, 백엔드 **1 → 10**. 백엔드에 행동 테스트가 처음 생겼다.
시드에 의존하지 않도록 필요한 행을 테스트가 직접 만든다(CI는 빈 DB).

## 처리량이 떨어져 보였는데 인증 탓이 아니었다

같은 명령이 ADR-0020의 105.9/s가 아니라 64/s를 냈다. 인증을 의심했지만
**Security 필터체인은 요청당 0.7ms**(전체 312ms의 **0.22%**)로 실측됐다 —
actuator가 `spring_security_filterchains_seconds`를 공짜로 준다.

두 번째 가설(`trades` 47,052행 누적)도 시드를 다시 적용해 재측정하니 그대로 64/s라
기각했다. 대기·보유가 **같은 배수(1.67×)**로 늘고 대기/보유 비(26×)와
실측/이론상한 비(0.72)가 **그대로**인 걸 보면 시스템이 아니라 박스가 느려진 쪽이다.

**귀속시킬 근거가 없으므로 귀속시키지 않았다.** 대신 `load/README.md`에 "절대
처리량을 세션 간에 비교하지 말 것"을 규칙으로 남겼다.

## 부수

- Boot 4에서 `@AutoConfigureMockMvc`가 `org.springframework.boot.webmvc.test.autoconfigure`로
  이동. `spring-boot-4-autoconfigure-공통패턴` 사례가 하나 늘었다
- `JWT_SECRET`은 **두 곳에 같은 값**이 필요하다(루트 `.env`, `ai/.env`).
  다르면 발급은 되는데 AI 서버만 401을 낸다

# Phase 8-5b: 요청 한도 (ADR-0024)

새 의존성 **0개**. 백엔드는 Redisson `RRateLimiter`(분산 락 때문에 이미 있음),
AI는 `redis.asyncio` 고정 윈도우(시맨틱 캐시가 쓰던 클라이언트).

## 설계 중에 대상이 하나 늘었다

`demo-token`이 **인증 없이 열린 유일한 경로**다. 여기가 무제한이면 나머지
한도는 "토큰을 새로 받아 우회"가 성립한다. 다만 신원이 없어 **키를 IP로** 잡아야
하고, 이번 범위의 유일한 예외다. NAT 뒤 오탐 가능성은 ADR에 한계로 적었다.

`X-Forwarded-For`는 **읽지 않는다.** 신뢰할 프록시가 없는데 그 헤더를 보면
누구나 값을 바꿔가며 새 버킷을 받는다 — 한도를 거는 코드가 스스로 우회로를
만드는 셈이다. 구현하다 넣을 뻔했고, 넣기 전에 걷어냈다.

## 한도 근거를 두 층으로 나눠 적었다

초안 서술이 틀렸다. "0.81 req/s 실측 → 20회/분, 정상 사용의 20배"라고 썼는데,
0.81 req/s는 **48.6회/분**이므로 20회는 상한의 **41%**이지 20배가 아니다.
*물리적 상한*(측정)과 *추정 정상 빈도*(추정)를 한 문장에 섞어 근거가 흐려졌다.
숫자는 유지하되 **측정과 판단을 갈라** 적었다.

## 부하테스트 충돌 — 시나리오 성격으로 갈랐다

기준은 **그 시나리오가 단일 사용자 행위인가 다중 사용자 행위인가**다.
`cache-warm`은 단일 사용자가 캐시를 데우는 것이 전제라 VU마다 토큰을 나누면
테스트 목적이 깨진다 → 구성 완화만. `purchase`는 다중 사용자가 실제에 가깝고
구매자가 3명뿐이라 사용자 확대도 자연스럽다.

완화는 **파일에 남지 않게** 한다 — 백엔드는 `application-loadtest.yml` 프로파일,
AI는 기동 시 환경변수. 손으로 고쳤다 되돌리는 방식은 잊을 수 있다. 우회 헤더를
기각한 것과 같은 기준(감사 가능해야 한다)이다. **끄지 않고 올린다** — 리미터
경로가 그대로 돌아야 오버헤드가 측정에 포함되고 오염 여부를 카운터로 단언할 수
있다.

## 안전망이 자기 자신에게 걸렸다

오염 경고를 붙였는데 **작동하지 않았다.** 3,361건 중 300건만 통과한 실행에서
경고가 조용했다.

원인은 리미터가 아니라 **경고의 입력**이었다. `snapshot_metrics.py`가 카운터를
증가분 상위 25개만 출력하는데, 바이트 카운터(억 단위)가 순위에 섞여 있고 Spring
Security가 3,362짜리 필터체인 계열을 9개 추가하면서 `rate_limited_total`의
증가분 3,057이 **표시에서 밀려났다.**

**잘린 화면을 안전망의 입력으로 삼은 것이 잘못이다.** 스냅샷 원본에서 직접 세도록
고쳤고, 같은 조건에서 10,178건을 잡았다.

## 실측

```
demo-token 30/분   : 30회 통과 → 31회차 429, Retry-After 60
assistant  20/분   : 20회 통과 → 21회차 429, Retry-After 29
사용자 격리         : user3 막힌 상태에서 user4 → 200
구매 10/초         : 순차 15건 전부 통과(리필), 동시 25건 → 17/8
loadtest 프로파일   : 동시 25건 → 25/25
부하테스트(완화)    : 체크 100%, 경고 없음, 오버셀 0건(834 == 834)
```

테스트 AI **108 → 116건**. Redis 없이 가짜 클라이언트로 돌며, 특히 `EXPIRE`를
창의 첫 요청에만 거는지를 고정한다 — 매번 갱신하면 창이 밀려 **한도가 사실상
사라지는데 정상 응답만 나와서** 눈치채기 어렵다.

## 트러블슈팅 — 세 번째라서 문서로 뺐다

이 하네스에서 **검사 자체가 틀린 것이 세 번째**다. 앞의 둘(ADR-0020)은 정상
시스템에 실패를 보고한 **오보**였고 이번은 결함을 놓친 **침묵**이라 방향이
반대다. 뒤쪽이 훨씬 나쁘다 — 오보는 확인하다 드러나지만 침묵은 **검사가 있다는
안심만 주고 아무것도 안 한다.**

[[검사-자체가-틀린-사례들]]에 세 건과 체크리스트를 모았다. 같이 확인한 것:
`run.sh:95`의 오버셀 단언도 **여전히 k6의 렌더링된 요약을 grep**한다. 지금은
k6가 커스텀 메트릭을 자르지 않아 안전하지만, 위험한 건 "요약을 읽는 것"이 아니라
**"잘라내는 요약을 읽는 것"**이라는 구분을 문서에 남겼다.

이번 라운드의 다른 후보들은 **일부러 뺐다** — 처리량 하락은 원인 미상이라
결함으로 진단된 게 아니고(교훈은 `load/README.md` 규칙으로 충분),
`X-Forwarded-For`와 `EXPIRE` 함정은 넣기 전에 걷어내 결함이 된 적이 없다
(ADR + 코드 주석 + 테스트로 고정).

# Phase 8-6a: 관측성 2단계 — 착수하지 않았다 (ADR-0025)

## 조건이 안 걸렸다

ADR-0019가 2단계(ELK·분산 트레이싱)를 **"부하테스트 결과가 지목할 때"**로
조건부 정의해뒀는데, 세 라운드를 돌아봐도 지목한 적이 없다. 로그를 뒤져야 답이
나온 사건이 없었고, 백엔드→AI 호출은 여전히 헬스체크 하나다. Grafana 6패널로
못 답한 질문도 없었다.

**조건을 걸어뒀으면 조건이 안 걸렸을 때 안 하는 것이 그 조건의 값어치다.**
4 OCPU에 상시 인프라를 늘리는 비용은 크다.

## 대신 관측이 지목한 것을 쟀고 — 고치지 않기로 했다

로드맵에 "캐시 적중 경로의 임베딩 낭비"가 올라 있었다. 그런데 ADR-0020이
`cache_ms` 107.9ms를 재고 **"임베딩 낭비"라고 단정한 근거는 코드 읽기**였고,
그 안에서 임베딩이 얼마인지는 잰 적이 없었다.

**측정 전에 판정 기준을 숫자로 박았다** — `encode ≥ cache_ms의 50%` **이고**
`≥ 30ms`일 때만 고친다. 목표 수치를 안 거는 것과 판정 기준을 안 거는 건 다르다.
후자가 없으면 재고 나서 "이 정도면 고칠 만한가"를 감으로 정하게 된다.

| 구간 | 평균 | 비중 |
|---|---|---|
| `cache` 전체 | 66.0ms | 100% |
| **`cache_encode`** | **18.0ms** | **27%** |
| **`cache_lookup`** | **48.1ms** | **73%** |

**둘 다 미달(27% < 50%, 18ms < 30ms). 고치지 않았다.**

`cache_encode` 18.0ms가 ADR-0020의 `live-llm` 임베딩 단계 18.1ms와 일치해
측정 자체는 신뢰할 만하다.

**ADR-0020의 귀속이 틀렸다.** 지배적인 건 조회 쪽이고, 원인은
`_load_entries()`가 정확 일치 여부와 무관하게 **모든 엔트리를 MGET하고 각각
384차원 임베딩을 JSON 파싱 + 정규화**한다는 것이다. 단일 키 조회면 될 일에
O(전체 엔트리)를 치른다.

**이것도 이번에 고치지 않았다** — 검토받지 않은 새 변경이고, 이 라운드의 규칙이
"지배적이지 않으면 고치지 않고 그쪽을 등록한다"였다. 측정값을 붙여 등록했다.

> 재보지 않고 고쳤으면 **이득 상한 18ms(요청의 8%)를 얻고 진짜 비용 48ms는
> 그대로 남았을 것**이다. 그리고 "고쳤다"는 사실만 남았을 것이다.

## 표시 결함 — 원인이 둘이었다

ADR-0024에서 오염 경고를 조용히 통과시킨 그 결함이다. 단위 혼합만이 아니었다:

1. 바이트(억)·나노초가 요청 수(천)를 밀어냄
2. **인증 도입으로 생긴 `spring_security_filterchains_*` 26개 계열이 전부 요청
   수와 같은 값**으로 자리를 잠식

자리를 늘리는 대신 **단위군을 분리하고 동일 증가분을 접었다**(값이 같으면 정보도
같다). 검증은 음성·양성 둘 다 — 숨었던 실행에서 `rate_limited 3057`이 **2위로
드러나고**, 깨끗한 실행에서는 안 나온다.

**검사는 여전히 표시를 안 읽는다.** 표시는 사람이 읽는 것이고, 검사가 표시에
의존하면 표시 규칙이 바뀔 때 다시 조용해진다.

작업 중 Docker Desktop이 내려가 있어 인프라를 다시 올렸다. ES 인덱스(42건)와
볼륨은 살아 있었다.

# Phase 8-6a′: 적중 경로 임베딩 지연화 (ADR-0026) — 앞 결론을 뒤집었다

## 예측의 근거를 대려다 전제가 무너졌다

원래 "조회 최적화"로 설계했고 성공 기준을 `48.1 → 20ms 이하`로 잡았다.
검토에서 **"20은 어디서 나온 숫자인가"**를 지적받았고, 답하려면 단일 GET 왕복
비용을 알아야 했는데 모르고 있었다. 재보러 갔다가 그림이 바뀌었다.

| | 격리 | 부하 중(10 VU) |
|---|---|---|
| `lookup()` | **1.05ms** | 48.1ms |
| `encode_one` | **15.77ms** | 18.0ms |

**Redis 작업은 1ms다.** 48ms 중 47ms는 Redis가 아니었다.

`encode_one`은 `async` 핸들러 안의 **동기 CPU 호출**이라 이벤트 루프를 막는다 —
10ms 타이머를 함께 돌리니 **평균 17.28ms, 최대 36.02ms** 밀렸다.

**즉 73%를 만든 원인이 바로 그 27%였다.** ADR-0025가 "임베딩은 27%뿐이니
안 고친다"고 한 것은 틀렸다.

## 결과 — "27%짜리"를 고쳤더니 전체가 10배

임베딩을 값이 아니라 **콜러블**로 넘겨 정확 일치일 때 부르지 않게 했다.

| | 전 | 후 |
|---|---|---|
| `cache_ms` | 66.0ms | **5.3ms** |
| 전체 p95 | 279ms | **25.9ms** (10.8배) |
| 처리량 | ~48/s | **316/s** (6.6배) |
| `cache_encode` 호출 | 매 요청 | **2회** (저장 시에만) |

예측(`cache_ms` ≤ 10ms)이 **격리 측정에서 도출된 계산**이었고 5.3ms로 적중했다.
단일 GET 최적화는 실측 이득 0.6ms라 **채택하지 않았다** — 표적이 틀렸었다.

`cache_encode` 호출 수 **2회**가 구조적 증거다. 적중 19,568회에서 임베딩이
한 번도 계산되지 않았다. 단위 테스트는 **부르면 터지는 콜러블**로 이를 고정한다 —
적중률이나 `llm_calls`가 같은 것만으로는 확인되지 않는 성질이다.

## 기록을 다시 쓰지 않았다

ADR-0025는 지우지 않고 **정정 블록**을 상단에 붙였다. 원래 표와 결론은 그대로
둔다 — "그 시점에 그 근거로 그렇게 판단했다"는 기록이고, 판정 기준을 미리
박아둔 절차 자체는 유효했다. 틀린 것은 **동시성 하의 wall-time을 작업량으로
귀속한 것** 하나다.

## 남긴 것

- 트러블슈팅 4번째 사례 — **"동시성 하의 단계 wall-time은 작업량이 아니다"**.
  확인은 10ms 타이머 지연으로 싸게 된다
- `asyncio.to_thread` 등록 — 미적중·검색·리랭킹 경로는 여전히 루프를 막는다.
  **전 요청의 동작을 바꾸는 결정**이라 별도 설계가 필요하다
- **"다른 단계 결론도 같은 함정일 수 있다"는 표식** — 지금 뒤지지 않되, 비슷한
  이상치가 나오면 이 패턴부터 의심하라는 기록만

# Phase 8-6b: 번들 분할 (ADR-0027) — Phase 8 마감

## 전제부터 확인했다

"Recharts 사용처가 하나"라는 전제가 틀리면 분할해도 다시 딸려온다. 먼저 셌다 —
`recharts`를 import하는 파일 **1곳**(`PriceChart.tsx`), 그걸 쓰는 곳 **1곳**
(`ItemDetail`), 차트 라이브러리 의존성도 recharts뿐. 간접 유입 경로가 없다.

## 라우트가 아니라 컴포넌트 단위

무게가 한 컴포넌트에 몰려 있다. 라우트 3개를 다 쪼개면 Suspense 경계만 셋으로
늘고 `ItemDetail`·`AnomalyQueue` 자체 코드는 작아 추가 이득이 거의 없다.

| | 이전 | 이후 |
|---|---|---|
| 엔트리 청크 | 683.15 kB / gzip **201.29 kB** | 288.36 kB / gzip **92.22 kB** |
| `PriceChart` 청크 | — | 394.74 kB / gzip 108.56 kB (지연) |
| 엔트리의 recharts 참조 | 15회 | **0회** |

**첫 로드 gzip 54% 감소.**

## 숫자를 미리 걸지 않은 이유

ADR-0026에서는 예측값을 걸었다 — **반증할 인과 모델이 있었기** 때문이다.
여기엔 없다. 모듈을 엔트리에서 빼면 바이트가 기계적으로 빠지고 크기는 빌드
출력에서 직접 읽힌다. 미리 적는 건 예측이 아니라 장식이다. 대신 **구조적
기준**(엔트리에 Recharts 부재)을 걸었다.

## 지연 로딩이 만든 UX 변화를 상쇄했다

"기능 무변화"가 아니라 **"기능은 같고 로딩 순간이 추가됨"**이 정확하다.

- **마운트 시 미리 받는다** — 청크 다운로드와 시세 조회는 독립인데, 차트가
  그려지는 건 예측 도착 후다. 그때 받기 시작하면 두 대기가 **직렬**로 붙는다
- **폴백 높이를 260px로 맞춘다** — 다르면 도착하는 순간 레이아웃이 튄다

**폴백이 실제로 자연스러운지는 확인하지 못했다.** 브라우저 자동화가 없다 —
ADR-0013 때와 같은 한계이고, 사람이 본 뒤 갱신한다.

# Phase 8 마감

여섯 항목으로 시작해 **ADR 0019~0027 아홉 개**로 끝났다. 늘어난 셋은 전부
**측정이 계획을 바꾼 것**이다.

**가장 값어치 있었던 것은 기능이 아니라 세 번의 정정이다.**

1. ADR-0020의 "임베딩 낭비" 귀속이 틀렸다 → 0025가 분해로 확인
2. ADR-0025의 "임베딩은 27%뿐" 결론이 틀렸다 → 0026이 격리 측정으로 확인
3. 오염 검사가 잘린 화면을 읽어 **조용히 통과**했다 → 0024→0025가 수정

셋 다 **기록을 다시 쓰지 않고 정정 블록으로** 남겼다. 그리고 셋 다 **누군가
"그 숫자 어디서 나왔나"를 물었기 때문에** 드러났다.

남긴 것(조건부 미착수): ELK·트레이싱, `asyncio.to_thread`, 다른 단계 결론
재검토, RAGAS 게이트·Docker 푸시, 실제 인증. 각각의 착수 조건은 로드맵에 있다.
