# Phase 8-4: id 공간 통일 (B-축소) (ADR-0022)

## 착수 전에 세 가지를 셌고, 그게 계획을 바꿨다

설계를 확정하기 전에 코드에서 확인했다.

| 확인 | 결과 |
|---|---|
| 가드 호출 지점 | **한 곳**뿐 (`detect_trade`). 공간 선언은 셋, 전부 `SYNTHETIC` |
| 합성 id의 성격 | `index + 1`, **배열 위치**. `features.py`는 id를 **묶음 키로만** 쓴다 — 모델은 id를 본 적이 없다 |
| 프론트 | **이미 `합성#3`으로 접두사를 붙이고 있었다** |

## 결론은 유지, 근거는 폐기

"표현 계층만"을 제안할 때 든 근거는 *"특징이 id를 값으로 쓸 수 있으니 전면
문자열화는 학습을 건드린다"* 였다. **확인 2가 이 근거를 폐기했다** — 안 쓴다.

실제 근거는 다르다: 위치 인덱스에 접두사를 붙여도 정체성이 되지 않고, 내부는
공간이 하나뿐이며(충돌은 경계에서만 가능), 표현 절반은 이미 돼 있었다.

**결론이 같아도 근거가 틀렸으면 틀린 것이다.** ADR-0016 → 0017에서 같은 정정을
한 적이 있다.

## 실질적 수정은 접두사가 아니라 기본 인자였다

```python
- def detect_trade(tenant_code, trade_id, id_space: IdSpace = IdSpace.SYNTHETIC)
+ def detect_trade(tenant_code, trade_id, id_space: IdSpace)
```

라우터는 처음부터 기본값을 안 뒀고 주석으로 이유까지 적어뒀는데 **함수는 두고
있었다.** 두 호출자가 우연히 명시하고 있어서 안 드러났을 뿐이다.

**접두사 파싱을 붙여도 이 구멍은 안 닫힌다.** `inspect.signature`로 고정했다.

## 400과 501을 갈랐다

`parse_ref()`는 지원 여부를 보지 않는다. 실측 확인:

```
syn:3   -> 200  trade_id=3 id_space=synthetic score=3.65
pg:3    -> 501  (요청은 맞다. 서버가 아직 그 평면을 못 읽는다)
3       -> 400  (어느 평면인지 알 수 없다 — 추측하지 않는다)
syn:abc -> 400    foo:3 -> 400    syn:0 -> 400
```

요청 형식도 두 필드(`trade_id` + `id_space`)에서 한 값(`trade_ref`)으로 합쳤다.
두 필드는 **서로 어긋나게 올 수 있고 어긋난 걸 검출할 방법이 없다.**

## `/alerts`가 가드를 안 지난다는 걸 기록했다

문서가 "id를 받는 모든 진입점이 가드를 통과한다"고 서술해왔는데 사실이 아니다.
GM 큐는 외부 id를 안 받고 합성 코퍼스만 훑으므로 검사 대상 자체가 없다.

**지금은 안전하고, 위험해지는 조건이 분명하다** — 이 목록에 백엔드 거래가
섞이면 `id_space` 하드코딩이 곧바로 거짓이 된다.

**가짜 가드는 넣지 않았다.** 하드코딩 값에 `require_supported()`를 불러봐야
항상 통과한다 — 통과가 보장된 검사는 잘못된 안심만 준다. docstring과 API
명세에 전제와 그 전제가 깨지는 조건을 적는 쪽을 택했다.

## 하지 않은 것

- **프론트 변경 없음.** `/detect`를 호출하지 않는다(`/alerts`만 쓴다).
  설계안의 "프론트가 접두사 전송" 항목은 대상이 없었다
- **`SUPPORTED_SPACES`에 `BACKEND`를 넣지 않았다.** 파싱이 된다고 처리가 되는
  건 아니다 — 백엔드 거래를 11개 특징 축으로 바꾸는 코드가 따로 필요하고,
  `pair_trades_7d` 같은 이력 기반 특징은 5건짜리 데모 데이터로는 무의미하다

## 검증

- 테스트 78 → **93건** 통과
- 엔드포인트 6종 입력으로 200/501/400 갈림 실측(위)
- `/alerts` 무변경 확인 (284건, `id_space=synthetic`)

# Phase 8-5a: JWT 인증 (ADR-0023)

rate limiting은 5b로 분리했다. JWT만으로도 변경면이 넓고, rate limit 키가 토큰
신원이라 순서 의존도 있다.

## 게이트웨이를 두지 않았다

4 OCPU 공유도 이유지만 더 결정적인 건 **AI 서버가 어차피 직접 노출돼 있다**는
점이다 — 8000이 열려 있고 비용(LLM)이 나가는 쪽이 여기다. 게이트웨이를 세워도
그 앞을 우회하면 의미가 없다. 단일 오리진은 Vite dev proxy가 이미 준다.

대가는 검증기가 두 벌인 것이다. 클레임 이름을 양쪽 한 곳씩에 모아 서로를
가리키게 하고, **발급은 백엔드만** 하게 했다.

## 발급은 데모, 검증은 진짜

`POST /api/auth/demo-token {userId}` — 비밀번호 없음. **경로 이름이 곧
경고다.** 대신 서명·만료·발급자·필수 클레임은 전부 실제로 검증한다.
클레임 값은 요청이 아니라 **DB에서** 읽는다.

## 테넌트를 클레임으로 옮긴 게 핵심이었다

`X-Tenant-Id: 1`은 그냥 문자열이라 누구나 아무 테넌트나 주장할 수 있었다.
멀티테넌시가 간판인 프로젝트에서 격리가 성립하지 않던 상태다.

AI 서버 요청 본문·쿼리에서도 `tenant_code`를 뺐다 — **ADR-0022에서
`trade_id`+`id_space`를 한 값으로 합친 것과 같은 논리**다. 부수 효과로 실제
구멍 하나가 닫혔다: 시맨틱 캐시 키가 테넌트별로 갈리는데, 본문으로 받던 동안엔
**남의 테넌트 캐시를 조회하도록 요청할 수 있었다.**

## 실측 검증

```
토큰 없이 구매                    401
쓰레기 토큰                       401
정상 토큰                         200
정상 토큰 + X-Tenant-Id: 2 덧붙임  200  ← 헤더가 실제로 죽었다
alerts: 없음 / USER / ADMIN       401 / 403 / 200
actuator/prometheus 인증 없이     200
부하 하네스 오버셀 단언            0건 유지 (1946 == 1946)
```

테스트 AI **93 → 108**, 백엔드 **1 → 10**. 백엔드에 행동 테스트가 처음 생겼다.
시드에 의존하지 않도록 필요한 행을 테스트가 직접 만든다(CI는 빈 DB).

## 처리량이 떨어져 보였는데 인증 탓이 아니었다

같은 명령이 ADR-0020의 105.9/s가 아니라 64/s를 냈다. 인증을 의심했지만
**Security 필터체인은 요청당 0.7ms**(전체 312ms의 **0.22%**)로 실측됐다 —
actuator가 `spring_security_filterchains_seconds`를 공짜로 준다.

두 번째 가설(`trades` 47,052행 누적)도 시드를 다시 적용해 재측정하니 그대로 64/s라
기각했다. 대기·보유가 **같은 배수(1.67×)**로 늘고 대기/보유 비(26×)와
실측/이론상한 비(0.72)가 **그대로**인 걸 보면 시스템이 아니라 박스가 느려진 쪽이다.

**귀속시킬 근거가 없으므로 귀속시키지 않았다.** 대신 `load/README.md`에 "절대
처리량을 세션 간에 비교하지 말 것"을 규칙으로 남겼다.

## 부수

- Boot 4에서 `@AutoConfigureMockMvc`가 `org.springframework.boot.webmvc.test.autoconfigure`로
  이동. `spring-boot-4-autoconfigure-공통패턴` 사례가 하나 늘었다
- `JWT_SECRET`은 **두 곳에 같은 값**이 필요하다(루트 `.env`, `ai/.env`).
  다르면 발급은 되는데 AI 서버만 401을 낸다
