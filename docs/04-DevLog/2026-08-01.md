# 2026-08-01

# Phase 8-4: id 공간 통일 (B-축소) (ADR-0022)

## 착수 전에 세 가지를 셌고, 그게 계획을 바꿨다

설계를 확정하기 전에 코드에서 확인했다.

| 확인 | 결과 |
|---|---|
| 가드 호출 지점 | **한 곳**뿐 (`detect_trade`). 공간 선언은 셋, 전부 `SYNTHETIC` |
| 합성 id의 성격 | `index + 1`, **배열 위치**. `features.py`는 id를 **묶음 키로만** 쓴다 — 모델은 id를 본 적이 없다 |
| 프론트 | **이미 `합성#3`으로 접두사를 붙이고 있었다** |

## 결론은 유지, 근거는 폐기

"표현 계층만"을 제안할 때 든 근거는 *"특징이 id를 값으로 쓸 수 있으니 전면
문자열화는 학습을 건드린다"* 였다. **확인 2가 이 근거를 폐기했다** — 안 쓴다.

실제 근거는 다르다: 위치 인덱스에 접두사를 붙여도 정체성이 되지 않고, 내부는
공간이 하나뿐이며(충돌은 경계에서만 가능), 표현 절반은 이미 돼 있었다.

**결론이 같아도 근거가 틀렸으면 틀린 것이다.** ADR-0016 → 0017에서 같은 정정을
한 적이 있다.

## 실질적 수정은 접두사가 아니라 기본 인자였다

```python
- def detect_trade(tenant_code, trade_id, id_space: IdSpace = IdSpace.SYNTHETIC)
+ def detect_trade(tenant_code, trade_id, id_space: IdSpace)
```

라우터는 처음부터 기본값을 안 뒀고 주석으로 이유까지 적어뒀는데 **함수는 두고
있었다.** 두 호출자가 우연히 명시하고 있어서 안 드러났을 뿐이다.

**접두사 파싱을 붙여도 이 구멍은 안 닫힌다.** `inspect.signature`로 고정했다.

## 400과 501을 갈랐다

`parse_ref()`는 지원 여부를 보지 않는다. 실측 확인:

```
syn:3   -> 200  trade_id=3 id_space=synthetic score=3.65
pg:3    -> 501  (요청은 맞다. 서버가 아직 그 평면을 못 읽는다)
3       -> 400  (어느 평면인지 알 수 없다 — 추측하지 않는다)
syn:abc -> 400    foo:3 -> 400    syn:0 -> 400
```

요청 형식도 두 필드(`trade_id` + `id_space`)에서 한 값(`trade_ref`)으로 합쳤다.
두 필드는 **서로 어긋나게 올 수 있고 어긋난 걸 검출할 방법이 없다.**

## `/alerts`가 가드를 안 지난다는 걸 기록했다

문서가 "id를 받는 모든 진입점이 가드를 통과한다"고 서술해왔는데 사실이 아니다.
GM 큐는 외부 id를 안 받고 합성 코퍼스만 훑으므로 검사 대상 자체가 없다.

**지금은 안전하고, 위험해지는 조건이 분명하다** — 이 목록에 백엔드 거래가
섞이면 `id_space` 하드코딩이 곧바로 거짓이 된다.

**가짜 가드는 넣지 않았다.** 하드코딩 값에 `require_supported()`를 불러봐야
항상 통과한다 — 통과가 보장된 검사는 잘못된 안심만 준다. docstring과 API
명세에 전제와 그 전제가 깨지는 조건을 적는 쪽을 택했다.

## 하지 않은 것

- **프론트 변경 없음.** `/detect`를 호출하지 않는다(`/alerts`만 쓴다).
  설계안의 "프론트가 접두사 전송" 항목은 대상이 없었다
- **`SUPPORTED_SPACES`에 `BACKEND`를 넣지 않았다.** 파싱이 된다고 처리가 되는
  건 아니다 — 백엔드 거래를 11개 특징 축으로 바꾸는 코드가 따로 필요하고,
  `pair_trades_7d` 같은 이력 기반 특징은 5건짜리 데모 데이터로는 무의미하다
