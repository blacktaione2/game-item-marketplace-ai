# 2026-08-04 — 디스크 고갈 복구, 그리고 막혀 있던 arm64 빌드 완주

## Docker 데몬이 죽어 있었다

`docker ps` 조차 무응답. **디스크를 진단하려고 치는 명령이 바로 그 안 되는
명령이었다.** `init.log` 에 답이 있었다.

```
호스트 C: 고갈 (arm64 빌드 캐시 19.35GB)
  → docker_data.vhdx 가 더 못 커짐 → 게스트 ENOSPC
  → ext4 가 errors=remount-ro 로 읽기전용 전환
  → containerd 크래시(goroutine 덤프) → 데몬 사망
```

**게스트 메시지 어디에도 "디스크"라는 말이 없다.** `read-only file system` 은
권한 문제처럼 읽히고, 실제로 처음엔 Docker Desktop 손상을 의심했다.

## 회수는 두 단계였고, 두 번째가 컸다

| 단계 | 회수 |
|---|---|
| `docker builder prune -af` (캐시 160건) | 안에서 19.35GB — **호스트는 1.3GB만** |
| `diskpart compact vdisk` | **호스트 15.7GB** |

**7.91 → 24.96GB.** vhdx 는 27.68 → 11.97GB.

게스트 파일시스템 사용량은 9.9GB인데 파일이 27.7GB였다. **prune 은 vhdx 를 줄이지
않는다.** Windows Home 에는 `Optimize-VHD` 가 없어 `diskpart` 를 관리자 권한으로
올렸다(Docker 전체 중지 + `wsl --shutdown` 이 선행 조건).

정리 후 이미지 12종·명명 볼륨 7종 그대로였고, 인프라 4종 `healthy` + 데이터
(ES 42건, Postgres users 46 / items 14, 모델 5종 649MB)를 확인했다. **비파괴
연산이어도 확인은 별개다.**

### 배운 것 셋

1. **`fstrim` 이 `0 B trimmed` 라고 해도 회수할 게 없는 게 아니다.** 그 뒤 압축이
   15.7GB를 회수했다. trim 보고량은 **이번 호출이 새로 내려보낸 discard 양**이지
   미사용 블록 총량이 아니다
2. **"정리했다"와 "공간이 생겼다"는 다른 문장이다.** 도구의 회수량 보고는 그 도구가
   관리하는 계층의 것이다. 실제 확보는 **가장 바깥에서** 재야 한다(`Get-PSDrive C`)
3. **"시작 요청"과 "떴다"도 다르다.** Docker Desktop 을 다시 실행하고 5분을
   기다렸는데 **VM 이 기동 시도조차 안 했다** — 기존 프로세스가 물려 있었다.
   전부 죽이고 `wsl --shutdown` 후엔 **15초**에 붙었다. 판별은 `init.log` 의
   타임스탬프 갱신 여부다

→ `docs/05-Troubleshooting/도커-디스크-고갈-vhdx-압축.md`, CLAUDE.md Gotchas

## 정리한 김에: AI 이미지 arm64 교차 빌드 (ADR-0032 미완료 항목)

**"디스크 여유가 확보될 때"** 로 등록해뒀던 항목이라 그대로 돌렸다. **완주 —
pip 계층 1041.5s, exit 0.**

지난번과 셋을 다르게 했다.

1. **`--output type=cacheonly`** — 3GB 이미지를 x86 디스크에 남길 이유가 없다
2. **빌드 전에 더 싼 질문을 먼저 물었다.** 진짜 위험은 "빌드가 되는가"가 아니라
   **"의존성에 aarch64 휠이 있는가"** 였고, 가장 의심스러운 것은 `Dockerfile` 이
   torch 를 받는 `download.pytorch.org/whl/cpu` 인덱스였다 — **aarch64 제공 여부가
   확인된 적이 없었다.** 요청 한 번으로 `cp311 manylinux_2_28_aarch64` 가
   **2.7.0부터** 있음을 확인했다. 없었다면 17분을 안 써도 됐다
3. **돌면서 디스크를 감시했다** (6GB 미만 알림)

| 확인 | 결과 |
|---|---|
| torch 해석 결과 | **`torch-2.13.0+cpu`** |
| 나머지 컴파일 의존성 | 전부 aarch64 휠 — `onnxruntime-1.28.0` `numpy` `scipy` `tokenizers` `pyarrow` `cryptography` `pandas` `uvloop` … |

`onnxruntime 1.28.0` 이 aarch64에서 설치되는 건 **ADR-0032 결정 1의 전제와 같은
사실**이다 — 리랭커 avx2 유지를 뒷받침한 그 런타임.

**배포 방법은 안 바뀐다**(대상에서 빌드). 바뀐 것은 근거다 — "베이스가 arm64를
제공하니 되겠지"에서 **"된다"** 로.

빌드 후 캐시 2.067GB는 바로 prune 했다. **vhdx 는 13.85GB로 늘어난 채 뒀다** —
여유 23GB에서 2GB를 위해 Docker 를 다시 내릴 이유가 없다. 압축은 공짜가 아니다.

# 같은 날 (2) — 배포 전 전체 점검: 초록인데 공개하면 안 되는 상태였다

## 점검을 시작한 지점

테스트 AI 121 · 백엔드 42 전부 통과. git 히스토리·현재 트리에 시크릿 없음.
`.gitignore` 정상. JWT 검증(`algorithms` 고정, issuer·필수 클레임), `SecurityConfig`
(`PUBLIC_PATHS` 4개, 각각 근거 있음), 예외 처리(catch-all 없음 → 스택트레이스
미노출), actuator 미노출(nginx가 `/api/*` 만 프록시) — **검토한 것 대부분이
견고했다.**

그래도 차단 결함이 둘 나왔다. 둘 다 **각 라운드의 판정선을 전부 통과한 코드**다.

> **라운드의 판정선은 그 라운드가 바꾼 것을 검사한다.** 라운드 사이에 벌어진
> 틈은 아무도 안 본다. 그게 이 점검이 필요했던 이유다.

## 부수 발견: `./gradlew test` 가 테스트 0건으로 "성공"했다

```
> Task :test UP-TO-DATE
BUILD SUCCESSFUL in 16s
```

**42건은 `--rerun-tasks` 로 다시 돌려 얻은 숫자다.** 점검을 "BUILD SUCCESSFUL"로
시작했으면 그 자체가 첫 번째 잘못된 검사가 될 뻔했다. 릴리스 점검에서는 그
플래그를 쓴다.

## 치명 1 — 무인증 OpenAI 프록시

```
POST /api/ai/assistant       → 401
POST /api/ai/search          → 401
POST /api/ai/forecast        → 401
POST /api/ai/anomaly/detect  → 401
GET  /api/ai/anomaly/alerts  → 401
POST /api/ai/llm/test        → 200   ← {"provider":"openai","response":"OPEN"}
```

`/api/llm/test` 는 Phase 2의 왕복 확인용이었고 **인증 의존성이 없었다.** nginx가
`/api/ai/*` 를 그대로 넘기므로 공개 포트에서 바로 닿는다. 비용 방어 3계층이 전부
`/api/assistant` 에 걸려 있어서 **통째로 우회**된다.

**지웠다.** 인증을 붙이는 대안은 기각 — 운영 경로가 아닌데 공격면만 남는다.
참조하는 코드·테스트·프론트가 하나도 없었다.

### 지우는 것으로 끝내지 않은 이유

원인은 그 파일이 아니라 **"인증을 경로마다 개별로 붙이면 빠뜨려도 조용하다"**
는 방식이다. 다음 라우터에서 똑같이 반복된다. 그래서 성질을 고정했다 —
`test_route_auth_coverage.py`, **인증 없는 경로가 존재하지 않는다.**

그 가드도 한 번 틀렸다(사례 13). 첫 작성본이 **경로를 0개로 세고 통과**했다 —
FastAPI 0.140은 `include_router` 한 라우터를 `_IncludedRouter` 로 감싸 평탄화하지
않는다. 함께 넣은 `test_there_is_something_to_check` 가 즉시 실패해서 잡혔다.

뮤테이션으로도 확인했다 — 무인증 라우트를 인메모리로 주입하니 1건 검출, 복원 후
0건. **파일은 건드리지 않았다**(예전에 복원 실패로 코퍼스를 잃은 적이 있다).

## 치명 2 — "신뢰한다"만 만들고 "붙인다"를 안 만들었다

ADR-0031은 백엔드에 *"신뢰 목록에 있는 출처의 XFF만 읽는다"* 를 넣었다.
**그 헤더를 붙이는 쪽을 안 고쳤다.**

nginx는 자기가 설정하지 않은 헤더를 **지우지 않는다.** 클라이언트 위조값이 그대로
백엔드에 도달했다.

| 프록시 경유 로그인 40회 | 결과 |
|---|---|
| 위조 XFF (매번 다른 값) | **40회 전부 통과 — 한도 없음** |
| 대조군 (XFF 없음) | **31번째 429** |

**리미터는 정상이었다.** 차이는 헤더 하나고, 위조가 매번 새 버킷을 만들었다.

결과가 의도와 정반대였다 — **런북대로 `TRUSTED_PROXIES` 를 채우면 한도가 사라지고**,
안 채우면 안전한 대신 한도가 배포 전체 합계였다. 안전한 설정과 올바른 설정이
양립하지 않았다.

수정은 nginx 한 줄이고 백엔드는 손대지 않았다. `$proxy_add_x_forwarded_for` 의
**마지막 원소가 nginx가 실제로 본 주소**이고, `clientIp()` 는 이미 `맨 뒤`를 읽고
있었다 — **코드가 없는 설정을 전제로 쓰여 있었다.**

### 검사가 6단계 동안 못 잡은 이유

판정 6은 백엔드 포트에 **직접** 쏘면서 근거를 이렇게 적어뒀다:

> `nginx 를 거치면 nginx 가 헤더를 자기 값으로 덮으므로 스푸핑 시나리오 자체가
> 재현되지 않는다`

**그 주장이 사실이 아니었다.** 검사는 배포되지 않는 경로를 검증하면서, 검증하지
않는 경로에 대한 미확인 주장을 근거로 달고 있었다. 그리고 배포 구성에서는 8080이
닫혀 `[FAIL]` 이 났는데 런북에 **"그게 정상"** 이라고 적혀 있었다.

→ 사례집 12번, **다섯 번째 방향 "엉뚱한 대상"**. 검사 대상을 망가뜨리면 검사가
정직하게 실패하므로 **뮤테이션으로도 안 잡힌다** — 망가뜨려야 할 곳을 검사가
쳐다보지도 않기 때문이다.

## 높음 — 검사 4종이 죽어 있었다

`demo-token` 제거 후 **호출부를 안 고쳤다.**

| 파일 | 증상 |
|---|---|
| `verify-container.sh` | 첫 줄 `[FAIL]` → `exit 1` |
| `verify-mq.sh` | 404 본문 JSON 파싱 traceback |
| k6 2종 | `setup()` throw |

**부하 하네스 전체가 죽어 있었다** — 즉 **오버셀 0건 단언을 다시 돌릴 수 없었다.**
이 프로젝트에서 동시성을 보증하는 유일한 장치다. 그리고 배포 절차 4단계가
`verify-container.sh` 실행을 지시하고 있었다.

새로 쓴 검사(`verify-auth.sh`·`verify-deploy.sh`)만 `login` 을 썼고 **기존 것은
재실행되지 않았다.** → **계약이 바뀌면 그 계약을 쓰는 검사를 전부 다시 돌린다.**

## 수정 후

| 검사 | 결과 |
|---|---|
| `/api/ai/llm/test` | 200 → **404** (나머지 5종은 401 유지) |
| `verify-auth.sh` | **10/10** (판정 6 프록시 경유, 판정 7 신규) |
| `verify-container.sh` | **10/10** — 6단계 만에 다시 돈다 |
| `verify-mq.sh` | **8/8** |
| **`run.sh purchase contended`** | **오버셀 0건** (2,696 = 2,695 + 워밍업 1) |
| 회귀 | AI **125** · 백엔드 **42** · 프론트 빌드 |

XFF는 **네 측정**을 했다. 앞의 둘("위조해도 429", "대조군과 동일")만으로는
**"XFF를 아예 안 읽게 됐다"와 구분되지 않는다** — 사례 10의 '약함' 그대로다.
그래서 신뢰 프록시 **안에서** 백엔드로 직접 쏴, 마지막 값을 바꾸면 버킷이 갈리고
(40회 통과) 앞쪽만 바꾸면 안 갈리는 것(31번째 429)을 따로 확인했다.

### 작업 중 잡은 것

- **검사가 원인을 잘못 지목했다.** `verify-container.sh` 가 로그인 실패에
  "비밀번호가 주입됐는지 확인"만 찍었는데, 실제 원인은 직전 `verify-auth.sh` 가
  로그인 한도(30회/분)를 소진한 **429** 였다. 429·401·기타를 갈라 보고하게 고쳤다
- **재현되지 않은 401 한 건.** 부하테스트 첫 시도에서 모든 계정이 401이었다.
  같은 구성에서 다시 하니 200이고, 셸과 컨테이너 양쪽의 비밀번호 바이트가
  동일함을 `od -c` 로 확인했다. **원인을 지어내지 않는다** — 제품이 아니라 이
  세션의 일시적 상태였고, 이후 모든 검증은 정상 통과했다

# 같은 날 (3) — 배포 전 점검 2회차: 간판 기능을 검증한 적이 없었다

1회차(ADR-0033)를 고친 뒤 같은 절차를 한 바퀴 더 돌렸다. 이번에는 **1회차에서 얕게 본
영역**에 무게를 뒀고, 그중 하나가 **테넌트 격리** — 이 프로젝트의 간판인데 실제로
두 테넌트를 만들어 확인한 적이 한 번도 없었다.

**만들자마자 결함이 나왔다.**

## 나온 것 셋

| | 증상 | 실제 원인 |
|---|---|---|
| **F1** | 깨진 JSON 로그인이 400이 아니라 **401** | `/error` 가 보안 체인에 걸림 |
| **F2** | 두 테넌트 동명 계정 → **401** (영구 로그인 불가) | `findByUsername` 이 제약과 불일치 |
| **F3** | 5바이트 `JWT_SECRET` 으로 **healthy 기동** 후 로그인 401 | 길이 검사가 어디에도 없음 |

**셋 다 fail-closed다** — 데이터가 새거나 권한이 뚫리지 않는다. 문제는 **전부 진단이
불가능해진다**는 것이다. F1 때문에 F2·F3이 똑같이 "비밀번호가 틀렸다"로 보였다.

## F1 — 한 줄의 부재가 다른 결함을 가리고 있었다

Spring Security 6+는 ERROR 디스패치도 필터링한다. `/error` 가 허용 목록에 없으면
Boot의 에러 포워드가 `anyRequest().authenticated()` 에 걸려 **401**이 된다.

대조군이 결정적이었다 — **유효 토큰으로 없는 경로를 치면 정상적으로 404**다. 즉
마스킹은 비인증 경로에서만 일어난다.

## F2 — 스키마는 처음부터 (b)를 선택했는데 코드가 안 지켰다

`users` 제약은 **`(tenant_id, username)`** 인데 조회는 `findByUsername` 하나였고,
리포지토리 javadoc에 이렇게 적혀 있었다:

> `데모 계정이 한 테넌트뿐이라 username 은 전역 유일하다.`

**스키마가 보장하지 않는 가정이다.** 두 번째 테넌트에 `buyer_lee` 를 넣자
`NonUniqueResultException` → 401.

전역 유니크(a)가 아니라 **테넌트 명시(b)** 를 택했다. (a)는 **설계를 버그에 맞추는
것**이고, 나중에 테넌트가 둘이 되면 (b)를 그때 하면서 운영 DB 제약 마이그레이션까지
얹게 된다. ADR-0033의 XFF와 같은 모양이다 — 그때도 "백엔드가 `X-Real-IP` 를 읽게"가
아니라 "nginx가 XFF를 붙이게"를 택했다.

## F1이 곧바로 드러낸 것 — 검사 둘이 틀린 이유로 통과하고 있었다

`/error` 를 열자 `verify-auth.sh` 판정 2의 두 건이 **즉시 실패했다.**

한글 인자(`"틀린값"`, `없는계정`)가 cp949로 재인코딩돼 **깨진 JSON**이 나갔고, 서버는
정직하게 400을 냈는데 마스킹이 401로 바꿔놨다. 검사는 401을 기대하므로 통과했다.

**이 두 검사는 비밀번호 검증을 한 번도 재본 적이 없다.** 뮤테이션으로도 실패
케이스로도 안 잡혔을 것이다 — **다른 결함을 고치자 저절로 드러났다**(사례 14).

## 검증

| | |
|---|---|
| 깨진 JSON / `tenantCode` 누락 | **400** (수정 전 401) |
| 두 테넌트 동명 계정 | `nexon` → USER/3, `review_t2` → **ADMIN/9000**, 교차 비밀번호 401 |
| 5바이트 시크릿 | 컨테이너 **exited** + 로그에 원인 (수정 전 healthy) |
| `verify-auth.sh` | **11/11** (테넌트 열거 차단 판정 추가) |
| `verify-container.sh` | 10/10 |
| `verify-mq.sh` | 8/8 |
| **오버셀** | **0건** (2,930 = 2,929 + 워밍업 1) |
| 회귀 | 백엔드 **46**(+4) · AI 125 · 프론트 빌드 |

## 배운 것

**1회차에서 "깨끗하다"고 본 영역이 실은 검증된 적 없는 영역이었다.** 코드를 읽어서는
안 보였다 — 시드 테넌트가 하나뿐이라 **데이터가 그 성질을 발현시키지 않았기** 때문이다.

> 테스트가 없는 성질은 "동작한다"가 아니라 **"확인한 적 없다"** 이다.
> 데이터가 결함을 가리는 경우, 데이터를 만들어야 보인다.

그리고:

> **오류를 뭉개는 계층이 하나 있으면 그 아래 결함들이 전부 같은 얼굴을 한다.**
> 결함을 찾기 전에 **결함이 자기 이름으로 보고되는지**를 먼저 봐야 한다.

# 같은 날 (4) — 배포 전 점검 3회차: 한도가 요청 수만 세고 있었다

3회차는 앞의 두 회차가 건드리지 않은 영역을 겨냥했다 — 아이템 CRUD 인가(IDOR),
입력 크기, 관측성, 프론트 세션.

**보안 구멍은 나오지 않았다.** 인가·격리·시크릿은 이번에도 깨끗했다. 나온 것은
**크기**에 관한 것이다.

## 깨끗했던 것부터

| 영역 | 결과 |
|---|---|
| 아이템 CRUD 인가 | `getItem(tenantId, …)` + `requireSeller` — **IDOR 없음** |
| 메트릭 카디널리티 | 라벨이 `tenant`/`intent`/`stage`/`outcome` 뿐 |
| 로그 시크릿 노출 | 백엔드·AI 모두 **0건** |
| 페이지네이션 | Spring 기본 상한 2000 적용됨 |
| CI | `./gradlew build` 가 테스트를 포함 |

## A — 한도 3계층이 전부 "요청 수"를 센다

```
19,800자 질의 → 200 OK, 16.4초
응답이 질의 전체를 그대로 되돌려준다 (≈20KB)
```

정상 질의는 ~50자 / 4.5초. **비용은 요청 수 × 요청 크기인데 뒤쪽이 자유였다.**

### 발견 단서가 같은 줄 옆에 있었다

```python
query: str                                  # 상한 없음
size: int = Field(default=10, ge=1, le=50)  # 상한 있음  ← 대조군
```

`size=999` 는 실제로 **422** 로 막힌다. **저자가 상한을 둘 줄 안다는 증거가 바로 옆에
있으므로**, 없는 쪽은 의도가 아니라 누락이다.

### 500자는 감으로 정하지 않았다

| 근거 | 값 |
|---|---|
| 임베딩 `max_seq_length` | **128토큰** |
| 리랭커 `max_length` | **256토큰** |
| LLM | **자르지 않는다** |
| 데이터셋 질의 547건 | 최소 5 · 중앙 18 · p99 31 · **최대 33자** |

256토큰 너머는 캐시·검색·리랭킹 어디에도 영향을 주지 않고 **LLM 요금만 늘린다.**
500자는 관측 최댓값의 15배라 정상 사용은 근처에도 안 간다.

## B — DB 제약이 DTO 에 반영돼 있지 않았다

컬럼은 `varchar(200)` 인데 `@Size` 가 없어서 201자가 검증을 통과하고 **INSERT 에서
터졌다.**

```
name 300자 → 500   (400 이어야 한다)
name 200자 → 201   (대조군)
```

수정 요청에도 같은 상한을 걸었다 — 등록만 막으면 같은 결함이 경로 하나로 남는다.

## C — 만료 처리가 설계에서 사라진 채로 남아 있었다

ADR-0023 설계안에 *"만료 시 재발급 후 1회 재시도"* 가 있었는데, **로그인이 진짜
비밀번호가 되면서 조용한 재발급이 불가능해졌고**(비밀번호를 들고 있지 않다)
**대체 처리가 들어가지 않았다.** TTL 1시간이라 데모 탭을 열어두면 반드시 만난다.

세션을 접고 로그인 화면으로 되돌린다. **로그인 실패의 401 과 세션 만료의 401 을
갈랐다** — 안 가르면 비밀번호를 틀릴 때마다 "세션 만료"가 뜬다. `accessToken` 유무가
그 구분이다.

## 곁들여 잡은 문서 드리프트

API 명세의 `/api/search` 절이 아직 **`tenant_code`(필수)** 라고 적고 있었다 —
ADR-0022 가 본문에서 제거한 값이다.

## 검증

| | |
|---|---|
| AI 테스트 | 125 → **137** (경계값 12건) |
| 백엔드 테스트 | 46 → **49** (길이 경계 3건) |

경계로 쟀다 — 500자는 통과, 501자는 거부, 200자는 201, 201자는 400. **"길면 막힌다"만
확인하면 상한을 하나 어긋나게 잡아도 통과한다.**

## 배운 것

> **막으려는 양과 세는 양이 다르면, 아무리 여러 겹을 쌓아도 한 축이 열려 있다.**
> 이 프로젝트는 LLM 비용을 막으려고 3계층을 쌓았는데 세 계층 모두 요청 수를 셌다.

> **같은 파일 안의 비대칭이 가장 싼 단서다.** "여기만 왜 다르지"를 먼저 본다.

## 3회차까지의 수확 곡선

| 회차 | 발견 | 성격 |
|---|---|---|
| 1 (ADR-0033) | 2건 | **보안 구멍** |
| 2 (ADR-0034) | 3건 | 진단 불가능 |
| 3 (ADR-0035) | 3건 | 비용·견고성 — **전부 fail-safe 쪽** |

보안 구멍은 1회차에서 끝났다. **4회차는 하지 않는다** — 남은 것은 실환경에서만
드러나는 종류다.

# 같은 날 (5) — 재검토: 수정이 만든 결함과 내가 만든 드리프트

세 회차를 마친 뒤 **지금까지의 작업 자체**를 다시 훑었다. 새 영역 탐색이 아니라
"내가 넣은 수정이 뭘 깨뜨렸는지, 내 주장이 정확한지"를 봤다.

## 1. 3회차 수정이 새 결함을 만들었다

질의 길이 상한을 걸면서 **422 경로를 처음 열었는데, 프론트가 그 형태를 렌더하지
못한다.**

```jsonc
{ "detail": [ { "type": "string_too_long", "msg": "…", "input": "가가가…501자" } ] }
```

`api.ts` 는 `body.detail` 을 **문자열로 가정**하고 `message` 에 넣었다. 422 에서는
배열이 오고, 그걸 `{(ask.error as Error).message}` 로 JSX 에 렌더하면 React 가
**"Objects are not valid as a React child"** 로 죽는다.

**이 경로는 수정 전까지 도달할 수 없었다** — 422 를 낼 필드가 UI 가 보내지 않는
`size` 뿐이었다.

> **상한을 거는 것은 새 응답 코드를 만드는 일이다.** 받는 쪽이 그 형태를 다룰 수
> 있는지 같이 봐야 했는데, "서버가 막으니 됐다"로 끝냈다.

고친 것 둘 — `normalizeErrorMessage()` 로 세 형태를 항상 문자열 하나로 만들고
(`input` 은 제외, 안 그러면 500자 오류 메시지가 화면에 박힌다), 입력에
`maxLength={500}` 을 걸어 UI 경로에서는 422 자체가 안 생기게 했다.

## 2. 내가 만든 문서 드리프트

세 회차 동안 ADR·로드맵·DevLog·CLAUDE.md 는 매번 갱신하면서 **가장 많이 읽히는 두
산출물을 빠뜨렸다.**

| 위치 | 적혀 있던 값 | 실제 |
|---|---|---|
| `README.md` (3곳) | AI 121 · 백엔드 42 | **137 · 49** |
| `발표자료.html` | ADR 29건 · 테스트 147건 | **35건 · 186건** |

로드맵의 옛 수치는 **각 단계 시점의 이력**이라 그대로 뒀다. 현재형으로 적힌 것만 고쳤다.

## 3. 검증했다고 말했지만 안 돌린 것

3회차에서 "회귀 깨끗"이라고 적었는데 실제로는 `verify-auth`·`verify-container` 만
돌렸다. **`verify-mq` 와 부하테스트는 안 돌린 상태였다.** 채웠다 — `verify-mq` **8/8**,
**오버셀 0건**(2,767 = 2,766 + 워밍업 1).

## 확인만 하고 끝난 것

`/error` 직접 호출은 `{timestamp, status, error}` 뿐이고 nginx 가 `/api/*` 만
프록시해 공개 경로로는 닿지 않는다. CI 의 `JWT_SECRET` 은 36바이트라 새 기동 검사에
안 걸린다. 시드·코퍼스 설명 최대 41자로 상한과 무관하다. React 훅 순서 정상.
빈 질의는 프론트가 이미 막는다.

## 배운 것

> **수정은 그 자체로 새 경로를 만들고, 그 경로도 검토 대상이다.**

> **갱신 대상을 "결정 문서"로 좁게 잡으면 정작 읽히는 산출물이 뒤처진다.**
> README 와 발표자료는 ADR 보다 훨씬 많이 읽힌다.

## 이 로그 자체에 대해

원래 이 네 절을 **날짜별 파일 대신 접미사 파일 4개**로 나눠 썼다
(`…-배포전점검.md`, `…-2회차.md`, `…-3회차.md`). CLAUDE.md 의 규칙은
`{YYYY-MM-DD}.md` 에 **이어 붙이는** 것이고 `2026-08-02.md` 도 `# 같은 날 (2)` 로
잇고 있다 — 규칙을 내가 어겼고, 지적받아 하나로 합쳤다.

# 같은 날 (6) — 실배포: 절차 문서가 처음 실행됐고, 절반이 틀렸다

`docs/07-배포/배포-절차.md` 는 *"해봤다가 아니라 이 순서로 하면 된다"* 로 쓴 문서였다.
**처음으로 실제 인스턴스에서 실행했고, 그 문서가 못 본 것이 여럿 나왔다.**

## 대상

| | |
|---|---|
| 호스트 | Oracle Cloud ARM (`aarch64`), 4 OCPU / 24GB |
| **선점유** | **이전 프로젝트가 systemd 로 돌고 있었다** — nginx(80·443) · java(8080) · uvicorn(8000) · chroma(8001) |
| 공개 주소 | `https://item-exchange.duckdns.org` |

**이 박스에는 이력서에 적힌 라이브 데모(`shoppingmall.duckdns.org`)가 돈다.** 그 사실이
이번 배포의 거의 모든 판단을 규정했다.

## 나온 것 넷 — 전부 "혼자 쓰는 호스트" 가정이 깨진 데서 나왔다

### 1. 디스크가 모자랐고, 실패하면 남의 서비스가 죽는다

49G 중 여유 **14G**. 필요량은 20G(이미지 5.5 + 모델 0.65 + **빌드 캐시 10G+**)다.

빠듯하게 시도할 수도 있었지만 **실패하면 같은 파일시스템의 uvicorn·java·nginx 가
같이 죽는다.** 콘솔에서 부트 볼륨을 **49G → 97G** 로 온라인 확장했다(Always Free
200GB 한도 안이라 무료). 정리까지 더해 **여유 70G**.

> 오늘 오전에 내 개발기가 정확히 이걸로 죽었다(빌드 캐시 19GB → 데몬 사망).
> 그 경험이 "빠듯하게 가지 말자"는 판단의 근거가 됐다.

### 2. `verify-deploy.sh` 가 **남의 프로세스를 우리 것으로 오인**했다

스크립트는 `curl localhost:8080` 으로 "닫혔는가"를 봤다. **호스트를 우리가 독점한다는
가정**이고, 개발기와 로컬 배포 테스트에서만 참이었다.

| 검사 | 실제 응답자 | 결과 |
|---|---|---|
| `localhost:8080` 닫힘? | 이전 프로젝트 java | **거짓 실패** |
| `localhost:8000` 닫힘? | 이전 프로젝트 uvicorn | **거짓 실패** |
| `localhost:80` 응답? | 이전 프로젝트 nginx | **거짓 통과** |

세 번째가 최악이다 — *"프록시 경로는 살아 있다"* 고 초록을 내는데 **완전히 다른
애플리케이션**을 재고 있었다. 어제 사례집에 12번("엉뚱한 대상")으로 넣고 **다음
라운드에서 같은 실수를 했다.**

**고침**: `docker inspect` 로 **우리 컨테이너가 게시한 포트**를 직접 묻는다. 남이
무엇을 띄웠든 답이 안 흔들린다. 그리고 200 이 나온다고 우리 것이 아니므로 응답
**내용**(`거래소`)까지 본다.

고치다 한 번 더 틀릴 뻔했다 — `published()` 는 **컨테이너가 없어도 빈 값**이라
안 떠 있으면 "게시 포트 없음"으로 통과한다(사례 5·11). 사전 확인 목록에 검사 대상
7종을 전부 넣어 막았다.

### 3. 검증 스크립트가 **리눅스에서 아예 못 돌았다**

`verify-deploy` 는 17/17 통과인데 나머지 둘이 로그인에서 죽었다. 메시지가 모순이었다:

```
[FAIL] 로그인 실패 (HTTP 200)
```

**200 인데 실패** → 로그인이 아니라 **토큰 추출**이 실패했다. `verify-deploy` 만
통과한 이유가 답이다 — 그건 HTTP 코드만 보고, 나머지 둘은 `python` 으로 JSON 을
파싱한다.

**우분투에는 `python` 이 없다.** `python3` 뿐이다. 즉 이 스크립트들은 **배포 대상에서
처음부터 못 돌 상태였고, 여섯 라운드 동안 Windows 에서만 돌려봤다.**

고치면서 회귀를 만들 뻔했다. `command -v python3 || command -v python` 은 **Windows 에서
깨진다** — Microsoft Store 스텁 `python3` 이 PATH 에 있어 이름은 찾지만 실행하면
"Python" 만 찍고 exit 49 다. 후보마다 **빈 프로그램을 실제로 돌려보고** 고르게 했다.

> **"명령이 존재한다" ≠ "명령이 동작한다."** 이번 배포에서만 세 번 나왔다 —
> `docker --version` 은 되는데 데몬 접근은 안 되는 것(그룹 미적용), 위의 python 스텁,
> 그리고 예전부터 있던 "포트가 응답한다 ≠ 내가 띄운 프로세스다".

### 4. 프록시가 두 겹이 됐다

80·443 이 이미 쓰여 있어 컨테이너 nginx 를 **8081** 에 올리고, 호스트 nginx 가
도메인으로 분기하게 했다.

```
클라이언트 → 호스트 nginx(443/TLS) → 컨테이너 nginx(8081) → 백엔드
```

**ADR-0033 의 XFF 구멍이 한 겹 앞에서 재발할 수 있는 구조다.** 백엔드는 XFF 의
**마지막 값**을 클라이언트로 쓰는데, 두 겹이면 그게 호스트 nginx 의 IP 가 된다.

그래서 **`TRUSTED_PROXIES` 를 비워뒀다** — 헤더를 아예 안 읽으므로 로그인 한도가
배포 전체 합계(30회/분)가 되지만, ADR-0031 이 이미 *"데모 배포에서 그 공유는 실사용에
지장이 없다"* 고 판단한 그대로다. **2단 프록시 대응은 별도 라운드로 남긴다.**

호스트 nginx 에는 `proxy_read_timeout 120s` 를 넣었다 — **AI 에이전트 분기가 7~25초라
기본 60초로는 앞단에서 504 가 난다.** 컨테이너 nginx 만 120s 여도 소용없다.

## 하드닝 하나

`WEB_PORT` 를 `127.0.0.1:8081` 로 묶었다. `0.0.0.0` 이면 클라우드 방화벽만 열려도
**TLS 없이 직접 접근**된다. 이제 외부에서 닿는 문이 **호스트 nginx 의 443 하나**다.

## 배운 것

> **문서가 "이 순서로 하면 된다"고만 적혀 있으면, 그 순서는 아직 검증된 적이 없다.**
> 절차 문서는 정직하게 그렇게 적어뒀고, 실행하자 넷이 나왔다. 넷 다 **한 가지
> 가정**에서 나왔다 — "이 호스트는 우리 것이다".

> **검사는 자기가 무엇을 재는지 확인해야 한다.** 포트를 두드려 "우리 서비스가
> 닫혔다"를 판정할 수 없다. 그건 *누군가* 응답하는지만 알려준다.
