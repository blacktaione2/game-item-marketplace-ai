# 2026-08-04 — 디스크 고갈 복구, 그리고 막혀 있던 arm64 빌드 완주

## Docker 데몬이 죽어 있었다

`docker ps` 조차 무응답. **디스크를 진단하려고 치는 명령이 바로 그 안 되는
명령이었다.** `init.log` 에 답이 있었다.

```
호스트 C: 고갈 (arm64 빌드 캐시 19.35GB)
  → docker_data.vhdx 가 더 못 커짐 → 게스트 ENOSPC
  → ext4 가 errors=remount-ro 로 읽기전용 전환
  → containerd 크래시(goroutine 덤프) → 데몬 사망
```

**게스트 메시지 어디에도 "디스크"라는 말이 없다.** `read-only file system` 은
권한 문제처럼 읽히고, 실제로 처음엔 Docker Desktop 손상을 의심했다.

## 회수는 두 단계였고, 두 번째가 컸다

| 단계 | 회수 |
|---|---|
| `docker builder prune -af` (캐시 160건) | 안에서 19.35GB — **호스트는 1.3GB만** |
| `diskpart compact vdisk` | **호스트 15.7GB** |

**7.91 → 24.96GB.** vhdx 는 27.68 → 11.97GB.

게스트 파일시스템 사용량은 9.9GB인데 파일이 27.7GB였다. **prune 은 vhdx 를 줄이지
않는다.** Windows Home 에는 `Optimize-VHD` 가 없어 `diskpart` 를 관리자 권한으로
올렸다(Docker 전체 중지 + `wsl --shutdown` 이 선행 조건).

정리 후 이미지 12종·명명 볼륨 7종 그대로였고, 인프라 4종 `healthy` + 데이터
(ES 42건, Postgres users 46 / items 14, 모델 5종 649MB)를 확인했다. **비파괴
연산이어도 확인은 별개다.**

### 배운 것 셋

1. **`fstrim` 이 `0 B trimmed` 라고 해도 회수할 게 없는 게 아니다.** 그 뒤 압축이
   15.7GB를 회수했다. trim 보고량은 **이번 호출이 새로 내려보낸 discard 양**이지
   미사용 블록 총량이 아니다
2. **"정리했다"와 "공간이 생겼다"는 다른 문장이다.** 도구의 회수량 보고는 그 도구가
   관리하는 계층의 것이다. 실제 확보는 **가장 바깥에서** 재야 한다(`Get-PSDrive C`)
3. **"시작 요청"과 "떴다"도 다르다.** Docker Desktop 을 다시 실행하고 5분을
   기다렸는데 **VM 이 기동 시도조차 안 했다** — 기존 프로세스가 물려 있었다.
   전부 죽이고 `wsl --shutdown` 후엔 **15초**에 붙었다. 판별은 `init.log` 의
   타임스탬프 갱신 여부다

## 정리한 김에: AI 이미지 arm64 교차 빌드 (ADR-0032 미완료 항목)

**"디스크 여유가 확보될 때"** 로 등록해뒀던 항목이라 그대로 돌렸다. **완주 —
pip 계층 1041.5s, exit 0.**

지난번과 셋을 다르게 했다.

1. **`--output type=cacheonly`** — 3GB 이미지를 x86 디스크에 남길 이유가 없다
2. **빌드 전에 더 싼 질문을 먼저 물었다.** 진짜 위험은 "빌드가 되는가"가 아니라
   **"의존성에 aarch64 휠이 있는가"** 였고, 가장 의심스러운 것은 `Dockerfile` 이
   torch 를 받는 `download.pytorch.org/whl/cpu` 인덱스였다 — **aarch64 제공 여부가
   확인된 적이 없었다.** 요청 한 번으로 `cp311 manylinux_2_28_aarch64` 가
   **2.7.0부터** 있음을 확인했다. 없었다면 17분을 안 써도 됐다
3. **돌면서 디스크를 감시했다** (6GB 미만 알림)

| 확인 | 결과 |
|---|---|
| torch 해석 결과 | **`torch-2.13.0+cpu`** |
| 나머지 컴파일 의존성 | 전부 aarch64 휠 — `onnxruntime-1.28.0` `numpy` `scipy` `tokenizers` `pyarrow` `cryptography` `pandas` `uvloop` … |

`onnxruntime 1.28.0` 이 aarch64에서 설치되는 건 **ADR-0032 결정 1의 전제와 같은
사실**이다 — 리랭커 avx2 유지를 뒷받침한 그 런타임.

**배포 방법은 안 바뀐다**(대상에서 빌드). 바뀐 것은 근거다 — "베이스가 arm64를
제공하니 되겠지"에서 **"된다"** 로.

빌드 후 캐시 2.067GB는 바로 prune 했다. **vhdx 는 13.85GB로 늘어난 채 뒀다** —
여유 23GB에서 2GB를 위해 Docker 를 다시 내릴 이유가 없다. 압축은 공짜가 아니다.
