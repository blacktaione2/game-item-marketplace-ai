# 2026-08-04 (2) — 배포 전 전체 점검: 초록인데 공개하면 안 되는 상태였다

## 점검을 시작한 지점

테스트 AI 121 · 백엔드 42 전부 통과. git 히스토리·현재 트리에 시크릿 없음.
`.gitignore` 정상. JWT 검증(`algorithms` 고정, issuer·필수 클레임), `SecurityConfig`
(`PUBLIC_PATHS` 4개, 각각 근거 있음), 예외 처리(catch-all 없음 → 스택트레이스
미노출), actuator 미노출(nginx가 `/api/*` 만 프록시) — **검토한 것 대부분이
견고했다.**

그래도 차단 결함이 둘 나왔다. 둘 다 **각 라운드의 판정선을 전부 통과한 코드**다.

> **라운드의 판정선은 그 라운드가 바꾼 것을 검사한다.** 라운드 사이에 벌어진
> 틈은 아무도 안 본다. 그게 이 점검이 필요했던 이유다.

## 부수 발견: `./gradlew test` 가 테스트 0건으로 "성공"했다

```
> Task :test UP-TO-DATE
BUILD SUCCESSFUL in 16s
```

**42건은 `--rerun-tasks` 로 다시 돌려 얻은 숫자다.** 점검을 "BUILD SUCCESSFUL"로
시작했으면 그 자체가 첫 번째 잘못된 검사가 될 뻔했다. 릴리스 점검에서는 그
플래그를 쓴다.

## 치명 1 — 무인증 OpenAI 프록시

```
POST /api/ai/assistant       → 401
POST /api/ai/search          → 401
POST /api/ai/forecast        → 401
POST /api/ai/anomaly/detect  → 401
GET  /api/ai/anomaly/alerts  → 401
POST /api/ai/llm/test        → 200   ← {"provider":"openai","response":"OPEN"}
```

`/api/llm/test` 는 Phase 2의 왕복 확인용이었고 **인증 의존성이 없었다.** nginx가
`/api/ai/*` 를 그대로 넘기므로 공개 포트에서 바로 닿는다. 비용 방어 3계층이 전부
`/api/assistant` 에 걸려 있어서 **통째로 우회**된다.

**지웠다.** 인증을 붙이는 대안은 기각 — 운영 경로가 아닌데 공격면만 남는다.
참조하는 코드·테스트·프론트가 하나도 없었다.

### 지우는 것으로 끝내지 않은 이유

원인은 그 파일이 아니라 **"인증을 경로마다 개별로 붙이면 빠뜨려도 조용하다"**
는 방식이다. 다음 라우터에서 똑같이 반복된다. 그래서 성질을 고정했다 —
`test_route_auth_coverage.py`, **인증 없는 경로가 존재하지 않는다.**

그 가드도 한 번 틀렸다(사례 13). 첫 작성본이 **경로를 0개로 세고 통과**했다 —
FastAPI 0.140은 `include_router` 한 라우터를 `_IncludedRouter` 로 감싸 평탄화하지
않는다. 함께 넣은 `test_there_is_something_to_check` 가 즉시 실패해서 잡혔다.

뮤테이션으로도 확인했다 — 무인증 라우트를 인메모리로 주입하니 1건 검출, 복원 후
0건. **파일은 건드리지 않았다**(예전에 복원 실패로 코퍼스를 잃은 적이 있다).

## 치명 2 — "신뢰한다"만 만들고 "붙인다"를 안 만들었다

ADR-0031은 백엔드에 *"신뢰 목록에 있는 출처의 XFF만 읽는다"* 를 넣었다.
**그 헤더를 붙이는 쪽을 안 고쳤다.**

nginx는 자기가 설정하지 않은 헤더를 **지우지 않는다.** 클라이언트 위조값이 그대로
백엔드에 도달했다.

| 프록시 경유 로그인 40회 | 결과 |
|---|---|
| 위조 XFF (매번 다른 값) | **40회 전부 통과 — 한도 없음** |
| 대조군 (XFF 없음) | **31번째 429** |

**리미터는 정상이었다.** 차이는 헤더 하나고, 위조가 매번 새 버킷을 만들었다.

결과가 의도와 정반대였다 — **런북대로 `TRUSTED_PROXIES` 를 채우면 한도가 사라지고**,
안 채우면 안전한 대신 한도가 배포 전체 합계였다. 안전한 설정과 올바른 설정이
양립하지 않았다.

수정은 nginx 한 줄이고 백엔드는 손대지 않았다. `$proxy_add_x_forwarded_for` 의
**마지막 원소가 nginx가 실제로 본 주소**이고, `clientIp()` 는 이미 `맨 뒤`를 읽고
있었다 — **코드가 없는 설정을 전제로 쓰여 있었다.**

### 검사가 6단계 동안 못 잡은 이유

판정 6은 백엔드 포트에 **직접** 쏘면서 근거를 이렇게 적어뒀다:

> `nginx 를 거치면 nginx 가 헤더를 자기 값으로 덮으므로 스푸핑 시나리오 자체가
> 재현되지 않는다`

**그 주장이 사실이 아니었다.** 검사는 배포되지 않는 경로를 검증하면서, 검증하지
않는 경로에 대한 미확인 주장을 근거로 달고 있었다. 그리고 배포 구성에서는 8080이
닫혀 `[FAIL]` 이 났는데 런북에 **"그게 정상"** 이라고 적혀 있었다.

→ 사례집 12번, **다섯 번째 방향 "엉뚱한 대상"**. 검사 대상을 망가뜨리면 검사가
정직하게 실패하므로 **뮤테이션으로도 안 잡힌다** — 망가뜨려야 할 곳을 검사가
쳐다보지도 않기 때문이다.

## 높음 — 검사 4종이 죽어 있었다

`demo-token` 제거 후 **호출부를 안 고쳤다.**

| 파일 | 증상 |
|---|---|
| `verify-container.sh` | 첫 줄 `[FAIL]` → `exit 1` |
| `verify-mq.sh` | 404 본문 JSON 파싱 traceback |
| k6 2종 | `setup()` throw |

**부하 하네스 전체가 죽어 있었다** — 즉 **오버셀 0건 단언을 다시 돌릴 수 없었다.**
이 프로젝트에서 동시성을 보증하는 유일한 장치다. 그리고 배포 절차 4단계가
`verify-container.sh` 실행을 지시하고 있었다.

새로 쓴 검사(`verify-auth.sh`·`verify-deploy.sh`)만 `login` 을 썼고 **기존 것은
재실행되지 않았다.** → **계약이 바뀌면 그 계약을 쓰는 검사를 전부 다시 돌린다.**

## 수정 후

| 검사 | 결과 |
|---|---|
| `/api/ai/llm/test` | 200 → **404** (나머지 5종은 401 유지) |
| `verify-auth.sh` | **10/10** (판정 6 프록시 경유, 판정 7 신규) |
| `verify-container.sh` | **10/10** — 6단계 만에 다시 돈다 |
| `verify-mq.sh` | **8/8** |
| **`run.sh purchase contended`** | **오버셀 0건** (2,696 = 2,695 + 워밍업 1) |
| 회귀 | AI **125** · 백엔드 **42** · 프론트 빌드 |

XFF는 **네 측정**을 했다. 앞의 둘("위조해도 429", "대조군과 동일")만으로는
**"XFF를 아예 안 읽게 됐다"와 구분되지 않는다** — 사례 10의 '약함' 그대로다.
그래서 신뢰 프록시 **안에서** 백엔드로 직접 쏴, 마지막 값을 바꾸면 버킷이 갈리고
(40회 통과) 앞쪽만 바꾸면 안 갈리는 것(31번째 429)을 따로 확인했다.

### 작업 중 잡은 것

- **검사가 원인을 잘못 지목했다.** `verify-container.sh` 가 로그인 실패에
  "비밀번호가 주입됐는지 확인"만 찍었는데, 실제 원인은 직전 `verify-auth.sh` 가
  로그인 한도(30회/분)를 소진한 **429** 였다. 429·401·기타를 갈라 보고하게 고쳤다
- **재현되지 않은 401 한 건.** 부하테스트 첫 시도에서 모든 계정이 401이었다.
  같은 구성에서 다시 하니 200이고, 셸과 컨테이너 양쪽의 비밀번호 바이트가
  동일함을 `od -c` 로 확인했다. **원인을 지어내지 않는다** — 제품이 아니라 이
  세션의 일시적 상태였고, 이후 모든 검증은 정상 통과했다
