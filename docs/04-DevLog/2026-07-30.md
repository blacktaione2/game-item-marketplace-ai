# 2026-07-30 — Phase 7 프론트엔드

## 착수 전에 정정한 전제 두 가지

설계안을 쓰면서 확인한 것이 계획과 달랐다.

1. **세션 기반 로그인은 없었다.** `spring-boot-starter-security` 의존성 자체가
   없고 `X-Tenant-Id`/`X-User-Id` 헤더가 전부다. 그래서 "쿠키 유지 vs 토큰
   전환"이 아니라 "인증을 만들 것인가"가 실제 질문이었다.
2. **PostgreSQL이 비어 있어 시연 시나리오가 끊겨 있었다.** items/users/
   tenants/trades 전부 0건. ES에는 42건이 있는데 백엔드 DB엔 없어서
   `검색 → 상세 → 구매` 경로가 원리적으로 불가능했다.

2번이 Phase 7의 첫 작업이 화면이 아니게 만든 이유다.
→ `docs/05-Troubleshooting/저장소-분리로-인한-id-공간-균열.md`

## 카테고리 혼입 — subcategory 재판단 근거

로드맵대로 화면을 붙인 뒤 확인했다. `"3만원 이하 불속성 검"` 결과 5건:

| 아이템 | 실제 종류 | 불속성? |
|---|---|---|
| +8 강화 롱소드 | 검 | ✗ |
| 미스릴 단검 | 단검 | ✗ |
| +7 강화 롱소드 | 검 | ✗ |
| +6 강화 스틸 해머 | 해머 | ✗ |
| 초심자용 단궁 | **활** | ✗ |

예상보다 나쁘다. 종류 혼입(활·해머)만이 아니라 **불속성 아이템이 한 건도
없다.** 코퍼스의 불속성 아이템은 불꽃의 마법봉(33,000원)과 불꽃의
대검(143,000원)뿐이라 3만원 이하 조건을 만족하는 게 애초에 없다.

즉 문제가 두 겹이다.

1. `subcategory` 하드 필터로 풀리는 **종류 혼입**
2. **조건을 만족하는 결과가 없을 때 "없다"고 하지 않고 유사한 것으로 채우는
   것** — 이건 subcategory 필터로 안 풀린다

에이전트 답변은 `"3만원 이하의 불속성 검은 없지만…"`으로 스스로 짚어 완화가
되고 있지만, 검색 레이어는 여전히 근사치를 채운다. 2번을 로드맵에 별도
항목으로 추가했다.

| users | 1 ~ 206 | 1 ~ 5 |
| trades | 1 ~ 26,702 | 1 ~ |

**범위 검사로는 못 막는다** — 겹치기 때문이다. 그래서 (A) 안전장치로
`app/core/ids.py`에 공간 정책을 두고 호출자가 명시하게 했다.

```
id_space 누락      → 422    backend 지목 → 501    synthetic → 200
```

정책을 한 파일에 모아서 Phase 8에 `SUPPORTED_SPACES`에 한 줄 추가하면 모든
진입점 가드가 동시에 열리게 했다. (B) 네임스페이스 분리 / (C) 완전 통합은
Phase 8로 이관 — (C)는 "실거래 연동을 어떻게 할 것인가"라는 미결 설계와 묶여야

화면은 합성 id에 `합성#` 접두사와 경고 문구를 붙였다. 라벨만으로는 사용자가 그

## 리랭커 하한 실측 — 보류하고 순서를 되돌렸다

`"5만원 이하 검"`에 활이 섞이는 문제를 리랭커 점수 하한으로 자르려 했다.
근거는 "리랭커가 이미 최하위로 판정하고 있으니 자르기만 하면 된다"였다.

수작업 질의 10건(튜닝 5 / 홀드아웃 5) × 상위 8건 = 70건에 적합/부적합을
라벨링해 측정했다(`scripts/evaluate_rerank_floor.py`).

**같은 스크립트를 두 번 돌렸는데 홀드아웃 판정이 뒤집혔다.**

| 실행 | 튜닝 적합 최솟값 | T | 홀드아웃 적합 잘림 |
|---|---|---|---|
| A | −3.59 | −4.09 | **1건 (실패)** |
| B | −3.71 | −4.21 | 0건 (통과) |

원인은 **LLM 질의 재작성의 비결정성**이었다. `"5만원 이하 검"`이 실행마다
`"검 소드 대검"` 또는 `"검 소드 대검 단검"`으로 재작성되고, **토큰 하나 차이로
미스릴 단검 점수가 1.31점 이동했다**(−3.66 ↔ −2.35). 리랭커 자체는 결정론적이다
(같은 재작성 질의면 3회 반복에서 소수점까지 동일).

재려던 마진이 0.3~0.6인데 **입력 노이즈가 0.5~1.3이다.** 신호보다 노이즈가 크면
어떤 임계값도 "이번 실행에서는 맞았다" 이상이 못 된다.
→ `docs/05-Troubleshooting/비결정적-입력-위의-임계값.md`

### 이전 주장 정정

"리랭커는 이미 올바르게 판정하고 있다"고 보고했는데 **n=1 관찰이었다.**
질의를 늘려 보니 `"단검 보여줘"`에서 `전설 등급 대검`(−3.11)·`+8 롱소드`
(−3.35)·`+9 롱소드`(−3.40)가 정답인 `미스릴 단검`(−3.64)보다 **위에 있다.**
순위 자체가 뒤집힌 경우가 있고, 그러면 하한은 원리적으로 무력하다.

### 순서 개정

`1. 리랭커 하한 → 2. subcategory` 를 **`1. subcategory → 2. 재작성 결정성
→ 3. 리랭커 하한`** 으로 되돌렸다.

"작은 변경"이 "안전한 변경"은 아니었다. 하한은 코드 몇 줄이고 재색인이
필요 없지만, 그 작은 변경을 안전하게 하려면 임계값을 정할 수 있어야 하고
지금은 못 정한다. `subcategory`는 재색인 비용이 있는 대신 **임계값이 아예
없다** — `subcategory == "활"`은 실행마다 흔들리지 않는다.

## subcategory 하드 필터 — 완료

리랭커 하한이 기각되면서 순서가 앞으로 온 항목. 채택 근거는 하나다 —
**임계값이 없다.** `subcategory == "활"`은 실행마다 흔들리지 않는다.

- 42건 전부에 세부 종류 부여(검 7 / 지팡이 4 / 활 4 / 둔기 3 / 창 1,
  갑옷 6 / 방패·신발·로브·모자·각반, 반지·목걸이·팔찌·귀걸이,
  물약 2 / 주문서 2 / 재료, 계정 2 / 재화)
- 매핑에 `keyword` 필드, `SearchFilters.subcategory` → `term` 절
- 프롬프트에 표기 대응(소드/롱소드/암살검 → 검, 궁/장궁/쇠뇌 → 활 …)과
  **"종류를 특정할 수 없으면 null로 두라"** 명시 — 억지로 채우면 맞는 결과까지
  걸러진다
- `corpus/__init__.py` 임포트 시점 가드. `subcategory`가 빠지면 그 아이템은
  종류 필터가 걸린 검색에서 **조용히 사라지므로** 그 자리에서 터뜨린다.
  **가드가 실제로 발동하는지 충돌을 주입해 확인했다** — 체크리스트를 만들고
  안 돌려본 전례가 있어서
- MCP 도구 출력·프론트 카드에도 종류 노출. 모델이 이름만 보고 활을 검이라
  단정한 전례가 있어 스스로 검증할 근거를 준다
- `단검`·`대검`은 `검`에 넣었다. 더 잘게 쪼개면 `"검 찾아줘"`가 단검을 놓친다

### 남은 것

`"3만원 이하 불속성 검"`은 이제 **검류만** 돌려주지만 **불속성은 한 건도 없다** —
코퍼스의 불속성 아이템이 전부 3만원 초과다. 속성은 여전히 텍스트 신호이고,
`element` keyword 필드로 같은 메커니즘을 한 번 더 적용하면 풀린다. 그게 들어가면
이 질의가 0건이 되고, **비로소 "없다"고 말하는 처리가 가능해진다.**

## element 속성 하드 필터 — 완료

`subcategory`와 같은 메커니즘을 속성 축에 한 번 더 적용했다(ADR-0015).
매핑·필터·프롬프트·가드·재색인. 42건에 `화염`(3) / `냉기`·`번개`·`신성`·`암흑`
(각 1) / `무속성`(35).

### 메커니즘은 판단할 게 없었고, 판단은 분류 규칙이었다

착수 전 예상은 "같은 메커니즘이라 설계 판단이 필요 없다"였다. 절반만 맞았다 —
매핑·필터·프롬프트는 그대로 복사됐지만 **"무엇을 속성으로 볼 것인가"는
자명하지 않았다.** 세 가지를 정해야 했다.

- **저항은 속성이 아니다.** `용비늘 방패`(화염 피해 40% 감소)를 `화염`으로
  태깅하면 `"불속성 장비"`에 **대화염 방패**가 나온다. 지금 없애려는 오탐과
  정확히 같은 종류다. `암흑 로브`(암흑 저항), `미스릴 갑옷`(모든 속성 저항)도
  같은 이유로 `무속성`
- **이름이 아니라 효과로 판정한다.** `바람의 장궁`은 이름에 속성어가 있지만
  효과가 순수 물리(공격력+사거리)라 `무속성`. 반대로 `폭풍의 창`은 이름에
  없지만 번개 피해가 있어 `번개`. 양방향으로 어긋나서 기준을 못박아야 했다
- **`무속성`은 값이고 `null`이 아니다.** 데이터의 `"무속성"`은 "속성이 없다",
  필터의 `None`은 "속성 조건을 안 건다". 섞으면 `"검 찾아줘"`에서 불꽃의 대검이
  사라진다. 이건 단위 테스트로 못박았다

정본 어휘는 **설명문 쪽 단어**(`화염`/`냉기`/…)로 잡았다. 사용자는 `"불속성"`
이라고 하지만 정본을 설명문에 맞추면 BM25 텍스트와 필터 값이 같은 단어를 쓴다.
사용자 표기는 프롬프트 대응표가 흡수한다.

### 이전/이후를 같은 실행 안에서 쟀다

지난 실행의 집계와 비교하면 그 사이 질의 재작성이 달라진 효과가 섞인다 —
리랭커 하한이 기각된 것과 같은 함정이다. `element` 절만 빼는 패스를 연달아
돌려 A/B로 잡았다(`scripts/evaluate_hard_filters.py` 신규).

| | 이전 | 이후 |
|---|---|---|
| 부적합 결과 | 26건 | **14건 (−46%)** |
| 적합 결과 | 20건 | **20건 (손실 0)** |

| 질의 | 부적합 이전→이후 |
|---|---|
| `"불속성 검 찾아줘"` | **6 → 0** (검류 7건 → 불꽃의 대검 1건) |
| `"얼음속성 지팡이"` | **3 → 0** |
| `"3만원 이하 불속성 검"` | **3 → 0건 반환** |
| 속성 조건 없는 7건 | 변화 없음 |

감소분 12건이 전부 속성 질의 3건에서 나왔고 나머지 7건은 한 건도 안 변했다 —
**효과의 귀속이 깨끗하다.** 이전 상태의 부적합 26건이 위 subcategory 절의
수치와 정확히 일치해서 교차 검증도 됐다.

### 0건이 재현된다 (이번 작업의 핵심 기준)

```
3만원 이하 불속성 검 찾아줘
  필터  {'subcategory': '검', 'element': '화염', 'price_max': 30000.0, ...}
  결과 0건 → 5회 반복 전부 0건 (분포 {0: 5})
```

**한 번 0건인 건 증거가 아니다** — 재작성이 비결정적이라 필터 추출이 흔들릴 수
있다. 5회 돌려 필터 조합까지 동일하게 재현되는 것을 확인했다.

지금도 답 자체는 맞게 나온다(`"검색 결과가 없습니다…"`). 하지만 그건 **결과
0건을 LLM에 넘겨 LLM이 알아서 맞춘 것**이고, 필요 없는 LLM 호출을 쓰며 항목을
지어내지 않는다는 보장이 없다. 구조적 처리는 다음 항목이다.

가드는 `HARD_FILTER_FIELDS = ("subcategory", "element")`로 일반화했고, 충돌
3종(줄 삭제 / 빈 문자열 / subcategory 삭제)을 주입해 전부 발동함을 확인했다.
테스트 49건 통과(`test_filters.py` +3), 프론트 타입체크 통과.

### 측정 중 발견 — 세 번째 축, 다만 공짜가 아니다

`"2만원 이하 전설 등급 무기"`도 정답이 0건인 질의인데 **부적합 3건을 계속
돌려주고 5회 전부 0건이 아니었다.** `전설 등급`이 아직 텍스트 신호다 —
`element` 이전의 속성과 같은 상태다.

그런데 이건 앞의 두 건과 **같은 작업이 아니다.** `subcategory`/`element`는
설명문에 근거가 있어서 태깅이 *판독*이었지만, 등급은 코퍼스에 개념 자체가 없어
**새로 발명**해야 한다 — `미스릴 단검`이 몇 등급인지는 데이터가 답해주지 않는다.
"같은 메커니즘으로 풀린다"고 계산에 넣지 않고 별도 후보로 로드맵에 올렸다.

**다음 작업 범위에 영향이 있다**: "결과 없음" 처리를 넣어도 이 질의는 여전히
근사치를 돌려준다. 0건 경로를 타는 질의만 고쳐진다.

## "결과 없음" 처리 — 완료

0건을 LLM에 넘겨 알아서 답하게 하던 것을 확정 응답으로 바꿨다(ADR-0016).

### 이전 동작이 왜 문제였는지를 먼저 쟀다

같은 입력으로 5회 돌렸다.

| | 답변 종류 | LLM 호출 |
|---|---|---|
| 이전 (빈 결과 → LLM) | **5회 / 5가지** | 2회 |
| 이후 (확정 응답) | **5회 / 1가지** | 1회 |

**이전 5건은 전부 답이 맞았다.** 지어내기는 관측되지 않았고 측정된 건 변동성이다
— 처음에 "항목을 지어낼 수 있다"를 근거로 들었는데, 실제로 재보니 그 근거는
관측되지 않았고 대신 **다섯 개 모두 질의를 어떻게 해석했는지 말하지 않는다**는
공통 결함이 나왔다. 재작성이 아직 비결정적인 상태에서 이게 실질적인 문제다 —
`"불속성"`을 `냉기`로 잘못 뽑아 0건이 된 경우와 진짜로 없는 경우가 사용자에게
똑같이 보인다.

그래서 조건을 노출하기로 했다: `검 · 화염 속성 · 30,000원 이하 조건에 맞는
매물이 없습니다.` 5회 전부 문자열까지 동일했다.

### `llm_calls`는 0이 아니라 1이다

0으로 적고 싶었지만 틀린 값이다. `run_search` 안의 `understand_query`가 이미
호출됐고 **그건 건너뛸 수 없다** — 어떤 필터가 걸렸는지 알아야 0건 판정이
성립한다. 없어지는 건 설명 생성 호출 하나(2 → 1)다. `llm_calls == 0`은 캐시
적중 경로뿐이고 그 구분이 흐려지면 캐시 효과 측정이 망가진다. 프론트 배지도
`no_results`인데 `llm_calls > 1`이면 회귀로 표시하게 했다.

### 조건 노출은 0건일 때만 (의도된 비대칭)

결과가 있으면 항목 자체가 종류·속성을 달고 나와서 사용자가 검증할 수 있다
(subcategory·element 작업의 결과). **0건에는 검증할 대상이 없다** — 그때 유일한
근거가 "무슨 조건으로 찾았는가"다. 필드를 항상 붙이는 것보다 이 경계가 이유를
더 잘 설명한다.

### 핵심 결정 — 0건 응답은 캐시에 저장하지 않는다

`is_cacheable(intent, response)`에 응답 기반 예외를 뒀다.

- **판정 근거인 필터 추출이 비결정적이다.** 질의 문자열로 캐시하면 여러 추출
  결과 중 하나를 임의로 골라 TTL(10분) 동안 고정하는 셈이다
- **0건은 가장 낡기 쉬운 답이다.** 매물 하나만 등록돼도 거짓이 되고, 오류의
  방향("없다")이 더 나쁘다

검증: 0건 질의 2회 연속 → 2회차도 `cache.hit=False`, `llm_calls=1`, 필터 재추출.
대조군(정상 검색) 2회차는 `cache.hit=True`, `llm_calls=0`으로 기존 동작 유지.

로드맵의 "재작성 결과 캐싱" 검토안과 혼동하지 않게 로드맵에 구분을 적어뒀다 —
재작성 캐싱(질의 → 재작성 질의)은 결정성을 높이므로 검토안이고, 판정 캐싱
(질의 → "없음")은 금지다.

테스트 63건 통과(`test_no_results.py` 신규 11건, `test_cache.py` +4건),
프론트 타입체크 통과.

### 범위 한계 (명시)

`"2만원 이하 전설 등급 무기"`는 **고쳐지지 않는다.** `전설 등급`이 아직 텍스트
신호라 ES가 0건을 반환하지 않고 근사치 3건을 돌려주며, 그러면 이 경로를 아예
밟지 않는다. 이 처리는 0건을 **만들지 않고** 이미 0건이 된 것을 제대로 말할
뿐이다 — 0건을 만드는 쪽은 하드 필터(`rarity`)의 몫이다.
