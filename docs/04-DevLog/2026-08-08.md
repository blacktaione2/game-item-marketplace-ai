# 2026-08-08

## 사각지대를 배포본에 태웠고, 라운드가 줄었다

전날 평가셋을 늘리다 찾은 「아이템 어휘를 단 게임 메커니즘 질문」 사각지대를
정면으로 고칠지 정하려고 **먼저 실측**했다. 로컬이 아니라 배포본에 태웠다 —
분류기 가중치가 학습마다 달라 로컬 라우팅은 배포된 동작이 아니다(ADR-0039 기록).

### 8건 중 실제 결함은 2건이었다

| 분기 | 건수 | 결과 |
|---|---|---|
| `faq_smalltalk` | **4** | **이미 올바르게 거절** — 범위를 밝히며 사양, LLM 0회 |
| `compound` | 1 | 되묻는다 |
| `item_search` | 1 | 라벨 보류 (아래) |
| **`price_forecast`** | **2** | **동문서답** — 무관한 아이템의 시세 |

### 2차 방어선이 설계 주장에서 실측으로 바뀌었다

두 동문서답 모두 **진짜 아이템 이름을 밝혔다** (`'+9 강화 롱소드'의 최근 거래가는
29,260원…`). 질의의 주어(`이 옵션`, `세트 효과`)를 채택하지 않았다 — ADR-0039
결정 4가 의도대로 작동한다. **거짓말이 아니라 동문서답**이다.

### 내가 늘린 평가셋에 결함이 있었다

ADR-0039 는 원래 38건에 대해 "어느 분기로 가는지 먼저 무료로 쟀다" 는 단계를
밟았다. **전날 추가한 3건에는 그 단계를 안 밟았다.** 둘이 `faq_smalltalk` 로 가
게이트에 닿지도 않는다.

**그런데 분모에서 뺄 수는 없다.** 로컬/배포 라우팅을 대조하니 **6/8 만 일치**했고
어긋난 둘은 전부 분류기 판정이었다(룰 판정 3건은 완전 재현). *"게이트에 닿는가"*
는 질의의 안정된 속성이 아니다. 그래서 미검출 옆에 **분기를 같이 찍는** 것으로
바꿨다.

> 같은 이유로 ADR-0039 의 커버리지 논증(22+7+9=38/38)도 **분기별로** 읽어야 한다.
> 보장은 "어느 분기로 가든 뭔가가 받는다" 이지 "이 9건이 FAQ 로 간다" 가 아니다.

### 라벨 하나 보류

`강화 확률 올리는 방법 있어?` — *"방법"* 을 물었으니 플레이 질문이라는 읽기와,
거래소의 정직한 답이 "그 확률을 올려주는 물건을 판다" 라는 읽기가 **둘 다
성립한다**(배포본이 성공률 70% 주문서를 돌려줬다). 채점 세트에서 빼고
`AMBIGUOUS_LABEL` 에 이유와 함께 남겼다 — import 가드가 재유입을 막는다.

### 남은 2건은 고치지 않는다

`_forecast_branch` 가 `run_search(size=1)` 의 1등을 **얼마나 약하게 맞았든 그대로
쓴다.** 필요한 건 주제 판정이 아니라 관련성 판정이고, 그건 **ADR-0018 이 이미
기각한 문제**다 — 크로스 인코더 로짓은 한 질의 안에서만 의미가 있다.

근거 셋이 겹쳐서 안 연다: 8건 중 2건, 결과가 거짓이 아님, 기전이 기각된 접근과
겹치고 **해결 방법 자체가 불투명**. 대신 로드맵에 **"ADR-0018 과 같은 뿌리"** 로
등록했다 — 표면이 단순해서("점수 낮으면 버리면 되지") 다시 시작하기 쉬운 문제다.

## 같은 날 (2) — `무속성` 을 고쳤다. 프롬프트를 건드리지 않고

로드맵에 "평가셋 구축이 선행" 으로 1주일 넘게 묶여 있던 항목이다. **평가셋을
만들었더니 프롬프트 문제가 아니었다.**

### 먼저 프롬프트를 읽었다

`query_understanding.py` 에 **이미** 이렇게 적혀 있었다.

```
- 무속성/속성 없는 -> "무속성"
- null("속성 조건 없음")과 "무속성"("속성이 없는 아이템만")은 다릅니다.
```

**정확히 옳은 말로 이미 지시받았는데 42/50 을 틀린다.** 그리고 여기는 프롬프트
한 줄로 97.5% → 22% 를 겪은 바로 그 자리다. 직전 라운드에서도 프롬프트 변형 셋이
연달아 기각됐다 — 네 번째로 같은 무기를 드는 건 판단이 아니라 관성이다.

### 평가셋 39건 — `미언급` 무리가 핵심이다

| 무리 | 정답 | 없으면 |
|---|---|---|
| 무속성 (14) | `"무속성"` | 결함이 안 보인다 |
| 타속성 (8) | 해당 속성 | 다른 속성을 덮어써도 모른다 |
| **미언급 (10)** | `None` | **"전부 무속성" 이 만점** |
| 저항 (4) | `None` | `"화염 저항 방어구"` 가 화염으로 걸린다 |
| 부정형 (3) | `None` (한계) | 정반대를 주는 걸 못 잡는다 |

`"속성 좋은 무기"`(낱말은 있고 답은 `None`)와 **일부러 미수록인** `"속성 안 붙은
신발"` 을 넣었다. 전부 맞는 평가셋은 한계를 못 보여준다.

### 결과

| 무리 | 1차 | 2차 | 오채움 |
|---|---|---|---|
| 무속성 | 62% → **93%** | 86% → **93%** | 0 → 0 |
| 타속성·미언급·저항·부정형 | **전후 동일** | **전후 동일** | **0 → 0** |

**정확도보다 결정성이 더 큰 소득이다.** 기준선이 62% ↔ 86% 로 흔들리는데 후처리
뒤는 두 번 다 93%, 잔여 오답까지 같은 두 질의다.

### 내 정규식이 처음에 틀렸다

```python
r"무속성|속성\s*없...아닌"    # 괄호가 없다
```

`|` 가 가장 약하게 묶여서 **`무속성` 하나만으로 부정형 판정**이 된다. 그러면 모든
무속성 질의가 부정형으로 걸려 **후처리가 한 번도 안 걸린다.** 증상은 "고쳤는데
아무것도 안 변했다" 다. 실행 전에 읽다가 잡았고, 회귀 테스트로 박았다.

### 사전 등록 기준 둘이 실패했고 고쳐 쓰지 않았다

- **타속성 95%** — 전후가 같다(88% → 88%). 의도는 *"후처리 때문에 나빠지면 안
  된다"* 는 **상대** 기준이었는데 **절대** 문턱으로 썼다. **두 라운드 전에
  held-out 기준을 전부 대조군 상대값으로 쓴 이유가 정확히 이건데 여기서 안 했다.**
- **무속성 95%** — 부족분이 전부 일부러 넣은 미수록 표현이다. 14건 중 1건 = 7.1%
  이므로 **처음부터 만족 불가능**한 기준이었다.

ADR-0028 이 한 대로 실패한 채 남기고, 채택 근거를 안전 기준 셋(오채움 = 0, 두 실행
통과) + 손댄 16건이 전부 정답 + 회귀 0 + 두 실행 일치에 뒀다.

### 덤으로 찾은 것

`"어둠 속성 로브"` 가 `null` 을 낸다 — **6/6.** 프롬프트에 `어둠 -> 암흑` 이
있는데도 그렇다. 무속성과 같은 가족인데 **같은 처방을 쓸 수 없다** — `암흑` 을
낱말로 채우면 `"암흑 저항 목걸이"` 가 깨진다. 별도 항목으로 등록했다.

### 남긴 것

- `app/corpus/element_queries.py` (39건), `scripts/evaluate_element_extraction.py`
- `fill_missing_element()` + 테스트 26건 — **전부 LLM 없이 돈다**
- ADR-0040, 로드맵 체크박스 해제, CLAUDE.md

## 같은 날 (3) — 프로바이더가 죽었을 때 무엇을 돌려줄지 정했다 (ADR-0041)

계획서에 있는데 없는 것을 찾다가 `circuit`·`resilience`·`fallback` 이 코드에
**0건**인 걸 봤다. 그런데 장애 시 동작이 **비대칭**이었다.

| 분기 | OpenAI 장애 시 |
|---|---|
| 검색 · FAQ | 산다 (각각 폴백 / LLM 0회) |
| **시세 · 이상거래 · 에이전트** | **500** |

검색이 사는 건 설계가 아니라 fail-open 두 개가 우연히 겹친 결과다.

### 그 시점에 답은 이미 손에 있었다

설명 호출이 터질 때 시세 분기는 예측 결과를, 이상거래 분기는 판정과 기여도를
**이미 계산해뒀다.** 없는 건 산문뿐인데 500 을 냈다. 그래서 ADR-0036 과 같은
처방으로 내려앉게 했다 — 결정 단계가 가진 값으로 문장을 만든다.

- 사과하지 않는다. 답은 다 들어 있고 `degraded` 는 운영자용이다
- 프롬프트가 조건부로 붙이던 고지(콜드스타트 추정, 합성 코퍼스)를 그대로 붙인다.
  빠지면 **모델이 살아 있을 때만 정직한** 응답이 된다
- `llm_calls` 를 줄인다(시세 3→2, 이상거래 1→0). 안 줄이면 안 나간 돈을 센다
- `outcome="degraded"` — **500 이 안 나므로 다른 데서는 안 보인다**
- 에이전트는 손대지 않았다. 거기선 LLM 이 곧 분기라 정직한 500 이 맞다

### 덤으로 찾은 것 — 500 이 예외 문자열을 내보내고 있었다

```python
detail=f"요청 처리 실패: {e}"
```

백엔드는 `include-stacktrace: never` 로 처음부터 막아뒀는데 AI 서버만 안 맞춰져
있었다. **한쪽만 선언된 설정은 결정이 아니라 누락이다.**

그리고 **하나만 고치면 안 됐다** — 훑어보니 **다섯 라우터 중 다섯**이 전부
그랬다. 전부 일반 메시지로 바꾸고 `logger.exception` 을 남겼다. 소스를 훑는
테스트로 고정했고, **그 검사가 헛돌지 않는지 일부러 틀린 문자열로 확인**했다.

### 하지 않은 것

**Claude 폴백.** API 키가 없어 경로를 밟아볼 수 없다. 배선만 하고 "됐다" 고
적는 건 ADR-0039 에서 값을 치른 실수다(MCP 안내문이 한 번도 안 밟혔다).

순서도 이쪽이 맞다 — 폴백이 생겨도 **양쪽이 다 죽는 경우**는 남고, 그때 필요한
게 지금 만든 내려앉기다. 서킷브레이커는 이 위에 얹는다.

테스트 203 → **228**, 전부 LLM 없이 돈다.

## 같은 날 (4) — Claude 폴백을 실제로 만들었다 (ADR-0042)

앞 항목에서 *"API 키가 없어 경로를 밟아볼 수 없다"* 고 적었는데 **확인 안 하고 한
말이었다.** 사용자가 알려줘서 보니 키는 있었다.

그런데 보니 **폴백이 지금 상태로는 동작할 수 없는 이유**도 같이 나왔다.

| 파일 | `ANTHROPIC_API_KEY` |
|---|---|
| 루트 `.env` | **있음** |
| `ai/.env` | **없음** |

CLAUDE.md 가 이미 적어둔 함정이다 — 루트는 docker-compose 용이고 앱은 `ai/.env` 를
읽는다. 게다가 코드에 `anthropic` 이 0건이라 **키가 어디 있든 아무 일도 없었다.**

> **"없다" 는 "안 봤다" 와 다르다.** 결론은 우연히 맞았고 근거는 틀렸다.

### 이 라운드의 진짜 위험은 형식 번역이었다

`LLMClient` 는 중립인데 **에이전트 루프가 OpenAI 메시지 형식을 그대로 쓴다.**
인터페이스만 맞추면 `complete()` 는 되고 **에이전트만 조용히 깨진다** — 폴백이
가장 필요한 순간에.

- `system` 메시지 → 최상위 파라미터
- `assistant.tool_calls` → `tool_use` 블록
- `{"role":"tool"}` → `user` 안의 `tool_result` 블록
- **연속된 도구 결과는 한 메시지로 합친다** — 안 합치면 도구 하나일 땐 되고 둘일 때 400

### 서킷 브레이커는 지연 축 때문이다

예외만 잡아 넘기면 장애 동안 **모든 요청이 1차 타임아웃을 먼저 문다.** RabbitMQ
때 겪은 그것이다(기본 60초 → "구매는 성공하는데 1분"). 연속 3회 실패면 60초 동안
1차를 건너뛴다. 새 의존성 없이 카운터 하나와 타임스탬프 하나.

둘 다 죽으면 **1차 예외**를 올린다 — 2차 예외로 바꿔치면 진단이 엉뚱한 데를 본다.
그 위를 ADR-0041 의 내려앉기가 받아서 두 겹이 순서대로 선다.

### 실제로 밟았다 — 다섯 항목

| | 확인 | 결과 |
|---|---|---|
| 1 | Claude 단독 호출 | `"서울"` |
| 2 | 1차 죽음 → 폴백 | `"서울"` |
| 3 | 임계값에서 1차를 안 부르는가 | 5회 중 **3회만** |
| 4 | **질의이해 JSON 파싱** | `element=화염 subcategory=검 price_max=30000` |
| 5 | **에이전트 도구 호출** | `search_items(tenant_code, query)` |

4·5 가 핵심이었다. 1~3만 보고 끝냈으면 *"폴백은 되는데 검색과 에이전트만 안 되는"*
상태를 채택할 뻔했다.

테스트 228 → **248**, 추가분은 네트워크 없이 돈다.

> **배포 서버의 `ai/.env` 에도 키를 넣어야 한다.** 안 넣으면 기동 로그에
> "폴백 없음" 이 남고 동작은 지금과 같다 — 조용히 깨지지는 않는다.

## 같은 날 (5) — 배포했는데 안 고쳐진 것처럼 보였다. 캐시였다

`"무속성 검 찾아줘"` 에 불꽃의 대검이 그대로 나왔다. 코드가 틀렸거나 배포가 안 된
것처럼 보였는데 **둘 다 아니었다.**

화면 관측 패널이 답을 들고 있었다 — `캐시 적중 (exact)` · `LLM 호출 0회`.
**배포 전에 저장된 응답이 재생된 것이다.** 답변 문구도 증거였다: 고쳐졌다면
`검 · 무속성 조건으로` 인데 `검 조건으로` 뿐이었다.

### 원인 둘

**하나.** `cache_version` 을 안 올렸다. ADR-0040 이 *"응답 모양은 그대로라 올릴
필요 없다"* 고 **명시적으로 판단했는데**, 설정 주석은 **모양과 내용 둘 다**라고
말하고 있었다. 필터가 하나 더 걸리면 같은 질의가 다른 결과 집합을 낸다 — 그게
내용 변경이다. 주석의 절반만 읽었다. **v2 → v3.**

**둘.** 내가 준 확인 절차가 그 실패를 구분하지 못했다. *"불꽃의 대검이 안 나와야
한다"* 는 참/거짓 하나뿐이라, 거짓일 때 **후처리 미적용 / 배포 누락 / 캐시 재생**
셋을 못 가른다. 이 저장소가 반복해 적은 *"판정에 쓴 값을 전부 출력에 넣어라"* 를
**내가 준 절차에는 적용하지 않았다.** 사례 24 로 남겼다.

### 고친 것

- `cache_version` v3
- 확인 절차를 **두 신호로**: ① 배지(`캐시 적중`/`LLM 호출`) ② 답변 문구
- 그 문구를 테스트로 고정(`TestTheUserVisibleSignal`) — 진단에 쓰는 문자열이
  말없이 바뀌면 다음 사람이 같은 데서 헤맨다

테스트 248 → **250**.

## 같은 날 (6) — 배포가 안 갔고, 그다음엔 로그가 안 나왔다

두 건 다 내 실수다.

**하나: 푸시를 안 했다.** 세션 내내 커밋만 하고 `git push` 를 한 번도 안 한 채로
배포를 세 번 안내했다. 서버의 `git pull` 이 `Already up to date.` 라고 답했고
빌드가 전 단계 `CACHED` 였는데, **내가 준 확인 절차는 그걸 안 봤다** — 사례 24 와
같은 실패의 재발이다(원인 후보가 여럿인데 신호가 하나).

**둘: 로그 레벨을 잘못 골랐다.** ADR-0042 에 *"어느 쪽이든 기동 로그에 남는다"* 고
적었는데 둘 다 `logger.info` 였다. **이 앱은 로깅을 설정하지 않는다** — 파이썬 루트
기본값이 `WARNING` 이라 그 줄은 어디에도 안 나온다. `docker logs | grep` 이 빈
결과를 냈고, 그건 **"폴백 없음" 과 "로그가 안 보임" 을 구분해주지 못했다.**

### 고친 것

- **없음 = `warning`.** 레벨도 내용상 맞다 — 폴백 없이 도는 것은 약화된 구성이다
- **`/health` 에 `llm_fallback`**(bool) + 모델명. **키 자체는 안 싣는다.**
  로그 레벨에 기대지 않고 확인할 수 있는 자리를 만든 것이다
- 백엔드 `AiHealthResponse` 의 *"일치해야 한다"* 주석을 정정했다 — **부분집합**이다.
  그렇게 적혀 있으면 AI 쪽에 필드를 더할 때 백엔드까지 재빌드하게 된다

> **로그로 확인하라고 안내하려면 그 레벨이 실제로 출력되는지부터 확인해야 한다.**
> "판정에 쓴 값을 출력에 넣어라" 의 인프라 버전이다 — 값을 넣어도 통로가 막혀
> 있으면 없는 것과 같다.

테스트 250 → **253**.

## 같은 날 (7) — 폴백이 만든 지표 모호함을 메웠다

ADR-0042 가 스스로 등록한 구멍을 닫았다. **그런데 처음 적은 이유가 틀렸다.**

"서킷 상태가 어디에도 안 남는다" 고 썼는데, `logger.warning("1차 LLM 실패 —
폴백으로 넘긴다")` 는 실제로 출력된다. **남기는 하고 집계가 안 됐다.** 그 이유만
으로는 약하다 — Prometheus 는 옵트인이라 평소에 돌지도 않는다.

### 진짜 이유는 내가 만든 드리프트다

`ai_llm_calls_total` 은 *"이 요청이 LLM 을 몇 번 썼나"* 를 센다. 프로바이더가
하나일 땐 그게 곧 OpenAI 사용량이었는데, **폴백이 붙는 순간 그 해석이 깨졌다.**
어디에 청구됐는지 말해주지 않는다.

`ai_llm_provider_calls_total{provider, outcome}` — 라벨 2×2 = 4 시계열.

- **계측을 각 클라이언트 안에** 둔다. 래퍼에 두면 키가 없는 구성에서 아무것도
  안 잡힌다 — 프로바이더가 하나뿐이라 더 취약한 쪽이다
- **`record_response()` 로는 표현이 불가능하다.** 에이전트 한 요청이 `chat()` 을
  다섯 번 부르고 그중 둘만 폴백일 수 있다 — 응답 모양이 아니다. 계측점 원칙의
  두 번째 예외이고, `rate_limited_total` 처럼 이유를 코드에 적어뒀다
- **게이지는 안 만들었다.** 카운터에서 읽히고, 볼 대시보드가 없다

덤으로 교차 검증이 생겼다. `ai_llm_calls_total` 은 응답의 `llm_calls` **상수**에서
오고 새 카운터는 **실제 호출**을 센다 — **어긋나면 그 상수가 틀린 것**이다.
ADR-0039·0041 에서 세 번 손으로 고친 값이라 마침 필요한 검증이다.

테스트 253 → **257**.

## 같은 날 (8) — `running` 을 `준비됨` 으로 읽었다

배포 안내에 `up -d` 직후 `/health` 를 묻는 명령을 넣었고 `Connection refused` 가
났다. **앱이 아직 안 뜬 것뿐**이었는데, 그 오류는 "기동 중 / 죽음 / 바인딩 오류"
셋을 구분해주지 않는다.

**compose 자신은 알고 있었다** — `ai` 헬스체크가 같은 URL 로 `start_period: 20s`,
`retries: 12` 를 단다. 기동에 시간이 걸린다는 게 설정에 이미 적혀 있는데
**내가 준 명령만 그걸 몰랐다.**

`load/verify-deploy.sh` 도 같은 사각이었다 — 사전 확인이 `running` 만 봤다.
`healthy`(있으면)로 바꾸고, 실패 시 **status 와 health 를 둘 다** 찍게 했다.
`unhealthy` 는 기다리지 않고 즉시 실패한다.

> 검증하려고 만든 시뮬레이션이 **그 자리에서 또 틀렸다.** 가짜 `docker` 가
> `$3`(`--format`)을 컨테이너 이름으로 봐서 다섯 경우가 전부 "실패" 로 나왔다.
> 하마터면 멀쩡한 로직을 고칠 뻔했다 — **전부 실패하면 harness 를 의심할 것.**

사례 25.

## 같은 날 (9) — 검색 품질 CI 게이트: "RAGAS 게이트"를 만들지 않았다 (ADR-0043)

기획서가 `build → test → RAGAS 품질 게이트 → 이미지 푸시`라고 적어둔 것 중
게이트를 넣었다. **다만 RAGAS 는 게이트가 아니다.**

| | 역할 | 근거 |
|---|---|---|
| Recall@k · MRR | **pass/fail**, 매 커밋 | 결정론적, LLM 0회, 무료 |
| RAGAS | **리포트**, 수동 실행 | 심판 변동폭 미측정 + 매 커밋 약 648회 과금 |

심판이 흔들리는 지표에 문턱을 걸면 ADR-0028·0040 에서 사전 등록 기준이 실패한
것과 같은 실수의 3회차가 된다. **이름을 지키려고 그러는 게 더 나쁘다.**

### ADR-0021 이 적어둔 착수 조건이 무너졌다

*"모델 아티팩트 배포 전략이 먼저"* 라고 적혀 있었는데, 그건 **독립인 문제 둘을
한 줄로 묶은 것**이었다.

- "새 클론에 모델이 없다" → 트리플 162건 x 2에폭 = **약 20스텝**, 로컬 2.1분.
  배포할 게 아니라 다시 만들면 된다. "수 분" 이라는 추정에 리랭커 ONNX 변환이
  섞여 있었는데 그건 임베딩 게이트에 필요 없다
- "LLM 과금" → RAGAS 를 내리니 사라졌다

**묶어놓은 착수 조건은 실제보다 커 보인다.** 미룰 땐 이유를 항목별로 쪼갤 것.

### 문턱은 재학습 변동을 재고 정했다 — 재는 법이 함정이었다

그냥 두 번 돌려 비교하려 했는데, `finetune_embedding` 은 시드가 42로 고정돼 있다.
**같은 박스에서 반복하면 변동 0 이 나오고 그건 측정이 아니라 구조다.** 세 갈래로
나누고 셋 다 **가중치 파일 해시**를 같이 찍었다(학습 7회, LLM 0회).

| 팔 | 가중치 해시 | recall@1 | recall@5 | mrr |
|---|---|---|---|---|
| 같은 시드 x2 | **동일** | 0.3889 | 0.6111 | 0.5099 |
| 시드 x3 | 셋 다 상이 | 0.3889~0.4074 | 0.5556~0.5926 | 0.4999~0.5126 |
| 스레드 1 vs 2 | **상이** | 0.3889 | 0.6111 | 0.5099 |

- 같은 시드는 **비트 단위로 같은 모델**을 낸다 — 대조군이 없었으면 "변동 0" 을
  안정성으로 읽었을 것이다
- **스레드 수를 바꾸면 가중치는 달라지는데 지표는 넷째 자리까지 같다.**
  `mean_rank` 까지 같으니 순위 순열이 통째로 안 바뀌었다 — 머신이 달라지는 축이
  시드 축보다 훨씬 작다는 실측이다
- 부수 소득: **"지표가 같다" 와 "모델이 같다" 는 다른 명제다.** 해시를 안 찍었으면
  몰랐다

하한 = 관측 최솟값 − 2×변동폭 → **0.35 / 0.48 / 0.47**. 2배는 유도가 아니라
판단이고(표본 3개의 범위는 참값을 과소추정한다), 반올림은 전부 내림이다.

**잡는 회귀의 크기를 과장하지 않는다** — 코퍼스 훼손·베이스 모델 오지정·트리플
깨짐 같은 큰 회귀는 잡고, 미세한 저하는 못 잡는다.

### 착수 전 교차 확인

문서에 기록된 Phase 4 수치(recall@1 0.1481→0.3889, MRR 0.3005→0.5099)를 다시
재서 **넷째 자리까지 일치**를 확인했다. 다만 이건 **평가의 결정성**만 증명한다 —
같은 모델 파일을 다시 잰 것이라, 재학습 쪽은 위에서 따로 쟀다.

### 검사를 만들어놓고 읽는 데서 틀렸다

실패 경로가 exit 1 인지 확인하는데 `cmd | tail` 뒤에서 `$?` 를 읽었다.
**그건 `tail` 의 종료 코드라 언제나 0** 이고, 두 가드가 정상 동작하는데 둘 다
"통과" 로 나왔다. 한글 출력이 깨져서 보기 좋게 만들려고 끼운 필터였다.

**표시용 필터가 판정 경로에 있으면 안 된다.** 사례 21 의 `grep … | head -1` 과
같은 과다. CI `run:` 스텝에서는 원리적으로 안 나는 결함이라, **손 확인이 CI 보다
약한 경우**이기도 하다. 사례 26.

테스트 257 → **267**. `test_ir_gate.py` 는 통과 케이스마다 떨어지는 케이스를
같이 넣었다 — CI 에서만 도는 검사라 잘못 만들면 초록만 보다가 회귀를 놓친다.

## 같은 날 (10) — RAGAS 경로를 실제로 밟았고, 비용 추정이 두 번 더 틀렸다

시크릿 등록 + 수동 실행으로 RAGAS 스텝을 돌렸다. **성공** — 배선이 확인됐고,
직전 항목에서 "밟지 않은 경로"라고 적어둔 한계가 해소됐다. 동시에 이 결정의
근거 수치가 두 번 더 틀린 것으로 드러났다.

| | 처음 | 1차 정정 | **실측** |
|---|---|---|---|
| 호출 수 | 216 | 648 | 약 648 |
| 소요 | (추정 안 함) | 40분 이상 | **7,160초 = 119분** |

게이트 부분은 **45초**(파인튜닝 35 + 측정 10 + 판정 0)이고 나머지 119분이 전부
RAGAS다. "매 커밋 RAGAS 게이트"는 **커밋마다 2시간짜리 잡**이라는 뜻이었다 —
게이트에서 내린 결정이 훨씬 강해졌다.

원인은 산수였다. *"질의 54 × 지표 2종 × 모델 2개"* 로 곱해 **지표당 1회**를
가정했는데, ragas 의 `ContextPrecisionWithReference` 는 소스에서
**검색된 컨텍스트마다 1회씩 순차 호출**한다. top-k=5 이므로 precision 만
54×5×2=540 이다. **입력 개수로 곱해 만든 비용 추정은, 라이브러리가 호출당
무엇을 하는지 확인하기 전에는 추측이다.**

### 리포트가 안 읽히면 리포트가 아니다

RAGAS 점수가 **로그에만 찍히고 어디에도 저장되지 않았다.** Actions 로그는 공개
저장소여도 토큰이 있어야 읽히니, 두 시간과 요금을 쓴 수치를 사실상 아무도 못
본다 — 게이트 여유폭에서 방금 고친 것과 **같은 결함**이 리포트 쪽에 그대로
있었다. 점수를 반환해 `--json` 과 실행 요약에 싣고, **"판정에 쓰지 않는다"를 표
안에 넣었다**(표만 보면 게이트처럼 읽힌다). 채점 실패율 10% 초과면 신뢰할 수
없다고 명시한다 — 기존 코드는 실패를 출력만 하고 성공분 평균을 그대로 냈다.

### `concurrency` 가 유료 실행을 죽일 뻔했다

`group: ai-quality-${{ github.ref }}` + `cancel-in-progress` 인데
`workflow_dispatch` 도 ref 가 `refs/heads/main` 이라 **push 와 같은 그룹**이다.
이 파일을 고치는 커밋을 밀면(이 파일은 자기 자신의 `paths` 에 있다) 돌고 있던
2시간짜리 실행이 취소된다. 그룹 키에 `github.event_name` 을 넣어 갈랐다.

> **취소 정책은 "같은 일의 새 버전"에만 걸어야 하는데, 그룹 키가 거친 만큼
> 서로 다른 일이 한 그룹에 묶인다.** 비싸고 반복하기 어려운 수동 실행을 자동
> 실행과 같은 취소 그룹에 두지 않는다.

### 이름을 고쳤다

잡 이름을 `ir-gate`, 스텝을 "IR 게이트"로 줄여 썼다가 **런타임에 검색 여부를
결정하는 장치**로 읽혔다. 그렇게 읽힐 만하다 — 이 프로젝트에 그런 게 셋이나
있다(시맨틱 캐시 · 도메인 게이트 · Intent Router). IR 은 Information
Retrieval 이고 여기서 재는 것은 **빌드 시점의 검색 품질**이다.
`search-quality-gate` / "검색 품질 측정" / "검색 품질 게이트 판정" 으로 바꿨다.
스크립트 파일명은 그대로 뒀다 — 코드 안에서는 "IR 지표"가 이미 정의된 어휘다.

**저자가 헷갈리게 줄인 이름은 읽는 사람도 헷갈린다.** 맥락이 없는 곳(CI 화면)만
고치는 게 표면 대비 효과가 크다.

테스트 267 → **270**.

## 같은 날 (11) — 진행 상황 스트리밍(SSE): 실측이 설계를 두 번 고쳤다

복합 질의는 7~25초가 걸리는데 화면은 **고정 문구 하나**를 20초 내내 띄웠다.
진행 중인 것과 멈춘 것이 구분되지 않았다.

**흘리는 것은 토큰이 아니라 단계다.** 그 7~25초의 정체는 답변 생성이 아니라 그
앞의 도구 호출이라, 토큰만 흘리면 마지막 1~2초만 빨라 보인다. 게다가 토큰
스트리밍은 `chat()` 을 통째로 바꿔야 하고 그러면 프로바이더 번역을 다시 짜야
한다(ADR-0042). 단계는 이미 있는 계측점에 콜백 한 줄이다.

### 짜고 나서 재보니 두 번 틀렸다 — 둘 다 코드로는 안 보였다

**① 가장 긴 대기가 진행 표시에 안 잡혔다.** 도구 호출이 *끝날 때*만 알렸더니:

```
0.27s  branch
6.86s  tool search_items    <- 6.6초 무음
```

그 6.6초가 LLM 이 도구를 고르는 시간이고, **진행 표시를 넣은 이유가 정확히 그
구간**이었다. `thinking` 을 LLM 호출 앞에 넣어 덮었다.

**② 라벨이 11초 동안 틀린 말을 했다.** 다시 재니 `thinking → tool` 이 11.12초인데,
응답의 **`agent_tool_ms` 가 11150.4** 였다 — 그 구간은 생각이 아니라 도구 실행
(콜드 상태의 임베딩·리랭커 로딩)이었다. 화면엔 내내 "도구를 정하는 중"이 떠 있었다.
이벤트를 *끝난 것*에서 **시작하는 것**으로 바꿨다. 실패만 한 번 더 알린다 —
성공은 다음 줄이 뜨는 것으로 드러나지만 **실패는 말하지 않으면 안 보인다.**

> 둘이 같은 뿌리다. 진행 표시의 의미는 "무엇이 끝났나"가 아니라 **"지금 무엇을
> 하고 있나"**다. 그리고 **그 답은 재봐야 안다** — `timings` 가 이미 답을 갖고
> 있었는데(`agent_llm_ms`/`agent_tool_ms` 를 따로 재는 이유가 그것이다) 이벤트를
> 붙일 때 그걸 안 읽었다.

**덤: 지배 구간은 워밍 여부로 뒤집힌다.**

| | routing | 지배 구간 | 전체 |
|---|---|---|---|
| 콜드 | 0.98s | **도구 11.1s** | 16.4s |
| 워밍 | 0.24s | **LLM 3.6s** | 5.2s |

한쪽만 보고 "에이전트는 도구가 병목"이라 적었으면 틀렸을 것이다.

### 그 밖의 결정

- **캐시 적중도 스트림으로 감싼다** — 안 그러면 프론트에 코드 경로가 둘 생긴다.
  아끼는 건 25.9ms 다
- **기존 엔드포인트를 안 갈아치운다** — 부하 하네스와 배포 검증이 거기 걸려 있다
- **`EventSource` 불가** — `Authorization` 을 못 붙이고, 토큰을 쿼리로 옮기면
  nginx 접근 로그에 남는다. `fetch` + `ReadableStream`
- **스트림이 열린 뒤의 오류는 상태 코드가 아니라 페이로드다.** 헤더가 이미 나갔다

### 검증 도중 함정 두 개를 그대로 밟았다

**`until` 루프의 종료 조건을 거꾸로 썼다** — 완료되지 않았을 때 0을 반환하게 해서
즉시 빠져나왔고, "완료됨"으로 읽을 뻔했다.

**서버를 재시작했는데 옛 프로세스가 포트를 잡고 있었다.** `curl` 은 200을 냈다 —
이 저장소가 두 번 기록한 *"포트가 답한다 ≠ 내가 띄운 게 답한다"* 다. 새 uvicorn 은
`[Errno 10048]` 로 죽어 있었다. 이후로는 **로그의 PID 와 포트 보유 PID 를 비교**한다.

프론트 번들 **+0.64KB gzip**(변경 전후 각각 빌드해서 실측). 테스트 270 → **281**.

## 같은 날 (12) — 일일 한도가 캐시 적중까지 세고 있었다

SSE 가 같은 리미터를 타는지 확인하다가 **원래 있던 어긋남**을 찾았다.

`limit_assistant` 은 FastAPI 의존성이라 핸들러보다, 따라서 **캐시 조회보다** 먼저
돈다. 그래서 두 한도가 다 적중을 셌다. 두 경로가 서로 다르진 않았으니 SSE 가 만든
문제는 아니고, 파이프라인 문서에 한 줄 적혀 있기도 했다 — *"캐시 조회보다 앞이라
적중도 카운트된다"*. **그런데 그건 `Depends` 순서의 결과를 서술한 것이지 결정이
아니다.** ADR-0024·0031 어디에도 근거가 없었다.

두 한도의 목적이 다르다.

| | 목적 | 캐시 적중 | 세는 시점 |
|---|---|---|---|
| **20회/분** | 부하·남용 차단 | **센다** | 요청 **앞** |
| **50회/일** | **LLM 비용** | **안 센다** | 응답 **뒤** |

**이론이 아니라 실제로 닿던 경로다.** ADR-0037 이 배지를 정직하게 유지하려고
`staleTime` 을 일부러 안 걸었고 `refetchOnMount` 는 기본 `true` 라, **아이템
상세에 들어갔다 돌아올 때마다 재요청**이 나간다. 서버는 캐시로 25.9ms 에 답하는데
하루 50회는 그렇게 소진된다.

### 조용히 사라질 수 있는 자리 둘

- **검사와 증가가 다른 키를 쓰면 한도가 없어진다** — 검사는 영원히 0을 읽고
  증가는 아무도 안 보는 카운터를 올린다. 정상 응답만 나온다. `_daily_key()`
  하나를 양쪽이 쓰게 하고 테스트로 박았다
- **`_peek` 는 올리기 전에 보므로 `_hit` 과 부등호가 하나 다르다**(`<` vs `<=`).
  그대로 옮겨 적으면 한도가 1 늘어난다

그리고 **두 라우트가 `_ask_metered()` 하나만 부르게** 묶었다. 규칙이 갈라지면
스트리밍 경로가 곧 상한 우회로다 — 소스 스캔으로 고정했다.

### 실측 (로컬 Redis, FAQ 질의라 LLM 0회)

| | `cache.hit` | 일일 카운터 |
|---|---|---|
| **미적중 x2 (대조군)** | False | 0 → **1 → 2** |
| **적중 x3** | True | **2 → 2 → 2** |

**대조군이 요점이다.** 처음엔 적중만 3회 재고 "카운터 0, 통과"로 넘어갈 뻔했는데,
그건 *"적중이 안 센다"* 와 *"증가가 통째로 고장"* 을 구분하지 못한다.

> 그 과정에서 401 을 만나 **본문부터 파싱하다 `KeyError: 'cache'`** 를 봤다.
> 토큰이 10분짜리라 만료된 것이었다. 이 저장소의 사례 21 — *"본문을 파싱하기 전에
> HTTP 코드를 봐라"* — 그대로다.

테스트 281 → **292**.

## 같은 날 (13) — 배포 검증: 프록시가 두 겹이었다

`load/verify-sse.sh` 가 **첫 실행에서 진짜 버퍼링을 잡았다.** 이벤트 8건이 전부
마지막 0.27초에 몰려 왔다(전체 13.98초, 비율 0.98). 만든 이유가 정확히 그것이다.

원인은 내가 "프록시 한 겹"을 가정한 것이었다.

**nginx 는 `X-Accel-Buffering` 을 존중하면서 동시에 지운다.**
`Date`·`Server`·`X-Pad`·`X-Accel-*` 는 업스트림 응답에서 클라이언트로 넘기지 않는
기본 숨김 목록이다. 우리 nginx 하나면 문제가 없는데, 배포가 `https` 이고
`gimp-web` 은 평문 80 을 내므로 **TLS 를 끝내는 호스트 nginx 가 앞에 하나 더**
있다. 우리가 헤더를 소비해 지우니 앞단은 아무 지시도 못 받고 자기 차례에
버퍼링했다. `proxy_pass_header X-Accel-Buffering;` — 존중과 전달은 별개다.

**같은 검사를 사슬의 두 지점에서 돌려 층을 짚었다.**

| | 비율 | 헤더 | 판정 |
|---|---|---|---|
| `localhost:8081` (우리 nginx 만) | **0.01** | **있음** | 3/3 |
| `https://…duckdns.org` (+ 앞단) | **0.02** | **없음** | 3/3 |

**B 에서 헤더가 사라진 것이 실패가 아니라 증거다** — 앞단이 받아 소비했다는 뜻이고,
그래서 버퍼링을 껐다. 한 지점만 재면 "버퍼링된다"까지가 끝이고 어느 프록시인지는
추측이 된다. **소비되는 헤더는 사라지는 위치로 추적한다.**

그리고 내 판정 하나가 **참이 될 수 없는 것**이었다 — 헤더 존재를 FAIL 로 걸었는데
프록시 뒤에서는 없는 게 정상이다. 앱이 붙이는지는 `test_assistant_stream.py` 가
소스로 고정하므로, 배포 검사가 판정할 것은 **실제로 나눠서 도착하는가** 하나다.

수신 순서(B, 워밍 4.39초):

```
0.08s  routing → branch → thinking
0.82s  tool search_items
1.95s  thinking
2.71s  tool forecast_item_price
4.39s  done
```

### 이 라운드의 배포 검증에서 내가 낸 오류 여섯

| | 증상 | 이미 있던 답 |
|---|---|---|
| 명령에 생략 기호 `...` | `unknown docker command` | — |
| `git pull` 누락 | 코드가 안 감 | 로그의 `CACHED [COPY app app]` |
| `restart backend` 누락 | 401 | 3-a 가 이유를 적어둠(db-seed) |
| 실행 비트 `100644` | Permission denied | `gradlew` 전례(ADR-0021) |
| `python` 호출 | 우분투에 없음 | 배포-절차.md 가 적어둠 |
| 준비 대기가 `/` | 502 | 로그의 `backend Restarting` |

**여섯 중 넷은 답이 이미 출력이나 문서에 있었다.** 이 세션 앞부분(ADR-0040~0042)의
"판정에 쓸 신호가 실제로 도달하는지 확인하지 않았다"와 같은 형태이고, 이번엔
**남이 이미 적어둔 것을 안 읽은 것**이 더 컸다. 사례 27이 이 파일에서 가장 긴
항목이 된 이유다.
