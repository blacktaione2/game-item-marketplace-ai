# 2026-08-08

## 사각지대를 배포본에 태웠고, 라운드가 줄었다

전날 평가셋을 늘리다 찾은 「아이템 어휘를 단 게임 메커니즘 질문」 사각지대를
정면으로 고칠지 정하려고 **먼저 실측**했다. 로컬이 아니라 배포본에 태웠다 —
분류기 가중치가 학습마다 달라 로컬 라우팅은 배포된 동작이 아니다(ADR-0039 기록).

### 8건 중 실제 결함은 2건이었다

| 분기 | 건수 | 결과 |
|---|---|---|
| `faq_smalltalk` | **4** | **이미 올바르게 거절** — 범위를 밝히며 사양, LLM 0회 |
| `compound` | 1 | 되묻는다 |
| `item_search` | 1 | 라벨 보류 (아래) |
| **`price_forecast`** | **2** | **동문서답** — 무관한 아이템의 시세 |

### 2차 방어선이 설계 주장에서 실측으로 바뀌었다

두 동문서답 모두 **진짜 아이템 이름을 밝혔다** (`'+9 강화 롱소드'의 최근 거래가는
29,260원…`). 질의의 주어(`이 옵션`, `세트 효과`)를 채택하지 않았다 — ADR-0039
결정 4가 의도대로 작동한다. **거짓말이 아니라 동문서답**이다.

### 내가 늘린 평가셋에 결함이 있었다

ADR-0039 는 원래 38건에 대해 "어느 분기로 가는지 먼저 무료로 쟀다" 는 단계를
밟았다. **전날 추가한 3건에는 그 단계를 안 밟았다.** 둘이 `faq_smalltalk` 로 가
게이트에 닿지도 않는다.

**그런데 분모에서 뺄 수는 없다.** 로컬/배포 라우팅을 대조하니 **6/8 만 일치**했고
어긋난 둘은 전부 분류기 판정이었다(룰 판정 3건은 완전 재현). *"게이트에 닿는가"*
는 질의의 안정된 속성이 아니다. 그래서 미검출 옆에 **분기를 같이 찍는** 것으로
바꿨다.

> 같은 이유로 ADR-0039 의 커버리지 논증(22+7+9=38/38)도 **분기별로** 읽어야 한다.
> 보장은 "어느 분기로 가든 뭔가가 받는다" 이지 "이 9건이 FAQ 로 간다" 가 아니다.

### 라벨 하나 보류

`강화 확률 올리는 방법 있어?` — *"방법"* 을 물었으니 플레이 질문이라는 읽기와,
거래소의 정직한 답이 "그 확률을 올려주는 물건을 판다" 라는 읽기가 **둘 다
성립한다**(배포본이 성공률 70% 주문서를 돌려줬다). 채점 세트에서 빼고
`AMBIGUOUS_LABEL` 에 이유와 함께 남겼다 — import 가드가 재유입을 막는다.

### 남은 2건은 고치지 않는다

`_forecast_branch` 가 `run_search(size=1)` 의 1등을 **얼마나 약하게 맞았든 그대로
쓴다.** 필요한 건 주제 판정이 아니라 관련성 판정이고, 그건 **ADR-0018 이 이미
기각한 문제**다 — 크로스 인코더 로짓은 한 질의 안에서만 의미가 있다.

근거 셋이 겹쳐서 안 연다: 8건 중 2건, 결과가 거짓이 아님, 기전이 기각된 접근과
겹치고 **해결 방법 자체가 불투명**. 대신 로드맵에 **"ADR-0018 과 같은 뿌리"** 로
등록했다 — 표면이 단순해서("점수 낮으면 버리면 되지") 다시 시작하기 쉬운 문제다.

## 같은 날 (2) — `무속성` 을 고쳤다. 프롬프트를 건드리지 않고

로드맵에 "평가셋 구축이 선행" 으로 1주일 넘게 묶여 있던 항목이다. **평가셋을
만들었더니 프롬프트 문제가 아니었다.**

### 먼저 프롬프트를 읽었다

`query_understanding.py` 에 **이미** 이렇게 적혀 있었다.

```
- 무속성/속성 없는 -> "무속성"
- null("속성 조건 없음")과 "무속성"("속성이 없는 아이템만")은 다릅니다.
```

**정확히 옳은 말로 이미 지시받았는데 42/50 을 틀린다.** 그리고 여기는 프롬프트
한 줄로 97.5% → 22% 를 겪은 바로 그 자리다. 직전 라운드에서도 프롬프트 변형 셋이
연달아 기각됐다 — 네 번째로 같은 무기를 드는 건 판단이 아니라 관성이다.

### 평가셋 39건 — `미언급` 무리가 핵심이다

| 무리 | 정답 | 없으면 |
|---|---|---|
| 무속성 (14) | `"무속성"` | 결함이 안 보인다 |
| 타속성 (8) | 해당 속성 | 다른 속성을 덮어써도 모른다 |
| **미언급 (10)** | `None` | **"전부 무속성" 이 만점** |
| 저항 (4) | `None` | `"화염 저항 방어구"` 가 화염으로 걸린다 |
| 부정형 (3) | `None` (한계) | 정반대를 주는 걸 못 잡는다 |

`"속성 좋은 무기"`(낱말은 있고 답은 `None`)와 **일부러 미수록인** `"속성 안 붙은
신발"` 을 넣었다. 전부 맞는 평가셋은 한계를 못 보여준다.

### 결과

| 무리 | 1차 | 2차 | 오채움 |
|---|---|---|---|
| 무속성 | 62% → **93%** | 86% → **93%** | 0 → 0 |
| 타속성·미언급·저항·부정형 | **전후 동일** | **전후 동일** | **0 → 0** |

**정확도보다 결정성이 더 큰 소득이다.** 기준선이 62% ↔ 86% 로 흔들리는데 후처리
뒤는 두 번 다 93%, 잔여 오답까지 같은 두 질의다.

### 내 정규식이 처음에 틀렸다

```python
r"무속성|속성\s*없...아닌"    # 괄호가 없다
```

`|` 가 가장 약하게 묶여서 **`무속성` 하나만으로 부정형 판정**이 된다. 그러면 모든
무속성 질의가 부정형으로 걸려 **후처리가 한 번도 안 걸린다.** 증상은 "고쳤는데
아무것도 안 변했다" 다. 실행 전에 읽다가 잡았고, 회귀 테스트로 박았다.

### 사전 등록 기준 둘이 실패했고 고쳐 쓰지 않았다

- **타속성 95%** — 전후가 같다(88% → 88%). 의도는 *"후처리 때문에 나빠지면 안
  된다"* 는 **상대** 기준이었는데 **절대** 문턱으로 썼다. **두 라운드 전에
  held-out 기준을 전부 대조군 상대값으로 쓴 이유가 정확히 이건데 여기서 안 했다.**
- **무속성 95%** — 부족분이 전부 일부러 넣은 미수록 표현이다. 14건 중 1건 = 7.1%
  이므로 **처음부터 만족 불가능**한 기준이었다.

ADR-0028 이 한 대로 실패한 채 남기고, 채택 근거를 안전 기준 셋(오채움 = 0, 두 실행
통과) + 손댄 16건이 전부 정답 + 회귀 0 + 두 실행 일치에 뒀다.

### 덤으로 찾은 것

`"어둠 속성 로브"` 가 `null` 을 낸다 — **6/6.** 프롬프트에 `어둠 -> 암흑` 이
있는데도 그렇다. 무속성과 같은 가족인데 **같은 처방을 쓸 수 없다** — `암흑` 을
낱말로 채우면 `"암흑 저항 목걸이"` 가 깨진다. 별도 항목으로 등록했다.

### 남긴 것

- `app/corpus/element_queries.py` (39건), `scripts/evaluate_element_extraction.py`
- `fill_missing_element()` + 테스트 26건 — **전부 LLM 없이 돈다**
- ADR-0040, 로드맵 체크박스 해제, CLAUDE.md

## 같은 날 (3) — 프로바이더가 죽었을 때 무엇을 돌려줄지 정했다 (ADR-0041)

계획서에 있는데 없는 것을 찾다가 `circuit`·`resilience`·`fallback` 이 코드에
**0건**인 걸 봤다. 그런데 장애 시 동작이 **비대칭**이었다.

| 분기 | OpenAI 장애 시 |
|---|---|
| 검색 · FAQ | 산다 (각각 폴백 / LLM 0회) |
| **시세 · 이상거래 · 에이전트** | **500** |

검색이 사는 건 설계가 아니라 fail-open 두 개가 우연히 겹친 결과다.

### 그 시점에 답은 이미 손에 있었다

설명 호출이 터질 때 시세 분기는 예측 결과를, 이상거래 분기는 판정과 기여도를
**이미 계산해뒀다.** 없는 건 산문뿐인데 500 을 냈다. 그래서 ADR-0036 과 같은
처방으로 내려앉게 했다 — 결정 단계가 가진 값으로 문장을 만든다.

- 사과하지 않는다. 답은 다 들어 있고 `degraded` 는 운영자용이다
- 프롬프트가 조건부로 붙이던 고지(콜드스타트 추정, 합성 코퍼스)를 그대로 붙인다.
  빠지면 **모델이 살아 있을 때만 정직한** 응답이 된다
- `llm_calls` 를 줄인다(시세 3→2, 이상거래 1→0). 안 줄이면 안 나간 돈을 센다
- `outcome="degraded"` — **500 이 안 나므로 다른 데서는 안 보인다**
- 에이전트는 손대지 않았다. 거기선 LLM 이 곧 분기라 정직한 500 이 맞다

### 덤으로 찾은 것 — 500 이 예외 문자열을 내보내고 있었다

```python
detail=f"요청 처리 실패: {e}"
```

백엔드는 `include-stacktrace: never` 로 처음부터 막아뒀는데 AI 서버만 안 맞춰져
있었다. **한쪽만 선언된 설정은 결정이 아니라 누락이다.**

그리고 **하나만 고치면 안 됐다** — 훑어보니 **다섯 라우터 중 다섯**이 전부
그랬다. 전부 일반 메시지로 바꾸고 `logger.exception` 을 남겼다. 소스를 훑는
테스트로 고정했고, **그 검사가 헛돌지 않는지 일부러 틀린 문자열로 확인**했다.

### 하지 않은 것

**Claude 폴백.** API 키가 없어 경로를 밟아볼 수 없다. 배선만 하고 "됐다" 고
적는 건 ADR-0039 에서 값을 치른 실수다(MCP 안내문이 한 번도 안 밟혔다).

순서도 이쪽이 맞다 — 폴백이 생겨도 **양쪽이 다 죽는 경우**는 남고, 그때 필요한
게 지금 만든 내려앉기다. 서킷브레이커는 이 위에 얹는다.

테스트 203 → **228**, 전부 LLM 없이 돈다.

## 같은 날 (4) — Claude 폴백을 실제로 만들었다 (ADR-0042)

앞 항목에서 *"API 키가 없어 경로를 밟아볼 수 없다"* 고 적었는데 **확인 안 하고 한
말이었다.** 사용자가 알려줘서 보니 키는 있었다.

그런데 보니 **폴백이 지금 상태로는 동작할 수 없는 이유**도 같이 나왔다.

| 파일 | `ANTHROPIC_API_KEY` |
|---|---|
| 루트 `.env` | **있음** |
| `ai/.env` | **없음** |

CLAUDE.md 가 이미 적어둔 함정이다 — 루트는 docker-compose 용이고 앱은 `ai/.env` 를
읽는다. 게다가 코드에 `anthropic` 이 0건이라 **키가 어디 있든 아무 일도 없었다.**

> **"없다" 는 "안 봤다" 와 다르다.** 결론은 우연히 맞았고 근거는 틀렸다.

### 이 라운드의 진짜 위험은 형식 번역이었다

`LLMClient` 는 중립인데 **에이전트 루프가 OpenAI 메시지 형식을 그대로 쓴다.**
인터페이스만 맞추면 `complete()` 는 되고 **에이전트만 조용히 깨진다** — 폴백이
가장 필요한 순간에.

- `system` 메시지 → 최상위 파라미터
- `assistant.tool_calls` → `tool_use` 블록
- `{"role":"tool"}` → `user` 안의 `tool_result` 블록
- **연속된 도구 결과는 한 메시지로 합친다** — 안 합치면 도구 하나일 땐 되고 둘일 때 400

### 서킷 브레이커는 지연 축 때문이다

예외만 잡아 넘기면 장애 동안 **모든 요청이 1차 타임아웃을 먼저 문다.** RabbitMQ
때 겪은 그것이다(기본 60초 → "구매는 성공하는데 1분"). 연속 3회 실패면 60초 동안
1차를 건너뛴다. 새 의존성 없이 카운터 하나와 타임스탬프 하나.

둘 다 죽으면 **1차 예외**를 올린다 — 2차 예외로 바꿔치면 진단이 엉뚱한 데를 본다.
그 위를 ADR-0041 의 내려앉기가 받아서 두 겹이 순서대로 선다.

### 실제로 밟았다 — 다섯 항목

| | 확인 | 결과 |
|---|---|---|
| 1 | Claude 단독 호출 | `"서울"` |
| 2 | 1차 죽음 → 폴백 | `"서울"` |
| 3 | 임계값에서 1차를 안 부르는가 | 5회 중 **3회만** |
| 4 | **질의이해 JSON 파싱** | `element=화염 subcategory=검 price_max=30000` |
| 5 | **에이전트 도구 호출** | `search_items(tenant_code, query)` |

4·5 가 핵심이었다. 1~3만 보고 끝냈으면 *"폴백은 되는데 검색과 에이전트만 안 되는"*
상태를 채택할 뻔했다.

테스트 228 → **248**, 추가분은 네트워크 없이 돈다.

> **배포 서버의 `ai/.env` 에도 키를 넣어야 한다.** 안 넣으면 기동 로그에
> "폴백 없음" 이 남고 동작은 지금과 같다 — 조용히 깨지지는 않는다.

## 같은 날 (5) — 배포했는데 안 고쳐진 것처럼 보였다. 캐시였다

`"무속성 검 찾아줘"` 에 불꽃의 대검이 그대로 나왔다. 코드가 틀렸거나 배포가 안 된
것처럼 보였는데 **둘 다 아니었다.**

화면 관측 패널이 답을 들고 있었다 — `캐시 적중 (exact)` · `LLM 호출 0회`.
**배포 전에 저장된 응답이 재생된 것이다.** 답변 문구도 증거였다: 고쳐졌다면
`검 · 무속성 조건으로` 인데 `검 조건으로` 뿐이었다.

### 원인 둘

**하나.** `cache_version` 을 안 올렸다. ADR-0040 이 *"응답 모양은 그대로라 올릴
필요 없다"* 고 **명시적으로 판단했는데**, 설정 주석은 **모양과 내용 둘 다**라고
말하고 있었다. 필터가 하나 더 걸리면 같은 질의가 다른 결과 집합을 낸다 — 그게
내용 변경이다. 주석의 절반만 읽었다. **v2 → v3.**

**둘.** 내가 준 확인 절차가 그 실패를 구분하지 못했다. *"불꽃의 대검이 안 나와야
한다"* 는 참/거짓 하나뿐이라, 거짓일 때 **후처리 미적용 / 배포 누락 / 캐시 재생**
셋을 못 가른다. 이 저장소가 반복해 적은 *"판정에 쓴 값을 전부 출력에 넣어라"* 를
**내가 준 절차에는 적용하지 않았다.** 사례 24 로 남겼다.

### 고친 것

- `cache_version` v3
- 확인 절차를 **두 신호로**: ① 배지(`캐시 적중`/`LLM 호출`) ② 답변 문구
- 그 문구를 테스트로 고정(`TestTheUserVisibleSignal`) — 진단에 쓰는 문자열이
  말없이 바뀌면 다음 사람이 같은 데서 헤맨다

테스트 248 → **250**.

## 같은 날 (6) — 배포가 안 갔고, 그다음엔 로그가 안 나왔다

두 건 다 내 실수다.

**하나: 푸시를 안 했다.** 세션 내내 커밋만 하고 `git push` 를 한 번도 안 한 채로
배포를 세 번 안내했다. 서버의 `git pull` 이 `Already up to date.` 라고 답했고
빌드가 전 단계 `CACHED` 였는데, **내가 준 확인 절차는 그걸 안 봤다** — 사례 24 와
같은 실패의 재발이다(원인 후보가 여럿인데 신호가 하나).

**둘: 로그 레벨을 잘못 골랐다.** ADR-0042 에 *"어느 쪽이든 기동 로그에 남는다"* 고
적었는데 둘 다 `logger.info` 였다. **이 앱은 로깅을 설정하지 않는다** — 파이썬 루트
기본값이 `WARNING` 이라 그 줄은 어디에도 안 나온다. `docker logs | grep` 이 빈
결과를 냈고, 그건 **"폴백 없음" 과 "로그가 안 보임" 을 구분해주지 못했다.**

### 고친 것

- **없음 = `warning`.** 레벨도 내용상 맞다 — 폴백 없이 도는 것은 약화된 구성이다
- **`/health` 에 `llm_fallback`**(bool) + 모델명. **키 자체는 안 싣는다.**
  로그 레벨에 기대지 않고 확인할 수 있는 자리를 만든 것이다
- 백엔드 `AiHealthResponse` 의 *"일치해야 한다"* 주석을 정정했다 — **부분집합**이다.
  그렇게 적혀 있으면 AI 쪽에 필드를 더할 때 백엔드까지 재빌드하게 된다

> **로그로 확인하라고 안내하려면 그 레벨이 실제로 출력되는지부터 확인해야 한다.**
> "판정에 쓴 값을 출력에 넣어라" 의 인프라 버전이다 — 값을 넣어도 통로가 막혀
> 있으면 없는 것과 같다.

테스트 250 → **253**.

## 같은 날 (7) — 폴백이 만든 지표 모호함을 메웠다

ADR-0042 가 스스로 등록한 구멍을 닫았다. **그런데 처음 적은 이유가 틀렸다.**

"서킷 상태가 어디에도 안 남는다" 고 썼는데, `logger.warning("1차 LLM 실패 —
폴백으로 넘긴다")` 는 실제로 출력된다. **남기는 하고 집계가 안 됐다.** 그 이유만
으로는 약하다 — Prometheus 는 옵트인이라 평소에 돌지도 않는다.

### 진짜 이유는 내가 만든 드리프트다

`ai_llm_calls_total` 은 *"이 요청이 LLM 을 몇 번 썼나"* 를 센다. 프로바이더가
하나일 땐 그게 곧 OpenAI 사용량이었는데, **폴백이 붙는 순간 그 해석이 깨졌다.**
어디에 청구됐는지 말해주지 않는다.

`ai_llm_provider_calls_total{provider, outcome}` — 라벨 2×2 = 4 시계열.

- **계측을 각 클라이언트 안에** 둔다. 래퍼에 두면 키가 없는 구성에서 아무것도
  안 잡힌다 — 프로바이더가 하나뿐이라 더 취약한 쪽이다
- **`record_response()` 로는 표현이 불가능하다.** 에이전트 한 요청이 `chat()` 을
  다섯 번 부르고 그중 둘만 폴백일 수 있다 — 응답 모양이 아니다. 계측점 원칙의
  두 번째 예외이고, `rate_limited_total` 처럼 이유를 코드에 적어뒀다
- **게이지는 안 만들었다.** 카운터에서 읽히고, 볼 대시보드가 없다

덤으로 교차 검증이 생겼다. `ai_llm_calls_total` 은 응답의 `llm_calls` **상수**에서
오고 새 카운터는 **실제 호출**을 센다 — **어긋나면 그 상수가 틀린 것**이다.
ADR-0039·0041 에서 세 번 손으로 고친 값이라 마침 필요한 검증이다.

테스트 253 → **257**.
