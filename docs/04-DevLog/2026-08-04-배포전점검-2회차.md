# 2026-08-04 (3) — 배포 전 점검 2회차: 간판 기능을 검증한 적이 없었다

1회차(ADR-0033)를 고친 뒤 같은 절차를 한 바퀴 더 돌렸다. 이번에는 **1회차에서 얕게 본
영역**에 무게를 뒀고, 그중 하나가 **테넌트 격리** — 이 프로젝트의 간판인데 실제로
두 테넌트를 만들어 확인한 적이 한 번도 없었다.

**만들자마자 결함이 나왔다.**

## 나온 것 셋

| | 증상 | 실제 원인 |
|---|---|---|
| **F1** | 깨진 JSON 로그인이 400이 아니라 **401** | `/error` 가 보안 체인에 걸림 |
| **F2** | 두 테넌트 동명 계정 → **401** (영구 로그인 불가) | `findByUsername` 이 제약과 불일치 |
| **F3** | 5바이트 `JWT_SECRET` 으로 **healthy 기동** 후 로그인 401 | 길이 검사가 어디에도 없음 |

**셋 다 fail-closed다** — 데이터가 새거나 권한이 뚫리지 않는다. 문제는 **전부 진단이
불가능해진다**는 것이다. F1 때문에 F2·F3이 똑같이 "비밀번호가 틀렸다"로 보였다.

## F1 — 한 줄의 부재가 다른 결함을 가리고 있었다

Spring Security 6+는 ERROR 디스패치도 필터링한다. `/error` 가 허용 목록에 없으면
Boot의 에러 포워드가 `anyRequest().authenticated()` 에 걸려 **401**이 된다.

대조군이 결정적이었다 — **유효 토큰으로 없는 경로를 치면 정상적으로 404**다. 즉
마스킹은 비인증 경로에서만 일어난다.

## F2 — 스키마는 처음부터 (b)를 선택했는데 코드가 안 지켰다

`users` 제약은 **`(tenant_id, username)`** 인데 조회는 `findByUsername` 하나였고,
리포지토리 javadoc에 이렇게 적혀 있었다:

> `데모 계정이 한 테넌트뿐이라 username 은 전역 유일하다.`

**스키마가 보장하지 않는 가정이다.** 두 번째 테넌트에 `buyer_lee` 를 넣자
`NonUniqueResultException` → 401.

전역 유니크(a)가 아니라 **테넌트 명시(b)** 를 택했다. (a)는 **설계를 버그에 맞추는
것**이고, 나중에 테넌트가 둘이 되면 (b)를 그때 하면서 운영 DB 제약 마이그레이션까지
얹게 된다. ADR-0033의 XFF와 같은 모양이다 — 그때도 "백엔드가 `X-Real-IP` 를 읽게"가
아니라 "nginx가 XFF를 붙이게"를 택했다.

## F1이 곧바로 드러낸 것 — 검사 둘이 틀린 이유로 통과하고 있었다

`/error` 를 열자 `verify-auth.sh` 판정 2의 두 건이 **즉시 실패했다.**

한글 인자(`"틀린값"`, `없는계정`)가 cp949로 재인코딩돼 **깨진 JSON**이 나갔고, 서버는
정직하게 400을 냈는데 마스킹이 401로 바꿔놨다. 검사는 401을 기대하므로 통과했다.

**이 두 검사는 비밀번호 검증을 한 번도 재본 적이 없다.** 뮤테이션으로도 실패
케이스로도 안 잡혔을 것이다 — **다른 결함을 고치자 저절로 드러났다**(사례 14).

## 배운 것

**1회차에서 "깨끗하다"고 본 영역이 실은 검증된 적 없는 영역이었다.** 코드를 읽어서는
안 보였다 — 시드 테넌트가 하나뿐이라 **데이터가 그 성질을 발현시키지 않았기** 때문이다.

> 테스트가 없는 성질은 "동작한다"가 아니라 **"확인한 적 없다"** 이다.
> 데이터가 결함을 가리는 경우, 데이터를 만들어야 보인다.

그리고:

> **오류를 뭉개는 계층이 하나 있으면 그 아래 결함들이 전부 같은 얼굴을 한다.**
> 결함을 찾기 전에 **결함이 자기 이름으로 보고되는지**를 먼저 봐야 한다.
