# 2026-08-07 — 배포된 걸 브라우저로 써보다가 결함 둘

배포 자체는 이틀 전에 끝났다. 자동 검증 38/38 과 공개 경로 10/10 이 통과했고,
남은 건 "실제로 써보기"였다. **써보자마자 나왔다.**

## 발견 경로 — 검사가 아니라 사용

점검을 A~H 단계로 나눠 순서대로 밟았다.

- **A(세션)·B(4분기)**: 통과
- **C(캐시)**: 같은 질문을 두 번 했는데 두 번 다 `캐시 미적중`, `LLM 2회`

C 가 걸렸다. 자동 검사가 전부 통과한 배포에서다.

## 결함 1: ai 컨테이너가 Redis 비밀번호를 못 받고 있었다

```yaml
# docker-compose.yml — ai 서비스
REDIS_URL: redis://redis:6379/0      # 있음
# REDIS_PASSWORD 없음                ← 코드 기본값 gimp_local_pw 로 붙는다
```

백엔드는 같은 파일에서 **이미 받고 있었다.** AI 만 빠졌다.

### 로컬에서 안 보이는 이유가 `RABBITMQ_HOST` 와 다르다

`localhost` 는 로컬에서 **맞는 값**이라 컨테이너로 옮길 때 깨진다. 이번 건은
`.env.example` 의 값이 하필 코드 기본값과 **같아서**(`gimp_local_pw`) 로컬에서
우연히 맞았다. 깨지는 조건이 컨테이너화가 아니라 **비밀번호 교체**이고, 그건
실배포에서 처음 일어난다 — 배포 절차가 `REDIS_PASSWORD=<생성>` 을 지시하니까.

컨테이너화 라운드(ADR-0029)를 통과해도 안 잡히는 이유다.

### 조용했던 게 절반이다 — 그리고 조용한 쪽이 더 위험했다

같은 Redis 클라이언트를 두 기능이 쓰는데 **둘 다 예외를 삼킨다.**

| 기능 | 실패 시 | 관측되는 것 |
|---|---|---|
| 시맨틱 캐시 | `except Exception` 두 곳이 `pass` | **없음.** 적중률 0뿐 |
| AI 요청 한도 | fail-open + 경고 로그 | 실측 **34건** |

캐시 쪽엔 알리바이까지 있었다 — 이 저장소는 "임계값 0.98이라 적중률이 낮다"
(ADR-0012)고 문서에 적어뒀다. **정상이라고 설명할 근거가 이미 있으면 결함은 더
오래 산다.**

그런데 눈에 보인 건 캐시고, 실제로 위험한 건 한도였다. 공개 URL 에서 분당
20회·일 50회가 **통째로 열려 있었다.** 비용 방어 계층 세 개 중 둘이 무력화된
상태다.

### 고친 것

1. `ai`·`ai-init` 에 `REDIS_PASSWORD` 추가 (진짜 원인)
2. `pipeline.py` 의 두 `except` 가 `logger.warning` 을 남기게 —
   리미터가 *"조용히 열지 않는다. 열되 남긴다"* 고 한 것과 같은 이유
3. `verify-container.sh` 에 판정 1-b 추가

3번이 필요한 이유: 기존 4분기 검사는 `use_cache: false` 로 보낸다. 분기가
실제로 도는지 보려면 맞는 선택이라 그 자체는 결함이 아니고, **캐시 경로가
어느 검사에도 안 덮여 있었던 것**이다.

AI 서버의 인프라 설정값을 전수 대조했다 — `elasticsearch_url`·`redis_url`·
`redis_password`·`jwt_secret`. 누락은 `REDIS_PASSWORD` 하나뿐이었다.

## 결함 2: 그 새 검사의 단언 **절반이 항상 참**이었다

배포에서 FAIL, 고친 뒤 PASS. 여기까지만 보면 정상적인 성공 사례다. 그런데
실패 출력이 이상했다.

```
[FAIL] 캐시 미적중 (hit=False, llm_calls=0)
```

**미적중인데 `llm_calls=0`.** FAQ 분기는 LLM 을 아예 안 부른다. 즉 그 단언은
캐시가 죽어 있어도 참이었고, 실제로 일한 건 `hit == True` 하나였다.

검색 질의로 바꿔서 실측했다.

| 질의 | 1회차 | 2회차 | 단언 |
|---|---|---|---|
| FAQ (전) | — | `hit=False, llm_calls=0` | 하나만 일함 |
| 검색, 고치기 전 | `False 2` | `hit=False, llm_calls=2` | 둘 다 (FAIL) |
| 검색, 고친 뒤 | `False 2` | `적중, llm_calls=0` | 둘 다 (PASS) |

`2 → 0` 이 캐시가 LLM 을 실제로 아꼈다는 직접 증거다. 최종 **11/11**.

### 딸려 나온 것 — 문서가 오독을 부추기고 있었다

*"`llm_calls == 0` 은 캐시 적중을 뜻한다"* 가 `CLAUDE.md`·`API-명세.md`·
ADR-0016 세 곳에 **일반 명제로** 적혀 있었다. 원래 문맥(검색 분기의 0건 처리)
에서는 맞는데, 그 문맥이 지워진 채 규칙으로 읽혔고 **그 규칙을 믿고 검사를
짰다.**

- `CLAUDE.md`·`API-명세.md` — 정정 (지금 참인 것을 적는 파생 문서)
- ADR-0016 — 인라인 정정 블록 (결정 기록이라 덮어쓰지 않는다)

## 방법론 — 이번에 확인된 것

- **실패 메시지에 판정에 쓴 값을 전부 싣는다.** 통과 여부만 찍었으면 결함 2는
  그대로 나갔다. `hit` 과 `llm_calls` 가 한 줄에 같이 찍혔고, **그 둘이 서로 안
  맞는다**는 게 검사의 결함을 가리켰다.
- **새 검사는 실패하는 것도 봐야 한다.** 이번엔 공짜였다 — 깨진 배포가 그
  자리에 있었으므로 FAIL → 수정 → PASS 를 순서대로 관측했다.
- **한 결함을 잡으면 그 결함이 왜 안 잡혔는지도 잡는다.** 원인(`REDIS_PASSWORD`)
  만 고치고 끝냈으면 캐시 경로는 여전히 어느 검사에도 안 덮인 채였다.

## 절차 문서 갱신

`restart backend web` 뒤에 **healthy 대기**를 넣었다. restart 는 즉시 돌아오는데
백엔드는 `start_period: 40s` 라, 바로 검증을 돌리면 502 가 난다. 실제로 겪었고
검사 실패를 배포 실패로 오해하기 좋은 형태다.

## 같은 날 (2) — 브라우저 점검 D~H 에서 결함 둘 더 (ADR-0036)

점검을 이어가다 나왔다. 둘 다 **자동 검사로는 원리적으로 안 잡히는 것**이다 —
하나는 LLM 출력의 사실성이고, 하나는 새로고침이라는 사용자 행동이다.

### 결함 3: 검색 설명이 자기 결과를 부정했다

`10만원 이하 검 찾아줘` → 22,000~45,000원짜리 검 **네 건**을 찾아놓고:

> 10만원 이하의 검 아이템은 **없습니다** … 모두 10만원을 초과하거나
> **검이 아닌 무기**입니다.

두 주장 다 거짓이고, 반증하는 카드 넷이 답변 **바로 아래**에 떠 있었다.

원인은 프롬프트가 **하드 필터가 이미 끝낸 판정을 다시 시킨 것**이다.

```python
_SEARCH_PROMPT = "... 종류가 맞지 않는 항목은 빼고 말하세요 ..."
def _brief(...): return [{"category": ...}]   # subcategory 가 없다
```

판단하라면서 판단할 필드(`subcategory="검"`)를 안 줬다. 네 건 모두
`category="무기"` 로만 보였다. 그 지시는 ADR-0014·0015 **이전의 화석**이다 —
카테고리 혼입이 실제로 UI 에 보이던 시절의 것이고, 지금은 ES `term` 절이
처리한다.

**설명 LLM 을 제거했다.** 0건과 같은 `_describe_filters` 로 확정 문장을 만든다.
`검 · 100,000원 이하 조건으로 4건 찾았습니다.` 검색 분기 `llm_calls` 가 2 → 1.

프롬프트만 고치는 안도 있었지만 고르지 않았다 — **결과 목록을 문장으로 옮길
이유가 없다.** 카드가 이름·가격·종류·속성을 다 보여주므로 설명이 더할 정보가
없고, 더할 게 없는 자리에서 LLM 은 지어낸다.

### 결함 4: 새로고침하면 로그아웃

`/items/5` 에서 F5 → 로그인 화면. SPA 폴백은 정상이고(200) 세션이 메모리에만
있어서다 — ADR-0031 의 결정이다.

`sessionStorage` 로 옮겼다. **XSS 가 나면 메모리의 토큰도 그 자리에서 빼간다** —
공격자가 이미 페이지 안에서 JS 를 돌리고 있으니까. 실질적 차이는 `localStorage`
와의 사이(탭 닫아도 생존, 탭 간 공유)에 있고 그건 그대로 피한다.

세션을 끝내는 자리가 **셋**(로그아웃·만료·복원 실패)이고 전부 저장소를 비워야
한다. 상태만 지우면 만료 토큰이 남아 새로고침마다 복원 → 401 → 로그인이 반복된다.

### 검사 하나가 이 변경으로 낡았다

오늘 오전에 만든 판정 1-b 의 실패 메시지가 *"1회차 `llm_calls` 가 1 이면 0건"*
이라고 적고 있었다. 검색이 0건이든 아니든 1 이 되므로 그 구분이 사라진다.
응답의 `no_results` 를 직접 읽게 바꿨다.

> **호출 수처럼 파생된 값을 판정 근거로 쓰면, 그 값을 만드는 쪽이 바뀔 때 조용히
> 틀린다.** 사실을 직접 말하는 필드가 있으면 그쪽을 읽는다. 같은 날 만든 검사가
> 같은 날 낡았다는 게 이 규칙의 값어치를 보여준다.

### 테스트

`TestSearchAnswer` 4건 추가 (137 → **141**). 핵심 단언은
**"결과가 있는데 없다고 말하지 않는다"** 다 — 프롬프트로는 보장할 수 없어서
문장 생성을 코드로 옮긴 것이므로, 그 보장을 테스트가 들고 있어야 한다.

고장난 구현 셋(결과 부정 / 조건 미표기 / 말투 불일치)을 만들어 단언이 전부
잡는지 확인했다. 실제 버그였던 "결과 부정"은 단언 3개 모두에 걸린다.

## 같은 날 (3) — 화면 결손 넷 (ADR-0037)

브라우저 점검을 이어가며 사용자가 잡아낸 것들이다. **전부 자동 검사가 통과한
상태에서 나왔다** — 검사는 엔드포인트가 답하는지를 보지, 화면에서 거기 갈 수
있는지를 보지 않는다.

| 증상 | 실체 |
|---|---|
| 재로그인하면 직전 화면 | 라우팅 안 함 — **그리고 쿼리 캐시가 안 비워진다** |
| 알림 배지가 안 눌림 | `<span>` 이다. `api.notifications()` 는 있는데 아무도 안 부른다 |
| 거래 내역 없음 | 백엔드에 조회 엔드포인트가 없다 |
| ← 검색으로 | `<Link to="/">`. 뒤로가기로 바꿔도 **결과는 사라진다** |

### 1번이 사용자가 본 것보다 한 겹 더 나빴다

증상은 "직전 페이지가 남는다"인데, 그 옆에 **쿼리 캐시가 안 비워지는 문제**가
있었다. 키에 사용자가 없어서(`["notifications","unread"]`, `["trades"]`,
`["alerts"]`) 토큰만 지우면 **이전 계정의 응답이 다음 사용자 화면에** 재요청
전까지 남는다.

`queryClient.clear()` 로 해결했다. 키마다 사용자 id 를 넣는 쪽이 정밀하지만
**새 쿼리를 추가할 때마다 잊을 수 있고 잊으면 조용하다.** "세션이 끝나면 서버
상태는 전부 무효"는 빠뜨릴 데가 없다.

### 4번은 링크만 고쳐서는 안 됐다

뒤로가기로 바꿔도 `Assistant` 가 재마운트되면서 결과가 사라진다 — 지역 상태는
언마운트와 함께 없어지고 mutation 결과는 캐시에 안 남는다. **질의를 URL 로**
옮겨야(`/?q=...`) 뒤로가기가 질의를 되살리고 `useQuery` 가 캐시된 응답을 내준다.
검색 링크 공유는 덤이다.

> v5 함정 하나: `enabled: false` 인 쿼리는 status 가 계속 `pending` 이다.
> `isPending` 으로 로딩을 그리면 **질의를 넣기도 전에** 버튼이 잠긴다.
> `isFetching` 을 써야 한다.

### 신규 엔드포인트 둘

- `GET /api/trades` — 구매·판매 양쪽, `side` 로 방향 표시. `join fetch` 로 N+1
  방지(50건이면 쿼리 151회). `TradeResponse` 를 재사용하지 않은 이유는 **보는
  사람이 정해져 있어서**다 — `buyerId: 3` 은 화면에서 아무 뜻이 없다.
- `PATCH /api/notifications/read` — 모두 읽음. **id 목록을 받지 않는다.** 받으면
  남의 알림 id 를 넣을 수 있어 소유권 검사를 따로 붙여야 하는데, 수신자를
  토큰에서 받으면 그 검사가 필요 없어진다.

### 테스트 — 혼자 있는 DB 에서는 격리를 검증할 수 없다

`MyDataScopeTest` 6건 (백엔드 49 → **55**). 공통 주제는 "내 것만 나오는가"다.

**다른 사용자를 반드시 같이 만든다.** 혼자만 있으면 "내 것만 나온다"와 "전부
나온다"가 **같은 결과**라, 격리를 하나도 안 해도 통과한다.

일부러 틀린 구현으로 돌려 확인했다.

| 변조 | 결과 |
|---|---|
| `n.recipient.id <> :recipientId` | `모두_읽음은_내_알림만_바꾼다` 실패 |
| `... or t.id > 0` | `내가_관여한_거래만_나온다` · `side_로_갈린다` 실패 |

원복 후 `git diff` 로 변조 흔적이 없음을 확인했다.

### 부수적으로 닫힌 것

이력서 비교에서 **누락으로 잡혔던 "거래 내역 조회"** 가 이 라운드에서 닫혔다.

### 배포 후 재점검에서 두 건 더 — 하나는 내가 방금 만든 것

**같은 질문을 다시 눌러도 아무 반응이 없었다.** `setSearchParams({q})` 는 값이
같으면 URL 을 안 바꾸고, 그러면 아무 일도 안 일어난다. 주석에 *"캐시된 결과가
이미 떠 있으니 맞는 동작"* 이라고 적어뒀는데 틀렸다 — 버튼을 눌렀는데 반응이
없으면 사용자에게는 고장이다.

> **합리화가 코드 주석에 들어가면 검토를 통과한다.** "이게 맞다"고 적혀 있으면
> 다음 사람은 그게 판단인지 변명인지 구분할 수 없다. 이번엔 사용자가 잡았다.

**`"...알려줘!"` 가 캐시 미적중이었다.** 키가 `sha1(query.strip())` 이라 종결
기호 하나로 다른 키다. `normalize_query()` 로 문장 끝 부호와 중복 공백을 없애고
해싱한다 — **유사도를 연 게 아니다.** 여전히 정확 일치이고 "같은 글자"의 범위만
넓혔다. ADR-0012 가 막은 건 `+8`/`+9` 처럼 한 글자가 답을 뒤집는 경우인데 종결
기호는 그 축에 없다.

여기서도 **양방향**을 쟀다 (AI 141 → **144**).

| 확인 | 결과 |
|---|---|
| 정규화 없을 때 부호 변형이 기준과 일치 | **0 / 3** (새 테스트가 수정 전이면 실패) |
| 정규화 있을 때 | 3 / 3 |
| 함정 쌍 16쌍 — 현재 정규화로 충돌 | **0** |
| 같은 쌍 — 과잉 정규화(공백·숫자 제거)로 충돌 | **4** |

마지막 줄이 없으면 함정 쌍 테스트는 "원래 다른 것이 다르다"는 동어반복이다.
과하게 했을 때 실제로 걸린다는 걸 봐야 그 테스트가 일하는 것이다.

## 같은 날 (4) — 브라우저 점검 완료, 그리고 랜딩에 매물 목록

F·G·H 까지 전부 통과. 실측 몇 가지가 남았다.

- **한도**: 콘솔에서 25회 연속 → 1~20 은 200, 21~25 는 429 (`Retry-After: 57`).
  화면에도 `요청이 너무 잦습니다…` 가 그대로 나온다. `normalizeErrorMessage()` 가
  422(`detail` 배열)뿐 아니라 429(`detail` 문자열)도 처리하는 게 여기서 확인됐다.
- **콘솔**: 새 탭 기준 오류 0건. Mixed Content 없음.
- **`assistant` 2.24초** — ARM 실측 첫 데이터. 로컬 live-llm p95 4.45초(ADR-0020)
  보다 낫다. 배포 대상이 개발 박스보다 느리지 않다.
- `favicon.ico` 가 `text/html` 200 으로 오고 있었다(SPA 폴백). SVG 하나 추가.

### 랜딩이 빈 검색창이었다

가장 큰 결손이 마지막에 나왔다. **거래소인데 매물을 볼 수가 없다.** 그리고
`GET /api/items` 는 **페이징까지 되는 채로 이미 있었다** — 프론트가 안 불렀을 뿐이다.

`?q=` 가 없을 때 목록을 보인다. 별도 라우트를 안 만든 이유는 둘이 같은 질문의 두
형태이기 때문이다.

### 기록된 결정을 화면 사정으로 뒤집지 않았다

목업에는 종류·속성·강화·레벨 열을 그렸는데 **Postgres `items` 에 그 필드가 없다.**
`export_demo_sql.py` 가 "화면을 위해 백엔드 스키마를 늘리지 않는다"고 명시해뒀고,
게다가 `seed-demo.sql` 은 `DELETE FROM trades` 로 시작해서 **재시딩이 방금 만든
실거래를 지운다.**

그래서 있는 것으로 만들고, 남은 불일치를 등록했다 — 검색 카드는 `검 · +9 · 60렙`
을 보여주는데 그걸 눌러 들어간 상세에는 없다.

### 라이브러리를 안 넣은 것도 결정이다

정렬·페이징이 서버 쪽이라 TanStack Table 이 파는 것(클라이언트 정렬·필터·가상화)이
전부 남는다. **화면 전체가 번들을 2.9KB 늘렸다** — 라이브러리를 넣었으면 그 몇 배가
기능 없이 들어갔다. Tailwind/shadcn 은 다섯 화면 스타일을 전부 다시 쓰는 대가에
기능이 0이라 제외.

### 내 테스트가 틀렸다 (또)

정렬 검사를 `sort=name,asc` 로 쓰고 `내가 파는 검` 이 먼저라고 단언했다가 실패.
**한글에서 `남`(ㅏ) 이 `내`(ㅐ) 보다 앞이다.** 더 중요한 건 그 다음인데 —
**한글 정렬 순서는 DB 로케일이 정한다.** 판정 근거를 환경에 맡기면 여기서 통과하고
배포에서 갈릴 수 있다. 가격으로 바꿨다.

`Page<T>` 직렬화 형태(`content`/`totalElements`/`number`/`size`)도 테스트로
고정했다. 프론트가 그 이름에 직접 의존하는데 그건 Spring 이 정하는 것이라,
판올림에서 바뀌면 **화면이 조용히 빈 표가 된다.**

### ADR-0024 보강

"분당 한도 없애도 되지 않나"는 질문에 **문서가 답을 못 했다.** 일일 한도는
ADR-0031 에서 따로 붙었고 두 층의 역할 분담이 어디에도 없었다. 표로 남겼다 —
일일은 **비용**, 분당은 **순간 부하**. 일일만 두면 50건을 1초에 다 쓸 수 있고,
이 박스는 4 OCPU 를 라이브 프로젝트와 공유한다.

## 같은 날 (5) — 배지가 거짓말을 하고 있었다

"재질문했을 때 캐시 적중이 안 된다"는 보고. 두 가지가 섞여 있었다.

**하나는 정상이다.** `anomaly_check` 는 설계상 캐시하지 않는다(policy.py) —
단건 판정이라 재사용될 일이 없고 유사 질의 오탐이 곧 보안 오판이 된다. 그
질의로 몇 번을 물어도 미적중인 게 맞다.

**나머지는 내가 만든 것이다.** 같은 날 오후에 넣은 `staleTime: 5 * 60 * 1000`.

```
Q1 물음 → 미적중 (정상)
Q2 물음
Q1 다시 → React Query 가 서버를 **안 부르고** 첫 응답을 다시 그린다
        → 거기 박힌 cache:{hit:false} 가 그대로 보인다
```

의도는 "AI 응답은 비싸니 돌아왔을 때 다시 부르지 말자"였다. 결과는 **계측이
잔상이 된 것**이다. 이 화면의 배지 줄은 서버 파이프라인을 눈에 보이게 하는
장치인데, 그 값을 클라이언트가 얼려두면 무엇을 보고 있는지가 사라진다.

빼는 데 대가가 없다는 것도 뒤늦게 확인했다 — 서버 적중은 LLM 0회에 p95
25.9ms(ADR-0026)이고, `staleTime: 0` 이어도 **캐시된 데이터는 즉시 그려지고
뒤에서 다시 받으므로** 뒤로가기로 결과가 살아 돌아오는 동작은 그대로다.
비용을 아끼려고 넣었는데 아낄 비용이 애초에 크지 않았다.

> **관측값을 나르는 응답은 클라이언트에서 캐시하지 않는다.** 값이 맞느냐가
> 아니라 *언제 찍힌 값이냐*가 의미의 일부이기 때문이다.

### 이상거래 답변의 잘린 문장은 잘린 게 아니었다

`…번호 체계가 별개라는 점.` 으로 끝나는 게 `max_tokens` 때문인 줄 알았는데
그런 설정은 저장소에 없다. 프롬프트를 보니 **템플릿 문장 자체가 그 조각**이다.

```
**반드시 한 문장으로 덧붙이세요**: 이 판정은 합성 데모 거래 데이터를 대상으로
하며, 사용자의 실제 거래 내역과는 번호 체계가 별개라는 점.
```

모델은 시킨 대로 글자 하나까지 그대로 옮겨 붙였다. 결함은 지시문에 있다.
시세 분기의 `cold_start가 false이므로` 와 같은 부류라 **한 라운드로 묶는다** —
프롬프트는 측정 없이 고치지 않는다(97.5% → 22% 전례).

## 같은 날 (6) — 배포 대상에서 CPU 단계 재측정

ADR-0028 의 워커 수 표가 **12코어 개발기** 것이고, 그 논리(torch intra-op 초과
구독)는 **코어 수에 직접 의존**한다. 배포 대상은 4 OCPU aarch64 다.
`scripts/benchmark_cpu_stages.py` 를 만들어 쟀다. LLM 을 안 부르므로 비용 0이다.

### 하네스를 로컬에서 먼저 검증했고, 거기서 두 번 고쳤다

- **cp949 에서 죽었다.** 한글은 깨지기만 하는데 em dash 에서
  `UnicodeEncodeError` 가 났다. stdout 을 UTF-8 로 고정했다.
- **문서에 `name` 만 넘겼다.** 리랭커는 `name + description` 을 쓴다. 그래서 첫
  실행이 54.71ms 였는데, **ADR-0028 의 103~189ms 와 비교 불가능한 숫자**다.
  주석에는 "합성 문자열을 쓰면 실제와 다른 길이를 본다"고 적어놓고 정작 필드를
  절반만 넘긴 셈이었다.

고친 뒤 개발기 재현: `encode_one` 16.75ms(기준 15.77), `rerank` 97.99ms
(기준 103~189). **기존 수치를 재현 못 하는 하네스로 새 환경을 재면 차이가 환경
탓인지 하네스 탓인지 알 수 없다.**

### 반복 2회로는 설정을 비교할 수 없었다

ARM 첫 실행에서 `rerank` 2워커가 **1420ms 와 1009ms** 를 냈다. 411ms 차이면
설정 간 차이(1워커 897 vs 4워커 999)보다 크다 — 순위가 아니라 실행 순서를
읽고 있었던 것이다. `RUNS=7` 로 올리고 표에 **실행간 폭**을 열로 냈다.

### 결과

| | 개발기 | **ARM** | 배율 |
|---|---:|---:|---:|
| `encode_one` | 16.75ms | 29.31ms | 1.75× |
| `rerank` | 97.99ms | 108.95ms | **1.11×** |
| 티커 잡음 바닥 | 5.54ms | **0.11ms** | 0.02× |

**ADR-0032 의 미해결 항목이 닫혔다** — "느릴 수 있다"는 추측뿐이던 ARM 리랭커
지연이 **1.11배**다. ONNX Runtime 이 torch 보다 아키텍처 전환을 잘 견뎠다.

**잡음 바닥 0.11ms** 는 ADR-0028 의 실패담을 정정한다. "판정선 20ms 가 잡음
바닥 16.34ms 안에 있었다"는 **Windows 타이머 문제**였고 배포 대상에는 없다.

### 워커 수 — 근거는 뒤집혔고 결론은 남았다

`encode_one` 은 ARM 에서 **4워커가 확실히 빠르다**(277/241/205ms, 2워커 최소
232 > 4워커 최대 223 — 범위가 안 겹친다). 12코어에서 4워커가 +85% 였던 것과
**정반대**다. 초과 구독 메커니즘이 4코어에서는 안 나타난다.

`rerank` 는 7회로도 결론이 안 났다 — 설정 간 차이 233ms 에 실행간 폭이
298~874ms 다. 순위를 읽지 않았다.

**그래도 `cpu_pool_workers` 는 2로 뒀다.** 얻는 게 검색 1건당 12ms 인데 실 LLM
검색 p95 가 4.45초라 **0.3%** 다. 대가는 4 OCPU 를 라이브 프로젝트와 공유하는
박스에서 코어를 다 채우는 것이고, **유휴 박스 벤치마크는 그 비용을 못 본다.**

> 측정이 결정의 *근거*를 뒤집었는데 *결론*은 다른 이유로 살아남았다. 근거를
> 조용히 갈아끼우면 다음 사람은 왜 그 값인지 알 수 없다. **둘 다 적었다.**

### 부하 기준선은 미뤘다

`k6` 미설치, 부하용 아이템 0건. 그런데 준비 자체가 공개 데모를 건드린다 —
`seed-loadtest.sql` 이 만드는 9001~9021 이 **내가 만든 매물 목록에 노출된다.**
그 파일은 "ES 에는 색인하지 않는다, 부하테스트는 검색을 거치지 않는다"고
적어뒀는데 **목록 화면이 그 전제를 깼다.** 게다가 배포 오버레이가
`SPRING_PROFILES_ACTIVE: prod` 를 박아둬서 `loadtest` 로 바꾸면 `SecretGuard`
가 그동안 무장 해제된다.

얻는 건 처리량 숫자 하나인데 대가가 넷이라 미뤘다. 오버셀 0 은 로컬 26,600건
에서 이미 검증됐고 락 로직은 아키텍처가 아니라 코드다.
