# 2026-08-07 — 배포된 걸 브라우저로 써보다가 결함 둘

배포 자체는 이틀 전에 끝났다. 자동 검증 38/38 과 공개 경로 10/10 이 통과했고,
남은 건 "실제로 써보기"였다. **써보자마자 나왔다.**

## 발견 경로 — 검사가 아니라 사용

점검을 A~H 단계로 나눠 순서대로 밟았다.

- **A(세션)·B(4분기)**: 통과
- **C(캐시)**: 같은 질문을 두 번 했는데 두 번 다 `캐시 미적중`, `LLM 2회`

C 가 걸렸다. 자동 검사가 전부 통과한 배포에서다.

## 결함 1: ai 컨테이너가 Redis 비밀번호를 못 받고 있었다

```yaml
# docker-compose.yml — ai 서비스
REDIS_URL: redis://redis:6379/0      # 있음
# REDIS_PASSWORD 없음                ← 코드 기본값 gimp_local_pw 로 붙는다
```

백엔드는 같은 파일에서 **이미 받고 있었다.** AI 만 빠졌다.

### 로컬에서 안 보이는 이유가 `RABBITMQ_HOST` 와 다르다

`localhost` 는 로컬에서 **맞는 값**이라 컨테이너로 옮길 때 깨진다. 이번 건은
`.env.example` 의 값이 하필 코드 기본값과 **같아서**(`gimp_local_pw`) 로컬에서
우연히 맞았다. 깨지는 조건이 컨테이너화가 아니라 **비밀번호 교체**이고, 그건
실배포에서 처음 일어난다 — 배포 절차가 `REDIS_PASSWORD=<생성>` 을 지시하니까.

컨테이너화 라운드(ADR-0029)를 통과해도 안 잡히는 이유다.

### 조용했던 게 절반이다 — 그리고 조용한 쪽이 더 위험했다

같은 Redis 클라이언트를 두 기능이 쓰는데 **둘 다 예외를 삼킨다.**

| 기능 | 실패 시 | 관측되는 것 |
|---|---|---|
| 시맨틱 캐시 | `except Exception` 두 곳이 `pass` | **없음.** 적중률 0뿐 |
| AI 요청 한도 | fail-open + 경고 로그 | 실측 **34건** |

캐시 쪽엔 알리바이까지 있었다 — 이 저장소는 "임계값 0.98이라 적중률이 낮다"
(ADR-0012)고 문서에 적어뒀다. **정상이라고 설명할 근거가 이미 있으면 결함은 더
오래 산다.**

그런데 눈에 보인 건 캐시고, 실제로 위험한 건 한도였다. 공개 URL 에서 분당
20회·일 50회가 **통째로 열려 있었다.** 비용 방어 계층 세 개 중 둘이 무력화된
상태다.

### 고친 것

1. `ai`·`ai-init` 에 `REDIS_PASSWORD` 추가 (진짜 원인)
2. `pipeline.py` 의 두 `except` 가 `logger.warning` 을 남기게 —
   리미터가 *"조용히 열지 않는다. 열되 남긴다"* 고 한 것과 같은 이유
3. `verify-container.sh` 에 판정 1-b 추가

3번이 필요한 이유: 기존 4분기 검사는 `use_cache: false` 로 보낸다. 분기가
실제로 도는지 보려면 맞는 선택이라 그 자체는 결함이 아니고, **캐시 경로가
어느 검사에도 안 덮여 있었던 것**이다.

AI 서버의 인프라 설정값을 전수 대조했다 — `elasticsearch_url`·`redis_url`·
`redis_password`·`jwt_secret`. 누락은 `REDIS_PASSWORD` 하나뿐이었다.

## 결함 2: 그 새 검사의 단언 **절반이 항상 참**이었다

배포에서 FAIL, 고친 뒤 PASS. 여기까지만 보면 정상적인 성공 사례다. 그런데
실패 출력이 이상했다.

```
[FAIL] 캐시 미적중 (hit=False, llm_calls=0)
```

**미적중인데 `llm_calls=0`.** FAQ 분기는 LLM 을 아예 안 부른다. 즉 그 단언은
캐시가 죽어 있어도 참이었고, 실제로 일한 건 `hit == True` 하나였다.

검색 질의로 바꿔서 실측했다.

| 질의 | 1회차 | 2회차 | 단언 |
|---|---|---|---|
| FAQ (전) | — | `hit=False, llm_calls=0` | 하나만 일함 |
| 검색, 고치기 전 | `False 2` | `hit=False, llm_calls=2` | 둘 다 (FAIL) |
| 검색, 고친 뒤 | `False 2` | `적중, llm_calls=0` | 둘 다 (PASS) |

`2 → 0` 이 캐시가 LLM 을 실제로 아꼈다는 직접 증거다. 최종 **11/11**.

### 딸려 나온 것 — 문서가 오독을 부추기고 있었다

*"`llm_calls == 0` 은 캐시 적중을 뜻한다"* 가 `CLAUDE.md`·`API-명세.md`·
ADR-0016 세 곳에 **일반 명제로** 적혀 있었다. 원래 문맥(검색 분기의 0건 처리)
에서는 맞는데, 그 문맥이 지워진 채 규칙으로 읽혔고 **그 규칙을 믿고 검사를
짰다.**

- `CLAUDE.md`·`API-명세.md` — 정정 (지금 참인 것을 적는 파생 문서)
- ADR-0016 — 인라인 정정 블록 (결정 기록이라 덮어쓰지 않는다)

## 방법론 — 이번에 확인된 것

- **실패 메시지에 판정에 쓴 값을 전부 싣는다.** 통과 여부만 찍었으면 결함 2는
  그대로 나갔다. `hit` 과 `llm_calls` 가 한 줄에 같이 찍혔고, **그 둘이 서로 안
  맞는다**는 게 검사의 결함을 가리켰다.
- **새 검사는 실패하는 것도 봐야 한다.** 이번엔 공짜였다 — 깨진 배포가 그
  자리에 있었으므로 FAIL → 수정 → PASS 를 순서대로 관측했다.
- **한 결함을 잡으면 그 결함이 왜 안 잡혔는지도 잡는다.** 원인(`REDIS_PASSWORD`)
  만 고치고 끝냈으면 캐시 경로는 여전히 어느 검사에도 안 덮인 채였다.

## 절차 문서 갱신

`restart backend web` 뒤에 **healthy 대기**를 넣었다. restart 는 즉시 돌아오는데
백엔드는 `start_period: 40s` 라, 바로 검증을 돌리면 502 가 난다. 실제로 겪었고
검사 실패를 배포 실패로 오해하기 좋은 형태다.
