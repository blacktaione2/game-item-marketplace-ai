## Phase 1: 백엔드 최소 골격 (얇은 수직 슬라이스)

- **Spring Boot 버전 변경**: Spring Initializr가 3.x 지원을 완전히 중단(`compatibility range >=4.0.0`)해서 계획했던 3.x 대신 Spring Boot 4.x(Spring Framework 7, Java 21)로 스캐폴딩. `CLAUDE.md`에 사유 기록.
- `backend/` Gradle 프로젝트 생성 (`com.gimp:backend`), 패키지 구조: `domain`(엔티티) / `repository` / `service` / `controller` / `dto` / `config` / `exception`
- 엔티티 설계 — 4개 테이블 전부 `tenant_id`를 처음부터 포함:
  - `Tenant`(게임사), `User`(테넌트 스코프, username은 테넌트 내 unique)
  - `Item`(정가/경매 겸용 — `saleType`으로 분기, 경매는 `currentBidPrice`/`currentBidder` 보유), `@Version` 낙관적 락을 Redis 락과 별개의 최후 방어선으로 추가
  - `Trade`(구매는 즉시 `COMPLETED`, 입찰은 `ACTIVE`→`OUTBID`로 갱신)
- 아이템 CRUD API (`/api/items`) — `X-Tenant-Id`/`X-User-Id` 헤더로 테넌트·행위자 식별 (JWT 도입 전 임시 방편, 추후 클레임 추출로 교체 예정). 삭제는 물리 삭제 대신 `CLOSED` 전환(거래 이력이 FK로 물려있어서).
- 구매/입찰 API (`/api/items/{id}/purchase`, `/api/items/{id}/bids`) — Redisson `RLock`으로 아이템 단위 분산 락을 건 뒤 `TransactionTemplate`으로 트랜잭션 경계를 명시적으로 감싸는 구조로 구현 (AI/RabbitMQ 없이 순수 락+트랜잭션만, 로드맵 Phase 1 범위). `@Transactional` self-invocation 함정을 피하기 위해 같은 클래스 내 프록시 우회 대신 `TransactionTemplate` 선택.
  - 재고 부족, 자기 아이템 거래, 판매중 아님, 경매 최고가 이하 입찰 등은 `409 Conflict`로 응답
- **트러블슈팅**: `redisson-spring-boot-starter`가 Spring Boot 4.1 클래스패스에서 `RedisProperties` 클래스를 찾지 못해 컨텍스트 로딩 실패(`ClassNotFoundException`) → Redisson 자체 Boot 오토컨피그를 쓰지 않고 있었으므로 순수 `org.redisson:redisson` 라이브러리 + 수동 `RedissonClient` 빈으로 교체해 해결.
- `./gradlew build` 성공 (Postgres 연결, ddl-auto=update로 4개 테이블 생성 확인), `bootRun`으로 기동 후 curl로 아이템 CRUD·구매·입찰·아웃비드·소유권 검증까지 실제 동작 확인.

## Phase 3: 검색 파이프라인

### 인덱스 설계

- 게임사별 인덱스 분리(`items-{tenant_code}`), 테넌트마다 shard/replica를 독립 지정할 수 있게 생성 함수 인자로 노출
- **nori 형태소 분석기 추가**: 기본 standard analyzer는 "강화된"을 통째로 한 토큰으로 잡아 "강화" 질의에 안 걸린다. nori는 `강화된 → 강화`로 어간을 뽑아준다. 실행 중 컨테이너에 수동 설치하면 컨테이너 재생성 시 사라지므로(플러그인은 볼륨이 아니라 컨테이너 파일시스템에 설치됨) `docker/elasticsearch/Dockerfile`로 이미지에 구움
- `dense_vector` 384차원(cosine), `enhancement_level`은 별도 정수 필드 — "+8 vs +9"는 BM25로 구분이 안 되므로 필터로 정확히 거르는 축을 따로 뒀다
- 더미 아이템 20건 색인 (강화 수치만 다른 롱소드 3종을 일부러 포함 — 하이브리드/리랭킹이 이걸 구분하는지 보려고)
- 테넌트 격리 확인: `items-ncsoft`에서 3건 삭제해도 `items-nexon`은 20건 유지

### 하이브리드 검색 (BM25 + kNN → RRF)

- **ES 네이티브 RRF를 못 씀**: 8.14의 `retriever` 문법은 우리 8.13.4에 아예 없고(`Unknown key ... [retriever]`), 8.13의 `rank.rrf`는 라이선스가 막는다(`current license is non-compliant for [Reciprocal Rank Fusion (RRF)]` — basic 라이선스). → 앱 레이어에서 직접 계산 (ADR-0005)
- BM25와 kNN을 `_msearch`로 한 번의 왕복에 던지고, 순위만 가지고 `1/(60+rank)` 합산
- RRF 순수 함수는 단위 검증: 대칭 입력 정확히 동점 / 두 리스트에 모두 등장한 문서가 한쪽 1위 문서를 이김
  - 처음엔 "양쪽 2위"가 "1위+3위"를 이긴다고 단정하고 테스트를 짰다가 실패 → 손으로 계산해보니 `1/61+1/63 > 2/62`(1/x가 볼록)이라 **내 가정이 틀렸고 구현이 맞았다.** 테스트를 실제 성질에 맞게 고침

### Query Rewrite + Text-to-DSL

- 동의어 확장과 구조화 필터 추출을 **한 프롬프트/한 호출**로 처리해서 검색당 LLM 왕복을 1회로 유지 (Phase 2의 `LLMClient` 인터페이스 그대로 재사용 — 프로바이더 교체 시 이 모듈은 손댈 필요 없음)
- 실제 OpenAI 키가 없어서 진짜 왕복은 미검증. 대신 스텁 LLM으로 파싱 경로를 검증: 순수 JSON / ```json 코드블록 / 앞뒤에 산문이 섞인 JSON / LLM 예외 / JSON이 아예 없는 응답 → 앞 3개는 정상 파싱, 뒤 2개는 원본 질의로 폴백(검색이 죽는 것보단 필터 없는 검색이 낫다)

### Cross-Encoder 리랭킹 (ONNX + int8)

- ONNX 변환 + int8 동적 양자화, 리랭킹 대상은 상위 20건으로 제한, 산출물은 디스크 캐시 + 지연 로딩 (`scripts/build_reranker_onnx.py`로 사전 생성 권장)
- **계획서 모델이 한국어에서 못 씀을 발견**: `ms-marco-MiniLM-L-6-v2`로 돌렸더니 리랭킹이 오히려 결과를 악화시켰다(질의 "강화 롱소드"에 롱소드 3종을 전부 밀어내고 강화 주문서를 1위로). 점수가 8.5~8.8에 몰려 변별력이 0
  - 영어 통제군(`pasta` 질의)은 -0.6 vs -11.2로 정상 → "모델 고장"이 아니라 "언어 불일치"로 범위 좁힘
  - 토크나이저 확인: `강화 롱소드 → ['ᄀ','##ᅡ','##ᆼ',...]` 자모 단위로 분해. 의미 신호가 소실된 노이즈를 채점하고 있었음
  - → 같은 계열 다국어 버전 `mmarco-mMiniLMv2-L12-H384-v1`로 교체 (ADR-0006). 교체 후 "+9 강화 롱소드"가 1위, 관련/무관 점수 차 6점 이상. "마법사가 쓸 만한 지팡이"에서도 RRF 4위였던 "얼음 서리 지팡이"를 1위로 올리고 "게임 머니"를 상위권 밖으로 밀어냄
  - 대가: 모델이 L-6→L-12 + 다국어 어휘라 양자화 산출물 22MB → 112.8MB

### 성능 (웜, 후보 20건)

`embedding 19ms / retrieval 26ms / rerank 121ms` — 첫 호출은 지연 로딩 때문에 훨씬 느리다(임베딩 14초, 리랭커 1.5초).

### 실제 OpenAI API로 Query Rewrite + Text-to-DSL 검증

키를 넣고 실제 왕복 테스트. (키는 루트 `.env`가 아니라 `ai/.env`에 있어야 함 — 루트 쪽은 docker-compose용)

**Text-to-DSL은 처음부터 잘 동작**했다:
- `"3만원 이하 강화된 갑옷"` → `category=방어구, price_max=30000` → 41000/52000원짜리 갑옷들이 정확히 걸러짐
- `"경매로 나온 +9 이상 무기"` → `category=무기, sale_type=AUCTION, enhancement_min=9` 3개 전부 추출, 결과 0건 — 데이터에 세 조건을 동시에 만족하는 아이템이 실제로 없으므로 **정직한 0건**
- 스키마에 없는 조건은 억지로 채우지 않음(프롬프트의 "추측하지 마세요"가 지켜짐)

**Query Rewrite(동의어 확장)는 처음에 사실상 동작하지 않았다.**
- `"불속성 검"` → 재작성 결과가 원문 그대로. 유일한 불 속성 아이템인 "불꽃의 마법봉"이 6위
- 원인 분리: 수동으로 `"불꽃 화염 속성 무기"`를 넣어보니 BM25/kNN 둘 다 1위로 잡음. 반면 `"불속성 검"`은 **`bm25_rank=None`** — "불속성"과 "불꽃" 사이에 어휘 겹침이 없어서 키워드 검색이 아예 못 찾고 있었다. 즉 검색/리랭킹은 멀쩡했고 **프롬프트가 문제**
- 수정: 프롬프트에 동의어 확장을 명시적 규칙(속성/장비종류/약어 카테고리별)과 few-shot 예시로 추가
- 결과: `"불속성 검"` → `"불꽃 화염 검 소드"`, 불꽃 관련 아이템이 1·2위로 올라옴

**더미 데이터 보강**: `"100렙 이상 활"` 테스트를 하려다 데이터에 활이 한 개도 없다는 걸 발견. 활 3종 + 불속성 대검 1종 추가(20건 → 24건). 추가 후 활 3종이 상위 3위를 차지

**스키마에 레벨 필드가 없던 문제 → 해결**: 처음엔 `"100렙 이상 활"`의 "100렙 이상"이 조용히 사라졌다. 인덱스에 `enhancement_level`은 있지만 `required_level`이 없어서 LLM이 (올바르게) 추측을 거부하고 필터를 안 만들었고, 그 결과 레벨 10짜리 "초심자용 단궁"이 2위로 올라왔다.

`required_level`(integer)을 매핑 / `SearchFilters`(`level_min`/`level_max`) / 프롬프트에 추가하고 더미 24건 전부에 값을 부여해 재색인. 계정·재화·재료처럼 레벨 개념이 없는 아이템은 0.

- 프롬프트에 **"강화 수치(+숫자)와 레벨은 서로 다른 축이니 절대 섞지 마세요"** 규칙과 `"100렙 이상 활"` few-shot 예시를 명시 — 두 축이 헷갈리면 조용히 엉뚱한 필터가 나가는 게 제일 위험하다
- 검증 결과:
  - `"100렙 이상 활"` → `level_min=100`, 바람의 장궁(lvl 100)이 1위. lvl 10 단궁과 lvl 80 사냥꾼의 활은 정확히 제외됨
  - `"50렙 이하 저렙 무기"` → `level_max=50`, 결과 전부 50 이하
  - `"80렙 이상 120렙 이하 장비"` → 상·하한 동시 추출
  - `"+9 이상 강화된 활"` → `enhancement_min=9`만 잡고 level은 건드리지 않음 (두 축 분리 확인)
- 한계: "활"이라는 아이템 종류 자체는 필터가 아니라 텍스트 신호라서, `"100렙 이상 활"`에도 레벨 조건을 만족하는 대검류가 하위에 섞인다. 아이템 세부 종류(subcategory) 필드를 두는 건 별도 판단 사항

**레이턴시 구성이 뒤집혔다**: `query_understanding 0.9~2.2초` vs `retrieval 10~20ms / rerank 14~64ms`. LLM 호출이 검색 전체 레이턴시의 **95% 이상**을 차지한다. Phase 6의 Semantic Cache와 경량 Intent Router가 성능 관점에서 왜 필요한지가 수치로 확인됨(`"안녕하세요"` 같은 비검색 질의도 1초씩 LLM을 태우고 있다)

### 기타 수정

- 존재하지 않는 테넌트로 검색하면 ES 원본 에러가 500으로 새던 것을 404 + 명확한 메시지로 변경
- `requirements.txt`에 한글 주석을 넣었더니 pip이 cp949로 읽어서 설치 자체가 실패(`UnicodeDecodeError`) → 이 파일은 ASCII만 유지

## Phase 3 마무리 요약

### 완성된 파이프라인

```
자연어 질의
  → Query Rewrite + Text-to-DSL   [LLM 1회]  동의어 확장 + 구조화 필터 추출
  → 임베딩                                    다국어 MiniLM(384차원), 지연 로딩
  → BM25 + kNN                    [msearch 1회] → RRF 융합(앱 레이어)
  → Cross-Encoder 리랭킹                      ONNX + int8, 상위 20건만
  → 결과
```

`POST /api/search` 하나로 노출. 게임사별 인덱스(`items-{tenant_code}`) 분리, 테넌트 격리 검증 완료.

### 계획서와 달라진 것 (3건, 전부 실측 근거 있음)

| 항목 | 계획 | 실제 | 근거 |
|---|---|---|---|
| RRF | ES 네이티브 기능 | 앱 레이어 직접 구현 | basic 라이선스가 막음 (ADR-0005) |
| 리랭커 | `ms-marco-MiniLM-L-6-v2` | `mmarco-mMiniLMv2-L12-H384-v1` | 영어 토크나이저가 한국어를 자모로 분해 (ADR-0006) |
| 한국어 분석 | (명시 없음) | nori 플러그인 추가 | standard analyzer가 "강화된"을 못 쪼갬 |

### 측정값 (웜, 후보 20건)

| 단계 | 레이턴시 |
|---|---|
| Query Rewrite + Text-to-DSL (LLM) | **0.9 ~ 2.2초** |
| 임베딩 | 15 ~ 21ms |
| BM25 + kNN 검색 (msearch) | 10 ~ 40ms |
| Cross-Encoder 리랭킹 | 13 ~ 64ms |

**LLM 호출이 검색 전체 레이턴시의 95% 이상.** 나머지 전 단계를 합쳐도 100ms 안쪽이다.
Phase 6의 Semantic Cache / 경량 Intent Router가 "있으면 좋은 것"이 아니라 이 파이프라인의
핵심 성능 레버라는 게 수치로 확인됐다 — `"안녕하세요"` 같은 비검색 질의조차 지금은 1초를 태운다.

첫 호출은 지연 로딩 때문에 훨씬 느림(임베딩 ~14초, 리랭커 ~1.5초). 배포 전
`python -m scripts.build_reranker_onnx`로 ONNX 산출물을 미리 만들어둘 것.

### 알려진 한계 (의도적으로 남김)

- **`subcategory` 하드 필터 없음**: 활/검/지팡이 같은 아이템 세부 종류가 텍스트 신호로만
  작동한다. `"100렙 이상 활"`에 레벨 조건을 만족하는 대검류가 하위에 섞임(활 자체는 1위라
  치명적이진 않음). 로드맵 Phase 3 스트레치 항목으로 등록
- **임베딩이 도메인 파인튜닝 안 됨**: 범용 다국어 MiniLM 그대로 — Phase 4에서 해결 예정
- **리랭커도 도메인 파인튜닝 안 됨**: mMARCO 사전학습 그대로. `"마법사가 쓸 만한 지팡이"`에
  "행운의 목걸이"가 상위에 섞이는 등 잔여 오류가 있음
- **RAGAS 정량 평가 미실시**: 지금까지의 품질 판단은 전부 눈으로 본 것. Phase 4에서
  수치화하는 게 첫 증명 결과물

### 배운 것

1. **사전학습 모델은 "계획서에 적혀 있으니까" 붙이면 안 된다.** ONNX 변환·양자화·배치
   추론이 전부 정상 동작해도 모델과 데이터의 언어가 안 맞으면 결과가 조용히 나빠진다.
   영어 통제군을 같이 돌려 "모델 고장"과 "언어 불일치"를 분리한 게 원인 파악의 핵심이었다
2. **파이프라인이 여러 단계면 실패 지점을 먼저 좁혀야 한다.** `"불속성 검"`이 안 나올 때
   검색기/리랭커를 의심하기 쉬웠지만, 수동으로 동의어를 펼쳐 넣어보니 BM25/kNN 둘 다 1위로
   잡았다(`bm25_rank=None` → 어휘 겹침 부재). 범인은 프롬프트였다
3. **테스트가 실패하면 구현이 아니라 내 가정을 먼저 의심할 것.** RRF 단위 테스트가 깨졌을 때
   손으로 계산해보니 `1/61+1/63 > 2/62`(볼록성)라 구현이 맞고 내 기대가 틀렸다
4. **"결과 0건"이 정답일 때가 있다.** `"경매로 나온 +9 이상 무기"`가 0건인 건 세 조건을
   동시에 만족하는 데이터가 실제로 없어서다. 억지로 뭔가 반환하는 것보다 정확하다
