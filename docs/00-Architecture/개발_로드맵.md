  ### 그런데 분할 검증에서 다시 뒤집혔다 — **도입하지 않는다**

  위 반복 실행은 **같은 분할**을 되풀이한 것이라 "노이즈가 줄었다"와 "이
  분할에서 우연히 여유가 생겼다"를 구분하지 못한다. 같은 수집 데이터를
  질의 단위로 재분할해 **126가지 전수 열거**했다(추가 API 호출 없음).

  `Δ = 홀드아웃 적합 최솟값 − 튜닝 적합 최솟값`:

  | | 값 |
  |---|---|
  | Δ 범위 / 중앙값 | −3.54 ~ +2.17 / **−0.34** |
  | **부등호 유지(Δ>0)** | **56/126 = 44%** |
  | 마진 0.5에서 적합 손실 0 | 91/126 = 72% |
  | **실제 쓰던 분할의 Δ 백분위** | **83%** |

  - **부등호가 절반도 유지되지 않는다.** 실제 분할은 유리한 소수에 속했다
  - **마진을 키워도 안 된다**: 분할 전체가 안전해지는 지점(마진 ≥ 4.0)에서는
    부적합 제거가 **0건**이다. 안전과 효용을 동시에 만족하는 값이 없다
  - **뿌리**: 질의별 적합 최솟값이 −3.84 ~ +2.90(**폭 6.74점**)으로 움직이는데
    전역 부적합 최댓값은 −2.54다. 크로스인코더 로짓은 **질의를 가로질러 비교
    가능한 눈금이 아니다** — 상대 낙폭이 실패한 이유(top1이 5.7점 이동)와
    같은 뿌리다
  - **기각 사유가 07-30과 다르다.** 그때는 노이즈(고칠 수 있었고 고쳤다),
    지금은 점수 눈금의 성질(**고칠 수 없다**). `temperature`를 더 만지거나
    질의셋을 늘려도 이 결론은 안 바뀐다
  - 보류 비용은 낮다 — 1차 결론의 임계값도 홀드아웃 부적합 4/10건만 잘랐다

    "혼동하지 마라"고 말하는 것이 오히려 혼동을 만들었다

- [ ] **`"무속성"` 추출이 동작하지 않는다** (2026-07-31 신규, 위 측정의 부산물)

  `"무속성 검 찾아줘"` 50회 중 `element="무속성"`이 **8회**뿐이고 42회가
  `null`이다. 모델이 `"무속성"`을 "속성 언급 없음"으로 읽는다. 결과적으로
  무속성 검을 요청해도 불꽃의 대검이 섞여 나온다 — **element 필터의 `무속성`
  방향이 사실상 무력하다.**

  - 결정성 문제가 아니라 **정확도** 문제다(일관되게 틀린다)
  - **착수 조건**: 프롬프트 평가셋이 먼저 필요하다. ADR-0017에서 그럴듯한
    프롬프트 한 줄이 4배 악화를 냈으므로, 눈으로 판단하지 말고 측정 루프를
    갖춘 뒤에 손댄다

- [x] **`element` 속성 하드 필터 — 2026-07-30 완료** (ADR-0015).
  42건에 `화염`/`냉기`/`번개`/`암흑`/`신성`/`무속성` 부여 + keyword 매핑 +
  `SearchFilters.element` + 프롬프트 표기 대응 + 임포트 가드 일반화, 재색인 1회.

  - 같은 실행 안에서 A/B 측정(`scripts/evaluate_hard_filters.py`):
    **부적합 26 → 14 (−46%), 적합 20 → 20 (손실 0)**
  - 감소분 12건이 전부 속성 질의 3건에서 나왔고 속성 조건 없는 7건은 무변화 —
    귀속이 깨끗하다
  - **`"3만원 이하 불속성 검"` → 0건, 5회 반복 전부 재현.** 아래 항목의
    전제 조건이 충족됐다
  - 메커니즘은 `subcategory`와 동일해서 판단할 게 없었고, 실제 판단은
    **분류 규칙**이었다 — 저항은 속성이 아니고(대화염 방패가 `"불속성 장비"`에
    나오면 안 된다), 이름이 아니라 효과로 판정한다(`바람의 장궁`은 무속성)

- [x] **"조건 만족 결과 없음" 처리 — 2026-07-30 완료** (ADR-0016).
  0건이면 LLM을 거치지 않고 확정 응답을 만들고, 걸린 조건을 노출하며,
  **그 응답을 캐시에 저장하지 않는다.**

  | | 이전 | 이후 |
  |---|---|---|
  | 같은 입력 5회의 답변 종류 | **5가지** | **1가지** |
  | LLM 호출 | 2회 | **1회** |
  | 걸린 조건 표시 | 없음 | `검 · 화염 속성 · 30,000원 이하` |

  - 이전 5건은 전부 답이 맞았다 — **지어내기는 관측되지 않았고** 측정된 건
    변동성이다. 다만 다섯 개 모두 **질의를 어떻게 해석했는지 말하지 않았다**
  - `llm_calls`는 **0이 아니라 1**이다. `understand_query`는 건너뛸 수 없다 —
    필터를 알아야 0건 판정이 선다. 없어지는 건 설명 생성 호출 하나
  - **0건 응답 미저장이 이번 작업의 핵심 결정.** 판정 근거인 필터 추출이
    비결정적이라, 질의 문자열로 캐시하면 여러 추출 중 하나를 TTL 동안 임의로
    고정하게 된다. 그리고 0건은 매물 하나만 등록돼도 거짓이 되는 가장 낡기 쉬운 답
  - **범위 한계**: `"2만원 이하 전설 등급 무기"`는 고쳐지지 않는다. 이 처리는
    0건을 **만들지** 않고 이미 0건이 된 것을 제대로 말할 뿐이다 — 0건을 만드는
    쪽은 하드 필터(아래 `rarity`)의 몫이다

- [ ] **`rarity` 등급 축 — 세 번째 하드 필터 후보 (2026-07-30 발견)**

  `"2만원 이하 전설 등급 무기"`도 정답이 0건인데 부적합 3건을 계속 돌려준다
  (5회 전부). `전설 등급`이 아직 텍스트 신호다 — `element` 이전의 속성과
  같은 상태다.

  - **다만 앞의 두 건과 같은 작업이 아니다.** `subcategory`/`element`는 설명문에
    근거가 있어서 태깅이 *판독*이었지만, 등급은 코퍼스에 개념 자체가 없어
    **새로 발명**해야 한다. `미스릴 단검`이 몇 등급인지는 데이터가 답해주지
    않는다
  - 착수하려면 등급 체계 정의가 선행돼야 하고 그건 별도 판단이다. 지금은
    "같은 메커니즘으로 풀린다"고 계산에 넣지 않는다

- [ ] **프롬프트 레벨 완화는 신뢰할 수 없다 (2026-07-30 확인)** —
  구조적 해법이 필요하다는 논거.

  Phase 6에서 시스템 프롬프트에 "종류가 맞지 않는 항목은 빼고 말하라"를 넣었고,
  `"3만원 이하 불속성 검"` 때는 LLM이 실제로 `"미스릴 단검과 초심자용 단궁은
  불속성 검이 아닙니다"`라고 스스로 짚었다. 그런데 `"5만원 이하 검 찾아줘"`
  에서는 **같은 프롬프트인데 단궁을 검 목록에 넣어 설명했다.**

  같은 완화책이 질의에 따라 되기도 하고 안 되기도 한다. **완화책으로 계산에
  넣으면 안 된다** — 위 두 항목(리랭커 하한 / subcategory)이 구조적으로
  필요한 이유다.

1·2가 먼저인 이유는 하나다 — **임계값이 없다.** 하드 필터는 캘리브레이션이
필요 없어서 측정 노이즈에 영향받지 않는다. 4·5는 그 반대라 순서가 뒤로 갔다.

순서를 되돌린 이유는 하나다. 하한이 "작은 변경"이라는 건 맞지만
**그 작은 변경을 안전하게 하려면 임계값을 정할 수 있어야 하고, 지금은 정할
수 없다.** 반면 `subcategory` 필터는 재색인 비용이 있는 대신
**임계값이 없다** — `subcategory == "활"`은 실행마다 흔들리지 않는다.
불확실한 임계값보다 확실한 필터를 먼저 두는 편이 낫다.

## 기술 부채 (단계 무관)

특정 Phase의 산출물이 아니라 여러 단계에 걸쳐 있는 항목. 발견 시점이 아니라
영향이 드러나는 시점에 처리한다.

- [ ] **AI 서버의 동기 호출이 이벤트 루프를 막는다** — 임베딩 인코딩
  (`sentence-transformers`)이 `async` 함수 안에서 동기로 실행된다.
  Phase 3 `search/pipeline.py`에서 시작해 Phase 5 `forecast/cold_start.py`도
  같은 패턴이다. 모델 지연 로딩이 걸리는 첫 호출에서는 **13.5초 동안 루프
  전체가 멈추는 것을 실측**했고, 그 사이 다른 요청은 처리되지 않는다.
  계획서의 "FastAPI, strict async/await" 방침과도 어긋난다.
  - 해결 방향: `run_in_executor` / `anyio.to_thread.run_sync`로 스레드 풀에
    넘기거나, 모델 로딩을 기동 시점 워밍업으로 분리
  - **착수 조건**: Phase 8 부하테스트 **착수 전**. 이 상태로 측정하면
    처리량 수치가 아키텍처가 아니라 이 결함을 재게 된다

- [ ] **자동화 테스트 커버리지** — 현재 테스트는 `ai/tests/test_hybrid.py`
  (RRF 순수 함수 7건)와 backend의 `contextLoads()` 하나가 전부다. Item CRUD,
  Redis 분산 락 구매/입찰, 피처 추출, 시세/이상탐지 파이프라인은 전부 수동
  curl과 임시 스크립트로만 검증했다.
  - 우선순위: **Redis 분산 락 동시성**이 가장 급하다. 정확성을 수동 검증으로
    주장하기 어려운 종류이고(경합 상황을 손으로 재현할 수 없다), 이 프로젝트가
    내세우는 핵심 기능이기도 하다
  - **착수 조건**: Phase 8 부하테스트 **착수 전**. 부하 상황에서 락이 실제로
    맞게 도는지를 수동으로는 확인할 수 없다
