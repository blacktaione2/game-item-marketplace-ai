  ### 그런데 분할 검증에서 다시 뒤집혔다 — **도입하지 않는다**

  위 반복 실행은 **같은 분할**을 되풀이한 것이라 "노이즈가 줄었다"와 "이
  분할에서 우연히 여유가 생겼다"를 구분하지 못한다. 같은 수집 데이터를
  질의 단위로 재분할해 **126가지 전수 열거**했다(추가 API 호출 없음).

  `Δ = 홀드아웃 적합 최솟값 − 튜닝 적합 최솟값`:

  | | 값 |
  |---|---|
  | Δ 범위 / 중앙값 | −3.54 ~ +2.17 / **−0.34** |
  | **부등호 유지(Δ>0)** | **56/126 = 44%** |
  | 마진 0.5에서 적합 손실 0 | 91/126 = 72% |
  | **실제 쓰던 분할의 Δ 백분위** | **83%** |

  - **부등호가 절반도 유지되지 않는다.** 실제 분할은 유리한 소수에 속했다
  - **마진을 키워도 안 된다**: 분할 전체가 안전해지는 지점(마진 ≥ 4.0)에서는
    부적합 제거가 **0건**이다. 안전과 효용을 동시에 만족하는 값이 없다
  - **뿌리**: 질의별 적합 최솟값이 −3.84 ~ +2.90(**폭 6.74점**)으로 움직이는데
    전역 부적합 최댓값은 −2.54다. 크로스인코더 로짓은 **질의를 가로질러 비교
    가능한 눈금이 아니다** — 상대 낙폭이 실패한 이유(top1이 5.7점 이동)와

  - **기각 사유가 07-30과 다르다.** 그때는 노이즈(고칠 수 있었고 고쳤다),

  - 보류 비용은 낮다 — 1차 결론의 임계값도 홀드아웃 부적합 4/10건만 잘랐다

- [x] **질의 재작성 비결정성 — 2026-07-31 완료** (ADR-0017).
  원인은 **`temperature`가 코드상 아예 설정돼 있지 않았던 것**이다. 생략하면

  |---|---|---|
  | 토큰집합 평균 모드 일치율 | 0.840 | **0.990** |

  - **정정 1**: ADR-0016이 0건 캐시 금지 이유로 든 "필터 추출이 비결정적"은

    동일했다(관측했던 건 재작성 *텍스트* 변동이었다). 다만 90회 중 1회
    오추출은 있어 완전히 안정적이진 않다. **ADR-0016의 결정은 유지되고
    이유 1의 강도만 낮춘다** — 이유 2가 독립적으로 선다
  - **정정 2**: 온도가 필터 오추출의 원인이 아니다. n=30으로 다시 재니
    양쪽 다 1/40이었다
  - **실패 기록**: `불속성`↔`무속성` 혼동을 막으려 프롬프트에 한 줄
    추가했다가 정답률이 **97.5% → 22%로 4배 악화**해서 되돌렸다.
    "혼동하지 마라"고 말하는 것이 오히려 혼동을 만들었다

- [x] **`"무속성"` 추출이 동작하지 않는다** (2026-07-31 신규) — **ADR-0040 으로 완료 (2026-08-08). 아래 「착수 조건」의 결론이 뒤집혔다: 프롬프트 문제가 아니었다.**

  `"무속성 검 찾아줘"` 50회 중 `element="무속성"`이 **8회**뿐이고 42회가
  `null`이다. 모델이 `"무속성"`을 "속성 언급 없음"으로 읽는다. 결과적으로
  무속성 검을 요청해도 불꽃의 대검이 섞여 나온다 — **element 필터의 `무속성`
  방향이 사실상 무력하다.**

  - 결정성 문제가 아니라 **정확도** 문제다(일관되게 틀린다)
  - **착수 조건**: 프롬프트 평가셋이 먼저 필요하다. ADR-0017에서 그럴듯한
    프롬프트 한 줄이 4배 악화를 냈으므로, 눈으로 판단하지 말고 측정 루프를
    갖춘 뒤에 손댄다
  - **2026-08-07 갱신 — 조건이 좁아졌다.** ADR-0038·0039 로 프롬프트 측정
    **방법론**은 생겼다: 수집/채점 분리(`--score-only` 로 지표를 고쳐도 재호출
    0), 같은 프롬프트끼리의 **대조군**, 한 번에 하나씩, 걸린 표본 읽기.
    `evaluate_explanation_prompts.py` / `evaluate_domain_gate.py` 가 그 형태다.
  - **아직 없는 것은 "정답이 붙은 추출 평가셋"이다.** 기존
    `evaluate_rewrite_determinism.py` 는 **안정성**만 재지 정확도를 안 잰다
    (같은 답을 일관되게 틀려도 만점이다). `element` 라벨이 달린 질의 세트를
    만드는 것이 남은 전부다 — 방법론은 더 만들 필요가 없다

  - **2026-08-08 결론 — 평가셋을 만들었더니 프롬프트 문제가 아니었다** (ADR-0040).
    `element_queries.py` 39건(무속성·타속성·미언급·저항·부정형)을 손으로 붙이고
    보니, 프롬프트에는 **이미** `무속성/속성 없는 -> "무속성"` 과 `null` 과의 차이가
    적혀 있었다. **옳은 말로 이미 지시받았는데 42/50 을 틀린다.**

    그래서 프롬프트를 안 건드리고 **결정적 후처리**로 갔다 — 질의에 글자가 있는지는
    코드가 확실히 안다(ADR-0036·0039 와 같은 처방). 무속성 정확도
    **62~86% → 93%**, 회귀 0, 두 실행 동일.

    > 이 항목의 착수 조건이 "프롬프트 평가셋" 이었는데, **평가셋의 값어치는
    > 프롬프트를 고치는 데 있지 않았다.** 그것 없이는 "프롬프트 문제가 아니다" 를
    > 알 수도 없었다는 데 있었다. 미언급 10건이 100% 로 나온 것이 "채우면 안 될 때"
    > 를 보장했고, 그게 없었으면 이 처방은 위험했다.

- [x] **`element` 속성 하드 필터 — 2026-07-30 완료** (ADR-0015).
  42건에 `화염`/`냉기`/`번개`/`암흑`/`신성`/`무속성` 부여 + keyword 매핑 +
  `SearchFilters.element` + 프롬프트 표기 대응 + 임포트 가드 일반화, 재색인 1회.

  - 같은 실행 안에서 A/B 측정(`scripts/evaluate_hard_filters.py`):
    **부적합 26 → 14 (−46%), 적합 20 → 20 (손실 0)**
  - 감소분 12건이 전부 속성 질의 3건에서 나왔고 속성 조건 없는 7건은 무변화 —
    귀속이 깨끗하다
  - **`"3만원 이하 불속성 검"` → 0건, 5회 반복 전부 재현.** 아래 항목의
    전제 조건이 충족됐다
  - 메커니즘은 `subcategory`와 동일해서 판단할 게 없었고, 실제 판단은
    **분류 규칙**이었다 — 저항은 속성이 아니고(대화염 방패가 `"불속성 장비"`에
    나오면 안 된다), 이름이 아니라 효과로 판정한다(`바람의 장궁`은 무속성)

- [x] **"조건 만족 결과 없음" 처리 — 2026-07-30 완료** (ADR-0016).
  0건이면 LLM을 거치지 않고 확정 응답을 만들고, 걸린 조건을 노출하며,
  **그 응답을 캐시에 저장하지 않는다.**

  | | 이전 | 이후 |
  |---|---|---|
  | 같은 입력 5회의 답변 종류 | **5가지** | **1가지** |
  | LLM 호출 | 2회 | **1회** |
  | 걸린 조건 표시 | 없음 | `검 · 화염 속성 · 30,000원 이하` |

  - 이전 5건은 전부 답이 맞았다 — **지어내기는 관측되지 않았고** 측정된 건
    변동성이다. 다만 다섯 개 모두 **질의를 어떻게 해석했는지 말하지 않았다**
  - `llm_calls`는 **0이 아니라 1**이다. `understand_query`는 건너뛸 수 없다 —
    필터를 알아야 0건 판정이 선다. 없어지는 건 설명 생성 호출 하나
  - **0건 응답 미저장이 이번 작업의 핵심 결정.** 판정 근거인 필터 추출이
    비결정적이라, 질의 문자열로 캐시하면 여러 추출 중 하나를 TTL 동안 임의로
    고정하게 된다. 그리고 0건은 매물 하나만 등록돼도 거짓이 되는 가장 낡기 쉬운 답
  - **범위 한계**: `"2만원 이하 전설 등급 무기"`는 고쳐지지 않는다. 이 처리는
    0건을 **만들지** 않고 이미 0건이 된 것을 제대로 말할 뿐이다 — 0건을 만드는
    쪽은 하드 필터(아래 `rarity`)의 몫이다

- [ ] **`rarity` 등급 축 — 세 번째 하드 필터 후보 (2026-07-30 발견)**

  `"2만원 이하 전설 등급 무기"`도 정답이 0건인데 부적합 3건을 계속 돌려준다
  (5회 전부). `전설 등급`이 아직 텍스트 신호다 — `element` 이전의 속성과
  같은 상태다.

  - **다만 앞의 두 건과 같은 작업이 아니다.** `subcategory`/`element`는 설명문에
    근거가 있어서 태깅이 *판독*이었지만, 등급은 코퍼스에 개념 자체가 없어
    **새로 발명**해야 한다. `미스릴 단검`이 몇 등급인지는 데이터가 답해주지
    않는다
  - 착수하려면 등급 체계 정의가 선행돼야 하고 그건 별도 판단이다. 지금은
    "같은 메커니즘으로 풀린다"고 계산에 넣지 않는다

- [ ] **프롬프트 레벨 완화는 신뢰할 수 없다 (2026-07-30 확인)** —
  구조적 해법이 필요하다는 논거.

  Phase 6에서 시스템 프롬프트에 "종류가 맞지 않는 항목은 빼고 말하라"를 넣었고,
  `"3만원 이하 불속성 검"` 때는 LLM이 실제로 `"미스릴 단검과 초심자용 단궁은
  불속성 검이 아닙니다"`라고 스스로 짚었다. 그런데 `"5만원 이하 검 찾아줘"`
  에서는 **같은 프롬프트인데 단궁을 검 목록에 넣어 설명했다.**

  같은 완화책이 질의에 따라 되기도 하고 안 되기도 한다. **완화책으로 계산에
  넣으면 안 된다** — 위 두 항목(리랭커 하한 / subcategory)이 구조적으로
  필요한 이유다.

## Phase 10: 비동기 후처리 (RabbitMQ)

> **이 항목은 기획서에 있었는데 로드맵으로 내려온 적이 없다.** Phase 9a에서 배포
> 프로파일을 짜다가 RabbitMQ가 **코드 어디에도 없다**는 걸 확인하고서야 드러났다 —
> 인프라만 떠 있고 아무도 쓰지 않는 상태로 아홉 단계를 지나왔다. Phase 0의
> "docker-compose에 RabbitMQ 포함"이 전부였고, 구현 항목은 없었다.
>
> 드리프트의 방향이 지금까지와 다르다. 여태 잡은 것들은 **로드맵이 코드보다 낡은**
> 경우였는데, 이건 **기획서가 로드맵보다 넓은** 경우다. 계획 문서를 훑어 로드맵에
> 안 내려온 항목이 더 있는지는 확인하지 않았다 — 별건이다.

### 완료 (2026-08-02, ADR-0030)

- [x] **거래 처리 자체는 큐로 보내지 않는다.** 기획서 그대로 하면 구매가 비동기가
  되고 `201 → 202` 계약 변경 + **ADR-0020이 26,600건에서 검증한 오버셀 단언**이
  응답 시점에 성립하지 않는다. 큐가 맡는 것은 기획서 4단계(체결 후 알림)다
- [x] **`AFTER_COMMIT` 발행** — 트랜잭션 안에서 보내면 롤백된 거래의 알림이 나간다
- [x] **fail-open** — 브로커가 죽어도 구매는 성공한다. 단 지연도 같이 막아야 해서
  `connection-timeout: 2s` + 템플릿 재시도 비활성. 클라이언트 기본값 60초를 그대로
  두면 "성공은 하는데 1분 걸린다"가 된다
- [x] **멱등성** — `(recipient_id, trade_id)` unique. 그리고 `DuplicateKeyException`만
  잡는다(상위 타입을 잡으면 FK 위반까지 삼킨다)
- [x] **DLQ + 재시도 3회** — 소비 실패가 무한 재전달이 되지 않는다
- [x] 알림 조회 API + 헤더 뱃지, 백엔드 테스트 **29 → 36건**

**판정선 8개 전부 통과, 그중 4개는 실패를 인위로 만들어 확인했다.**

| # | 기준 | 결과 |
|---|---|---|
| 1 | 오버셀 0 단언 유지 | 재고 감소 2,752 = 성공 응답 수 |
| 2 | 큐 배수 후 구매 수 == 알림 수 | 5 → 5 |
| 3 | 롤백되면 발행 안 됨 ※ | 통과 (+ 대조군) |
| 4 | 2회 소비 → 알림 1건 ※ | 통과 |
| 5 | 브로커 정지 시 성공 + 지연 상한 ※ | 201, 증가 7ms ≤ 2,000ms |
| 6 | 3회 실패 → DLQ 1건 ※ | 원본 0 / DLQ 1 |
| 7 | 재전달이 DLQ를 안 채움 | DLQ 0 |
| 8 | 시드 재적용 FK 위반 없음 | 통과 |

### 이 라운드가 드러낸 것

- **내 롤백 테스트가 공허했다.** `AFTER_COMMIT`을 트랜잭션 내부 발행으로 바꿔도
  통과했다 — `quantity=99`가 **발행 지점 이전**의 재고 확인에서 거절되기 때문이다.
  "롤백됐는데 발행 안 됨"이 아니라 "발행 지점에 도달조차 안 함"을 재고 있었다.
  고친 뒤 다시 뮤테이션을 넣으니 정확히 그 한 건만 실패했다
- **`DataIntegrityViolationException`을 잡으면 FK 위반까지 삼킨다.** 판정 6(DLQ)을
  어떻게 만들지 고민하다 발견했다 — **검증 방법을 설계하는 과정이 설계 결함을 드러냈다**
- 컨슈머가 할 수 있는 일은 **알림 하나뿐**이었다. 시세 갱신·이상탐지 트리거는
  둘 다 "합성 코퍼스를 읽는다"에 막혀 있다

### 남긴 것 (트리거 있음)

| 항목 | 트리거 |
|---|---|
| outbox 패턴 | 알림 유실이 실제로 문제가 될 때 — 지금 fail-open은 의도된 선택이다 |
| 시세 갱신 소비자 | 시세 예측이 Postgres 거래를 읽게 될 때 (id 공간 (C)) |
| 이상거래 탐지 트리거 | 같은 조건 |
| DLQ 감시 | DLQ가 0이 아닌 상태가 관측될 때. 지금은 사람이 보는 신호다 |
| 기획서 대비 로드맵 전수 점검 | 이번처럼 "기획서에만 있는 항목"이 또 나오면 |

| `BadCredentialsException` 이 **500** | Security 예외 변환은 필터 체인 것만 다룬다 |

| 판정 1의 검사가 **약했다** | 401 은 "핸들러 없음"의 증거가 아니다 → 유효 토큰을 들고 가게 고침 |
| compose `environment` 누락 **3회** | `RABBITMQ_HOST`·`DEMO_PASSWORD`·`DB_PASSWORD`. **셸 환경은 자동 상속이 아니다** |
| `ports: []` 가 포트를 **안 지운다** | Compose 는 시퀀스를 이어 붙인다 → `!override` |
| 비밀번호 주입이 **시드에 덮인다** | `db-seed` 가 backend healthy 뒤에 돈다 |

마지막 둘은 **기동 후 `restart backend web`** 으로 해결되고, 잊으면
`verify-deploy.sh` 의 로그인 검사가 401/502 로 지목한다.

> **"검사가 약했다"는 새 하위분류다.** 틀린 게 아니라 **다른 이유로 맞는** 경우이고,
> 뮤테이션으로도 잘 안 잡힌다 — [[검사-자체가-틀린-사례들]] 사례 10.

## Phase 9b: ARM 대응 (2026-08-04, ADR-0032)

- [x] **리랭커 arm64 재양자화 — 측정하고 기각했다.** 사전 등록한 판정선
  ("top-5 순위 일치")이 **0/5 로 실패**했다. top-1 은 5/5 일치하는데 2~5위가
  매번 재배열된다(점수차 0.064~0.268).
  - 기각 사유: **기록된 품질 수치가 전부 avx2 기준**이다(하드 필터 50→14,
    Recall@1 0.148→0.389). 바꿀 이유인 "ARM 에서 더 빠를 수 있다"는 **미측정**이라,
    재보지 않은 이득을 위해 재본 수치를 버리는 거래가 된다
  - 되살릴 조건: ARM 에서 리랭킹이 병목으로 지목될 때. **품질 재측정이 전환의 일부**
- [x] **avx2 모델이 aarch64 에서 실행되는지 직접 확인** — 유지 결정의 전제가
  주장이 아니라 측정이 되게. `machine=aarch64`, output shape `(4,1)`, finite
- [x] 베이스 이미지 9종 arm64 제공 확인 (ES 포함), **web·backend** arm64 빌드 확인
- [x] 배포 절차 문서 (`docs/07-배포/배포-절차.md`)
- [x] **AI 이미지 arm64 교차 빌드 — 완주했다** (2026-08-04, 디스크 정리 후).
  처음엔 디스크가 차서 못 했고(C: 여유 2.56GB) "여유가 생기면"으로 등록해뒀던 항목.
  - pip 계층 **1041.5s**, exit 0. `--output type=cacheonly` — 3GB 이미지를 x86
    디스크에 남길 이유가 없다. 알고 싶은 건 "빌드가 되는가"뿐이다
  - **진짜 위험은 빌드가 아니라 휠이었다.** `Dockerfile` 이 torch 를
    `download.pytorch.org/whl/cpu` 에서 받는데 **그 인덱스의 aarch64 제공 여부가
    확인된 적이 없었다** → `cp311 manylinux_2_28_aarch64` 가 **2.7.0부터** 있고
    실제로 **`torch-2.13.0+cpu`** 로 해석된다
  - 나머지 컴파일 의존성도 전부 aarch64 휠(`onnxruntime-1.28.0` `numpy` `scipy`
    `tokenizers` `pyarrow` `cryptography` …)
  - **배포 방법은 안 바뀐다**(대상에서 빌드). 바뀐 것은 근거다 — "베이스가 arm64를
    제공하니 되겠지"에서 "된다"로
- [x] **부작용 하나를 문서로 남겼다** — 이 빌드의 캐시(19.35GB)가 호스트를 채워
  **Docker 데몬을 죽였다.** 게스트 증상은 `read-only file system` 이라 원인을
  가리키지 않는다. `docs/05-Troubleshooting/도커-디스크-고갈-vhdx-압축.md`
  - **prune 은 vhdx 를 줄이지 않는다** — 안에서 19.35GB를 지워도 호스트 여유는
    1.3GB만 늘었고, 나머지 15.7GB는 `diskpart compact vdisk` 에서 나왔다

## Phase 9c: 배포 전 전체 점검 (2026-08-04, ADR-0033)

배포 직전 비판적 점검. **테스트는 전부 초록이었고 시크릿도 깨끗했는데, 공개하면
안 되는 상태였다.** 차단 결함 2건은 둘 다 **각 라운드의 판정선을 통과한 코드**에서
나왔다 — 판정선은 그 라운드가 바꾼 것을 검사하지, 라운드 사이의 틈을 검사하지 않는다.

- [x] **무인증 LLM 경로 제거.** `/api/ai/llm/test` 가 **토큰 없이 200** 이었다
      (다른 5개 경로는 전부 401). 익명 요청이 임의 프롬프트로 실제 OpenAI 호출에
      성공했고, 비용 방어 3계층이 전부 `/api/assistant` 에 걸려 있어 **통째로
      우회**됐다. Phase 2 유물이라 이후 어느 라운드도 쳐다보지 않았다
  - 라우터를 지우는 것으로 끝내지 않았다 — **원인은 파일이 아니라 "개별 `Depends`
    는 빠뜨려도 조용하다"는 방식**이다. `test_route_auth_coverage.py` 가 인증 없는
    경로의 **부재**를 고정한다 (AI 121 → **125**)
- [x] **nginx가 `X-Forwarded-For` 를 붙인다.** ADR-0031은 "신뢰 목록의 출처에서 온
      XFF만 읽는다"를 넣었는데 **그 헤더를 쓰는 쪽을 안 만들었다.** nginx는 설정하지
      않은 헤더를 지우지 않으므로 클라이언트 위조값이 그대로 통과했다
  - 실측: **위조 40회 전부 통과** / 대조군(헤더 없음) **31번째 429**
  - 즉 **런북대로 `TRUSTED_PROXIES` 를 채우면 한도가 사라졌다.** 안 채우면 안전한
    대신 한도가 전체 합계 — **안전한 설정과 올바른 설정이 양립하지 않았다**
- [x] **죽어 있던 검사 4종 복구.** `demo-token` 제거 후 호출부를 안 고쳐
      `verify-container.sh`·`verify-mq.sh`·k6 2종이 전부 실패했다. **오버셀 0건
      단언을 다시 돌릴 방법이 없었고**, 배포 절차 4단계가 그중 하나를 지시하고 있었다
- [x] `.env.example` 에 `DEMO_PASSWORD`·`ADMIN_PASSWORD`·`TRUSTED_PROXIES` 추가
- [x] 문서 정정 — API 명세(`demo-token` 절 → `login`), README 자기모순,
      nginx 주석, `load/README.md`, ADR-0031 정정 블록
- [x] 사례집 **12·13번** — "엉뚱한 대상"이 **다섯 번째 방향**이다. 검사 대상을
      망가뜨리면 검사가 정직하게 실패하므로 **뮤테이션으로도 안 잡힌다**

## Phase 9d: 배포 전 점검 2회차 (2026-08-04, ADR-0034)

같은 절차를 한 바퀴 더 돌렸다. 이번엔 **1회차에서 얕게 본 영역**에 무게를 뒀고,
그중 하나가 **테넌트 격리** — 간판 기능인데 두 테넌트를 만들어 확인한 적이 없었다.
**만들자마자 결함이 나왔다.**

- [x] **`/error` 를 `PUBLIC_PATHS` 에 추가.** 없으면 Spring Security 6+ 가 ERROR
      디스패치를 필터링해 **비인증 경로의 400·500이 전부 401** 이 된다. 대조군:
      유효 토큰으로 없는 경로는 정상 404
  - **이 한 줄의 부재가 아래 둘을 가리고 있었다** — 서버 오류가 "비밀번호가 틀렸다"로 보였다
- [x] **로그인이 `tenantCode` 를 받는다.** 제약이 `(tenant_id, username)` 인데 조회는
      `findByUsername` 하나였다. 두 번째 테넌트에 같은 아이디를 넣자
      `NonUniqueResultException` → 401, 즉 **그 계정은 영구 로그인 불가**
  - 전역 유니크(a)를 기각한 이유: **설계를 버그에 맞추는 것**이고, 나중에 (b)를 하면서
    운영 DB 제약 마이그레이션까지 얹게 된다
- [x] **짧은 `JWT_SECRET` 이 기동을 막는다.** 주석은 "짧으면 즉시 실패"라고 했지만
      `SecretKeySpec` 은 길이를 안 본다 — 5바이트로 **healthy 기동** 후 로그인만 401 이었다.
      `SecretGuard`(prod 전용)가 아니라 `SecurityConfig` 생성자에 뒀다 — 모든 프로파일에서 고장이므로
- [x] **사례 14** — F1을 고치자 검사 둘이 **틀린 이유로 통과하고 있었음**이 드러났다.
      한글 인자가 cp949로 깨져 400이 나가던 것을 마스킹이 401로 바꿔놨고, 검사는
      401을 기대해 통과했다. **비밀번호 검증을 한 번도 재본 적이 없었다**

검증: `verify-auth.sh` **11/11** · container 10/10 · mq 8/8 · **오버셀 0건**
(2,930 = 2,929 + 1) · 백엔드 **46**(+4) · AI 125 · 프론트 빌드

## Phase 9e: 배포 전 점검 3회차 (2026-08-04, ADR-0035)

앞의 두 회차가 안 건드린 영역을 겨냥했다 — 아이템 CRUD 인가(IDOR), 입력 크기,
관측성, 프론트 세션. **보안 구멍은 나오지 않았다.** 인가·격리·시크릿은 깨끗했고
(`getItem(tenantId,…)` + `requireSeller`, 메트릭 라벨 유한, 로그 시크릿 0건),
나온 것은 **크기**에 관한 것이다.

- [x] **질의 길이 상한 500자.** 한도 3계층이 전부 **요청 수**를 세는데 길이가 자유라,
      한도를 지키면서 하루 예산을 배수로 늘릴 수 있었다 — 실측 **19,800자 → 200 OK,
      16.4초**(정상 ~50자 / 4.5초)
  - 발견 단서는 같은 DTO 안의 비대칭이다: `size` 는 `ge=1, le=50` 인데 `query` 는 무제한.
    **저자가 상한을 둘 줄 안다는 증거가 옆 줄에 있으므로 누락이다**
  - 500자 근거: 임베딩 **128토큰** · 리랭커 **256토큰** 에서 자르므로 그 너머는 LLM
    요금만 늘린다. 데이터셋 질의 547건의 **최댓값이 33자**(15배 여유)
- [x] **DB 제약을 DTO 에 반영.** 컬럼이 `varchar(200)` 인데 `@Size` 가 없어 201자가
      검증을 통과하고 INSERT 에서 터졌다(**300자 → 500**). 수정 요청에도 같이 걸었다 —
      등록만 막으면 같은 결함이 경로 하나로 남는다
- [x] **토큰 만료 처리.** ADR-0023 설계안의 "재발급 후 재시도"가 로그인이 진짜
      비밀번호가 되며 **불가능해졌는데 대체 처리가 안 들어갔다.** 세션을 접고 로그인
      화면으로 되돌린다. **로그인 실패 401 과 세션 만료 401 을 갈랐다**
- [x] 문서 드리프트 — API 명세의 `/api/search` 가 아직 `tenant_code`(필수)라고 적고
      있었다(ADR-0022 가 제거한 값)

검증: 19,800자·501자 → **422** / 201자 → **400** / 경계 안(500자·200자)은 통과 ·
verify-auth **11/11** · container **10/10** · AI **137**(+12) · 백엔드 **49**(+3)

> **수확 곡선**: 1회차 보안 구멍 2건 → 2회차 진단 불가능 3건 → 3회차 비용·견고성 3건
> (전부 fail-safe 쪽). **4회차는 하지 않는다** — 남은 것은 실환경에서만 드러난다.

## Phase 10: 실배포 (2026-08-05)

**공개 주소: `https://item-exchange.duckdns.org`**

절차 문서가 처음 실행됐고 **넷이 틀렸다.** 넷 다 한 가지 가정에서 나왔다 —
**"이 호스트는 우리 것이다."** 실제 대상은 이전 프로젝트(`shoppingmall.duckdns.org`)가
systemd 로 돌고 있는 박스였다.

- [x] **디스크 확장** — 여유 14G 로는 부족(필요 20G, 빌드 캐시가 10G+). 부트 볼륨
      49G → 97G 온라인 확장. **빠듯하게 안 간 이유: 실패하면 남의 서비스가 같이 죽는다**
- [x] **`verify-deploy.sh` 수정** — `curl localhost:8080` 으로 "닫혔는가"를 보다가
      **남의 프로세스를 우리 것으로 오인**했다. 8080/8000 거짓 실패, **80 거짓 통과**
  - 고침: `docker inspect` 로 **우리 컨테이너의 게시 포트**를 직접 묻는다 + 응답 **내용** 확인
  - 고치다 또 틀릴 뻔했다 — `published()` 는 컨테이너가 없어도 빈 값이라 사전 확인 목록에 7종 전부 추가
- [x] **검증 스크립트가 리눅스에서 아예 못 돌았다** — `python` 은 우분투에 없다(`python3` 뿐).
      **여섯 라운드 동안 Windows 에서만 돌려봤다.** 증상이 "로그인 실패 (HTTP 200)" 이라
      원인이 안 보였다. 고치면서 Windows 스토어 스텁 `python3` 때문에 회귀할 뻔해,
      **이름이 아니라 실행 여부로** 고르게 했다
- [x] **2단 프록시 구성** — 80/443 이 점유돼 컨테이너 nginx 를 `127.0.0.1:8081` 에 묶고
      호스트 nginx 가 도메인 분기 + TLS 종단. `proxy_read_timeout 120s` 를 **앞단에도**
      (에이전트 분기 7~25초라 기본 60초면 앞단에서 504)
- [x] **검증 38/38** — deploy 17 · auth 11 · container 10, 그리고 **공개 HTTPS 경로로 10/10**
  - **AI 4분기가 전부 ARM 에서 돈다.** 특히 리랭커 — ADR-0032 가 QEMU 로만 확인했던
    "avx2 가 aarch64 에서 실행된다"가 **진짜 하드웨어에서 확인**됐다
  - 빌드도 예측대로 빨랐다(에뮬레이션 pip 계층 1041.5초 → 네이티브는 훨씬 짧음)

## Phase 11: 도메인 밖 질의 거절 (2026-08-07, ADR-0039)

사용자가 배포된 화면에 `"삼성전자 주식 어때?"` 를 넣었더니 **다른 아이템의 진짜
예측값에 주어만 바꿔** 답했다. 라우터의 출력 공간에 "내 도메인이 아니다" 가 없고,
**kNN 은 어떤 질의에도 k 건을 돌려주기** 때문이다.

- [x] **도메인 밖 38건 + 경계 16건 수작업 평가셋** (`app/corpus/out_of_domain.py`).
      **양방향을 같이 잰다** — 거절만 재면 "전부 거절" 이 만점을 받는다
- [x] **어느 분기를 막을지 먼저 무료로 측정** — 라우터에 태워보니
      검색·시세 22 / 복합 7 / **FAQ 9**. FAQ 는 `_DEFAULT_FAQ` 가 이미 범위를
      밝히며 거절해서 **손대지 않았다**
- [x] **판정을 별도 호출로 분리하고 `asyncio.gather` 로 병렬** — 처음엔
      `understand_query` 스키마에 필드를 얹었는데 **2회 측정 2회 기각**
- [x] MCP `search_items` 가 빈 목록 대신 **문장으로 된 안내**를 돌려준다
- [x] 캐시 저장 거부 · `outcome="out_of_domain"` 메트릭 · 관측 패널 배지
- [x] `load/verify-container.sh` 판정 1-c — **거절과 대조군을 같이 본다**
- [x] AI 테스트 148 → **174건**, 백엔드 57건 유지

### 이 라운드가 드러낸 것

- **한 호출에 두 일을 시켰더니 둘째가 첫째를 망가뜨렸다.** 재작성 토큰집합
      일치도가 대조군 대비 **-0.234 → -0.248**, 문구를 고쳐도 그대로였다.
      **대조군을 뒀기 때문에만** 알 수 있었다
- **프롬프트에 목록을 주면 목록 밖을 자른다.** 취급 품목을 열거하니 오거부가
      4.13% → 5.30% 로 올랐다. 같이 넣은 "플레이 방법은 NO" 는 의미가 아니라
      `스킬`·`강화` 라는 **낱말**에 걸렸다 — 정규식에서 두 번 겪은 실패의 재연
- **오거부의 정체가 회차마다 바뀌었다** — 시세 질문 → 흐릿한 대상 → 게임 은어.
      매번 **걸린 표본을 읽어야만** 알 수 있었고, 숫자만으로는 방향이 안 잡혔다
- **검사가 또 틀렸다 (사례 19)** — 845회 중 443회가 429 로 죽었는데 판정을 냈다.
      실패를 `None` 으로 두고 한 지표는 `is not False`, 다른 지표는 `is False` 로
      세는 바람에 **같은 실패가 오보와 침묵을 동시에** 냈다
- **API 명세 드리프트** — `item_search` 의 `llm_calls` 가 ADR-0036 이후로 1인데
      문서는 2로 남아 있었다. 이번에 2가 되면서 값은 맞아졌지만 **이유가 달랐다**
