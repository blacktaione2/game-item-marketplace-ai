# 게임 아이템 통합 거래 플랫폼 - 최종 기획서

---

## 1. 프로젝트 개요

여러 게임사(테넌트)의 아이템·계정·게임머니를 하나의 플랫폼에서 거래하는 AI 기반 통합 거래소.
"LLM API를 wrapping하는 서비스"가 아니라, **검색 AI + 예측 AI + 이상탐지 AI + Agent + LLM을 요청 유형별로 분기하여 통합한 AI 시스템**으로 설계.

- **차별점**: 게임 GM 경력(약 2년)을 도메인 전문성으로 연결
- **설계 원칙**: 기능을 나열하지 않고, 요청 유형별 파이프라인 분기로 지연시간·비용을 통제. 현업에서 실제로 쓰이는 기술 스택을 우선 채택

---

## 2. 핵심 요구사항

| 항목 | 내용 |
|---|---|
| AI 기능 | 메인 기능, 자체 학습/파인튜닝 모델 + LLM을 요청 유형별로 분기 결합 |
| 프론트/백 분리 | React(SPA) ↔ Spring Boot(REST API) |
| 대규모 트래픽 | 실 사용에 가까운 DB/트래픽 처리 구조 |
| 관계형 DB | PostgreSQL |
| 검색 엔진 | Elasticsearch (분산 클러스터, 샤딩, 하이브리드 검색) |
| 컨테이너화 | Docker 사용 |

## 3. 기술 스택

### Backend
- Spring Boot 3.x (Java 21)
- FastAPI (Python, AI 서버, async/await 엄격 적용)
- **PostgreSQL** (관계형 데이터)

### Frontend
- React (컴포넌트/라이브러리 기반 SPA)

### 관계형 DB: PostgreSQL
- **선택 이유**: 오픈소스로 라이선스/운영 부담이 없고, 이전 프로젝트(Oracle 23ai)와 다른 DB 경험을 포트폴리오에 추가해 기술 폭을 넓힘. RAC/Data Guard 같은 Oracle 엔터프라이즈 기능은 이 규모에서 활용할 일이 없어 오버스펙
- pgvector는 메인 검색에는 쓰지 않음(검색은 Elasticsearch 담당). 필요 시 소규모 실험/시맨틱 캐시 보조 저장소 정도로만 고려

### 검색 엔진: Elasticsearch
- **선택 이유**: 현업 채용 연관성이 가장 높은 검색엔진. 별도 클러스터로 구성해 샤딩/노드 분산을 실제로 보여줄 수 있음
- **하이브리드 검색**: BM25 + kNN(dense_vector)을 RRF(Reciprocal Rank Fusion)로 융합
- **멀티테넌시**: 게임사별 **인덱스 분리** 방식 (물리적 완전 격리는 아니지만 인덱스 단위로 샤드/레플리카 독립 구성 가능)
- **샤딩/분산 클러스터**: 게임사별 인덱스마다 샤드 수를 다르게 구성, 최소 3노드 클러스터로 분산 구성

### AI / ML
- **임베딩 모델 파인튜닝**: sentence-transformers + Contrastive Learning + **Hard Negative Mining**(`+8` vs `+9` 등 미세 옵션 차이 대조 학습)
- **Hard Negative 자동 생성**: LLM으로 Positive/Negative/Hard Negative 페어 자동 생성
- **Cross-Encoder Re-ranking**: 경량 모델(ms-marco-MiniLM 계열) + **ONNX 변환 + int8 양자화** 필수, Top-15~20으로 제한, 배치 처리
- **Query Rewrite + Text-to-DSL 통합**: 검색어 동의어 확장과 필터 조건(JSON) 추출을 LLM 호출 1회로 처리
- **LSTM/Transformer 시계열 모델**: 아이템 시세 예측 (자체 학습, from-scratch)
- **Cold Start 백오프 알고리즘**: 거래량 부족 아이템은 Elasticsearch로 유사 아이템군 검색 후 트렌드 가중치 상속
- **Autoencoder**: 거래 이상탐지 (재구성 오차 기반 설명가능성 확보)
- **경량 Intent Router**: 룰 기반(정규식/키워드) 우선 분기 → 애매한 요청만 KoELECTRA 파인튜닝 모델로 확장
- **CLIP(제로샷) + OCR**: 아이템 스크린샷 위조 검증
- **LLM (OpenAI API)**: 자연어 설명 생성, Agentic tool-calling, 조건부 Reflection
- **RAGAS**: RAG 품질 정량 평가 (파인튜닝 전/후, 리랭킹 전/후 비교)
- **Semantic Cache**: Redis + 임베딩 유사도 기반 LLM 호출 생략

### 트래픽/인프라
- Redis: 분산 락, 재고/입찰 원자적 차감, 캐싱, 시맨틱 캐싱
- MQ: RabbitMQ
- ONNX Runtime: 모델 추론 경량화
- Docker (컨테이너화, docker-compose)

## 4. AI 파이프라인 아키텍처 (요청 유형별 분기)

```
사용자 요청
    │
    ▼
[경량 Intent Router] ── 룰 기반 우선, 애매하면 KoELECTRA
    │
    ├── 단순 FAQ/Small Talk → 즉시 응답 (LLM 호출 없음)
    │
    ├── 검색 질의
    │     → Query Rewrite + Text-to-DSL (LLM 1회)
    │     → Elasticsearch Hybrid Search (BM25+kNN, RRF, Top-15~20)
    │     → Cross-Encoder Re-ranking (ONNX 양자화)
    │     → LLM 설명 생성
    │
    ├── 시세 문의
    │     → 거래량 충분? LSTM/Transformer 예측
    │     → 거래량 부족? Cold Start 백오프
    │     → LLM 설명 생성
    │
    ├── 이상 거래 확인
    │     → Autoencoder 재구성 오차 계산 → 피처별 기여도 분해 → LLM 설명 생성
    │
    └── 복합 질의 → Agentic Tool-Calling → 확신도 낮을 시 조건부 Reflection → LLM 최종 설명
```

**모든 분기 이전에 Semantic Cache 체크**

## 5. 대규모 트래픽 처리 시나리오

**예시: 인기 아이템 동시 입찰/즉시구매**

1. Redis 분산 락으로 아이템 선점
2. 선점 성공 → MQ에 거래 처리 메시지 발행
3. 컨슈머가 순서대로 소비하며 DB 트랜잭션 처리
4. 거래 완료 후 알림/시세 갱신은 비동기 처리

**검증**: k6 / nGrinder 부하 테스트로 실측 응답시간/처리량 수치 확보

## 6. 인프라 배포 전략 (오라클 클라우드 ARM, 4 OCPU/24GB)

- 이전 프로젝트와 상시 동시 구동하지 않고 **온디맨드 전환** 방식 채택
- Elasticsearch는 JVM 기반으로 메모리 사용량이 큼 → 힙 크기 명시적 제한, 3노드 클러스터는 시연 시점에만 기동
- 모델은 항시 상주시키지 않고 lazy loading

## 10. 포트폴리오 스토리 포인트

1. 전직 게임 GM 경력 → 도메인 이해도
2. 요청 유형별 AI 파이프라인 분기 설계 + 비용·지연시간 고려 → "AI API 통합자"가 아닌 AI 서비스 개발자 포지셔닝
3. Oracle(이전 프로젝트) vs PostgreSQL(이번 프로젝트) — 두 DB 경험으로 기술 폭 확보, 선택 근거(라이선스/운영 부담, 채용시장) 설명 가능
4. Elasticsearch 인덱스 분리 방식을 택한 이유(물리적 격리 완전성 vs 현업 표준 스택 트레이드오프)
5. Autoencoder를 택한 이유(설명가능성 리스크 최소화)
6. RAG 품질을 정량 지표(RAGAS)로 증명
7. 제한된 인프라(ARM, 무GPU, 4 OCPU/24GB 공유)에서 온디맨드 전환·경량화로 대응한 엔지니어링 판단
